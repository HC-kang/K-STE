가장 유력한 원인은 2.0.0에서 추가된 `exports` 필드입니다. `exports`가 있으면 Node는 목록에 적힌 경로만 가져올 수 있습니다. 목록에 없는 `@company/ui/button`은 찾을 수 없으므로 CI에서 에러가 납니다. 로컬 빌드가 성공하는 것은 로컬 `node_modules`가 3일 전 이전에 설치된 1.4.0일 수 있기 때문입니다. 아직 확인하지 않은 가설이므로 아래 방법으로 검증해야 합니다.

## 원인 가설

1. **로컬은 2.0.0으로 빌드한 적이 없을 수 있습니다.** 로컬 `node_modules`가 1.4.0 그대로라면 로컬 성공은 2.0.0 호환성의 근거가 되지 않습니다.
2. **CI는 2.0.0을 설치했을 가능성이 높습니다.** 2.0.0의 `exports`에 `./button` 경로가 없거나 이름이 바뀌었다면 위 에러와 일치합니다.
3. **Node 18과 20의 차이는 주된 원인일 가능성이 낮습니다.** Node 18도 `exports` 필드를 지원합니다. 다만 두 버전의 해석 차이는 확인하지 않았습니다.

## 검증 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인하십시오.
2. CI 워크플로에 `npm ls @company/ui` 단계를 추가해 CI가 설치한 버전을 확인하십시오.
3. 2.0.0 패키지의 `package.json`에서 `exports` 항목을 열어 `./button` 경로가 있는지 확인하십시오.
4. 로컬에서 Node 18로 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드하십시오. 이때도 실패하면 Node 버전 차이는 원인에서 제외됩니다.
5. CI 캐시는 `package-lock.json` 해시가 같으면 이전 설치 결과를 복원합니다. 복원된 `node_modules`가 실제로 2.0.0인지 2번 단계로 확인하십시오. 또한 커밋된 lock 파일이 2.0.0을 반영하는지 확인하십시오.

## 수정 방향

- 원인이 확인되면 2.0.0의 `exports`에 노출된 경로로 import 문을 바꿉니다.
- 경로가 노출되어 있지 않다면 `@company/ui` 담당자에게 `exports` 추가를 요청하는 방법이 있습니다.
- 빌드를 빨리 복구해야 하면 1.4.0으로 되돌려 빌드가 통과하는지 확인하는 방법도 있습니다.

## PM용 요약

빌드 실패는 UI 라이브러리 2.0.0 업그레이드와 관련된 것으로 보입니다. 로컬 성공은 로컬 설치본이 옛 버전이라서일 가능성이 높습니다. 원인을 확정하려면 위 검증 1번부터 3번까지를 먼저 진행하십시오. 빌드를 빨리 복구해야 하면 롤백 여부를 함께 판단하십시오.
