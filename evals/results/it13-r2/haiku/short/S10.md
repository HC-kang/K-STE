원인은 2.0.0에 새로 추가된 `exports` 필드일 가능성이 높습니다. `exports` 필드(패키지가 외부에 공개하는 import 경로 목록)가 있으면 목록에 없는 경로는 import할 수 없습니다. 로컬 빌드가 통과한 이유는 `node_modules`가 업그레이드 전에 설치된 것이라 1.4.0을 쓰고 있을 가능성이 높기 때문입니다. 두 판단 모두 추론이므로 아래 순서로 확인해야 합니다.

## 확인된 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0의 package.json에 `exports` 필드가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

## 원인 후보

에러 문구 `Cannot find module`은 `exports`가 경로를 막은 경우와 파일이 실제로 없는 경우를 모두 나타낼 수 있습니다. 그래서 두 경우를 구분하는 확인이 먼저 필요합니다.

| 후보 | 근거 | 현재 판단 | 확인 방법 |
|---|---|---|---|
| 2.0.0의 `exports`가 `./button` 경로를 막음 | `exports` 추가와 업그레이드가 같은 릴리스에 있음 | 가능성 높음(추론) | 2.0.0 package.json의 `exports` 항목 확인 |
| 로컬 `node_modules`에 1.4.0이 남아 로컬만 통과함 | 로컬 설치가 업그레이드보다 먼저 이루어짐 | 가능성 높음(추론) | 로컬에서 `npm ls @company/ui` 실행 |
| 2.0.0에서 button 파일의 위치나 이름이 바뀌었거나 누락됨 | 파일이 없어도 같은 에러가 발생함 | 확인 필요 | 설치된 패키지의 파일 목록 확인 |
| Node 18과 20의 차이 | 실행 환경이 다름 | 가능성 낮음. 두 버전 모두 `exports`를 지원함 | 로컬에서 Node 18로 빌드 |
| 캐시가 오래된 설치본을 복원함 | 캐시 키가 lock 파일 해시임 | 가능성 낮음. lock 파일이 바뀌면 캐시 키도 바뀜 | CI의 캐시 복원 로그 확인 |

## 확인 순서

1. 로컬과 CI에서 `@company/ui`의 실제 설치 버전을 확인합니다. 로컬은 `npm ls @company/ui`로, CI는 설치 단계 로그로 확인합니다.
2. 2.0.0 패키지의 `exports` 항목에 `./button`이 있는지 확인합니다.
3. 코드에서 `@company/ui/button`을 import하는 위치를 검색합니다.
4. 로컬 `node_modules`를 삭제하고 `npm ci`로 다시 설치한 뒤 빌드합니다. 이때 CI와 같은 에러가 재현되면 로컬 설치본이 원인이었다는 추론이 강화됩니다.
