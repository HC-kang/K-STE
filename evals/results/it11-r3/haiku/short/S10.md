## 요약

원인은 아직 확정되지 않았다. 현재 가장 유력한 가설은 로컬 `node_modules`에 1.4.0이 남아 있어 로컬 빌드가 2.0.0을 거치지 않았다는 것이다. 이 내용은 추론이며, 아직 확인하지 않았다.

## 확인된 사실

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에서 패키지에 `exports` 필드가 추가됐다.
- CI는 Node 18을 쓰고, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`의 해시다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치됐다.
- CI 빌드는 `Cannot find module '@company/ui/button'` 에러로 실패하고, 로컬 빌드는 성공한다.

## 추론

가장 유력한 원인은 로컬 빌드의 성공이 2.0.0 검증이 아닐 수 있다는 점이다. 로컬 `node_modules`가 업그레이드 이전에 설치됐으므로 1.4.0이 그대로 남아 있을 가능성이 높다. 1.4.0에는 `exports` 제한이 없어 `@company/ui/button` 경로가 그대로 해석된다. 따라서 로컬과 CI는 서로 다른 버전의 패키지로 빌드하고 있을 수 있다.

두 번째 가능성은 2.0.0의 `exports` 필드가 `./button` 경로를 노출하지 않은 경우다. 이때 Node는 해당 하위 경로를 막는다.

Node 18과 20의 차이는 가능성이 낮아 보인다. 두 버전 모두 `exports` 필드를 지원하기 때문이다. 다만 Next.js 번들러의 해석 방식에서 차이가 날 수 있으므로 배제하지는 않는다.

## 미확인

- CI가 실제로 설치한 `@company/ui`의 버전
- 로컬 `node_modules`에 실제로 남아 있는 버전
- 2.0.0 `exports` 필드에 `./button` 경로가 있는지 여부
- CI 캐시가 hit됐는지, `restore-keys`가 설정돼 있는지 여부
- Node의 `exports` 차단 에러는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`로 나오는데, 이 빌드에서는 `Cannot find module`로 나온다. 이 메시지 차이가 번들러 동작 때문인지 여부

이 분석은 코드나 CI를 실행하지 않고 제공된 정보만으로 작성했다.

## 확인 방법

| 확인 항목 | 확인 방법 | 결과의 의미 |
|---|---|---|
| 로컬 설치 버전 | 로컬에서 `npm ls @company/ui` 실행 | 1.4.0이면 로컬 빌드는 2.0.0을 검증하지 않은 것이다. |
| CI 설치 버전 | CI에 `npm ls @company/ui` 단계를 추가하고 로그 확인 | 2.0.0이 아니면 설치 단계나 캐시 문제다. |
| `exports` 내용 | 2.0.0 패키지의 `package.json`에서 `exports` 확인 | `./button`이 없으면 경로 노출 문제다. |
| 캐시 상태 | CI 로그에서 cache hit 여부와 `restore-keys` 설정 확인 | hit이고 오래된 `node_modules`가 복원됐다면 캐시가 원인이다. |
| Node 버전 | Node 18로 전환한 뒤 `rm -rf node_modules && npm ci`를 실행하고 빌드 | 여기서 실패하면 Node 버전 차이가 원인 후보가 된다. |

## 권장 조치

먼저 로컬의 설치 버전과 2.0.0의 `exports` 내용을 확인하는 것을 권장한다. 두 항목은 비용이 적고 원인을 가장 빨리 좁힐 수 있다.

`exports`에 `./button` 경로가 없다면 `@company/ui` 담당자에게 경로 추가를 요청해야 한다.

원인이 확인되기 전까지 임시 조치로 `@company/ui`를 1.4.0에 고정하는 방안을 검토할 수 있다.
