CI 실패의 가장 유력한 원인은 `@company/ui` 2.0.0이 `exports` 필드(패키지 외부에 공개할 경로를 정하는 설정)를 새로 추가하면서 `button` 하위 경로(`@company/ui/button`처럼 패키지 안의 특정 파일을 가리키는 경로)가 공개 목록에서 빠졌거나 바뀌었기 때문으로 추론된다. 이 분석은 공유된 정보만으로 작성했으며, 저장소, CI 로그, 2.0.0 패키지 내용은 직접 확인하지 않았다.

## 로컬에서만 성공하는 이유

로컬 `node_modules`는 3일 전보다 먼저 설치되었으므로 1.4.0이 그대로 남아 있을 가능성이 높다(추론). 1.4.0에는 `exports` 필드가 없으므로 하위 경로 import가 파일 경로대로 해석되어 성공한다.

CI는 락 파일(`package-lock.json`, 설치할 패키지 버전을 기록한 파일)의 해시를 캐시 키로 쓴다. 락 파일이 3일 전에 바뀌었다면 캐시 키도 바뀌므로 CI는 2.0.0을 새로 설치한다. 그래서 CI에서만 실패한다.

**로컬 빌드 성공을 2.0.0 호환의 근거로 보면 안 된다.** 로컬에는 2.0.0이 설치되어 있지 않을 가능성이 높다.

## 원인 후보 비교

| 후보 | 근거 | 확인 방법 |
|---|---|---|
| 2.0.0 `exports`에 `./button` 경로가 없음 | 에러가 하위 경로 import에서 발생하고, 2.0.0에서 `exports`가 추가됨 | 2.0.0의 `package.json`에서 `exports` 내용을 확인한다 |
| CI 캐시가 1.4.0 `node_modules`를 복원함 | 캐시 키는 락 파일 해시이며, `restore-keys`로 부분 일치 복원을 허용하면 이전 캐시가 쓰일 수 있다 | CI 로그에서 설치된 `@company/ui` 버전과 캐시 적중 키를 확인한다 |
| Node 18과 20 차이 | Node 18과 20 모두 `exports`를 지원하므로 단독 원인일 가능성은 낮다(추론) | CI를 Node 20으로 바꾸거나 로컬을 Node 18로 빌드해 재현한다 |

## 확인이 필요한 항목

에러 문구 `Error: Cannot find module`은 Node 런타임 형식이다. 웹팩 빌드 단계의 에러는 보통 `Module not found`로 표시된다. 따라서 실패 지점이 Next.js 빌드 자체인지, `next.config.js`나 코드 생성 스크립트 같은 Node 프로세스인지 확인이 필요하다(미확인).

또한 3일 전에 락 파일이 실제로 바뀌었는지, 워크플로 파일에 `restore-keys`가 있는지도 확인이 필요하다(미확인).

## 권장 조치

1. CI 로그에서 설치된 `@company/ui` 버전과 실패 지점을 확인한다.
2. 2.0.0의 `exports` 목록에 `./button`이 있는지 확인한다.
3. 2.0.0 경로가 확인되면 코드의 import를 그 경로에 맞춘다. 패키지 측 `exports` 추가가 어렵다면 `@company/ui`를 1.4.0으로 고정하는 방안도 검토한다.
4. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치해 재현한다. CI와 같은 Node 버전으로 재현하면 Node 버전 영향도 함께 확인된다.
