가장 가능성이 큰 원인은 로컬의 `@company/ui`가 아직 1.4.0이라서 로컬 빌드가 통과하고, CI는 2.0.0을 설치해서 실패한다는 것입니다. 2.0.0에 추가된 `exports` 필드(패키지가 외부에 공개하는 경로 목록)에 `./button`이 없으면 `@company/ui/button` import가 막힙니다. 로컬 빌드가 성공했다는 사실만으로는 2.0.0이 정상이라고 볼 수 없습니다.

## 원인 가설

| 가설 | 근거 | 판단 |
|---|---|---|
| 로컬 node_modules가 1.4.0이다 | 로컬 설치가 3일 전보다 먼저이고, 그 뒤 다시 설치했다는 언급이 없음 | 가능성 높음. 설치 버전으로 확인 필요 |
| 2.0.0 `exports`에 `./button` 경로가 없다 | 2.0.0에 `exports`가 추가됐고, 1.4.0에는 없었음 | 가능성 높음. 실패 메커니즘과 맞음 |
| Node 18과 20의 차이 | Node 18과 20 모두 `exports`를 지원함 | 가능성 낮음. 배제하지는 않음 |
| CI 캐시가 구버전 node_modules를 복원함 | 캐시 키가 lock 파일 해시라 lock이 바뀌면 키도 바뀜. 복원 키(restore-keys)가 있으면 다른 캐시가 복원될 수 있음 | 확인 필요 |

## 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인하십시오.
2. 2.0.0의 `node_modules/@company/ui/package.json`에서 `exports` 항목에 `./button`이 있는지 확인하십시오.
3. CI 로그에서 설치된 `@company/ui` 버전과 캐시 복원 여부를 확인하십시오.
4. 로컬에서 `rm -rf node_modules && npm ci`로 깨끗하게 설치한 뒤 빌드하여 실패가 재현되는지 확인하십시오.

## 조치 옵션

- `@company/ui`를 2.0.0으로 유지한다면, 2.0.0의 `exports`에 `./button` 경로를 추가하거나 앱의 import 경로를 `exports`에 있는 경로로 바꿔야 합니다. 어느 쪽이 맞는지는 `@company/ui`를 관리하는 쪽과 정해야 합니다.
- 당장 빌드를 복구해야 하면 `@company/ui`를 1.4.0으로 고정하는 방법이 있습니다. 2.0.0 전환은 그 뒤에 다시 진행해야 합니다.

먼저 4번을 실행해 CI 실패가 로컬에서도 재현되는지 확인하십시오.
