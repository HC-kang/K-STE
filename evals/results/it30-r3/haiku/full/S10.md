가장 가능성이 높은 원인은 로컬 빌드가 1.4.0을 쓰고 CI는 2.0.0을 설치해서, 2.0.0의 `exports` 필드 때문에 `@company/ui/button` 경로가 막히는 것입니다. 실제로 설치된 버전은 아직 확인하지 않았으므로 이것은 추정입니다.

추정의 근거는 다음과 같습니다.

- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다. 그래서 `package.json`을 2.0.0으로 올렸어도 로컬에는 1.4.0이 남아 있을 가능성이 큽니다. 1.4.0에는 `exports` 필드가 없으므로 `@company/ui/button`이 파일 경로로 해석되어 빌드가 성공합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다. 2.0.0 업그레이드로 lockfile이 바뀌었다면 캐시가 무효화되고 CI는 새로 설치하면서 2.0.0을 받습니다. 확인 필요: lockfile이 커밋되었는지, 그리고 CI가 `npm ci`로 설치하는지 `npm install`로 설치하는지 알 수 없습니다.
- 2.0.0의 `exports` 필드는 외부에 노출하는 경로만 허용합니다. 그 목록에 `./button`이 없거나 경로가 바뀌었다면 `@company/ui/button`은 해석되지 않습니다.

두 가지는 원인에서 제외하기 어렵습니다.

- Node 버전 차이(18과 20)는 단독 원인일 가능성이 낮습니다. 두 버전 모두 `exports`를 지원합니다. 다만 직접 확인하지 않았습니다.
- 에러 문구 `Cannot find module`은 Node가 `exports` 차단 시 보통 내는 문구와 다릅니다. 실패를 낸 도구가 Node의 CommonJS 해석기인지, Next.js(webpack)나 TypeScript인지 확인 필요합니다. 도구에 따라 수정 방법이 달라집니다.

확인 순서는 다음과 같습니다.

1. CI 로그에서 `@company/ui`의 설치 버전을 확인하십시오. `npm ls @company/ui` 출력이 가장 확실합니다.
2. 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치한 뒤 빌드를 실행하십시오. 여기서 같은 에러가 나오면 원인은 설치 버전과 `exports` 쪽에 있습니다.
3. 2.0.0 패키지의 `package.json`에서 `exports` 필드에 `./button` 경로가 있는지 확인하십시오.
4. 2번에서 재현되면 Node 18로 로컬 빌드를 돌려 Node 버전의 영향을 따로 확인하십시오.

PM 관점에서 원인이 재현되면 수정 방향은 세 가지입니다. 첫째, 2.0.0 기준의 올바른 import 경로로 바꿉니다. 둘째, 패키지 버전을 1.4.0으로 되돌립니다. 셋째, 패키지 쪽에 `button` 경로를 `exports`에 추가하도록 요청합니다. 어떤 방법을 쓸지는 2.0.0의 `exports` 목록을 본 뒤 정하는 것이 좋습니다.

먼저 CI 로그에서 설치된 `@company/ui` 버전을 확인해 주십시오.
