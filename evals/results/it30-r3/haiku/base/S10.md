# 분석: CI에서만 발생하는 `Cannot find module '@company/ui/button'` 빌드 실패

## 요약

**가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드 추가로 인한 하위 경로 import 깨짐입니다.** 다만 "로컬은 성공한다"는 사실이 이 가설과 맞지 않는 부분이 있어서, 로컬 `node_modules`가 오래된 1.4.0일 가능성을 먼저 확인해야 합니다. 이 가능성이 맞다면 로컬 빌드는 2.0.0을 전혀 검증하지 못한 것입니다.

**신뢰도:** 원인이 패키지 버전 변경과 관련 있다는 판단은 높습니다. 정확한 메커니즘(exports 매핑 누락, 설치 누락, 캐시 복원 등)은 아래 확인 항목으로 좁혀야 합니다.

## 1. 핵심 원인 후보

### 가설 A: `exports` 추가로 하위 경로가 노출되지 않음 (주요 후보)

- 1.4.0은 `exports`가 없어서 `@company/ui/button`이 파일 경로로 그대로 해석됐습니다.
- 2.0.0에서 `exports`가 추가되면, 맵에 명시된 경로만 외부에서 import할 수 있습니다.
- 2.0.0의 `exports`에 `./button`이 없거나 다른 경로로 매핑돼 있으면 import가 실패합니다.
- 이는 semver 기준으로도 메이저 버전 변경(breaking change)에 해당합니다.

### 가설 B: 2.0.0이 설치되었지만 대상 파일이 없음

- `exports`에 `./button`이 있어도 가리키는 파일이 배포 tarball에 없으면 같은 계열의 에러가 납니다.
- 원인은 빌드 산출물 누락, `files` 필드 설정, `.npmignore` 등일 수 있습니다.

### 가설 C: CI의 `node_modules`에 2.0.0이 없음

- CI 캐시 키가 `package-lock.json` 해시라서 lock이 바뀌면 캐시 미스가 나는 것이 정상입니다.
- 하지만 `restore-keys`로 이전 캐시를 폴백 복원하면, 1.4.0이 들어 있는 `node_modules`가 복원될 수 있습니다.
- 이 경우 CI에서도 실제로 어떤 버전이 설치됐는지 확인해야 합니다.

## 2. "로컬은 성공"이 말해주는 것

| 로컬 상황 | 해석 |
|---|---|
| `node_modules`가 3일 전 이전 설치본 (1.4.0) | 로컬은 2.0.0을 쓰지 않았으므로 **성공은 검증이 아님** |
| 로컬이 실제로 2.0.0 사용 | Node 18/20 차이 또는 CI 환경 차이를 의심 |

**현재 정보로는 첫 번째 경우일 가능성이 큽니다.** 3일 전 이전에 설치한 `node_modules`는 1.4.0일 가능성이 높습니다.

### 에러 메시지에 대한 참고

- `Cannot find module`은 Node의 `require`/`import` 해석에서 나오는 메시지입니다.
- Webpack이 번들 중에 실패하면 보통 `Module not found: Can't resolve ...`가 나옵니다.
- 따라서 이 import가 Node 런타임에서 평가되는 코드(예: `next.config.js`, 서버 외부화 패키지, 빌드 스크립트)에 있을 가능성이 있습니다. 어느 파일에서 에러가 났는지 스택 트레이스로 확인하면 좋습니다.

## 3. Node 18 vs 20

- Node 18과 20 모두 `exports`를 지원하므로, Node 버전 자체가 주원인일 가능성은 낮습니다.
- 다만 패키지가 ESM 전용이거나 `require`/`import` 조건부 exports를 쓴다면 Node 버전에 따라 해석 결과가 다를 수 있습니다.
- CI와 로컬의 Node 버전을 맞추는 것은 어떤 경우든 권장합니다.

## 4. 확인 방법 (우선순위 순)

1. **로컬 버전 확인**
   ```bash
   npm ls @company/ui
   ```
   - 1.4.0이면 로컬 성공 결과는 무효입니다. `rm -rf node_modules && npm ci` 후 재빌드하세요.

2. **CI 설치 버전 확인**
   - CI 로그에 `npm ls @company/ui` 결과를 출력하게 하거나, 캐시 복원 여부 로그를 확인하세요.
   - `restore-keys` 사용 여부도 확인하세요.

3. **2.0.0 패키지 구조 확인**
   ```bash
   npm view @company/ui@2.0.0 exports
   npm pack @company/ui@2.0.0   # 내용물 확인 (별도 빈 디렉터리에서 실행)
   ```
   - `exports`에 `./button`이 있는지, 매핑된 파일이 tarball에 있는지 확인하세요.

4. **Node 18에서 직접 재현**
   ```bash
   node -v   # 18인지 확인
   node -e "console.log(require.resolve('@company/ui/button'))"
   ```

## 5. 해결 옵션

| 옵션 | 내용 | 장단점 |
|---|---|---|
| A. import 경로 수정 | 2.0.0 `exports`가 허용하는 경로로 변경 (예: 패키지 루트 export 사용) | 근본 해결, 코드 수정 필요 |
| B. 패키지 측 수정 | `exports`에 `./button` 추가 또는 2.0.0.1 배포 요청 | 소비자 코드 수정 불필요, 패키지 팀 협업 필요 |
| C. 임시 롤백 | `@company/ui`를 1.4.0으로 고정 | 즉시 복구, 기술 부채 누적 |
| D. CI 캐시 정리 | `restore-keys` 제거 또는 캐시 키에 `package.json` 포함 | 캐시로 인한 오동작 방지, 근본 원인 해결은 아님 |

**권장 순서:** 먼저 C로 빌드를 복구하고, 확인 1~3으로 원인을 확정한 뒤 A 또는 B로 영구 해결하세요. 로컬과 CI의 Node 버전도 함께 맞추세요.
