PM에게 보낼 답변입니다.

**로컬 캐시 vs Redis 캐시, 그리고 이번 도입 효과**

**로컬 캐시 (지금 방식)**
- 서버 4대가 각자 상품 목록을 자기 메모리에 복사해 둡니다. 복사본은 5분마다 갱신됩니다.
- 서버마다 복사 시점이 달라서 같은 시각에도 서버마다 다른 가격을 보여줄 수 있습니다.
- 가격을 바꾸면 서버 4대가 각자 복사본을 갱신하는 시점이 달라서, 고객에게 반영되기까지 최대 5분이 걸리고 그 사이 가격이 들쭉날쭉할 수 있습니다.

**Redis 캐시 (이번 도입 방식)**
- 서버 4대가 함께 쓰는 공용 캐시 서버 1대를 둡니다. 상품 정보가 한 곳에만 있습니다.
- 서버 4대가 항상 같은 가격을 보게 됩니다.
- 가격을 바꾸면 공용 캐시를 한 번만 고치면 되고, 모든 서버에 같은 값이 바로 적용됩니다.

**우리 서비스에서 좋아지는 점**
1. **가격 일관성**: 어느 서버에 연결되든 같은 가격이 보입니다.
2. **가격 반영 속도**: 5분 지연을 없앨 수 있습니다. 단, 이건 가격 변경 시 캐시를 갱신하도록 개발을 함께 해야 가능합니다. Redis만 도입하고 5분 주기를 그대로 두면 지연은 그대로입니다.
3. **서버 재시작 후 속도**: 로컬 캐시는 서버를 재시작하면 날아가지만, Redis는 API 서버와 별도로 살아 있어서 재시작 후에도 캐시가 유지됩니다.
4. **서버 증설 용이**: 서버를 더 늘려도 각 서버가 같은 데이터를 공유하므로 관리가 단순해집니다.

**알아둘 점 (단점과 비용)**
- 서버가 Redis에 요청을 보내고 받는 과정이 추가되어, 메모리에서 바로 읽는 것보다 아주 조금 느릴 수 있습니다. 보통 수 밀리초 이내라 체감은 거의 없습니다.
- Redis 서버가 멈추면 캐시 기능이 중단됩니다. 그래서 Redis 장애 시 DB에서 직접 읽도록 하는 대비책이 필요하고, Redis 서버를 운영하는 비용과 관리 부담이 새로 생깁니다.
- 가격 변경 시 캐시를 갱신하는 로직을 추가로 개발해야 합니다.

**한 줄 요약**
로컬 캐시는 서버마다 따로 보관해서 가격이 최대 5분 어긋날 수 있고, Redis는 공용 저장소 하나를 같이 써서 가격을 한 곳에서 맞춥니다. 가격 반영을 즉시 하려면 Redis 도입과 함께 가격 변경 시 캐시 갱신 작업도 같이 해야 합니다.
