현재 원인은 확정되지 않았습니다. 가장 유력한 가설은 로컬 `node_modules`에 1.4.0이 남아 있고, CI는 lockfile에 따라 2.0.0을 새로 설치하며, 2.0.0의 `exports` 필드에 `@company/ui/button` 경로가 빠져 있다는 것입니다. 이 가설은 아직 검증하지 않았습니다.

## 확인된 사실

- CI에서만 `Cannot find module '@company/ui/button'` 오류가 발생합니다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0부터 패키지에 `exports` 필드가 있습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 업그레이드 이전에 설치되어 있습니다.

## 추론

`exports` 필드가 있는 패키지는 필드에 나열된 경로만 외부에서 import할 수 있습니다. 따라서 2.0.0의 `exports`에 `./button`이 없거나 경로가 바뀌었다면, `@company/ui/button` import는 Node에서 실패합니다. 반면 1.4.0에는 `exports`가 없으므로 같은 import가 통과합니다. 로컬 `node_modules`가 1.4.0 그대로라면 로컬 빌드만 성공하는 현상이 설명됩니다.

CI 캐시 키가 lockfile 해시이므로, lockfile이 바뀌면 CI는 새 캐시를 만들고 lockfile이 지정한 2.0.0을 설치할 가능성이 높습니다. Node 18과 Node 20은 모두 `exports`를 지원하므로, Node 버전 차이만으로 이 오류가 생길 가능성은 낮습니다.

| 가설 | 근거 | 확인 방법 | 가능성 |
|---|---|---|---|
| 로컬에는 1.4.0이, CI에는 2.0.0이 설치되어 있다 | 로컬만 성공하고 설치 시점이 다르다 | 로컬에서 `npm ls @company/ui`를 실행한다 | 높음 |
| 2.0.0의 `exports`에 `./button`이 없거나 경로가 바뀌었다 | 2.0.0에서 `exports`가 추가되었다 | 2.0.0의 `package.json`에서 `exports` 항목을 확인한다 | 높음 (첫 번째 가설과 함께 성립할 수 있다) |
| Node 18과 20의 차이 | 실행 환경이 다르다 | Node 18로 로컬 빌드를 재현한다 | 낮음 |

## 확인되지 않은 사항

- 확인 필요: CI 실패가 업그레이드 직후부터 시작되었는지, 그 이후 다른 커밋이 섞였는지 확인해야 합니다.
- 확인 필요: CI 캐시 설정에 `restore-keys` 같은 이전 캐시 복원 규칙이 있는지 확인해야 합니다.
- 확인 필요: 사용처의 import 경로가 2.0.0에서 공개된 경로와 일치하는지 확인해야 합니다.

## 다음 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. 2.0.0 패키지의 `package.json`에서 `exports` 항목을 열어 `./button` 경로가 있는지 확인합니다.
3. CI 로그에서 `@company/ui`의 설치 버전과 캐시 hit 여부를 확인합니다.
4. 로컬 `node_modules`를 삭제하고 `npm ci`로 다시 설치한 뒤 빌드합니다. 로컬 빌드도 실패하면 설치 버전 차이 가설을 지지합니다.

확인 결과에 따라 수정 방향이 달라집니다. `exports`에 `./button`이 없다면 패키지 쪽에 경로 추가를 요청하거나, 사용처 import를 2.0.0이 공개한 경로로 바꿔야 합니다. 원인이 확인되기 전까지는 `@company/ui`를 1.4.0으로 되돌려 CI를 복구하는 방법도 있습니다.
