# 원인 분석: CI에서만 `Cannot find module '@company/ui/button'` 발생

## 한 줄 요약
CI는 `@company/ui` 2.0.0으로 빌드하고, 로컬은 설치 시점이 오래돼 1.4.0으로 빌드하고 있을 가능성이 가장 높다. 2.0.0에 추가된 `exports` 필드가 `@company/ui/button` 경로를 허용하지 않아 CI에서만 실패한다.

## 원인
1. **`exports` 필드의 효과**
   - `exports`가 없는 1.4.0에서는 패키지 내부 파일 경로(`@company/ui/button` → `button.js`)로 직접 import할 수 있었다.
   - `exports`가 있는 2.0.0에서는 `exports`에 명시된 경로만 import할 수 있다. `./button`이 없거나 다른 경로로 바뀌었다면 모듈을 찾지 못한다.
   - 이 동작은 Node 18과 20이 같고, Next.js의 webpack도 `exports`를 따른다.

2. **로컬과 CI의 차이**
   - 로컬 `node_modules`는 3일 전 업그레이드보다 먼저 설치했으므로 1.4.0이 남아 있을 가능성이 높다. 이 경우 로컬 빌드는 업그레이드 이후의 상태를 검증하지 못한다.
   - CI 캐시 키는 `package-lock.json` 해시다. 업그레이드로 lock 파일이 바뀌면서 캐시가 갱신됐고, CI는 2.0.0을 새로 설치한다.
   - 따라서 CI는 lock 파일 기준의 실제 상태를 보여 준다. CI 캐시는 원인이 아니라 차이를 드러낸 계기다.

## 가능성이 낮은 요인
- **Node 18 vs 20:** 두 버전 모두 `exports`를 지원하므로 주된 원인일 가능성은 낮다. 다만 환경을 통일해 두면 이후 분석이 쉬워진다.
- **캐시 오염:** 캐시 키가 lock 해시이므로 낡은 캐시가 쓰였을 가능성은 낮다.

## 확인 방법
아래 내용은 제공된 정황에서 추론한 것이며 아직 직접 확인하지 않았다.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 확인한다.
2. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 확인한다.
3. 로컬에서 `rm -rf node_modules && npm ci` 후 빌드한다. CI와 같은 에러가 재현되면 원인이 확정된다.

## 해결 방안
| 방안 | 내용 | 비고 |
|---|---|---|
| A. import 경로 수정 | 2.0.0의 `exports`에 정의된 경로로 변경 | 2.0.0 마이그레이션 가이드나 changelog 확인 필요 |
| B. 패키지에 서브패스 추가 | `@company/ui` 담당 팀에 `./button` export 추가 요청 | 다른 사용처에도 같은 문제가 있으면 이쪽이 효율적 |
| C. 1.4.0으로 롤백 | 임시 조치 | 근본 해결이 아니므로 A 또는 B와 병행 |

## 재발 방지
- 의존성 업그레이드 후에는 로컬에서 `npm ci`로 클린 설치한 뒤 빌드한다.
- 메이저 버전 업그레이드 PR에서는 CI 통과를 머지 조건으로 한다.
- 로컬과 CI의 Node 버전을 `.nvmrc` 또는 `engines`로 통일한다.

## PM 참고
- 영향 범위: 현재 CI 빌드와 배포가 막혀 있다. 운영 중인 서비스는 영향이 없다.
- 예상 작업량: 방안 A는 import 경로 수정 수준이다. 방안 B는 다른 팀과의 조율이 필요하다.
