CI 실패의 가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드(패키지가 외부에 공개하는 import 경로 목록)입니다. 로컬은 2.0.0 이전에 설치한 `node_modules`를 쓰기 때문에 이 영향을 받지 않았다고 추정합니다. 아직 검증하지 않았습니다.

## 추정 원인

`exports` 필드가 있는 패키지는 목록에 없는 경로로 import할 수 없습니다. 2.0.0의 `exports`에 `./button`이 없으면 Node가 `Cannot find module '@company/ui/button'` 에러를 냅니다. 1.4.0에는 `exports`가 없었으므로 같은 import가 동작했습니다.

로컬과 CI의 차이는 다음과 같습니다.

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `node_modules` | 3일 전보다 먼저 설치함 | 캐시 키(`package-lock.json` 해시)에 따라 설치함 |
| `@company/ui` 버전 (추정) | 1.4.0 | 2.0.0 |

CI의 `@company/ui` 버전이 2.0.0이라는 것은 추론입니다. 업그레이드로 `package-lock.json`이 바뀌었고, 그래서 캐시 키도 바뀌어 CI가 새로 설치했다고 보는 것입니다. 로컬이 1.4.0이라는 것도 설치 시점에서 추론한 값입니다.

## 부차 후보

Node 18과 20의 차이는 주원인일 가능성이 낮다고 봅니다. Node 18도 `exports` 필드를 지원하기 때문입니다. 다만 직접 확인하지 않았습니다.

## 확정 절차

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인하십시오.
2. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드하십시오. CI와 같은 에러가 나면 원인은 확정됩니다.
3. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 확인하십시오.
4. 2단계에서 에러가 나지 않으면 Node 18로 로컬 빌드를 다시 하십시오. 이때 Node 버전 차이가 원인 후보로 남습니다.

## 미확인 사항

- 로컬에 설치된 `@company/ui`의 실제 버전
- 2.0.0의 `exports`에 `./button`이 있는지
- CI가 설치한 `@company/ui`의 실제 버전

3단계에서 `./button`이 없으면, 앱의 import 경로를 2.0.0이 공개한 경로로 바꾸거나 `@company/ui`에 `./button`을 추가해야 합니다. 어느 쪽을 택할지는 2.0.0의 공개 경로 설계를 아는 사람이 정해야 합니다.
