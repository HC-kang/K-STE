Redis를 도입해도 가격 반영이 최대 5분 늦는 문제는 그대로 남습니다. 대신 서버 4대가 같은 캐시를 보기 때문에 서버마다 가격이 다르게 보이는 문제는 없어집니다. 여기서 캐시는 자주 쓰는 데이터를 미리 저장해 두고 꺼내 쓰는 임시 보관 장소를 말합니다.

두 방식을 비교하면 다음과 같습니다.

| 구분 | 로컬 캐시 (지금) | Redis 캐시 (도입 예정) |
|---|---|---|
| 저장 위치 | 서버마다 자기 메모리에 저장합니다. | 서버 4대가 함께 쓰는 캐시 서버 1대에 저장합니다. |
| 서버 간 내용 | 서버마다 달라질 수 있습니다. | 4대가 같은 내용을 봅니다. |
| 조회 속도 | 서버 안에서 바로 꺼냅니다. | 네트워크를 한 번 거칩니다. |
| 가격 반영 지연 | 최대 5분입니다. | 유효 시간(캐시를 다시 불러올 때까지의 기간)을 5분으로 두면 최대 5분입니다. |
| 서버 재시작 시 | 메모리의 캐시가 사라집니다. | 캐시 서버에 그대로 남아 있습니다. |
| 추가 운영 부담 | 없습니다. | 캐시 서버를 따로 운영해야 합니다. |

Redis로 얻는 효과는 서버 4대의 상품 정보가 같아지는 것입니다. 최대 5분 지연을 줄이려면 가격을 바꿀 때 Redis에 저장된 상품 목록을 바로 지우는 방식을 함께 넣는 것을 권장합니다. 이 방식을 넣을지는 개발팀과 함께 정해야 합니다.

확인 필요: 캐시 서버가 멈췄을 때 API 서버가 상품 목록을 어떻게 가져올지는 아직 확인되지 않았습니다.
