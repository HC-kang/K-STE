가장 유력한 원인은 2.0.0에서 추가된 `exports` 필드가 `@company/ui/button` 경로를 허용하지 않는 것으로 보입니다. 이 저장소의 파일은 직접 확인하지 않았고, 아래 내용은 전달해 주신 정보에 근거한 추론입니다.

### 확인된 사실

- `@company/ui`를 1.4.0에서 2.0.0으로 3일 전에 올렸습니다.
- 2.0.0에 `exports` 필드가 추가되었습니다. `exports`는 패키지가 외부에 공개하는 파일 경로 목록이며, 목록에 없는 경로는 가져올 수 없습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.
- 빌드 오류는 CI에서만 발생하고 로컬에서는 발생하지 않습니다.

### 원인 분석

로컬 `node_modules`가 3일 전에 설치되었다면 로컬에는 1.4.0이 그대로 남아 있을 가능성이 큽니다. 그러면 로컬 빌드는 옛 패키지 구조로 성공하며, 로컬 빌드는 2.0.0 변경을 검증하지 못합니다. 반면 CI는 lockfile 기준으로 패키지를 받으므로 2.0.0을 설치하고, 2.0.0에서 `button` 경로를 찾지 못해 실패합니다. 이 설명은 로컬 성공과 CI 실패를 모두 설명합니다. 다만 2.0.0의 `exports` 목록에 `button`이 실제로 빠졌는지는 아직 확인하지 않았습니다.

원인 후보별 근거는 다음과 같습니다.

| 원인 후보 | 로컬이 성공하는 이유 | CI가 실패하는 이유 | 확인 방법 |
|---|---|---|---|
| 2.0.0 `exports`에 `button` 경로가 없거나 이름이 바뀜 | 로컬에 1.4.0이 남아 있음 | CI가 2.0.0을 설치함 | 설치된 `package.json`의 `exports` 확인 |
| Node 18과 Node 20의 차이 | 로컬은 Node 20에서 성공함 | Node 18에서 경로 해석이 다를 가능성 | Node 18로 로컬 재현 |
| 캐시 문제 | 로컬과 무관함 | 캐시 키가 lockfile 해시라 lockfile이 바뀌면 CI는 새로 설치함 | lockfile에 2.0.0이 기록되었는지 확인 필요 |

Node 버전 차이는 가능성이 낮습니다. Node 18도 `exports`를 지원하기 때문입니다.

오류 메시지도 확인이 필요합니다. `Cannot find module`은 보통 Node의 `require` 방식이나 테스트 도구에서 나오는 메시지입니다. Node는 `exports`에 경로가 없을 때 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`를 냅니다. Next.js 빌드는 보통 `Module not found`를 냅니다. 확인 필요: 이 오류를 낸 명령이 Next.js 빌드인지, 다른 스크립트나 테스트인지 확인해야 합니다.

### 확인 순서

1. CI 로그에서 설치된 `@company/ui` 버전과 오류를 낸 명령을 확인합니다.
2. 로컬 `node_modules`를 지운 뒤 `npm ci`로 다시 설치하고, Node 18로 빌드를 실행해 CI 조건을 재현합니다.
3. 설치된 `node_modules/@company/ui/package.json`의 `exports`에 `./button` 항목이 있는지 확인합니다.
4. 2.0.0 변경 로그에서 `button` 경로가 바뀌었는지 확인합니다.

### 수정 방향

확인 결과 `exports`에 `button` 경로가 없다면 다음 방법을 검토할 수 있습니다.

- 2.0.0이 공개한 새 경로로 import 경로를 바꿉니다.
- 패키지 담당 팀에 `button` 경로 추가를 요청합니다.
- 당장 빌드를 살려야 하면 `@company/ui`를 1.4.0으로 임시 고정할 수 있습니다. 이 경우 2.0.0 전환은 다시 미뤄집니다.

Node 18은 2025년 4월에 지원이 종료되었습니다. 로컬과 CI의 Node 버전을 맞추고 CI를 지원되는 버전으로 올리는 것을 권장합니다.
