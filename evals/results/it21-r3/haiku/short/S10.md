현재 자료로는 원인을 확정할 수 없습니다. 가장 유력한 가설은 `@company/ui` 2.0.0의 `exports` 필드가 `button` 경로를 노출하지 않는다는 것입니다. 로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 여전히 1.4.0일 가능성이 높기 때문입니다.

## 확인된 사실

- `@company/ui`는 3일 전 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0 패키지에는 `exports` 필드가 추가되었습니다.
- CI는 Node 18을 사용합니다.
- 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.
- CI에서 발생하는 에러는 `Cannot find module '@company/ui/button'`입니다.

## 추론

- 로컬 `node_modules`는 1.4.0을 가리킬 가능성이 높습니다. 따라서 로컬 빌드는 2.0.0의 변경을 거치지 않았을 수 있습니다.
- 2.0.0의 `exports` 필드에 `./button` 항목이 없다면 `@company/ui/button` 경로는 해석되지 않을 수 있습니다.
- 에러 문구만으로는 `exports`가 경로를 막은 경우와 `button` 파일이 패키지에 없는 경우를 구분할 수 없습니다.
- Node 18과 Node 20의 차이가 원인이라는 근거는 현재 자료에 없습니다.

## 미확인

- 2.0.0 패키지의 `exports` 전체 내용과 `button` 파일이 실제로 있는지
- 로컬 `node_modules/@company/ui/package.json`의 `version` 값
- CI 로그에 실제로 설치된 `@company/ui` 버전
- 커밋된 `package-lock.json`에 2.0.0이 기록되어 있는지
- 에러가 Next.js 빌드 단계에서 나는지, Node 런타임에서 나는지

## 확인 방법

아래 항목은 아직 실행하지 않았습니다.

1. 로컬 `node_modules/@company/ui/package.json`을 열어 `version` 값을 읽습니다.
2. 2.0.0 패키지의 `package.json`에서 `exports` 필드를 읽고 `./button` 항목이 있는지 봅니다.
3. CI 워크플로에 `npm ls @company/ui` 단계를 추가해 설치된 버전을 로그로 남깁니다.
4. Node 18로 전환한 뒤 로컬에서 빌드를 다시 실행해 CI와 같은 조건을 만듭니다.
5. 로컬 `node_modules`를 삭제하고 `npm ci`로 다시 설치한 뒤 빌드합니다.

## 해결 방향

두 방향 중 하나를 고를 수 있습니다. 어느 쪽을 택할지는 2.0.0이 꼭 필요한 변경을 담고 있는지에 따라 달라집니다.

| 방향 | 내용 | 전제 |
|---|---|---|
| 1.4.0으로 되돌리기 | `package.json`과 `package-lock.json`에서 버전을 1.4.0으로 되돌립니다. | 2.0.0의 변경이 지금 당장 필요하지 않아야 합니다. |
| 2.0.0에 맞추기 | `button` import 경로를 2.0.0의 `exports`가 허용하는 경로로 바꿉니다. | 2.0.0 패키지에 필요한 경로와 기능이 있어야 합니다. |
