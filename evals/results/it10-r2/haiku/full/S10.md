가장 가능성이 높은 원인은 2.0.0에서 추가된 `exports` 필드가 `./button` 경로를 노출하지 않아서, CI가 2.0.0을 새로 설치한 뒤 `@company/ui/button` 해석에 실패하는 것입니다. 현재 자료만으로는 확정할 수 없으므로 아래 확인 절차가 필요합니다.

로컬 빌드가 성공하는 이유는 node_modules가 3일 전보다 먼저 설치되었기 때문입니다. 그렇다면 로컬에는 1.4.0이 들어 있을 가능성이 큽니다. 1.4.0에는 `exports` 필드가 없어서 하위 경로를 모두 import할 수 있었습니다. 따라서 로컬 빌드 성공은 2.0.0이 정상이라는 근거가 되지 않습니다. 로컬은 이 변경을 재현하지 못하는 환경입니다.

CI가 2.0.0을 받는 경로는 다음과 같습니다. 캐시 키가 `package-lock.json` 해시이므로, 버전을 올리면서 lock 파일이 바뀌었다면 캐시 키도 바뀌어 캐시가 적중하지 않습니다. 그 결과 CI는 새로 설치하면서 2.0.0을 받습니다. CI가 실패한다는 사실 자체가 CI에서 2.0.0이 쓰였다는 간접 근거입니다. 다만 워크플로에 `restore-keys` 같은 이전 캐시 복원 설정이 있다면 오래된 설치 상태가 복원되었을 가능성도 있으므로 워크플로 설정을 함께 보아야 합니다.

Node 버전 차이는 원인 후보로서 우선순위가 낮습니다. `exports` 필드는 Node 12.7 이상에서 지원되기 때문입니다. 다만 조건부 exports 해석이 런타임이나 번들러 버전에 따라 달라질 수 있어서 완전히 제외하지는 않습니다.

| 가설 | 근거 | 확인 방법 |
|---|---|---|
| 2.0.0의 `exports`에 `./button`이 없거나 다른 경로로 정의되어 있다 | 1.4.0은 통과하고 CI에서 2.0.0을 설치하면 실패한다 | 2.0.0의 `package.json`에서 `exports` 항목을 확인한다 |
| Node 18과 Node 20의 해석이 달라서 실패한다 | CI와 로컬의 Node 버전이 다르다 | 로컬에서 Node 18로 클린 설치 후 빌드해 재현 여부를 확인한다 |
| 오래된 캐시가 복원되었다 | 캐시 키는 lock 해시이고 복원 설정은 확인되지 않았다 | CI 로그에서 캐시 적중 여부와 실제 설치된 버전을 확인한다 |

개발자는 로컬에서 `rm -rf node_modules && npm ci`로 클린 설치한 뒤 `npm ls @company/ui`로 설치된 버전이 2.0.0인지 확인하고, 같은 빌드를 Node 18로 실행해 재현되는지 확인하십시오. 재현되면 2.0.0의 `exports`에 `./button` 경로를 추가하도록 패키지 쪽에 요청하거나, 앱의 import를 `exports`에 정의된 공식 경로로 바꾸는 것이 해결 방향입니다. PM에게는 로컬 성공이 2.0.0 검증이 아니며, 재현 확인 결과를 기다려야 한다는 점을 공유하십시오.
