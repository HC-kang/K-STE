CI 빌드 실패의 가장 유력한 원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드로 보입니다. 로컬 빌드가 성공하는 이유는 로컬에 설치된 패키지가 여전히 1.4.0일 가능성이 높기 때문으로 보입니다. 이 분석은 전달받은 사실만 근거로 하며, 코드와 설정 파일은 직접 확인하지 않았습니다.

## 확인된 사실

- `@company/ui`는 3일 전에 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0에는 `exports` 필드(패키지 바깥에서 가져올 수 있는 경로를 정하는 설정)가 추가되었습니다.
- CI는 Node 18을 쓰고, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`(설치할 패키지 버전을 고정해 둔 파일)의 해시(파일 내용으로 계산한 고유 값)입니다.
- 로컬 `node_modules`(설치된 패키지가 담기는 폴더)는 업그레이드 이전에 설치되었습니다.

## 원인 분석 (추론)

`exports` 필드가 있으면 외부에서 가져올 수 있는 경로가 `exports`에 적힌 경로로 제한됩니다. 2.0.0의 `exports`에 `./button` 경로가 없거나 다른 경로로 바뀌었다면 `@company/ui/button` import가 실패합니다. 이 설명은 에러 메시지와 맞습니다.

로컬에는 1.4.0이 남아 있을 가능성이 높습니다. 1.4.0에는 `exports` 제한이 없으므로 같은 import가 성공합니다.

CI는 캐시 키가 바뀌면서 저장된 캐시를 쓰지 못하고 2.0.0을 새로 설치한 것으로 보입니다.

로컬과 CI의 차이는 다음과 같습니다.

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `@company/ui` 설치 버전 | 1.4.0 (추론) | 2.0.0 (추론) |
| `node_modules` 설치 시점 | 업그레이드 이전 | 캐시 키 변경 후 새로 설치 (추론) |
| 빌드 결과 | 성공 | 실패 |

Node 버전 차이만으로는 이 에러를 설명하기 어렵습니다. Node 18과 Node 20은 모두 `exports` 필드를 지원하기 때문입니다. 다만 Node 18은 2025년 4월에 지원이 종료되었으므로 CI의 Node 버전도 함께 점검하는 것을 권장합니다.

## 확인 필요

- 로컬에서 `npm ls @company/ui`를 실행하면 실제 설치 버전을 확인할 수 있습니다.
- 2.0.0 패키지의 `package.json`에서 `exports` 항목을 열어 `./button` 경로가 있는지 확인합니다.
- 업그레이드 커밋에 `package.json`과 `package-lock.json`이 함께 들어 있었는지 확인합니다. 두 파일이 함께 바뀌지 않았다면 캐시 키가 그대로 남아 이전 설치 상태가 복원될 수 있습니다.
- 확인 필요: 에러가 나는 위치입니다. 에러 문구가 Node의 `require` 형식이므로, `next.config.js`나 빌드 스크립트처럼 Node가 직접 실행하는 파일에서 나는지, 웹팩(Next.js가 코드를 묶는 번들러) 단계에서 나는지 확인해야 합니다.
- CI 로그에서 캐시가 복원되었는지(cache hit) 확인합니다.

## 권장 조치

1. 빠른 복구가 필요하면 `@company/ui`를 1.4.0으로 되돌릴 수 있습니다.
2. 로컬 `node_modules`를 지우고 `npm ci`로 다시 설치합니다. 2.0.0이 설치된 상태에서 같은 에러가 나면 원인이 확인된 것입니다.
3. 2.0.0의 변경 내역(changelog)을 보고, 공개된 새 경로에 맞게 `@company/ui/button` import 경로를 고칩니다.
4. CI의 Node 버전을 20 이상으로 올리는 것을 권장합니다.
5. 캐시 키에 Node 버전을 함께 넣는 것을 권장합니다.
