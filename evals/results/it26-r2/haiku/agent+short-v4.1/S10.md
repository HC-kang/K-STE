원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드로 보입니다. 다만 아래 내용은 코드와 패키지를 직접 확인하지 않고 정리한 것이므로, 재현 단계로 확정해야 합니다.

## 사실 (제공된 정보)

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에서 `exports` 필드(패키지가 외부에 공개하는 import 경로 목록)가 추가되었습니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

## 추론

- 로컬은 여전히 1.4.0을 쓰고 있습니다. `node_modules`를 다시 설치하지 않았기 때문입니다. 그래서 로컬 빌드가 성공한 것은 Node 버전이나 코드가 아니라 옛 패키지를 쓰고 있었기 때문으로 보입니다.
- CI는 lockfile이 바뀌어 캐시가 맞지 않으므로 2.0.0을 새로 설치합니다.
- 2.0.0의 `exports` 목록에 `button` 경로가 없거나 경로가 바뀌었을 가능성이 큽니다. 그러면 `@company/ui/button` import는 2.0.0을 설치한 모든 환경에서 실패합니다.
- Node 18도 `exports`를 지원하므로 Node 버전 차이가 주된 원인일 가능성은 낮습니다.

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| 설치 시점 | 3일 전보다 이전 | lockfile 변경 후 새로 설치 |
| 설치되는 `@company/ui` | 1.4.0 (추정) | 2.0.0 (추정) |
| 빌드 결과 | 성공 | 실패 |

## 미확인

- 2.0.0의 실제 `exports` 목록에 `./button`이 있는지 확인이 필요합니다.
- 커밋된 `package-lock.json`에 2.0.0이 반영되었는지 확인 필요: 반영되지 않았다면 CI도 1.4.0을 설치하므로 원인이 다릅니다.
- Node 18과 20 중 어느 쪽이 영향을 주는지는 아직 검증하지 않았습니다.

## 재현 및 확인 순서

1. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 Node 20으로 빌드합니다. 여기서 실패하면 버전 업그레이드가 원인이라는 것이 확정됩니다.
2. `npm view @company/ui@2.0.0 exports`로 2.0.0의 공개 경로를 확인합니다.
3. 1번에서 실패한 상태를 Node 18로도 빌드해 Node 버전의 영향을 확인합니다.

## 수정 방안

- 앱의 import를 2.0.0 `exports`에 있는 경로로 바꿉니다.
- `@company/ui` 담당자에게 `./button` 경로를 `exports`에 추가해 달라고 요청합니다.
- 급하게 배포해야 하면 `@company/ui`를 1.4.0으로 되돌릴 수 있습니다.
