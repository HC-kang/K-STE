원인은 `@company/ui` 2.0.0의 `exports` 필드가 `./button` 경로를 공개하지 않기 때문으로 보입니다. 로컬에는 2.0.0 이전 버전이 설치돼 있어서 이 문제가 드러나지 않았을 가능성이 큽니다.

**사실**
- CI에서만 `Cannot find module '@company/ui/button'`이 발생합니다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드가 추가됐습니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치한 것입니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- CI는 Node 18, 로컬은 Node 20입니다.

**추론**
- 로컬 `node_modules`에는 1.4.0이 남아 있을 가능성이 큽니다. 1.4.0에는 `exports`가 없으므로 `@company/ui/button`이 실제 파일 경로로 해석돼 빌드가 성공합니다.
- CI는 업데이트된 `package-lock.json`으로 2.0.0을 설치합니다. `exports`가 있으면 Node는 그 목록에 정의된 경로만 허용합니다. `./button`이 목록에 없거나 이름이 바뀌었다면 모듈을 찾지 못합니다.
- 캐시 키가 lockfile 해시이므로 lockfile이 바뀐 시점에 캐시도 새로 만들어졌을 것입니다. 오래된 캐시가 원인일 가능성은 낮습니다.
- Node 18과 20은 둘 다 `exports`를 지원합니다. Node 버전 차이는 주원인이 아닐 가능성이 큽니다.

**확인하지 못한 것**
- 2.0.0의 `exports`에 `./button`이 있는지 확인하지 못했습니다.
- 로컬에 실제로 설치된 `@company/ui` 버전을 확인하지 못했습니다.
- `exports` 위반 시 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`가 나옵니다. 이번 메시지는 번들러(webpack)가 낸 형태일 수 있습니다. 확인 필요: CI 로그 전체에 다른 에러 코드가 있는지 봐야 합니다.

**확인 순서**
1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인한다.
2. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드한다. 같은 에러가 나면 원인이 확정된다.
3. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 확인한다.
4. 없으면 2.0.0 변경 이력(changelog)에서 button의 새 경로를 찾는다.
5. 2번에서 재현되지 않으면 CI의 Node를 20으로 바꿔 한 번 실행하고 결과를 비교한다.

**수정 방향**
- 앱 쪽에서 import 경로를 `exports`에 정의된 경로로 바꿀 수 있습니다.
- 패키지 쪽에서 `exports`에 `./button`을 추가해 2.0.1 이상으로 배포할 수 있습니다.

PM 관점에서는 2.0.0이 `./button` 경로를 제거한 변경이라면 breaking change이므로, 이 앱 외에 `@company/ui`를 쓰는 다른 앱도 같은 에러가 날 수 있습니다.
