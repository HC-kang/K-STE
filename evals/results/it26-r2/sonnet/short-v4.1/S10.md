원인은 로컬과 CI가 서로 다른 버전의 `@company/ui`를 쓰기 때문으로 보입니다. CI는 2.0.0을 설치하고, 로컬은 1.4.0을 그대로 쓰는 것으로 추정됩니다. 아직 확인한 사실은 아니고, 아래 순서로 검증해야 합니다.

**사실 (제공된 정보)**
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에 `exports` 필드가 추가됐습니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치한 것입니다.
- CI는 Node 18, 로컬은 Node 20입니다.

**추론**
- `exports`는 패키지가 외부에 공개하는 import 경로의 목록입니다. 이 필드가 있으면 목록에 없는 경로는 파일이 실제로 있어도 가져올 수 없습니다. 1.4.0에는 이 필드가 없어서 `@company/ui/button`처럼 파일 경로로 직접 가져올 수 있었습니다. 2.0.0의 `exports`에 `./button`이 없거나 잘못 연결돼 있으면 이 import가 실패합니다.
- 버전을 올리면서 `package-lock.json`이 바뀌었으므로 CI 캐시 키도 바뀌어 캐시를 쓰지 못했을 것입니다. 그래서 CI는 락 파일(설치할 정확한 버전을 적은 파일) 기준으로 2.0.0을 새로 설치했을 것입니다.
- 로컬은 3일 전 이전에 설치한 `node_modules`를 다시 설치하지 않았다면 1.4.0이 남아 있어 빌드가 성공합니다.
- Node 18과 20은 모두 `exports`를 지원하므로 Node 버전 차이가 주원인일 가능성은 낮습니다.

**미확인**
- 로컬 `node_modules`의 실제 `@company/ui` 버전.
- 2.0.0의 `exports`에 `./button`이 있는지, 있다면 그 경로가 가리키는 파일이 패키지에 들어 있는지.
- 에러 문구가 `exports` 차단의 전형적인 문구(`ERR_PACKAGE_PATH_NOT_EXPORTED`)와 다르다는 점. `exports`가 `./button`을 공개하지만 가리키는 파일이 없는 경우에도 이런 문구가 나올 수 있어서, 아래 3번과 4번 확인이 필요합니다.
- 2.0.0이 Node 20 이상에서만 동작하는지.

**검증 순서**
1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다. 1.4.0이면 위 추론이 맞을 가능성이 높습니다.
2. 로컬 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드합니다. 로컬에서도 실패하면 원인은 버전 차이로 확정됩니다.
3. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 확인합니다.
4. `./button`이 있으면 그 경로가 가리키는 파일이 `node_modules/@company/ui` 안에 실제로 있는지 확인합니다.
5. 2번에서 재현되지 않으면 CI의 Node를 20으로 바꿔 다시 실행해 Node 버전의 영향을 확인합니다.

**조치 방향 (원인 확인 후)**
- `exports`에 `./button`이 없으면 import 경로를 2.0.0이 공개하는 경로로 바꾸거나, 패키지 쪽에 `./button`을 추가해야 합니다.
- 급하면 `@company/ui`를 1.4.0으로 고정해 CI를 복구할 수 있습니다.
- 로컬과 CI의 Node 버전은 `.nvmrc`나 `engines` 필드로 통일하는 것을 권장합니다.
