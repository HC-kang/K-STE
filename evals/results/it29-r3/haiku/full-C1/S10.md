가장 유력한 원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드입니다. 이 필드가 있으면 패키지 외부에서 import할 수 있는 경로가 `exports`에 정의된 것으로 제한됩니다. 로컬 빌드가 성공하는 것은 로컬 `node_modules`가 3일 전 설치본이라 1.4.0을 쓰고 있을 가능성이 높기 때문으로 보입니다. 두 가지 모두 아직 확인하지 않은 가설입니다.

## 현재 확인된 차이

| 항목 | CI | 로컬 |
| --- | --- | --- |
| Node 버전 | 18 | 20 |
| `@company/ui` 버전 | 2.0.0으로 보임 (실패 조건과 일치) | 1.4.0일 가능성 높음 (확인 필요) |
| 의존성 설치 시점 | lock 해시가 바뀌면 새로 설치 | 3일 전 이전 설치본 |
| 빌드 결과 | 실패 | 성공 |

## 원인 분석

1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`이 패키지 안의 파일 경로로 해석되었을 것으로 보입니다. 2.0.0의 `exports`에 `./button` 항목이 없다면 같은 import는 실패합니다. 2.0.0의 실제 `exports` 목록은 확인하지 않았습니다.

에러 메시지 `Cannot find module`은 Node나 TypeScript에서 나오는 형식입니다. Node가 `exports` 제한으로 실패하면 보통 다른 메시지가 나오므로, 실제 출처는 CI 로그 전체로 확인해야 합니다.

Node 18과 20은 모두 `exports`를 지원하므로, 버전 차이만으로 실패를 설명하기는 어렵습니다. 버전 차이가 결과에 영향을 줬는지는 확인되지 않았습니다.

캐시 키가 `package-lock.json`의 해시이므로, lock 파일이 바뀌었다면 CI 캐시는 무효화되고 새로 설치됩니다. 따라서 캐시보다 lock 파일에 기록된 `@company/ui` 버전이 2.0.0인지가 관건입니다.

로컬 성공은 정상 신호가 아닙니다. 로컬이 옛 버전을 쓰고 있을 수 있기 때문입니다.

## 확인할 것

1. 로컬에서 `npm ls @company/ui`를 실행하여 실제 설치 버전을 확인하십시오.
2. `package-lock.json`에 기록된 `@company/ui` 버전을 확인하십시오.
3. CI 로그에서 실패한 import 파일과 에러 원문 전체를 확인하십시오.
4. 2.0.0 패키지의 `exports` 항목에 `./button`이 있는지 확인하십시오.

## 조치 방향

- `exports`에 `./button`이 없으면, 코드의 import를 `exports`에 정의된 경로로 바꾸거나 패키지 관리 측에 경로 추가를 요청해야 합니다.
- 빌드를 당장 복구해야 하면, 2.0.0 업그레이드 커밋을 되돌리거나 `@company/ui`를 1.4.0으로 고정할 수 있습니다.
- 로컬과 CI의 Node 버전을 하나로 맞추려면 `.nvmrc` 같은 파일로 버전을 지정하는 것이 좋습니다.

가장 먼저 1번과 4번을 확인하면 원인이 확정됩니다.
