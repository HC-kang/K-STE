CI에서만 실패하는 원인은 `@company/ui` 2.0.0에서 새로 추가된 `exports` 필드일 가능성이 높습니다. `exports`가 있으면 패키지가 공개한 경로만 import할 수 있습니다. `@company/ui/button`이 공개 목록에 없으면 이 에러가 납니다.

로컬 빌드가 성공하는 이유는 아직 확인되지 않았습니다. 로컬 `node_modules`가 3일 전보다 먼저 설치된 것이라 1.4.0을 쓰고 있을 가능성이 있습니다. 그렇다면 로컬 빌드는 2.0.0 변경을 검증하지 않은 것입니다.

Node 버전 차이만으로 이 에러를 설명하기는 어렵습니다. Node 18과 20 모두 `exports` 필드를 지원하기 때문입니다.

| 후보 원인 | 근거 | 확인 방법 |
|---|---|---|
| 2.0.0의 `exports`에 `./button` 경로가 없음 | 2.0.0에서 `exports`가 추가됐고, 3일 전부터 CI가 실패함 | 2.0.0 패키지의 `package.json`에서 `exports` 항목을 확인함 |
| 로컬이 1.4.0을 쓰고 있음 | 로컬 `node_modules`가 3일 전보다 먼저 설치됨 | `npm ls @company/ui`로 설치 버전을 확인함 |
| Node 버전 차이 | CI는 Node 18, 로컬은 Node 20을 씀 | Node 18로 로컬 빌드를 재현함. 두 버전 모두 `exports`를 지원하므로 가능성은 낮음 |
| 캐시가 오래된 패키지를 복원함 | 캐시 키가 `package-lock.json` 해시라 lock이 바뀌면 새로 설치됨 | CI 로그에서 캐시 복원 키(restore-keys)로 복원됐는지 확인함 |

확인 필요: 로컬 `@company/ui` 버전. 가능한 해석은 1.4.0이거나, 3일 이후 재설치로 2.0.0이 설치된 경우입니다. 이 답에 따라 로컬 재현 방법이 달라집니다.

확인 필요: `package-lock.json`이 2.0.0으로 갱신되어 커밋되었는지 여부. 커밋되지 않았다면 CI가 설치하는 버전과 로컬 버전이 다를 수 있습니다.

수정 방향은 두 가지입니다. 하나는 2.0.0 문서에서 공개된 import 경로로 바꾸는 것이고, 다른 하나는 패키지 관리자에게 `./button` 공개를 요청하는 것입니다.

먼저 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인하십시오. 그다음 설치된 패키지의 `package.json`에서 `exports`에 `./button`이 있는지 확인하십시오.
