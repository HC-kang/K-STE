가장 유력한 원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드(패키지가 외부에 공개하는 경로 목록)에 `./button` 경로가 없거나 이름이 바뀐 것입니다. 로컬 빌드가 성공하는 이유는 3일 전에 설치된 1.4.0을 쓰고 있기 때문으로 보입니다. 이 내용은 설명에서 얻은 정보로 세운 추론이며, 코드, 락파일, CI 로그는 확인하지 않았습니다.

## 원인 추정

`exports` 필드가 있으면 목록에 없는 파일은 외부에서 가져올 수 없습니다. 앱 코드의 `@company/ui/button`은 패키지 안쪽 파일을 직접 가져오는 방식(딥 임포트)입니다. 2.0.0 목록에 `./button`이 없으면 이 import가 해석되지 않아 빌드가 실패합니다.

## 로컬과 CI가 다른 이유

로컬 `node_modules`는 3일 전 설치본이므로 1.4.0일 가능성이 높습니다. 1.4.0에는 `exports` 필드가 없어서 같은 import가 통과합니다. 따라서 로컬 빌드 성공은 2.0.0이 정상 동작한다는 근거가 되지 않습니다.

| 항목 | 로컬 | CI |
|---|---|---|
| `@company/ui` 버전 | 1.4.0으로 보임 (확인 필요) | 2.0.0으로 보임 (확인 필요) |
| Node 버전 | 20 | 18 |
| 패키지 준비 방식 | 3일 전 설치본 재사용 | 락파일 해시 키의 캐시 복원 후 설치 |

Node 18과 20의 차이는 이 에러의 주원인으로 보기 어렵습니다. Node 18도 `exports` 필드를 지원합니다. 다만 2.0.0이 ESM 전용 패키지(새 방식의 모듈 형식만 지원하는 패키지)라면 Node 18에서 다른 오류가 날 수 있습니다. 이 경우 메시지는 `ERR_REQUIRE_ESM`이 되므로 현재 메시지와 맞지 않아 가능성은 낮습니다. 확인 필요: 2.0.0이 ESM 전용 패키지인지 여부.

에러 문구 `Cannot find module`은 Node가 `require`로 파일을 찾지 못할 때 내는 형식입니다. Next.js 빌드 단계에서 나온 메시지인지는 확인 필요합니다.

## 캐시 관련

CI 캐시 키가 `package-lock.json`의 해시이므로, 락파일이 3일 전에 바뀌었다면 캐시 키도 바뀌어 새로 설치됐을 가능성이 높습니다. 그러면 CI는 락파일이 가리키는 버전을 받습니다. 다만 복원 키(restore-keys, 정확히 맞는 캐시가 없을 때 이전 캐시를 쓰는 설정)가 있으면 이전 캐시가 복원될 수 있습니다. 확인 필요: 복원 키 설정 여부와 락파일에 2.0.0이 기록돼 있는지 여부.

## 확인 방법

1. CI 로그에서 에러가 난 단계와 메시지 전체를 확인합니다.
2. CI의 설치 단계 뒤에 `npm ls @company/ui`를 추가해 실제 설치된 버전을 출력합니다.
3. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다. 1.4.0이면 로컬은 2.0.0을 아직 테스트하지 않은 상태입니다.
4. 2.0.0의 `exports` 필드에 `./button`이 있는지 패키지 소스나 `node_modules/@company/ui/package.json`에서 확인합니다.
5. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드합니다. 같은 에러가 나면 CI 환경과 무관하게 재현된 것입니다. 이어서 `nvm use 18`로 Node 18을 맞춰 한 번 더 빌드합니다.

## 권장 조치

4번에서 `./button` 경로가 없고 경로 변경이 의도된 변경이라면, 앱 코드의 import를 2.0.0이 공개한 방식으로 바꾸는 것을 권장합니다. 누락이 실수라면 패키지 쪽 `exports`에 경로를 추가해 달라고 요청해야 합니다. 원인을 확인하기 전에는 CI 설정을 바꾸지 않는 것을 권장합니다. 임시 조치로 `@company/ui`를 1.4.0으로 되돌릴 수 있지만, 그러면 2.0.0 적용이 보류됩니다.
