가장 유력한 원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드(패키지가 외부에 공개할 파일 경로를 정하는 설정)가 `button` 하위 경로 import를 허용하지 않는 것이다. 로컬 빌드가 성공하는 이유는 로컬 `node_modules`에 3일 전 설치한 1.4.0이 남아 있기 때문으로 보인다. 이는 추론이므로 아래 항목으로 검증해야 한다.

## 확인된 사실

- CI는 Node 18을, 로컬은 Node 20을 사용한다.
- `@company/ui`는 3일 전에 1.4.0에서 2.0.0으로 올라갔다.
- 2.0.0에는 `exports` 필드가 추가됐다.
- CI 캐시 키는 `package-lock.json`(설치 버전을 고정하는 파일)의 해시다.
- 로컬 `node_modules`(설치된 패키지가 담기는 폴더)는 3일 전보다 먼저 설치됐다.
- CI 빌드는 `Cannot find module '@company/ui/button'` 에러로 실패한다.

## 추론

`exports` 필드가 있으면 Node.js와 번들러는 그 필드에 적힌 경로만 허용한다. 2.0.0의 `exports`에 `./button` 경로가 없다면 `@company/ui/button` import는 실패한다. 이 규칙은 Node 18과 Node 20에 똑같이 적용되므로, Node 버전 차이만으로는 이 에러를 설명하기 어렵다.

로컬 `node_modules`가 1.4.0 상태로 남아 있다면, 1.4.0에 `exports` 제약이 없었을 경우 같은 import가 로컬에서 성공한다.

캐시 키가 lock 파일 해시이므로, lock 파일이 2.0.0으로 갱신됐다면 CI는 새 캐시로 설치해야 한다. 다만 캐시 설정에 `restore-keys`(키가 정확히 일치하지 않을 때 비슷한 이전 캐시를 복원하는 설정)가 있다면 오래된 `node_modules`가 복원됐을 수 있다.

## 확인 항목

| 확인 항목 | 확인 방법 | 결과에 따른 의미 |
|---|---|---|
| 2.0.0 `exports`에 `./button`이 있는지 | `node_modules/@company/ui/package.json`의 `exports` 항목을 본다 | 없으면 원인이 확정된다 |
| 로컬 설치 버전 | 로컬에서 `npm ls @company/ui`를 실행한다 | 1.4.0이면 로컬 성공 이유가 확정된다 |
| CI가 설치한 버전 | CI 로그에서 설치 후 `npm ls @company/ui` 출력을 본다 | 2.0.0이면 CI는 최신 버전을 설치한 것이다 |
| CI 캐시 복원 방식 | 워크플로 파일의 cache 단계에 `restore-keys`가 있는지 본다 | 있으면 오래된 `node_modules`가 복원됐을 수 있다 |
| 실패 시작 시점 | 실패가 처음 나타난 빌드를 확인한다 | 3일 전 업그레이드와 일치하는지 본다 |

## 권장 조치

먼저 로컬에서 `rm -rf node_modules` 후 `npm ci`로 다시 설치하고 빌드를 실행해 로컬에서도 같은 에러가 나는지 확인해야 한다. 같은 에러가 나면 원인이 패키지 쪽임이 확정된다.

원인이 `exports`에 `./button`이 빠진 것으로 확인되면, 패키지 관리 측에 경로 추가를 요청하거나 1.4.0으로 되돌리는 방안을 검토해야 한다.

CI와 로컬의 Node 버전은 하나로 맞추기를 권장한다.
