가장 유력한 원인은 2.0.0에 새로 추가된 `exports` 필드입니다. `exports`는 패키지가 바깥에 공개하는 파일 경로 목록인데, 이 목록이 있으면 목록에 없는 하위 경로는 import할 수 없습니다. `@company/ui/button`이 공개 목록에 없으면 지금 에러가 납니다. 다만 로컬 빌드가 성공하는 이유는 아직 확인하지 않았습니다.

아래 표는 사실과 추론을 구분한 것입니다.

| 가설 | 근거 | 확인 방법 |
|---|---|---|
| 2.0.0의 `exports`에 `./button` 경로가 없다 | 2.0.0에 `exports`가 추가되었다(사실). 목록에 없는 경로가 차단된다는 것은 Node의 패키지 해석 규칙에 따른 추론이다. | 2.0.0의 `package.json`에서 `exports` 항목을 확인한다. |
| 로컬에는 1.4.0이 설치되어 있다 | 로컬 `node_modules`는 업그레이드 전에 설치되었다(사실). 업그레이드 후 다시 설치했는지는 확인하지 않았다. | `npm ls @company/ui`로 설치된 버전을 확인한다. |
| Node 버전 차이가 원인이다 | `exports`는 Node 12.7 이상에서 지원되며 Node 18과 20이 모두 해당한다. 따라서 차이만으로 설명하기는 어렵다(추론). | 로컬에서 Node 18로 빌드해 재현되는지 본다. |
| 캐시 키가 원인이다 | 캐시 키가 lock 파일 해시이므로 lock 파일이 바뀌면 CI는 새로 설치한다(추론). 캐시가 에러를 직접 만든다고 보기는 어렵다. | CI 설치 로그에서 설치된 버전과 캐시 적중 여부를 확인한다. |

용어를 풀면, lock 파일(`package-lock.json`)은 설치할 패키지 버전을 고정해 둔 파일이고, 캐시 키는 CI가 이전 설치 결과를 재사용할지 정하는 기준값입니다.

재현 순서는 다음과 같습니다.

1. `npm ls @company/ui`를 실행해 로컬에 설치된 버전을 확인하십시오.
2. `rm -rf node_modules && npm ci && npm run build`로 깨끗이 설치한 뒤 빌드하십시오.
3. 같은 빌드를 Node 18로 실행해 에러가 재현되는지 확인하십시오.
4. CI 로그의 설치 단계에서 실제로 설치된 버전과 캐시 적중 여부를 확인하십시오.

원인이 `exports` 누락으로 확인되면 선택지는 두 가지입니다. 패키지 쪽에 필요한 경로를 `exports`에 추가해 달라고 요청하거나, 공개된 경로로 import를 바꾸십시오. 임시 조치로 1.4.0으로 되돌리는 방법도 있습니다.

확인 필요: 3일 전 업그레이드 커밋에 `package-lock.json`이 포함되었는지. 포함되지 않았다면 CI와 로컬이 서로 다른 버전을 쓰고 있을 가능성이 있습니다.

배포가 이 실패로 막혀 있는지는 제공된 정보로는 알 수 없습니다.
