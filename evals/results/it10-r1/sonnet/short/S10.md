가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드가 `./button` 경로를 공개하지 않는 것으로 보이고, 로컬이 아직 1.4.0을 쓰고 있어서 이 문제가 로컬에서 드러나지 않는 것입니다. 이 내용은 추론이며, 아래 확인 단계를 실행하기 전에는 확정할 수 없습니다.

**확인된 사실**
- CI에서만 `Cannot find module '@company/ui/button'` 에러가 납니다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드(패키지가 외부에 공개할 파일 경로를 정해 두는 설정)가 새로 생겼습니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치한 것입니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.

**추론**
- `exports` 필드가 있으면 목록에 없는 경로는 import할 수 없습니다. 2.0.0의 `exports`에 `./button`이 없거나 다른 형태로 적혀 있으면 `@company/ui/button`을 찾지 못합니다.
- 로컬 `node_modules`는 업그레이드 전에 설치했으므로 1.4.0이 남아 있을 가능성이 큽니다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`이 파일 경로 그대로 열립니다. 그래서 로컬 빌드는 성공합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다. 업그레이드로 lock 파일이 바뀌었다면 캐시가 새로 만들어지고 CI는 2.0.0을 설치합니다. 따라서 CI 캐시는 원인이 아닐 가능성이 높습니다.
- Node 18도 `exports` 필드를 지원하는 것으로 알고 있습니다. 그래서 Node 버전 차이가 주된 원인일 가능성은 낮다고 봅니다. 다만 이 환경에서 실행해 확인하지 않았습니다.

**미확인**
- 2.0.0의 `exports`에 `./button`이 실제로 있는지 확인하지 않았습니다.
- 로컬에 설치된 `@company/ui` 버전이 1.4.0인지 확인하지 않았습니다.
- 에러가 업그레이드 직후부터 났는지도 확인하지 않았습니다.

**확인 단계**
1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다. 1.4.0이면 위 추론이 맞을 가능성이 커집니다.
2. 로컬의 `node_modules/@company/ui/package.json`을 열어 `exports`에 `./button`이 있는지 확인합니다.
3. `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 Node 20과 Node 18에서 각각 빌드합니다. 두 버전에서 모두 실패하면 원인은 Node 버전이 아니라 2.0.0의 `exports`입니다.

3단계에서 로컬 빌드가 같은 에러로 실패하면 원인이 확정됩니다. 그다음에는 `@company/ui` 쪽에서 `./button`을 `exports`에 추가하거나, 앱의 import 경로를 2.0.0이 공개하는 경로로 바꿔야 합니다. 어느 쪽이 맞는지는 2.0.0의 `exports` 내용과 변경 안내를 본 뒤에 정해야 합니다.
