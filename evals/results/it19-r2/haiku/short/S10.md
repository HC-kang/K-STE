CI에서만 실패하는 가장 유력한 원인은 `@company/ui` 2.0.0이 추가한 `exports` 필드입니다. 로컬 `node_modules`에는 아직 1.4.0이 남아 있을 가능성이 크므로 로컬 빌드가 통과합니다. 다만 아래 확인 항목을 실행하기 전에는 확정할 수 없습니다.

### 확인된 사실

- 3일 전 `@company/ui`가 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0에는 `exports` 필드(패키지 외부에 공개할 경로 목록을 정하는 설정)가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키(캐시를 찾는 식별값)는 `package-lock.json`(설치 버전을 기록한 파일)의 해시입니다.
- 로컬 `node_modules`(설치된 패키지 폴더)는 3일 전보다 먼저 설치되었습니다.

### 추론

1. `exports`에 없는 경로는 가져올 수 없습니다. `@company/ui/button`이 2.0.0의 `exports` 목록에 없으면 빌드가 이 경로를 찾지 못하고 실패할 수 있습니다.
2. 로컬 빌드가 성공하는 이유는 로컬에 1.4.0이 남아 있기 때문일 가능성이 큽니다. 1.4.0은 `exports` 제한이 없어서 `@company/ui/button` 경로를 그대로 가져올 수 있습니다.
3. CI가 2.0.0을 설치하는 이유는 lockfile이 바뀌어 캐시 키도 바뀌었기 때문입니다. 캐시를 쓰지 못한 CI는 lockfile에 적힌 2.0.0을 새로 설치합니다.
4. Node 버전 차이가 원인일 가능성은 낮습니다. Node 18과 20 모두 `exports`를 지원하기 때문입니다. 다만 두 버전의 차이가 이 빌드에 영향을 주지 않는다는 점은 아직 검증하지 않았습니다.
5. Node 18은 2025년 4월에 지원이 끝났으므로, 원인과 별개로 CI의 Node 버전을 올리는 방안도 검토할 만합니다.

### 확인 필요

- 원문에 나온 오류 문구 `Cannot find module`만으로는 실패 지점을 특정할 수 없습니다. CI 로그의 전체 스택 트레이스(오류가 발생한 파일과 단계를 보여 주는 기록)를 확인해야 합니다.
- 2.0.0의 `package.json`에 `./button`에 해당하는 `exports` 항목이 있는지, 있다면 실제 경로가 무엇인지 확인해야 합니다.
- 2.0.0 변경 기록(changelog)에 `button` 경로가 바뀌었다는 공지가 있는지 확인해야 합니다.
- 실패한 CI 로그에서 실제 설치된 `@company/ui` 버전이 2.0.0인지 확인해야 합니다.

### 검증 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 확인합니다.
2. 로컬에서 `rm -rf node_modules && npm ci`로 lockfile 기준 클린 설치를 한 뒤 빌드합니다. 여기서도 실패하면 CI 문제가 아니라 코드와 패키지 버전의 문제입니다.
3. Node 18 환경에서 같은 빌드를 실행해 Node 버전이 원인인지 분리합니다.

### 수정 방향 (PM 참고)

1. import 경로를 2.0.0의 `exports` 목록에 맞게 바꿉니다. 코드 수정만으로 해결되지만, 2.0.0에 맞는 경로를 먼저 확인해야 합니다.
2. `@company/ui` 담당자에게 `./button` 경로를 `exports`에 추가해 달라고 요청합니다. 패키지 쪽 수정이 필요합니다.
3. 당장 배포가 급하면 `@company/ui`를 1.4.0으로 되돌립니다. 이 방법은 빠르지만 2.0.0 적용이 다시 미뤄집니다.
