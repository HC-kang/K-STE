CI에서만 빌드가 실패하는 가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드(패키지가 바깥에 공개하는 모듈 경로를 정한 설정)가 `button` 경로를 공개하지 않아서, `@company/ui/button` import를 해석하지 못하는 것이다. 다만 이는 정황에 근거한 추론이며, 패키지 설정과 import 구문을 확인하기 전까지 확정되지 않는다.

## 확인된 사실

- CI 빌드는 Node 18에서, 로컬 빌드는 Node 20에서 실행된다.
- `@company/ui`를 3일 전에 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0부터 패키지에 `exports` 필드가 추가되었다.
- CI 캐시 키는 `package-lock.json`(설치할 패키지 버전을 고정하는 파일)의 해시이다.
- 로컬 `node_modules`(설치된 패키지가 담긴 폴더)는 3일 전보다 먼저 설치되었다.
- 실패 메시지는 `Cannot find module '@company/ui/button'`이다.

## 추론

- 로컬 `node_modules`에는 1.4.0이 남아 있을 가능성이 높다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`처럼 패키지 안의 파일 경로를 직접 가져오는 방식(하위 경로 import)이 제한 없이 동작하고, 그래서 로컬 빌드가 성공했을 것으로 보인다.
- `package-lock.json`이 2.0.0으로 갱신되었다면 캐시 키가 바뀌어 CI는 2.0.0을 새로 설치한다. 이때 2.0.0의 `exports`에 `./button`이 없으면 같은 import가 실패한다.
- Node 18과 20의 차이가 원인일 가능성은 낮게 본다. 두 버전 모두 `exports` 필드를 지원하기 때문이다.
- 로컬 빌드가 성공했다는 사실은 2.0.0 설정이 정상이라는 근거가 되지 않는다. 로컬에 설치된 패키지가 오래된 버전일 가능성이 높기 때문이다.

## 확인 필요

- 확인 필요: 커밋된 `package-lock.json`에 `@company/ui` 2.0.0이 반영되었는지 확인해야 한다. 반영되지 않았다면 CI와 로컬이 설치하는 버전이 다를 수 있다.
- 확인 필요: 2.0.0의 `exports` 필드에 `./button` 경로가 포함되어 있는지 확인해야 한다.
- 확인 필요: 실제 import 구문이 `@company/ui/button`인지, 다른 경로인지 확인해야 한다.
- 확인 필요: CI가 실제로 2.0.0을 설치했는지 확인해야 한다.

## 확인 방법

1. CI 설치 단계에 `npm ls @company/ui`를 추가해 설치된 버전을 로그에서 확인한다.
2. 로컬과 CI에서 `node_modules/@company/ui/package.json`의 `exports` 필드를 비교한다.
3. `package-lock.json`의 `@company/ui` 버전 변경 이력을 git에서 확인한다.
4. 로컬 `node_modules`를 삭제하고 `npm ci`로 lock 파일 기준 재설치 후 빌드하여 로컬에서도 재현되는지 확인한다.
5. Node 18로 로컬 빌드를 실행하여 Node 버전의 영향을 검증한다.

## 조치 검토 사항

- 패키지 관리 측에 2.0.0의 `exports`에 `./button` 경로 추가를 요청하는 방안을 검토한다.
- 사용처의 import를 2.0.0이 공개한 진입점 경로로 바꾸는 방안을 검토한다.
- 두 방안 모두 위 확인 방법의 결과가 나온 뒤에 선택한다.
