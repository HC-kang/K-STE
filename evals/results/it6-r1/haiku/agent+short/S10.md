CI에서만 실패하는 가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다. 다만 이것은 추론이므로 CI 로그와 로컬 재현으로 확인해야 합니다. 이 분석은 전달해 주신 정보만으로 작성했으며, 실제 코드와 CI 설정은 확인하지 않았습니다.

## 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드(패키지 바깥에서 쓸 수 있는 경로를 정하는 설정)가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`(설치할 패키지 버전을 기록한 파일)의 해시입니다.
- 로컬 `node_modules`(설치된 패키지가 담긴 폴더)는 3일 전보다 먼저 설치되었습니다.

## 추론

1.4.0에는 `exports` 필드가 없으므로 `@company/ui/button`처럼 하위 경로를 import하는 것이 허용됩니다. 2.0.0에서는 `exports`에 적힌 경로만 외부에서 import할 수 있습니다. 2.0.0의 `exports`에 `./button`이 없다면 이 import는 실패합니다.

로컬 빌드가 성공하는 이유는 로컬 `node_modules`에 아직 1.4.0이 남아 있기 때문으로 보입니다. 로컬에서 `npm install`을 다시 실행하지 않았다면 패키지는 2.0.0으로 바뀌지 않습니다.

CI가 실패하는 이유는 캐시 키가 lockfile 해시이기 때문으로 보입니다. lockfile이 2.0.0 기준으로 바뀌었다면 캐시가 일치하지 않아 CI는 새로 설치하고, 그 결과 2.0.0이 들어가 실패합니다.

| 항목 | 로컬 | CI |
|---|---|---|
| `@company/ui` 버전 | 1.4.0으로 추정 | 2.0.0으로 추정 |
| Node 버전 | 20 | 18 |
| `node_modules` 출처 | 3일 전 설치본 | 캐시 복원 또는 새 설치 (확인 필요) |
| `exports` 적용 | 적용 안 됨 | 적용됨 |

Node 18과 20은 모두 `exports`를 지원하므로 Node 버전 차이만으로 실패할 가능성은 낮습니다. 다만 Node 버전이 Next.js 설정이나 다른 의존성에 영향을 줄 가능성은 아직 배제하지 못했습니다.

오류 문구 `Cannot find module`은 Node가 `require`로 모듈을 찾지 못할 때 쓰는 형식입니다. Next.js 빌드 중의 모듈 해석 오류는 보통 `Module not found`로 표시되므로, 이 오류가 빌드 단계에서 났는지 다른 스크립트에서 났는지 확인이 필요합니다.

## 확인 필요

1. CI 로그에서 실제로 설치된 `@company/ui` 버전을 확인합니다.
2. 3일 전 변경 커밋에서 `package-lock.json`이 2.0.0으로 바뀌었는지 확인합니다.
3. 오류가 난 단계와 전체 스택 트레이스(오류가 발생한 호출 경로 기록)를 확인합니다.
4. CI 캐시 설정에 `restore-keys` 같은 대체 키가 있는지 확인합니다. 있다면 오래된 `node_modules`가 복원되었을 수 있습니다.
5. 로컬에서 Node 18로 바꾼 뒤 `rm -rf node_modules && npm ci`를 실행하고 빌드합니다. 같은 오류가 재현되면 버전 변경이 원인일 가능성이 높습니다.

## 해결 방향

1. `@company/ui` 2.0.0의 `exports`에 `./button` 경로를 추가합니다. 패키지를 관리하는 쪽에서 해야 하는 작업입니다.
2. 앱의 import 경로를 2.0.0이 공개한 경로로 바꿉니다.
3. 긴급하게 빌드를 살려야 하면 `@company/ui`를 1.4.0으로 되돌립니다. 가장 빠른 복구 방법입니다.

원인이 확인되면 1번이나 2번 중에서 고르는 것을 권장합니다.
