원인은 `@company/ui` 2.0.0의 `exports` 필드(패키지가 외부에 공개하는 경로 목록)가 `@company/ui/button` 경로를 공개하지 않는 것으로 보입니다. 로컬은 이 변경이 반영되지 않은 옛 설치본을 쓰고 있어서 빌드가 성공하는 것으로 추정합니다.

**확인된 사실**

- CI에서만 `Cannot find module '@company/ui/button'` 오류가 납니다.
- `@company/ui`를 1.4.0에서 2.0.0으로 올렸고, 2.0.0에서 `exports` 필드가 추가됐습니다.
- 로컬 `node_modules`는 3일 전 버전 업보다 먼저 설치한 것입니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.

**추론**

- 패키지에 `exports` 필드가 있으면 `exports`에 적힌 경로로만 내부 파일을 가져올 수 있습니다. 1.4.0에는 이 필드가 없어서 `@company/ui/button`이 파일 경로 그대로 열렸습니다.
- 로컬 `node_modules`는 업그레이드 전에 설치했으므로 아직 1.4.0일 가능성이 높습니다. 그래서 로컬에서는 기존 경로가 계속 동작합니다.
- `package-lock.json`이 2.0.0으로 바뀌었다면 캐시 키도 바뀌므로 CI는 2.0.0을 새로 설치합니다. 여기서 2.0.0의 `exports`에 맞지 않는 경로가 오류를 냅니다.
- Node 18과 20은 모두 `exports`를 지원하므로 Node 버전 차이는 주원인으로 보기 어렵습니다.

**미확인**

- 로컬에 실제로 설치된 `@company/ui` 버전.
- 2.0.0의 `exports`에 `./button`이 있는지, 있다면 어떤 경로로 공개되는지.
- 변경한 `package-lock.json`이 커밋에 포함돼 CI가 2.0.0을 설치하는지.

**확인 순서**

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다. 1.4.0이면 위 추론과 맞습니다.
2. CI와 같은 버전의 `node_modules/@company/ui/package.json`을 열어 `exports`에 `./button`이 있는지 확인합니다.
3. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드합니다. CI와 같은 오류가 나면 원인이 확정됩니다.

**수정 방향**

- 2.0.0이 버튼을 다른 경로로 공개하고 있으면 앱의 import 경로를 그 경로로 바꿉니다.
- 2.0.0이 버튼 경로를 공개하지 않으면 `@company/ui` 담당자에게 `exports`에 해당 경로를 추가해 달라고 요청합니다. 급하면 1.4.0으로 되돌립니다.
