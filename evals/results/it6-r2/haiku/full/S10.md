가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다. `exports` 필드는 패키지가 외부에 공개하는 경로를 정하는 설정입니다. 이 필드가 있으면 목록에 없는 하위 경로는 가져올 수 없습니다. 다만 2.0.0의 `exports` 목록에 `./button`이 빠져 있는지는 아직 확인하지 않았습니다.

이 가설은 로컬과 CI의 차이를 설명합니다.

- 로컬: 3일 전에 설치한 `node_modules`에는 1.4.0이 그대로 남아 있습니다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button` 경로가 동작합니다. 그래서 로컬 빌드는 성공합니다.
- CI: 2.0.0으로 올린 커밋에서 잠금 파일(`package-lock.json`)도 바뀌었다면 캐시 키가 달라져 CI가 새로 설치합니다. 새로 설치하면 2.0.0이 들어오고, `exports` 규칙에 따라 import가 실패합니다.

Node 버전 차이는 원인일 가능성이 낮습니다. Node 18도 `exports` 필드를 해석하기 때문입니다. 다만 2.0.0이 Node 20 이상을 요구하거나 Node 18이 처리하지 못하는 조건을 `exports`에 쓴다면 Node 버전이 원인이 될 수 있습니다. 이 부분은 확인되지 않았습니다. 참고로 Node 18은 2025년 4월에 지원이 끝났습니다.

원인을 확정하려면 다음을 확인하십시오.

1. CI 로그에서 설치된 `@company/ui` 버전을 확인하십시오. 2.0.0이면 가설이 맞을 가능성이 높습니다.
2. 설치된 `node_modules/@company/ui/package.json`의 `exports` 항목에 `./button`이나 `./*`가 있는지 보십시오. 없다면 이 경로 import가 실패하는 것이 설명됩니다.
3. 2.0.0 변경 로그에서 button 경로가 바뀌었는지, 공개 경로가 어떻게 바뀌었는지 확인하십시오.
4. CI 로그에서 캐시가 복원되었는지(hit 여부) 확인하십시오. 캐시가 복원되었다면 오래된 `node_modules`가 쓰였을 수 있습니다.
5. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드하십시오. 실패하면 CI와 같은 조건이 재현된 것입니다.

수정 방법은 확인 결과에 따라 정합니다. 2.0.0이 공개한 경로로 import를 바꾸는 것이 기본 방향입니다. 당장 빌드를 복구해야 하면 1.4.0으로 되돌리는 방법도 있습니다.

먼저 1번과 2번을 확인하십시오. 두 결과로 원인이 확정됩니다.
