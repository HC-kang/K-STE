## 결론

원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드로 보입니다. `exports`가 있으면 패키지 안에서 명시된 경로만 가져올 수 있으므로, `@company/ui/button`이 `exports`에 없으면 CI에서 해석이 실패합니다. 로컬은 3일 전에 설치한 1.4.0 파일이 그대로 남아 있어 같은 import가 성공합니다. 이 결론은 전달받은 정보에서 추론한 것이며, 아직 패키지 내용이나 빌드 로그로 확인하지 않았습니다.

## 로컬과 CI가 다르게 동작하는 이유

로컬 `node_modules`는 3일 전에 설치되었으므로 1.4.0이 들어 있습니다. 이후 `package.json`을 2.0.0으로 올렸어도 로컬에서 `npm install`이나 `npm ci`를 다시 실행하지 않으면 1.4.0이 계속 사용됩니다. 반면 CI는 캐시 키가 `package-lock.json` 해시이므로, lock 파일이 바뀌면 캐시를 쓰지 않고 2.0.0을 새로 설치합니다. 따라서 두 환경에서 서로 다른 버전의 패키지를 사용하고 있었습니다.

Node 버전 차이는 주요 원인일 가능성이 낮습니다. Node 18과 20 모두 `exports` 필드를 지원하기 때문입니다. 다만 완전히 배제하려면 로컬에서 Node 18로 확인해야 합니다.

## 가설 비교

| 가설 | 근거 | 가능성 | 확인 방법 |
|---|---|---|---|
| 2.0.0 `exports`에 `./button` 경로가 없다 | 2.0.0에서 `exports`가 추가되었고, 실패한 import가 하위 경로다 | 높음 | 2.0.0 패키지의 `package.json`에서 `exports` 항목을 확인한다 |
| 로컬은 1.4.0을 계속 쓰고 있다 | 로컬 `node_modules`가 3일 전 설치본이다 | 높음 | `npm ls @company/ui`로 로컬 버전을 확인한다 |
| Node 18과 20의 해석 차이 | CI와 로컬의 Node 버전이 다르다 | 낮음 | 로컬에서 Node 18로 클린 빌드를 실행한다 |
| CI 캐시가 오래된 설치본을 복원한다 | 캐시 키는 lock 해시지만 `restore-keys` 설정은 확인되지 않았다 | 낮음 | CI 캐시 설정에서 `restore-keys`를 확인한다 |

## 확인 필요 사항

- 확인 필요: 에러 메시지 형식이 맞는지 확인해야 합니다. `Cannot find module`은 Node의 CommonJS나 Jest에서 나오는 형식에 가깝습니다. `exports` 위반이면 Node는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`를 출력하고, Next.js 빌드는 `Module not found`를 출력합니다. 실패한 단계가 `next build`인지 테스트 단계인지 전체 스택 트레이스로 확인해야 합니다.
- 확인 필요: `package.json`과 `package-lock.json`이 같은 커밋에서 2.0.0으로 바뀌었는지 확인해야 합니다. 두 파일이 어긋나 있다면 CI 설치 결과도 달라질 수 있습니다.
- 확인 필요: 2.0.0의 마이그레이션 가이드에서 버튼 컴포넌트를 가져오는 공식 경로를 확인해야 합니다.

## 권장 조치

1. 로컬에서 Node 18로 `rm -rf node_modules && npm ci && npm run build`를 실행하여 CI 실패를 재현합니다. 재현되면 원인이 패키지 버전임이 확정되고, 재현되지 않으면 Node 버전이나 CI 설정을 봐야 합니다.
2. 2.0.0 문서에 따라 `@company/ui/button` import를 공식 경로로 바꿉니다.
3. `@company/ui`를 우리 팀이 관리한다면 `exports`에 `./button` 항목을 추가하는 방법을 검토합니다. 외부 패키지라면 임시로 1.4.0에 고정하는 방법이 있습니다.
4. CI 캐시 설정에서 `restore-keys`가 있는지 확인하고, 설치 단계가 항상 `npm ci`를 실행하도록 합니다.

이번 분석은 전달받은 정보만으로 작성했습니다. 코드 저장소, 패키지 내용, CI 로그는 확인하지 않았습니다.
