현재 원인은 확정되지 않았습니다. 가장 유력한 원인은 2.0.0에 새로 추가된 `exports` 필드입니다. 이 필드 때문에 `@company/ui/button` 같은 하위 경로가 CI에서 해석되지 않는 것으로 보입니다. 로컬에서 새로 설치해 재현하면 이 가설을 검증할 수 있습니다.

### 사실

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드가 추가됐습니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치됐습니다.
- 에러 문구는 `Error: Cannot find module '@company/ui/button'`입니다.

### 추론

로컬이 성공하는 이유는 `node_modules`에 1.4.0이 그대로 남아 있을 가능성이 큽니다. 1.4.0에는 `exports`가 없어서 `@company/ui/button`이 파일 경로로 그대로 풀립니다. 따라서 로컬 성공은 2.0.0에 문제가 없다는 근거가 되지 않습니다.

CI는 lock 파일 해시가 바뀌면 캐시가 맞지 않아 새로 설치합니다. 그래서 CI는 2.0.0을 받았을 가능성이 큽니다. `exports` 필드의 영향이 CI에서 처음 드러난 것으로 보입니다.

Node 버전 차이가 원인일 가능성은 낮게 봅니다. Node 18과 20 모두 `exports`를 지원하기 때문입니다. 다만 2.0.0의 `engines` 값이 Node 20 이상을 요구하면 이 판단은 달라집니다.

에러 문구의 `Error: Cannot find module`은 Node가 `require`에 실패할 때 나오는 형식입니다. 웹팩이 Next.js 빌드 중 내는 에러는 보통 `Module not found`로 나옵니다. 그래서 이 import는 웹팩 번들 단계가 아니라 Node가 직접 실행하는 파일(예: `next.config.js`나 빌드 보조 스크립트)에서 실패했을 수 있습니다.

### 확인 필요

- 확인 필요: 로컬 `node_modules`에 설치된 `@company/ui` 버전. `npm ls @company/ui`로 확인하십시오.
- 확인 필요: CI 로그의 설치 버전과 캐시 복원 결과. 캐시가 hit였는지, `restore-keys`로 오래된 캐시가 복원됐는지 봐야 합니다.
- 확인 필요: 2.0.0의 `exports` 맵에 `./button` 경로가 있는지, 있다면 어떤 파일을 가리키는지.
- 확인 필요: 2.0.0의 `engines` 값.
- 확인 필요: 에러가 난 파일과 import 위치.
- 확인 필요: 이 실패로 배포가 막혔는지 여부.

### 다음 단계

먼저 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치한 뒤 빌드하십시오. 같은 에러가 나면 원인이 2.0.0 설치로 좁혀집니다. 이어서 `nvm use 18`로 Node 18에서도 빌드하면 Node 버전의 영향까지 함께 확인됩니다. 에러가 나지 않으면 로컬의 오래된 `node_modules`가 성공 이유이므로, CI의 설치와 캐시 로그를 먼저 봐야 합니다.

수정 방법은 두 가지입니다. 2.0.0의 `exports` 맵에 같은 기능의 경로가 있으면 import 경로를 그 경로로 바꾸십시오. 경로가 없으면 2.0.0 제공자에게 `exports` 추가를 요청하거나, 수정이 나올 때까지 1.4.0으로 고정하십시오.
