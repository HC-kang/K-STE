가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다. 로컬에는 3일 전에 설치된 1.4.0이 남아 있어 문제가 드러나지 않고, CI는 2.0.0을 받아 실패하는 것으로 보입니다. 다만 에러 문구가 이 원인과 완전히 맞지 않아 아래 확인 항목을 먼저 점검해야 합니다.

## 확인된 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

## 원인 추정

`exports` 필드가 있으면 패키지는 공개한 경로로만 import를 허용합니다. 2.0.0의 `exports`에 `button` 경로가 없다면 `@company/ui/button` import는 차단됩니다. 1.4.0에는 `exports`가 없어서 모든 하위 경로를 import할 수 있었습니다. 그래서 오래된 1.4.0이 설치된 로컬에서는 빌드가 성공하고, 2.0.0을 받는 CI에서는 실패하는 것으로 추정합니다.

lock 파일이 2.0.0으로 바뀌었다면 캐시 키도 바뀌므로, CI는 캐시를 쓰지 않고 새로 설치해 2.0.0을 받았을 가능성이 높습니다.

| 항목 | 로컬 | CI |
| --- | --- | --- |
| 설치 시점 | 3일 전 이전 | 새로 설치 (추정) |
| `@company/ui` 버전 | 1.4.0 (추정) | 2.0.0 (추정) |
| `exports` 적용 | 없음 | 적용 |
| Node 버전 | 20 | 18 |

Node 버전 차이는 이 원인과 직접 관련이 낮습니다. Node 18과 20 모두 `exports` 필드를 지원하기 때문입니다.

에러 문구는 이 추정과 완전히 맞지 않습니다. Node는 `exports`에 막힌 경로를 열 때 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`를 냅니다. `Cannot find module`은 파일이나 패키지를 찾지 못했을 때 나오는 문구입니다. 따라서 CI에서 패키지가 제대로 설치되지 않았거나, 2.0.0에서 `button` 파일의 위치가 바뀌었을 가능성도 함께 봐야 합니다.

## 확인 필요

- 확인 필요: CI가 실제로 설치한 `@company/ui` 버전이 2.0.0인지 빌드 로그에서 확인해야 합니다.
- 확인 필요: 2.0.0의 `exports`에 `button` 경로가 정의되어 있는지 패키지 문서나 `package.json`에서 확인해야 합니다.
- 확인 필요: 2.0.0 패키지 안에 `button` 파일이 실제로 있는지 확인해야 합니다.
- 확인 필요: 2.0.0으로 바뀐 `package-lock.json`이 커밋되어 있는지 확인해야 합니다.
- 확인 필요: CI 캐시가 lock 해시 외에 다른 경로를 캐시하는지 확인해야 합니다.

## 권장 조치

1. CI 빌드 단계에 `npm ls @company/ui`를 추가해 설치된 버전과 경로를 로그로 남깁니다.
2. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드합니다. 로컬에서도 같은 에러가 나오면 원인이 2.0.0에 있다는 점이 확정됩니다.
3. 2.0.0의 `exports` 목록을 보고 `button` import를 공개된 경로로 바꿉니다. 공개된 경로가 없다면 `@company/ui` 담당자에게 문의합니다.
4. 빌드를 바로 복구해야 하면 `@company/ui`를 1.4.0으로 되돌리는 방법을 쓸 수 있습니다.
5. CI의 Node 버전을 20 이상으로 맞추는 것을 권장합니다. Node 18은 2025년 4월 30일에 지원이 종료되었습니다.
