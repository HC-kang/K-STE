원인은 2.0.0에서 추가된 `exports` 필드일 가능성이 가장 큽니다. 다만 아직 확인되지 않은 추론입니다.

로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 3일 전 설치본이어서 `@company/ui`가 1.4.0인 채로 남아 있기 때문으로 보입니다. 1.4.0에는 `exports` 필드가 없으므로 `@company/ui/button`이 파일 경로로 그대로 해석됩니다. 즉 로컬에서는 2.0.0으로 빌드를 검증한 적이 없습니다. `npm ls @company/ui`로 로컬 설치 버전을 확인하면 이 추론을 확정할 수 있습니다.

CI는 `package-lock.json` 해시로 캐시를 잡습니다. 락 파일이 2.0.0으로 갱신되어 커밋되었다면 캐시가 새로 만들어지고 2.0.0이 설치되었을 것입니다. 이 경우 `exports`에 맞지 않는 경로를 쓰는 코드가 CI에서 실패하는 것이 맞습니다. 다만 락 파일 갱신이 커밋에 반영되었는지는 확인되지 않았습니다.

원문 에러 형식도 판단 근거가 됩니다. `exports`가 하위 경로를 막으면 Node는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`를 냅니다. 원문은 `Cannot find module`이므로 다음 두 경우 중 하나일 수 있습니다. 하나는 `exports`에 `./button`이 없는 경우이고, 다른 하나는 경로는 허용되었지만 2.0.0 패키지에 해당 파일이 없는 경우입니다. 또한 이 메시지가 Node가 아니라 TypeScript나 webpack에서 나왔을 수도 있습니다.

Node 버전 차이는 가능성이 낮아 보입니다. Node 18과 20 모두 `exports`를 지원합니다. 다만 2.0.0이 ESM 전용이거나 조건부 `exports`를 쓴다면 두 버전의 해석 차이가 영향을 줄 수 있습니다. 이것도 확인되지 않았습니다.

| 가설 | 근거 | 확인 방법 |
|---|---|---|
| 2.0.0 `exports`에 `./button` 경로가 없음 | 2.0.0에 `exports` 추가, 로컬은 1.4.0 | 2.0.0 `package.json`의 `exports` 확인 |
| 경로는 허용되었으나 파일이 없음 | 에러가 `Cannot find module` 형식 | 설치된 2.0.0 패키지의 파일 목록 확인 |
| CI가 구버전을 설치함 | 캐시 키가 락 파일 해시 | CI 설치 로그의 `@company/ui` 버전 확인 |
| Node 18과 20의 해석 차이 | CI와 로컬의 Node 버전이 다름 | 로컬에서 Node 18로 재현 |

확인 필요: 에러를 낸 주체가 Node, webpack, TypeScript 중 무엇인지. 전체 스택 트레이스로만 가릴 수 있습니다.

확인 필요: 커밋된 `package-lock.json`에 기록된 `@company/ui` 버전. CI 설치 로그와 대조해야 합니다.

PM께는 실패 범위가 CI 빌드이고 로컬 빌드는 정상이라는 점을 공유하십시오. 개발자는 위 가설을 표의 순서대로 확인하고, 스택 트레이스와 2.0.0의 `exports` 항목을 먼저 확인하십시오.
