원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드로 보입니다. `exports`가 있는 패키지에서는 공개된 경로 밖의 하위 경로(`@company/ui/button`)를 import하면 해석에 실패합니다. 1.4.0에는 이 제한이 없었습니다. 로컬은 3일 전에 설치한 `node_modules`가 남아 있어 1.4.0으로 빌드되고, CI는 lock 파일 기준으로 새로 설치해 2.0.0으로 빌드되기 때문에 결과가 갈립니다.

## 확인된 사실

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에 `exports` 필드가 추가됐습니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치됐습니다.

## 추론

| 구분 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `node_modules` | 업그레이드 전에 설치됨 | lock 기준으로 새로 설치됨 (추정) |
| 실제 빌드에 쓰이는 `@company/ui` | 1.4.0으로 추정 | 2.0.0으로 추정 |
| 결과 | 성공 | 실패 |

- 1.4.0에는 `exports` 제한이 없어서 `@company/ui/button`이 그대로 해석됩니다.
- 2.0.0에서는 `exports`에 `./button` 항목이 없으면 같은 경로를 해석할 수 없습니다.
- Node 버전 차이는 주원인일 가능성이 낮습니다. Node 18과 20 모두 `exports`를 지원합니다.

## 확인 필요

- 확인 필요: 로컬 `node_modules`에 실제로 설치된 `@company/ui` 버전이 1.4.0인지. `npm ls @company/ui`로 확인해야 합니다.
- 확인 필요: 커밋된 `package-lock.json`에 2.0.0이 기록되어 있는지. 기록되어 있지 않으면 CI도 1.4.0을 설치하므로 이 가설은 맞지 않습니다.
- 확인 필요: 2.0.0의 `exports`에 `./button`에 해당하는 항목이 있는지. 패키지의 `package.json`을 봐야 합니다.
- 확인 필요: 에러가 Next.js 빌드 단계에서 발생했는지, 다른 스크립트에서 발생했는지.

## 재현과 검증

1. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드합니다. 같은 에러가 나오면 원인이 의존성 버전이라는 것이 확인됩니다.
2. CI 로그와 로컬에서 각각 `npm ls @company/ui`를 실행해 설치 버전을 비교합니다.
3. nvm 등으로 Node 18을 선택해 로컬 빌드를 재현합니다. 에러가 Node 버전과 무관한지 확인하는 단계입니다.

## 해결 방향

- 앱 코드에서 `@company/ui/button` 대신 2.0.0의 `exports`가 공개한 진입점을 import합니다. 어떤 진입점을 쓸 수 있는지는 패키지 문서를 확인해야 합니다.
- `@company/ui`를 사내에서 관리한다면 패키지 쪽 `exports`에 `./button` 항목을 추가하는 방법도 있습니다. 담당 팀과 조율이 필요합니다.
- 1.4.0으로 되돌리는 것은 임시 조치로만 쓰는 편이 낫습니다. 2.0.0 적용이 목표라면 근본 해결이 아닙니다.
