원인은 `@company/ui` 2.0.0으로 올린 뒤 CI가 패키지를 새로 설치하면서 `@company/ui/button` 경로를 찾지 못한 것으로 추정됩니다. 로컬에는 3일 전에 설치한 1.4.0 파일이 남아 있어 같은 문제가 드러나지 않습니다. 다만 아래 확인 항목으로 아직 검증하지 않았습니다.

주어진 정보에서 확인되는 사실은 다음과 같습니다.

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드가 추가됐습니다.
- CI 캐시 키는 `package-lock.json` 해시입니다.
- 로컬 `node_modules`는 업그레이드 전에 설치됐습니다.
- CI는 Node 18, 로컬은 Node 20을 사용합니다.

이 사실로부터 추론되는 내용은 다음과 같습니다.

- 로컬 빌드는 1.4.0 파일로 빌드되므로 2.0.0의 동작을 검증하지 못합니다.
- 업그레이드 커밋에서 lock 파일이 바뀌었다면 해시가 달라져 CI 캐시가 무효화되고, CI는 2.0.0을 새로 설치합니다.
- `exports` 필드가 `./button` 경로를 공개하지 않았다면 CI에서 해당 import가 실패합니다.
- Node 18과 20은 모두 `exports`를 지원하므로, Node 버전 차이만으로 이 실패가 생긴다고 보기는 어렵습니다.

확인이 필요한 부분은 다음과 같습니다.

- 2.0.0의 `package.json`에 `./button` 항목이 있는지, 그리고 그 항목이 가리키는 파일이 패키지에 실제로 있는지 확인이 필요합니다.
- 에러 문구가 `Cannot find module`인 점이 `exports` 차단 오류의 전형적인 문구와 다릅니다. Node의 exports 차단 오류는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`로 표시되므로, 파일 누락이나 번들러 경로 설정 문제일 가능성도 함께 봐야 합니다.
- CI 로그에서 실제 설치된 `@company/ui` 버전과 `node_modules/@company/ui`의 파일 목록을 확인해야 합니다.
- CI에서 캐시가 정확히 hit했는지, 아니면 `restore-keys`로 이전 캐시가 복원됐는지 확인해야 합니다.

먼저 로컬에서 `npm ls @company/ui`로 설치된 버전을 확인한 뒤, `rm -rf node_modules && npm ci`로 새로 설치하고 Node 18로 빌드해 CI 실패를 재현하십시오.
