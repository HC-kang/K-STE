# 결론

CI 빌드 실패의 가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드(패키지가 외부에 공개하는 import 경로를 정하는 설정)다. 2.0.0의 `exports`가 `@company/ui/button` 경로를 허용하지 않는 것으로 보인다. 이는 추론이며 아직 확인하지 않았다.

# 로컬과 CI가 다르게 동작하는 이유

로컬 `node_modules`는 3일 전보다 먼저 설치되었으므로 `@company/ui` 1.4.0이 그대로 남아 있을 가능성이 높다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`이 파일 경로로 해석된다. 그래서 로컬 빌드는 성공한다.

CI는 `package-lock.json`을 기준으로 패키지를 새로 설치하므로 2.0.0을 받는다. 2.0.0의 `exports`가 적용되면서 같은 import가 해석되지 않는다.

# 원인 후보 비교

| 후보 | 근거 | 가능성 | 확인 방법 |
|---|---|---|---|
| `exports`에 `./button` 경로가 없다 | 2.0.0에서 `exports`가 추가되었고, 1.4.0 상태의 로컬만 성공한다 | 높음 | 로컬에서 `npm ci`를 실행한 뒤 재현하고, `node_modules/@company/ui/package.json`의 `exports`를 확인한다 |
| 대소문자 차이 | macOS 로컬은 대소문자를 구분하지 않고, Linux 기반 CI는 구분한다 | 중간 | import 경로와 실제 파일명의 대소문자를 비교한다 |
| Node 18과 20의 차이 | 두 버전 모두 `exports`를 지원한다 | 낮음 | Node 18로 `npm ci`를 실행한 뒤 빌드한다 |
| 캐시 오염 | 캐시 키가 lock 파일 해시라서 1.4.0이 복원될 가능성이 낮다 | 낮음 | CI 로그에서 캐시 적중 여부와 실제 설치 버전을 확인한다 |

# 확인 필요

- 주어진 에러 메시지가 정확한지 확인해야 한다. Node가 `exports` 제한으로 실패하면 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED` 오류가 나온다. `Cannot find module`은 다른 도구가 낸 메시지일 수 있다.
- 실패가 어느 단계에서 발생하는지 확인해야 한다. 번들러, 타입 검사, 서버 빌드 중 어디인지에 따라 원인이 달라진다.
- 2.0.0의 `exports` 필드에 실제로 무엇이 들어 있는지 확인해야 한다.

# 권장 조치

1. CI 로그에서 실패한 파일명, 전체 오류 메시지, 실패 단계를 확인한다.
2. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드해 재현한다.
3. `node_modules/@company/ui/package.json`의 `exports`에 `./button` 항목이 있는지 확인한다.
4. 원인이 확인되면 다음 중 하나를 고른다. 임포트를 `exports`에 있는 경로로 바꾸거나, `@company/ui` 관리자에게 경로 추가를 요청한다.
5. 1.4.0으로 되돌리는 방법은 임시 조치로만 사용한다.

# PM 공유 사항

- 현재 CI 빌드는 실패하고 있다.
- 로컬 빌드는 정상이다. 그러나 새로 설치하는 개발자 환경에서는 같은 문제가 생길 가능성이 높다.
- 배포 일정에 미치는 영향은 확인 필요하다.
