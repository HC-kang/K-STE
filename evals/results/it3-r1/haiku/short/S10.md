가장 유력한 원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드(패키지가 외부에 공개할 경로를 정하는 설정)가 `button` 하위 경로를 공개하지 않아 import가 해석되지 않는 것이다. 이는 추론이며, 2.0.0 패키지 내용을 확인하기 전까지 확정하지 않는다.

## 근거

로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 3일 전 이전에 설치되어 1.4.0이 그대로 남아 있을 가능성이 높기 때문이다. `package.json`에 2.0.0이 적혀 있어도 `npm install`을 다시 실행하지 않으면 설치된 버전은 바뀌지 않는다. 이 경우 로컬은 `exports` 필드가 없는 1.4.0으로 빌드하므로 `@company/ui/button` 같은 하위 경로 import가 동작한다. 따라서 로컬 성공은 2.0.0에 문제가 없다는 근거가 되지 않는다.

`exports` 필드가 있으면 Node.js와 번들러는 그 목록에 적힌 경로만 허용한다. 목록에 `./button`이 없으면 하위 경로 import는 실패하고, 그 결과가 "Cannot find module" 에러로 나타난다. CI는 lock 파일에 따라 2.0.0을 새로 설치하므로 같은 에러가 재현되는 것과 일치한다.

## 확인하지 않은 사항

Node 18과 Node 20의 차이는 이 에러의 직접 원인일 가능성이 낮다고 판단한다. Node 18도 `exports` 필드를 지원하기 때문이다. 다만 실제로 확인하지 않았다.

CI 캐시 키는 `package-lock.json`의 해시이므로, 업그레이드 커밋에서 lock 파일이 바뀌었다면 캐시가 무효화되어 2.0.0이 새로 설치되었을 것이다. lock 파일이 바뀌지 않았다면 오래된 캐시가 복원되었을 수 있다. 확인 필요: 업그레이드 커밋에 lock 파일 변경이 포함되었는지 여부.

## 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행하여 실제 설치 버전을 확인한다. 1.4.0으로 나오면 로컬이 업그레이드를 반영하지 않은 상태이므로 원인 가설을 뒷받침한다.
2. `npm view @company/ui@2.0.0 exports`를 실행하여 2.0.0의 공개 경로 목록에 `./button`이 있는지 확인한다.
3. `git log -p -- package-lock.json`으로 업그레이드 커밋에서 lock 파일이 바뀌었는지 확인한다.
4. CI 로그에서 캐시 복원 단계와 설치 단계가 실제로 설치한 `@company/ui` 버전을 확인한다.
5. 프로젝트에서 `grep -r "@company/ui/" src`를 실행하여 하위 경로 import가 어디에 있는지 목록을 만든다.

## 조치 방안

원인이 확인되면 다음 중 하나를 선택한다.

1. 해당 import를 2.0.0이 공개하는 경로로 바꾼다. 이 방법이 가장 직접적이다.
2. 패키지 관리 팀에 `button` 경로의 공개를 요청한다.
3. `@company/ui`를 1.4.0으로 되돌린다. 빌드는 복구되지만 2.0.0 적용이 미뤄지므로 임시 조치로만 사용한다.
