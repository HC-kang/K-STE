현재 자료로는 원인을 확정할 수 없습니다. 가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드가 `@company/ui/button` 같은 하위 경로 import를 막는 것입니다. 다만 로컬과 CI에서 실제로 설치된 버전을 확인하기 전까지는 추론입니다.

## 확인된 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.
- CI 빌드는 `Cannot find module '@company/ui/button'` 에러로 실패합니다.
- 로컬 빌드는 성공합니다.

## 가장 유력한 원인 (추론)

`exports` 필드가 있으면 패키지는 외부에서 import할 수 있는 경로를 그 목록으로 제한합니다. 1.4.0에는 이 필드가 없어서 `@company/ui/button`처럼 내부 파일을 직접 가리키는 import가 동작했습니다. 2.0.0의 `exports`에 `./button`이 없거나 파일 경로가 바뀌었다면, 같은 import가 실패합니다.

다만 에러 문구가 이 가설과 완전히 맞지는 않습니다. `exports`에 의한 차단은 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED` 코드로 나타나고, `Cannot find module`은 주로 파일 경로가 실제로 없을 때 나오는 문구입니다. 따라서 전체 스택 트레이스와 에러 코드를 함께 확인해야 합니다.

## 로컬 빌드가 성공하는 이유 (추론)

로컬 `node_modules`가 3일 전보다 먼저 설치되었으므로, 로컬은 1.4.0을 계속 쓰고 있을 가능성이 큽니다. 이 경우 로컬 빌드의 성공은 2.0.0 문제와 무관합니다. 로컬이 실제로 2.0.0을 쓰는지는 자료에 없습니다.

## 환경 차이

| 항목 | 로컬 | CI | 원인 가능성 |
|---|---|---|---|
| Node 버전 | 20 | 18 | 낮음. Node 12.7 이상은 `exports`를 지원합니다. |
| 설치된 `@company/ui` 버전 | 미확인 (1.4.0 가능성 높음) | 미확인 (2.0.0 가능성 높음) | 높음. 핵심 후보입니다. |
| 캐시 복원 여부 | 해당 없음 | 미확인 | 낮음에서 중간. 오래된 캐시가 복원되면 설치 버전이 달라질 수 있습니다. |

Node 버전은 `exports` 해석 차이의 직접 원인으로 보기 어렵습니다. 다만 Next.js나 의존성이 Node 20을 요구하는지는 확인하지 않았습니다.

캐시 키가 lock 파일 해시이므로, lock 파일이 바뀐 커밋에서는 CI가 새로 설치하며 2.0.0을 받습니다. 이 경우 CI 실패는 가설과 맞습니다. lock 파일이 바뀌지 않았다면 CI는 lock 파일에 적힌 버전을 설치하므로, 가설과 맞지 않습니다.

## 확인 필요

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. `package-lock.json`에서 `@company/ui` 항목이 2.0.0인지 확인합니다.
3. 2.0.0 패키지의 `package.json`에서 `exports`에 `./button`이 있는지 확인합니다.
4. CI 캐시를 지우고 다시 실행해서 오래된 캐시가 원인인지 배제합니다.
5. CI 로그에서 전체 에러 스택과 에러 코드를 확인합니다.
6. 실패하는 import를 `exports`에 정의된 경로로 바꿀 수 있는지 검토합니다.
