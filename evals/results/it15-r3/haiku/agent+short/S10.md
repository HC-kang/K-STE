CI에서만 실패하는 가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드입니다. 이 필드가 `@company/ui/button` 경로를 공개하지 않거나 다른 경로로 옮겼을 가능성이 있고, 로컬은 3일 전에 설치한 1.4.0을 써서 이 제한을 받지 않는 것으로 보입니다. 다만 아래 미확인 항목을 확인하기 전에는 확정할 수 없습니다.

## 확인된 사실

- CI 빌드에서만 `Cannot find module '@company/ui/button'` 에러가 발생합니다.
- 로컬 빌드는 성공합니다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에 `exports` 필드(패키지 바깥에 공개할 파일 경로를 정한 설정)가 추가됐습니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`(설치할 정확한 버전을 기록한 파일)의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치했습니다.

## 추론

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `@company/ui` 버전 | 1.4.0으로 추정 (3일 전 설치본) | 2.0.0으로 추정 (lock 파일 변경으로 캐시가 무효화되어 새로 설치) |
| `exports` 제한 적용 | 적용되지 않음 (1.4.0에는 `exports`가 없음) | 적용됨 |

가장 유력한 경로는 다음과 같습니다. 올린 커밋에 `package-lock.json` 변경이 포함됐다면 캐시 키가 바뀌어 CI가 2.0.0을 새로 설치합니다. 2.0.0의 `exports`가 `./button` 경로를 빠뜨렸거나 다른 경로로 옮겼다면 import가 실패합니다. 로컬은 옛 버전을 그대로 써서 통과합니다.

Node 버전이 직접 원인일 가능성은 낮게 봅니다. Node 18과 20 모두 `exports`를 지원하기 때문입니다. 다만 Node 버전과 패키지 버전이 동시에 달라서, 지금 상태로는 둘 중 무엇이 원인인지 나눠 볼 수 없습니다.

**로컬 빌드 성공은 2.0.0 빌드가 통과했다는 뜻이 아닙니다.** 로컬에 2.0.0이 설치돼 있는지부터 확인해야 합니다.

에러 문구도 확인이 필요합니다. `Cannot find module`은 Node가 `require`를 처리할 때 내는 형식입니다. 번들러(Next.js가 쓰는 webpack 등)는 보통 다른 문구를 냅니다. 어느 도구가 이 메시지를 냈는지에 따라 원인을 좁히는 방향이 달라집니다.

## 미확인 항목

- 올린 커밋이 `package-lock.json`도 바꿨는지
- 2.0.0의 `exports`에 `./button` 경로가 있는지
- 로컬 `node_modules`에 실제로 1.4.0이 설치돼 있는지
- CI 캐시 설정에 `restore-keys`(정확히 일치하는 캐시가 없을 때 쓸 이전 캐시 이름)가 있어서 오래된 캐시가 복원되는지
- 에러 메시지를 낸 도구가 무엇인지

## 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 확인합니다.
3. CI 로그에서 설치 단계의 실제 버전을 확인합니다. 필요하면 `npm ls @company/ui` 단계를 추가합니다.
4. 로컬에서 Node 18로 바꾼 뒤 `rm -rf node_modules && npm ci`를 실행하고 빌드합니다. 이렇게 하면 Node 버전과 패키지 버전의 영향을 나눠 볼 수 있습니다.
5. CI 워크플로의 캐시 설정에서 `restore-keys` 항목을 확인합니다.

## 조치 방안

| 방안 | 내용 | 특징 |
|---|---|---|
| import 경로 변경 | `exports`에 공개된 경로(예: 패키지 루트)에서 import합니다. | 앱 코드만 고치면 됩니다. 가장 빠릅니다. |
| 패키지에 `exports` 추가 | `@company/ui`에 `./button` 경로를 추가합니다. | 패키지 관리자가 고쳐야 합니다. 이 패키지를 쓰는 다른 앱도 영향을 받습니다. |
| 1.4.0으로 고정 | 버전을 1.4.0으로 되돌립니다. | 임시 조치입니다. 2.0.0 호환 문제는 그대로 남습니다. |

원인이 `exports` 누락으로 확인되면, 패키지를 우리가 관리하는 경우에는 패키지에 경로를 추가하는 방안을, 빠르게 막아야 하는 경우에는 import 경로를 바꾸는 방안을 권장합니다.
