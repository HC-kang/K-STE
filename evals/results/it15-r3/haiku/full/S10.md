원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드일 가능성이 가장 큽니다. `exports`가 있으면 외부에서 import할 수 있는 경로가 그 목록으로 제한됩니다. 2.0.0 목록에 `./button`이 없거나 경로가 바뀌었다면 `@company/ui/button` import는 어느 환경에서든 실패해야 합니다. 로컬 빌드가 성공했다는 사실만으로는 이 가능성을 배제할 수 없습니다.

로컬이 성공하는 이유는 다음과 같이 추정됩니다. 로컬 `node_modules`가 3일 전 이전에 설치되었다면, 로컬은 1.4.0을 쓰고 있을 가능성이 큽니다. 1.4.0에는 `exports` 제한이 없어서 같은 import가 통과합니다. 이 경우 로컬은 2.0.0으로 빌드해 본 적이 없습니다.

Node 버전 차이(CI 18, 로컬 20)가 직접 원인이라는 근거는 아직 없습니다. Node 18과 20은 모두 `exports`를 지원하므로, 지원 여부 자체의 차이로 보기는 어렵습니다. 다만 번들러가 조건부 `exports`를 해석하는 방식에 버전 차이가 영향을 줄 가능성은 남아 있으므로 함께 확인해야 합니다.

캐시 키가 `package-lock.json` 해시이므로 lock 파일이 바뀌면 캐시 키도 바뀝니다. 그러나 `restore-keys` 같은 부분 일치 fallback을 쓰고 있다면 오래된 `node_modules`가 복원되어 CI가 의도와 다른 버전으로 빌드했을 수 있습니다.

아직 확인되지 않은 사실은 다음과 같습니다.
- 2.0.0의 `exports` 목록에 `./button`이 있는지
- CI가 실제로 2.0.0을 설치했는지
- 사용 중인 Next.js 버전이 Node 18을 지원하는지

다음 순서로 확인하십시오.
1. `npm view @company/ui@2.0.0 exports`를 실행하여 2.0.0의 `exports` 목록을 확인하십시오.
2. 로컬에서 `npm ls @company/ui`를 실행하여 설치된 버전을 확인하십시오. 1.4.0이면 로컬 빌드는 2.0.0을 검증하지 않은 것입니다.
3. CI 로그의 설치 단계에 나온 `@company/ui` 버전과 `package-lock.json`의 항목을 대조하십시오.
4. CI 캐시 복원 로그에서 캐시가 정확히 일치했는지, 부분 일치로 복원됐는지 확인하십시오.

1번에서 `./button`이 목록에 없다고 나오면, `@company/ui` 쪽 `exports`에 `./button`을 추가하거나 앱의 import 경로를 `exports`에 있는 경로로 바꾸는 방법이 있습니다. 그다음 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치한 뒤 빌드하여 2.0.0 기준으로 재현하십시오. Node 18 재현이 필요하면 `nvm use 18`로 전환하여 같은 빌드를 실행하십시오.
