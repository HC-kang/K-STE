CI 빌드는 `@company/ui` 2.0.0을 설치해서 실패하고, 로컬 빌드는 1.4.0이 그대로 남아 있어서 성공하는 것으로 보입니다. 두 환경이 실제로 서로 다른 버전을 쓰고 있다는 것이 핵심입니다.

## 추론

`exports` 필드는 패키지가 외부에 공개할 파일 경로를 적어 두는 목록입니다. 이 필드가 있으면 Node는 목록에 없는 경로를 불러오지 못합니다. 1.4.0에는 `exports`가 없어서 `@company/ui/button`처럼 패키지 안쪽 파일을 직접 불러와도 됐습니다. 2.0.0에는 `exports`가 생겼고, 여기에 `./button`이 없거나 이름이 바뀌었다면 같은 import가 `Cannot find module` 에러를 냅니다.

로컬이 성공하는 이유는 `node_modules`를 3일 전보다 먼저 설치했기 때문입니다. 로컬에는 아직 1.4.0이 있고, 1.4.0에서는 이 import가 동작합니다. CI는 `package-lock.json`의 해시가 바뀌어 캐시(이전 설치 결과를 재사용하는 기능)를 쓰지 못하고 새로 설치하므로 2.0.0을 받습니다.

Node 18과 20의 차이는 원인일 가능성이 낮습니다. 두 버전 모두 `exports`를 지원하기 때문입니다.

## 아직 확인하지 않은 것

- 로컬 `node_modules`의 `@company/ui`가 실제로 1.4.0인지 확인하지 않았습니다.
- 2.0.0의 `exports`에 `./button`이 있는지 확인하지 않았습니다.
- 다른 import 경로에도 같은 문제가 있는지 확인하지 않았습니다.

## 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 봅니다.
2. 로컬에서 `node_modules/@company/ui/package.json`의 `version`과 `exports`를 봅니다.
3. 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치한 뒤 빌드합니다. CI와 같은 에러가 나면 원인이 확정됩니다.
4. 코드에서 `@company/ui/`로 시작하는 import를 모두 검색해 `exports`에 있는 경로와 비교합니다.

## 해결 방안

- 2.0.0의 `exports`에 새 경로가 있으면 import를 그 경로로 바꿉니다.
- 새 경로가 없으면 `@company/ui` 담당자에게 `./button` 추가를 요청합니다.
- 급하게 빌드를 복구해야 하면 `@company/ui`를 1.4.0으로 되돌립니다. 다만 업그레이드 목적이 사라지므로 임시 조치로만 권장합니다.

재발을 막으려면 로컬 Node를 CI와 같은 버전으로 맞추고, 의존성을 올린 뒤에는 `npm ci`로 다시 설치해 빌드하는 것을 권장합니다.
