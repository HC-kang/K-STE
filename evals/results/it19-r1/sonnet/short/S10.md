가장 유력한 원인은 로컬이 아직 `@company/ui` 1.4.0을 쓰고, CI만 2.0.0을 설치해서 새로 생긴 `exports` 필드(패키지가 외부에 공개하는 import 경로 목록)의 제한을 받는 것입니다. 이 결론은 아래 사실에서 추론한 것이고, 아직 확인하지 않았습니다.

**사실**
- 빌드는 CI에서만 실패하고, 로컬에서는 성공합니다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0부터 패키지에 `exports` 필드가 있습니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치한 것입니다.

**추론**
- 로컬 `node_modules`에는 1.4.0이 남아 있을 가능성이 높습니다. 1.4.0에는 `exports`가 없으므로 `@company/ui/button`이 파일 경로로 그대로 열립니다.
- CI는 2.0.0을 설치합니다. `exports`가 있는 패키지는 목록에 적힌 경로만 import할 수 있으므로, `./button`이 목록에 없으면 import가 실패합니다.
- 2.0.0에서 button 파일의 위치나 이름이 바뀌었을 가능성도 있습니다. 이 경우에도 증상은 같습니다.
- Node 버전 차이는 원인일 가능성이 낮습니다. Node 18과 Node 20은 둘 다 `exports`를 지원합니다.

**미확인**
- 확인 필요: 로컬에 실제로 설치된 `@company/ui` 버전.
- 확인 필요: 2.0.0의 `exports`에 `./button`이 있는지.
- 확인 필요: 업그레이드 커밋에 `package-lock.json` 변경이 포함됐는지. 캐시 키가 lockfile 해시이므로, lockfile이 바뀌었다면 CI는 캐시를 쓰지 않고 새로 설치했을 것입니다.
- 확인 필요: 에러 문구가 `Cannot find module`입니다. `exports` 때문에 막힌 경우에는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED` 또는 번들러(webpack 등)의 "Can't resolve" 문구가 나옵니다. 문구가 다르므로 파일 자체가 없는 경우도 함께 봐야 합니다.

**확인 순서**
1. 로컬에서 `npm ls @company/ui`를 실행해 설치 버전을 확인합니다.
2. `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 로컬에서 빌드합니다. CI와 같은 에러가 나오면 원인은 버전 차이로 확정됩니다.
3. 설치된 `node_modules/@company/ui/package.json`의 `exports`에서 `./button`을 찾습니다.

2단계에서 에러가 재현되면, 3단계 결과에 따라 import 경로를 `exports`에 있는 경로로 바꾸거나, 패키지 관리자에게 `./button` 공개를 요청해야 합니다.
