원인은 2.0.0에 새로 추가된 `exports` 필드일 가능성이 높습니다. 이 필드가 있으면 패키지 바깥에서 import할 수 있는 경로가 목록으로 제한되는데, `@company/ui/button`이 그 목록에 없거나 2.0.0 패키지에 해당 파일이 없을 수 있습니다. 다만 아래 가정 중 일부는 아직 확인하지 않았으므로 확인 순서를 거쳐야 합니다.

## 로컬에서는 성공하고 CI에서만 실패하는 이유

로컬 `node_modules`는 3일 전보다 먼저 설치되었으므로 `@company/ui` 1.4.0이 들어 있을 가능성이 높습니다. 1.4.0에는 `exports` 필드가 없어서 하위 경로 import가 제한 없이 동작합니다. 이것은 설치 시점으로 추론한 내용이며, 실제 설치 버전은 `npm ls @company/ui`로 확인해야 합니다.

CI는 `package-lock.json` 해시를 캐시 키로 씁니다. 업그레이드로 lockfile이 바뀌었다면 CI 캐시가 맞지 않아 새로 설치하게 되고, 이때 2.0.0이 설치되었을 가능성이 큽니다. 캐시 히트 여부는 CI 로그의 설치 단계에서 확인할 수 있습니다.

Node 버전 차이는 원인으로 보기 어렵습니다. Node 18과 20 모두 `exports`를 해석하므로 버전 차이만으로 이 오류가 나지는 않습니다. 다만 CI에서 Node 버전만 20으로 바꿔 한 번 실행하면 이 가능성을 확실히 배제할 수 있습니다.

## 에러 메시지에 대한 주의

Node가 `exports`에서 막은 하위 경로는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`라는 다른 문구로 나옵니다. 지금 보신 `Cannot find module`은 파일을 찾지 못했다는 뜻이므로, 2.0.0에서 해당 파일의 위치가 바뀌었거나 파일이 빠졌을 가능성도 있습니다. 전체 에러 원문과 스택 트레이스를 함께 확인하십시오.

## 사실, 추론, 미확인

| 구분 | 내용 |
|---|---|
| 사실 | 2.0.0에 `exports` 추가, CI는 Node 18과 lockfile 해시 캐시 사용, 로컬은 Node 20과 업그레이드 전 설치본 사용, 에러는 `Cannot find module '@company/ui/button'` |
| 추론 | 로컬은 1.4.0, CI는 2.0.0을 사용 중이며 `exports`가 `button` 경로를 막고 있음 |
| 미확인 | 실제 설치 버전, 2.0.0의 `exports` 내용, 2.0.0 패키지 안의 button 파일 존재 여부, 에러 원문 |

## 확인 순서

1. CI 설치 단계에 `npm ls @company/ui`를 추가해 실제 설치 버전과 캐시 히트 여부를 확인하십시오.
2. 2.0.0의 `package.json`에서 `exports` 항목을 열어 `./button` 또는 이에 대응하는 경로가 있는지 확인하십시오.
3. 2.0.0 패키지 안에 button 파일이 있는지 확인하십시오. 파일이 없다면 `exports` 문제가 아니라 경로 변경 문제입니다.
4. 로컬에서 `npm ci`로 새로 설치한 뒤 빌드해 재현하는지 확인하십시오. 재현되면 로컬 환경 차이가 아니라 설치된 패키지 문제입니다.
5. 원인이 정해지면 수정 방향을 고르십시오. 하나는 import 경로를 2.0.0이 허용한 경로로 바꾸는 것이고, 다른 하나는 `@company/ui` 쪽 `exports`에 해당 경로를 추가해 달라고 요청하는 것입니다.

개발자는 1번부터 3번까지 먼저 확인하십시오. PM께서는 현재 상태가 CI 빌드 실패이며, 원인은 위 확인으로 정해진다는 점을 참고하시면 됩니다.
