현재 정보로는 원인을 하나로 확정할 수 없습니다. 가장 가능성이 높은 설명은 로컬과 CI가 서로 다른 버전의 `@company/ui`를 쓰고 있다는 것입니다. 이 분석은 코드, 로그, 설치된 패키지를 직접 확인하지 않고 전달받은 정보만으로 작성했습니다.

### 확인된 사실

- CI 빌드는 실패하고, 로컬 빌드는 성공합니다.
- `@company/ui`는 3일 전에 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0에는 `exports` 필드(패키지가 외부에 공개할 파일 경로를 정한 설정)가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`(설치할 패키지 버전을 고정하는 파일)의 해시(파일 내용을 요약한 값)입니다.
- 로컬 `node_modules`(설치된 패키지가 담긴 폴더)는 3일 전보다 먼저 설치되었습니다.

### 추론

로컬 빌드가 성공하는 이유는 `node_modules`가 3일 전 이전에 설치되어 `@company/ui` 1.4.0을 그대로 쓰기 때문일 가능성이 큽니다. 다만 3일 뒤에 다시 설치했는지는 알 수 없습니다.

`package-lock.json`이 바뀌면 캐시 키도 바뀌므로 CI는 기존 캐시를 쓰지 못하고 새로 설치합니다. 바뀐 락 파일에 2.0.0이 반영되어 있다면 CI는 2.0.0을 받습니다. 이때 2.0.0의 `exports`에 `@company/ui/button` 경로가 없으면 CI에서 이 import가 실패합니다.

에러 문구 `Cannot find module`은 Node가 모듈을 불러올 때 내는 형식입니다. Next.js의 webpack 빌드 단계는 보통 `Module not found` 문구를 씁니다. 그러므로 이 에러는 Node가 설정 파일이나 스크립트를 직접 읽는 단계에서 났을 가능성이 있습니다.

Node 18과 20의 차이만으로 이 에러를 설명하기는 어렵습니다. `exports` 필드는 Node 18에서도 지원되기 때문입니다. 다만 Node 버전이 결과에 영향을 주는지는 실행해 보지 않았으므로 미확인입니다.

### 가설 비교

| 가설 | 근거 | 확인 방법 |
|---|---|---|
| CI가 2.0.0을 설치했고, 2.0.0의 `exports`에 `./button` 경로가 없다 | 3일 전 업그레이드, `exports` 필드 추가 | CI 로그의 설치 버전, 2.0.0 `package.json`의 `exports` 항목 |
| CI 설치 결과에 `@company/ui`가 없거나 필요한 파일이 빠졌다 | `Cannot find module` 문구 | CI의 설치 단계 로그 |
| Node 18과 20의 차이가 원인이다 | 실행 환경이 다르다 | Node 18로 로컬에서 재현 |

### 확인 필요

1. CI 로그에서 에러가 난 단계를 확인합니다.
2. CI 로그에서 설치된 `@company/ui` 버전을 확인합니다.
3. 로컬 `node_modules/@company/ui/package.json`에서 버전을 확인합니다.
4. 2.0.0의 `exports` 항목에 `button` 경로가 있는지 확인합니다.
5. 2.0.0이 반영된 `package-lock.json`이 저장소에 커밋되었는지 확인합니다.

확인 결과 `exports`에 `button` 경로가 없다면 import 경로를 2.0.0이 공개한 경로로 바꾸거나, `@company/ui`를 1.4.0으로 되돌려야 합니다.
