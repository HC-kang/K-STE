CI 빌드 실패의 가장 유력한 원인은 로컬과 CI가 서로 다른 `@company/ui` 버전을 쓰고 있기 때문이다. 이는 추론이며, 아직 확인하지 않았다.

로컬 `node_modules`는 3일 전보다 먼저 설치되었다. 따라서 로컬에는 1.4.0이 그대로 남아 있을 가능성이 높다. 1.4.0에는 `exports` 필드가 없으므로 `@company/ui/button`이 파일 경로로 해석되고, 로컬 빌드가 성공한다.

CI는 캐시 키가 `package-lock.json` 해시이므로, lockfile이 바뀌면 캐시가 새로 만들어진다. CI가 새로 설치하면서 2.0.0을 받았을 가능성이 높다. 이 경우 2.0.0의 `exports` 필드가 적용되어 `@company/ui/button`을 찾지 못한다는 것이 현재 가설이다.

이 가설에는 맞지 않는 부분이 하나 있다. `exports` 필드가 막은 경로에 Node가 내는 전형적인 메시지는 `ERR_PACKAGE_PATH_NOT_EXPORTED`인데, 보고된 에러는 `Cannot find module`이다. 따라서 `exports` 때문인지, 2.0.0에서 파일 위치가 바뀌어 실제 파일이 없는 것인지, TypeScript나 번들러의 해석 방식 때문인지는 CI 전체 스택을 봐야 구분할 수 있다.

Node 버전 차이도 원인 후보에 넣어 두지만, Node 18과 20은 모두 `exports` 필드를 지원한다. 따라서 Node 버전 차이만으로 이 실패를 설명하기는 어렵다는 것이 현재 판단이다.

검증은 다음 순서로 하면 된다.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인한다.
2. CI 로그에서 설치된 `@company/ui` 버전과 에러가 난 빌드 단계(Next.js, TypeScript 타입 검사, 번들러 중 하나)를 확인한다.
3. 로컬에서 `node_modules`를 지우고 `npm ci`로 설치한 뒤 Node 20으로 빌드한다.
4. 같은 빌드를 Node 18로 실행해 실패가 재현되는지 확인한다.
5. 2.0.0의 `package.json`에서 `exports`에 `./button` 항목이 있는지, 그 경로의 파일이 실제로 있는지 확인한다.

확인 필요: 3일 전 변경에 `package-lock.json`이 함께 들어갔는지 확인해야 한다. 들어가지 않았다면 CI도 1.4.0을 받았을 것이므로 현재 가설과 맞지 않는다.

확인 필요: CI가 `node_modules`를 캐시하는지, `~/.npm`만 캐시하는지 확인해야 한다. 이에 따라 "캐시가 새로 만들어진다"는 설명의 범위가 달라진다.

가설이 맞다면 import 경로를 2.0.0의 `exports`에 맞게 바꾸는 것을 권장한다. 원인이 확인되기 전에는 1.4.0으로 되돌리는 방안도 함께 검토할 수 있다.
