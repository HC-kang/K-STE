현재 가장 유력한 원인은 CI가 `@company/ui` 2.0.0을 새로 설치했고, 2.0.0의 `exports` 필드(패키지가 외부에 공개할 파일 경로를 정하는 설정)가 `button` 경로를 공개하지 않아 임포트가 실패하는 것입니다. 아직 검증하지 않은 추정이므로 아래 확인 방법으로 먼저 확인합니다.

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `@company/ui` 버전 | 1.4.0으로 추정 | 2.0.0으로 추정 |
| 설치 방식 | 3일 전 설치본(`node_modules`) 재사용으로 추정 | 새로 설치로 추정 |
| 빌드 결과 | 성공 | 실패 |

### 확인된 사실

- 에러 메시지는 `Cannot find module '@company/ui/button'`입니다.
- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시(설치 결과를 저장해 두는 공간)의 키는 `package-lock.json`(설치 버전을 고정하는 파일)의 해시(내용을 요약한 고유 값)입니다.
- 로컬 `node_modules`(설치된 외부 패키지가 담긴 폴더)는 3일 전보다 먼저 설치되었습니다.

### 추론

- 로컬 `node_modules`에는 아직 1.4.0이 남아 있을 가능성이 큽니다. 그러므로 **로컬 빌드의 성공은 2.0.0이 정상 동작한다는 근거가 되지 않습니다.**
- 2.0.0의 `exports` 필드가 `./button` 경로를 공개하지 않아 `@company/ui/button` 임포트(다른 파일의 코드를 가져오는 구문)가 실패한다고 추정됩니다.
- CI 캐시 키가 lockfile 해시이므로, 업그레이드 커밋에서 lockfile이 함께 바뀌었다면 CI는 캐시를 쓰지 않고 2.0.0을 새로 설치합니다.
- Node 18과 Node 20의 차이가 원인이라는 근거는 아직 없습니다.

### 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. CI 로그의 설치 단계에서 `@company/ui`의 설치 버전을 확인합니다.
3. `node_modules/@company/ui/package.json`의 `exports` 항목에 `./button`이 있는지 확인합니다.
4. 업그레이드 커밋에 `package-lock.json`이 포함되었는지 확인합니다.
5. 확인 필요: CI 캐시 설정에 이전 캐시를 대신 쓰게 하는 대체 키(restore-keys)가 있는지 확인합니다.
