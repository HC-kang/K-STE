CI 빌드 실패의 가장 유력한 원인은 2.0.0의 `exports` 필드 때문에 `@company/ui/button` 같은 하위 경로 import가 막히는 것이다. 로컬은 3일 전 설치한 1.4.0을 아직 쓰고 있을 가능성이 높아서 빌드가 성공한다. 다만 아래 확인 절차를 거치기 전까지는 추론이다.

## 확인된 사실

- CI에서 Next.js 빌드가 `Cannot find module '@company/ui/button'` 오류로 실패한다.
- 로컬 빌드는 성공한다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0 패키지에는 `exports` 필드가 있다. `exports`는 패키지가 바깥에 공개하는 경로 목록이다. 목록에 없는 경로로 import하면 Node.js와 번들러(코드를 묶어 빌드하는 도구)가 이를 막을 수 있다.
- CI는 Node 18을, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`(설치 버전을 고정하는 파일)의 해시다.
- 로컬 `node_modules`(패키지가 설치되는 폴더)는 3일 전 업그레이드 이전에 설치되었다.

## 원인 추정

로컬 `node_modules`는 업그레이드 이전 설치본이므로 1.4.0일 가능성이 높다. 1.4.0에는 `exports`가 없어서 `@company/ui/button`이 파일 경로로 그대로 찾아진다. 반면 CI는 2.0.0을 설치하므로 같은 import가 `exports` 목록에서 막힌다. 따라서 로컬이 성공하는 이유는 코드가 맞아서가 아니라 로컬에 옛 버전이 남아 있어서일 수 있다.

오류 문구에는 주의가 필요하다. Node.js가 `exports`에 의해 막힌 경로를 만나면 보통 `Package subpath ... is not defined by "exports"` 형태의 다른 오류를 낸다. `Cannot find module`은 파일이 실제로 없을 때 나오는 문구이므로, 2.0.0에서 `button` 파일의 위치가 바뀌었을 가능성도 배제할 수 없다. 어떤 도구가 이 오류를 냈는지는 전체 스택 트레이스(오류가 발생한 호출 경로)를 봐야 알 수 있다.

Node 버전 차이는 2차 원인으로 본다. Node 18은 2025년 4월에 지원이 끝난 버전이므로 CI의 Node 버전도 함께 점검할 가치가 있다.

캐시는 가능성이 낮다. 캐시 키가 lockfile 해시이므로 lockfile이 바뀌면 새 캐시를 쓴다. 다만 워크플로에 `restore-keys`(이전 캐시 fallback 설정)가 있거나 `node_modules`를 직접 캐시하면 옛 패키지가 복원될 수 있다.

## 가설별 확인 방법

| 가설 | 맞으면 나타나는 것 | 확인 방법 |
|---|---|---|
| A. 로컬 `node_modules`가 1.4.0이다 | 로컬 버전이 1.4.0이다 | `node_modules/@company/ui/package.json`의 version 값을 본다 |
| B. 2.0.0 `exports`에 `./button`이 없다 | 목록에 button 경로가 없다 | 2.0.0 `package.json`의 `exports` 필드를 연다 |
| C. 2.0.0에서 button 파일 위치가 바뀌었다 | 설치된 패키지 안에 해당 파일이 없다 | CI 로그 또는 설치 폴더 구조를 본다 |
| D. Node 18과 20의 차이이다 | 로컬을 Node 18로 바꾸면 실패한다 | nvm(Node 버전 관리 도구)으로 Node 18에서 빌드한다 |
| E. 캐시가 옛 `node_modules`를 복원한다 | CI 로그에 캐시 복원 기록이 있다 | 워크플로의 cache 설정을 연다 |

## 확인 순서

1. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드한다. 로컬이 실패하면 가설 A가 맞다는 뜻이다. 이 명령은 로컬 `node_modules`만 지우므로 되돌리기 쉽다.
2. 2.0.0의 `exports` 필드에 `./button` 경로가 있는지 확인한다.
3. CI 로그에서 오류를 낸 도구(Next.js 빌드, tsc, jest 중 어느 것인지)를 찾는다.
4. 워크플로에서 `npm ci`를 쓰는지 `npm install`을 쓰는지 확인한다.

## 수정 방향

`exports`에 `./button`이 없다면 import를 공개된 경로로 바꾸는 것을 권장한다. 2.0.0은 하위 경로 import를 의도적으로 막은 것이므로 패키지 쪽에 경로를 추가해 달라고 요청하는 방법도 있다. 임시 조치로 1.4.0에 머무는 방법도 있지만, 어떤 방법을 쓸지는 위 확인 결과를 보고 정한다.

확인 필요: 2.0.0 `exports`의 실제 내용, CI 전체 오류 로그, 워크플로의 캐시 설정과 설치 명령, 마지막으로 CI가 성공한 시점. 마지막 성공 시점을 알면 업그레이드 커밋과 실패 시작 시점이 맞는지 대조할 수 있다.
