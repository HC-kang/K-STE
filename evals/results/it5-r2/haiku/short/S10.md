가장 유력한 원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드이며, 로컬 빌드가 성공하는 이유는 로컬 `node_modules`에 1.4.0이 남아 있기 때문으로 추정된다. 이 결론은 추론이며 아직 검증하지 않았다.

## 확인된 사실

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에는 `exports` 필드가 추가되었다.
- 에러 메시지는 `Cannot find module '@company/ui/button'`이다.
- CI는 Node 18을, 로컬은 Node 20을 사용한다.
- CI 캐시 키는 `package-lock.json`의 해시이다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었다.

## 추론

- `exports` 필드는 패키지가 외부에 공개하는 파일 경로 목록이다(패키지 바깥에서 가져다 쓸 수 있는 경로를 정의한다). 이 필드가 있으면 목록에 없는 하위 경로 import는 거부된다. 2.0.0 목록에 `./button`이 빠졌거나 경로 형식이 바뀌었을 가능성이 높다.
- 로컬 `node_modules`가 1.4.0이면 `exports` 필드가 없으므로 `@company/ui/button`이 그대로 해석된다. 따라서 로컬 성공은 Node 버전이 아니라 설치 시점의 차이 때문일 가능성이 높다.
- CI는 `package-lock.json` 기준으로 새로 설치하므로, lock 파일이 2.0.0을 가리킨다면 CI에 2.0.0이 들어가 같은 import에서 실패한다.
- `Cannot find module`은 Node 런타임의 에러 형식이다. 웹팩 번들링 단계의 해석 실패는 보통 `Module not found`로 표시된다. 따라서 실패 지점이 Next.js 빌드 중 Node가 직접 실행하는 파일(설정 파일 등)일 수 있다.
- Node 18과 20은 모두 `exports` 필드를 지원한다. Node 버전 차이만으로 이 에러가 설명되지는 않는다.

## 원인 가능성 평가

| 가설 | 근거 | 가능성 |
| --- | --- | --- |
| 2.0.0의 `exports` 필드가 하위 경로 import를 막는다 | 버전 변경 시점과 에러가 일치한다 | 높음 |
| 로컬은 1.4.0이 설치된 상태로 남아 성공한다 | 로컬 `node_modules`가 3일 전보다 먼저 설치되었다 | 높음, 확인 필요 |
| Node 18과 20의 차이가 원인이다 | 현재 사실만으로는 근거가 없다 | 낮음 |
| 캐시 복원이 원인이다 | 캐시 키가 lock 해시이므로 lock이 바뀌면 새로 설치된다 | 낮음 |

## 미확인 항목과 확인 방법

- 로컬에서 `npm ls @company/ui`를 실행하여 설치된 버전을 확인한다.
- `node_modules/@company/ui/package.json`의 `exports` 필드에 `./button`이 있는지 확인한다.
- `package-lock.json`이 가리키는 `@company/ui` 버전을 확인한다.
- CI 로그에서 실제로 설치된 `@company/ui` 버전을 확인한다.
- CI 로그에서 에러가 난 빌드 단계와 호출한 파일을 확인한다.
- 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치해 같은 에러가 재현되는지 확인한다. 이 검사는 아직 실행하지 않았다.
- 배포 차단 여부와 영향 범위는 확인되지 않았다.

## 조치 방향

- 2.0.0의 `exports` 필드를 확인하여 `button`이 공개된 정확한 경로로 import를 바꾼다.
- 2.0.0에서 `exports` 목록이 의도적으로 바뀌었는지, 누락인지 패키지 관리 담당자에게 확인한다.
- 원인이 확정되기 전까지 임시 방편으로 `@company/ui`를 1.4.0에 고정할 수 있으나, 이는 근본 해결이 아니다.
