## 결론

CI 실패의 가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드다. `exports` 필드는 패키지가 외부에 공개하는 import 경로 목록이다. 이 목록에 `./button`이 없으면 `@company/ui/button`은 찾을 수 없다. 로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 3일 전 설치본이라 1.4.0을 그대로 쓰고 있기 때문일 가능성이 크다. 이 분석은 전달받은 정보만 근거로 했다. 실제 `package.json`, lock 파일, CI 설정은 확인하지 않았다.

## 가설별 판단

| 가설 | 근거 | 판단 |
|---|---|---|
| 2.0.0의 `exports`가 하위 경로를 막았다 | 2.0.0 적용 후 실패가 시작되었고, 에러가 해당 경로를 가리킨다 | 가장 유력하다 |
| 로컬은 구버전 1.4.0을 쓰고 있다 | 로컬 `node_modules`가 3일 전 설치본이다 | 유력하다. 로컬 성공은 수정 근거가 되지 않는다 |
| Node 18과 20의 차이 | CI와 로컬의 Node 버전이 다르다 | 보조 변수다. Node 18도 `exports`를 지원하므로 단독 원인으로 보기 어렵다 |
| 캐시가 오래된 설치 상태를 복원했다 | CI 캐시 키는 lock 파일 해시다 | 가능성이 낮다. lock 파일이 바뀌면 키도 바뀐다. 단, 이전 캐시를 복원하는 `restore-keys` 설정이 있으면 예외다 |

## 확인 필요

1. 로컬에서 `npm ls @company/ui`를 실행해 실제 설치 버전을 확인한다.
2. `node_modules/@company/ui/package.json`의 `exports`에 `./button` 항목이 있는지 확인한다.
3. `rm -rf node_modules && npm ci`로 깨끗하게 설치한 뒤 Node 20에서 빌드한다. 여기서 실패하면 패키지 버전이 원인으로 확정된다.
4. Node 18로 같은 빌드를 실행해 CI 실패가 재현되는지 확인한다.
5. CI 로그에서 실패한 단계(설치, 빌드, 테스트 중 어디인지)와 캐시 복원 여부를 확인한다.
6. 에러 메시지가 Node 기본 형식(`Cannot find module`)이라 Next.js 기본 형식(`Module not found`)과 다르다. 어느 도구가 이 에러를 냈는지 확인한다.
7. 2.0.0이 ESM 전용 빌드인지 확인한다. 맞다면 CommonJS 방식으로 import하는 코드가 Node 버전에 따라 다르게 동작할 수 있다.

## 권장 조치

1. 2.0.0 문서나 `exports` 항목에서 button의 공식 import 경로를 찾아 코드를 그 경로로 바꾼다.
2. 공식 경로가 없으면 `@company/ui` 관리 팀에 `./button` 경로 공개를 요청한다.
3. 배포를 당장 막아야 하면 `@company/ui`를 1.4.0으로 되돌린다. 빌드는 통과하지만 2.0.0 전환은 미뤄진다.
4. CI와 로컬의 Node 버전을 하나로 맞춘다. 운영 환경이 쓰는 버전을 기준으로 정한다.

**주의**: 로컬 빌드 성공만으로 수정이 충분하다고 판단하면 안 된다. 수정 후에는 깨끗한 설치 상태에서 CI로 다시 검증해야 한다.
