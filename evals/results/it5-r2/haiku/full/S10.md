가장 가능성이 높은 원인은 로컬 `node_modules`가 아직 1.4.0을 쓰고 있어서 로컬 빌드에서는 2.0.0의 변경이 드러나지 않는다는 것입니다. 이 추론은 로컬 설치 버전을 확인해야 확정됩니다.

1.4.0에는 `exports` 필드가 없어서 `@company/ui/button` 같은 하위 경로를 파일 위치대로 가져올 수 있었습니다. 2.0.0은 `exports` 필드를 추가했으므로 `exports`에 등록된 경로만 가져올 수 있습니다. 로컬 `node_modules`는 3일 전보다 먼저 설치되었으므로 1.4.0일 가능성이 큽니다. `npm run build`는 의존성을 다시 설치하지 않으므로, `package.json`이 2.0.0을 가리켜도 로컬 빌드는 1.4.0으로 진행됩니다.

다만 에러 메시지가 전형적인 `exports` 차단 메시지와 다릅니다. "Cannot find module"은 설치된 패키지에 해당 파일이 없을 때도 나오므로, 아래 가설을 함께 열어 두어야 합니다.

| 가설 | 근거 | 확인 방법 |
|---|---|---|
| 로컬은 1.4.0이고 CI는 2.0.0이라 `exports` 차단이 CI에서만 드러났다 | 로컬 `node_modules`가 3일 전보다 먼저 설치되었다 | 로컬 `node_modules/@company/ui/package.json`의 `version` 값을 확인하십시오. |
| 2.0.0의 `exports` 맵에 `button` 경로가 없거나 파일 위치가 바뀌었다 | 2.0.0에서 `exports`가 추가되었고 에러가 "Cannot find module"이다 | 2.0.0의 `exports` 항목과 패키지 파일 목록을 1.4.0과 비교하십시오. |
| CI가 기대와 다른 패키지를 설치했다 | 캐시 키는 `package-lock.json` 해시이며, 부분 일치 캐시(`restore-keys`)가 있으면 이전 `node_modules`가 복원될 수 있다 | CI 로그에서 캐시 복원 여부와 설치된 `@company/ui` 버전을 확인하십시오. |
| Node 18과 20의 차이가 원인이다 | Node 18과 20 모두 `exports`를 지원하므로 단독 원인일 가능성은 낮다 | CI에서 Node 20으로 빌드를 한 번 실행해 결과를 비교하십시오. |

가장 먼저 CI 로그에서 설치된 `@company/ui` 버전과 캐시 복원 여부를 확인하십시오. 원인이 2.0.0의 경로 구성으로 확인되면 2.0.0의 `exports`에 해당 경로를 추가하거나 import 경로를 바꾸는 방안을 검토할 수 있습니다.
