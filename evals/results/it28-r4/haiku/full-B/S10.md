가장 유력한 원인은 `@company/ui` 2.0.0에서 추가된 `exports` 필드가 `./button` 경로를 노출하지 않아서, 2.0.0이 설치되는 CI에서만 `@company/ui/button` import가 실패하는 것입니다. 이 결론은 확인된 사실에서 추론한 것이므로, 아래 검증 순서로 먼저 확인하십시오.

### 확인된 사실

- 에러는 `Cannot find module '@company/ui/button'`이며, CI에서만 발생합니다. 로컬 빌드는 성공합니다.
- `@company/ui`는 3일 전 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0에서 패키지에 `exports` 필드가 추가되었습니다.
- CI는 Node 18, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

### 추론

- 로컬 `node_modules`가 업그레이드 이전에 설치되었으므로, 로컬에는 1.4.0이 남아 있을 가능성이 큽니다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`이 파일 경로로 그대로 해석됩니다. 그래서 로컬 빌드가 성공했을 가능성이 높습니다.
- `exports` 필드가 추가되면 그 맵에 없는 하위 경로 import는 막힙니다. 메이저 버전 변경에서 흔히 생기는 호환성 문제입니다.
- lock 파일이 바뀌면 캐시 키도 바뀌므로, CI는 새로 설치하면서 2.0.0을 받았을 가능성이 큽니다. 다만 복원 키(restore-keys)로 이전 캐시를 가져오도록 설정되어 있다면 예외가 있을 수 있습니다.
- Node 18과 Node 20은 모두 `exports` 필드를 지원합니다. 그러므로 Node 버전 차이가 원인일 가능성은 낮다고 봅니다. 이 판단은 일반적인 동작에 근거하며, CI 로그로 직접 확인하지는 않았습니다.

### 미확인

- 확인 필요: 2.0.0의 `exports` 맵에 `./button` 항목이 있는지. 있다면 어떤 조건(`import`, `require`, `types`)으로 연결되는지.
- 확인 필요: CI가 실제로 설치한 `@company/ui` 버전이 2.0.0인지.
- 확인 필요: 로컬 `node_modules`의 `@company/ui` 버전이 1.4.0인지.
- 확인 필요: CI 캐시 설정에 복원 키가 있는지.

### 검증 순서

1. CI 로그의 설치 단계에서 `@company/ui`가 어느 버전으로 설치되었는지 확인하십시오.
2. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인하십시오.
3. `node_modules/@company/ui/package.json`을 열어 `exports` 맵에 `./button` 항목이 있는지 확인하십시오.
4. 로컬에서 `rm -rf node_modules && npm ci`로 lock 파일 기준 재설치를 한 뒤 빌드하십시오. 같은 에러가 재현되면 Node 버전 차이가 아니라 2.0.0의 `exports` 문제라는 가설을 확인할 수 있습니다.
5. 재현되면 두 방향 중 하나를 검토하십시오. 패키지 쪽에서 `exports`에 `./button`을 추가하거나, 앱 쪽에서 import 경로를 `exports`에 맞게 바꾸는 것입니다.

PM께서 알아두실 점은, 이 빌드 실패의 원인이 앱 코드보다 라이브러리 업그레이드에 있을 가능성이 크다는 것입니다. 참고로 Node 18은 이미 지원이 종료된 버전이므로, CI의 Node 버전도 함께 점검하십시오.
