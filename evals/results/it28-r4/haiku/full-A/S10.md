가장 가능성이 높은 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다. 로컬 `node_modules`는 업그레이드 전에 설치한 것이라 1.4.0이 남아 있는 것으로 보이고, 1.4.0에는 `exports`가 없어 `@company/ui/button`이 파일 경로로 풀립니다. CI는 lock 해시가 바뀌어 캐시가 새로 만들어지면서 2.0.0을 설치했고, 2.0.0의 `exports`에는 `./button` 항목이 없는 것으로 보입니다. 이 부분은 아직 확인하지 않은 추정입니다.

로컬 성공은 2.0.0 호환성을 검증한 결과가 아닙니다. 로컬은 2.0.0을 쓰지 않았기 때문에 성공한 것입니다. PM께는 이 점을 함께 전달하십시오.

Node 버전 차이는 원인일 가능성이 낮습니다. Node 18과 20 모두 `exports` 필드를 지원하므로 같은 규칙을 따릅니다.

| 가설 | 근거 | 확인 방법 |
|---|---|---|
| 로컬이 1.4.0을 사용 중 | 로컬 `node_modules`가 업그레이드 이전에 설치됨 | 로컬에서 `npm ls @company/ui` 실행 |
| 2.0.0 `exports`에 `./button` 누락 또는 경로 불일치 | 2.0.0에 `exports` 필드 추가됨 | `node_modules/@company/ui/package.json`의 `exports` 항목 확인 |
| Node 18과 20의 차이 | 실행 환경이 다름 | 로컬에서 Node 18로 빌드 재현 |

에러 메시지 형식도 확인해야 합니다. Node가 `exports` 위반을 검사하면 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED` 오류가 나오는데, 지금 메시지는 `Cannot find module`입니다. 경로 자체가 설치본에 없을 가능성도 있습니다.

확인 필요: 에러가 빌드 단계에서 나는지, 실행 단계에서 나는지. 전체 로그와 스택 트레이스로 구분해야 합니다.
확인 필요: 커밋된 `package-lock.json`이 실제로 2.0.0을 가리키는지. 로컬에서 lock 변경분이 빠졌다면 CI와 로컬이 다른 버전을 쓸 수 있습니다.
확인 필요: 업그레이드 커밋 이후 CI가 처음 실패한 시점과 그때 실행된 커밋.

다음 순서로 진행하십시오.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인하십시오.
2. 로컬 `node_modules`를 삭제하고 `npm ci`로 다시 설치한 뒤 빌드하십시오. 이때 로컬도 같은 에러로 실패하면 버전 차이가 원인인 것으로 볼 수 있습니다.
3. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 확인하십시오.
4. `./button` 항목이 없으면 import 경로를 `exports`에 맞게 고치거나, UI 패키지 담당자에게 해당 경로 노출을 요청하십시오.
