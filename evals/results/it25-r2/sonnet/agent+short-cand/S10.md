CI 실패의 원인은 `@company/ui` 2.0.0의 `exports` 필드로 보입니다. 로컬은 2.0.0이 아닌 이전 버전이 설치돼 있어서 빌드가 성공하는 것으로 추정합니다. 아래 내용은 모두 주어진 정황에서 추론한 것이며, 패키지 파일은 아직 열어 보지 않았습니다.

## 추론 근거

`exports`(패키지가 외부에 공개하는 import 경로를 직접 지정하는 `package.json` 항목)는 필드가 생기면 그 목록에 없는 경로를 막습니다. 1.4.0에는 이 필드가 없어서 `@company/ui/button`처럼 파일 경로를 직접 적어도 import가 됐습니다. 2.0.0의 `exports`에 `./button`이 없거나 이름이 다르면 같은 import가 `Cannot find module '@company/ui/button'`으로 실패합니다.

로컬 `node_modules`는 3일 전 업그레이드보다 먼저 설치했습니다. 그래서 로컬에는 1.4.0이 남아 있을 가능성이 높습니다. CI는 `package-lock.json`대로 새로 설치하므로 2.0.0을 받습니다. 두 환경이 서로 다른 버전을 쓰고 있다는 것이 가장 단순한 설명입니다.

## 다른 요인

| 요인 | 판단 | 이유 |
|---|---|---|
| Node 18과 20의 차이 | 원인일 가능성이 낮음 | 두 버전 모두 `exports`를 지원합니다. |
| CI 캐시 | 원인이 아닐 가능성이 높음 | 캐시 키가 `package-lock.json` 해시입니다. 업그레이드 때 lock 파일이 바뀌었다면 캐시도 새로 만들어졌을 것입니다. |

Node 차이가 원인이 아니라는 판단은 추론입니다. 업그레이드 때 lock 파일을 커밋했는지는 아직 모릅니다.

## 검증 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 봅니다. 1.4.0이면 위 추론이 맞을 가능성이 높습니다.
2. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드합니다. CI와 같은 오류가 나면 재현에 성공한 것입니다.
3. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 봅니다.
4. `./button`이 없으면 2.0.0이 공개하는 경로를 찾아 앱의 import를 그 경로로 바꾸는 것을 권장합니다. 앱 쪽에서 바꿀 수 없으면 `@company/ui` 담당자에게 `./button` 추가를 요청해야 합니다.

확인 필요: 2.0.0이 `./button`을 다른 경로로 옮겼는지, 아예 제거했는지는 모릅니다. 3번의 결과에 따라 앱 수정이 필요한지, 패키지 수정이 필요한지가 달라집니다.
