## 결론

가장 유력한 원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드다. 로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 3일 전 설치본이라 1.4.0이 들어 있기 때문이다. 따라서 로컬은 2.0.0 동작을 아직 검증하지 않았다. 이 판단은 추론이며, 아래 확인 항목으로 아직 검증하지 않았다.

## 확인된 사실

- 에러 메시지는 `Cannot find module '@company/ui/button'`이다.
- `@company/ui`는 오늘(2026-10-19) 기준 3일 전에 1.4.0에서 2.0.0으로 올랐다.
- 2.0.0 패키지에는 `exports` 필드가 추가됐다.
- CI는 Node 18, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`의 해시다.
- 로컬 `node_modules`는 패키지를 올리기 전에 설치됐다.

## 추론

- `exports` 필드가 있으면 Node와 번들러는 `exports`에 명시된 경로만 허용한다. 2.0.0의 `exports`에 `./button`이 없거나 경로가 바뀌었다면 `@company/ui/button` 임포트가 실패한다.
- 1.4.0에는 `exports`가 없었으므로 deep import가 제한 없이 동작했을 가능성이 높다.
- 로컬은 1.4.0을 그대로 쓰므로 통과한다. CI는 `package-lock.json` 기준으로 새로 설치하므로 2.0.0을 받는다. 이 차이가 로컬과 CI의 결과를 가른다.
- CI 캐시 키가 `package-lock.json` 해시이므로, lockfile이 2.0.0으로 갱신됐다면 캐시는 새로 만들어졌을 가능성이 높다. 캐시가 오래된 패키지를 가리킨다는 근거는 없다.
- Node 18과 Node 20은 모두 `exports`를 지원하므로, Node 버전 차이만으로는 이 현상을 설명하기 어렵다. 다만 Next.js나 번들러가 Node 버전에 따라 다르게 해석할 가능성은 배제하지 못했다. 미확인이다.
- 에러 문구도 확인이 필요하다. Node의 `exports` 위반 에러는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`이고, `Cannot find module`은 파일이 없을 때 나오는 문구다. 2.0.0에서 파일 경로 자체가 바뀌었을 가능성도 있다. 두 경우 모두 "2.0.0에서 경로 구조가 바뀌었다"로 수렴하지만, 어느 쪽인지는 CI 로그 전문과 패키지 내용으로 확인해야 한다.

## 확인 필요

1. CI 로그에서 실제로 설치된 `@company/ui` 버전을 확인한다.
2. 2.0.0 패키지의 `package.json`에서 `exports` 필드에 `./button` 경로가 있는지 확인한다.
3. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드해 실패가 재현되는지 확인한다.
4. Node 18로 로컬 빌드를 재현해 Node 버전이 영향을 주는지 확인한다.
5. `package-lock.json`이 2.0.0으로 갱신되어 커밋돼 있는지 확인한다.
6. 이 빌드 실패가 배포 파이프라인을 막고 있는지 확인한다. 현재 자료로는 알 수 없다.

## 해결 방향

확인 결과에 따라 다음 중 하나를 고른다.

- 임포트 경로를 2.0.0의 `exports`가 허용하는 경로로 바꾼다.
- `@company/ui` 담당자에게 `./button` export 추가를 요청한다.
- 확인이 끝나기 전까지 `@company/ui`를 1.4.0으로 되돌린다. 이는 임시 조치이며, 2.0.0의 변경 사항은 쓸 수 없게 된다.
