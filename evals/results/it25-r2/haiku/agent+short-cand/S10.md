현재 전달받은 정보만으로는 원인을 하나로 확정할 수 없습니다. 가장 유력한 설명은 로컬 `node_modules`에 아직 1.4.0이 남아 있어서 로컬 빌드가 2.0.0 변경을 검증하지 못한다는 것입니다. 저장소 코드와 CI 로그는 확인하지 않았고, 아래 내용은 전달받은 정보만으로 세운 가설입니다.

## 사실 (전달받은 정보)

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에서 `exports` 필드(패키지 외부에 공개할 경로를 정한 설정)가 추가됐습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- 로컬 `node_modules`(설치된 외부 패키지가 담긴 폴더)는 3일 전보다 먼저 설치됐습니다.
- CI 캐시 키는 `package-lock.json`(설치 버전을 고정한 기록 파일)의 해시입니다.

## 추론

로컬 빌드가 성공하는 이유는 로컬에 1.4.0이 그대로 남아 있을 가능성이 높기 때문입니다. 1.4.0에는 `exports` 필드가 없으므로 `@company/ui/button` 같은 하위 경로를 제한 없이 가져올 수 있습니다.

CI가 실패하는 이유는 2.0.0이 설치된 상태에서 `exports`가 `button` 경로를 허용하지 않기 때문일 가능성이 있습니다. 경로 이름이 바뀌었거나 공개 목록에서 빠졌다면 같은 증상이 나타납니다.

Node 버전 차이가 주된 원인일 가능성은 낮습니다. `exports` 해석 방식은 Node 18과 Node 20에서 같습니다. 다만 `exports`에 막힌 경로는 Node에서 보통 다른 오류 코드로 보고되므로, 이 메시지(`Cannot find module`)는 실제 파일이 없거나 `exports`를 무시하는 도구가 import를 처리했다는 뜻일 수 있습니다. 이 부분은 전체 스택 트레이스를 봐야 구분할 수 있습니다.

CI 캐시는 직접 원인으로 보기 어렵습니다. 락 파일이 바뀌면 캐시 키도 바뀌어 새로 설치하므로, CI는 2.0.0을 받은 것으로 보입니다.

| 가설 | 로컬이 성공하는 이유 | CI가 실패하는 이유 | 가능성 |
|---|---|---|---|
| 로컬에 1.4.0이 남아 있음 | 1.4.0은 하위 경로 제한이 없음 | 2.0.0에서 경로가 막힘 | 높음 |
| 2.0.0 `exports`에 `button` 경로가 없음 | 로컬은 2.0.0을 쓰지 않음 | `exports`가 경로를 허용하지 않음 | 높음 |
| Node 18과 20의 차이 | 로컬 Node 20에서 해석 성공 | CI Node 18에서 해석 실패 | 낮음 |

## 확인 필요

다음 순서로 확인하면 원인을 좁힐 수 있습니다.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 확인합니다.
2. 2.0.0의 `package.json`에서 `exports` 필드에 `./button` 경로가 있는지 확인합니다.
3. CI 로그에서 에러를 낸 파일과 전체 스택 트레이스를 확인합니다. `next.config.js`처럼 Node가 직접 실행하는 파일에서 발생했는지 알아야 합니다.
4. CI 로그에서 캐시가 복원됐는지, 복원됐다면 어떤 버전이 설치됐는지 확인합니다.

## 권장 조치

- 로컬 `node_modules`를 지우고 `npm ci`로 다시 설치해서 로컬도 2.0.0으로 맞춥니다. 그래야 로컬 빌드가 CI와 같은 조건에서 실행됩니다.
- import 경로를 2.0.0의 `exports`에 맞게 수정하거나, 패키지 관리자에게 `button` 경로 공개를 요청합니다. 어느 쪽을 택할지는 2.0.0 `exports`를 확인한 뒤 정합니다.
- Node 18은 이미 지원이 끝났으므로, CI와 로컬을 현재 LTS 버전으로 맞추고 `.nvmrc` 같은 파일에 명시합니다.

PM이 판단해야 할 사항은 두 가지입니다. 2.0.0을 유지하고 import를 고칠지, 임시로 1.4.0으로 되돌릴지 정해야 합니다. 또한 CI 빌드가 막혀 있는 동안 배포를 어떻게 할지도 정해야 합니다.
