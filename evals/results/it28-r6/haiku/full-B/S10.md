결론부터 말하면, 현재 사실로 보아 원인은 `@company/ui` 2.0.0에서 추가된 `exports` 필드일 가능성이 높습니다. `exports` 필드는 패키지 바깥에서 가져올 수 있는 파일 경로를 정한 목록입니다. CI에서는 2.0.0이 새로 설치되어 `@company/ui/button` 경로가 막혔고, 로컬에는 3일 전에 설치된 1.4.0이 남아 있어 빌드가 통과한 것으로 보입니다. 다만 2.0.0의 `exports` 목록에 `./button`이 빠졌다는 점은 아직 확인하지 않았습니다.

## 환경 비교

| 구분 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `@company/ui` 버전 | 1.4.0으로 추정 | 2.0.0으로 추정 |
| 패키지 설치 방식 | 3일 전 설치본 유지로 추정 | lock 해시가 바뀌어 캐시를 버리고 새로 설치로 추정 |
| 빌드 결과 | 성공 | 실패 |

표의 버전과 설치 방식은 주어진 사실에서 추론한 값입니다. 실제 값은 아래 확인 항목으로 검증해야 합니다.

## 원인 추정 경로

1. 2.0.0에 `exports` 필드가 추가되었습니다. 이 필드가 있으면 외부에서 쓸 수 있는 경로가 목록에 적힌 것으로 제한됩니다.
2. 코드의 `@company/ui/button`은 목록에 `./button`이 있을 때만 해석됩니다. 목록에 없으면 모듈을 찾지 못하고 실패합니다.
3. 1.4.0에는 `exports` 필드가 없으므로 같은 경로가 로컬에서 그대로 해석됩니다.
4. CI 캐시 키(설치 결과를 재사용할지 정하는 식별값)는 `package-lock.json`의 해시(파일 내용을 요약한 값)입니다. 업그레이드로 lock 파일이 바뀌었다면 캐시가 무효화되어 CI가 2.0.0을 새로 설치합니다.

Node 18과 20의 차이는 현재 사실만으로는 원인이라는 근거가 없습니다. 두 환경이 다르므로 함께 확인할 변수로 남겨 둡니다.

## 확인 필요

확인 필요: 2.0.0의 `exports` 필드에 `./button` 경로가 있는지. 없다면 이 경로가 실패 원인으로 확정됩니다.

확인 필요: 로컬 `node_modules`에 설치된 실제 `@company/ui` 버전. `npm ls @company/ui`로 확인하십시오.

확인 필요: CI 로그의 전체 에러 메시지와 Node 18에서 `exports` 해석이 달라지는지 여부.

개발자는 먼저 2.0.0의 `exports` 목록을 확인하십시오. 목록에 `./button`이 없다면 패키지 쪽 경로 추가와 코드의 import 경로 변경 중 무엇을 택할지 PM과 함께 정하십시오.
