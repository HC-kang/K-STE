가장 유력한 원인은 `@company/ui`를 2.0.0으로 올린 뒤 CI가 새로 설치한 패키지에서 `@company/ui/button` 경로를 찾지 못하는 것입니다. 로컬은 3일 전에 설치한 `node_modules`(패키지가 설치되는 폴더)를 계속 쓰고 있어서 옛 버전 1.4.0으로 빌드되는 것으로 보입니다. 아직 직접 확인하지 않았으므로 아래 검증 순서대로 확인하십시오.

## 로컬과 CI가 다르게 동작하는 이유

| 항목 | 로컬 | CI |
| --- | --- | --- |
| 설치된 @company/ui 버전 | 1.4.0으로 추정 (3일 전 이전에 설치됨) | 2.0.0으로 추정 (업그레이드 후 새로 설치됨) |
| 패키지의 `exports` 필드 | 없음으로 추정 (1.4.0 기준) | 있음 (2.0.0) |
| Node 버전 | 20 | 18 |
| 의존성 설치 방식 | 기존 `node_modules` 재사용 | 캐시가 없으면 새로 설치 |

`exports` 필드는 패키지가 외부에 공개하는 경로 목록입니다. 이 필드가 있으면 목록에 없는 경로는 import할 수 없습니다. 1.4.0에는 이 필드가 없어서 `button` 파일 경로가 그대로 열려 있었을 가능성이 큽니다. 2.0.0에서 목록이 추가되었는데 `./button`이 빠져 있다면 CI에서만 실패하는 현상이 설명됩니다.

에러 문구만으로 exports 미노출을 단정할 수는 없습니다. exports에 없는 경로는 보통 "not exported"라는 문구로 보고되는데, 이번에는 "Cannot find module"이 나왔습니다. 그래서 2.0.0에서 파일 위치가 바뀌었을 가능성도 함께 봐야 합니다.

캐시 키는 `package-lock.json`(설치할 패키지의 정확한 버전을 기록한 파일)의 해시입니다. 업그레이드로 lock 파일이 바뀌었다면 캐시가 무효화되어 CI가 새로 설치하고, 그 과정에서 2.0.0을 받습니다. 따라서 캐시를 지우는 것은 원인 해결이 아닙니다.

Node 18과 20은 모두 `exports` 필드를 지원하므로 Node 버전 차이가 주원인일 가능성은 낮습니다. 다만 검증 3번에서 함께 확인합니다.

## 확인 필요

- 확인 필요: 2.0.0 패키지의 `exports` 필드에 `./button`이 있는지, 그 경로의 파일이 실제로 있는지. 이 정리에는 2.0.0 패키지 내용이 포함되지 않았습니다.
- 확인 필요: lock 파일에 2.0.0이 기록되어 있는지. 로컬 lock 상태는 제공되지 않았습니다.
- 확인 필요: 2.0.0 변경 기록에 import 경로 변경 안내가 있는지.

## 검증 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인하십시오. 1.4.0이면 로컬이 옛 패키지를 쓰고 있다는 뜻입니다.
2. `node_modules/@company/ui/package.json`을 열어 `exports` 필드에 `./button` 항목이 있는지 확인하십시오.
3. 로컬의 `node_modules`를 지운 뒤 `npm ci`로 다시 설치하고, Node 18 환경에서 빌드하십시오. 실패하면 원인은 패키지 버전과 경로에 있습니다. 성공하면 Node 버전이나 CI 설정 차이를 다시 확인하십시오.

## 해결 선택지

- A안: 2.0.0의 `exports`에 맞게 import 경로를 수정합니다. 공개된 경로 중 대응하는 항목을 찾아 적용하십시오.
- B안: `@company/ui`를 1.4.0으로 되돌립니다. 이 경우 2.0.0에서 필요한 기능은 쓸 수 없습니다. 확인 필요: 2.0.0을 올린 이유와 필요 일정.

개발자는 검증 1번부터 3번까지 먼저 수행하고, 결과에 따라 A안과 B안 중 하나를 PM과 함께 정하십시오.
