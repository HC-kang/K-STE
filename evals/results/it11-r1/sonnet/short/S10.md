CI 실패의 가장 유력한 원인은 CI가 `@company/ui` 2.0.0을 설치하는 반면 로컬은 아직 1.4.0을 쓰고 있어서, 두 환경이 서로 다른 버전을 빌드하는 것입니다. 이 결론은 아래 사실에서 추론한 것이고, 로컬 버전은 아직 확인하지 않았습니다.

**사실로 주어진 내용**
- 로컬 `node_modules`는 3일 전 업그레이드보다 먼저 설치했습니다.
- 2.0.0에서 패키지에 `exports` 필드가 추가됐습니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.

**추론한 원인**
`exports` 필드는 패키지가 외부에 공개할 파일 경로를 `package.json`에 적어 두고, 적지 않은 경로의 import를 막는 설정입니다. 1.4.0에는 이 필드가 없어서 `@company/ui/button`이 패키지 안의 `button` 파일로 바로 연결됐습니다. 2.0.0에서는 `exports`에 `./button`이 없거나 import 조건이 맞지 않으면 `Cannot find module '@company/ui/button'`이 발생합니다.

로컬 `node_modules`가 업그레이드 이전 상태이므로 로컬은 1.4.0으로 빌드했을 가능성이 높습니다. 반면 CI는 `package-lock.json`을 기준으로 새로 설치하므로 2.0.0으로 빌드합니다. 업그레이드로 lock 파일이 바뀌었으니 캐시 키도 바뀌어, CI가 옛 캐시를 쓸 가능성은 낮습니다.

**원인이 아닐 가능성이 높은 항목**
Node 18과 Node 20은 모두 `exports` 필드를 지원합니다. 그래서 Node 버전 차이가 이 에러의 원인일 가능성은 낮습니다.

**미확인**
- 로컬에 설치된 `@company/ui`의 실제 버전
- 2.0.0의 `exports`에 `./button`이 있는지, 있다면 조건(`import`, `require`)이 Next.js 빌드와 맞는지

**확인 순서**
1. 로컬과 CI 양쪽에서 `npm ls @company/ui`를 실행해 설치된 버전을 비교합니다.
2. `node_modules/@company/ui/package.json`의 `exports` 항목에 `./button`이 있는지 봅니다.
3. 로컬에서 `rm -rf node_modules && npm ci`로 CI와 같은 방식으로 다시 설치한 뒤 빌드합니다. 이때 로컬 빌드도 실패하면 원인이 확정됩니다.

**수정 방향**
- `exports`에 공개된 경로로 import 문을 바꾸는 방법이 있습니다.
- `./button`이 의도적으로 빠진 것이 아니라면, `@company/ui` 담당자에게 `exports`에 추가해 달라고 요청해야 합니다.
- 급하면 `@company/ui`를 1.4.0으로 되돌릴 수 있습니다. 다만 이 방법은 2.0.0 업그레이드를 취소하는 것입니다.

PM 판단이 필요한 부분은 마지막 항목입니다. 되돌리기는 빌드를 바로 복구하지만 업그레이드 일정은 미룹니다.
