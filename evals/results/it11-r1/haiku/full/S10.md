CI에서만 실패하는 원인은 로컬 `node_modules`가 1.4.0을 그대로 쓰고 있어서 로컬 빌드가 2.0.0을 검증하지 못했고, 2.0.0의 `exports` 필드(패키지가 외부에 공개하는 경로 목록)에 `./button` 경로가 빠졌을 가능성이 높습니다. 이는 사실이 아니라 추론이므로 아래 확인 방법으로 검증해야 합니다.

## 확인된 사실

- CI(Node 18)에서 `Cannot find module '@company/ui/button'` 오류로 빌드가 실패합니다.
- 로컬(Node 20) 빌드는 성공합니다.
- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에 `exports` 필드가 추가되었습니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

## 원인 후보

1. 로컬이 2.0.0을 쓰지 않았을 가능성이 높습니다. 로컬 `node_modules`가 업그레이드 이전에 설치되었으므로 로컬 설치 버전은 1.4.0일 수 있습니다. 1.4.0에 `exports`가 없었다면 `button` 경로가 제한 없이 해석되어 로컬 빌드가 성공했을 것으로 보입니다. 이 경우 로컬 성공은 2.0.0이 문제없다는 근거가 되지 않습니다.

2. 2.0.0의 `exports`에 `./button`이 없을 가능성이 있습니다. `exports`가 있으면 Node와 번들러는 목록에 있는 경로만 허용합니다. 이 오류 메시지는 그 경우와 맞아 보이지만, 2.0.0 패키지의 `exports` 목록을 직접 확인하기 전에는 확정할 수 없습니다.

3. Node 버전 차이는 단독 원인일 가능성이 낮습니다. Node 18과 20 모두 `exports`를 지원합니다. 다만 조건부 `exports`(import와 require 구분)의 해석 방식이 달라질 여지는 있으므로 로컬에서 Node 18로 재현해 볼 필요가 있습니다. Node 18은 2025년 4월에 지원이 끝났으므로 CI의 Node 버전도 함께 올리는 것을 권장합니다.

4. 캐시 키가 lock 파일 해시이므로 lock 파일이 2.0.0으로 갱신되어 커밋되었다면 CI는 캐시를 새로 만드는 것이 정상입니다. 캐시 복원에 부분 일치 키(restore-keys)가 있으면 오래된 `node_modules`가 복원될 수 있으므로 CI 설정을 확인하십시오. 확인 필요: lock 파일이 2.0.0 기준으로 커밋되어 있는지.

## 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행하여 설치된 버전을 확인하십시오.
2. CI 로그에서 `@company/ui`가 설치된 버전을 확인하십시오.
3. `@company/ui@2.0.0`의 `package.json`에서 `exports`에 `./button`이 있는지 확인하십시오.
4. 로컬에서 `node_modules`를 지우고 다시 설치한 뒤 빌드하십시오. 실패하면 2.0.0 적용이 원인이라고 확정할 수 있습니다.
5. 로컬에서 Node 18로 빌드하여 CI 조건을 재현하십시오.

## 해결 방향 (확인 방법 3의 결과에 따라 선택)

- `./button`이 2.0.0 `exports`에 없으면 import 경로를 2.0.0이 공개한 경로로 바꾸십시오.
- `./button`이 필요하면 `@company/ui`를 관리하는 팀에 경로 추가를 요청하십시오.
- 당장 배포가 급하면 2.0.0 적용을 되돌리고 1.4.0을 유지하십시오.

확인 필요: 배포 영향과 긴급도. 마지막으로 성공한 CI 빌드 시점과 해당 빌드가 배포되었는지 알려 주셔야 PM이 우선순위를 정할 수 있습니다.
