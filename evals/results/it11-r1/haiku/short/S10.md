## 원인 분석 요약

현재 자료로는 원인을 확정할 수 없다. 가장 유력한 가설은 `@company/ui` 2.0.0의 `exports` 필드(패키지 외부에 공개할 파일 경로를 정하는 설정)에 `button` 경로가 빠졌다는 것이다. 로컬에는 여전히 1.4.0이 설치되어 있어 이 문제가 재현되지 않았을 가능성이 높다. 이 가설은 아직 검증하지 않았다.

## 확인된 사실

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| 의존성 설치 기준 | 3일 전보다 이전에 설치한 `node_modules` | `package-lock.json` 해시 기반 캐시 |
| 빌드 결과 | 성공 | 실패 (`Cannot find module '@company/ui/button'`) |

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에 `exports` 필드가 추가되었다.

## 추론

1. `exports`에 `button` 경로가 없으면 Node와 번들러는 `@company/ui/button` 같은 하위 경로 import를 막는다. 1.4.0에는 `exports`가 없어서 같은 import가 통과했을 것이다.
2. 로컬 빌드가 성공한 이유는 로컬이 1.4.0을 계속 쓰고 있기 때문일 가능성이 높다. 따라서 로컬 성공은 2.0.0이 정상이라는 근거가 되지 않는다.
3. Node 버전 차이(18과 20)만으로는 이 오류를 설명하기 어렵다. 두 버전 모두 `exports`를 지원한다.
4. CI 캐시 키가 lock 파일 해시이므로, lock 파일이 바뀌었다면 CI는 새로 설치했을 것이다. 오래된 캐시 때문에 실패했다고 보기는 어렵다. 다만 lock 파일이 바뀌지 않았다면 이 추론은 성립하지 않는다.

## 확인 필요

- 대소문자 불일치 가능성이 있다. macOS 로컬 파일 시스템은 대소문자를 구분하지 않고, Linux 기반 CI는 구분한다. 파일명 대소문자가 다르면 로컬에서는 통과하고 CI에서만 실패한다. 이 가능성은 배제하지 않았다.

## 확인 순서

1. CI 로그나 `npm ls @company/ui`로 CI가 설치한 `@company/ui` 버전을 확인한다.
2. 2.0.0 패키지의 `package.json`에서 `exports` 항목에 `./button`이 있는지 확인한다.
3. 로컬에서 `rm -rf node_modules && npm ci` 후 빌드해 오류를 재현한다.
4. `git ls-files | grep -i button`으로 파일명 대소문자를 확인한다.

## 수정 방향 (원인 확인 후)

- `@company/ui` 관리 측에 `exports`에 `./button` 경로를 추가해 달라고 요청하거나, 앱의 import 경로를 2.0.0이 공개한 경로로 바꿀 수 있다.
- 당장 빌드를 복구해야 하면 `@company/ui`를 1.4.0으로 임시 고정할 수 있다.

## 현재 상태

CI 빌드는 여전히 실패 상태다. 원인은 위 순서로 확인해야 확정된다.
