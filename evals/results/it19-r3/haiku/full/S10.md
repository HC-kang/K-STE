원인은 2.0.0에 추가된 `exports` 필드가 `@company/ui/button` 경로를 노출하지 않기 때문으로 보입니다. 다만 아직 직접 확인하지 않은 추정이므로 아래 검증 단계로 확인해야 합니다.

**확인된 사실**
- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에 `exports` 필드(패키지가 외부에 공개하는 경로를 `package.json`에 명시한 목록)가 추가되었습니다. 이 목록에 없는 경로는 import해도 찾을 수 없습니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다. lock 파일이 바뀌면 키도 바뀌어 CI가 패키지를 새로 설치합니다.
- 로컬 `node_modules`는 3일 전 업그레이드보다 먼저 설치되었습니다.

**추정**
- 로컬 `node_modules`에는 아직 1.4.0이 남아 있을 가능성이 높습니다. 그래서 로컬 빌드는 `exports` 제한을 받지 않고 통과합니다.
- CI는 2.0.0을 새로 설치하므로, 2.0.0의 `exports`에 `./button`이 없거나 다른 경로로 바뀌었다면 실패합니다.
- Node 18과 Node 20은 모두 `exports`를 지원하므로, Node 버전 차이만으로 이 에러가 생겼다고 보기는 어렵습니다. 이 점은 검증으로 확인합니다.

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `@company/ui` 버전 | 1.4.0 추정 (업그레이드 전 설치) | 2.0.0 추정 (새로 설치) |
| 패키지 설치 | 업그레이드 전 상태 유지 | 캐시 키 기준으로 설치 |

**검증 순서**
1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인하십시오.
2. `node_modules/@company/ui/package.json`의 `exports` 필드에 `./button`이 있는지 확인하십시오.
3. CI 로그에서 실제로 설치된 `@company/ui` 버전을 확인하십시오.
4. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 Node 20으로 빌드해 실패가 재현되는지 확인하십시오.
5. 같은 빌드를 Node 18로 실행해 Node 버전의 영향을 배제하십시오.

**확인 필요:** 3일 전 업그레이드 커밋에서 `package-lock.json`이 함께 바뀌었는지, CI가 업그레이드 직후부터 실패했는지. 이 정보에 따라 CI가 2.0.0을 설치했는지가 달라집니다.

원인이 확인되면 수정은 두 방향입니다. 하나는 import 경로를 2.0.0 `exports`에 맞게 바꾸는 것이고, 다른 하나는 `@company/ui` 쪽에 `./button` 경로 노출을 요청하는 것입니다. 어느 쪽이 맞는지는 2.0.0의 변경 내역에서 button의 새 경로를 확인한 뒤 정하십시오.
