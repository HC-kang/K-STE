이 자료만 보면 가장 유력한 원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드(패키지가 외부에 공개할 파일 경로를 정하는 설정)가 `@company/ui/button` 같은 하위 경로 import를 막는 것입니다. 다만 이는 추론이며, 실제 빌드, 설치, 패키지 내용은 확인하지 않았습니다.

### 확인된 사실

- CI에서만 `Cannot find module '@company/ui/button'` 오류가 발생합니다.
- 3일 전에 `@company/ui`가 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0에는 `exports` 필드가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시(내용으로 계산한 고정 길이 값)입니다.
- 로컬 `node_modules`는 업그레이드 이전에 설치되었습니다.

### 추론

`exports` 필드가 있으면 목록에 없는 하위 경로를 가져오는 import가 실패할 수 있습니다. 1.4.0에서는 `button` 경로가 제한 없이 열려 있었을 가능성이 있으므로 기존 코드가 문제없이 동작했을 수 있습니다.

로컬 빌드가 성공하는 이유는 Node 20이 아니라 오래된 `node_modules`가 1.4.0을 그대로 담고 있기 때문일 가능성이 높습니다. 이 경우 로컬 성공은 2.0.0과의 호환성을 증명하지 않습니다.

CI에서 같은 오류가 난다는 것은 CI가 2.0.0을 설치했다는 뜻일 가능성이 높습니다. 캐시 키가 lock 파일의 해시이므로 lock 파일이 바뀌면 캐시가 새로 만들어집니다.

Node 18과 20은 모두 `exports` 필드를 지원하므로 Node 버전 차이만으로 이 오류가 생기는 경우는 드뭅니다. 다만 Node 버전마다 npm 버전이 달라 설치 결과가 달라질 수 있습니다.

### 미확인 사항

오류 메시지 형식이 Node 기본 오류와 달라서 번들러(웹 코드를 묶어 주는 도구)의 해석 과정이 개입했을 수 있습니다. 또 2.0.0에서 `button` 파일이 이름이 바뀌거나 삭제되었을 가능성도 배제하지 못합니다.

### 검증 순서

1. CI 로그에서 설치된 `@company/ui` 버전을 찾습니다. (`npm ls @company/ui` 결과)
2. 2.0.0 패키지의 `package.json`에 `./button` 항목이 있는지 봅니다.
3. 2.0.0 패키지 안에 button 파일이 실제로 있는지 봅니다. 이 결과로 `exports` 문제와 파일 누락을 구분합니다.
4. 로컬 `node_modules`를 지우고 `npm ci`(lock 파일 기준으로 패키지를 정확히 다시 설치하는 명령)를 실행한 뒤 빌드를 다시 해 봅니다. Node 18로도 같은 과정을 재현합니다.
5. 업그레이드 커밋에 `package-lock.json` 변경이 포함되었는지 봅니다.

### 권장 방향

- 2.0.0 패키지 관리자에게 `button` 경로를 `exports`에 추가해 달라고 요청하는 것을 권장합니다.
- 루트 경로(`@company/ui`)에서 `button`을 가져올 수 있다면 import 경로를 바꾸는 것을 권장합니다.
- 당장 빌드를 살려야 하면 `@company/ui`를 1.4.0으로 되돌리는 방법을 쓸 수 있습니다.
