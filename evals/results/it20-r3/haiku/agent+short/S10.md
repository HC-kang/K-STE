가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드가 `button` 하위 경로(서브패스)를 공개하지 않아서, 앱의 `@company/ui/button` import가 CI에서 해석되지 않는 것이다. 다만 로컬 `node_modules`가 3일 전 이전에 설치되었으므로, 로컬 빌드는 아직 2.0.0을 검증하지 않았을 가능성이 높다.

## 원인 분석

### 1. 가장 유력한 원인: exports 필드

1.4.0에 `exports` 필드가 없었다면, `@company/ui/button`은 패키지 안의 파일 경로로 그대로 찾아졌다.

2.0.0에 `exports` 필드(패키지가 외부에 공개하는 경로 목록)가 추가되면, Node.js와 번들러는 이 목록에 있는 경로만 허용한다.

따라서 2.0.0의 `exports`에 `./button`이 없으면 import가 실패한다.

이 추론은 2.0.0의 `package.json`에 `./button` 항목이 없다는 것을 확인해야 확정된다.

에러 메시지도 확인이 필요하다. Node.js가 `exports`에 없는 서브패스를 막을 때는 보통 "is not defined by exports"라는 메시지를 낸다. 이번 메시지는 "Cannot find module"이므로, 다른 도구(번들러나 테스트 러너 등)가 에러를 냈을 수 있다. 전체 스택 트레이스로 어느 도구가 실패를 일으켰는지 확인해야 한다.

### 2. 로컬 성공의 의미가 불확실하다

로컬 `node_modules`는 3일 전 업그레이드 이전에 설치되었다. 그러므로 로컬에는 1.4.0이 그대로 남아 있을 가능성이 높다. 이 경우 로컬 빌드는 1.4.0으로 성공한 것이며, 2.0.0이 문제없다는 증거가 되지 않는다.

### 3. 캐시가 CI의 설치 경로를 설명한다

CI 캐시 키는 `package-lock.json`(설치할 정확한 버전을 기록한 파일)의 해시다. 업그레이드로 lock 파일이 바뀌면 캐시 키도 바뀌고, 캐시가 없는 상태(캐시 미스)가 된다. 그래서 CI는 새로 설치하면서 2.0.0을 받는다. 다만 복원 키(restore-keys)가 이전 캐시로 대체하도록 설정되어 있다면, 오래된 캐시가 쓰였을 수 있다. 이 설정은 확인이 필요하다.

### 4. Node.js 버전 차이는 미확인 요인이다

CI는 Node 18, 로컬은 Node 20을 쓴다. 버전 차이가 패키지 해석 결과에 영향을 줄 수 있다. 다만 현재 자료만으로는 이 프로젝트에서 영향이 있는지 판단할 수 없다. 원인 후보로만 남겨 두고, 아래 5번 단계의 재현 테스트로 가린다.

### 환경 비교

| 항목 | 로컬 | CI |
|---|---|---|
| Node.js 버전 | 20 | 18 |
| `@company/ui` 버전 | 확인 필요 (1.4.0으로 추정) | lock 파일 기준 2.0.0 (확인 필요) |
| node_modules 상태 | 3일 전 이전에 설치됨 | 캐시 키 변경으로 새로 설치 (추정) |
| 빌드 결과 | 성공 | 실패 |

## 확인 순서

1. 로컬에 실제로 설치된 버전을 확인한다. 명령은 `npm ls @company/ui`이다.
2. 2.0.0 패키지의 `package.json`에서 `exports`에 `./button`이 있는지 확인한다.
3. 앱 코드에서 `@company/ui/` import 위치를 찾는다. 명령은 `grep -rn "@company/ui/" src`이다.
4. CI 로그에서 실패 지점의 전체 스택 트레이스를 확인하고, 에러를 낸 도구를 특정한다.
5. Node 18 환경에서 로컬 `node_modules`를 지운 뒤 `npm ci`로 다시 설치하고 빌드한다. 이 단계로 CI 실패를 로컬에서 재현하고 Node.js 버전 영향을 가릴 수 있다. `node_modules`는 다시 설치할 수 있으므로 지워도 된다.

## 해결 방안

1. 앱의 import를 2.0.0이 공개하는 경로로 바꾼다. 가장 간단하므로 이 방법을 권장한다.
2. 2.0.0 패키지의 `exports`에 `./button` 경로를 추가한다. 이 방법은 라이브러리를 다시 배포해야 한다.
3. 배포 전까지 CI를 살리려면 `@company/ui`를 1.4.0으로 되돌린다. 임시 조치로만 쓴다.
4. Node.js 버전을 로컬과 CI에서 같게 맞춘다. `.nvmrc`와 CI 설정에 같은 버전을 적는 방식을 권장한다.

## 확인 필요 항목

- 로컬과 CI에서 실제 설치된 `@company/ui` 버전
- 2.0.0 `exports`의 전체 내용
- CI 실패의 전체 스택 트레이스
- 실패가 시작된 정확한 시점이 업그레이드 시점과 일치하는지
- 캐시 복원 키 설정
- Node.js 18과 20 차이가 이 프로젝트의 해석 결과에 주는 영향
