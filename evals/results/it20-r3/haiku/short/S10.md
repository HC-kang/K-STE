가장 가능성이 높은 원인은 2.0.0에 새로 추가된 `exports` 필드(패키지가 외부에 공개할 파일 경로를 정한 설정)가 `./button` 경로를 빠뜨렸기 때문입니다. 이는 추론이며 아직 확인하지 않았습니다.

## 원인 후보

| 후보 | 근거 | 확인 방법 |
|---|---|---|
| 2.0.0의 `exports`에 `./button`이 없음 | 에러 발생 시점이 2.0.0 적용 시점과 같고, `exports`가 추가된 시점과 맞음 | 2.0.0 패키지의 `package.json`에서 `exports` 항목 확인 |
| 로컬은 1.4.0을 계속 사용함 | 로컬 `node_modules`가 3일 전보다 먼저 설치되었음 | 로컬에서 `npm ls @company/ui` 실행 |
| Node 18과 20의 차이 | 실행 환경이 다름 | 로컬에서 Node 18로 빌드 재현 |

## 로컬 빌드가 성공하는 이유

로컬 `node_modules`는 3일 전보다 먼저 설치되었으므로, 여기에 남아 있는 `@company/ui`는 1.4.0일 가능성이 큽니다. 1.4.0에는 `exports` 제한이 없다고 보이므로 `@company/ui/button`이 그대로 동작합니다. 이 추론이 맞다면 로컬 빌드는 2.0.0을 한 번도 검증하지 않은 상태에서 성공한 것입니다.

## 근거와 한계

에러 메시지 "Cannot find module"은 Node의 모듈 해석 실패에서 나오는 형식입니다. 따라서 실패 지점이 Next.js 번들러보다 Node 실행 단계일 가능성이 있습니다. CI는 `package-lock.json`이 바뀌면 캐시 키가 달라져 새로 설치하므로, CI가 2.0.0을 받은 것과도 맞습니다. Node 18과 20 모두 `exports`를 지원하므로 Node 버전 차이만으로는 이 에러를 설명하기 어렵다고 봅니다.

확인 필요: CI 로그에서 실패한 단계가 빌드 명령인지, `next.config.js` 같은 설정 파일을 읽는 단계인지.

## 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 확인합니다.
3. 로컬 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 Node 20으로 빌드합니다.
4. 같은 빌드를 Node 18로 실행해 CI와 같은 실패가 나오는지 확인합니다.

위 항목은 아직 실행하지 않았습니다. 결과가 2번에서 `./button` 누락으로 확인되면, 해결 방법은 두 가지입니다. 2.0.0 문서에 맞게 import 경로를 바꾸거나, 1.4.0으로 되돌리는 방법입니다.
