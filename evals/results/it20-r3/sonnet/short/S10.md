가장 유력한 원인은 로컬과 CI가 서로 다른 버전의 `@company/ui`를 쓰고 있다는 점입니다. 로컬은 아직 1.4.0이고, CI는 2.0.0을 설치하는 것으로 보입니다. 아래 비교는 모두 주어진 정보에서 추론한 것이며, 실제 설치 버전은 확인하지 않았습니다.

| 항목 | 로컬 | CI |
|---|---|---|
| `@company/ui` 버전 | 1.4.0으로 보임 | 2.0.0으로 보임 |
| `exports` 필드 | 없음 | 있음 |
| Node | 20 | 18 |

## 왜 오류가 나는가

`exports` 필드는 패키지가 외부에 공개할 경로의 목록을 정하는 `package.json` 설정입니다. 이 필드가 있으면 목록에 없는 경로는 가져올 수 없습니다.

1.4.0에는 이 필드가 없어서 `@company/ui/button`처럼 파일 경로로 직접 가져와도 됐습니다. 2.0.0에는 이 필드가 있으므로, 목록에 `./button`이 없으면 `Cannot find module` 오류가 납니다. 2.0.0의 `exports` 내용은 아직 보지 못했으므로 이 부분은 가설입니다.

로컬 `node_modules`는 업그레이드 3일 전보다 먼저 설치한 것이어서 1.4.0이 남아 있을 가능성이 높습니다. 그래서 로컬 빌드만 성공하는 것으로 보입니다.

## 가능성이 낮은 원인

- Node 버전: Node 18과 20 모두 `exports` 필드를 지원합니다. 그래서 Node 차이가 주원인일 가능성은 낮습니다.
- CI 캐시: 캐시 키가 `package-lock.json`의 해시이므로, 락 파일이 바뀌면 캐시도 새로 만들어집니다. 그래서 오래된 캐시가 원인일 가능성도 낮습니다.

## 검증 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 봅니다. 1.4.0이면 가설과 맞습니다.
2. 2.0.0의 `package.json`에서 `exports`에 `./button`이 있는지 봅니다.
3. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드합니다. 같은 오류가 나면 CI와 같은 조건이 재현된 것입니다.
4. 3번에서 오류가 나지 않으면 Node 18로 바꿔 같은 절차를 반복합니다.

## 해결 선택지

- `exports`에 있는 경로로 import 문을 바꿉니다.
- `@company/ui` 담당자에게 `./button` 경로를 `exports`에 추가해 달라고 요청합니다.
- 급하면 `@company/ui`를 1.4.0으로 되돌립니다.

어느 쪽이든 2.0.0이 `./button`을 공개하는지 확인한 뒤에 정해야 합니다.
