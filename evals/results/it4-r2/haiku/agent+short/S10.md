CI에서만 실패하는 가장 유력한 원인은 2.0.0에 새로 추가된 `exports` 필드가 `@company/ui/button` 경로를 막는 것이다. 로컬은 3일 전에 설치된 1.4.0을 그대로 쓰고 있을 가능성이 높아 빌드가 통과한다. 이는 주어진 정보로 세운 추정이며, 아직 실제 파일과 로그로 확인하지 않았다.

## 확인된 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에는 `exports` 필드(패키지 바깥에서 쓸 수 있는 import 경로를 정의하는 설정)가 추가되었다.
- 앱은 `@company/ui/button` 경로로 import하고 있다.
- CI는 Node 18을, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`(설치 버전을 고정하는 파일)의 해시다.
- 로컬 `node_modules`는 업그레이드 3일 전에 설치되었다.

## 원인 분석

### 가설 1: 로컬에는 옛 버전이 남아 있다 (가장 유력)

`exports` 필드가 없는 1.4.0에서는 `@company/ui/button`이 파일 경로 그대로 해석된다. 로컬 `node_modules`를 업그레이드 이후에 다시 설치하지 않았다면 로컬에는 여전히 1.4.0이 있다. CI는 매번 깨끗하게 설치하므로 2.0.0을 받는다. 2.0.0의 `exports`에 `./button` 항목이 없으면 같은 import가 실패한다. 이 가설은 "로컬은 성공하고 CI만 실패한다"는 현상을 함께 설명한다.

### 가설 2: CI 캐시가 옛 설치 상태를 복원한다 (가능성 낮음, 확인 필요)

캐시 키가 lockfile 해시이므로 lockfile이 바뀌면 키도 바뀐다. 다만 `restore-keys`(키가 정확히 맞지 않을 때 이전 캐시를 찾는 설정)가 있으면 이전 캐시가 복원될 수 있다. CI가 `npm ci`로 설치한다면 기존 `node_modules`를 지우고 다시 설치하므로 이 가설의 영향은 작다.

### 가설 3: Node 18과 Node 20의 차이 (근거 부족, 미확인)

Node 18도 `exports`를 지원하므로 Node 버전 차이만으로 이 오류가 난다고 볼 근거는 없다. 다만 Node 18은 2025년 4월에 지원이 종료되었으므로, 팀의 Node 버전 통일은 별도로 검토할 만하다.

## 확인할 사항

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인한다.
2. CI 로그에서 설치된 `@company/ui` 버전을 확인한다. 로그에 없으면 설치 단계 뒤에 `npm ls @company/ui`를 추가한다.
3. 2.0.0 패키지의 `package.json`에서 `exports` 항목을 읽고 `./button` 경로가 있는지 확인한다.
4. 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치한 뒤 빌드한다. 이 단계에서 실패하면 가설 1이 확정된다.
5. `nvm use 18`로 Node 18에서 같은 빌드를 실행해 Node 버전의 영향을 분리한다.

## 수정 방안

- 권장: 앱의 import 경로를 2.0.0의 `exports`에 정의된 경로로 바꾼다. 정확한 경로는 확인 3의 결과에 따라 정한다.
- 대안: 같은 조직에서 `@company/ui`를 관리한다면, 패키지 담당자에게 `./button` 항목 추가를 요청한다.
- 임시 조치: 1.4.0으로 되돌린다. 업그레이드 목적이 사라지므로 권장하지 않는다.
- 로컬 정리: 로컬 `node_modules`를 지우고 `npm ci`로 다시 설치한다. 로컬을 CI와 같은 상태로 맞추며, 이후 같은 문제가 로컬에서 가려지지 않게 한다.

**주의:** 로컬 빌드 성공은 CI 통과를 보장하지 않는다. 수정 후에는 CI에서 빌드를 다시 확인해야 한다.

## 확인 범위

이 작업 디렉터리에는 코드, `package.json`, lockfile, CI 설정 파일이 없다. 따라서 위 분석은 전달받은 설명만으로 작성되었다. 실제 파일과 CI 로그는 확인하지 않았다.
