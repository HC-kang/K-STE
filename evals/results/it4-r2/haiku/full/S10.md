현재 정보로 가장 가능성 높은 원인은 **로컬과 CI가 서로 다른 버전의 `@company/ui`를 쓰고 있다는 것**입니다. 로컬 `node_modules`가 3일 전보다 먼저 설치된 것이라면 로컬은 아직 1.4.0을 쓰고 있을 가능성이 큽니다. 그러면 "로컬 빌드는 성공한다"는 2.0.0에서 문제가 없다는 근거가 되지 않습니다.

2.0.0에 `exports` 필드가 추가되면 패키지 바깥에서는 `exports`에 적힌 경로만 import할 수 있습니다. 1.4.0에서 `@company/ui/button`이 동작했다면, 2.0.0의 `exports`에 `./button`이 없거나 다른 경로로 매핑되어 있을 수 있습니다. 이 경우 Node 18과 20 모두 같은 방식으로 실패하므로, Node 버전 차이는 직접 원인이 아닐 가능성이 높습니다.

에러 문구도 확인해야 합니다. `Cannot find module`은 보통 Node의 CommonJS 해석 실패에서 나오는 문구입니다. `exports`에서 막힌 경우에는 보통 "is not defined by exports" 계열의 문구가 나옵니다. 따라서 실패가 Next.js 빌드(webpack) 단계에서 났는지, Node 실행 단계에서 났는지에 따라 해석이 달라집니다.

가능한 원인을 가능성이 높은 순서로 정리하면 다음과 같습니다. 모두 추론이며 아직 확인하지 않았습니다.

- 2.0.0의 `exports`에 이 프로젝트가 import하는 `./button` 경로가 없다. 2.0.0의 호환성 깨짐(breaking change)에 해당합니다.
- 로컬이 실제로는 1.4.0을 쓰고 있어서 로컬 성공이 비교 근거가 되지 않는다.
- CI가 캐시나 lock 파일 상태 때문에 예상과 다른 버전을 설치했다.
- Node 18과 20의 차이가 관여했다. 가능성은 낮지만 배제하지 않는다.

다음 순서로 확인하십시오.

1. CI 로그에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인하십시오.
2. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인하십시오.
3. 2.0.0 패키지의 `package.json`에서 `exports` 항목에 `./button`이 있는지 확인하십시오.
4. 로컬에서 `rm -rf node_modules && npm ci`로 새로 설치한 뒤 빌드하십시오. 여기서 실패하면 CI 환경이 아니라 패키지나 코드 문제입니다.
5. Node 18로 로컬 빌드를 실행하십시오. 여기서 재현되면 Node 버전 차이가 관여한 것입니다.
6. CI 캐시 복원 단계에 `restore-keys`가 있는지 확인하십시오. 있다면 이전 캐시가 복원되었을 수 있습니다.

확인 필요: CI가 설치한 실제 버전. 로그에서 1.4.0이 나오면 캐시나 lock 파일 문제이고, 2.0.0이 나오면 `exports` 경로 문제일 가능성이 높습니다.
