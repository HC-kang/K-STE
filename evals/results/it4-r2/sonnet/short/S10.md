원인은 로컬과 CI가 서로 다른 버전의 `@company/ui`로 빌드하는 것일 가능성이 가장 높습니다. 로컬은 1.4.0, CI는 2.0.0을 쓰고, 2.0.0의 `exports` 필드가 `@company/ui/button` 경로를 열어 주지 않아 CI에서만 실패한다고 추정합니다.

## 확인된 사실

| 항목 | 로컬 | CI |
|---|---|---|
| Node | 20 | 18 |
| `@company/ui` 설치 시점 | 3일 전보다 이전 | 캐시 키(`package-lock.json` 해시)가 바뀌어 새로 설치 |
| 예상 버전 | 1.4.0 | 2.0.0 |
| 빌드 결과 | 성공 | `Cannot find module '@company/ui/button'` |

## 추론

1. 로컬 `node_modules`는 업그레이드 전에 설치했으므로 아직 1.4.0일 가능성이 높습니다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`처럼 패키지 내부 파일을 직접 가져오는 방식이 동작합니다.
2. 2.0.0에는 `exports` 필드가 있습니다. `exports`가 있으면 Node는 그 필드에 선언한 경로만 허용하고, 선언하지 않은 하위 경로는 "모듈을 찾을 수 없음"으로 처리합니다.
3. `package-lock.json`이 3일 전에 바뀌었으므로 CI 캐시가 무효화되었고, CI는 2.0.0을 새로 설치했습니다. 그래서 CI에서만 실패합니다.

## 미확인

- 로컬 `node_modules/@company/ui/package.json`의 실제 버전을 확인하지 않았습니다.
- 2.0.0의 `exports`에 `./button`이 있는지, 있다면 경로가 어떻게 바뀌었는지 확인하지 않았습니다.
- Node 18과 20의 차이가 원인인지 확인하지 않았습니다. 두 버전 모두 `exports`를 지원하므로 주원인일 가능성은 낮다고 봅니다.

## 검증 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. 로컬에서 `rm -rf node_modules && npm ci`로 새로 설치한 뒤 빌드합니다. 이때 CI와 같은 오류가 나면 원인이 확정됩니다.
3. `node_modules/@company/ui/package.json`의 `exports` 필드에서 `./button` 항목을 확인합니다.

## 해결 방향

- 2.0.0의 `exports`가 `./button`을 다른 경로로 제공하면, 앱의 import 경로를 그 경로로 바꿉니다.
- `./button`이 `exports`에 없고 패키지 쪽 누락이면, `@company/ui` 담당자에게 `exports`에 해당 경로를 추가해 달라고 요청합니다.
- 앱 수정이나 패키지 수정이 끝나기 전까지 빌드를 살려야 하면, 의존성을 1.4.0으로 되돌립니다.

확인 필요: 2.0.0 릴리스 노트에 `./button` 경로 변경이나 제거가 기록되어 있는지 확인해야 합니다.
