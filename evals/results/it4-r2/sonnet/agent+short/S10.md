원인은 로컬과 CI가 서로 다른 버전의 `@company/ui`를 쓰기 때문일 가능성이 가장 높습니다. 로컬은 1.4.0, CI는 2.0.0으로 빌드하고 있을 것입니다.

## 사실

- 2.0.0부터 패키지에 `exports` 필드가 있습니다.
- `exports`가 있으면 Node와 번들러는 그 필드에 선언된 경로만 허용합니다. 선언되지 않은 `@company/ui/button` 같은 하위 경로는 `Cannot find module`로 실패합니다.
- 로컬 `node_modules`는 업그레이드 3일 전보다 먼저 설치한 것입니다.
- CI 캐시 키는 `package-lock.json` 해시입니다. 업그레이드로 lock 파일이 바뀌었으므로 CI는 캐시를 쓰지 않고 2.0.0을 새로 설치합니다.

## 추론

- 로컬 `node_modules`에는 아직 1.4.0이 있어서 `exports` 제한을 받지 않습니다. 그래서 로컬 빌드가 성공합니다.
- CI는 2.0.0을 설치하므로 `exports` 제한을 받습니다. 2.0.0의 `exports`에 `./button`이 없거나 이름이 바뀌었다면 위 에러가 납니다.
- Node 18과 20의 차이는 원인일 가능성이 낮습니다. 두 버전 모두 `exports`를 지원합니다.

## 확인 필요

아래 순서로 확인하면 추론을 확정할 수 있습니다.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다. 1.4.0이면 추론이 맞습니다.
2. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 확인합니다. 로컬을 `npm ci`로 다시 설치한 뒤에 확인해야 합니다.
3. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드합니다. CI와 같은 에러가 나면 원인이 확정됩니다.

## 조치

- 2.0.0의 `exports`에 `./button`이 없으면, 마이그레이션 가이드에서 새 import 경로를 확인해 코드를 수정합니다.
- 경로는 있는데 CI에서만 실패한다면, 패키지의 `exports` 조건(`import`, `require`, `types`)과 Next.js 설정을 추가로 확인합니다.
- 재발을 막으려면 로컬도 `npm ci`로 설치해 lock 파일과 같은 상태를 유지합니다. Node 버전은 `.nvmrc`나 `engines`로 CI와 맞춥니다.
