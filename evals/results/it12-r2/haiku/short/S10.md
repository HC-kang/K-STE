결론부터 말하면, 가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드다. 로컬 빌드가 성공하는 것은 로컬 `node_modules`가 3일 전 설치된 1.4.0을 그대로 쓰고 있을 가능성이 높아서이므로, 로컬 성공은 2.0.0이 정상이라는 근거가 되지 않는다. 다만 아직 확인하지 않은 사항이 있어 원인을 확정하지는 않는다.

## 현상

CI(GitHub Actions)에서 Next.js 빌드가 `Error: Cannot find module '@company/ui/button'`으로 실패한다. 로컬에서는 같은 빌드가 성공한다. 두 환경의 차이는 `@company/ui` 설치 버전, Node 버전, 설치 상태(로컬 `node_modules`의 설치 시점)에 있다.

## 원인 분석

`@company/ui`는 3일 전 1.4.0에서 2.0.0으로 올랐다. 2.0.0에서는 패키지 `package.json`에 `exports` 필드(패키지 바깥에 공개할 파일 경로를 정하는 설정)가 추가되었다. `exports` 필드가 있으면 Node는 그 목록에 적힌 경로만 불러올 수 있게 한다. 따라서 2.0.0의 `exports`에 `./button`이 없다면 `@company/ui/button` import는 실패한다.

로컬과 CI의 차이도 이 가설로 설명된다. 로컬 `node_modules`는 3일 전에 설치되어 1.4.0 상태로 남아 있을 수 있다. 1.4.0에는 `exports` 제한이 없으므로 로컬 빌드는 성공한다. CI는 lock 파일(`package-lock.json`, 설치 버전을 고정하는 파일)이 바뀌면 캐시 키가 달라져 새로 설치하므로 2.0.0을 받는다. 다만 복원 키(캐시가 정확히 맞지 않을 때 가까운 캐시를 쓰게 하는 설정)가 있으면 이전 캐시가 복원될 수도 있다.

오류 메시지에도 확인할 점이 있다. Node가 `exports` 제한으로 경로를 막으면 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED` 계열 메시지가 나온다. 그런데 실제 메시지는 `Cannot find module`이므로, 패키지 자체가 CI 설치 결과에 없거나 다른 위치에 있을 가능성도 남아 있다. 전체 스택 트레이스를 봐야 어느 단계에서 실패했는지 확정할 수 있다.

| 가설 | 근거 | 확인 방법 |
|---|---|---|
| H1. CI는 2.0.0을, 로컬은 1.4.0을 쓴다 | 로컬 `node_modules`가 3일 전 설치본이다 | 로컬에서 `npm ls @company/ui` 실행, CI 로그에 같은 명령 추가 |
| H2. 2.0.0의 `exports`에 `./button` 경로가 없다 | `exports` 추가 시점과 실패 시점이 일치한다 | `node_modules/@company/ui/package.json`의 `exports` 확인 |
| H3. CI 설치 상태가 lock 파일과 다르다 | 캐시 복원 또는 lock 파일 커밋 누락 가능성이 있다 | CI에서 lock 파일 커밋 여부와 설치 버전 확인 |
| H4. Node 18과 20의 차이가 영향을 준다 | 실행 환경이 다르다 | CI만 Node 20으로 바꿔 재현 여부 확인 |

H4는 가능성이 낮다고 보지만 아직 배제하지 않았다.

## 확인되지 않은 사항

- 2.0.0 `exports` 필드의 실제 내용
- CI 로그의 전체 스택 트레이스
- CI가 실제로 설치한 `@company/ui` 버전
- 오류 메시지가 `Cannot find module`로 표시되는 정확한 경로

## 권장 확인 순서

다음 순서로 확인하는 것을 권장한다.

1. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드한다. 기존 설치본을 지우지 않으면 로컬 성공은 2.0.0 검증이 되지 않는다.
2. 로컬에 설치된 `@company/ui`의 `package.json`에서 `exports` 필드에 `./button`이 있는지 확인한다.
3. CI 워크플로에 `npm ls @company/ui`를 추가해 실제 설치 버전을 로그로 남긴다.
4. CI 빌드 로그 전체에서 실패 지점과 스택 트레이스를 확인한다.
5. 원인 분리를 위해 CI의 Node 버전만 20으로 바꿔 재현 여부를 확인한다. 이 변경은 실험용으로만 쓰고, 원인이 확인되기 전에는 운영 설정으로 유지하지 않는 것을 권장한다.

확인 결과에 따라 조치는 둘 중 하나가 된다. `exports`에 `./button`이 없으면 import 경로를 공개된 경로로 바꾸거나 패키지 관리 팀에 `exports` 항목 추가를 요청해야 한다. CI가 예상과 다른 버전을 설치했다면 lock 파일 커밋 상태와 캐시 키 설정을 고쳐야 한다.
