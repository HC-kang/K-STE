# CI 빌드 실패 원인 분석: `@company/ui` 2.0.0 업그레이드

CI에서 `Error: Cannot find module '@company/ui/button'` 오류로 빌드가 실패하고, 원인은 아직 확정되지 않았다. 가장 유력한 가설은 2.0.0에 새로 추가된 `exports` 필드가 `@company/ui/button` 경로를 허용하지 않는다는 것이다. 이 가설은 아직 검증하지 않았다. 로컬 빌드 성공은 이 가설을 뒷받침하는 근거가 되지 않는다. 로컬 `node_modules`가 업그레이드 이전 버전(1.4.0)일 가능성이 있기 때문이다.

## 확인된 사실

1. 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
2. 2.0.0 패키지에 `exports` 필드가 추가됐다.
3. CI는 Node 18을, 로컬은 Node 20을 사용한다.
4. CI 캐시 키는 `package-lock.json`의 해시다.
5. 로컬 `node_modules`는 업그레이드 이전에 설치했다.

## 추론

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `@company/ui` 버전 | 확인 필요: 1.4.0일 가능성이 높다 | 2.0.0일 가능성이 높다 |
| 설치 방식 | 업그레이드 이전 설치분을 재사용한다 | lock 해시가 바뀌면 새로 설치한다 |

- 로컬이 1.4.0을 쓰고 있다면 로컬 빌드는 2.0.0의 호환성을 검증하지 않았다. 이 경우 실패 원인은 Node 버전보다 2.0.0 자체일 가능성이 크다.
- `exports` 필드가 `./button` 하위 경로를 정의하지 않으면 `@company/ui/button` 임포트는 Node 버전과 무관하게 실패한다.
- 캐시 키가 lock 파일 해시이므로 lock이 2.0.0으로 갱신됐다면 CI는 새로 설치한다. 이 경우 오래된 캐시가 원인일 가능성은 낮다.
- Node 18과 20은 `exports` 해석을 모두 지원한다. 두 버전에 동봉된 npm 버전이 다를 수 있다. 이 차이가 실패에 영향을 줬는지는 확인 필요하다.
- 오류 문구 "Cannot find module"은 Node의 CommonJS 해석 실패 문구다. 웹팩 빌드 단계라면 보통 "Module not found" 문구가 나온다. 따라서 실패 지점이 빌드 설정 파일이나 Node로 직접 실행되는 스크립트일 수 있다. 확인 필요: 전체 스택 트레이스에서 실패 지점을 확인해야 한다.

## 미확인

- 실패가 나는 정확한 단계와 전체 스택 트레이스
- 2.0.0 `exports` 맵에 `./button` 항목이 있는지 여부
- CI와 로컬에서 실제로 설치된 `@company/ui` 버전
- 업그레이드 이전 CI 빌드의 성공 여부
- lock 파일이 2.0.0으로 갱신됐는지 여부

## 다음 확인 순서

1. CI 로그에서 실패 단계와 전체 스택 트레이스를 확인한다.
2. CI와 로컬에서 각각 `npm ls @company/ui`를 실행해 설치된 버전을 비교한다.
3. `node_modules/@company/ui/package.json`의 `exports` 필드에 `./button` 항목이 있는지 확인한다.
4. 캐시 없이 CI를 한 번 실행해 캐시의 영향을 배제한다.
5. 로컬에서 Node 18로 `npm ci` 후 빌드해 Node 버전의 영향을 분리한다.

## 대응 방향

확인 순서의 결과가 나온 뒤에 대응을 정한다. 예상되는 방향은 두 가지다.

- `@company/ui` 측에 `./button` 경로를 `exports`에 추가하도록 요청한다.
- 임포트 경로를 패키지가 허용하는 경로로 바꾼다.

2.0.0 업그레이드를 유지할지는 위 결과를 보고 결정한다. 결과가 나오기 전까지는 1.4.0으로 되돌리는 것을 임시 조치로 검토할 수 있다.
