가장 유력한 원인은 로컬이 아직 `@company/ui` 1.4.0을 쓰고, CI만 2.0.0을 설치해서 `@company/ui/button` 경로가 막힌 것입니다. 이 결론은 주신 사실에서 추론한 것이고, 아직 실행해서 확인하지 않았습니다.

`exports` 필드는 패키지가 외부에 공개하는 import 경로의 목록입니다. 이 필드가 있으면 Node와 번들러(코드를 하나로 묶는 도구)는 목록에 없는 경로를 불러오지 못합니다. 1.4.0에는 이 필드가 없었으므로 `@company/ui/button`처럼 파일 경로를 직접 지정해도 동작했습니다. 2.0.0의 `exports`에 `./button`이 없으면 같은 import가 `Cannot find module`로 실패합니다.

로컬에서 성공하는 이유도 같은 흐름으로 설명됩니다. 로컬 `node_modules`는 3일 전보다 먼저 설치했으므로 1.4.0이 그대로 남아 있을 가능성이 높습니다. 반면 CI는 새 환경에 설치하므로, `package-lock.json`이 2.0.0을 가리킨다면 2.0.0을 받습니다. 따라서 로컬 빌드는 2.0.0을 검증하지 못한 상태입니다.

나머지 두 요인은 원인일 가능성이 낮습니다.

- Node 18과 Node 20은 둘 다 `exports`를 지원합니다. 그래서 Node 버전 차이만으로 이 에러가 생길 가능성은 낮습니다.
- CI 캐시 키가 `package-lock.json`의 해시이므로, 버전을 올리면 키가 바뀌어 캐시를 새로 만듭니다. 그래서 낡은 캐시가 원인일 가능성도 낮습니다.

아직 확인하지 못한 내용은 다음과 같습니다.

- 2.0.0의 `exports`에 `./button`이 실제로 없는지 확인하지 못했습니다.
- `package-lock.json`이 2.0.0으로 커밋됐는지 확인하지 못했습니다.
- CI가 3일 전부터 실패했는지, 최근에야 실패했는지 확인하지 못했습니다.

원인은 다음 순서로 확인할 수 있습니다.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 봅니다.
2. 로컬에서 `rm -rf node_modules && npm ci`로 CI와 같은 방식으로 다시 설치하고 빌드합니다. 같은 에러가 나면 원인이 확정됩니다.
3. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 봅니다.
4. 2번이 재현되면 Node 18로 같은 빌드를 한 번 더 실행해 Node 버전의 영향을 배제합니다.

원인이 확정되면 수정 방향은 두 가지입니다. 하나는 앱의 import를 2.0.0의 `exports`가 공개한 경로로 바꾸는 것입니다. 다른 하나는 `./button`을 공개해야 한다고 판단되면 `@company/ui` 쪽 `exports`에 추가하는 것입니다. 어느 쪽을 택할지는 `@company/ui` 담당자가 2.0.0의 공개 경로 정책을 확인한 뒤 정해야 합니다.
