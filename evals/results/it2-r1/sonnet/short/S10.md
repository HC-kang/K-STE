CI 빌드 실패의 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드일 가능성이 가장 높고, 로컬 빌드가 성공하는 것은 로컬이 아직 1.4.0을 쓰고 있기 때문일 가능성이 높습니다. 아래 내용 중 확인이 끝난 것은 사실로, 나머지는 추론과 미확인으로 구분했습니다.

**사실**
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에서 패키지에 `exports` 필드가 추가됐습니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치한 것입니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 에러는 `Cannot find module '@company/ui/button'`이고, CI에서만 발생합니다.

**추론**
- `exports` 필드(패키지가 외부에 공개하는 경로 목록)가 생기면, 목록에 없는 하위 경로는 import할 수 없습니다. 2.0.0의 `exports`에 `./button`이 없거나 경로가 다르면 `@company/ui/button`을 찾지 못합니다. 1.4.0에는 `exports`가 없어서 같은 경로가 동작했습니다.
- 로컬 `node_modules`가 업그레이드 이전에 설치됐으므로, 로컬은 1.4.0을 쓰고 있을 가능성이 높습니다. 그러면 로컬 빌드 성공은 2.0.0을 검증한 결과가 아닙니다.
- 업그레이드로 `package-lock.json` 해시가 바뀌었으므로 CI 캐시는 무효화됐고, CI는 lock 파일대로 2.0.0을 새로 설치했을 것입니다. 따라서 CI의 결과가 실제 상태에 가깝습니다.

**미확인**
- 로컬에 실제로 설치된 `@company/ui` 버전이 1.4.0인지 확인하지 않았습니다.
- 2.0.0의 `exports`에 `./button`이 있는지 확인하지 않았습니다.
- Node 18과 Node 20의 차이가 영향을 줬는지 확인하지 않았습니다. 두 버전 모두 `exports`를 지원하므로 주원인일 가능성은 낮지만, 조건부 export(`import`, `require` 등 조건별 경로) 처리에서 차이가 날 수 있습니다.

**확인 방법**
1. 로컬에서 `npm ls @company/ui`를 실행해 설치 버전을 확인합니다.
2. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드합니다. CI와 같은 에러가 나면 원인이 확정됩니다.
3. `node_modules/@company/ui/package.json`의 `exports`에서 `./button` 항목이 있는지 확인합니다.
4. 3단계에서 항목이 있다면, 로컬 Node를 18로 맞춰 다시 빌드해 Node 버전 영향을 분리합니다.

**조치 후보**
- `./button`이 `exports`에 없다면, 2.0.0이 공개하는 경로로 import를 바꿉니다. 2.0.0의 변경 내역(CHANGELOG)에서 새 경로를 확인해야 합니다.
- `./button`이 의도적으로 빠진 것이 아니라면, `@company/ui` 담당자에게 `exports`에 해당 경로를 추가해 달라고 요청합니다.
- 두 조치 모두 어느 쪽이 맞는지는 확인 필요: 2.0.0에서 `./button`을 제거한 것이 의도된 변경인지.

**재발 방지**
- 로컬과 CI 모두 `npm ci`로 설치하고, Node 버전을 `.nvmrc` 또는 `engines` 필드로 통일합니다. 그러면 "로컬만 성공"하는 상황을 줄일 수 있습니다.
