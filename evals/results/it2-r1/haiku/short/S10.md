가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다. `exports`가 있으면 패키지가 공개한 경로만 import할 수 있는데, `@company/ui/button`이 그 목록에 없으면 CI에서 이 에러가 납니다. 아직 패키지 내용을 직접 확인하지 않았으므로 이 내용은 추론입니다.

확인된 사실은 다음과 같습니다. 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다. 2.0.0에는 `exports` 필드가 추가되었습니다. CI는 Node 18, 로컬은 Node 20을 씁니다. CI 캐시 키는 `package-lock.json` 해시입니다. 로컬 `node_modules`는 업그레이드 전에 설치되었습니다.

다음은 추론입니다. 로컬 `node_modules`에는 아직 1.4.0이 남아 있습니다. 1.4.0은 하위 경로 import를 제한하지 않으므로 로컬 빌드는 성공합니다. CI는 lock 파일 기준으로 새로 설치하므로 2.0.0을 받고, `exports` 제한에 걸립니다. Node 버전 차이가 주원인일 가능성은 낮습니다. Node 18도 `exports` 필드를 지원하기 때문입니다.

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `node_modules` 상태 | 업그레이드 전 설치본 | 새로 설치 (캐시 상태는 미확인) |
| `@company/ui` 버전 (추정) | 1.4.0 | 2.0.0 |
| 빌드 결과 | 성공 | 실패 |

아직 확인하지 않은 내용은 다음과 같습니다. 2.0.0의 `exports` 목록에 `./button` 경로가 있는지 모릅니다. CI에서 실제로 설치된 버전과 캐시 복원 여부도 모릅니다. 앱 코드의 import 경로가 에러 메시지와 정확히 같은지도 확인하지 않았습니다.

원인을 확정하려면 다음 순서로 확인하면 됩니다.

1. 2.0.0의 `package.json`에서 `exports` 필드를 열어 `./button` 또는 `./*` 항목이 있는지 확인합니다.
2. CI 빌드 단계에 `npm ls @company/ui`를 추가해 실제 설치 버전을 로그로 남깁니다.
3. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드합니다. 여기서도 실패하면 원인은 패키지 설정 쪽으로 좁혀집니다.

수정 방향은 두 가지입니다. 앱에서 2.0.0이 공개한 경로로 import를 바꾸거나, 패키지 관리자에게 `./button` 경로 추가를 요청할 수 있습니다. 위 확인 결과에 따라 방향을 정하면 됩니다.
