가장 유력한 원인은 `@company/ui` 2.0.0에서 추가된 `exports` 필드(패키지가 외부에 공개하는 모듈 경로를 정하는 설정)에 `./button` 경로가 빠진 것입니다(추론). 이 경우 Node 버전과 관계없이 실패합니다. 다만 현재 자료만으로는 확정할 수 없으므로 아래 확인 항목으로 검증해야 합니다.

## 확인된 사실

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에 `exports` 필드가 추가됐습니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 업그레이드 전에 설치했습니다.
- 에러는 `Cannot find module '@company/ui/button'`입니다.

## 원인 분석

### 1. 로컬 빌드 성공은 2.0.0을 검증한 결과가 아닙니다(추론)

로컬 `node_modules`가 업그레이드 전에 설치됐으므로, 로컬에는 아직 1.4.0이 있을 가능성이 높습니다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`이 파일 경로로 해석되고 빌드가 성공합니다. 따라서 로컬 성공은 2.0.0에서 이 import가 동작한다는 근거가 되지 않습니다.

### 2. CI 실패는 2.0.0 설치 결과와 맞습니다(추론)

`package-lock.json`이 바뀐 뒤로 캐시 키도 바뀌므로, CI는 캐시를 쓰지 못하고 새로 설치합니다. 새로 설치되는 버전은 2.0.0이고, 2.0.0에는 `exports` 제한이 적용됩니다.

### 3. Node 18과 20의 차이는 아직 근거가 없습니다

Node 18과 20은 모두 `exports`를 지원합니다. 따라서 버전 차이만으로 이 에러를 설명할 근거는 현재 없습니다. 변수로만 남겨 둡니다.

### 4. 에러 메시지의 출처를 확인해야 합니다(확인 필요)

`Cannot find module`은 Node의 모듈 해석기가 내는 메시지입니다. Next.js 번들러(webpack)가 내는 메시지는 보통 `Module not found`입니다. 이 에러가 `next.config.js` 같은 Node 스크립트에서 나왔을 수 있으므로 CI 로그의 스택 트레이스로 확인해야 합니다.

## 확인 항목

1. `@company/ui` 2.0.0의 `package.json`에서 `exports` 필드를 확인하십시오. `./button` 또는 `./*` 패턴이 있는지 봅니다.
2. CI 로그에서 에러를 낸 파일과 스택 트레이스를 확인하십시오.
3. CI에서 `npm ls @company/ui`로 실제 설치된 버전을 확인하십시오.
4. 로컬에서도 `npm ls @company/ui`로 버전을 확인하십시오. 1.4.0이면 로컬 빌드는 2.0.0을 검증하지 않은 것입니다.
5. 로컬에서 `rm -rf node_modules && npm ci` 후 빌드하십시오. Node 18로도 한 번 실행하십시오.
6. `package.json`과 `package-lock.json`의 버전이 일치하는지 확인하십시오.

## 조치 방향 (확인 1번 결과에 따라)

- `exports`에 `./button`이 빠졌다면 두 가지 중 하나를 고르십시오. 패키지 쪽에 경로를 추가해 새 버전을 내거나, 앱의 import를 공개된 경로로 바꾸십시오.
- 경로가 있다면 import 방식이나 Node 18 환경 설정을 다시 확인하십시오.
- 2.0.0은 주버전 변경이므로 릴리스 노트에서 다른 호환성 변경도 함께 확인하십시오.

PM께는 현재 CI가 실패하는 상태이며, 이 실패로 배포나 머지가 막혀 있는지는 자료에 없으므로 확인이 필요하다고 전하십시오.
