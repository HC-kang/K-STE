현재 가장 유력한 원인은 2.0.0의 `exports` 필드가 `@company/ui/button` 경로를 공개 목록에 넣지 않았기 때문입니다. 이는 추론이며, 2.0.0 패키지의 `exports` 내용은 아직 확인하지 않았습니다. 로컬이 성공하는 이유도 같은 추론으로 설명됩니다. 로컬 `node_modules`가 업그레이드 전에 설치되어 1.4.0이 남아 있으므로, 1.4.0에는 없는 `exports` 제한을 받지 않습니다.

## 확인된 사실

- CI에서 `Cannot find module '@company/ui/button'` 오류로 빌드가 실패합니다.
- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드(패키지 외부에 공개할 파일 경로를 정하는 설정)가 추가됐습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키(저장된 의존성 묶음을 찾는 식별값)는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치됐습니다.

## 원인 가설

`exports`가 있으면 패키지 내부 파일을 경로로 직접 가져오는 방식(딥 임포트)은 목록에 있는 경로에만 허용됩니다. 아래 가설은 가능성이 높은 순서로 정리했습니다.

| 순위 | 가설 | 근거 | 확인 방법 |
|---|---|---|---|
| 1 | 2.0.0의 `exports`에 `./button` 경로가 없습니다. | 오류 경로와 `exports` 추가 시점이 일치합니다. | 2.0.0의 `package.json`에서 `exports` 목록을 확인합니다. |
| 2 | 로컬에는 1.4.0이 남아 있어 로컬만 성공합니다. | 로컬 `node_modules`가 업그레이드 전에 설치됐습니다. | 로컬에서 `npm ls @company/ui`를 실행합니다. |
| 3 | 대소문자 차이가 있습니다. | macOS는 대소문자를 구분하지 않고, CI의 Linux는 구분합니다. | 2.0.0의 실제 파일명과 import 경로를 대조합니다. |
| 4 | Node 18과 Node 20의 모듈 해석 차이가 있습니다. | 두 버전의 해석 방식이 다를 가능성이 있습니다. | CI 러너를 Node 20으로 바꿔 한 번 실행합니다. |

캐시는 가능성이 낮게 봅니다. 캐시 키가 lock 파일 해시이므로 lock 파일이 바뀌면 CI가 의존성을 새로 설치합니다. 따라서 오래된 캐시 때문에 실패했을 가능성은 낮습니다.

Node 18은 2025년 4월에 지원이 종료됐습니다. 원인과 무관하더라도 CI의 Node 버전을 올리는 것을 검토할 가치가 있습니다.

## 다음 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. CI 로그에서 설치된 `@company/ui` 버전을 확인합니다.
3. 2.0.0의 `exports` 목록에 `./button` 또는 그에 해당하는 경로가 있는지 확인합니다.
4. CI 러너를 Node 20으로 바꿔 한 번 실행해 Node 버전의 영향을 분리합니다.

확인 결과가 가설 1이면 import 경로를 2.0.0의 `exports` 목록에 맞게 바꾸는 것을 권장합니다. 확인 전에는 원인을 단정할 수 없습니다. 위 네 가지 중 어느 것도 아직 실행하지 않았습니다.
