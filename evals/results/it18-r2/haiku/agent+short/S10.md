이 빌드 실패의 가장 유력한 원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드다. 이 필드 때문에 `@company/ui/button` 같은 하위 경로 import가 막혔을 가능성이 높다. 로컬에는 3일 전에 설치된 1.4.0이 그대로 남아 있을 가능성이 커서, 로컬 빌드 성공은 2.0.0에서 문제가 없다는 근거가 되지 못한다. 다만 아래 가설은 아직 검증하지 않았다.

## 확인된 사실

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에는 `exports` 필드가 추가됐다.
- CI는 Node 18을 쓰고, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`의 해시다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치됐다.
- 빌드 에러는 `Cannot find module '@company/ui/button'`이다.

## 원인 분석

1.4.0에는 `exports` 필드가 없었다. `exports`가 없으면 Node와 번들러(앱 코드를 묶어 배포용 파일을 만드는 도구)는 패키지 폴더 안의 파일 경로를 그대로 찾는다. 그래서 `@company/ui/button`은 `button` 파일을 바로 찾아 성공했다.

2.0.0에는 `exports`가 있다. `exports`가 있으면 그 목록에 적힌 경로만 패키지 바깥에서 import할 수 있다. 목록에 `./button`이 없으면 같은 import가 실패한다.

2.0.0의 `exports` 목록에 `./button`이 있는지는 아직 확인하지 않았다. 목록에 없다면 이 가설이 맞다는 근거가 된다. 목록에 있다면 이 가설은 틀리며, 다른 원인을 찾아야 한다.

확인 필요: Node가 `exports` 위반을 보고할 때는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`라는 다른 메시지를 낸다. 실제 에러 문구가 `Cannot find module`이므로, 전체 스택 트레이스에서 에러를 낸 주체가 Node인지 Next.js 빌드 도구인지 특정해야 한다.

## 왜 CI에서만 실패하는가

CI는 매번 패키지를 새로 설치한다. lock 파일이 2.0.0으로 갱신됐다면 CI는 2.0.0을 받는 것으로 보인다(추론). 로컬 `node_modules`는 3일 전 설치본이므로 1.4.0이 남아 있는 것으로 보인다(추론). 따라서 같은 코드가 로컬에서는 1.4.0으로, CI에서는 2.0.0으로 빌드된다.

캐시는 원인일 가능성이 낮다. 캐시 키가 lock 해시이므로 lock 파일이 바뀌면 캐시도 새로 만들어진다. 다만 복원 키(restore-keys, 키가 정확히 맞지 않을 때 가까운 이전 캐시를 쓰게 하는 설정)가 있으면 이전 버전 패키지가 복원될 수 있다.

Node 버전 차이만으로 이 에러가 생긴다고 보기는 어렵다. 두 버전 모두 `exports`를 지원하기 때문이다.

## 가설 검토

| 가설 | 판단 | 근거 | 확인 방법 |
|---|---|---|---|
| 2.0.0 `exports`에 `./button`이 없다 | 추론, 가능성 높음 | 1.4.0에는 `exports`가 없고 2.0.0에는 있다 | 2.0.0 `package.json`의 `exports` 목록을 연다 |
| 로컬은 1.4.0을 쓰고 있다 | 추론, 가능성 높음 | `node_modules`가 3일 전 설치본이다 | 로컬에서 `npm ls @company/ui`를 실행한다 |
| 캐시가 오래된 패키지를 복원했다 | 추론, 가능성 낮음 | 캐시 키가 lock 해시이며, restore-keys가 있으면 예외가 된다 | CI 설정 파일의 restore-keys와 install 로그의 버전을 본다 |
| Node 18과 20의 차이가 원인이다 | 추론, 가능성 낮음 | 두 버전 모두 `exports`를 지원한다 | 로컬에서 Node 18로 빌드한다 |

## 다음에 볼 것

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 본다.
2. CI 로그의 install 단계에서 `@company/ui`의 버전을 본다.
3. 2.0.0 패키지의 `package.json`에서 `exports` 목록에 `./button`이 있는지 본다.
4. 로컬에서 `node_modules`를 지운 뒤 `npm ci`로 다시 설치하고 빌드한다.
5. 로컬에서 Node 18로 빌드해 본다.

## 수정 방향

아직 방법을 정하지 않았다. 후보는 다음과 같다.

| 방법 | 장점 | 단점 |
|---|---|---|
| A. 앱 코드의 import 경로를 2.0.0 `exports`가 허용하는 경로로 바꾼다 | 우리 쪽 변경만으로 해결된다 | 2.0.0 `exports`에 허용된 대응 경로가 있어야 한다 |
| B. `@company/ui` 담당자에게 `./button` 경로를 `exports`에 추가해 달라고 요청한다 | 기존 import 코드를 유지한다 | 담당자의 새 배포를 기다려야 한다 |
| C. `@company/ui`를 1.4.0으로 임시로 되돌린다 | 빌드를 가장 빨리 복구한다 | 2.0.0 적용이 늦어진다 |

위 1번부터 3번까지의 결과가 가설과 맞으면 A를 먼저 검토하기를 권장한다. 2.0.0 `exports`에 대응 경로가 없으면 A는 쓸 수 없으므로 B가 필요하다. 빌드를 바로 복구해야 하면 C로 임시 복구한 뒤 A 또는 B를 진행하기를 권장한다.

## PM 참고

- 배포가 막혔는지는 미확인이다.
- 실패가 CI에서만 나타나므로 로컬 개발 환경은 당장 영향을 받지 않는 것으로 보인다(추론).
