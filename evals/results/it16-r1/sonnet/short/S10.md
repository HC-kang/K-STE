가장 유력한 원인은 로컬에는 `@company/ui` 1.4.0이 남아 있고 CI에는 2.0.0이 설치돼, 두 환경이 서로 다른 버전으로 빌드하는 것입니다. 이 판단은 주어진 정황에서 추론한 것이며, 직접 실행해서 확인하지는 않았습니다.

## 확인된 사실

- CI에서만 빌드가 실패하고, 에러는 `Cannot find module '@company/ui/button'`입니다.
- `@company/ui`를 3일 전에 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0부터 패키지에 `exports` 필드가 있습니다. `exports`는 패키지가 외부에 공개할 파일 경로를 제한하는 `package.json` 설정입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치한 것입니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.

## 추론

1. 1.4.0에는 `exports`가 없으므로, `@company/ui/button`처럼 패키지 안의 파일 경로를 직접 지정해도 모듈을 찾습니다.
2. 2.0.0에는 `exports`가 있으므로, 목록에 없는 경로는 Node가 모듈로 인정하지 않습니다. `./button`이 목록에 없거나 다른 이름으로 바뀌었다면 이 에러가 납니다.
3. 로컬 `node_modules`는 업그레이드 전에 설치한 것이므로, 로컬은 아직 1.4.0일 가능성이 높습니다. 그래서 로컬 빌드는 성공합니다.
4. 업그레이드 때 `package-lock.json`이 바뀌었다면 캐시 키도 바뀌므로, CI는 2.0.0을 새로 설치했을 것입니다. 이 경우 캐시는 원인이 아닙니다.
5. Node 18과 Node 20은 모두 `exports`를 지원하므로, Node 버전 차이는 원인일 가능성이 낮습니다.

## 미확인

- 2.0.0의 `exports`에 `./button`이 있는지 확인하지 않았습니다.
- 로컬에 실제로 설치된 `@company/ui` 버전을 확인하지 않았습니다.
- 업그레이드 커밋에 `package-lock.json` 변경이 포함됐는지 확인하지 않았습니다.

## 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다. 1.4.0이면 위 추론이 맞습니다.
2. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 확인합니다. 2.0.0을 설치한 뒤에 봐야 합니다.
3. 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치하고 빌드합니다. CI와 같은 에러가 나면 원인이 확정됩니다.
4. 3번에서 재현되지 않으면 `nvm use 18`로 Node 18에서 같은 빌드를 해서 Node 버전 영향을 확인합니다.

## 해결 방향

2.0.0의 `exports`에 공개된 경로를 확인한 뒤, 앱의 import 경로를 그 경로로 바꿔야 합니다. 공개된 경로가 없으면 `@company/ui` 담당자가 `exports`에 `./button`을 추가해야 합니다. 어느 쪽이 맞는지는 2번 확인 결과에 따라 정해집니다.
