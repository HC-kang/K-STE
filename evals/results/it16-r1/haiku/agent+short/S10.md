## 결론

가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다. 이 필드가 있으면 패키지가 외부에 공개한 경로만 import할 수 있습니다. 공개 목록에 `./button`이 없으면 `@company/ui/button` import가 실패합니다. 다만 이것은 추론이며, 2.0.0의 `exports` 내용은 아직 확인하지 않았습니다.

로컬에서 성공하는 이유도 설명할 수 있습니다. 로컬 `node_modules`는 3일 전보다 먼저 설치되었으므로 1.4.0이 들어 있을 가능성이 큽니다. 1.4.0에는 `exports`가 없어서 `button` 경로가 그대로 해석됩니다. 따라서 로컬 성공은 2.0.0에서도 빌드된다는 증거가 아닙니다.

이 정리는 말씀하신 내용만 근거로 합니다. 패키지 소스, lockfile, CI 로그는 열어 보지 않았습니다.

## 원인 후보

| 후보 | 근거 | 가능성 |
|---|---|---|
| 2.0.0의 `exports`가 하위 경로를 막음 | 2.0.0에 `exports`가 추가되었고, 로컬은 구버전을 쓸 가능성이 큼 | 높음 |
| 로컬은 1.4.0, CI는 2.0.0을 설치함 | 로컬 `node_modules`가 3일 전 이전에 설치됨 | 높음 |
| 2.0.0에서 해당 파일의 경로가 바뀌었거나 없음 | 에러 메시지가 `Cannot find module`임 | 중간 |
| CI의 캐시가 구버전 패키지를 복원함 | 캐시 키는 `package-lock.json` 해시임 | 낮음에서 중간 |
| Node 18과 Node 20의 차이 | CI는 Node 18을 씀 | 낮음 |

`exports` 때문에 경로가 막히면 Node는 보통 `is not defined by "exports"` 메시지를 냅니다. 지금 메시지는 `Cannot find module`이므로, 경로 자체가 설치된 패키지에 없을 가능성도 함께 봐야 합니다. Node 18도 `exports`를 지원하므로 Node 버전만으로는 이 문제를 설명하기 어렵습니다. 다만 2.0.0이 ESM 전용 패키지라면 Node 18에서 `require`가 실패할 수 있습니다. 이 점은 2.0.0의 `exports` 조건과 `engines` 필드를 보고 판단해야 합니다.

캐시는 `package-lock.json`이 바뀌면 키도 바뀌므로, 2.0.0 lockfile이 커밋되었다면 캐시 문제일 가능성이 낮습니다. 다만 캐시 설정에 `restore-keys`(키가 맞지 않을 때 이전 캐시를 대신 쓰는 설정)가 있다면 구버전 캐시가 복원될 수 있습니다.

## 확인 필요

- 확인 필요: 2.0.0의 `package.json`에 `./button` 또는 `./*` 항목이 있는지 확인해야 합니다. 이 항목이 없으면 원인 1이 맞습니다.
- 확인 필요: 빌드가 막힌 범위가 `button`만인지, 다른 하위 경로도 함께 깨졌는지 확인해야 합니다. 배포가 실제로 중단되었는지도 확인해야 합니다.
- 확인 필요: CI 로그에서 설치된 `@company/ui` 버전이 2.0.0인지 확인해야 합니다. 로그에서 이 버전을 찾을 수 없으면 CI도 구버전을 쓴 것이므로 원인이 달라집니다.

## 권장 조치

1. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드합니다. 로컬에서도 같은 에러가 나면 원인은 CI 환경이 아니라 패키지 쪽입니다.
2. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다. CI 로그의 버전과 비교하면 로컬과 CI 중 어느 쪽이 다른 버전을 쓰는지 알 수 있습니다.
3. Node 18로 로컬 빌드를 한 번 해 보면 Node 버전의 영향을 분리할 수 있습니다.
4. 수정 방향은 두 가지입니다. 앱에서는 패키지가 공개한 경로로 import를 바꾸는 방법을 권장합니다. 패키지에서는 UI 팀에 `./button` 경로를 `exports`에 추가해 달라고 요청하는 방법이 있습니다.
