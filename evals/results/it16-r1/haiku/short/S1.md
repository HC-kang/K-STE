Redis를 도입하면 서버 4대가 같은 캐시(자주 쓰는 정보를 빠르게 꺼내려고 임시로 저장해 둔 곳)를 함께 쓰므로, 서버마다 상품 정보가 달라지는 문제가 없어집니다. 다만 가격을 바꾼 뒤 고객 화면에 언제 보이는지는 Redis를 도입하는 것만으로 정해지지 않습니다.

두 방식의 차이는 다음과 같습니다.

| 구분 | 현재 방식 (서버마다 로컬 캐시) | Redis 방식 (캐시 서버 1대 공유) |
|---|---|---|
| 저장 위치 | 서버 4대 각각의 메모리 | 별도 캐시 서버 1대 |
| 서버별 내용 | 서버마다 다를 수 있습니다 | 4대가 같은 내용을 읽습니다 |
| 가격 변경 후 고객에게 보이는 시점 | 최대 5분 뒤 | Redis 값을 갱신하는 방식에 따라 다릅니다 (확인 필요) |
| 응답 속도 | 자기 메모리에서 바로 읽습니다 | 네트워크(서버 사이의 통신 경로)를 거쳐 읽으므로 메모리보다 느립니다 |
| 장애 영향 | 서버 1대가 멈춰도 나머지 3대는 동작합니다 | Redis가 멈추면 4대 서버 모두 캐시를 쓸 수 없습니다 |

현재 방식에서는 각 서버가 상품 목록을 메모리에 저장하고 5분이 지나면 저장값을 버립니다. 그래서 가격을 바꾸면 서버마다 최대 5분 뒤에 새 가격을 읽습니다.

Redis 방식에서 가격을 바꾼 직후에 고객에게 새 가격을 보이려면, 가격을 바꿀 때 Redis에 저장된 값을 바로 고치도록 설계해야 합니다. 확인 필요: 이 설계를 적용할지, 아니면 5분 만료 방식을 그대로 둘지 개발팀에 확인이 필요합니다.
