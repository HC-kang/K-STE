가장 유력한 원인은 2.0.0에서 추가된 `exports` 필드(패키지가 외부에 공개할 경로를 정한 설정)가 `@company/ui/button`이라는 하위 경로 import를 허용하지 않는 것입니다. 이는 추론이며, 아직 2.0.0의 `exports` 내용을 확인하지 않았습니다.

### 확인된 사실

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에 `exports` 필드가 추가되었습니다.
- CI는 Node 18, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

### 추론

로컬과 CI의 차이는 다음과 같이 추정합니다.

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `@company/ui` 설치 버전 | 1.4.0일 가능성이 큼 (설치 이후 재설치 기록 없음) | 2.0.0일 가능성이 큼 (lock 해시가 바뀌면 캐시 미스로 새로 설치) |
| `exports` 적용 여부 | 1.4.0에는 `exports`가 없어 하위 경로가 그대로 해석될 가능성이 큼 | 2.0.0의 `exports`가 적용됨 |

이 추정이 맞다면 로컬은 1.4.0으로 빌드되어 성공하고, CI는 2.0.0으로 빌드되어 실패합니다.

Node 버전은 원인일 가능성이 낮습니다. Node 18도 `exports`를 지원하므로, Node 버전 차이만으로 이 에러가 나지는 않습니다.

한편 macOS 기본 파일 시스템은 대소문자를 구분하지 않고, Linux CI는 구분합니다. import 경로의 대소문자가 실제 파일 이름과 다르면 로컬에서는 성공하고 CI에서만 실패할 수 있습니다.

### 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 실제 설치 버전을 확인합니다.
2. `npm view @company/ui@2.0.0 exports`를 실행해 2.0.0이 공개하는 경로 목록에 `./button`이 있는지 확인합니다.
3. CI 로그에서 `npm ci` 단계의 설치 버전을 확인합니다.
4. `button` 파일의 실제 이름과 import 경로의 대소문자가 같은지 확인합니다.

확인 필요: CI 에러 로그 전문, 2.0.0의 `exports` 전체 내용, 캐시 복원 로그.

### 수정 방향

- 2.0.0의 `exports`에 `./button`이 없으면, import 경로를 2.0.0이 공개하는 경로로 바꿔야 합니다. 대상 경로는 패키지 문서나 `exports` 목록에서 확인합니다.
- `exports`에 `./button`이 있는데도 실패하면, 대소문자와 빌드 설정(`tsconfig`, `next.config`)을 먼저 봅니다.
- 원인을 확정하기 전까지 임시로 `@company/ui`를 1.4.0으로 되돌릴 수 있습니다. 이 방법은 2.0.0 업그레이드를 미루는 것이므로, PM과 일정을 함께 정해야 합니다.
