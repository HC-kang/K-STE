이 빌드 실패는 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드가 `button` 하위 경로를 노출하지 않아서 생겼을 가능성이 가장 높다. 다만 이 분석은 전달받은 정보에만 근거하며, 패키지 코드와 CI 로그는 직접 확인하지 않았다.

## 확인된 사실

- CI(Node 18)에서 `Error: Cannot find module '@company/ui/button'`으로 빌드가 실패한다.
- 로컬(Node 20)에서는 빌드가 성공한다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0부터 패키지에 `exports` 필드가 있다.
- CI 캐시 키는 `package-lock.json`의 해시다.
- 로컬 `node_modules`는 업그레이드 전에 설치된 것이다.

## 추론: 원인 메커니즘

`exports` 필드가 있으면 Node와 번들러는 패키지가 `exports`에 명시한 경로만 외부에서 import하도록 허용한다. 1.4.0에는 `exports`가 없었으므로 `@company/ui/button`은 파일 경로(예: `button.js`)로 그대로 해석되었다. 2.0.0의 `exports`에 `./button`이 없거나 경로가 바뀌었다면, 같은 import는 실패한다.

로컬에서 성공하는 이유도 같은 맥락에서 설명된다. 로컬 `node_modules`가 업그레이드 전 설치본(1.4.0)이라면, 로컬은 2.0.0을 한 번도 쓰지 않은 상태다. 즉 로컬 빌드 성공은 2.0.0이 문제없다는 증거가 되지 못한다.

에러 문구도 확인이 필요하다. Node의 CommonJS 해석은 `exports`에 없는 경로를 `ERR_PACKAGE_PATH_NOT_EXPORTED`로 알리고, 웹팩은 `Module not found: Can't resolve`로 알린다. `Cannot find module`은 파일이 없을 때 주로 나오는 문구다. 따라서 이 에러가 Next.js 빌드 단계에서 나온 것인지, Node로 직접 실행되는 설정 파일이나 스크립트에서 나온 것인지 전체 스택 트레이스로 확인해야 한다.

## 가설별 비교

| 가설 | 근거 | 로컬에서 재현되지 않는 이유 | 가능성 | 확인 방법 |
|---|---|---|---|---|
| 2.0.0의 `exports`가 `button` 경로를 노출하지 않는다 | 업그레이드 시점과 에러가 일치한다 | 로컬 `node_modules`가 1.4.0이다 | 높음(추정) | 2.0.0 `package.json`의 `exports` 항목 확인 |
| CI와 로컬의 Node 버전 차이 | CI는 Node 18, 로컬은 Node 20이다 | Node 18과 20은 `exports` 해석 방식이 같다 | 낮음 | 두 버전에서 `require.resolve('@company/ui/button')` 결과 비교 |
| 캐시가 오래된 의존성을 복원한다 | 캐시 키가 lock 해시다 | 오래된 설치본이면 CI가 1.4.0을 써서 에러가 나지 않아야 한다 | 낮음 | CI 로그에서 캐시 복원 여부와 설치 버전 확인 |

Node 버전 차이는 원인이 아닐 가능성이 크지만, CI와 로컬의 Node 버전을 맞추는 것을 권장한다. 버전이 다르면 이번처럼 원인 파악이 어려워진다.

## 확인이 필요한 항목

- CI 로그에서 실제로 설치된 `@company/ui` 버전이 2.0.0인지 확인 필요.
- 전체 스택 트레이스에서 에러가 발생한 단계(Next.js 빌드, Node 스크립트, 테스트 중 어느 것인지) 확인 필요.
- 2.0.0의 `exports` 전체 항목에 `./button`이 있는지, 다른 경로(예: `./components/button`)로 바뀌었는지 확인 필요.
- 2.0.0의 `engines` 필드와 현재 Next.js 버전이 요구하는 Node 버전 확인 필요.

## 검증 절차

1. 로컬에서 `npm ls @company/ui`를 실행해 설치 버전을 확인한다. 1.4.0이면 로컬은 업그레이드를 검증하지 않은 상태다.
2. 로컬에서 `rm -rf node_modules && npm ci`로 새로 설치한 뒤 빌드한다. 같은 에러가 나면 CI 조건을 재현한 것이다.
3. Node 18과 Node 20에서 각각 `node -e "require.resolve('@company/ui/button')"`을 실행해 결과를 비교한다.
4. 2.0.0의 `exports` 항목과 코드의 import 경로를 한 줄씩 대조한다.

## 수정 방향 (아직 실행하지 않음)

- 원인이 확정되면 import 경로를 2.0.0 `exports`에 있는 경로로 바꾸는 것을 권장한다.
- 2.0.0 `exports`에 `./button`이 없다면 패키지 관리자에게 export 추가를 요청할 수 있다.
- 당장 막혀 있다면 `@company/ui`를 1.4.0으로 되돌려 빌드를 살릴 수 있다. 다만 2.0.0에서만 쓰는 기능이 있다면 이 방법은 제한된다.
