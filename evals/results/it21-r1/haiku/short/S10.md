현재 원인은 확정하지 못했습니다. 가장 유력한 설명은 CI가 `@company/ui` 2.0.0을 설치하고, 2.0.0의 `exports` 필드(패키지가 외부에 공개하는 파일 경로를 정하는 설정)가 `@company/ui/button` 경로를 허용하지 않아서 모듈을 찾지 못한다는 것입니다. 이 작업 환경에서는 저장소나 패키지 파일을 열어 보지 않았으므로, 아래 내용은 전달받은 정보에 근거한 추론입니다.

### 확인된 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에서 패키지에 `exports` 필드가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`(설치할 패키지 버전을 기록한 파일)의 해시입니다.
- 로컬 `node_modules`(설치된 패키지가 담긴 폴더)는 업그레이드 전에 설치되었습니다.

### 추론

- 로컬 `node_modules`가 업그레이드 전 설치본이므로, 로컬 빌드는 1.4.0을 사용하고 있을 가능성이 큽니다. 1.4.0에는 `exports` 제한이 없어서 `button` 경로가 그대로 해석됩니다.
- `exports` 필드가 `./button` 경로를 빠뜨렸거나 다른 경로로 바꿨다면, `@company/ui/button` 같은 서브경로(패키지 안의 특정 파일을 가리키는 경로) import가 실패합니다. 이는 2.0.0의 `exports` 내용을 확인해야 확정됩니다.
- Node 18과 20 모두 `exports` 필드를 지원하므로, Node 버전 차이가 주원인일 가능성은 낮다고 봅니다. 다만 실제로 재현해 보지 않았습니다.

### 확인 필요

- 확인 필요: 커밋된 `package-lock.json`에 `@company/ui`가 2.0.0으로 기록되어 있는지 확인해야 합니다. 기록되어 있지 않다면 CI가 설치하는 버전도 1.4.0일 수 있습니다.
- 확인 필요: CI 로그에서 실제 설치된 `@company/ui` 버전을 확인해야 합니다. `npm ls @company/ui` 출력이 이 목적에 맞습니다.
- 확인 필요: 로컬에서도 `npm ls @company/ui`를 실행해 1.4.0인지 확인해야 합니다.
- 확인 필요: 2.0.0의 `package.json`에 있는 `exports` 필드에 `./button` 항목이 있는지 확인해야 합니다.
- 확인 필요: Node 18 환경에서 로컬 빌드를 재현해 실패 여부를 확인해야 합니다. nvm(Node 버전 관리 도구)으로 전환하면 됩니다.

PM이 볼 때는 "로컬은 옛 버전을 쓰고 있어서 문제가 가려졌고, CI는 새 버전을 쓰면서 새 설정 때문에 실패하는 것으로 보인다"로 이해하면 됩니다. 캐시 키(CI가 저장된 설치본을 찾는 식별자)는 lock 파일이 바뀌면 달라지므로, lock 파일 갱신 여부가 확인되면 캐시 문제는 자연스럽게 정리됩니다.
