## 결론

CI 빌드 실패의 가장 유력한 원인은 로컬과 CI가 서로 다른 버전의 `@company/ui`를 쓰고 있다는 점이다. 이는 추론이며 아직 확인되지 않았다.

## 확인된 사실

- Next.js 앱 빌드는 CI(GitHub Actions)에서만 실패한다.
- 실패 에러는 `Error: Cannot find module '@company/ui/button'`이다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에서 패키지에 `exports` 필드가 추가되었다.
- CI는 Node 18을, 로컬은 Node 20을 사용한다.
- CI 캐시 키는 `package-lock.json`의 해시이다.
- 로컬 `node_modules`는 업그레이드 3일 전에 설치되었다.

## 원인 추론

### 1. 로컬이 2.0.0을 실제로 설치하지 않았을 가능성 (유력)

로컬 `node_modules`가 업그레이드 이전 상태로 남아 있다면 1.4.0이 설치된 상태일 가능성이 크다. 1.4.0에서는 `@company/ui/button` 경로가 동작하므로 로컬 빌드가 성공한다.

CI는 `package-lock.json`이 바뀌면서 캐시 키도 바뀌었으므로 캐시를 쓰지 못하고 새로 설치한다. 이때 2.0.0을 받으면 실패한다.

로컬에 설치된 실제 버전은 아직 확인되지 않았다.

### 2. 2.0.0의 `exports` 필드가 `./button` 경로를 막았을 가능성

`exports` 필드가 있으면 Node와 번들러는 목록에 명시된 경로만 허용한다. 2.0.0의 `exports`에 `./button` 항목이 없거나 경로가 바뀌었다면 이 import는 실패한다.

에러 문구 `Cannot find module`은 번들러나 TypeScript의 경로 해석 단계에서도 나올 수 있으므로, 어느 단계에서 발생했는지 전체 로그로 확인해야 한다.

### 3. Node 18과 20의 차이 (가능성 낮음)

Node 18과 Node 20은 모두 `exports` 필드를 지원한다. 따라서 Node 버전 차이만으로 이 에러가 난다고 보기는 어렵다. 다만 조건부 `exports` 해석의 차이는 확인하지 않았으므로 배제하지 않는다.

### 4. 파일명 대소문자 차이 (미확인)

macOS 기본 파일 시스템은 대소문자를 구분하지 않고, Linux 계열 CI 러너는 구분한다. 2.0.0의 파일명이 `Button.js`처럼 대문자로 시작하면 로컬에서는 성공하고 CI에서만 실패할 수 있다. CI 러너의 OS는 확인되지 않았다.

## 검증 방법

| 확인 항목 | 방법 | 결과 해석 |
|---|---|---|
| lock 파일의 버전 | `grep -A2 '"node_modules/@company/ui"' package-lock.json` | 2.0.0이면 CI가 2.0.0을 설치한다. 1.4.0이면 원인 1은 성립하지 않는다. |
| 로컬 설치 버전 | `npm ls @company/ui` | 1.4.0이면 로컬이 구버전을 쓰고 있다. |
| CI 설치 버전 | CI 로그에서 설치 버전을 확인하거나 `npm ls @company/ui`를 임시로 추가 실행 | 2.0.0이면 버전 차이가 확정된다. |
| 2.0.0의 `exports` 내용 | 2.0.0의 `package.json`에서 `exports` 항목 확인 | `./button` 항목이 없으면 원인 2가 유력하다. |
| 2.0.0의 파일명 | 빈 임시 디렉터리에서 `npm pack @company/ui@2.0.0` 실행 후 내용 확인 | 파일명 대소문자가 import 경로와 다르면 원인 4가 유력하다. |
| 전체 에러 로그 | CI 로그 전체 확인 | 에러가 난 도구(Next.js, webpack, tsc)를 특정한다. |

로컬에서 재현하려면 `rm -rf node_modules && npm ci`로 깨끗하게 다시 설치한 후 빌드한다. 재현되면 원인을 로컬에서 직접 확인할 수 있다.

## 수정 방향 (검증 후 선택)

- 원인 1이 확인되면 로컬을 다시 설치하여 CI와 같은 조건에서 재현한다.
- 원인 2나 4가 확인되면 2.0.0의 변경 문서를 확인하여 import 경로를 수정한다.
- 2.0.0의 `exports`에 필요한 경로가 빠져 있으면 패키지 관리자에게 추가를 요청하거나 1.4.0으로 되돌린다.
- Node 버전 차이는 원인이 아닐 가능성이 크지만, CI와 로컬의 Node 버전을 `.nvmrc` 등으로 맞추면 같은 문제를 줄일 수 있다.

## PM용 요약

- 현재 상태: CI 빌드가 실패한다. 로컬 빌드는 성공한다.
- 배포 영향: 확인되지 않았다.
- 원인 후보: `@company/ui` 2.0.0 업그레이드와 관련이 있을 가능성이 크다. 로컬과 CI가 같은 버전을 쓰고 있는지가 핵심이다.
- 다음 단계: 위 검증 표의 첫 두 항목을 확인한 후 원인을 확정하고 수정 방향을 정한다.
