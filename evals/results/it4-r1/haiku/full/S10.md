현재 정보만으로는 원인을 하나로 확정할 수 없다. 먼저 로컬에 실제로 어떤 버전의 `@company/ui`가 설치되어 있는지 확인해야 한다. 로컬 `node_modules`가 3일 전보다 먼저 설치된 것이라면 로컬 빌드는 2.0.0이 아니라 1.4.0으로 성공했을 가능성이 크다. 그러면 로컬 성공은 2.0.0이 문제없다는 근거가 되지 않는다.

### 확인된 사실

- CI(GitHub Actions)에서만 `Cannot find module '@company/ui/button'` 오류로 빌드가 실패한다.
- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에 `exports` 필드가 추가됐다. `exports`는 패키지 안의 어떤 경로를 외부에 공개할지 정하는 설정이며, 여기에 없는 경로는 import할 수 없다.
- CI는 Node 18, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`의 해시다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치됐다.

### 가능한 원인 (추론, 아직 검증하지 않음)

1. 로컬이 2.0.0을 쓰지 않을 가능성이다. 로컬 `node_modules`가 오래됐다면 로컬과 CI의 차이는 Node 버전이 아니라 설치된 패키지 버전일 수 있다.
2. 2.0.0의 `exports`에 `./button` 경로가 없거나 다르게 적혀 있을 가능성이다. 2.0.0에서 파일 구조가 바뀌었다면 `@company/ui/button`은 외부에 공개되지 않은 경로가 된다. 다만 Node가 이 경로를 막을 때는 보통 다른 오류 문구를 내므로, 이 문구가 어떤 도구에서 나왔는지도 확인이 필요하다.
3. Node 18과 Node 20의 모듈 해석 차이일 가능성이다. 패키지가 ESM(ES Module, 최신 자바스크립트 모듈 방식) 전용이라면 Node 18은 이를 `require`로 불러오지 못한다. 로컬 Node 20의 세부 버전에 따라 결과가 달라질 수 있다.
4. 파일 이름 대소문자 차이일 가능성이다. macOS(로컬)는 대소문자를 구분하지 않고 Linux(CI)는 구분한다. 2.0.0의 파일명이 `Button.js`인데 `button`으로 import하면 CI에서만 실패한다.

캐시는 가능성이 낮다. 캐시 키가 `package-lock.json` 해시이므로 lock 파일이 바뀌면 캐시가 새로 만들어진다. 다만 `package.json`만 2.0.0으로 바뀌고 lock 파일이 1.4.0으로 남아 있다면 CI 설치 결과가 로컬과 달라지므로, 커밋된 lock 파일의 버전도 확인해야 한다.

### 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 실제 설치 버전을 확인한다.
2. CI 로그에서 설치된 `@company/ui` 버전과 Node 버전을 확인한다.
3. 2.0.0 패키지의 `exports` 필드와 실제 파일 경로(대소문자 포함)를 비교한다.
4. 로컬에서 `nvm`으로 Node 18을 선택하고 `rm -rf node_modules && npm ci`를 실행해 CI 조건으로 재현한다.

1번 결과에 따라 다음 확인이 달라지므로 1번부터 실행하십시오.
