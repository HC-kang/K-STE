가장 유력한 원인은 로컬 `node_modules`에 아직 `@company/ui` 1.4.0이 설치되어 있어서, 2.0.0의 `exports` 제한이 로컬에서만 적용되지 않는 것입니다. 이 내용은 제공된 사실에서 추론한 것이고, 로컬 설치 버전은 아직 확인하지 않았습니다.

## 추론 근거

- `exports` 필드가 없는 1.4.0에서는 `@company/ui/button`을 파일 경로 그대로 찾기 때문에 로컬 빌드가 성공합니다.
- 2.0.0에는 `exports` 필드가 있으므로, 이 필드에 `./button`이 없으면 해당 경로를 찾지 못합니다. CI는 2.0.0을 설치하므로 이 경우 `Cannot find module` 에러가 납니다.
- 로컬 `node_modules`는 3일 전 업그레이드보다 먼저 설치했으므로, 1.4.0이 남아 있을 가능성이 높습니다.

## 다른 가설 검토

| 가설 | 판단 | 이유 |
| --- | --- | --- |
| Node 18과 20의 차이 | 가능성이 낮습니다 | `exports` 필드는 Node 18과 20 모두 지원하므로, 이 차이만으로 모듈 해석 결과가 달라질 이유가 없습니다. |
| CI 캐시 | 가능성이 낮습니다 | 캐시 키가 `package-lock.json` 해시이므로, 업그레이드 커밋에 lock 파일이 포함됐다면 캐시는 새로 만들어집니다. |

CI 캐시 판단은 업그레이드 커밋에 `package-lock.json`이 포함됐다는 전제에 기대고 있습니다.

## 확인 필요

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 확인합니다.
2. `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드합니다. 로컬에서도 같은 에러가 나면 원인이 확정됩니다.
3. `@company/ui` 2.0.0의 `package.json`에서 `exports` 항목에 `./button`이 있는지 확인합니다.
4. 업그레이드 커밋에 `package-lock.json` 변경이 들어 있는지 확인합니다.

## 해결 방향

- 2.0.0이 `./button`을 노출하지 않는다면, import 경로를 `exports`에 정의된 경로로 바꿉니다.
- 2.0.0이 `./button`을 노출해야 하는 패키지라면, 패키지 담당자에게 `exports` 추가를 요청합니다.

확인 필요: 2.0.0에서 `button`의 공식 import 경로가 무엇인지는 패키지 릴리스 노트나 마이그레이션 문서를 봐야 알 수 있습니다.
