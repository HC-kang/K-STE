CI 빌드 실패의 가장 유력한 원인은 2.0.0에 새로 추가된 `exports` 필드입니다. 이 필드는 패키지 안에서 외부에 공개할 경로를 적은 목록(패키지가 허용하는 import 경로 목록)이고, 목록에 없는 `@company/ui/button` 같은 하위 경로 import를 막습니다. 로컬 빌드가 성공하는 이유는 로컬에 아직 `exports`가 없는 1.4.0이 남아 있어서로 보입니다(추론). 따라서 로컬 빌드 성공을 2.0.0이 정상이라는 근거로 쓰면 안 됩니다.

## 원인

`exports` 필드가 있는 패키지는 목록에 적힌 경로만 가져오게 허용합니다. 2.0.0의 `exports` 목록에 `./button`이 없다면 `@company/ui/button` import는 실패합니다. 다만 이 분석에서는 2.0.0 패키지의 실제 내용을 열어 보지 않았습니다. 확인 필요: 2.0.0의 `exports`에 `./button` 항목이 있는지 여부. 에러 문구 `Cannot find module`만으로는 어느 도구가 에러를 냈는지 확정할 수 없습니다. 확인 필요: 전체 에러 로그와 에러를 낸 도구(Next.js, webpack, Node 중 무엇인지).

## 로컬과 CI의 차이

| 항목 | 로컬 | CI |
|---|---|---|
| `@company/ui` 버전 | 1.4.0으로 보임(추론) | 2.0.0으로 보임(추론) |
| `exports` 필드 | 없음 | 있음 |
| `@company/ui/button` import | 동작함 | 막힘 |
| Node 버전 | 20 | 18 |
| `node_modules` 출처 | 3일 전 설치본 | lock 해시 기준 캐시 또는 새 설치 |

로컬 `node_modules`는 업그레이드 전에 설치되었으므로, `package-lock.json`만 바꾸고 다시 설치하지 않았다면 1.4.0이 남아 있습니다. `node_modules`(설치된 패키지가 저장되는 폴더)를 다시 만들지 않으면 로컬은 2.0.0을 전혀 테스트하지 않은 상태입니다.

## Node 18과 20의 차이

Node 18과 Node 20은 둘 다 `exports` 필드를 지원합니다. 따라서 Node 버전 차이만으로 이 에러가 생긴다고 보기는 어렵습니다(추론). 다만 Node 18은 2025년 4월에 지원이 끝난 버전이므로, CI에서 Node 버전을 올리는 일은 별도로 검토할 가치가 있습니다.

캐시 키는 `package-lock.json`의 해시입니다(캐시 키는 저장된 설치 결과를 찾는 이름표입니다). 업그레이드로 lock 해시가 바뀌었다면 새 캐시 키가 생기고, 그 경우 새로 설치되는 것이 정상입니다. 확인 필요: 캐시가 실제로 miss였는지, 또는 `restore-keys`로 이전 캐시를 가져왔는지 여부.

## 확인할 항목

이 분석에서는 명령을 실행하거나 빌드를 돌려 보지 않았습니다. 아래 항목은 원인을 확정하기 위해 확인할 순서입니다.

1. 로컬에서 `npm ls @company/ui`를 실행하여 실제 설치 버전을 확인합니다.
2. 로컬에서 `node_modules`를 지우고 `npm ci` 후 `npm run build`를 실행하여 2.0.0 기준 빌드가 실패하는지 확인합니다.
3. 2.0.0 패키지의 `package.json`에서 `exports` 항목을 열어 `./button` 경로가 있는지 확인합니다.
4. CI 로그에서 캐시 복원 단계가 hit였는지 miss였는지 확인합니다.
5. Node 20으로 맞춘 CI 브랜치에서 빌드하여 Node 버전의 영향을 따로 확인합니다.

## 권장 조치

가장 간단한 해결책은 2.0.0 문서에 나온 공식 import 경로로 코드를 바꾸는 것입니다. 2.0.0에 `./button` 경로가 없다면 이는 2.0.0의 호환성 깨짐(기존 사용법이 동작하지 않는 변경)입니다. 이 경우 패키지 관리 측에 `exports`에 해당 경로를 추가해 달라고 요청할 수 있습니다. 수정이 끝나기 전까지는 `@company/ui`를 1.4.0으로 고정하는 방법도 있습니다. Node 버전은 20 이상으로 올리는 것을 권장합니다.
