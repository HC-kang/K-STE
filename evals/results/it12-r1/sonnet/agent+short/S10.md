원인은 `@company/ui` 2.0.0의 `exports` 필드로 보이고, CI만 2.0.0을 설치하기 때문에 CI에서만 실패하는 것으로 보입니다. 아래 내용 중 "확인한 사실"을 뺀 나머지는 아직 실행해서 확인하지 않았습니다.

## 확인한 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0 패키지에는 `exports` 필드가 있습니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치했습니다.

## 추론한 원인

1. 로컬 `node_modules`에는 1.4.0이 남아 있을 가능성이 높습니다. 1.4.0에는 `exports` 필드가 없으므로 `@company/ui/button` 같은 하위 경로를 파일 경로로 직접 읽을 수 있습니다.
2. 버전을 올리면서 `package-lock.json`이 바뀌었으므로 캐시 키도 바뀌었습니다. 그래서 CI는 캐시를 쓰지 않고 새로 설치하며, 2.0.0을 받습니다.
3. 패키지에 `exports` 필드가 있으면 Node와 번들러는 `exports`에 적힌 경로만 허용합니다. 2.0.0의 `exports`에 `./button`이 없거나 다른 이름으로 바뀌었다면 `Cannot find module '@company/ui/button'`이 발생합니다.

캐시는 원인이 아닙니다. 캐시 키가 lockfile 해시이므로 오래된 캐시가 재사용된 것이 아니라, 새 lockfile로 정상 설치된 것입니다. 오히려 로컬 환경이 오래된 상태입니다.

Node 버전 차이는 원인일 가능성이 낮습니다. Node 18과 Node 20 모두 `exports`를 지원합니다. 다만 `exports`의 조건 이름(`import`, `require`, `default` 등)에 따라 동작이 달라지는지는 확인하지 않았습니다.

## 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 확인해야 합니다.
2. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드해야 합니다. 로컬에서도 같은 에러가 나면 원인이 확정됩니다.
3. `node_modules/@company/ui/package.json`의 `exports`에 `./button` 항목이 있는지 확인해야 합니다.
4. 2번에서 재현되지 않으면 Node 20과 Node 18을 바꿔 가며 빌드해서 Node 버전 영향을 따로 확인해야 합니다.

## 해결 방안

- `exports`에 `./button`이 없고 이름만 바뀌었다면, import 경로를 2.0.0의 새 경로로 바꾸는 방안을 권장합니다.
- 2.0.0이 해당 하위 경로를 의도적으로 공개하지 않는다면, 패키지 변경 문서(changelog)에서 대체 import 방법을 확인해야 합니다.
- `@company/ui` 담당 팀의 실수로 `./button`이 빠졌다면, 담당 팀에 `exports` 수정을 요청해야 합니다.
- 임시 조치로 `@company/ui`를 1.4.0으로 고정할 수 있습니다. 이 방안은 2.0.0 업그레이드를 되돌리므로 PM과 일정 협의가 필요합니다.

확인 필요: 2.0.0의 `exports`에 `./button`이 실제로 없는지, 아니면 `import`나 `require` 조건 때문에 해석에 실패하는지 아직 모릅니다.
