가장 유력한 원인은 2.0.0에 추가된 `exports` 필드(패키지가 외부에 공개할 경로를 적은 설정 항목)에 `./button` 경로가 빠져 있어서, CI가 `@company/ui/button`을 찾지 못하는 것으로 보입니다. 이는 추론이며, 아직 2.0.0의 `exports` 정의를 직접 확인하지 않았습니다.

### 확인된 사실
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에서 패키지에 `exports` 필드가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

### 추론
- `exports` 필드가 있으면 패키지는 그 목록에 적힌 경로만 외부에 공개합니다. 2.0.0의 `exports`에 `./button`이 없다면 `@company/ui/button` import는 실패합니다.
- 로컬 `node_modules`는 3일 전에 설치되었으므로 1.4.0일 가능성이 높습니다. 따라서 로컬 빌드 성공은 2.0.0에서 이 import가 동작한다는 근거가 되지 않습니다.
- `package-lock.json`이 바뀌면 캐시 키도 바뀝니다. 그러면 CI는 캐시를 쓰지 않고 lock 파일 기준으로 새로 설치하며, 이 과정에서 2.0.0을 받습니다.
- Node 18과 20은 모두 `exports`를 지원합니다. 따라서 Node 버전 차이만으로 이 에러를 설명하기는 어렵습니다.
- `Cannot find module`은 보통 Node가 `require`로 모듈을 찾을 때 나오는 메시지입니다. 에러가 번들러(여러 파일을 하나로 묶는 빌드 도구) 단계에서 났는지, 설정 파일이나 테스트 실행 단계에서 났는지에 따라 원인 범위가 달라집니다.

### 확인 필요
- 2.0.0의 `exports` 정의에 `./button`이 있는지
- CI 로그에서 실제로 설치된 `@company/ui` 버전
- 에러가 발생한 정확한 파일과 스택 트레이스(에러가 거쳐 온 호출 경로)
- CI 실패가 3일 전 업그레이드 이후부터 시작되었는지
- Node 18로 로컬 빌드했을 때 같은 에러가 재현되는지

### 확인 방법
1. 빈 디렉터리에서 `npm install @company/ui@2.0.0`을 실행하고, 생성된 `node_modules/@company/ui/package.json`의 `exports` 항목을 확인합니다.
2. `exports`에 `./button` 또는 `./*` 같은 패턴이 있는지 확인합니다.
3. CI 로그에서 설치된 버전과 에러가 난 단계를 확인합니다.
4. 로컬에서 `rm -rf node_modules && npm ci`로 lock 파일 기준으로 다시 설치한 뒤 빌드합니다. 이 결과로 2.0.0에서 로컬 빌드가 실패하는지 확인할 수 있습니다.
5. 로컬에서 Node 18로 빌드해 CI와 같은 에러가 나는지 확인합니다.

### 조치 선택지
- `exports`에 `./button` 경로가 없다면, `@company/ui` 관리 팀에 경로 추가를 요청하는 것을 권장합니다.
- 경로를 추가할 수 없다면, import 경로를 `exports`에 공개된 경로로 바꿉니다.
- 당장 배포가 필요하다면 `@company/ui`를 1.4.0으로 되돌리는 방법도 있습니다.
