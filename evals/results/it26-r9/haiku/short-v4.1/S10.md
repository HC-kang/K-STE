원인은 2.0.0에 새로 추가된 `exports` 필드가 `@company/ui/button` 같은 서브경로 import(패키지 안의 특정 파일을 경로로 직접 가져오는 방식)를 막은 것으로 보입니다. 로컬에는 3일 전에 설치한 `node_modules`가 남아 있어 옛 버전이 쓰이므로 빌드가 성공합니다. 이는 현재 정보로 세운 추론이며, 아직 실행해서 확인하지 않았습니다.

## 확인된 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드(패키지가 외부에 공개할 경로를 정하는 설정)가 추가되었습니다.
- CI는 Node 18을 쓰고, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시(파일 내용에서 만든 짧은 식별값)입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

## 추론

- `exports`가 있으면 패키지는 그 목록에 있는 경로만 외부에서 가져가게 허용합니다.
- 2.0.0의 `exports`에 `./button`이 없다면 CI는 `@company/ui/button`을 찾지 못합니다.
- 로컬의 오래된 `node_modules`에는 `exports`가 없으므로 같은 경로가 파일로 바로 찾아집니다.
- `package-lock.json`이 바뀌었다면 캐시 키도 바뀌어 CI가 2.0.0을 새로 설치합니다.

## 미확인

현재 자료로는 Node 18과 Node 20의 차이가 이 에러의 원인이라는 근거가 없습니다. 2.0.0의 `exports`에 `./button` 항목이 있는지는 아직 보지 않았습니다. 로컬 `node_modules`에 실제로 1.4.0이 설치되어 있는지도 확인하지 않았습니다. `package-lock.json`이 3일 전에 바뀌었는지도 확인하지 않았습니다.

## 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. `node_modules/@company/ui/package.json`을 열어 `exports`에 `./button` 항목이 있는지 확인합니다.
3. 로컬에서 `rm -rf node_modules && npm ci`로 lock 파일 기준 패키지를 새로 설치한 뒤 빌드를 실행합니다.
4. 3번에서 같은 에러가 나면 이 추론이 맞을 가능성이 높습니다.
5. CI 로그에서 설치된 `@company/ui` 버전을 확인합니다.

## 수정 방향 후보

수정 방향은 세 가지 후보가 있습니다. 각 방법마다 확인할 점이 다릅니다. 선택은 위 확인 결과에 따라 달라집니다.

| 방법 | 내용 | 확인할 점 |
|---|---|---|
| 라이브러리의 `exports`에 `./button` 추가 | `@company/ui` 쪽을 수정합니다 | 라이브러리 관리 담당자에게 요청해야 합니다 |
| 앱의 import를 루트 경로로 변경 | `@company/ui`에서 `Button`을 가져옵니다 | 2.0.0 루트 경로에서 `Button`을 export하는지 확인해야 합니다 |
| 1.4.0으로 고정 | 2.0.0 업그레이드를 보류합니다 | 2.0.0의 새 기능이 필요한지 확인해야 합니다 |
