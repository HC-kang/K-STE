가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드(패키지가 외부에 공개하는 경로를 제한하는 설정)에 `./button` 경로가 없는 것입니다. 로컬은 아직 1.4.0이 설치돼 있어서 이 문제가 드러나지 않습니다. 이 결론은 주어진 정황에서 추론한 것이고, 패키지 내용은 아직 보지 않았습니다.

## 추론 근거

- 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`처럼 패키지 내부 파일 경로를 직접 불러올 수 있습니다.
- 2.0.0에는 `exports` 필드가 있어서 여기에 적힌 경로만 불러올 수 있습니다. `./button`이 적혀 있지 않으면 `Cannot find module` 에러가 납니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다. 버전을 올리면서 lock 파일이 바뀌었으므로 캐시가 새로 만들어졌고, CI는 2.0.0을 설치했다고 볼 수 있습니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치한 것입니다. 그래서 로컬은 1.4.0을 쓰고 있을 가능성이 높습니다.

## Node 버전의 영향

Node 18과 Node 20은 모두 `exports` 필드를 적용합니다. 그래서 Node 버전 차이는 이 에러의 주된 원인이 아닌 것으로 보입니다. 다만 `exports`에 Node 18이 지원하지 않는 문법이 있는지는 아직 보지 않았습니다.

## 아직 확인하지 않은 것

- 로컬에 설치된 `@company/ui`의 실제 버전
- 2.0.0의 `exports`에 `./button`이 있는지 여부
- `exports`에 `./button`이 있다면, Node 18이나 Next.js 번들러(코드를 묶는 도구)가 그 경로를 해석하지 못하는지 여부

## 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 봅니다. 1.4.0이면 위 추론이 맞을 가능성이 커집니다.
2. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드합니다. CI와 같은 에러가 나면 원인이 CI 환경이 아니라 2.0.0이라는 뜻입니다.
3. `node_modules/@company/ui/package.json`의 `exports` 필드에서 `./button`이 있는지 봅니다.
4. 3번에서 `./button`이 있으면 CI와 같은 Node 18로 로컬 빌드를 다시 해서 Node 버전의 영향을 따로 봅니다.

## 해결 방법

`./button`이 `exports`에 없다면 방법은 세 가지입니다.

- `@company/ui` 담당자에게 `exports`에 `./button`을 추가해 달라고 요청합니다.
- 2.0.0이 새로 제공하는 경로로 앱의 import 구문을 바꿉니다.
- 위 두 가지가 끝날 때까지 `@company/ui`를 1.4.0으로 되돌립니다. 이 방법은 임시 조치입니다.

PM이 판단할 사항은 일정입니다. 담당자 수정을 기다릴지, 앱의 import를 먼저 바꿀지에 따라 일정이 달라집니다.
