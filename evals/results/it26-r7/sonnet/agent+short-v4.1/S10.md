CI 빌드 실패의 가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드(패키지가 외부에 공개하는 경로 목록)에 `@company/ui/button`이 없는 것으로 보입니다. 이 내용은 추론이고, 아직 검증하지 않았습니다.

## 근거

- 2.0.0부터 패키지에 `exports` 필드가 생겼습니다. `exports`가 있으면 Node와 번들러는 목록에 적힌 경로만 불러옵니다. 1.4.0에서 되던 `@company/ui/button` 같은 내부 파일 경로 import가 2.0.0에서는 `Cannot find module`로 실패할 수 있습니다.
- CI 캐시 키가 `package-lock.json`의 해시입니다. 업그레이드로 락파일이 바뀌었다면 캐시가 갱신되고, CI는 2.0.0을 설치합니다.
- 로컬 `node_modules`는 업그레이드 3일 전보다 먼저 설치한 것입니다. 그래서 로컬에는 1.4.0이 남아 있을 가능성이 있고, 이 경우 로컬 빌드는 `exports` 제약을 받지 않고 성공합니다.

## Node 버전의 영향

Node 18과 Node 20 차이가 원인일 가능성은 낮아 보입니다. 두 버전 모두 `exports`를 지원합니다. 다만 Node 버전이 영향을 주는지는 검증하지 않았습니다.

## 검증 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 2.0.0인지 봅니다.
2. 2.0.0의 `package.json`에서 `exports`에 `./button`이 있는지 봅니다.
3. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드합니다. 이 빌드가 실패하면 원인은 2.0.0의 `exports`로 확정됩니다. Node 18에서도 같은 빌드를 해 두 버전의 결과를 비교합니다.

## 해결 방향

2에서 `./button`이 없으면 선택지는 두 가지입니다.

- 앱의 import를 2.0.0이 공개하는 경로로 바꿉니다.
- `@company/ui` 담당자에게 `./button` 경로를 `exports`에 추가해 달라고 요청합니다.

2에서 `./button`이 있는데도 실패하면 이 추론이 틀린 것이므로, 다시 분석해야 합니다.

확인 필요: "3일 전에 올렸다"는 `package.json`과 `package-lock.json`을 모두 커밋했다는 뜻인지, `package.json`만 바꿨다는 뜻인지 알 수 없습니다. 락파일이 커밋되지 않았다면 CI 캐시가 갱신되지 않아 위 두 번째 근거가 성립하지 않습니다.
