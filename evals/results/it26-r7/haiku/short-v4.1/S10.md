가장 가능성이 높은 원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드입니다. 이 필드가 있으면 Node.js(JavaScript 실행 환경)는 패키지가 공개한 경로만 불러올 수 있습니다. 2.0.0의 공개 목록에 `button` 경로가 없거나 다른 이름으로 바뀌었다면 CI에서 이 에러가 납니다. 다만 2.0.0의 `exports` 내용은 아직 확인하지 않았습니다.

#### 로컬에서만 성공하는 이유

로컬 `node_modules`가 3일 전 이전에 설치되었다면 1.4.0이 그대로 남아 있을 가능성이 높습니다(추론). 1.4.0에는 `exports` 필드가 없어서 패키지 안의 어떤 파일 경로든 불러올 수 있습니다. 따라서 로컬 빌드는 2.0.0이 아니라 1.4.0으로 성공한 것일 수 있습니다.

CI는 `package-lock.json`에 적힌 버전을 설치합니다. lock 파일이 2.0.0으로 갱신되었다면 CI는 2.0.0으로 빌드합니다(추론). lock 파일의 실제 내용은 확인하지 않았습니다.

#### 원인 후보별 판단

| 가능성 | 근거 | 확인 방법 |
|---|---|---|
| 2.0.0의 `exports`에 `button` 경로가 없거나 바뀜 (가능성 높음) | 에러가 하위 경로 import에서 발생하고 2.0.0에 `exports`가 추가됨 | 2.0.0 `package.json`의 `exports` 항목 확인 |
| 로컬이 1.4.0을 계속 사용 (가능성 높음) | 로컬 `node_modules`가 3일 전 이전 설치본임 | 로컬에서 `npm ls @company/ui` 실행 |
| Node 18과 20의 차이 (가능성 낮음) | Node 18과 20 모두 `exports`를 지원함 | Node 18 환경에서 재현 |
| 오래된 캐시 복원 (미확인) | 캐시 키는 lock 해시라서 lock이 바뀌면 새로 만들어짐 | CI 캐시 설정에 `restore-keys`가 있는지 확인 |

Node 버전 차이는 두 버전 모두 `exports`를 지원하므로 직접 원인일 가능성이 낮습니다. 다만 Next.js 버전이나 번들러 설정에 따른 해석 차이는 확인하지 않았습니다.

#### 점검 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 실제 설치 버전을 확인합니다.
2. 로컬에서 `npm ci`를 실행해 lock 파일 기준으로 다시 설치한 뒤 빌드합니다. 실패하면 CI 실패가 재현된 것입니다.
3. 2.0.0 패키지의 `package.json`에서 `exports` 항목을 확인하고 `button` 경로가 공개되어 있는지 봅니다.
4. CI 로그에 설치된 버전을 출력하는 단계를 추가해 CI가 실제로 2.0.0을 설치했는지 확인합니다.

아직 위 검사를 실행하지 않았으므로 원인은 확정되지 않았습니다. 해결 방향은 두 가지입니다. 하나는 import 경로를 2.0.0의 `exports`에 맞게 바꾸는 것이고, 다른 하나는 `@company/ui`를 1.4.0으로 되돌리는 것입니다. 어느 쪽을 택할지는 3번 검사 결과에 따라 달라집니다.
