원인은 `@company/ui` 2.0.0에 새로 생긴 `exports` 필드일 가능성이 큽니다. 로컬 빌드가 성공하는 이유는 로컬에 3일 전 이전 버전인 1.4.0이 남아 있기 때문으로 추정됩니다. 이 분석은 주어진 사실에 근거한 추정이며, 저장소 코드와 CI 로그는 직접 보지 않았습니다.

## 실패 원인 추정

`exports` 필드(패키지 바깥에 공개할 경로를 정하는 설정)가 있으면 Node는 그 목록에 있는 경로만 불러올 수 있습니다. 1.4.0에는 이 필드가 없어서 `@company/ui/button`이 파일 경로로 그대로 찾아집니다. 2.0.0의 `exports` 목록에 `./button`이 없거나 패턴이 맞지 않으면 이 import가 실패합니다.

에러 문구 `Cannot find module`은 Node의 모듈 해석기가 내는 형식입니다. Next.js 웹팩 빌드에서 난 에러라면 보통 `Module not found`로 표시됩니다. 따라서 `next.config.js`처럼 Node가 직접 실행하는 파일에서 이 import가 발생했을 가능성이 있습니다. (추론)

## 로컬과 CI가 다른 이유

로컬 `node_modules`(설치된 패키지가 담긴 폴더)는 3일 전보다 먼저 설치되었으므로 `@company/ui`는 1.4.0일 가능성이 큽니다. 로컬 빌드는 1.4.0으로 성공했으므로, 2.0.0이 문제없다는 증거가 되지 않습니다.

CI(코드 변경 시 자동으로 빌드하는 서버)는 락파일(`package-lock.json`, 설치 버전을 고정한 파일)을 기준으로 설치합니다. 락파일이 2.0.0으로 바뀌었다면 캐시 키(캐시를 찾는 식별자)인 락파일 해시도 바뀌어 기존 캐시가 맞지 않습니다. 그러면 CI는 새로 설치하면서 2.0.0을 받습니다. (추론)

## Node 버전 차이

Node 18과 Node 20은 모두 `exports`를 지원하므로, Node 버전 차이만으로 이 에러가 난다고 보기는 어렵습니다. 다만 두 환경이 다르면 로컬 결과로 CI 결과를 대신할 수 없습니다. Node 18은 2025년 4월에 지원이 끝났으므로, CI의 Node 버전도 20 이상으로 올리는 것을 권장합니다.

## 검증 방법 (권장 순서)

1. 로컬에서 `rm -rf node_modules`를 실행한 뒤 `npm ci`로 다시 설치하고 빌드합니다. 설치 후 `npm ls @company/ui`로 버전을 기록합니다.
2. 1번과 같은 절차를 Node 18로 실행합니다.
3. 2.0.0 패키지의 `package.json`에서 `exports` 항목을 읽고, 앱의 `@company/ui/` import 위치와 대조합니다.

1번에서 새로 설치한 2.0.0 빌드가 실패하면 원인은 `exports`로 확정되며, Node 버전과는 무관합니다.

## 수정 방향

| 방법 | 장점 | 단점 |
|---|---|---|
| import 경로를 2.0.0 `exports`에 맞게 수정 | 앱 코드만 수정하면 됩니다 | import 위치가 많으면 작업량이 늘어납니다 |
| `@company/ui`의 `exports`에 경로 추가 | 앱 코드를 바꾸지 않아도 됩니다 | 패키지를 관리하는 팀의 새 배포가 필요합니다 |
| 2.0.0을 1.4.0으로 되돌리기 | CI를 가장 빨리 복구합니다 | 2.0.0의 변경 사항을 쓰지 못합니다 |

2.0.0의 `exports`가 의도된 공개 경로라면 앱의 import 경로를 수정하는 방법을 먼저 권장합니다. 이 방법은 앱 저장소 안에서 끝납니다.
