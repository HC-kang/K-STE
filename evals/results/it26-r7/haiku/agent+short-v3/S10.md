가장 유력한 원인은 Node 버전이 아니라 **로컬과 CI가 서로 다른 `@company/ui` 버전을 쓰고 있을 가능성**입니다. 로컬 `node_modules`가 3일 전보다 먼저 설치되었으므로 1.4.0을 그대로 쓰고 있을 수 있습니다. 그러면 로컬 빌드 성공은 2.0.0이 정상이라는 근거가 되지 않습니다. 아직 확인하지 않은 추론입니다.

## 확인된 사실

- CI 빌드가 `Cannot find module '@company/ui/button'`으로 실패합니다.
- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드(패키지 바깥에 공개할 모듈 경로를 정하는 설정)가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`(설치 버전을 고정하는 파일)의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

## 원인 가설

| 가설 | 근거 | 가능성 | 확인 방법 |
|---|---|---|---|
| 로컬은 1.4.0을 쓰고 CI는 2.0.0을 써서 로컬 성공이 2.0.0 검증이 아니었습니다. | 로컬 `node_modules`가 3일 전 이전에 설치되었습니다. | 높음 | 로컬에서 `npm ls @company/ui`를 실행합니다. |
| 2.0.0의 `exports`에 `./button` 경로가 없거나 다른 경로로 바뀌었습니다. | 1.4.0에서 가능했던 내부 파일 직접 import가 exports 추가 후 막힐 수 있습니다. | 높음 | `npm view @company/ui@2.0.0 exports`로 2.0.0의 exports를 확인합니다. |
| Node 18이 직접 원인입니다. | Node 18도 `exports`를 지원하므로 직접 원인일 가능성은 낮습니다. | 낮음 | CI만 Node 20으로 바꿔 같은 실패가 나는지 확인합니다. |
| 캐시가 오래된 설치 결과를 복원했습니다. | 캐시 키가 lock 파일 해시라서 lock이 바뀌면 캐시도 새로 만들어집니다. 다만 복원 키(restore-keys, 정확히 맞지 않을 때 쓰는 대체 키)가 있으면 예외가 생깁니다. | 낮음, 확인 필요 | 워크플로 파일에서 restore-keys 설정과 설치 명령(`npm ci` 또는 `npm install`)을 확인합니다. |

에러 문구도 확인이 필요합니다. `Cannot find module`은 보통 패키지를 아예 찾지 못할 때 나오고, exports에 경로가 없을 때 Node는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`를 냅니다. 따라서 패키지가 설치되지 않았거나 번들러가 다른 메시지를 냈을 수 있습니다. CI 로그 전문으로 확인해야 합니다.

## 권장 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다. 1.4.0이면 로컬은 2.0.0으로 빌드를 검증하지 않은 상태입니다.
2. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드합니다. 같은 실패가 재현되는지 봅니다.
3. CI 로그에서 설치된 `@company/ui` 버전과 실패한 import 파일 경로를 확인합니다.
4. 2.0.0 exports에 `./button`이 있는지 확인합니다. 없으면 import 경로를 exports가 허용하는 경로로 바꾸는 방안을 검토합니다.
5. 재현되면 CI를 Node 20 이상으로 올립니다. Node 18은 지원이 끝난 버전이라 어느 쪽이든 올리는 것을 권장합니다.

CI를 급히 살려야 하면 `@company/ui`를 1.4.0으로 고정하는 것이 임시 조치가 됩니다. 이 경우 2.0.0의 변경 사항 적용은 뒤로 미뤄집니다.

현재 원인은 확정되지 않았습니다. 위 내용은 제공하신 정보에 근거한 추론이며, 저장소나 CI 로그는 아직 확인하지 않았습니다.
