가장 유력한 원인은 로컬이 아직 `@company/ui` 1.4.0을 쓰고 CI만 2.0.0을 설치해서, 2.0.0의 `exports` 필드 때문에 `@company/ui/button` 경로를 찾지 못하는 것입니다. 이 결론은 주어진 정보에서 나온 추론이며, 로컬에 설치된 실제 버전과 2.0.0의 `exports` 내용은 아직 보지 않았습니다.

## 추론의 근거

1.4.0에는 `exports` 필드가 없습니다. 그래서 `@company/ui/button`은 `node_modules/@company/ui/button` 파일 경로로 바로 해석됩니다.

2.0.0에는 `exports` 필드가 있습니다. 이 필드가 있으면 `exports`에 적힌 서브패스만 import할 수 있습니다. `./button`이 `exports`에 없거나, 적힌 경로가 가리키는 파일이 패키지에 없으면 import가 실패합니다.

로컬 `node_modules`는 3일 전 업그레이드보다 먼저 설치했습니다. 이후에 `npm install`이나 `npm ci`를 다시 하지 않았다면 로컬은 1.4.0일 가능성이 높습니다. CI는 `package-lock.json`을 기준으로 새로 설치하므로 2.0.0을 받습니다.

## 다른 후보

| 후보 | 가능성 | 이유 |
|---|---|---|
| Node 18과 20의 차이 | 낮음 | 두 버전 모두 `exports`를 지원합니다. |
| CI 캐시 | 낮음 | 캐시 키가 `package-lock.json` 해시여서, 3일 전에 lock이 바뀌면서 캐시도 새로 만들어졌을 것입니다. |
| lock 파일 미커밋 | 확인 필요 | 업그레이드한 `package-lock.json`이 커밋되지 않았다면 CI가 다른 버전을 받을 수 있습니다. |

에러 메시지에도 불확실한 부분이 있습니다. `exports`에 서브패스가 없을 때 Node는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`를 냅니다. 이번 에러는 `Cannot find module`이므로, `exports`가 가리키는 파일이 2.0.0 패키지에 실제로 없는 경우도 함께 의심해야 합니다.

## 원인 확정 절차

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 봅니다.
2. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 `next build`를 합니다. 로컬 빌드가 실패하면 원인이 버전 차이로 확정됩니다.
3. 설치된 `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지, 그 경로의 파일이 존재하는지 봅니다.
4. 2번에서 로컬 빌드가 계속 성공하면 `nvm use 18`로 Node 18에서 다시 빌드합니다.
5. CI 로그의 install 단계에서 `@company/ui`의 설치 버전을 봅니다.

## 수정 방향

원인이 확정되면 아래 중 하나를 선택하는 것을 권장합니다.

- 앱의 import 경로를 2.0.0의 `exports`에 정의된 경로로 바꿉니다.
- `@company/ui` 패키지에 `./button` 서브패스를 추가해 배포합니다.
- 당장 빌드를 복구해야 하면 `@company/ui`를 1.4.0으로 고정합니다. 이 경우 2.0.0 업그레이드는 미뤄집니다.
