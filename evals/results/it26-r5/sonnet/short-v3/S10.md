가장 유력한 원인은 로컬이 `@company/ui` 1.4.0을 계속 쓰고, CI는 2.0.0을 설치하는데 2.0.0의 `exports` 필드에 `./button` 경로가 없는 것입니다. 이 내용은 추론이며, 아래 검증으로 확정해야 합니다.

## 근거

- 2.0.0부터 패키지에 `exports` 필드(패키지가 외부에 공개하는 경로 목록)가 있습니다. `exports`가 있으면 Node는 목록에 없는 하위 경로의 import를 막고 `Cannot find module` 오류를 냅니다. 이 동작은 Node의 규칙입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치했습니다. 그래서 로컬은 1.4.0일 가능성이 높고, 1.4.0에는 `exports` 제한이 없으므로 `@company/ui/button`을 불러올 수 있습니다. 이 부분은 추론입니다.
- 3일 전 업그레이드 커밋에서 `package-lock.json`이 바뀌었다면, 캐시 키도 바뀌었습니다. 그러면 CI는 캐시 없이 2.0.0을 새로 설치합니다.
- Node 18과 Node 20은 둘 다 `exports`를 지원합니다. 그래서 Node 버전 차이가 주원인일 가능성은 낮습니다. 이 부분도 추론입니다.

## 아직 확인하지 않은 것

- 로컬에 설치된 `@company/ui`의 실제 버전
- CI에 설치된 `@company/ui`의 실제 버전
- 2.0.0의 `exports`에 `./button`이 있는지, 있다면 어떤 조건(`import`, `require` 등)으로 연결되는지

## 검증 순서

1. 로컬과 CI 로그에서 `npm ls @company/ui`를 실행해 설치된 버전을 비교합니다.
2. CI에서 설치한 `node_modules/@company/ui/package.json`을 열어 `exports` 필드에 `./button`이 있는지 봅니다.
3. 로컬에서 `node_modules`를 지우고 `npm ci`를 실행한 뒤 빌드합니다. 이때 실패하면 원인은 버전 차이입니다.
4. 3번에서 실패하지 않으면 로컬에서 Node 18로 같은 빌드를 실행해 Node 버전 영향을 따로 봅니다.

## 해결 방향

3번에서 실패하고 `exports`에 `./button`이 없다면 선택지는 세 가지입니다.

- 코드의 import 경로를 2.0.0이 공개하는 경로로 바꿉니다.
- `@company/ui` 담당 팀에 `./button`을 `exports`에 추가해 달라고 요청합니다.
- 위 두 가지가 끝날 때까지 `@company/ui`를 1.4.0으로 고정합니다.

확인 필요: 2.0.0의 릴리스 노트나 마이그레이션 문서에 `./button`의 새 경로가 있는지 봐야 합니다. 제가 가진 정보에는 그 내용이 없습니다.
