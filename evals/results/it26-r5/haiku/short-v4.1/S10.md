가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다. `exports`가 있으면 패키지 바깥에서 import할 수 있는 경로가 목록에 있는 것으로 제한되므로, 2.0.0이 `./button` 경로를 노출하지 않았다면 `@company/ui/button` import가 실패합니다. 다만 이 내용은 추론이며, 2.0.0 패키지의 실제 `exports` 항목은 아직 확인하지 않았습니다.

## 로컬과 CI가 다르게 동작하는 이유

로컬 `node_modules`는 3일 전보다 먼저 설치되었으므로, 1.4.0이 그대로 남아 있을 가능성이 큽니다(추론). 1.4.0에는 `exports`가 없으므로 `button` 경로가 파일 구조대로 해석되고, 그래서 로컬 빌드가 성공합니다.

CI는 `package-lock.json` 해시를 캐시 키로 씁니다. lock 파일이 2.0.0으로 갱신되어 해시가 바뀌었다면 CI는 캐시를 쓰지 못하고 새로 설치하므로 2.0.0이 설치됩니다. CI가 실패한다는 사실은 CI가 2.0.0을 설치했다는 점과 맞습니다.

Node 버전 차이는 원인일 가능성이 낮습니다. Node 18도 `exports`를 지원하기 때문입니다. 다만 npm 버전이나 lock 파일 해석이 달라질 수 있으므로 배제하지는 않습니다. 또한 Node 18은 2025년 4월에 지원이 종료되어, CI 환경을 Node 20 이상으로 올리는 것도 함께 검토할 수 있습니다.

## 가설 비교

| 가설 | 근거 | 확인 방법 |
|---|---|---|
| 2.0.0 `exports`에 `./button` 경로가 없다 | 2.0.0에 `exports`가 추가되었다 | 2.0.0의 `package.json`에서 `exports` 항목을 본다 |
| CI는 2.0.0, 로컬은 1.4.0을 쓴다 | 로컬 `node_modules`는 이전에 설치되었고 CI만 실패한다 | CI 로그에서 설치된 버전을 보고, 로컬에서 `npm ls @company/ui`를 실행한다 |
| Node 버전 차이가 영향을 준다 | CI는 Node 18, 로컬은 Node 20을 쓴다 | 로컬에서 Node 18로 빌드하여 재현한다 |

## 확인할 항목

1. CI 로그에서 설치된 `@company/ui`의 버전을 확인합니다.
2. 2.0.0 패키지의 `package.json`에서 `exports`가 `./button`을 포함하는지 확인합니다.
3. 로컬에서 Node 18로 바꾸고 `npm ci` 후 빌드하여 실패가 재현되는지 확인합니다.
4. `package-lock.json`이 2.0.0으로 갱신되어 커밋되었는지 확인합니다.

확인 결과 1번과 2번이 원인과 일치하면 해결 방향은 두 가지입니다. 1.4.0을 유지하는 방법과, 2.0.0을 쓰면서 import 경로를 패키지가 노출한 경로로 바꾸는 방법입니다. 후자를 택하면 `@company/ui` 측에 `./button` 경로 추가를 요청할 수도 있습니다.

PM께는 현재 CI 빌드가 중단된 상태이며, 배포에 미치는 영향은 확인 필요라고 전달하면 됩니다.
