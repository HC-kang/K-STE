CI에서만 실패하는 가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드(패키지 바깥에서 가져올 수 있는 경로를 정하는 설정)가 `@company/ui/button` 같은 하위 경로를 허용하지 않는 것입니다. 이 결론은 주어진 정보로 세운 추론이며, 실제 패키지 파일과 CI 로그는 아직 확인하지 않았습니다.

## 확인된 사실

| 구분 | 로컬 | CI |
|---|---|---|
| Node 버전 | Node 20 | Node 18 |
| `node_modules` 설치 시점 | 3일 전 이전 | 캐시가 없으면 lock 파일 기준으로 새로 설치 |
| `@company/ui` 버전 | 1.4.0일 가능성이 높음 (추론) | 2.0.0일 가능성이 높음 (추론) |
| 빌드 결과 | 성공 | 실패 |

3일 전 `@company/ui`가 1.4.0에서 2.0.0으로 올라갔고, 2.0.0부터 `exports` 필드가 있습니다. 에러는 `Cannot find module '@company/ui/button'`입니다.

## 원인 분석

Node는 `exports` 필드가 있는 패키지에서 그 필드에 적힌 경로만 외부 import로 허용합니다. 1.4.0에는 이 필드가 없었으므로 `@company/ui/button`이 실제 파일로 바로 연결됐습니다. 2.0.0의 `exports`에 `./button` 항목이 없거나 파일 위치가 바뀌었다면, 같은 import 문이 실패합니다.

로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 3일 전 이전 설치본이라 1.4.0 기준으로 남아 있기 때문으로 보입니다. 따라서 로컬 성공은 2.0.0이 정상이라는 근거가 되지 못합니다. 로컬은 이 변경을 검증하지 않은 상태입니다.

CI는 lock 파일이 바뀌면서 캐시 키(캐시를 찾을 때 쓰는 식별값)도 달라졌으므로, 캐시를 쓰지 못하고 2.0.0을 새로 설치했을 가능성이 높습니다. 이 점은 실패가 시작된 시점과 맞습니다.

Node 18과 20의 차이는 현재 가장 약한 가설입니다. `exports` 해석은 두 버전 모두 지원하므로 Node 버전이 주원인일 가능성은 낮습니다. 다만 Node 18로 로컬에서 재현해 보기 전까지는 배제할 수 없습니다.

에러 문구가 Node 런타임의 `Cannot find module` 형식입니다. Next.js 번들러 오류는 보통 `Module not found`로 표시되므로, 실패 지점이 Next.js 번들링인지 Node가 직접 실행하는 스크립트(예: `next.config.js`, 테스트)인지 확인 필요: CI 로그에서 실패한 단계 이름과 에러가 난 파일 경로를 알려 주세요.

## 확인 방법

1. CI 로그에서 에러가 발생한 단계 이름과 파일 경로를 찾아 기록합니다.
2. 2.0.0 패키지의 `package.json`을 열어 `exports` 항목에 `./button`이 있는지 봅니다.
3. 로컬 프로젝트에서 `npm ls @company/ui`를 실행해 실제 설치 버전을 봅니다.
4. Node 18로 로컬 빌드를 실행해 CI와 같은 실패가 재현되는지 봅니다.
5. 재현이 확인되면 `@company/ui` 메인테이너에게 `exports`에 해당 경로를 추가해 달라고 요청하거나, 사용처의 import를 패키지가 공개한 경로로 바꿉니다.
