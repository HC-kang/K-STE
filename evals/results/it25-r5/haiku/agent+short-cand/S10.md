CI 실패의 가장 유력한 원인은 2.0.0의 `exports` 필드 때문에 `@company/ui/button` 같은 경로 import가 막힌 것이다. 다만 이 결론은 추론이며, 아래 확인 필요 항목으로 검증해야 한다. 아직 어떤 검사도 실행하지 않았다.

### 확인된 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에는 `exports` 필드(패키지가 외부에 공개할 파일 경로를 정한 설정)가 새로 추가되었다.
- CI는 Node 18을, 로컬은 Node 20을 사용한다.
- CI 캐시 키는 `package-lock.json`(설치할 패키지 버전을 고정해 적어 둔 파일)의 해시다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었다.
- CI에서 나는 에러는 `Cannot find module '@company/ui/button'`이다.

### 원인 분석 (추론)

`exports` 필드가 있으면 패키지는 그 목록에 적힌 경로만 외부에 공개한다. 목록에 없는 `@company/ui/button`은 패키지 내부 파일을 경로로 직접 가져오는 딥 임포트(deep import)로 취급되어 해석되지 않는다.

로컬과 CI가 다르게 동작하는 이유는 다음과 같이 추론한다.

- 로컬 `node_modules`는 3일 전 이전에 설치되었으므로 1.4.0이 남아 있을 가능성이 높다. 1.4.0에는 `exports`가 없으므로 `button` 경로가 파일 경로로 그대로 찾아진다.
- CI는 lock 파일이 바뀌었다면 캐시 키가 달라져 캐시를 쓰지 못하고(캐시 미스) 새로 설치한다. 이때 2.0.0이 설치되어 `exports` 제한이 적용된다.

따라서 로컬 빌드가 성공한 것은 2.0.0이 문제없다는 뜻이 아니다. 로컬은 2.0.0을 사용하지 않았을 가능성이 높다.

| 항목 | 로컬 | CI |
| --- | --- | --- |
| `@company/ui` 버전 | 1.4.0으로 추정 (확인 필요) | 2.0.0으로 추정 (확인 필요) |
| Node 버전 | 20 | 18 |
| 설치 방식 | 3일 전 이전에 설치된 `node_modules` | lock 기준 새 설치 (캐시 미스로 추정) |
| `exports` 적용 | 없음 | 있음 |

Node 18과 20은 모두 `exports`를 지원하므로 Node 버전 차이만으로 이 에러가 났을 가능성은 낮다고 본다.

### 확인 필요

- CI 로그 전체 에러 메시지와 이 에러를 낸 도구(Node, webpack, TypeScript 중 어느 쪽인지). Node가 `exports` 제한으로 내는 에러 문구는 `Cannot find module`과 다르므로, 어느 도구의 메시지인지 확인해야 원인을 확정할 수 있다.
- 로컬 `node_modules/@company/ui/package.json`의 `version` 값.
- 현재 `package-lock.json`에 기록된 `@company/ui` 버전.
- 2.0.0 `package.json`의 `exports`에 `./button` 또는 `./*` 항목이 있는지.
- CI 로그에서 캐시가 실제로 미스 났는지.

### 검증 방법

1. 로컬에서 `node_modules`를 지우고 `npm ci`를 실행한 뒤, 설치된 `@company/ui` 버전을 확인한다.
2. Node 18 환경에서 같은 빌드를 실행하여 에러 재현 여부를 본다.
3. 2번에서 같은 에러가 재현되면 원인이 2.0.0의 `exports`임이 확정된다.

### 조치 방안

- 단기: `@company/ui`를 1.4.0으로 되돌리는 롤백(이전 버전으로 되돌리는 것)으로 CI를 먼저 복구할 수 있다.
- 근본: 2.0.0이 공개한 경로로 import를 바꾼다. 해당 경로가 없다면 `@company/ui` 담당자에게 `exports` 항목 추가를 요청하는 것을 권장한다.
- 재현 전에는 Node 버전 차이를 원인으로 단정하지 않는다.
