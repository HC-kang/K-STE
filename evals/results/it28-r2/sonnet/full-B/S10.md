CI 빌드 실패의 가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드로 보이며, 로컬 빌드는 2.0.0이 아닌 1.4.0 기준으로 성공했을 것으로 보입니다.

`exports` 필드는 패키지가 외부에 공개할 import 경로를 정하는 package.json 항목입니다. 이 필드가 있으면 목록에 없는 경로는 import할 수 없습니다. 2.0.0의 `exports`에 `./button`이 없다면 `Cannot find module '@company/ui/button'` 에러가 납니다. 이 부분은 추론이고, 2.0.0의 `exports` 내용은 주어진 사실에 없습니다.

로컬은 `node_modules`(설치된 패키지가 저장되는 폴더)를 3일 전보다 먼저 설치했으므로 1.4.0이 남아 있는 것으로 보입니다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`을 import할 수 있었을 것입니다.

CI(코드를 올릴 때 자동으로 빌드하는 서버)의 캐시 키는 `package-lock.json`(설치할 버전을 고정해 기록한 파일)의 해시입니다. 버전 상향이 `package-lock.json`을 바꿨다면 캐시 키도 바뀌어 CI가 2.0.0을 새로 설치합니다. 로컬과 CI가 서로 다른 버전으로 빌드했다는 뜻입니다.

Node 18과 20은 둘 다 `exports` 필드를 지원하므로 Node 버전 차이는 주원인으로 보이지 않습니다.

아래 순서로 추론이 맞는지 가리십시오.

1. 로컬 `node_modules/@company/ui/package.json`의 `version` 값을 읽으십시오. 1.4.0이면 로컬 성공은 2.0.0의 검증이 아닙니다.
2. 2.0.0 패키지의 `package.json`에서 `exports`에 `./button`이 있는지 읽으십시오.
3. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드하십시오. CI와 같은 에러가 나면 원인이 이 경로 문제로 좁혀집니다.
4. `./button`이 `exports`에 없으면 import 경로를 `exports`에 있는 경로로 바꾸십시오.
