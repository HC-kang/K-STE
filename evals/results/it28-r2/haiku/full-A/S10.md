가장 유력한 원인은 2.0.0에 새로 추가된 `exports` 필드가 `button` 하위 경로의 import를 허용하지 않는 것입니다. 아직 이 내용을 직접 확인하지는 않았습니다. 로컬 빌드가 성공하는 이유는 3일 전에 설치된 `node_modules`가 1.4.0을 그대로 쓰고 있기 때문으로 보입니다. 그래서 로컬 성공은 2.0.0이 정상 동작한다는 근거가 되지 않습니다.

### 제공된 사실과 해석

| 항목 | 사실 | 해석 |
|---|---|---|
| 에러 | `Cannot find module '@company/ui/button'` | Node의 require 해석 실패에서 흔히 보이는 형식입니다. 어느 빌드 단계에서 났는지는 전체 로그로 확인해야 합니다. |
| 패키지 2.0.0 | `exports` 필드가 추가됨 | `exports`가 있으면 패키지가 허용한 경로만 import할 수 있습니다. `./button`이 허용 목록에 없으면 이 에러가 납니다. |
| 로컬 node_modules | 3일 전보다 먼저 설치됨 | 1.4.0일 가능성이 높습니다. 1.4.0에는 `exports`가 없어서 하위 경로가 모두 열려 있었습니다. |
| CI | 실패함, 캐시 키는 `package-lock.json` 해시 | 락 파일이 바뀌었다면 캐시가 새로 만들어지므로 CI는 2.0.0을 설치했을 가능성이 높습니다. CI가 실패한다는 사실은 이 해석과 맞습니다. |
| Node 버전 | CI는 18, 로컬은 20 | Node 18과 20은 모두 `exports`를 지원합니다. 그래서 버전 차이 자체가 원인이라고 보기는 어렵습니다. 다만 2.0.0이 조건부 `exports`를 쓰고 있다면 버전별로 다르게 해석될 여지는 남아 있습니다. |

### 확인 방법

1. 로컬에서 `node_modules`를 지운 뒤 `npm ci`로 다시 설치하고 빌드하십시오. 여기서 실패하면 Node 버전과 상관없이 2.0.0 패키지 문제가 거의 확실합니다.
2. 1번에서 실패했다면 설치된 `@company/ui`의 `package.json`을 열어 `exports`에 `./button` 또는 `./*`가 있는지 살펴보십시오.
3. 1번에서 성공했다면 `nvm`으로 Node 18을 선택해 같은 빌드를 실행하십시오. 여기서 실패하면 Node 버전 차이를 파고들어야 합니다.
4. CI에 `npm ls @company/ui` 단계를 추가해 실제로 설치된 버전을 기록하십시오.

### 참고

2.0.0 업그레이드는 의도한 변경이므로 수정 방향은 팀과 정해야 합니다. 2.0.0의 `exports`에 해당 경로가 빠져 있다면 패키지 쪽에 추가를 요청하거나, 앱의 import 경로를 공개된 경로로 바꾸는 방법이 있습니다. 긴급하면 1.4.0으로 되돌리는 방법도 있습니다.

이 분석은 제공된 정보만 근거로 합니다. 2.0.0의 `exports` 내용, CI 로그, 락 파일 변경 여부는 확인하지 않았습니다. 먼저 1번 실험을 실행하십시오.
