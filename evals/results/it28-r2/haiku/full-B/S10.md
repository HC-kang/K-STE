가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다. 이 필드 때문에 `@company/ui/button` 같은 하위 경로 import가 막혔을 가능성이 높습니다. 로컬 빌드가 성공하는 것은 로컬 `node_modules`가 3일 전 설치본이라 1.4.0을 계속 쓰고 있기 때문으로 보입니다.

## 원인 가설

| 가설 | 근거 | 판단 |
|---|---|---|
| 2.0.0의 `exports` 맵에 해당 하위 경로가 없다 | 2.0.0에서 `exports`가 추가되었고, 1.4.0에는 이 제약이 없다 | 가장 유력하다. 맵 내용으로 확인해야 한다 |
| 로컬이 2.0.0을 쓰지 않는다 | 로컬 `node_modules`가 3일 전 설치본이다 | 로컬 성공을 설명한다. 설치된 버전을 확인해야 한다 |
| Node 18과 20의 차이 | 두 버전 모두 `exports`를 지원한다 | 가능성이 낮다. 로컬 Node 18 재현으로 확인한다 |
| CI 캐시가 오래된 모듈을 쓴다 | 캐시 키가 `package-lock.json` 해시라서 lock이 바뀌면 캐시가 맞지 않는다 | 가능성이 낮다. CI 로그의 캐시 적중 여부로 확인한다 |

에러 메시지가 `Cannot find module`이라는 점도 확인이 필요합니다. `exports`에 막힌 경우 Node는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`를 냅니다. 이 메시지는 빌드 도구의 resolver가 다시 쓴 것일 수 있으므로, CI 로그 원문에서 어느 단계가 던진 오류인지 확인하십시오.

## 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행하여 설치된 버전을 확인하십시오. 1.4.0이면 로컬 빌드는 2.0.0 조건을 검증하지 못한 것입니다.
2. `node_modules/@company/ui/package.json`의 `exports` 맵에 `./button` 또는 그에 대응하는 항목이 있는지 확인하십시오.
3. 로컬에서 `npm ci`로 lock 파일 기준 재설치 후 빌드하여 실패가 재현되는지 확인하십시오.
4. Node 18로 같은 빌드를 실행하여 Node 버전의 영향이 없는지 확인하십시오.

2번과 3번의 결과가 수정 방향을 정합니다. 맵에 해당 경로가 없고 재현되면 원인이 `exports`로 확정됩니다.

## 수정 방향

- import 경로를 2.0.0 `exports` 맵이 허용하는 경로로 바꿉니다. 맵에 없는 경로라면 이 방법은 쓸 수 없습니다.
- 맵에 필요한 경로가 빠져 있다면 `@company/ui` 관리 팀에 해당 경로의 export 추가를 요청합니다.
- 당장 빌드를 복구해야 하면 `@company/ui`를 1.4.0으로 고정할 수 있습니다. 다만 이것은 2.0.0 전환을 미루는 임시 조치입니다.

PM에게는 업그레이드 검증이 캐시된 1.4.0 환경에서 이루어져서 문제가 CI에서 처음 드러났다고 전달하십시오. 가장 먼저 1번과 2번을 확인하십시오.
