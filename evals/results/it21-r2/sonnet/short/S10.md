가장 가능성이 높은 원인은 로컬이 `@company/ui` 2.0.0이 아니라 1.4.0으로 빌드하고, CI만 2.0.0으로 빌드하는 것입니다. 아래 내용은 주어진 사실에서 추론한 것이며, 설치된 버전과 2.0.0의 `exports` 내용은 아직 직접 조회하지 않았습니다.

## 사실

- CI에서만 `Cannot find module '@company/ui/button'` 에러가 나고, 로컬 빌드는 성공합니다.
- `@company/ui`를 3일 전에 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0 패키지에는 `exports` 필드가 추가됐습니다.
- CI의 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치한 것입니다.

## 추론

1. 로컬 `node_modules`는 업그레이드 전에 설치했으므로, 로컬에는 1.4.0이 남아 있을 가능성이 높습니다.
2. 1.4.0에는 `exports` 필드가 없으므로, `@company/ui/button`은 파일 경로(`node_modules/@company/ui/button`)로 그대로 찾아집니다.
3. 업그레이드 때 `package-lock.json`이 바뀌었으므로, CI의 캐시 키도 바뀌어 새로 설치가 일어났을 것입니다. 그래서 CI는 2.0.0을 설치합니다.
4. 패키지에 `exports` 필드가 있으면 `exports`에 적힌 경로만 import할 수 있습니다. 2.0.0의 `exports`에 `./button`이 없거나 다른 경로로 매핑돼 있으면, `@company/ui/button`을 찾지 못합니다.

즉 로컬 빌드의 성공은 2.0.0에 대한 검증이 아닙니다.

## Node 버전의 영향

Node 18과 Node 20은 둘 다 `exports` 필드를 지원합니다. 그래서 Node 버전 차이는 주원인이 아니라고 봅니다. 다만 이것도 직접 검증하지 않았습니다.

## 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 봅니다. 1.4.0이면 위 추론이 맞습니다.
2. 로컬에서 `node_modules`와 `.next` 캐시를 지우고 `npm ci`로 다시 설치한 뒤 빌드합니다. 같은 에러가 나면 CI와 같은 상태를 재현한 것입니다.
3. 2.0.0의 `node_modules/@company/ui/package.json`에서 `exports` 필드를 열어 `./button`이 있는지 봅니다.

## 해결 선택지

- 2.0.0의 `exports`에 있는 경로로 import 문을 바꿉니다. 이 방법을 권장합니다.
- `@company/ui` 담당자에게 `./button`을 `exports`에 추가해 달라고 요청합니다. 2.0.0에서 의도적으로 뺀 것인지는 확인 필요입니다.
- 위 두 가지가 당장 어려우면 `@company/ui`를 1.4.0으로 되돌립니다.

**주의:** 로컬에서 `npm ci`로 다시 설치하기 전에는 로컬 빌드 성공을 근거로 배포 가능 여부를 판단하면 안 됩니다.
