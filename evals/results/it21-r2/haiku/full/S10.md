가장 유력한 원인은 로컬과 CI가 서로 다른 `@company/ui` 버전을 쓰고 있다는 점입니다. 로컬 `node_modules`는 3일 전 설치본이라 1.4.0이 남아 있을 가능성이 높고, CI는 `package-lock.json` 기준으로 2.0.0을 새로 받았을 것으로 보입니다. 이 버전 차이를 먼저 확인하십시오.

## 확인된 사실

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에 `exports` 필드가 추가되었습니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.
- CI 빌드에서 `Error: Cannot find module '@company/ui/button'`이 발생합니다.

## 로컬과 CI의 차이

| 항목 | 로컬 | CI |
|---|---|---|
| 설치 시점 | 3일 전보다 이전 | 빌드 시점에 lock 기준으로 설치 (추정) |
| `@company/ui` 버전 | 1.4.0일 가능성이 높음 (확인 필요) | 2.0.0 (추정) |
| Node 버전 | 20 | 18 |
| `@company/ui/button` import | 1.4.0에서는 `exports`가 없어 통과 | 2.0.0의 `exports` 맵에 따라 판단 |

`exports` 필드가 없는 패키지는 하위 경로 import를 파일 경로 그대로 허용합니다. `exports` 필드가 생기면 맵에 적힌 경로만 허용되므로, 2.0.0 맵에 `./button`이 없으면 이 에러가 납니다. 따라서 로컬 빌드 성공은 2.0.0 변경에 문제가 없다는 뜻이 아니라, 로컬이 2.0.0을 아직 검증하지 않았다는 뜻일 수 있습니다.

## 원인 후보

1. 가장 유력한 원인은 로컬이 1.4.0을 쓰고 있어서 2.0.0 변경이 로컬에서 검증되지 않은 것입니다.
2. 2.0.0의 `exports` 맵에 `./button` 경로가 없거나 다른 경로로 바뀌었을 수 있습니다. 확인 필요: 2.0.0 패키지의 `exports` 맵 내용.
3. Node 18과 20의 차이가 원인일 가능성은 낮습니다. `exports` 필드는 Node 18에서도 지원됩니다. 다만 Node 버전에 따라 번들러 해석이 달라질 수 있으므로 확인 필요: 재현 시 Node 버전별 결과.
4. 캐시 문제는 가능성이 낮습니다. 캐시 키가 lock 해시이므로 lock이 바뀌면 캐시가 새로 만들어집니다. 확인 필요: 업그레이드 커밋에 `package-lock.json` 변경이 포함되었는지.

## 확인 명령

로컬에서 설치된 버전과 `exports` 맵을 확인합니다.

```
npm ls @company/ui
grep -n '"version"\|"exports"' node_modules/@company/ui/package.json
```

CI 로그에서 설치된 버전을 확인합니다. 빌드 단계 앞에 `npm ls @company/ui`를 추가하면 됩니다.

로컬에서 lock 기준으로 다시 설치한 뒤 빌드하면 CI와 같은 조건을 재현할 수 있습니다.

```
rm -rf node_modules
npm ci
npm run build
```

## 조치 방향

- 임시 조치로 `@company/ui/button` import를 2.0.0 `exports` 맵에 있는 경로로 바꿉니다.
- 패키지 쪽에 `button` 하위 경로를 `exports`에 추가해 달라고 요청합니다.
- 장기적으로는 로컬 설치를 주기적으로 lock 기준으로 맞추고, CI와 같은 Node 버전을 씁니다.

PM에게는 현재 CI 빌드가 실패하고 있고, 원인은 버전 차이에 따른 하위 경로 import 문제로 보인다고 공유하면 됩니다. 원인 확정은 위 확인 명령의 결과가 나온 뒤에 가능합니다.

먼저 로컬에서 `rm -rf node_modules && npm ci && npm run build`를 실행해 실패가 재현되는지 확인하십시오.
