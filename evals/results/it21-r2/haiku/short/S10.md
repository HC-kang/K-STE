로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 2.0.0 이전 버전을 그대로 쓰고 있기 때문일 가능성이 높습니다. 그러면 로컬 성공은 2.0.0 변경을 검증한 근거가 되지 못합니다. 이는 추론이며, 로컬에 실제로 설치된 버전은 아직 확인하지 않았습니다.

### 상황 정리

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 패키지 진입점 목록(`exports` 필드)이 새로 추가되었습니다.
- CI에서만 `Cannot find module '@company/ui/button'` 오류가 발생합니다.

### 추론되는 원인

`exports` 필드가 있으면 Node와 번들러는 그 목록에 적힌 경로만 가져올 수 있습니다. 2.0.0의 `exports` 목록에 `./button` 경로가 없거나 다른 이름으로 노출되어 있다면, 앱의 `@company/ui/button` import는 해석되지 않습니다. 1.4.0에는 이 제약이 없었으므로 기존 import가 통과했습니다. 다만 2.0.0의 `exports` 내용은 아직 열어 보지 않았기 때문에 이 원인은 미확인 상태입니다.

Node 버전 차이(CI 18, 로컬 20)는 이 오류를 설명할 가능성이 낮습니다. `exports` 필드는 Node 18에서도 지원되기 때문입니다. 다만 번들러가 Node 버전에 따라 다르게 동작할 가능성은 배제하지 않았으므로, 확인 항목에 포함합니다.

### 환경 비교

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `@company/ui` 설치 버전 | 3일 전 이전에 설치되어 1.4.0일 가능성이 높음(추론) | `package-lock.json` 기준 2.0.0일 가능성이 높음(추론) |
| 설치 방식 | 기존 `node_modules` 재사용(추정) | 캐시 식별자(캐시 키)가 lock 파일 해시라서 lock 파일이 바뀌면 새로 설치 |

lock 파일 해시가 캐시 키이므로 2.0.0 업데이트 후 CI는 새 캐시를 만들고 2.0.0을 설치했을 가능성이 높습니다. 따라서 CI에서만 실패하는 현상과 맞아떨어집니다.

### 확인 필요 항목

- 확인 필요: 로컬에서 `npm ls @company/ui`를 실행해 실제 설치 버전을 확인합니다.
- 확인 필요: 2.0.0 패키지의 `package.json`에서 `exports` 필드에 `./button`이 있는지 봅니다.
- 확인 필요: CI 로그에 설치된 `@company/ui` 버전이 2.0.0으로 나오는지 봅니다.
- 확인 필요: 3일 전부터 CI가 실패했는지, 그 이전에도 실패 기록이 있는지 봅니다.
- 확인 필요: Node 18 환경에서 같은 빌드를 재현할 수 있는지 봅니다.

### 대응 방향

1. 로컬 `node_modules`를 삭제한 뒤 `npm ci`로 lock 파일 기준으로 다시 설치하고 빌드합니다. 이 결과가 CI 실패를 재현하면 원인이 설치 버전이라는 근거가 됩니다.
2. Node 18로 같은 빌드를 실행해 Node 버전의 영향을 확인합니다.
3. 근본 해결은 2.0.0의 `exports`에 `./button`을 추가하거나, 앱의 import를 `exports`에 노출된 경로로 바꾸는 방식입니다. 패키지 쪽 수정이 필요하면 `@company/ui` 담당자와 협의해야 합니다.
4. 임시로 `@company/ui`를 1.4.0으로 되돌리면 CI는 바로 통과하지만, 2.0.0 변경은 그대로 남습니다.
