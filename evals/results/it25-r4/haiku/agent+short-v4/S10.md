CI 빌드 실패의 가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다. 다만 이 분석은 말씀해 주신 사실만 근거로 했습니다. 실제 코드, `package.json`, CI 로그는 아직 확인하지 않았습니다.

## 확인된 사실

- CI는 Node 18을 쓰고, 로컬은 Node 20을 씁니다.
- `@company/ui`는 3일 전에 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0에는 `exports` 필드가 추가됐습니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치됐습니다.
- CI 에러는 `Error: Cannot find module '@company/ui/button'`입니다.

## 추론: 가장 유력한 원인

로컬 `node_modules`는 3일 전보다 먼저 설치됐으므로 1.4.0이 그대로 남아 있을 가능성이 큽니다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`은 패키지 안의 파일 경로로 해석됩니다. 그래서 로컬 빌드는 성공합니다.

CI는 `package-lock.json`을 기준으로 새로 설치하므로 2.0.0을 받습니다. 2.0.0의 `exports` 필드에 `./button` 경로가 없으면 Node는 이 import를 해석하지 못합니다. 그래서 CI 빌드가 실패합니다.

## 아직 확인되지 않은 점

- 에러 메시지가 `exports` 위반 때 Node가 내는 메시지와 다릅니다. 그 경우 Node는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`를 냅니다. 따라서 CI에서 `@company/ui`가 아예 설치되지 않았을 가능성도 남아 있습니다.
- 로컬 `node_modules`의 실제 버전은 확인하지 않았습니다.
- 확인 필요: Node 18과 20에서 `@company/ui/button`의 해석 결과가 같은지. 두 버전에서 같은 명령으로 `require.resolve('@company/ui/button')`을 실행하면 판단할 수 있습니다. 두 Node 버전 모두 `exports`를 지원하므로, Node 버전 차이만으로 이 실패를 설명하기는 어렵습니다.
- 캐시 키가 lockfile 해시이므로 lockfile이 바뀐 커밋에서는 캐시가 새로 만들어집니다. 그래서 오래된 캐시가 원인일 가능성은 낮습니다. 다만 CI가 실제로 어떤 버전을 설치했는지는 로그로 확인해야 합니다.

## 다음 단계

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인하십시오.
2. `package-lock.json`에서 `@company/ui`가 2.0.0으로 고정됐는지 확인하십시오.
3. 2.0.0 패키지의 `package.json`에서 `exports` 필드에 `./button` 경로가 있는지 확인하십시오.
4. CI 로그에서 설치 단계의 `@company/ui` 버전과 캐시 복원 여부를 확인하십시오.
5. 2.0.0에 `./button`이 없으면 앱의 import 경로를 `exports`에 있는 경로로 바꾸는 방법을 권장합니다. 패키지 쪽에 `./button`을 추가하는 방법도 있지만, 패키지 담당자와 먼저 논의하십시오.
