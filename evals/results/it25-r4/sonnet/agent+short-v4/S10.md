빌드가 CI에서만 실패하는 가장 유력한 원인은 로컬과 CI가 서로 다른 버전의 `@company/ui`를 쓰는 것으로 보입니다.

로컬 `node_modules`는 3일 전보다 먼저 설치했으므로 1.4.0이 들어 있을 가능성이 큽니다. 1.4.0에는 `exports` 필드(패키지가 외부에 공개할 파일 경로를 제한하는 설정)가 없어서, Node가 `@company/ui/button`을 파일 경로로 바로 찾습니다. CI는 2.0.0을 설치하고, 2.0.0에는 `exports` 필드가 있습니다. 그래서 `exports`에 `./button`이 없으면 `Cannot find module '@company/ui/button'`이 납니다. 이 설명은 추론입니다.

다른 후보는 가능성이 낮아 보입니다.

| 후보 | 판단 | 근거 |
|---|---|---|
| Node 18과 Node 20의 차이 | 가능성이 낮아 보입니다. | 두 버전 모두 `exports` 필드를 지원합니다. |
| CI 캐시(이전 설치 결과를 저장해 재사용하는 기능)가 오래됨 | 가능성이 낮아 보입니다. | 캐시 키가 `package-lock.json`의 해시이므로, 업그레이드 때 이 파일이 바뀌었다면 캐시도 새로 만들어졌을 것입니다. |

원인은 다음 순서로 검증하십시오.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 봅니다.
2. `node_modules/@company/ui/package.json`의 `exports`에 `./button` 항목이 있는지 봅니다.
3. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드합니다. 이때 CI와 같은 에러가 나면 원인이 맞습니다.
4. 3번에서 에러가 나지 않으면 로컬에서 Node 18로 빌드해 Node 버전 차이를 봅니다.

3번에서 에러가 재현되면 수정 방향은 둘 중 하나입니다. 하나는 import 경로를 2.0.0의 `exports`가 공개하는 경로로 바꾸는 것입니다. 다른 하나는 `@company/ui` 담당자에게 `./button`을 `exports`에 추가해 달라고 요청하는 것입니다.
