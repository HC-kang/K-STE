가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드가 `@company/ui/button` 경로를 공개하지 않는 것입니다. 로컬은 2.0.0 이전에 설치한 `node_modules`를 쓰기 때문에 이 문제가 드러나지 않았을 가능성이 높습니다.

## 배경 용어

- `exports` 필드는 패키지가 외부에 공개할 파일 경로를 제한하는 설정입니다. 이 필드가 있으면 목록에 없는 경로는 파일이 실제로 존재해도 import할 수 없습니다.
- `node_modules`는 설치된 패키지가 저장되는 폴더입니다.

## 근거

- 사실: 1.4.0에는 `exports` 필드가 없었고, 2.0.0에는 있습니다. 1.4.0에서는 `@company/ui/button`이 패키지 안의 파일 경로로 바로 연결됩니다.
- 사실: 로컬 `node_modules`는 업그레이드 3일 전보다 먼저 설치했습니다. 따라서 로컬에는 `@company/ui` 1.4.0이 남아 있을 가능성이 높습니다.
- 사실: CI 캐시 키는 `package-lock.json`의 해시입니다. 업그레이드로 lock 파일이 바뀌었으므로 CI는 캐시를 새로 만들고 2.0.0을 설치했을 것으로 보입니다.
- 추론: CI는 2.0.0을 설치하고, 2.0.0의 `exports`에는 `./button`이 없거나 다른 경로로 정의돼 있어서 에러가 납니다.

| 항목 | 로컬 | CI |
|---|---|---|
| `@company/ui` 버전 | 1.4.0으로 추정 | 2.0.0으로 추정 |
| `exports` 필드 | 없음으로 추정 | 있음 |
| Node 버전 | 20 | 18 |

## 가능성이 낮은 원인

Node 버전 차이는 주된 원인일 가능성이 낮습니다. `exports` 필드는 Node 18과 Node 20 모두 지원하므로, 두 버전에서 이 필드의 기본 동작은 같습니다. 다만 2.0.0이 조건부 export(`import`, `require` 같은 조건별 경로)를 쓰는지는 확인하지 못했습니다.

## 확인 필요

- 로컬 `node_modules/@company/ui/package.json`의 `version`이 1.4.0인지 확인해야 합니다.
- 2.0.0의 `exports`에 `./button`이 있는지 확인해야 합니다.
- CI 실패가 업그레이드 커밋부터 시작했는지 확인해야 합니다.

## 재현 방법

1. 로컬에서 `rm -rf node_modules`를 실행합니다.
2. `npm ci`로 lock 파일 기준으로 다시 설치합니다.
3. `npm run build`를 실행합니다.
4. 같은 에러가 나면 원인은 확정입니다. 나지 않으면 Node 18로 바꿔 3단계를 반복합니다.

## 해결 방향

- 앱 쪽에서 import 경로를 2.0.0의 `exports`에 정의된 경로로 바꿀 수 있습니다.
- `@company/ui` 쪽에서 `./button`을 `exports`에 추가하고 패치 버전을 배포할 수 있습니다.
- 어느 쪽을 택할지는 2.0.0이 `button` 경로를 의도적으로 제거했는지에 따라 달라집니다. 이 부분은 `@company/ui` 담당자에게 확인해야 합니다.
