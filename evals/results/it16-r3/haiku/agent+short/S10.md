원인은 `@company/ui` 2.0.0에서 추가된 `exports` 필드로 보입니다. 로컬은 3일 전 설치본(1.4.0으로 보임)을 쓰므로 성공하고, CI는 캐시가 빗나가 2.0.0을 새로 설치하므로 실패하는 것으로 보입니다. 아래 항목은 아직 확인하지 않은 추론입니다.

### 확인된 사실과 추론

- **로컬이 2.0.0을 쓰지 않습니다.** 로컬 `node_modules`는 3일 전보다 먼저 설치되었으므로 1.4.0일 가능성이 높습니다. 따라서 로컬 빌드 성공은 2.0.0과의 호환성을 증명하지 않습니다.
- **`exports` 필드가 하위 경로 import(패키지 안의 특정 파일을 직접 가져오는 방식)를 막습니다.** `@company/ui/button`은 하위 경로 import입니다. `exports`(패키지가 외부에 공개할 경로를 적는 설정)가 없던 1.4.0에서는 파일 경로로 바로 찾을 수 있었습니다. 2.0.0에서 `exports`가 생겼고, `./button`이 목록에 없다면 Node와 번들러는 이 경로를 찾지 못합니다.
- **CI는 2.0.0을 받는 것으로 보입니다.** 캐시 키가 `package-lock.json`(설치할 정확한 버전을 기록한 파일)의 해시이므로, 버전을 올려 lockfile이 바뀌면 캐시가 빗나갑니다. 그러면 CI는 새로 설치하면서 2.0.0을 받습니다. 이 경로가 "CI에서만 실패한다"는 현상을 설명합니다.
- **Node 버전 차이는 원인일 가능성이 낮습니다.** Node 18과 20은 모두 `exports` 필드를 지원합니다. 다만 배제한 것은 아닙니다.

### 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다. 1.4.0이 나오면 로컬이 2.0.0을 테스트하지 않은 것입니다.
2. `node_modules/@company/ui/package.json`의 `exports` 항목에 `./button`이 있는지 확인합니다. 없다면 추론 2가 맞습니다.
3. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 Node 20으로 빌드합니다. 여기서 실패하면 Node 버전과 무관하게 버전 또는 `exports` 문제입니다.
4. 같은 환경에서 Node 18로 빌드해 Node 버전 차이를 배제합니다.
5. CI 로그에서 캐시 복원이 hit인지 miss인지 확인하고, 설치 후 `npm ls @company/ui` 결과를 로그에 추가합니다.

### 해결 방향

- `exports`에 `./button`이 있다면 import 경로를 그 항목에 맞게 바꿉니다.
- `exports`에 없다면 패키지 쪽에 경로 추가를 요청하거나, 공개된 진입점(예: `@company/ui` 루트)에서 가져오도록 바꿉니다. 루트에서 `Button`을 내보내는지는 확인 필요합니다.
- 2.0.0 전환을 당장 끝내기 어렵다면 `@company/ui`를 1.4.0으로 되돌려 CI를 먼저 살립니다.
- 두 방법 모두 로컬도 `npm ci`로 lockfile 기준 설치를 맞춰야 로컬과 CI의 결과가 같아집니다.

### 확인 필요

- 2.0.0 패키지의 `exports` 전체 목록
- CI의 설치 명령이 `npm ci`인지 `npm install`인지
- 2.0.0 변경 커밋에 `package-lock.json`이 포함되었는지
- 로컬 Node 18 빌드 결과
