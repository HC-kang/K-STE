원인은 로컬과 CI가 서로 다른 버전의 `@company/ui`를 쓰는 것으로 보입니다. 확인한 사실이 아니라 주어진 정보에서 추론한 내용입니다.

**사실**
- CI 빌드만 `Cannot find module '@company/ui/button'`으로 실패합니다.
- `@company/ui` 2.0.0은 `exports` 필드를 추가했습니다.
- 로컬 `node_modules`는 업그레이드 3일 전보다 먼저 설치한 것입니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.

**추론**
1. `exports` 필드가 있으면 패키지는 여기에 적은 경로만 외부에 공개합니다. 적지 않은 서브패스는 파일이 실제로 있어도 import할 수 없습니다.
2. 2.0.0의 `exports`에 `./button`이 없거나 다른 형태로 적혀 있으면 `@company/ui/button`을 찾을 수 없습니다.
3. 로컬 `node_modules`에는 아직 1.4.0이 있을 가능성이 큽니다. 1.4.0에는 `exports`가 없으므로 같은 import가 성공합니다.
4. 업그레이드로 `package-lock.json`이 바뀌었으므로 CI는 캐시를 쓰지 못하고 2.0.0을 새로 설치했을 것입니다. 그래서 CI에서만 실패합니다.

Node 버전 차이(18과 20)는 원인일 가능성이 낮습니다. 두 버전 모두 `exports`를 지원하기 때문입니다. 다만 직접 검증하지는 않았습니다.

**확인 필요**
- 로컬에 설치된 `@company/ui`의 실제 버전을 모릅니다.
- 2.0.0의 `exports`에 `./button`이 있는지 모릅니다.

**검증 순서**
1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인한다.
2. CI와 같은 버전의 `node_modules/@company/ui/package.json`을 열어 `exports`에 `./button`이 있는지 확인한다.
3. 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치한 뒤 `npm run build`를 실행한다. 이 빌드가 CI와 같은 에러로 실패하면 추론이 맞습니다.

**수정 방향**
- `exports`에 공개된 경로가 있으면 import 경로를 그 경로로 바꿉니다.
- `./button`이 의도치 않게 빠졌다면 `@company/ui` 담당자에게 `exports`에 추가해 달라고 요청합니다.
- 급하면 `@company/ui`를 1.4.0으로 되돌릴 수 있습니다. 이 경우 2.0.0의 다른 변경도 함께 되돌아갑니다.

PM께 공유할 내용은 두 가지입니다. 이 문제는 CI 설정 오류가 아니라 로컬 환경이 오래된 데서 생긴 불일치로 보입니다. 그리고 3번 검증을 끝내기 전에는 원인이 확정되지 않습니다.
