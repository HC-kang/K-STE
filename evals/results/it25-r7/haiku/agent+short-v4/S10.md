가장 유력한 원인은 로컬에 남은 1.4.0과 CI가 새로 설치하는 2.0.0의 버전 차이입니다. 2.0.0의 `exports` 필드에 `./button` 경로가 없으면 `@company/ui/button` import가 막혀 CI 빌드가 실패합니다. 이 내용은 아직 검증하지 않은 추정이므로 아래 확인 방법으로 먼저 확인해야 합니다.

## 원인 추정

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| @company/ui 버전 | 1.4.0 추정 | 2.0.0 추정 |
| node_modules 출처 | 3일 전보다 먼저 설치됨 | 확인 필요: 캐시 복원 또는 새 설치 |

원인은 다음 순서로 이어졌을 것으로 추정합니다.

1. 로컬 node_modules는 3일 전보다 먼저 설치되었으므로 1.4.0이 남아 있을 가능성이 높습니다.
2. 1.4.0에는 `exports` 필드가 없으므로 `@company/ui/button`은 패키지 안의 파일 경로로 그대로 찾아집니다.
3. CI는 package-lock.json에 따라 설치하므로 2.0.0을 받을 가능성이 높습니다. 확인 필요: CI가 캐시된 node_modules를 복원하는지 여부입니다.
4. 2.0.0의 `exports`에 `./button` 경로가 없으면 Node의 모듈 해석에서 이 import가 막힙니다.

에러 메시지는 주의해서 볼 필요가 있습니다. Node가 `exports` 제한으로 import를 막을 때는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED` 오류를 냅니다. `Cannot find module`은 CommonJS require 해석이나 Jest 같은 도구에서 흔히 나오고, Next.js의 webpack은 보통 `Module not found`로 표시합니다. 확인 필요: 이 메시지를 낸 단계가 Next.js 빌드인지, 테스트 같은 별도 단계인지 여부입니다.

Node 버전 차이만으로는 이 오류를 설명하기 어렵습니다. Node 18과 20은 모두 `exports` 필드를 지원합니다. 다만 확인 필요: Next.js 또는 `@company/ui` 2.0.0이 요구하는 최소 Node 버전입니다.

캐시 키가 package-lock.json 해시이므로 lock 파일이 바뀌면 키도 바뀌어 새 설치가 일어납니다. 그러나 restore-keys에 이전 키의 접두사가 있으면 1.4.0이 담긴 이전 캐시가 복원될 수 있습니다. 확인 필요: 워크플로 파일의 restore-keys 설정입니다.

## 확인 방법

- 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
- `node_modules/@company/ui/package.json`의 `exports` 필드에 `./button` 항목이 있는지 봅니다.
- 저장소의 package-lock.json에 `@company/ui` 2.0.0이 기록되어 있는지 봅니다.
- CI 로그에서 설치 명령(`npm ci` 또는 `npm install`)과 캐시 hit 또는 miss 메시지를 확인합니다.
- 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드합니다. node_modules는 다시 설치할 수 있습니다. 이 빌드가 실패하면 설치된 버전 차이가 원인이라는 근거가 됩니다.

## 해결 방향

PM과 함께 정할 사항은 두 가지입니다. 첫째, `@company/ui`를 1.4.0으로 되돌리면 빌드는 빨리 복구되지만 2.0.0의 변경 사항은 쓸 수 없습니다. 둘째, 2.0.0을 유지하려면 import 경로를 `exports`에 있는 경로로 바꾸거나, 패키지 관리자에게 `./button` 항목 추가를 요청해야 합니다. 2.0.0은 메이저 버전이므로 다른 import 경로도 깨졌을 수 있습니다. 따라서 저장소 전체에서 `@company/ui/` import를 검색하는 것을 권장합니다.
