CI에서만 실패하는 가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드가 `button` 경로를 1.4.0과 다르게 노출하는 것이다. 로컬은 3일 전에 설치한 패키지를 그대로 쓰고 있을 가능성이 커서 2.0.0을 검증하지 못한 것으로 보인다. 이 판단은 주어진 정보에 기반한 추론이며, 아직 패키지 내용과 CI 로그를 직접 확인하지 않았다.

## 확인된 사실

- CI 빌드에서 `Error: Cannot find module '@company/ui/button'`이 발생한다.
- 로컬 빌드는 성공한다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에 `exports` 필드(패키지가 외부에 공개하는 경로를 정하는 설정)가 추가됐다.
- CI는 Node 18, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`(설치 버전을 고정한 기록)의 해시다.
- 로컬 `node_modules`는 업그레이드 이전에 설치됐다.

## 추론

- 로컬 `node_modules`에는 1.4.0이 남아 있을 가능성이 크다. 그래서 로컬 빌드는 2.0.0에서 `button` 경로가 동작하는지 검증하지 않는다.
- 따라서 "CI에서만 실패한다"는 현상은 환경 차이보다 설치된 패키지 버전 차이에서 나왔을 가능성이 크다.

## 가설과 확인 방법

| 순위 | 가설 | 근거 | 확인 방법 |
|---|---|---|---|
| 1 | 2.0.0의 `exports`에 `./button` 항목이 없거나 경로가 바뀌었다. | `exports` 추가가 사실이고, 1.4.0의 직접 경로가 막힐 수 있다. | 2.0.0 패키지의 `package.json`에서 `exports` 키 목록을 확인한다. |
| 2 | Node 18이 2.0.0의 조건부 `exports`를 해석하지 못한다. | Node 18은 CJS(require 방식)에서 ESM 전용 패키지를 읽지 못한다. CI에서만 실패하는 설명이 된다. | `exports`의 조건(import, require, default, types) 구성을 확인하고, Node 18과 20에서 `require.resolve('@company/ui/button')`를 각각 실행한다. |
| 3 | `package-lock.json`이 2.0.0으로 갱신되지 않았거나 커밋되지 않았다. | CI와 로컬이 실제로 설치하는 버전이 달라질 수 있다. | 커밋된 lock 파일에서 `@company/ui` 버전을 확인한다. |
| 4 | TypeScript가 `exports`를 무시하고 파일 경로로 찾는다. | 타입 검사에서 생기는 오류일 수 있다. 다만 주어진 메시지에는 TypeScript 특유의 문구가 없다. | `tsconfig.json`의 `moduleResolution` 값을 확인한다. |
| 5 | CI 캐시가 오래된 `node_modules`를 복원한다. | 캐시 키가 lock 해시라 lock이 바뀌면 키도 바뀐다. 이전 캐시를 대체 키로 복원하면 발생할 수 있다. 다만 이 경우 CI가 성공해야 하므로 가능성은 낮다. | CI 로그에서 캐시 적중 여부와 복원된 키를 확인한다. |

가설 1과 2가 가장 유력하다. 가설 2는 CI와 로컬의 Node 버전 차이를 설명하는 유일한 가설이다.

## 확인 순서

1. CI 로그에 `npm ls @company/ui` 출력을 추가해 실제 설치 버전을 확인한다.
2. 2.0.0 패키지의 `exports` 키와 조건 목록을 확인한다.
3. Node 18과 Node 20에서 `button` 경로 해석 결과를 비교한다.
4. 로컬 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드한다.

## 권장 조치

- 2.0.0의 `exports`에 맞게 import 경로를 바꾼다. 
- 2.0.0에 필요한 경로가 없다면 `@company/ui` 측에 해당 경로 추가를 요청한다.
- 당장 배포를 막아야 한다면 `@company/ui`를 1.4.0으로 되돌린다.
- 팀 전체가 같은 Node 버전을 쓰도록 맞추는 것을 권장한다.
- 로컬 검증은 CI와 같은 Node 18에서 `npm ci` 후 빌드하는 방식으로 진행하는 것을 권장한다.

## 미확인 사항

- 2.0.0의 `exports` 내용은 확인하지 않았다.
- 로컬 `node_modules`의 실제 버전은 확인하지 않았다. 1.4.0이라는 판단은 설치 시점에 근거한 추정이다.
- 오류 메시지 "Cannot find module"을 Node, Next.js(webpack), TypeScript 중 어디서 냈는지 확인하지 않았다. 이 정보로 가설 1과 4 중 무엇이 맞는지 가릴 수 있다.
