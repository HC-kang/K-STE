# CI에서만 `Cannot find module '@company/ui/button'`이 나는 원인 분석

가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드가 하위 경로 import를 제한하고, CI는 2.0.0을 설치하는데 로컬은 3일 전에 설치한 1.4.0을 그대로 쓰고 있다는 점이다. 이 내용은 아래 추론이며, 아직 실제 설치 버전과 `exports` 목록으로 검증하지 않았다.

## 확인된 사실

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에는 `exports` 필드가 추가됐다.
- CI는 Node 18을, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`의 해시다.
- 로컬 `node_modules`는 버전을 올리기 전에 설치됐다.

## 추론

1. 로컬 `node_modules`에는 아직 1.4.0이 남아 있다. 1.4.0에는 `exports` 필드가 없으므로 `@company/ui/button`이 파일 경로로 그대로 해석된다. 그래서 로컬 빌드는 성공한다.
2. CI는 `package-lock.json` 기준으로 새로 설치한다. 2.0.0이 설치되면 `exports`에 없는 하위 경로 `@company/ui/button`은 Node 버전과 관계없이 해석되지 않는다.
3. 캐시 키가 lock 파일 해시이므로, lock 파일이 바뀌었다면 캐시가 새로 만들어져 2.0.0이 설치된다. lock 파일이 바뀌지 않았다면 이전 캐시가 복원되었을 가능성도 있다.
4. Node 18과 Node 20의 차이가 주원인일 가능성은 낮다. Node 18도 `exports`를 지원한다. 다만 조건부 `exports`(`import`, `require`, `node` 조건)나 번들러 해석 차이가 영향을 줄 가능성은 남아 있다.
5. 에러 문구 `Cannot find module`은 Node의 모듈 해석 에러 형식이다. Next.js의 웹팩 빌드 에러는 보통 `Module not found`로 나온다. 따라서 실패 지점은 `next build` 내부가 아니라 `next.config.js`, 빌드 전 스크립트, 또는 테스트 도구일 수 있다.

## 확인 필요

1. 확인 필요: CI 로그에서 실제 설치된 `@company/ui` 버전을 확인한다. `npm ls @company/ui` 출력을 남기면 된다.
2. 확인 필요: 로컬에서 `npm ls @company/ui`를 실행해 설치 버전을 확인한다. 1.4.0이면 추론 1이 맞다.
3. 확인 필요: 2.0.0 `package.json`의 `exports` 목록에 `./button`이 있는지 확인한다.
4. 확인 필요: 버전 bump 커밋에 `package-lock.json`이 포함됐는지 확인한다.
5. 확인 필요: 에러를 던진 파일을 스택 트레이스에서 찾는다.
6. 확인 필요: 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치한 뒤 빌드해 재현되는지 확인한다.

## 해결 방안

- 단기: 코드의 import 경로를 2.0.0 `exports`에 있는 경로로 바꾸는 것을 권장한다. 필요한 경로가 없다면 패키지 관리자에게 `exports` 추가를 요청할 수 있다.
- 단기 대안: `@company/ui`를 1.4.0으로 되돌릴 수 있다. 다만 2.0.0에 필요한 변경이 있는지 먼저 확인해야 한다.
- 공통: 로컬도 `npm ci`로 다시 설치해 CI와 같은 조건에서 빌드하도록 권장한다.
- 공통: Node 버전을 `.nvmrc`나 `engines` 필드로 맞추는 것을 권장한다. 다만 이 작업이 이 에러의 해결책이라고 보기는 어렵다.
- 2.0.0은 주 버전 변경이므로 릴리스 노트에서 나머지 호환성 변경도 함께 확인해야 한다.
