Redis를 도입하면 서버 4대가 같은 캐시를 보게 되므로, 서버마다 상품 정보가 다른 문제는 없어집니다. 가격을 바꾼 뒤 고객에게 보이기까지 걸리는 시간은 캐시를 언제 갱신하느냐에 따라 달라지므로, 도입만으로 줄어든다고 보기는 어렵습니다.

캐시는 자주 쓰는 데이터를 매번 원본에서 가져오지 않도록 임시로 복사해 두는 저장 공간입니다. 지금 방식과 Redis 방식을 비교하면 다음과 같습니다.

| 구분 | 지금 (서버별 로컬 캐시) | 도입 예정 (Redis 캐시) |
|---|---|---|
| 저장 위치 | 각 API 서버의 메모리 안 | 별도의 캐시 서버 1대 |
| 서버 4대의 캐시 내용 | 서버마다 다를 수 있음 | 4대가 같은 내용을 봄 |
| 읽는 방식 | 같은 서버 안에서 바로 읽음 | 네트워크를 거쳐 캐시 서버에 요청함 |
| 가격 변경 후 고객에게 보이기까지 | 서버마다 최대 5분 | 갱신 방식에 따라 다름 |

Redis의 단점도 있습니다. 모든 서버가 캐시 서버 1대에 의존하므로, 그 서버가 멈추면 4대 모두 영향을 받습니다.

확인 필요: Redis 도입 후 가격 변경이 고객에게 보이기까지 걸리는 시간. 가격을 바꿀 때 캐시를 바로 지우도록 설계하면 반영이 빨라지고, 지금처럼 5분 뒤에 만료되도록 두면 지금과 같은 시간이 걸립니다. 원하는 반영 시간이 있으면 개발팀과 갱신 방식을 함께 정하십시오.
