가장 유력한 원인은 2.0.0에서 추가된 `exports` 필드입니다. 이 필드가 `./button` 하위 경로를 노출하지 않거나 다른 경로로 바꿔 놓았을 가능성이 큽니다. 다만 아직 확인하지 않았습니다.

## 확인된 사실

- `@company/ui`를 1.4.0에서 2.0.0으로 올렸고, 2.0.0에는 `exports` 필드가 추가되었습니다.
- 로컬 `node_modules`는 업그레이드 3일 전에 설치되었습니다.
- CI는 `package-lock.json` 해시를 캐시 키로 씁니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.

## 추론

- **로컬 성공은 오래된 설치본 때문일 수 있습니다.** 로컬 `node_modules`가 업그레이드 전 상태라면 1.4.0 기준으로 빌드됩니다. 이 경우 Node 버전과 무관하게 로컬은 성공합니다.
- **CI 실패는 2.0.0이 새로 설치되었기 때문일 수 있습니다.** 업그레이드 커밋에서 lock 파일이 함께 바뀌었다면 캐시 키가 달라져 캐시가 무효화되고, CI는 2.0.0을 새로 설치합니다.
- **Node 버전 차이는 직접 원인일 가능성이 낮습니다.** Node 18과 20 모두 `exports`를 지원합니다. 다만 npm 버전 차이가 lock 파일 해석에 영향을 줄 가능성은 배제할 수 없습니다.

## 아직 확인하지 않은 것

- 에러 메시지가 정확히 맞지 않습니다. Node가 `exports`에 없는 경로를 거부할 때는 보통 "Package subpath ... is not defined by exports"라는 메시지를 냅니다. `Cannot find module`은 다른 해석 단계에서 나온 메시지일 수 있으므로, 전체 스택 트레이스로 어느 단계에서 실패하는지 확인해야 합니다.
- CI에서 캐시가 hit 되었는지 miss 되었는지 확인해야 합니다. hit 되었다면 1.4.0이 복원되었을 수 있으므로 원인이 달라집니다.

| 가설 | 근거 | 확인 방법 |
|---|---|---|
| 2.0.0 `exports`에 `./button`이 없거나 경로가 바뀜 | 에러가 2.0.0 업그레이드 이후 발생 | 2.0.0 `package.json`의 `exports` 필드에서 `./button` 항목 확인 |
| 로컬은 1.4.0, CI는 2.0.0을 사용 | 로컬 `node_modules`가 업그레이드 전 설치, 캐시 키가 lock 해시 | 로컬 `node_modules/@company/ui/package.json`의 version과 CI 로그의 설치 버전 비교 |
| Node 18 차이 | CI만 Node 18 사용 | 로컬에서 Node 18로 `npm ci` 후 빌드 |
| 전체 스택 트레이스 | 에러 메시지가 `exports` 거부 메시지와 다름 | CI 로그에서 에러 발생 지점의 스택 트레이스 확인 |

개발자는 CI 로그에서 설치된 `@company/ui` 버전과 캐시 hit 여부를 먼저 확인하십시오. 그다음 2.0.0 `exports` 항목과 전체 스택 트레이스를 대조하면 원인을 좁힐 수 있습니다.
