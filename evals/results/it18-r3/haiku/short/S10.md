CI가 `@company/ui` 2.0.0을 설치한 상태에서 `@company/ui/button` 경로를 해석하지 못해 빌드가 실패하는 것으로 보입니다. 로컬은 3일 전에 설치된 node_modules를 쓰므로 1.4.0이 남아 있을 가능성이 크고, 이 경우 2.0.0의 `exports` 제한을 받지 않습니다. 아래 원인은 모두 추론이며 확인 전까지 사실로 보지 않습니다.

## 확인된 사실

- 에러 메시지는 `Cannot find module '@company/ui/button'`입니다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에 `exports` 필드가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 업그레이드 전에 설치되었습니다.

## 추론

`exports` 필드가 2.0.0에서 처음 추가되었다는 것은 1.4.0에는 이 필드가 없다는 뜻입니다. `exports` 필드가 있으면 Node는 그 맵에 적힌 경로만 외부에 공개하므로, 맵에 `./button`이 없으면 `@company/ui/button`을 찾을 수 없습니다.

| 항목 | CI | 로컬 |
|---|---|---|
| Node 버전 | 18 (확인됨) | 20 (확인됨) |
| `@company/ui` 설치 버전 | 미확인 | 1.4.0으로 추정 (설치 시점 기준) |
| `exports` 제한 적용 여부 | 2.0.0이면 적용 | 1.4.0이면 미적용 |

원인 후보는 다음과 같습니다.

1. 2.0.0의 `exports` 맵에 `./button` 항목이 없거나 경로가 다릅니다. 가장 유력한 후보입니다.
2. 로컬은 오래된 node_modules를 써서 2.0.0의 해석 방식을 한 번도 시험하지 않았습니다. 그래서 로컬 성공이 CI 실패를 반박하지 못합니다.
3. CI 캐시 키가 lock 파일 해시이므로, lock 파일이 2.0.0을 반영하지 않은 커밋에서는 CI가 이전 node_modules를 복원했을 수 있습니다. 이 경우 CI가 실제로 설치한 버전은 로컬과 다를 수 있습니다.
4. Node 18과 20의 차이만으로 이 에러를 설명하기는 어렵다고 보입니다. `exports` 해석은 Node 18에서도 지원되기 때문입니다. 다만 Node 버전별 세부 차이는 확인하지 않았습니다.

## 확인 순서

1. CI 로그에서 `@company/ui`가 실제로 설치된 버전을 확인합니다.
2. 커밋된 `package-lock.json`의 `node_modules/@company/ui` 항목에서 version 값을 확인합니다.
3. 2.0.0 패키지의 `package.json`에서 `exports` 맵에 `./button`이 있는지 확인합니다.
4. 로컬에서 `npm ls @company/ui`를 실행해 설치 버전을 확인합니다.
5. 로컬에서 Node 18로 `npm ci` 후 빌드를 실행해 CI 실패를 재현하는 것을 권장합니다.

확인 결과에 따라 수정 방향이 달라집니다. `exports` 맵에 `./button`이 없다면 import 경로를 2.0.0이 공개하는 경로로 바꾸거나, 패키지 관리자에게 맵 추가를 요청하는 방법이 있습니다. CI가 lock 파일과 다른 버전을 설치했다면 캐시와 lock 파일 동기화를 먼저 고쳐야 합니다.
