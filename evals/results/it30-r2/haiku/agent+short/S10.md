CI에서만 실패하는 가장 유력한 계기는 @company/ui 2.0.0 업그레이드이며, 정확한 원인은 아직 확정되지 않았다. 아래 추론은 전달받은 여섯 가지 사실에만 근거하며, 패키지 파일이나 CI 로그는 아직 확인하지 않았다.

## 확인된 사실

- CI(Node 18)에서만 `Cannot find module '@company/ui/button'` 오류로 빌드가 실패한다.
- 로컬(Node 20)에서는 빌드가 성공한다.
- 3일 전 @company/ui 버전이 1.4.0에서 2.0.0으로 올라갔다.
- 2.0.0 패키지에 exports 필드(패키지 외부에 노출할 파일 경로를 정하는 설정)가 추가되었다.
- CI 캐시 키는 package-lock.json(설치 버전을 고정한 파일)의 해시(내용을 요약한 값)다.
- 로컬 node_modules(설치된 패키지 폴더)는 업그레이드 전에 설치되었다.

## 로컬 성공은 근거가 되지 않는다

로컬 node_modules가 업그레이드 전에 설치되었으므로, 안에 1.4.0이 그대로 남아 있을 가능성이 크다(추론). 그러면 로컬 빌드는 2.0.0을 쓰지 않은 상태에서 성공한 것이다. 따라서 로컬 성공은 2.0.0과의 호환성을 보여 주지 못한다. `npm ls @company/ui`를 실행하면 로컬에 설치된 실제 버전을 알 수 있다.

## 원인 후보

| 후보 | 근거 | 가능성(추론) | 검증 방법 |
|---|---|---|---|
| 파일명 대소문자 차이 | 로컬은 macOS, CI는 Linux일 가능성이 있다(확인 필요) | 중간에서 높음 | 패키지 파일명과 import 경로의 대소문자를 비교한다 |
| exports가 가리키는 파일이 없음 | 파일이 없으면 "Cannot find module" 메시지가 나온다 | 중간 | exports 항목이 가리키는 파일이 설치된 패키지 안에 있는지 본다 |
| exports가 button 하위 경로를 막음 | 2.0.0은 exports에 적힌 경로만 가져오게 한다 | 중간에서 낮음 | 설치된 package.json의 exports에 button 항목이 있는지 본다 |
| 캐시가 원인 | 캐시 키가 lock 해시라 의존성이 바뀌면 새로 설치된다 | 낮음 | CI 로그에서 캐시 복원 키와 설치 명령을 본다 |
| Node 18과 20의 차이 | 두 버전 모두 exports를 지원한다 | 낮음 | @company/ui 2.0.0의 engines 필드와 CI, 로컬의 node -v 값을 비교한다 |

exports 차단과 파일 없음은 Node가 내는 메시지가 다르다. Node는 차단된 하위 경로에 대해 "is not defined by exports" 계열의 메시지를 낸다. 따라서 "Cannot find module" 문구는 차단보다 파일 경로가 잘못되었거나 대소문자가 맞지 않는 쪽에 더 가깝다는 신호로 볼 수 있다(추론). 다만 이 메시지를 내는 도구가 Node인지 Next.js 빌드인지는 확인 필요하다.

캐시가 원인일 가능성은 낮다. 오래된 캐시는 1.4.0을 복원하므로 빌드를 오히려 통과시키는 방향이다. 다만 설치가 중간에 끊긴 불완전한 캐시가 남았다면 실패할 수 있다.

## 검증 순서

1. CI 로그 전문에서 오류가 난 단계와 설치된 @company/ui 버전 줄을 찾는다.
2. 로컬에서 Node 18을 쓰고 `rm -rf node_modules && npm ci`로 lock 기준에 맞춰 새로 설치한 뒤 빌드한다.
3. 설치된 `node_modules/@company/ui/package.json`의 exports에서 button 항목을 찾는다.
4. exports가 가리키는 파일이 실제로 있는지, 파일명 대소문자가 import 경로와 맞는지 비교한다.

2번에서 로컬도 실패하면 원인은 CI 환경이 아니라 2.0.0 패키지 설정에 있을 가능성이 크다(추론). 2번에서 로컬이 성공하면 CI와 로컬의 설치 상태 차이, 특히 OS와 1.4.0 잔존 여부를 먼저 확인한다.

## 해결 방향

- 대소문자 차이라면 import 경로의 대소문자를 패키지 파일명과 맞춘다.
- exports 항목이 잘못되었다면 패키지 유지관리자에게 경로 수정을 요청해야 한다.
- 빌드가 바로 막혀 있다면 @company/ui를 1.4.0으로 임시 고정해도 된다. 이 방법은 2.0.0 변경 사항을 나중에 다시 적용해야 한다.

어느 방법을 쓸지는 검증 결과가 나온 뒤 팀이 정한다.

## 확인 필요

- CI 실패가 정말 3일 전 업그레이드 이후에 시작되었는지 확인 필요: CI 실행 기록에서 첫 실패 시점을 비교해야 한다.
- 2.0.0 릴리스 노트에 경로 변경 안내가 있는지 확인 필요: 있다면 원인 확정에 바로 쓸 수 있다.
- CI와 로컬의 OS 차이가 실제로 있는지 확인 필요: 입력에는 OS 정보가 없었다.
- 오류가 나는 단계(Next.js 빌드, 설정 파일, 테스트 도구 중 어느 것인지) 확인 필요: CI 로그 전문이 있어야 특정할 수 있다.
