가장 유력한 원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드(패키지 바깥에 공개할 경로를 적는 설정)입니다. 이 필드 때문에 `@company/ui/button` 같은 하위 경로 import가 막혔을 가능성이 높습니다. 다만 아래 내용은 제공된 정보에서 나온 추론이며, 아직 실행해서 검증하지 않았습니다.

### 원인 분석

1.4.0에는 `exports` 필드가 없었으므로 `@company/ui/button`이 파일 경로로 그대로 풀렸습니다. 2.0.0에서는 `exports`에 `./button` 항목이 없으면 Node와 번들러(Next.js가 코드를 묶어 빌드할 때 쓰는 도구)가 이 경로를 찾지 못합니다. 에러 메시지와 버전 변경 시점이 이 설명과 맞습니다.

로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 3일 전에 설치된 상태라는 점으로 보입니다. 그 설치본에 1.4.0이 들어 있다면 `exports` 제한이 적용되지 않아 빌드가 통과합니다.

CI는 `package-lock.json` 해시를 캐시 키(캐시를 찾는 기준값)로 씁니다. 락 파일이 바뀌면 캐시가 무효화되어 깨끗하게 설치하고, 락 파일에 2.0.0이 기록되어 있으면 CI는 2.0.0을 받습니다. 캐시 키는 원인이 아니라 문제가 드러나게 한 경로입니다.

Node 18과 20의 차이는 주된 원인으로 보기 어렵습니다. 두 버전 모두 `exports`를 지원하기 때문입니다. 다만 번들러 설정에 따라 차이가 날 수 있으므로 배제하지는 않습니다.

### 검증 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 봅니다. 1.4.0이면 로컬이 성공한 이유가 설명됩니다.
2. `node_modules/@company/ui/package.json`의 `exports` 항목에 `./button`이 있는지 직접 봅니다.
3. CI 로그에서 `@company/ui`가 어떤 버전으로 설치됐는지 봅니다.
4. 로컬에서 `rm -rf node_modules && npm ci`를 실행해 CI와 같은 조건으로 빌드를 재현합니다.
5. nvm으로 Node 18을 설치해 같은 빌드를 돌려 Node 버전의 영향을 봅니다.

### 수정 방향

1. import 경로를 2.0.0 `exports`가 허용하는 경로로 바꿉니다. 먼저 허용 목록을 봐야 합니다.
2. 패키지 관리자에게 `./button` 경로를 `exports`에 추가해 달라고 요청합니다.
3. 급하면 `@company/ui`를 1.4.0에 고정합니다. 이 경우 2.0.0에서 들어온 변경을 받지 못하게 됩니다.

어느 방법이 맞는지는 2.0.0 변경 기록과 허용 경로 목록을 본 뒤에 정해야 합니다.
