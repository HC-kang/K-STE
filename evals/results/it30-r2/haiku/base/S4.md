# 운영 배포 롤백 런북: payment-api

**대상 서비스**: payment-api (운영)
**배포 도구**: ArgoCD
**롤백 명령**: `argocd app rollback payment-api <REVISION>`

---

## 0. 중단 조건 (먼저 확인)

아래 중 하나라도 해당하면 **롤백하지 말고** 1단계로 가서 DBA에게 연락한다.

- 롤백 대상 배포에 **DB 마이그레이션이 포함됨**
- 마이그레이션 포함 여부를 **확인하지 못함**

> 마이그레이션 포함 여부가 불확실하면 포함된 것으로 간주한다.

---

## 1. 마이그레이션 포함 여부 확인

1. 현재 배포 리비전과 롤백 대상 리비전을 확인한다.
   ```
   argocd app history payment-api
   ```
   - 출력의 `ID`가 `<REVISION>`에 들어갈 값이다.
   - 현재 배포된 리비전의 `ID`도 기록해 둔다.

2. 현재 리비전과 롤백 대상 리비전 사이에 변경된 코드를 비교하여 마이그레이션 파일 변경이 있는지 확인한다.
   - 대상: 마이그레이션 디렉터리(예: `db/migrate/`, `migrations/`) 및 스키마 변경 파일
   - 확인 방법: 해당 두 리비전의 커밋 범위에서 마이그레이션 경로의 diff를 조회한다.

3. 판정:
   - **마이그레이션 변경 없음** → 2단계로 진행한다.
   - **마이그레이션 변경 있음, 또는 확인 불가** → 롤백을 중단하고 아래 연락 절차를 따른다.

**연락 절차 (DBA 박지은)**
- 대상: 박지은 (DBA)
- 전달 내용: 서비스명(payment-api), 현재 리비전, 롤백 대상 리비전, 마이그레이션 포함 여부 확인 결과
- 연락이 닿을 때까지 롤백을 실행하지 않는다.

---

## 2. 롤백 실행

1. 롤백 전 현재 상태를 기록한다.
   ```
   argocd app get payment-api
   ```
2. 롤백을 실행한다.
   ```
   argocd app rollback payment-api <REVISION>
   ```
3. 동기화 상태가 완료될 때까지 기다린다.
   ```
   argocd app wait payment-api --health
   ```

---

## 3. 롤백 후 검증

### 3-1. 헬스체크
- `/healthz` 엔드포인트가 **HTTP 200**을 반환하는지 확인한다.
  ```
  curl -s -o /dev/null -w "%{http_code}\n" https://<payment-api 운영 호스트>/healthz
  ```
- 200이 아니면 롤백 실패로 간주하고 4단계(에스컬레이션)로 간다.

### 3-2. 결제 테스트 주문
- 결제 테스트 주문을 **1건** 실행하고 성공 여부를 확인한다.
- 실패하면 4단계(에스컬레이션)로 간다.

---

## 4. 이력 기록 (#deploy 채널)

롤백이 성공하든 실패하든 #deploy 채널에 아래 항목을 남긴다.

- 서비스: payment-api
- 롤백 시각
- 작업자
- 롤백 전 리비전 → 롤백 후 리비전
- 마이그레이션 포함 여부 확인 결과
- `/healthz` 응답 코드
- 결제 테스트 주문 결과 (성공/실패)
- 중단했다면 중단 사유와 DBA 연락 여부

---

## 5. 에스컬레이션

롤백 후 헬스체크 또는 결제 테스트가 실패하면:
1. 추가 롤백 시도 전에 상태를 기록하고 담당자에게 알린다.
2. DB 관련 문제가 의심되면 DBA 박지은에게 연락한다.

---

## 확인이 필요한 항목

아래 항목은 제공된 정보에 없어 런북에 구체적으로 적지 않았다. 실제 사용 전에 채워야 한다.

- **마이그레이션 diff 확인 방법**: 저장소 내 마이그레이션 경로와 비교 명령
- **운영 호스트 주소**: `/healthz` 확인용 URL
- **결제 테스트 주문 절차**: 테스트 계정, 실행 방법, 테스트 결제 취소 방법
- **에스컬레이션 담당자**: DBA 외에 서비스 책임자 연락처가 있는지
