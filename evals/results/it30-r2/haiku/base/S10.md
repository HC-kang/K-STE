# 빌드 실패 원인 분석: `Cannot find module '@company/ui/button'`

## 요약

**가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드 도입으로 인한 deep import 경로 차단입니다.** 로컬 빌드가 성공한 이유는 로컬이 아직 1.4.0을 쓰고 있기 때문으로 보입니다. 즉 로컬은 2.0.0에서 한 번도 검증되지 않았습니다.

## 배경 설명

- **`exports` 필드**: 패키지가 외부에 공개하는 경로를 명시적으로 정해 두는 설정입니다. 이 필드가 있으면 목록에 없는 내부 경로는 import할 수 없습니다.
- **deep import**: `@company/ui/button`처럼 패키지 내부 파일 경로를 직접 가리키는 import입니다. 1.4.0에는 `exports`가 없어서 이런 경로가 자유롭게 동작했습니다.
- 2.0.0에서 `exports`가 추가되면서 `./button`이 목록에 없거나 경로가 바뀌었다면, 같은 코드가 실패하게 됩니다.

## 왜 로컬은 성공하고 CI만 실패하나

| 구분 | 로컬 | CI |
|---|---|---|
| `@company/ui` 실제 설치 버전 | **1.4.0** (3일 전 설치한 `node_modules` 유지) | **2.0.0** (lock 해시 변경으로 캐시 미스, 새로 설치) |
| Node 버전 | 20 | 18 |
| 결과 | 성공 | 실패 |

로컬 `node_modules`는 3일 전에 설치된 그대로라서 1.4.0이 들어 있습니다. 따라서 로컬 성공은 "2.0.0에서도 된다"는 증거가 아닙니다. Node 버전 차이보다는 **설치된 패키지 버전 차이**가 결과를 갈랐을 가능성이 훨씬 큽니다.

## 원인 가설 (가능성 순)

1. **2.0.0 `exports`에 `./button` 경로가 없음** (가능성 높음)
   - 2.0.0이 `exports`에 `./button`을 노출하지 않았거나, `./components/button` 같은 새 경로로 바꿨을 수 있습니다.
2. **파일 경로 변경** (가능성 높음)
   - 2.0.0에서 `button` 파일이 다른 디렉터리로 옮겨졌다면 경로 자체가 존재하지 않습니다.
3. **Node 18과 20의 resolve 동작 차이** (가능성 낮음)
   - 두 버전 모두 `exports`를 지원하므로 단독 원인일 가능성은 낮습니다. 다만 2.0.0이 Node 20 이상을 요구하거나 특정 조건부 export를 쓴다면 영향을 줄 수 있습니다. Node 18은 2025년 4월에 EOL이므로 어쨌든 점검 대상입니다.
4. **CI 캐시 문제** (가능성 낮음)
   - lock 해시가 바뀌었다면 캐시는 정상적으로 무효화되었을 것입니다. 다만 `restore-keys` 폴백으로 오래된 캐시가 복원되었다면 1.4.0이 쓰였을 수 있는데, 그러면 빌드가 성공했어야 하므로 이 가설은 약합니다.

**참고**: 에러 메시지의 `Error: Cannot find module`은 Node의 CJS 로더나 `require` 경로에서 나오는 형식입니다. 웹팩 빌드에서는 보통 `Module not found`, Node에서는 `ERR_PACKAGE_PATH_NOT_EXPORTED`로 나옵니다. 따라서 **전체 스택 트레이스를 확인해서 어느 단계(Next.js 웹팩, Node 스크립트, 테스트 러너 등)에서 실패했는지 먼저 특정해야 합니다.**

## 확인 방법

1. CI 로그에서 전체 스택 트레이스와 실패 단계를 확인합니다.
2. 로컬에서 `rm -rf node_modules && npm ci`로 깨끗이 설치한 뒤 2.0.0 기준으로 빌드합니다. 이것이 로컬 재현 테스트입니다.
3. `node_modules/@company/ui/package.json`의 `exports` 필드를 열어 `./button` 항목이 있는지 확인합니다.
4. `ls node_modules/@company/ui`로 `button` 파일이 실제로 어디 있는지 확인합니다.
5. Node 18과 20에서 `node -e "console.log(require.resolve('@company/ui/button'))"`를 각각 실행해 차이가 있는지 확인합니다.

## 수정 방안

- **앱 코드 수정 (권장)**: 2.0.0이 공식적으로 노출하는 경로(루트 `@company/ui`의 named export 또는 새 subpath)로 import를 바꿉니다.
- **라이브러리 수정**: `@company/ui` 쪽에서 `exports`에 `./button`을 추가합니다. 라이브러리를 우리 팀이 관리한다면 이 방법도 가능합니다.
- **임시 조치**: 빌드를 살려야 한다면 `@company/ui`를 1.4.0으로 되돌립니다. 근본 해결은 아닙니다.
- **Node 버전 정렬**: CI를 Node 20으로 맞춥니다. 로컬과 CI 환경을 일치시키는 것은 어떤 경우에도 좋은 방향입니다.

## PM을 위한 한 줄 정리

> 라이브러리 2.0.0 업그레이드(3일 전)에서 내부 경로 import 방식이 막혔습니다. 로컬은 업그레이드 전 패키지를 계속 쓰고 있어서 문제가 드러나지 않았고, CI에서만 새 패키지가 설치되어 실패합니다. 수정은 import 경로 변경이 중심이며, 확인 후 반영 예정입니다.
