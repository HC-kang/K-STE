가장 유력한 원인은 로컬이 아직 `@company/ui` 1.4.0을 쓰고, CI(자동 빌드 서버)가 2.0.0을 설치해서 빌드한다는 점입니다. 이 내용은 추론이며, 아직 직접 검증하지 않았습니다.

## 확인된 사실

- 빌드는 CI(GitHub Actions)에서만 실패하고, 로컬 빌드는 성공합니다.
- 에러는 `Error: Cannot find module '@company/ui/button'`입니다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0 패키지에는 `exports` 필드가 추가됐습니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치한 것입니다.

## 추론

`exports` 필드는 패키지가 외부에 공개하는 파일 경로의 목록입니다. 이 필드가 있으면 목록에 없는 경로는 import할 수 없습니다. 1.4.0에는 이 필드가 없었으므로 `@company/ui/button`처럼 패키지 안의 파일을 직접 가리키는 import가 동작했을 것입니다.

로컬 `node_modules`는 업그레이드 전에 설치했습니다. 그래서 로컬에는 1.4.0이 남아 있을 가능성이 높습니다. 이 경우 로컬 빌드는 옛 버전으로 성공합니다.

CI 캐시 키는 `package-lock.json`의 해시입니다. 업그레이드로 lock 파일이 바뀌었다면 캐시가 맞지 않아 CI가 2.0.0을 새로 설치합니다. 2.0.0의 `exports`에 `./button`이 없거나 경로가 다르면, 이때 `@company/ui/button`을 찾지 못합니다.

Node 18과 20의 차이도 후보입니다. 하지만 위 추론이 맞다면 로컬을 Node 18로 바꿔도 같은 오류는 나지 않아야 합니다. 이 부분은 검증하지 않았습니다.

## 미확인

- 업그레이드 때 바뀐 `package-lock.json`을 커밋했는지 모릅니다.
- 2.0.0의 `exports`에 `./button`이 있는지 모릅니다.
- 로컬에 설치된 `@company/ui`의 실제 버전을 모릅니다.

## 검증 순서

1. 로컬에서 `npm ls @company/ui`를 실행해서 설치된 버전을 보십시오. 1.4.0이 나오면 추론이 맞습니다.
2. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드하십시오. CI와 같은 오류가 나면 원인은 2.0.0입니다.
3. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 보십시오.
4. 2번에서 오류가 나지 않으면 로컬을 Node 18로 바꿔서 같은 빌드를 다시 실행하십시오. 이때 Node 버전이 원인인지 판단할 수 있습니다.

## 수정 방향

3번에서 `./button`이 없으면 두 가지 방법이 있습니다.

- 2.0.0의 `exports`에 있는 경로로 import를 바꾸십시오.
- `@company/ui` 담당 팀에 `./button` 경로를 `exports`에 추가해 달라고 요청하십시오.

이 방향은 3번의 결과에 따라 달라집니다. 결과가 나오기 전에는 확정하지 마십시오.
