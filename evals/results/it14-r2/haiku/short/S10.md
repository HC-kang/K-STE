가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드에 `./button` 경로가 빠져 있어서, CI가 새로 설치한 2.0.0에서 `@company/ui/button`을 찾지 못하는 것입니다. 다만 이 가설은 아직 확인하지 않았습니다.

## 확인된 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0 패키지에 `exports` 필드(패키지가 외부에 공개하는 경로 목록을 정하는 설정)가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키(캐시를 찾을 때 쓰는 식별값)는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

## 원인 분석

`exports` 필드가 있으면 목록에 없는 경로는 `import`할 수 없습니다. 1.4.0에는 이 필드가 없어서 `@company/ui/button`이 파일 경로대로 해석되었습니다. 2.0.0에서는 공개 목록에 `./button`이 없으면 같은 import가 실패합니다.

로컬 빌드가 성공한 이유는 로컬 `node_modules`가 3일 전보다 먼저 설치되어 1.4.0이 그대로 남아 있을 가능성이 큽니다. 이 경우 로컬 빌드는 2.0.0을 검증하지 않은 것입니다.

**로컬 빌드 성공을 근거로 2.0.0이 정상이라고 판단하면 안 됩니다.**

CI 캐시는 키가 `package-lock.json` 해시이므로 lock 파일이 2.0.0으로 바뀐 뒤에는 새 캐시가 만들어지는 것이 정상입니다. 따라서 캐시가 원인이라고 단정하기는 어렵습니다. 다만 이전 키의 캐시를 대신 복원하는 설정(restore-keys)이 있으면 1.4.0이 담긴 옛 `node_modules`가 쓰일 수 있으므로 확인이 필요합니다.

Node 버전 차이만으로 이 실패를 설명하기는 어렵습니다. Node 18과 20 모두 `exports`를 지원하기 때문입니다. 다만 Node 18은 공식 지원이 종료된 버전이므로 별도로 올리는 방안을 검토할 수 있습니다.

## 가설 검증 방법

| 확인 항목 | 확인 방법 | 가설이 맞을 때 나타나는 결과 |
|---|---|---|
| 2.0.0의 공개 경로 | `node_modules/@company/ui/package.json`의 `exports` 확인 | `./button`이 없음 |
| 로컬 설치 버전 | 로컬에서 `npm ls @company/ui` 실행 | 1.4.0으로 표시됨 |
| CI 설치 버전 | CI 로그에서 설치된 버전 확인 | 2.0.0으로 표시됨 |
| CI 캐시 복원 | CI 로그의 캐시 적중(cache hit) 메시지와 restore-keys 설정 확인 | 이전 캐시가 복원됨 |
| Node 버전 영향 | CI를 Node 20으로 바꿔 실행 | 성공하면 Node 차이가 관련됨 |

## 해결 방향

1. `@company/ui` 관리 팀에 2.0.0의 `exports`에 `./button`을 추가해 달라고 요청하는 것을 권장합니다.
2. 앱의 import 경로를 공개된 경로로 바꾸는 방법도 있습니다.
3. 급하게 CI를 살려야 하면 `@company/ui`를 1.4.0으로 되돌리는(롤백, 이전 버전으로 되돌리기) 것도 방법입니다.

## 확인 필요

- CI에서 실패한 빌드의 전체 로그
- 로컬에서 `npm ls @company/ui`를 실행한 결과
- CI 캐시 설정 파일의 restore-keys 항목 유무
