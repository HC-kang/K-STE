원인은 `@company/ui` 2.0.0의 `exports` 필드가 `button` 하위 경로를 노출하지 않아서, `@company/ui/button`을 import하는 코드가 새로 설치되는 CI에서만 해석에 실패하는 것으로 보입니다. 이 내용은 아직 확인되지 않은 추론입니다.

사실로 확인된 내용은 다음과 같습니다. 2.0.0에 `exports` 필드가 추가되었고, CI 캐시 키는 `package-lock.json` 해시이며, 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다. 이 세 가지를 합치면 다음과 같이 설명됩니다.

로컬 `node_modules`에는 1.4.0이 남아 있을 가능성이 높습니다. 1.4.0에는 `exports` 필드가 없으므로 `@company/ui/button`이 파일 경로로 그대로 해석되어 로컬 빌드가 성공합니다. 반면 2.0.0 업그레이드로 `package-lock.json`이 바뀌면 캐시 키도 바뀌어 CI가 새로 설치하고, 이때 2.0.0을 받아 `exports` 제한을 적용받습니다.

Node 버전 차이는 이 에러의 원인으로 보기 어렵습니다. Node 18과 20 모두 `exports` 필드를 지원하기 때문입니다. 다만 재현 실험으로 배제해야 합니다.

가설을 검증하려면 다음 항목을 확인하십시오.

- 2.0.0 패키지의 `package.json`에서 `exports`에 `./button` 경로가 있는지 확인합니다. 없다면 이 가설이 맞습니다.
- CI 로그에서 `npm ls @company/ui`의 결과로 실제 설치된 버전을 확인합니다.
- 로컬에서 `npm ls @company/ui`로 설치된 버전이 1.4.0인지 확인합니다.
- 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드하여 에러가 재현되는지 확인합니다.
- Node 18로 같은 빌드를 실행하여 재현되는지 확인합니다. 재현되지 않으면 Node 버전은 원인에서 제외됩니다.

수정 방향은 세 가지입니다. 첫째, import 경로를 2.0.0의 `exports`가 허용하는 경로로 바꿉니다. 둘째, `@company/ui`의 `exports`에 `./button`을 추가하도록 패키지 담당자와 협의합니다. 셋째, 2.0.0에서 필요한 기능이 없다면 1.4.0으로 되돌립니다. PM은 2.0.0 업그레이드 목적과 되돌림 가능 여부를 기준으로 방향을 고르면 됩니다.

먼저 2.0.0 패키지의 `package.json`에서 `exports` 항목을 확인하십시오.
