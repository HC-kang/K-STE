**가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드가 `@company/ui/button` 같은 하위 경로 import를 막는 것입니다.** 로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 아직 1.4.0일 가능성이 크기 때문입니다. 이 결론은 제공된 정보에서 추론한 것이며, 패키지 파일이나 설치 결과는 아직 직접 확인하지 않았습니다.

## 원인 추론

로컬 `node_modules`는 3일 전보다 먼저 설치되었으므로 1.4.0 상태로 남아 있을 가능성이 큽니다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`이 파일 경로대로 해석됩니다. 반면 CI는 `package-lock.json` 해시가 바뀌면서 캐시가 새로 만들어지고, 2.0.0을 새로 설치합니다. 2.0.0의 `exports` 맵에 `./button` 항목이 없다면 같은 import가 실패합니다.

Node 버전 차이는 원인일 가능성이 낮습니다. Node 18과 Node 20은 모두 `exports` 필드를 지원합니다. 다만 Node 18은 2025년 4월에 지원이 끝난 버전이므로 별도로 정리할 필요가 있습니다.

| 구분 | 로컬 | CI |
|---|---|---|
| `@company/ui` 버전 | 1.4.0으로 추정 (3일 전 이전에 설치됨) | 2.0.0으로 추정 (lock 변경으로 새로 설치됨) |
| `exports` 필드 | 없음 | 있음 |
| Node 버전 | 20 | 18 |
| 빌드 결과 | 성공 | 실패 |

## 확인이 필요한 점

에러 메시지 형식이 원인 위치를 가르는 단서가 될 수 있습니다. Node의 `require`는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`를 내고, webpack은 `Module not found`를 냅니다. `Cannot find module`은 두 경우와 다르므로, 에러가 나온 단계를 확인해야 합니다. 확인 필요: 에러가 `next build` 로그에서 나왔는지, `next.config.js`처럼 Node로 직접 실행되는 파일에서 나왔는지 확인해야 합니다.

다른 원인도 배제하지 않았습니다. 확인 필요: CI에서 `npm ci`가 오류 없이 끝났는지, 그리고 `@company/ui`가 `dependencies`에 있는지 확인해야 합니다. 2.0.0의 `engines`가 Node 20 이상을 요구하면 CI의 Node 18에서 경고가 나올 수 있습니다. 2.0.0이 ESM 전용 패키지라면 CommonJS 로딩 단계에서 다른 오류가 납니다.

캐시 설정도 확인해야 합니다. `node_modules`를 캐시하고 설치 단계를 건너뛰는 구성이라면, `restore-keys`로 이전 캐시가 복원되어 1.4.0이 쓰일 수 있습니다. 확인 필요: 워크플로 파일의 `actions/cache` 설정입니다.

## 확인 순서

1. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드합니다. 같은 에러가 나오면 로컬에서 재현된 것이므로 원인이 `exports`인지 바로 검증할 수 있습니다.
2. `npm ls @company/ui`로 로컬과 CI에 설치된 실제 버전을 비교합니다.
3. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 확인합니다.
4. 2.0.0의 `engines` 필드와 모듈 형식(ESM 또는 CJS)을 확인합니다.

## 수정 방향

수정 방법은 세 가지로 볼 수 있습니다. 호출하는 쪽에서는 2.0.0이 노출하는 경로로 import를 바꾸는 것이 가장 직접적입니다. 패키지 쪽에서는 `./button` 하위 경로를 `exports`에 추가하는 방법이 있으며, 이는 `@company/ui` 유지보수 담당자가 처리해야 합니다. 빠르게 빌드를 복구하려면 1.4.0으로 되돌리는 것을 권장합니다. 다만 이 방법은 2.0.0의 변경 사항을 나중에 다시 적용해야 한다는 점을 감안해야 합니다.
