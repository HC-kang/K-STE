가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드로 보이며, 이 판단은 추론이고 아직 확인하지 않았습니다.

## 사실

- CI 빌드만 `Error: Cannot find module '@company/ui/button'`으로 실패하고, 로컬 빌드는 성공합니다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0 패키지에는 `exports` 필드가 추가됐습니다. `exports` 필드는 패키지가 외부에 공개할 파일 경로를 직접 정하는 설정입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치한 것입니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.

## 추론

패키지에 `exports` 필드가 생기면, 그 필드에 적힌 경로만 import할 수 있습니다. 2.0.0의 `exports`에 `./button`이 없으면 `@company/ui/button`을 찾을 수 없다는 오류가 납니다.

로컬은 2.0.0 이전에 설치한 `node_modules`를 그대로 쓰고 있을 가능성이 높습니다. 그렇다면 로컬에는 `exports`가 없는 1.4.0이 남아 있어서 `@company/ui/button`이 계속 열립니다.

CI는 2.0.0을 새로 설치하므로 같은 import가 막힙니다. 그래서 같은 코드가 로컬에서는 성공하고 CI에서는 실패합니다.

## 가능성이 낮은 후보

- Node 버전: `exports` 필드는 Node 18과 20이 모두 지원하는 기능입니다. 그래서 버전 차이가 주원인일 가능성은 낮습니다. 다만 아직 배제하지 않았습니다.
- CI 캐시: 캐시 키가 `package-lock.json`의 해시이므로, 업그레이드 커밋에서 lockfile이 바뀌었다면 캐시가 새로 만들어졌을 것입니다. 그래서 오래된 캐시가 원인일 가능성은 낮습니다. 업그레이드 커밋에 lockfile 변경이 포함됐는지는 확인하지 않았습니다.

## 검증 단계

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 2.0.0인지 본다.
2. `node_modules/@company/ui/package.json`의 `exports` 필드에 `./button`이 있는지 본다.
3. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드한다. 이때 로컬 빌드가 CI와 같은 오류로 실패하면 위 추론이 맞다.
4. 3번 후에도 결과가 CI와 다르면, Node 18로 같은 절차를 반복해 Node 버전 영향을 본다.

## 수정 방향

원인이 `exports` 누락으로 확인되면 방법은 두 가지입니다. 하나는 앱의 import를 2.0.0의 `exports`에 있는 경로로 바꾸는 것입니다. 다른 하나는 `@company/ui` 담당자에게 `./button` 경로를 `exports`에 추가해 달라고 요청하는 것입니다. 어느 쪽이 맞는지는 2.0.0이 `button` 경로를 의도적으로 없앴는지에 달려 있고, 이 정보는 아직 없습니다.

확인 필요: 2.0.0의 `exports`가 `./button`을 의도적으로 공개하지 않는지, 실수로 빠뜨렸는지.
