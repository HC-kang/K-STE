가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드에 `./button` 경로가 없는 것입니다. 로컬은 업그레이드 전에 설치한 1.4.0을 그대로 쓰고 있어서 이 문제가 드러나지 않았다고 추론합니다. 아직 명령을 실행해 확인하지 않았으므로 아래 내용은 주신 정보에서 도출한 추론입니다.

**로컬 빌드 성공은 2.0.0에서 검증한 결과가 아닐 수 있습니다.**

## 확인된 사실

- CI(GitHub Actions) 빌드만 실패하고 로컬 빌드는 성공합니다.
- 에러는 `Cannot find module '@company/ui/button'`입니다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0 패키지에 `exports` 필드가 추가됐습니다. `exports`는 패키지가 외부에 공개할 파일 경로를 제한하는 설정입니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`(설치할 버전을 고정하는 파일)의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치했습니다.

## 추론

1. 로컬 `node_modules`는 업그레이드 전에 설치했으므로 1.4.0이 남아 있을 가능성이 높습니다. 1.4.0에는 `exports`가 없어서 `@company/ui/button`이 파일 경로로 그대로 열립니다.
2. CI는 의존성을 새로 설치하므로 2.0.0을 받습니다. 2.0.0에 `exports`가 생겼으므로 Node와 번들러(빌드 도구)는 `exports`에 적힌 경로만 허용합니다.
3. `exports`에 `./button`이 없으면 `@company/ui/button`은 파일이 있어도 찾을 수 없는 경로가 되고, 이때 "Cannot find module" 에러가 납니다.
4. Node 18도 `exports`를 지원하므로 Node 버전 차이만으로는 이 현상을 설명하기 어렵습니다.
5. 업그레이드 때 `package-lock.json`이 바뀌었다면 캐시 키도 바뀌어 CI는 오래된 캐시를 쓰지 않습니다. lock 파일이 실제로 커밋됐는지는 확인하지 못했습니다.

## 원인 후보

| 후보 | 가능성 | 근거 |
|---|---|---|
| 2.0.0 `exports`에 `./button`이 없거나 경로 이름이 바뀜 | 높음 | 업그레이드 시점, `exports` 추가, 로컬과 CI의 설치 시점 차이가 모두 맞습니다. |
| `exports`에 `./button`이 있지만 `import`/`require` 조건이 빌드 방식과 맞지 않음 | 중간 | 같은 에러 문구가 나올 수 있어서 `exports` 내용을 봐야 구분됩니다. |
| Node 18과 20의 차이 | 낮음 | 두 버전 모두 `exports`를 지원합니다. |
| CI 캐시가 오래됨 | 낮음 | lock 파일이 바뀌었다면 캐시 키도 바뀝니다. |

## 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다. 1.4.0이면 로컬이 업그레이드를 반영하지 않았다는 추론이 맞습니다.
2. 로컬에서 `rm -rf node_modules && npm ci`로 재설치한 뒤 빌드합니다. 같은 에러가 나면 원인이 의존성 버전이라는 점이 확정됩니다.
3. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 봅니다. 있으면 `import`/`require` 조건도 함께 봅니다.
4. `./button`이 없으면 코드의 import를 `exports`가 공개한 경로로 바꾸거나, 패키지 담당자에게 `./button` 공개를 요청합니다. 어느 쪽을 택할지는 2.0.0에서 경로를 바꾼 의도에 따라 정해야 합니다.

확인 필요: 2.0.0에서 `./button` 경로를 의도적으로 없앴는지, 누락인지는 패키지 담당자에게 확인해야 합니다.
