원인은 아직 확정되지 않았다. 가장 유력한 가설은 `@company/ui` 2.0.0에 추가된 `exports` 필드 때문에 `@company/ui/button` 같은 하위 경로 import가 CI에서 막힌다는 것이다. 로컬은 업그레이드 전에 설치된 1.4.0을 계속 쓰고 있을 가능성이 커서 성공하는 것으로 보인다.

## 확인된 사실

- 빌드 실패는 CI(GitHub Actions, Node 18)에서만 발생한다.
- 로컬(Node 20) 빌드는 성공한다.
- 에러 메시지는 `Cannot find module '@company/ui/button'`이다.
- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0부터 패키지에 `exports` 필드가 있다.
- CI 캐시 키는 `package-lock.json`의 해시다.
- 로컬 `node_modules`는 업그레이드 3일 전 이전에 설치되었다.

## 추론

`exports` 필드가 있는 패키지는 그 필드에 적힌 경로만 외부에서 import할 수 있다. 2.0.0에서 이 필드가 추가되었으므로 1.4.0에는 이런 제한이 없었다고 볼 수 있다. 로컬 `node_modules`에 1.4.0이 남아 있다면 `@company/ui/button`이 그대로 찾아져 로컬 빌드가 성공한다. `package-lock.json`이 2.0.0을 가리키면 CI는 새로 설치하면서 2.0.0을 받는다. 그 결과 CI에서만 `@company/ui/button` 경로가 막힌다.

이 가설에는 맞지 않는 부분도 있다. `Cannot find module`은 Node의 일반적인 모듈 해석 실패 메시지이고, `exports`에 막힌 경로는 Node에서 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`로 나온다. 다른 도구가 같은 문구를 낼 수도 있으므로, 이 에러가 Node 런타임(예: `next.config.js`나 Node 스크립트)에서 나왔는지 번들러에서 나왔는지 확인 필요가 있다. Node 18과 20은 모두 `exports`를 지원한다. 그래서 Node 버전 차이만으로는 이 에러를 설명하기 어렵다. 다만 Next.js와 Node 버전 조합은 확인하지 않았으므로 배제하지 않는다.

## 확인 방법

- CI 로그에서 에러가 나온 단계와 전체 스택 트레이스를 확인한다.
- CI에서 `npm ls @company/ui`를 실행해 실제 설치된 버전을 확인한다.
- 로컬에서 `npm ls @company/ui`를 실행해 1.4.0이 남아 있는지 확인한다.
- `@company/ui` 2.0.0의 `package.json`에서 `exports` 필드에 `button` 경로가 있는지 확인한다.
- Node 18 환경에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드해 재현한다.
- `package-lock.json`이 2.0.0을 가리키는지, 그 변경이 커밋되었는지 확인한다.
- CI 캐시가 오래된 1.4.0 설치본을 복원하고 있지 않은지 CI 로그로 확인한다.

## 해결 방향

- 빌드 대상 코드의 import 경로를 2.0.0 `exports`에 정의된 공개 경로로 바꾸는 방법을 권장한다.
- `@company/ui` 쪽에 `button` 경로 export 추가를 요청하는 방법도 있다.
- 원인이 확정되기 전에는 CI의 Node 버전을 20으로 바꾸는 방법을 권장하지 않는다. 원인과 무관할 가능성이 크기 때문이다.

## PM 참고

- 확정된 내용은 실패 위치가 CI에만 있고 로컬은 성공한다는 점이다.
- 미확정 내용은 원인, 그리고 CI 실패가 배포를 막고 있는지 여부다. 확인 필요: 제공된 정보에는 배포 영향이 없다.
- 결정이 필요한 사항은 2.0.0을 유지하며 import 경로를 수정할지, `@company/ui` 측 export 추가를 기다릴지, 1.4.0으로 되돌릴지다.
