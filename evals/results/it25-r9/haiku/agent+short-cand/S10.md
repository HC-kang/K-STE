CI에서만 빌드가 실패하는 원인은 `@company/ui` 2.0.0의 `exports` 필드 추가로 보인다. 로컬은 업그레이드 전에 설치한 1.4.0을 계속 쓰고 있어서 같은 문제가 드러나지 않는다. 이 분석은 전달받은 정보만 근거로 하며, 코드와 패키지 파일은 직접 확인하지 않았다.

## 확인된 사실

- 에러는 `Cannot find module '@company/ui/button'`이다.
- `@company/ui`는 3일 전에 1.4.0에서 2.0.0으로 올라갔다.
- 2.0.0에는 `exports` 필드가 추가됐다.
- CI는 Node 18을, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`의 해시다.
- 로컬 `node_modules`는 업그레이드 3일 전에 설치됐다.

## 추론

1. 로컬 `node_modules`에는 아직 1.4.0이 들어 있다. 다시 설치하지 않았다면 로컬 빌드는 2.0.0을 전혀 검증하지 않은 상태다.
2. 1.4.0에 `exports` 필드가 없었다면 `@company/ui/button` 같은 하위 경로 import가 제한 없이 동작했다. 그래서 로컬 빌드는 성공한다.
3. 2.0.0에 `exports` 필드가 생기면 Node와 번들러는 `exports`에 적힌 경로만 허용한다. 적히지 않은 `./button` 경로는 찾지 못하고, 이 에러가 그 결과로 보인다.
4. CI는 lock 파일 해시가 바뀌어 캐시를 새로 만들고 2.0.0을 설치한다. 그래서 CI에서만 실패한다.
5. Node 18과 20의 차이는 이 에러의 직접 원인으로 보기 어렵다. 두 버전 모두 `exports` 필드를 지원하기 때문이다.

## 미확인

- 2.0.0의 `exports` 맵에 `button` 경로가 있는지 모른다. 이 항목이 없다면 추론 1-3이 맞다.
- CI 로그에서 실제로 설치된 버전이 2.0.0인지 모른다.
- CI 캐시가 hit였는지 miss였는지 모른다.
- Node 18에서 2.0.0 패키지가 다르게 동작하는지 모른다.

## 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인한다. 1.4.0이 나오면 추론 1이 맞다.
2. `node_modules/@company/ui/package.json`을 열어 `exports` 필드에 `button` 경로가 있는지 본다.
3. CI 로그에서 `npm ci` 또는 `npm install` 단계의 설치 결과를 확인한다.
4. 로컬에서 `rm -rf node_modules && npm ci`로 2.0.0을 새로 설치한 뒤 Node 18로 빌드해 같은 에러가 나는지 재현한다.

## 조치 방안

| 방법 | 내용 | 적합한 경우 |
| --- | --- | --- |
| import 경로 수정 | 2.0.0 `exports`에 있는 경로로 바꾼다 | 2.0.0 문서나 `exports`에 대체 경로가 있을 때 |
| 1.4.0 고정 | `package.json`을 1.4.0으로 되돌린다 | 2.0.0 기능이 당장 필요하지 않을 때 |
| 메인테이너 요청 | `exports`에 `button` 경로 추가를 요청한다 | 경로 제외가 의도적인지 불분명할 때 |

1번을 먼저 검토하는 것을 권장한다. 2.0.0 기능이 급하지 않다면 2번으로 CI를 즉시 복구하고, 이후 1번으로 옮겨 간다.

재발 방지를 위해 로컬과 CI가 같은 Node 버전과 같은 설치 상태를 쓰도록 맞추는 것을 권장한다. 현재 캐시 키에는 Node 버전이 포함되지 않으므로, 캐시 키에 Node 버전을 추가하는 것도 검토해야 한다.
