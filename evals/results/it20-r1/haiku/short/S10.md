가장 유력한 원인은 로컬과 CI가 서로 다른 버전의 `@company/ui`를 쓰고 있다는 것입니다. 이 내용은 추론이며, 아직 어떤 명령으로도 확인하지 않았습니다.

### 확인된 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에 `exports` 필드(패키지가 외부에 공개할 파일 경로를 정하는 설정)가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키(저장된 의존성을 재사용할지 정하는 기준값)는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`(패키지가 설치되는 로컬 폴더)는 3일 전보다 먼저 설치되었습니다.

### 추론: 가장 가능성 높은 경로

2.0.0의 `exports`에 `./button` 경로가 없거나 이름이 다르면, `@company/ui/button` import는 실패합니다. 로컬 `node_modules`에는 아직 제한이 없는 1.4.0이 남아 있을 가능성이 있어서 빌드가 성공합니다. CI는 lock 해시가 바뀌면 캐시를 버리고 새로 설치하므로 2.0.0을 받아 실패합니다. 이 경로가 맞으려면 lock 파일이 2.0.0으로 갱신되어 커밋되어 있어야 하며, 이는 확인이 필요합니다.

| 항목 | 로컬 | CI |
|---|---|---|
| `@company/ui` 버전 | 1.4.0으로 추정 (미확인) | 2.0.0으로 추정 (미확인) |
| 설치 시점 | 3일 전 이전 | 캐시 미스 시 새로 설치 (미확인) |
| Node 버전 | 20 | 18 |
| 파일 이름 대소문자 | macOS는 기본적으로 구분하지 않음 | Linux는 구분함 |

### 다른 후보 원인

- 파일 이름 대소문자: 로컬은 macOS라서 `Button.tsx`와 `button.tsx`를 같은 파일로 취급합니다. Linux CI는 이를 다른 파일로 취급하므로, 2.0.0과 관계없이 실패할 수 있습니다.
- Node 버전: Node 18과 20은 모두 `exports`를 지원하므로, Node 버전 차이만으로 실패할 가능성은 낮습니다. 다만 Next.js나 패키지 조건(conditions) 해석에서 차이가 나는지는 확인이 필요합니다.
- 오래된 캐시: 캐시 키가 lock 해시이므로 오래된 `node_modules`가 복원됐을 가능성은 낮습니다. 그래도 lock 파일이 실제로 갱신되어 커밋되었는지는 확인해야 합니다.

### 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. CI 로그에 같은 명령을 추가해 CI가 설치한 버전을 확인합니다.
3. `node_modules/@company/ui/package.json`의 `exports` 항목에 `./button`이 있는지 확인합니다.
4. `nvm use 18`로 Node 18 환경에서 로컬 빌드를 재현합니다.
5. `git ls-files`로 import 경로와 실제 파일 이름의 대소문자가 일치하는지 비교합니다.

확인 결과로 1번과 2번의 버전이 다르고 3번에 `./button`이 없다면, 원인은 2.0.0의 `exports` 변경으로 확정됩니다. 버전이 같다면 4번과 5번의 결과를 기준으로 다른 원인을 찾아야 합니다.
