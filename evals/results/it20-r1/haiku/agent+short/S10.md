CI 빌드 실패의 가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드가 `button` 하위 경로를 열어 두지 않은 것입니다. 패키지의 `exports` 내용은 아직 확인하지 않았으므로 이는 추론입니다. 이 정리는 제공해 주신 정보만 근거로 하며, 저장소와 패키지 코드는 열어 보지 않았습니다.

## 원인 분석

Node는 `exports` 필드가 있는 패키지에서 명시되지 않은 경로를 외부 코드가 가져가지 못하도록 막습니다. 1.4.0에는 `exports`가 없어서 `@company/ui/button`이 패키지 안의 파일 경로로 그대로 해석되었습니다. 2.0.0에서 `exports`가 추가되자 같은 import가 막혔을 가능성이 큽니다. 에러 문구도 Node의 기본 메시지와 다르므로, 빌드 도구(Next.js/webpack)가 같은 원인을 다른 문구로 표시한 것일 수 있습니다.

Node 18과 20은 모두 `exports`를 지원합니다. 따라서 Node 버전 차이만으로 이 에러가 생긴다고 볼 근거는 제공된 정보에 없습니다.

CI 캐시 키가 `package-lock.json` 해시이므로, lockfile이 2.0.0 변경과 함께 바뀌었다면 CI는 캐시를 쓰지 않고 2.0.0을 새로 설치합니다. CI가 실패한다는 사실과 맞아떨어집니다. 확인 필요: 이번 변경에서 lockfile이 실제로 바뀌었는지 PR diff에서 봐야 합니다.

## 로컬 빌드가 성공하는 이유

로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다. 따라서 `package.json`만 2.0.0으로 올렸고 로컬에서 다시 설치하지 않았다면, 로컬에는 1.4.0이 그대로 남아 있습니다. 1.4.0에는 `exports`가 없으므로 import가 통과하고, 로컬 빌드는 2.0.0 문제를 재현하지 않습니다. 이 추론은 로컬에서 `npm ls @company/ui`를 실행해 버전을 보면 확정됩니다.

## 검증 순서

1. CI 로그에 `npm ls @company/ui` 출력을 추가해 CI가 실제로 설치한 버전을 출력합니다.
2. 2.0.0 패키지의 `package.json`에서 `exports` 항목을 열어 `./button` 또는 `./*` 항목이 있는지 봅니다.
3. 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치한 뒤 Node 20으로 빌드합니다. 여기서 실패하면 패키지 변경이 원인일 가능성이 크게 올라갑니다.
4. 같은 방식으로 Node 18에서도 빌드해 Node 버전이 원인이 아님을 확인합니다.

## 수정 방향

| 방법 | 내용 | 주의할 점 |
|---|---|---|
| import 경로 변경 | 2.0.0의 `exports`가 허용하는 경로로 import를 바꿉니다. | 2.0.0 문서나 `exports` 항목에서 새 경로를 먼저 찾아야 합니다. |
| 패키지 측 수정 요청 | `@company/ui` 담당자에게 `./button` 경로 추가를 요청합니다. | 패키지 배포 일정에 따라 시간이 걸립니다. |
| 임시 롤백 | `@company/ui`를 1.4.0으로 되돌립니다. | 2.0.0에서 바뀐 기능을 받지 못합니다. |

권장하는 순서는 검증 3단계로 원인을 확정한 뒤, import 경로를 바꾸는 것입니다. 배포가 급하면 임시 롤백으로 CI를 먼저 살리고, 경로 수정을 이어서 진행해도 됩니다.

PM에게 전달할 한 줄 요약은 다음과 같습니다. CI 빌드는 `@company/ui` 2.0.0의 `exports` 변경 때문에 실패하고 있으며, 로컬은 이전 버전이 설치되어 있어 성공하고 있습니다. 원인은 검증 중이며, 수정은 import 경로 변경 또는 임시 롤백으로 진행합니다.
