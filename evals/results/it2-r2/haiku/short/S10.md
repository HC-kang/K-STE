가장 유력한 원인은 2.0.0의 `exports` 필드가 `@company/ui/button` 하위 경로를 노출하지 않는 것입니다. 로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 3일 전에 설치된 1.4.0을 그대로 쓰고 있기 때문일 가능성이 높습니다. 이 가설은 아직 확인하지 않았습니다.

| 구분 | 내용 |
|---|---|
| 확인된 사실 | CI는 Node 18, 로컬은 Node 20을 쓴다. CI 캐시 키는 `package-lock.json` 해시다. 2.0.0에서 `exports` 필드가 추가되었다. 로컬 `node_modules`는 업그레이드 이전에 설치되었다. |
| 추론 | `exports` 필드가 있으면 Node와 번들러는 명시된 경로만 가져올 수 있다. 1.4.0에는 이 필드가 없어서 `@company/ui/button`이 파일 경로로 해석되었을 것이다. 로컬은 1.4.0을 쓰므로 성공하고, CI는 2.0.0을 설치하므로 실패한다. |
| 추론 (약함) | Node 버전 차이만으로 `exports` 해석이 달라지지는 않는다. Node 18도 `exports` 필드를 지원한다. 다만 2.0.0이 ESM 전용 패키지라면 Node 18에서 별도 문제가 생길 수 있다. |
| 확인 필요 | 2.0.0의 `exports` 맵에 `./button` 또는 `./*` 항목이 있는지 확인되지 않았다. 로컬에 실제로 1.4.0이 설치되어 있는지도 확인되지 않았다. CI가 실제로 2.0.0을 설치했는지도 확인되지 않았다. |

캐시 문제일 가능성은 낮습니다. 캐시 키가 lock 파일 해시이므로 lock 파일이 바뀌면 캐시가 무효화됩니다. 다만 lock 파일이 2.0.0으로 갱신되어 커밋되었는지는 확인해야 합니다. lock 파일이 1.4.0 상태로 남아 있다면 CI도 1.4.0을 설치했을 것이고, 이 경우 원인은 다른 곳에 있습니다.

원인을 좁히려면 다음 순서로 확인하는 것이 좋습니다.

1. 로컬 `node_modules/@company/ui/package.json`의 `version` 값을 확인한다. 1.4.0이면 로컬 성공의 이유가 설명된다.
2. 2.0.0 패키지의 `package.json`에서 `exports` 필드를 열어 `./button` 경로가 있는지 확인한다.
3. CI 로그의 설치 단계에서 `@company/ui`의 실제 설치 버전을 확인한다.
4. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드해 2.0.0 기준으로 재현한다.
5. 2.0.0 변경 내역(changelog)에서 import 경로 변경이 breaking change로 명시되었는지 확인한다.

확인이 끝나면 조치 방향은 두 가지입니다. 2.0.0 maintainer에게 `./button` 경로 노출을 요청하거나, 앱의 import 경로를 2.0.0이 공개한 경로로 바꾸는 것입니다. 당장 빌드를 살리려면 `@company/ui`를 1.4.0으로 되돌리는 방법도 있습니다.
