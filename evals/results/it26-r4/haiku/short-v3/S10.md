가장 유력한 원인은 로컬과 CI가 서로 다른 버전의 @company/ui를 쓰고 있다는 것이다. 이는 추론이며, 아직 설치된 버전을 직접 확인하지 않았다.

## 확인된 사실

- 빌드는 CI(GitHub Actions)에서만 실패하고, 로컬에서는 성공한다.
- 실패 메시지는 `Error: Cannot find module '@company/ui/button'`이다.
- @company/ui는 3일 전에 1.4.0에서 2.0.0으로 올라갔다.
- 2.0.0에는 exports 필드(패키지 외부에 공개할 경로 목록을 정하는 설정)가 새로 추가됐다.
- CI는 Node 18을, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 package-lock.json(설치 버전을 고정한 파일)의 해시다.
- 로컬 node_modules(설치된 패키지가 담기는 폴더)는 3일 전보다 먼저 설치됐다.

## 추론

- 로컬 node_modules에는 1.4.0이 들어 있을 가능성이 높다. 3일 전 이후에 다시 설치하지 않았다면 그렇다.
- 1.4.0에는 exports 필드가 없으므로 `@company/ui/button`처럼 파일 경로를 직접 가져오는 방식이 허용된다. 그래서 로컬 빌드는 성공한다.
- 2.0.0에서는 exports 목록에 없는 경로를 가져올 수 없다. 목록에 './button'이 없거나 이름이 바뀌었다면 CI 빌드가 이 에러로 실패한다.
- 락 파일이 바뀌었다면 캐시 키도 바뀌므로, CI는 새로 설치하면서 2.0.0을 받았을 가능성이 높다. 이는 CI 실패의 원인이라기보다 CI가 2.0.0을 쓰고 있다는 근거다.
- Node가 exports 규칙을 어기면 보통 ERR_PACKAGE_PATH_NOT_EXPORTED 에러를 낸다. 하지만 Cannot find module은 파일이 없을 때나 번들러(빌드 도구)의 해석 설정에서도 나온다. 그래서 에러 문구만으로 exports를 원인이라고 단정하지 않는다.
- Node 18과 20은 모두 exports를 지원한다. 그래서 Node 버전 차이가 주원인일 가능성은 낮다. 다만 두 버전의 해석 차이는 확인하지 않았으므로 배제하지 않는다.

## 확인이 필요한 항목

1. 로컬에서 설치된 버전을 `npm ls @company/ui`로 확인한다.
2. CI 로그의 설치 단계에서 @company/ui 버전을 확인한다. 로그에 버전이 나오지 않으면 빌드 단계 앞에 `npm ls @company/ui`를 추가한다.
3. 2.0.0의 exports 목록을 `npm view @company/ui@2.0.0 exports`로 확인한다. './button' 항목이 있는지 본다.
4. 프로젝트에서 `@company/ui/` 경로를 쓰는 import 위치를 `grep -rn --exclude-dir=node_modules "@company/ui/" .`로 찾는다.
5. CI 캐시 설정에서 캐시 대상이 node_modules인지 ~/.npm인지 확인한다. 접두사 일치로 이전 캐시를 복원하는 restore-keys 설정이 있는지도 본다.
6. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 Node 18 환경에서 빌드해 CI 조건을 재현한다.

## 해결 방향

- 2.0.0의 exports 루트에서 Button이 공개되어 있다면, import 경로를 `@company/ui`로 바꾸는 방법을 권장한다.
- exports에 './button'이 없다면 @company/ui 패키지 관리자에게 경로 추가를 요청한다.
- 수정이 늦어지면 @company/ui를 1.4.0으로 고정하는 임시 조치를 쓸 수 있다.

## PM 관점 요약

- CI 빌드가 실패하므로 CI 빌드를 통과해야 하는 배포는 막혀 있다.
- 로컬 개발 환경에는 당장 문제가 없다. 다만 로컬과 CI의 패키지 버전이 달라서 같은 문제를 로컬에서 놓칠 수 있다.
- 2.0.0은 주 버전이 올라간 변경이므로 호환성이 깨진 변경이 포함됐을 가능성이 있다.
- CI 실패가 처음 시작된 시점과 영향받는 브랜치 범위는 확인하지 않았다.
