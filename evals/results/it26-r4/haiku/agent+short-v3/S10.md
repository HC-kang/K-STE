# 2.0.0 업그레이드 후 CI 빌드 실패 원인 분석

현재 가장 유력한 원인은 `@company/ui` 2.0.0에서 추가된 `exports` 필드가 `@company/ui/button` 경로를 막거나 다른 파일로 바꾼 것이다. 이 결론은 추론이며 아직 확인되지 않았다.

## 현재 확인된 사실

CI(GitHub Actions)에서만 Next.js 빌드가 실패한다. 로컬 빌드는 성공한다. 실패 메시지는 `Error: Cannot find module '@company/ui/button'`이다. 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다. 2.0.0에는 `exports` 필드가 추가되었다. CI는 Node 18을, 로컬은 Node 20을 쓴다. CI 캐시 키는 `package-lock.json`의 해시이다. 로컬 `node_modules`는 3일 전보다 먼저 설치되었다.

## 원인 가설

### 가설 1: 2.0.0의 exports 변경이 `@company/ui/button` 해석을 깨뜨렸다 (가능성 높음)

1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`이 패키지 안의 파일 경로로 그대로 풀린다. 2.0.0에서는 `exports` 필드가 허용한 경로만 import할 수 있다. `./button` 경로가 목록에 없거나, 목록에 있어도 가리키는 파일이 바뀌었다면 같은 import가 실패한다.

다만 `Cannot find module` 문구는 exports 차단보다 파일이 실제로 없을 때 자주 나온다. 그러므로 메시지만으로 원인을 단정하지 않는다. 전체 스택 트레이스와 실패 단계(타입 검사, 번들링 중 어느 단계인지)를 확인 필요하다.

### 가설 2: 로컬 빌드가 성공하는 이유는 로컬 node_modules가 여전히 1.4.0이기 때문일 수 있다 (추론)

로컬 `node_modules`는 3일 전보다 먼저 설치되었다. `package.json`을 2.0.0으로 바꿔도 `npm install`을 다시 실행하지 않으면 `node_modules`에는 1.4.0이 남는다. 이 경우 로컬 빌드는 1.4.0으로 빌드하므로 성공한다.

이 가설이 맞으면 로컬 성공은 2.0.0이 정상이라는 근거가 되지 않는다. 확인 필요: 로컬 설치 버전이 1.4.0인지 확인해야 한다. 2.0.0이면 이 가설은 틀리며 다른 원인을 찾아야 한다.

### 가설 3: CI는 2.0.0을 설치했다 (추론)

lock 파일이 2.0.0으로 갱신되어 커밋되었다면 캐시 키 해시가 바뀐다. 그러면 CI는 캐시를 쓰지 않고 새로 설치하며 2.0.0을 받는다. 확인 필요: lock 파일 변경이 커밋에 포함되었는지, CI 로그에서 캐시 적중 여부와 설치된 버전이 무엇인지 확인해야 한다.

### 가설 4: Node 18과 Node 20의 차이 (가능성 낮음)

이 import 경로의 해석 규칙이 Node 18과 Node 20 사이에서 바뀐 것으로 알려져 있지 않다. 다만 Next.js는 webpack으로 번들링하므로 Node 버전보다 번들러 설정이 영향을 줄 수 있다. 확인 필요: 아래 표의 재현 실험으로 검증해야 한다.

## 검증 방법

| 확인 항목 | 방법 | 결과가 의미하는 것 |
| --- | --- | --- |
| 로컬 설치 버전 | `npm ls @company/ui` | 1.4.0이면 가설 2가 맞다 |
| 2.0.0 exports 내용 | `cat node_modules/@company/ui/package.json`에서 `exports` 확인 | `./button` 항목이 없거나 경로가 다르면 가설 1이 맞다 |
| CI 설치 버전 | CI 로그에서 설치된 버전 확인, 필요하면 `npm ls` 단계 추가 | 2.0.0이면 가설 3이 맞다 |
| CI 캐시 상태 | CI 로그에서 캐시 적중(hit) 또는 미적중(miss) 확인 | miss면 새로 설치되었음을 뜻한다 |
| lock 파일 변경 | 2.0.0 업그레이드 커밋의 `package-lock.json` 변경 확인 | 변경이 없으면 캐시 키 해석을 다시 해야 한다 |
| 영향 범위 | `grep -rn "@company/ui/" src` | 같은 방식으로 깨질 import가 몇 곳인지 알 수 있다 |
| Node 18 재현 | Node 18에서 `rm -rf node_modules && npm ci && npm run build` 실행 | 실패하면 Node 버전과 무관하게 재현된 것이다 |

가장 빠른 확인은 로컬에서 `rm -rf node_modules && npm ci && npm run build`를 실행하는 것이다. 이 명령은 lock 파일 기준으로 다시 설치하므로 로컬에서 CI와 같은 상태를 만든다. 로컬에서 실패하면 가설 2는 틀리고, 로컬에서도 실패하면 CI 환경 문제가 아니라 2.0.0 자체의 문제로 좁혀진다.

## 수정 방향

가설 1이 확인되면 다음 세 가지 선택지가 있다.

- 빌드 복구가 급하면 `@company/ui`를 1.4.0으로 되돌린다. 가장 빠르지만 2.0.0 전환이 미뤄진다.
- 2.0.0을 유지하려면 소비하는 코드의 import를 2.0.0 exports가 허용하는 경로로 바꾼다. 예를 들어 루트 `@company/ui`에서 가져오는 방식이 있다. 확인 필요: 2.0.0 루트 export에 `Button`이 있는지 확인해야 한다.
- 패키지 쪽에서 `./button` 경로를 `exports`에 추가하는 방법이 있다. 확인 필요: `@company/ui`의 관리 주체가 누구인지 확인해야 한다.

PM 관점에서는 1.4.0 롤백이 가장 빠른 복구 수단이다. 2.0.0 전환 일정을 유지해야 하면 import 수정 작업이 필요하다.

## 아직 확인되지 않은 것

- 2.0.0의 `exports` 필드 실제 내용
- 로컬과 CI에 설치된 실제 버전
- CI 로그의 전체 스택 트레이스와 실패 단계
- Node 18에서의 재현 여부
- lock 파일 변경 여부와 캐시 적중 여부
