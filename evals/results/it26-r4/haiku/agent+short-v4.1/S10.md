CI 실패의 가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드가 `@company/ui/button` 경로를 허용하지 않는 것입니다. 로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 업그레이드 전의 1.4.0을 그대로 쓰고 있기 때문으로 보입니다. 아직 확인하지 않은 사항이 있으므로 아래 확인 항목을 먼저 실행해야 합니다.

### 확인된 사실

- 3일 전 `@company/ui`가 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0 패키지에는 `exports` 필드가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

### 원인 분석 (추론)

`exports` 필드가 있으면 패키지가 외부에 공개하는 경로 목록이 정해집니다. 그 목록에 `./button`이 없거나 이름이 바뀌었다면, 그 경로를 import하는 코드는 해석에 실패합니다. 1.4.0에는 `exports`가 없으므로 파일 경로를 그대로 찾을 수 있었습니다.

환경별로 실제 설치되는 버전이 다릅니다.

- CI는 캐시 키가 `package-lock.json` 해시이므로, 업그레이드로 lockfile이 바뀌면 캐시가 새로 만들어집니다. 그래서 CI는 2.0.0을 새로 설치합니다.
- 로컬은 3일 전에 설치한 `node_modules`를 다시 설치하지 않았다면 1.4.0을 그대로 씁니다. 그래서 `exports` 제한을 받지 않고 빌드가 성공합니다.

따라서 로컬이 성공하는 이유는 Node 20이 아니라 설치된 버전 차이일 가능성이 큽니다. Node 18과 20은 모두 `exports`를 지원하므로 Node 버전만으로는 이 에러를 설명하기 어렵습니다. 다만 2.0.0이 Node 18을 지원하지 않는 `engines` 조건을 두었거나 ESM 전용으로 배포되었다면 Node 18에서만 실패할 수 있습니다. 이 부분은 확인 필요입니다.

### 확인 필요 항목

1. CI 로그에서 에러가 난 단계와 전체 스택을 확인합니다. 이 메시지는 Next.js 빌드가 보통 내는 `Module not found` 형식과 달라서, 어느 도구가 던진 에러인지부터 구분해야 합니다.
2. 로컬에서 `npm ls @company/ui`를 실행해 실제 설치 버전을 확인합니다. 1.4.0이 나오면 로컬은 업그레이드를 검증하지 않은 상태입니다.
3. `node_modules/@company/ui/package.json`의 `exports` 항목에 `./button`이 있는지 확인합니다.
4. 2.0.0의 `engines` 필드와 배포 형식(ESM 또는 CJS)을 확인합니다.
5. `package-lock.json`에 2.0.0이 기록되어 있는지 확인합니다.
6. CI 캐시 설정에 `restore-keys`가 있는지 확인합니다. 있으면 이전 캐시가 복원되었을 수 있습니다.

### 재현 및 조치

- 로컬에서 `rm -rf node_modules && npm ci`를 실행해 `package-lock.json` 기준으로 다시 설치합니다. 이후 로컬 빌드가 실패하면 원인이 확정됩니다.
- 원인이 확정되면 다음 중 하나를 선택합니다.
  - import 경로를 2.0.0 `exports`에 맞게 바꿉니다.
  - 패키지 관리자에게 `./button` 경로 추가를 요청합니다.
  - 임시로 `@company/ui`를 1.4.0에 고정합니다.
- CI의 Node 버전을 20으로 바꾸는 작업은 원인이 Node 버전과 관련 있다고 확인된 뒤에 검토합니다.

**주의:** 로컬에서 재현하지 않고 CI 설정만 바꾸면 같은 에러가 다른 환경에서 다시 발생할 수 있습니다.
