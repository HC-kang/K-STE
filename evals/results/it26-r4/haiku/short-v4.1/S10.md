가장 유력한 원인은 2.0.0에서 추가된 `exports` 필드(패키지가 외부에 공개할 경로 목록)가 `@company/ui/button` 같은 하위 경로 import를 막는 것입니다. 패키지 파일과 CI 로그는 직접 확인하지 않았으므로, 아래 내용은 추론입니다.

### 사실로 주어진 내용

- 3일 전 `@company/ui`가 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0에는 `exports` 필드가 추가됐습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`(설치할 패키지 버전을 고정한 파일)의 해시입니다.
- 로컬 `node_modules`는 업그레이드 전에 설치됐습니다.

### 추론: 실패 경로

`exports` 필드가 있으면 Node와 번들러(웹 코드를 묶는 도구)는 패키지가 명시한 경로만 가져오도록 허용합니다. 2.0.0의 `exports`에 `./button` 경로가 없다면 `@company/ui/button`은 해석되지 않습니다.

로컬 `node_modules`는 설치 후 다시 설치하지 않았다면 1.4.0 그대로 남아 있으므로 이 제한이 적용되지 않습니다. CI는 lock 파일이 2.0.0으로 갱신되어 커밋됐다면 캐시 키가 바뀌어 2.0.0을 새로 설치합니다. 그래서 CI에서만 실패합니다.

`Cannot find module`은 Node가 파일을 불러올 때 나오는 메시지입니다. 웹팩(webpack, 웹 빌드 도구) 단계에서는 보통 다른 문구가 나옵니다. 따라서 오류가 `next.config.js` 같은 설정 파일이나 스크립트에서 발생했을 가능성이 있습니다.

### 환경 차이 비교

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| @company/ui 버전 (추론) | 1.4.0 | 2.0.0 |
| exports 제한 적용 (추론) | 적용되지 않음 | 적용됨 |
| 캐시 | 기존 node_modules 유지 | 캐시 키 변경으로 새로 설치 |

Node 18도 `exports`를 지원하므로 Node 버전 차이만으로 이 오류가 날 가능성은 낮습니다. 다만 Node 18은 2025년 4월에 지원이 끝났으므로 CI의 Node 버전도 함께 올리는 것을 권장합니다.

### 확인 방법

1. CI 로그에서 오류가 난 파일과 스택 트레이스(오류가 발생한 호출 경로)를 확인합니다.
2. CI 빌드 단계에 `npm ls @company/ui`를 추가해 설치된 버전을 확인합니다.
3. 2.0.0 패키지의 `package.json`에서 `exports`에 `./button`이 있는지 확인합니다.
4. `git log -p package-lock.json`으로 lock 파일이 3일 전 커밋에서 함께 바뀌었는지 확인합니다.
5. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드하면 CI와 같은 조건이 재현되는지 확인할 수 있습니다.

### 해결 방향

- 패키지 관리 측에 2.0.0의 `exports`에 `./button` 경로를 추가하도록 요청하는 것을 권장합니다.
- 앱 코드에서는 하위 경로 import 대신 패키지 루트에서 가져오도록 바꾸는 것을 권장합니다. 루트에서 `Button`을 export하는지는 먼저 확인해야 합니다.
- 배포가 당장 막혀 있다면 `@company/ui`를 1.4.0으로 되돌리는 방법을 임시 조치로 해도 됩니다.
