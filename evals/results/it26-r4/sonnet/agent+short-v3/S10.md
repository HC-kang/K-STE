가장 유력한 원인은 로컬 `node_modules`에 `@company/ui` 1.4.0이 남아 있고 CI는 2.0.0을 설치해서, 2.0.0의 `exports` 필드 때문에 `@company/ui/button` 경로를 찾지 못하는 것입니다. 이 원인은 추론입니다.

`exports` 필드는 패키지가 외부에 공개하는 import 경로를 지정하는 `package.json` 항목입니다. `exports`가 없는 1.4.0에서는 `@company/ui/button`처럼 파일 경로로 직접 import할 수 있습니다. `exports`가 있는 2.0.0에서는 `exports`에 적힌 경로만 import할 수 있습니다. 2.0.0의 `exports`에 `./button`이 없는지는 아직 모릅니다.

로컬 빌드가 성공하는 이유도 같은 방식으로 설명됩니다. 로컬 `node_modules`는 3일 전 업그레이드보다 먼저 설치했으므로, 로컬은 1.4.0을 쓰고 있을 가능성이 큽니다. 이 경우 로컬 빌드는 업그레이드 이후 한 번도 2.0.0으로 실행되지 않았습니다.

나머지 두 단서는 원인일 가능성이 낮습니다.

- Node 버전: Node 18과 20은 모두 `exports` 필드를 지원합니다. 그래서 버전 차이는 주원인으로 보기 어렵습니다.
- CI 캐시: 캐시 키가 `package-lock.json`의 해시이므로, 업그레이드 때 lock 파일이 바뀌었다면 캐시도 새로 만들어집니다. 그래서 오래된 캐시가 원인일 가능성은 낮습니다. 업그레이드 커밋에 lock 파일이 포함됐는지는 확인 필요: 주어진 정보에 없습니다.

아래 순서로 검증하면 원인을 가릴 수 있습니다.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 봅니다. 1.4.0이면 추론이 맞을 가능성이 커집니다.
2. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드합니다. CI와 같은 오류가 나면 원인은 로컬과 CI의 설치 버전 차이입니다.
3. 2.0.0의 `package.json`에서 `exports`에 `./button`이 있는지 봅니다. 없으면 import 경로를 `exports`가 공개한 경로로 바꾸거나, `@company/ui` 쪽에서 `./button`을 `exports`에 추가해야 합니다. 어느 쪽을 택할지는 `@company/ui` 담당자와 정해야 합니다.

PM이 알아야 할 점은, 이 문제가 CI에서만 드러났을 뿐 업그레이드 자체에서 생긴 문제로 보인다는 것입니다. 2.0.0을 쓰는 다른 빌드와 배포도 같은 오류가 날 수 있습니다.
