CI 빌드 실패의 원인은 아직 확정되지 않았습니다. 가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드가 `button` 경로를 노출하지 않는 것으로 보입니다. 로컬에는 3일 전에 설치한 1.4.0이 남아 있어서 빌드가 성공하는 것으로 추정됩니다. 배포에 영향을 주는지는 확인 필요합니다.

## 확인된 사실

- `@company/ui`를 3일 전에 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.
- 보고된 에러는 `Error: Cannot find module '@company/ui/button'`입니다.

## 추론

Node는 `exports` 필드가 있으면 패키지 바깥에서 가져올 수 있는 경로를 `exports`에 적힌 것으로 한정합니다. 2.0.0의 `exports`에 `./button`이 없으면 이 import가 실패합니다. 1.4.0에는 `exports`가 없어서 같은 import가 그대로 동작합니다. 로컬이 1.4.0을 유지한다는 점은 추정이며, `npm ls`로 확인해야 합니다.

다만 `exports`가 경로를 막을 때 Node가 내는 에러는 `ERR_PACKAGE_PATH_NOT_EXPORTED`입니다. 보고된 `Cannot find module` 문구와 정확히 일치하지 않습니다. 따라서 CI에 패키지가 없거나 다른 버전이 설치되었을 가능성도 함께 봐야 합니다. 에러가 webpack에서 나온 것인지, `next.config` 같은 Node 스크립트에서 나온 것인지도 스택 트레이스로 구별해야 합니다.

캐시 키가 lock 해시이므로 lock이 바뀌면 캐시도 새로 만들어집니다. 오래된 캐시가 원인일 가능성은 낮습니다. 다만 `restore-keys`로 이전 캐시를 불러오는 설정이라면 확인 필요합니다.

## 원인 후보

| 후보 | 근거 | 가능성 | 확인 방법 |
|---|---|---|---|
| 2.0.0 `exports`에 `./button` 경로가 없음 | 버전 변경 시점과 맞고, 로컬만 성공하는 현상을 설명함 | 높음 (추론) | 2.0.0 `package.json`의 `exports` 확인 |
| CI에 패키지가 없거나 다른 버전이 설치됨 | `Cannot find module` 문구와 맞음 | 중간 (미확인) | CI 로그의 설치 버전, lock 파일의 2.0.0 기록 확인 |
| Node 18과 20의 차이 | 두 버전 모두 `exports`를 지원함 | 낮음 (추론) | Node 18로 로컬 재현 |
| 캐시가 오래됨 | 캐시 키가 lock 해시임 | 낮음 (추론) | CI 캐시 hit/miss 로그 확인 |

## 확인 순서

1. CI 로그에서 `@company/ui`의 설치 버전과 에러 스택을 확인합니다. 스택에 webpack이 나오는지 Node 스크립트가 나오는지도 함께 봅니다.
2. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
3. 2.0.0 패키지의 `package.json`에서 `exports`에 `./button`이 있는지 확인합니다. 없으면 2.0.0 릴리스 노트에서 새 import 경로를 찾습니다.
4. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드합니다. 같은 에러가 나오면 2.0.0 변경이 원인이라는 근거가 됩니다.
5. Node 18로 같은 빌드를 실행해 Node 버전의 영향을 배제합니다. Next.js 버전의 최소 Node 요구 사항도 확인 필요합니다.
