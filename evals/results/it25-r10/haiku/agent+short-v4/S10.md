CI 빌드 실패의 원인은 아직 확정되지 않았다. 가장 유력한 설명은 CI가 `@company/ui` 2.0.0을 설치해서 `exports` 경로 해석이 달라졌고, 로컬은 3일 전에 설치된 1.4.0을 그대로 쓰고 있다는 것이다. 따라서 로컬 빌드가 성공했다는 사실은 2.0.0에서도 빌드된다는 근거가 되지 않는다.

## 확인된 사실

- 실패 에러는 `Error: Cannot find module '@company/ui/button'`이다.
- `@company/ui`는 3일 전에 1.4.0에서 2.0.0으로 올라갔다.
- 2.0.0에는 `exports` 필드(패키지가 외부에 공개하는 경로 목록)가 추가되었다.
- CI는 Node 18을, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`의 해시(파일 내용을 요약한 값)다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었다.

## 추론: 원인 후보

| 후보 | 근거 | 가능성 |
|---|---|---|
| 로컬에는 1.4.0이 남아 있다 | 로컬 `node_modules`가 업그레이드 전에 설치되었다. 2.0.0 경로를 로컬에서 한 번도 해석하지 않았다. | 높다 |
| CI가 2.0.0이 아닌 다른 버전을 쓴다 | 캐시 키가 lock 파일 해시라서 lock이 갱신되지 않았거나 이전 캐시가 복원되었을 수 있다. | 확인 필요 |
| 2.0.0에 `button` 경로가 없거나 위치가 바뀌었다 | `exports`가 있으면 Node는 목록에 없는 서브경로(`/button`처럼 패키지 뒤에 붙는 경로)를 막는다. | 중간 |
| Node 18에서만 해석이 다르다 | 2.0.0이 ESM 전용이거나 조건별 경로를 쓰면 Node 18의 `require`에서 실패할 수 있다. | 낮다 |

에러 메시지의 형태도 단서가 된다. Node가 `exports` 때문에 경로를 막을 때는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`가 나온다. 보고된 `Cannot find module`은 패키지나 파일이 설치본에 없을 때 나오는 메시지에 가깝다. 이 해석은 추론이므로 전체 스택 트레이스로 검증해야 한다.

## 확인 필요

- 에러가 Next.js 빌드 중 webpack에서 나왔는지, `next.config.js` 같은 Node 스크립트에서 나왔는지 확인 필요.
- `package-lock.json`이 2.0.0으로 갱신된 상태로 커밋되었는지 확인 필요.
- CI의 `npm ci` 로그에 설치된 `@company/ui` 버전이 찍혔는지 확인 필요.
- CI 캐시 복원에 이전 캐시를 쓰는 폴백(restore-keys)이 설정되어 있는지 확인 필요.
- 2.0.0의 `exports` 맵에 `./button`이 있는지, 파일 위치가 바뀌었는지 확인 필요.

## 다음 확인 순서

1. 로컬에서 `npm ls @company/ui`로 설치된 버전을 확인한다.
2. CI 로그에서 캐시 복원 여부와 `npm ci` 단계의 설치 버전을 확인한다.
3. 2.0.0 패키지의 `exports` 맵과 `button` 파일 경로를 확인한다.
4. 로컬 `node_modules`를 지운 뒤 `npm ci`로 다시 설치하고, Node 18로 빌드해 재현한다.

## 권장 사항

- 원인이 확정되기 전에는 `@company/ui`를 1.4.0으로 되돌리는 방안을 검토할 수 있다.
- CI에서 Node 18 대신 로컬과 같은 Node 20으로 맞추는 방안을 검토해도 된다. Node 18은 이미 지원이 끝난 버전이다.
- 원인이 2.0.0의 `exports` 문제로 확인되면, 임포트 경로를 2.0.0 공개 경로에 맞게 고치거나 패키지 쪽 경로 추가를 요청해야 한다.
