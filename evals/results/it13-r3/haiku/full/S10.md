가장 가능성이 높은 원인은 `@company/ui` 2.0.0에서 추가된 `exports` 필드(패키지 바깥에 공개하는 경로 목록)입니다. 이 필드에 `./button`이 없으면 `@company/ui/button` 같은 하위 경로 import가 막힙니다. 로컬에는 3일 전 이전에 설치한 1.4.0이 남아 있어 빌드가 통과하고, CI는 lockfile(의존성 버전을 고정한 `package-lock.json`)을 기준으로 2.0.0을 새로 설치해서 실패하는 것으로 설명됩니다. 다만 아직 검증되지 않았습니다.

| 원인 후보 | 근거 | 판단 |
|---|---|---|
| 2.0.0의 `exports`에 `./button`이 없음 | 2.0.0에서 `exports`가 추가됐고, 로컬은 1.4.0, CI는 2.0.0을 설치했을 가능성이 높음 | 가능성 높음. 미검증 |
| Node 18(CI)과 Node 20(로컬)의 차이 | 두 버전 모두 `exports`를 지원함 | 가능성 낮음. 버전 차이 자체로는 설명이 부족함 |
| CI 캐시가 오래된 `node_modules`를 복원 | 캐시 키가 lockfile 해시라 lockfile이 바뀌면 캐시가 무효화됨 | 실패 원인으로 보기 어려움 |

에러 메시지는 `Cannot find module`인데, Node가 `exports` 제한으로 import를 막을 때 내는 메시지와 다릅니다. 따라서 `exports` 제한인지, 2.0.0에서 `button` 파일 경로가 바뀐 것인지는 아직 구분되지 않습니다.

확인 필요:
- CI가 실제로 설치한 `@company/ui` 버전이 2.0.0인지
- 2.0.0 패키지의 `exports`에 `./button`이 있는지, 파일 경로가 바뀌었는지
- 에러가 Next.js 빌드의 어느 단계에서 나는지(전체 스택 트레이스)

다음 순서로 확인하십시오.
1. CI 로그나 CI에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. 설치된 `node_modules/@company/ui/package.json`에서 `exports` 항목을 열어 `./button`이 있는지 봅니다.
3. 로컬에서 `npm ls @company/ui`를 실행해 1.4.0이 설치되어 있는지 확인합니다.
4. 로컬에서 Node 18로 빌드해 Node 버전이 영향을 주는지 분리합니다.

2번에서 `./button`이 없으면 deep import를 `exports`에 있는 경로로 바꾸거나, `@company/ui` 측에 `./button` 노출을 요청하는 두 가지 수정 방향 중 하나를 고르십시오.
