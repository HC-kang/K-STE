**가장 가능성이 높은 원인은 `@company/ui` 2.0.0에서 추가된 `exports` 필드가 `button` 하위 경로를 노출하지 않거나 다른 경로로 바꾼 것입니다.** 다만 아래 내용은 전달해 주신 정보로 추론한 것이고, 패키지 코드와 `node_modules`는 직접 확인하지 않았습니다.

## 추론한 원인

- 1.4.0에는 `exports` 필드가 없습니다. 그래서 `@company/ui/button`은 패키지 안의 파일 경로로 바로 해석됩니다.
- 2.0.0에는 `exports` 필드가 있습니다. Node.js는 `exports`에 선언되지 않은 하위 경로를 외부에서 가져오지 못하게 막습니다.
- 로컬 `node_modules`는 3일 전에 설치한 것입니다. 로컬에는 아직 1.4.0이 남아 있을 가능성이 높으므로 빌드가 성공합니다.
- CI 캐시 키가 `package-lock.json` 해시입니다. lock 파일이 2.0.0으로 갱신되었다면 캐시가 무효화되고, CI는 2.0.0을 새로 설치합니다. 그래서 CI에서만 에러가 납니다.

즉, 로컬과 CI가 서로 다른 버전의 패키지를 쓰고 있을 가능성이 가장 큽니다.

## Node 18과 Node 20 차이

Node 18과 Node 20은 모두 `exports`를 지원합니다. 따라서 Node 버전 차이만으로 이 에러가 날 가능성은 낮다고 봅니다. 다만 Next.js 번들러의 해석 결과가 Node 버전에 따라 달라질 수 있으므로, 로컬에서 Node 18로 빌드해 재현되는지 확인하는 것이 안전합니다.

## 확인 필요

- 로컬 설치 버전이 1.4.0인지: `npm ls @company/ui`
- 2.0.0의 `exports`에 `./button` 항목이 있는지: `npm view @company/ui@2.0.0 exports --json`
- 2.0.0에서 `button` 경로가 바뀌었는지: 릴리스 노트 또는 소스 비교
- `package-lock.json`이 2.0.0으로 커밋되어 있는지
- 앱 코드의 import 경로가 3일 사이에 바뀌었는지

## 조치 방향

1. 앱 코드의 import를 2.0.0의 `exports`가 노출하는 경로로 바꿉니다. 이 방법이 보통 가장 빠릅니다.
2. 급하게 배포해야 하면 `@company/ui`를 1.4.0으로 되돌립니다. 대신 2.0.0의 변경 사항은 늦어집니다.
3. 패키지 쪽에서 `exports`에 `./button`을 추가하거나, 경로 변경을 릴리스 노트에 명시하도록 패키지 담당자에게 요청합니다.
4. 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치한 뒤 빌드해 CI와 같은 상태를 재현합니다.

**로컬 빌드가 성공했다는 사실만으로 CI 문제가 없다고 판단하면 안 됩니다.** 로컬이 과거 버전을 쓰고 있을 가능성이 높기 때문입니다.
