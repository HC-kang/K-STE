원인은 아직 확정하지 못했습니다. 가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드이고, 로컬 `node_modules`에 업그레이드 전 버전인 1.4.0이 남아 있어서 로컬 빌드만 성공하는 것으로 보입니다.

## 확인된 사실

- CI 빌드가 `Error: Cannot find module '@company/ui/button'`으로 실패합니다.
- 로컬 빌드는 성공합니다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드가 추가됐습니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 업그레이드 3일 전에 설치됐습니다.

## 추론

1. `exports` 필드는 패키지 바깥에서 import할 수 있는 경로를 정합니다. 1.4.0에는 이 필드가 없어서 `@company/ui/button`이 파일 경로로 바로 해석됐습니다. 2.0.0에서 `exports`에 `./button`이 없으면 같은 import가 실패합니다.
2. 로컬 `node_modules`가 업그레이드 전에 설치됐으므로 로컬에는 1.4.0이 남아 있을 가능성이 큽니다. 따라서 로컬 빌드가 성공해도 2.0.0과 호환된다는 근거는 되지 않습니다.
3. CI는 `package-lock.json`이 바뀌면 캐시 키도 바뀌므로 새로 설치해서 2.0.0을 받았을 가능성이 높습니다. 다만 캐시 설정에 `restore-keys`가 있으면 오래된 캐시가 복원됐을 수도 있습니다.
4. Node 18은 `exports`를 지원하므로 버전 차이만으로 이 에러가 난다고 보기는 어렵습니다. 다만 Node 버전 차이가 번들링 결과에 영향을 줄 가능성은 남아 있습니다.
5. `Cannot find module`은 Node가 모듈을 직접 찾을 때 나오는 문구입니다. Next.js 웹팩 빌드 오류는 보통 `Module not found`로 표시되므로, 에러가 빌드 중 어느 단계에서 났는지 전체 스택 트레이스로 구분해야 합니다.

## 로컬과 CI 비교

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `@company/ui` 버전 | 1.4.0으로 추정 | 2.0.0으로 추정 |
| `node_modules` 출처 | 업그레이드 전 설치본 | 캐시 키 기준 설치 또는 복원 |
| 빌드 결과 | 성공 | 실패 |

## 확인 필요

1. 로컬 `node_modules/@company/ui/package.json`의 `version` 값을 봅니다. 1.4.0이면 추론 2번이 맞습니다.
2. `@company/ui` 2.0.0의 `package.json`에서 `exports` 필드에 `./button` 항목이 있는지 봅니다.
3. CI 로그의 전체 스택 트레이스를 봅니다. 에러가 어느 파일과 어느 단계에서 나는지 구분하기 위해서입니다.
4. CI 캐시 복원 로그에서 cache hit 여부와 `restore-keys`로 복원됐는지 봅니다. 오래된 캐시가 쓰였는지 판단하기 위해서입니다.
5. 같은 빌드를 Node 18로 로컬에서 돌려 봅니다. Node 버전 영향을 로컬에서 분리하기 위해서입니다.

CI를 고치는 방법은 두 가지입니다. 첫째, 임포트 경로를 2.0.0의 `exports`가 허용하는 경로로 바꿉니다. 둘째, 원인이 확정될 때까지 `@company/ui`를 1.4.0으로 고정합니다. 어느 쪽을 택하든 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치해 실패를 재현한 뒤 적용하는 것을 권장합니다.
