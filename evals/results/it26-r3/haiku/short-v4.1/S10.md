CI에서만 실패하는 이유는 로컬 `node_modules`가 3일 전 설치본이라 `@company/ui` 1.4.0을 그대로 쓰고 있기 때문으로 보입니다. 따라서 로컬 빌드 성공은 2.0.0을 검증한 결과가 아닙니다. 원인은 2.0.0에서 추가된 `exports` 필드(패키지가 외부에 공개할 경로를 정하는 설정)가 `button` 경로를 다르게 다루는 것으로 추정합니다. 아직 실행해서 확인하지는 않았습니다.

### 사실

- 3일 전 `@company/ui`가 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0에는 `exports` 필드가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`(설치 버전을 고정한 파일)의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

### 추론

- 로컬 `node_modules`는 1.4.0 상태일 가능성이 높습니다. 그래서 로컬 빌드는 2.0.0 환경을 시험하지 못했습니다.
- CI는 락 파일 기준으로 새로 설치하므로 2.0.0이 설치되었을 가능성이 높습니다. 확인 필요: 락 파일이 2.0.0으로 갱신되어 커밋되었는지 확인해야 합니다.
- 에러 문구 `Cannot find module`은 Node가 파일을 찾지 못했을 때 내는 형식입니다. 그래서 `exports`가 경로를 막았다기보다, 2.0.0에서 `button` 파일의 위치나 이름이 바뀌었을 가능성을 먼저 봅니다.
- 캐시는 락 파일이 바뀌면 새 키로 저장되므로, 오래된 패키지 캐시가 원인일 가능성은 낮습니다. 확인 필요: 캐시 설정에 이전 키를 가져오는 `restore-keys`가 있는지 확인해야 합니다.
- Node 18과 20의 차이가 원인일 가능성은 낮게 봅니다. 두 버전 모두 `exports` 필드를 지원하기 때문입니다. 다만 Next.js의 모듈 해석 방식이 버전에 따라 다를 수 있어 배제하지는 않습니다.

### 확인 방법

1. CI 설치 로그에서 실제로 설치된 `@company/ui` 버전을 확인합니다.
2. 로컬에서 `npm ls @company/ui`를 실행해 현재 버전을 확인합니다.
3. `node_modules`를 지운 뒤 `npm ci`로 락 파일 기준 재설치를 하고 빌드를 실행합니다.
4. 설치된 패키지의 `package.json`에서 `exports` 필드에 `./button` 항목이 있는지 봅니다.
5. 설치된 패키지 폴더에서 `button` 파일이 실제 있는 경로를 확인합니다.
6. Node 18로 재설치한 로컬 환경에서 같은 빌드를 실행해 재현되는지 봅니다.

**로컬 빌드가 성공했다는 사실만으로 CI 문제를 배제하면 안 됩니다.** 로컬 환경이 2.0.0을 쓰지 않기 때문입니다.

### 조치 선택지

| 방안 | 장점 | 단점 |
|---|---|---|
| `@company/ui`를 1.4.0으로 되돌립니다 | CI를 바로 복구할 수 있습니다 | 2.0.0의 기능을 쓸 수 없고, 나중에 같은 문제가 다시 생깁니다 |
| `button` import 경로를 2.0.0의 `exports`에 맞게 고칩니다 | 2.0.0을 유지할 수 있습니다 | 여러 파일을 고쳐야 할 수 있습니다 |
| 패키지 유지 측에 `button` 경로 공개를 요청합니다 | 호출하는 쪽의 수정을 줄일 수 있습니다 | 요청 처리까지 시간이 걸립니다 |

권장하는 순서는 확인 방법 1번에서 3번을 먼저 수행하는 것입니다. 원인이 확인되면 위 방안 중 하나를 고르면 됩니다. 배포가 실제로 막혔는지는 확인 필요: 배포 파이프라인의 현재 상태를 보고 판단해야 합니다.
