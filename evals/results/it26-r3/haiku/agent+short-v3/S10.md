이 오류의 가장 유력한 원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드가 `button` 하위 경로를 외부에 공개하지 않아서, CI가 `@company/ui/button`을 찾지 못하는 것입니다. 다만 이는 제공해 주신 정보로 추론한 결과이며, 2.0.0 패키지의 `exports` 목록은 아직 확인하지 않았습니다.

로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 3일 전보다 먼저 설치되어 1.4.0이 그대로 남아 있을 가능성이 높기 때문입니다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`이 파일 경로로 그대로 해석됩니다. 그래서 로컬 빌드는 2.0.0 변경을 거치지 않고 통과합니다. 따라서 로컬 빌드 성공은 2.0.0이 동작한다는 근거가 되지 않습니다. 확인 필요: 로컬에 실제로 설치된 버전이 1.4.0인지는 아직 확인하지 않았습니다.

오류 메시지 형식도 단서가 됩니다. `Cannot find module`은 Node.js가 직접 내는 메시지이고, 웹팩 번들링 단계에서는 보통 `Module not found`로 표시됩니다. 따라서 `next.config.js`처럼 Node.js가 직접 실행하는 파일에서 이 경로를 `require`하고 있을 가능성도 확인해야 합니다. 확인 필요: 어느 파일에서 오류가 발생했는지는 CI 로그에서 확인해야 합니다.

원인 후보를 정리하면 다음과 같습니다.

| 후보 | 근거 | 확인 방법 |
|---|---|---|
| 2.0.0의 `exports`에 `./button`이 없음 | `exports` 추가 시점과 오류 발생 시점이 일치함 | `node_modules/@company/ui/package.json`의 `exports` 항목 확인 |
| 로컬 `node_modules`가 1.4.0임 | 설치가 3일 전보다 이전에 이뤄짐 | 로컬에서 `npm ls @company/ui` 실행 |
| CI가 캐시에서 1.4.0을 복원함 | 캐시 키가 `package-lock.json` 해시임 | 버전 변경이 담긴 lock 파일이 커밋에 포함됐는지, CI 로그에서 캐시 적중 여부 확인 |
| Node 18과 20의 차이 | CI와 로컬의 Node 버전이 다름 | 로컬에서 Node 18로 빌드 재현 |

Node 18과 20은 모두 `exports` 필드를 지원하므로, 버전 차이만으로 이 오류가 생길 가능성은 낮게 봅니다. 그래도 로컬 재현으로 한 번 확인하는 것이 좋습니다.

확인 순서는 다음과 같습니다.

1. 로컬에서 `npm ls @company/ui`를 실행하여 설치된 버전을 확인합니다. 1.4.0이면 로컬 빌드는 2.0.0을 검증하지 못한 것입니다.
2. `@company/ui` 2.0.0의 `package.json`에서 `exports` 항목에 `./button` 경로가 있는지 확인합니다.
3. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드합니다.
4. CI 로그에서 캐시 적중 여부와 설치된 `@company/ui` 버전을 확인합니다.

수정 방향은 두 가지입니다. 하나는 코드의 import 경로를 2.0.0이 공개한 경로에 맞추는 것이고, 다른 하나는 패키지 쪽 `exports`에 `button` 경로를 추가해 달라고 요청하는 것입니다. 급하게 배포해야 한다면 1.4.0으로 임시 되돌리는 방법도 있습니다. 어느 쪽을 택할지는 위 1번과 2번의 결과로 정하는 것이 맞습니다.
