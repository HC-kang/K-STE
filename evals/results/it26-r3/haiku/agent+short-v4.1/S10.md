원인은 `@company/ui`가 로컬과 CI에서 서로 다른 버전으로 설치되고 있기 때문일 가능성이 가장 높습니다. 로컬 `node_modules`는 3일 전 1.4.0 기준으로 설치되어 있어서, 2.0.0에서 바뀐 경로 규칙이 로컬 빌드에서는 적용되지 않습니다.

### 확인된 사실 (제공된 정보)

1. `@company/ui`가 1.4.0에서 2.0.0으로 올라갔습니다.
2. 2.0.0에 `exports` 필드가 추가되었습니다. `exports`는 패키지 밖에서 쓸 수 있는 경로를 정하는 설정입니다.
3. CI는 Node 18을, 로컬은 Node 20을 씁니다.
4. CI 캐시 키는 `package-lock.json`(설치할 패키지 버전을 고정한 파일)의 해시입니다.
5. 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

### 추론

`exports`가 있으면 Node와 번들러는 목록에 있는 경로만 허용합니다. 2.0.0 목록에 `./button`이 없거나 다른 경로로 바뀌었다면 `@company/ui/button` import가 실패합니다.

로컬에서는 1.4.0이 그대로 남아 있어서 같은 import가 성공합니다. 1.4.0에는 `exports` 제한이 없기 때문입니다.

CI는 락파일 변경으로 캐시 키가 바뀌므로 새로 설치하고, 이때 2.0.0을 받습니다. 그래서 실패가 CI에서만 나타납니다.

Node 18과 20의 차이는 주된 원인으로 보기 어렵습니다. 두 버전 모두 `exports`를 지원하기 때문입니다.

### 확인 필요

- 확인 필요: 에러 문구 `Cannot find module`은 CommonJS 방식의 오류 문구입니다. Node가 `exports` 제한을 어기면 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`를 내고, Next.js 번들러는 `Module not found`를 냅니다. CI 로그에서 이 에러를 낸 도구가 무엇인지 확인해야 합니다.
- 확인 필요: 로컬에서 `npm ls @company/ui`를 실행해 설치 버전이 1.4.0인지 확인해야 합니다.
- 확인 필요: 2.0.0 패키지의 `exports`에 `./button` 경로가 있는지 확인해야 합니다.
- 확인 필요: CI 캐시 설정에 `restore-keys`(이전 키의 캐시를 복원하는 설정)가 있는지 확인해야 합니다. 있다면 키가 바뀌어도 1.4.0이 담긴 이전 `node_modules`가 복원될 수 있습니다.
- 확인 필요: `package.json`과 `package-lock.json`이 같은 커밋에서 바뀌었는지 확인해야 합니다.

### 권장 조치

1. 로컬에서 `rm -rf node_modules` 후 `npm ci`로 다시 설치해 CI와 같은 조건을 재현합니다.
2. 재현되면 CI 로그의 에러를 낸 도구를 먼저 확인합니다.
3. 같은 환경에서 Node 18로 빌드해 Node 버전의 영향을 분리합니다.
4. 원인이 `exports` 누락으로 확인되면 아래 중 하나를 고릅니다.

| 방법 | 내용 | 성격 |
|---|---|---|
| 패키지 수정 | 2.0.0의 `exports`에 `./button` 경로를 추가합니다. | 근본 해결, 패키지 담당자가 배포해야 합니다. |
| 앱 import 수정 | `@company/ui/button` 대신 2.0.0이 공개한 경로로 바꿉니다. | 앱에서 바로 처리할 수 있습니다. |
| 1.4.0 고정 | `package.json`에서 1.4.0으로 되돌립니다. | 임시 조치이며 2.0.0 적용이 미뤄집니다. |

로컬 검증은 기존 `node_modules`가 아니라 `npm ci`로 새로 설치한 환경에서 해야 합니다. 이번 문제는 그렇게 하지 않아서 3일 동안 드러나지 않았습니다.
