Redis를 도입하면 API 서버 4대가 같은 캐시를 보므로, 서버마다 상품 정보가 어긋나는 문제가 없어집니다. 캐시(자주 쓰는 데이터를 빠르게 꺼내 쓰려고 임시로 저장해 두는 공간)는 지금 서버 안에 따로 있고, Redis는 서버 밖에 하나만 둡니다.

쉽게 비유하면 지금은 서버 4대가 각자 상품 목록 수첩을 들고 있는 구조이고, Redis 도입 후에는 4대가 같은 수첩 하나를 함께 보는 구조입니다.

| 구분 | 로컬 캐시 (지금 방식) | Redis 캐시 (도입 예정) |
|---|---|---|
| 저장 위치 | 각 API 서버의 메모리 안 | 서버 4대가 함께 쓰는 캐시 서버 1대 |
| 서버 간 데이터 | 서버마다 내용이 다를 수 있음 | 4대가 같은 내용을 봄 |
| 가격 변경 반영 | 서버마다 최대 5분 늦게 반영됨 | 서버마다 다르게 보이는 문제가 없음 |

다만 Redis를 도입해도 캐시를 5분 동안 유지하는 방식을 그대로 쓰면 고객에게 가격 변경이 늦게 보이는 시간은 최대 5분으로 남을 수 있습니다. 가격을 바꿀 때 캐시를 바로 갱신하도록 설계하면 이 지연을 줄일 수 있습니다.
