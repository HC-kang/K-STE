현재 자료만으로 원인을 하나로 확정할 수 없습니다. 가장 유력한 설명은 로컬 node_modules(설치된 패키지를 담는 폴더)에 아직 1.4.0이 남아 있어서, 로컬 빌드가 2.0.0의 변경을 검증하지 못했다는 것입니다.

## 확인된 사실

CI에서만 빌드가 실패하고 로컬 빌드는 성공합니다. 실패 메시지는 `Error: Cannot find module '@company/ui/button'`입니다. @company/ui는 3일 전에 1.4.0에서 2.0.0으로 올라갔고, 2.0.0에는 exports 필드(패키지 외부에 공개할 모듈 경로를 정한 설정)가 추가됐습니다. CI는 Node 18을, 로컬은 Node 20을 사용합니다. CI 캐시 키(캐시를 구분하는 식별값)는 package-lock.json의 해시입니다. 로컬 node_modules는 3일 전보다 먼저 설치됐습니다.

## 추론

로컬 node_modules에 1.4.0이 남아 있다면, 로컬 빌드는 exports 필드가 없는 구버전으로 `@company/ui/button`을 해석합니다. 그래서 로컬은 성공하고, CI는 package-lock.json에 기록된 2.0.0을 설치하므로 실패한다고 설명할 수 있습니다. 이 설명은 CI와 로컬의 차이를 가장 적은 가정으로 설명합니다. 다만 로컬에 실제로 설치된 버전은 아직 확인하지 않았습니다.

2.0.0의 exports에 `./button` 경로가 없거나 다른 경로로 연결돼 있다면, 로컬에서도 2.0.0을 설치하는 순간 같은 오류가 납니다. 이 경우 원인은 CI 환경이 아니라 2.0.0 자체의 호환성 문제입니다.

로컬 macOS는 대소문자를 구분하지 않고 CI의 Linux는 구분합니다. import 경로와 실제 파일명의 대소문자가 다르면 로컬에서만 성공하고 CI에서 실패합니다. 이 경우에는 exports 변경과 무관합니다.

Node 18과 Node 20의 차이가 exports 해석을 바꾼다는 근거는 현재 없습니다. 두 버전 모두 exports를 지원하므로 주원인일 가능성은 낮습니다. 다만 Next.js 빌드 도구가 버전별로 다르게 동작하는지는 확인되지 않았습니다.

캐시 키가 package-lock.json의 해시이므로, package-lock.json이 바뀌면 캐시도 새로 만들어집니다. 따라서 오래된 캐시가 원인일 가능성은 낮습니다. 확인 필요: CI 워크플로에 이전 키의 캐시를 복원하는 설정(restore-keys)이 있는지 확인해야 합니다.

| 원인 후보 | 근거 | 확인 방법 |
|---|---|---|
| 로컬 node_modules에 1.4.0 잔존 | 로컬 설치가 3일 전보다 먼저 이뤄짐 | `npm ls @company/ui` 실행 |
| 2.0.0 exports에 button 경로 없음 | 2.0.0에서 exports 추가 | 2.0.0 package.json의 exports 항목 확인 |
| 대소문자 차이 | macOS와 Linux의 파일 시스템 차이 | import 경로와 실제 파일명 비교 |
| Node 18과 20 차이 | 실행 환경 차이 | Node 18로 로컬 빌드 재현 |
| 오래된 캐시 | 캐시 키는 package-lock.json 해시 | CI 로그에서 캐시 적중 여부 확인 |

## 다음 확인 순서

1번과 3번 결과에 따라 조치 방향이 달라집니다.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. CI 로그에서 설치된 @company/ui 버전과 캐시 적중 여부를 확인합니다.
3. 2.0.0 패키지의 exports 필드에 `./button` 경로가 있는지 확인합니다.
4. node_modules를 지운 뒤 `npm ci`로 다시 설치하고 빌드해서 실패가 재현되는지 확인합니다.
5. 재현되면 Node 18로 같은 빌드를 실행해 결과를 비교합니다.
