**가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다.** 로컬에서 성공하는 이유는 로컬 `node_modules`가 2.0.0 이전 버전을 그대로 쓰고 있기 때문으로 보입니다. 이 분석은 주어진 사실에 근거한 추론이며, 저장소, `package.json`, CI 로그는 직접 확인하지 않았습니다.

## 확인된 사실

- 2.0.0에는 `exports` 필드가 추가되었습니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.
- CI는 `package-lock.json` 해시를 캐시 키로 사용합니다.
- CI는 Node 18, 로컬은 Node 20을 사용합니다.

## 추론

1. 로컬 `node_modules`에는 1.4.0이 남아 있을 가능성이 높습니다. 3일 전 이후에 `npm install`을 다시 실행하지 않았다면, `package.json`과 lockfile이 2.0.0으로 바뀌어도 로컬 패키지는 바뀌지 않습니다.
2. 1.4.0에는 `exports` 필드가 없으므로 `@company/ui/button`은 파일 경로로 그대로 찾아집니다.
3. 2.0.0의 `exports` 필드는 외부에 공개할 경로만 허용합니다. 목록에 없는 `./button` 같은 하위 경로는 찾을 수 없어 실패합니다.
4. CI는 lockfile이 바뀌어 캐시 키가 달라졌으므로 2.0.0을 새로 설치하고, 그래서 이 오류가 발생합니다.

**확인 필요:** 보고된 메시지 `Error: Cannot find module`은 Node의 `require` 실패 형식입니다. `exports` 때문에 생긴 실패인지는 전체 스택 트레이스와 에러 코드로 확인해야 합니다. 또한 이 메시지가 Next.js 빌드 과정에서 나온 것인지, `next.config.js`나 빌드 스크립트에서 나온 것인지도 확인해야 합니다.

## 가능성이 낮은 원인

- **Node 버전:** Node 18과 20은 모두 `exports`를 지원하므로 `exports` 자체 때문에 버전 차이가 생기지는 않습니다. 다만 2.0.0이 ESM 전용 패키지이거나 Node 20 이상 기능을 쓴다면 Node 18에서 실패할 수 있습니다. **확인 필요:** 2.0.0의 `package.json`에서 `type`, `main`, `engines` 필드를 봐야 합니다.
- **캐시:** lockfile 해시가 바뀌면 CI가 새로 설치하므로 오래된 패키지가 남는 원인은 아닙니다. **확인 필요:** 캐시 경로가 `node_modules`인지 `~/.npm`인지 확인해야 합니다.

## 검증 방법 (아직 실행하지 않음)

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다. 1.4.0이면 추론 1번이 맞습니다.
2. 로컬에서 `rm -rf node_modules && npm ci`로 lockfile 기준 재설치 후 빌드합니다. 여기서 실패하면 로컬에서도 재현됩니다.
3. 2.0.0의 `exports` 필드에 `./button` 경로가 있는지 확인합니다.
4. Node 18로 로컬 빌드를 해 보거나, CI를 Node 20으로 바꿔 결과를 비교합니다.

## 권장 조치

- **단기:** 2.0.0의 `exports`에 있는 경로로 import를 바꾸거나, 패키지 관리자에게 `./button` 경로 추가를 요청합니다. 급하면 1.4.0으로 되돌릴 수 있습니다.
- **장기:** CI와 로컬의 Node 버전을 `.nvmrc`나 `engines` 필드로 맞춥니다. 또한 로컬 `node_modules`를 lockfile 기준으로 다시 설치하는 절차를 문서화합니다.
