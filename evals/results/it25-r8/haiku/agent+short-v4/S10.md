로컬 `node_modules`가 3일 전 설치된 1.4.0 상태로 남아 있어서 로컬 빌드가 통과하고, 2.0.0의 `exports` 필드가 `@company/ui/button` 경로를 허용하지 않아 CI에서만 실패하는 것으로 보입니다. 이 결론은 추론이며, `exports` 내용은 아직 직접 확인하지 않았습니다.

**로컬 빌드 성공만으로 CI 설정이 정상이라고 판단하면 안 됩니다.**

### 전달받은 사실

- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- 3일 전 `@company/ui`가 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0에는 `exports` 필드(패키지 외부에 공개할 파일 경로를 정하는 설정)가 추가되었습니다.
- CI 캐시 키는 `package-lock.json`(설치할 패키지 버전을 고정하는 파일)의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

### 추론

- 1.4.0에는 `exports`가 없으므로 `@company/ui/button`은 파일 경로 그대로 찾혔을 가능성이 큽니다. 로컬의 오래된 설치본이 이 경로를 계속 찾아 주기 때문에 로컬 빌드가 통과합니다.
- 2.0.0의 `exports`에 `./button`이 없거나 다른 경로로 연결되어 있으면, Node는 CI에서 같은 import를 찾지 못합니다. Node 18도 `exports` 규칙을 따르므로 이 차이는 Node 버전과 무관합니다.
- Node 18과 20의 차이가 원인일 가능성은 낮아 보입니다.
- 에러 문구 `Cannot find module`은 Node나 테스트 도구의 메시지에 가깝고, Next.js(webpack) 빌드의 기본 메시지와는 다릅니다. 따라서 에러를 던진 단계가 빌드인지 타입 검사인지 테스트인지 확인이 필요합니다.

### 미확인 (확인 필요)

- 확인 필요: 2.0.0의 `exports`에 `./button` 항목이 있는지 여부
- 확인 필요: 에러를 던진 단계가 Next.js 빌드, TypeScript 타입 검사, 테스트 중 어디인지 여부
- 확인 필요: 커밋된 `package-lock.json`이 2.0.0을 기록하는지 여부
- 확인 필요: CI 캐시가 이전 실행의 `node_modules`를 복원했는지 여부

### 다음 확인 순서

1. 로컬에서 `node_modules`를 지우고 `npm ci`를 실행한 뒤 빌드합니다. 실패하면 원인이 로컬 설치 상태와 무관하지 않다는 뜻입니다.
2. `node_modules/@company/ui/package.json`의 `exports`에 `./button` 항목이 있는지 봅니다.
3. CI 로그에서 에러가 나온 단계를 확인합니다.
4. CI에서 캐시를 끄고 한 번 실행하여 캐시의 영향을 봅니다.

`exports`에 `./button`이 없으면 패키지 쪽 수정이 필요하거나, 앱의 import 경로를 2.0.0이 공개한 경로로 바꿔야 합니다. 이 판단은 2번 결과가 나온 뒤에 해야 합니다.
