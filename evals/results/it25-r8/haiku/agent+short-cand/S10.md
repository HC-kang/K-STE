로컬과 CI가 서로 다른 버전의 `@company/ui`를 쓰고 있을 가능성이 높습니다. 로컬은 1.4.0이, CI는 2.0.0이 설치됐을 것으로 보이며, 2.0.0의 `exports` 필드가 `button` 경로를 막는 것이 실패 원인으로 유력합니다. 아래 내용 중 추론은 실제 값을 확인해야 확정됩니다.

## 확인된 사실

- 빌드는 CI에서만 `Cannot find module '@company/ui/button'`으로 실패합니다.
- `@company/ui`는 3일 전에 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0에는 `exports` 필드(패키지 바깥에 공개할 파일 경로를 정하는 설정)가 새로 추가됐습니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치됐습니다.

## 추론

로컬 `node_modules`가 업그레이드 이전에 설치됐으므로, 다시 설치하지 않았다면 로컬에는 여전히 1.4.0이 있습니다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`이 파일 경로 그대로 해석되고, 그래서 로컬 빌드가 성공합니다. 로컬 성공은 2.0.0 기준의 검증이 아닙니다.

CI는 lock 파일 기준으로 2.0.0을 설치합니다. 2.0.0의 `exports`에 `./button` 경로가 없다면 import가 실패하며, 이것이 CI에서만 보이는 에러입니다.

캐시 키가 lock 해시이므로 lock이 바뀌면 기본적으로 캐시가 새로 만들어집니다. 다만 캐시 설정에 `restore-keys`(일부 키가 맞으면 이전 캐시를 복원하는 설정)가 있으면 오래된 `node_modules`가 복원될 수 있습니다.

Node 18과 20의 차이는 이 에러의 원인으로 보기 어렵습니다. 다만 아직 배제한 것은 아니므로 확인 대상에 넣습니다.

## 확인 필요

- 로컬에서 실제로 설치된 `@company/ui` 버전이 1.4.0인지 확인해야 합니다.
- 커밋된 `package-lock.json`에 2.0.0이 기록되어 있는지 확인해야 합니다.
- 2.0.0의 `exports`에 `./button`이 있는지 확인해야 합니다.
- CI 로그에서 캐시가 정확히 맞았는지, `restore-keys`로 복원됐는지 확인해야 합니다.
- 에러 스택 트레이스에서 어떤 도구(Node, Next.js 번들러, TypeScript 중 하나)가 에러를 던졌는지 확인해야 합니다. Node 자체의 `exports` 에러는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`로 표시되므로, "Cannot find module" 문구는 다른 도구에서 나왔을 가능성이 있습니다.

## 조치 방향

1. 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치한 뒤 빌드합니다. 이때 Node 18을 써서 CI와 환경을 맞춥니다. 로컬에서 같은 에러가 재현되면 원인이 확정됩니다.
2. 재현되면 두 가지 중 하나를 택합니다. `@company/ui` 측에 `./button` 경로를 `exports`에 추가해 달라고 요청하거나, 앱의 import를 2.0.0이 공개한 경로로 바꿉니다.
3. 원인을 확정한 뒤 Node 버전을 `.nvmrc`나 `engines` 필드에 명시해 로컬과 CI가 같은 버전을 쓰도록 합니다.
