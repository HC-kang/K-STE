가장 가능성이 높은 원인은 CI가 `@company/ui` 2.0.0을 설치하고, 로컬은 1.4.0을 쓰고 있다는 점입니다. 2.0.0의 `exports` 필드에 `./button` 경로가 없으면 CI에서만 이 모듈을 찾지 못합니다. 이 내용은 추론이며, 아래 확인 단계로 검증해야 합니다.

## 확인된 사실

- CI 빌드만 `Cannot find module '@company/ui/button'`로 실패하고, 로컬 빌드는 성공합니다.
- `@company/ui`를 3일 전에 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0부터 패키지에 `exports` 필드가 있습니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치했습니다.

## 추론

- 로컬 `node_modules`가 업그레이드 전에 설치됐으므로, 로컬에는 1.4.0이 남아 있을 가능성이 높습니다.
- 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`이 파일 경로 그대로 열립니다. 로컬 빌드가 성공하는 이유로 보입니다.
- `exports` 필드가 있으면 패키지 안의 경로는 `exports`에 적힌 것만 가져올 수 있습니다. 2.0.0의 `exports`에 `./button`이 없거나 이름이 바뀌었다면 CI에서 이 에러가 납니다.
- `package-lock.json`이 업그레이드 때 바뀌었다면 캐시 키도 바뀌므로, CI는 캐시 없이 2.0.0을 새로 설치했을 것입니다.
- Node 18도 `exports` 필드를 지원하므로, Node 버전 차이는 주원인일 가능성이 낮습니다.

## 확인 필요

- 로컬에 실제로 설치된 `@company/ui` 버전이 무엇인지 확인해야 합니다.
- `package-lock.json`에 2.0.0이 기록됐는지 확인해야 합니다.
- 2.0.0의 `exports`에 `./button`이 있는지, 있다면 어떤 이름인지 확인해야 합니다.

## 검증 단계

1. 로컬과 CI에서 각각 `npm ls @company/ui`를 실행해 설치된 버전을 비교한다.
2. 로컬에서 `node_modules`와 `.next`를 지우고 `npm ci`로 다시 설치한 뒤 빌드한다. 로컬에서도 같은 에러가 나면 원인은 버전 차이로 확정된다.
3. `node_modules/@company/ui/package.json`의 `exports` 필드에서 `./button` 항목을 확인한다.
4. 항목이 없으면 `@company/ui` 담당자에게 `exports` 추가를 요청하거나, 2.0.0 문서에 적힌 새 import 경로로 코드를 수정한다.
5. 3번에서 항목이 있고 로컬 재설치 후에도 성공하면, CI의 Node 버전을 20으로 올려 다시 실행해 Node 차이를 따로 배제한다.

PM에게 전달할 요점은 두 가지입니다. 로컬 빌드 성공은 업그레이드가 반영된 결과가 아닐 가능성이 높습니다. 따라서 CI 실패가 실제 문제이고, 수정 전까지 2.0.0 기반 배포는 막힌 상태로 봐야 합니다.
