가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드(패키지가 외부에 공개하는 경로 목록)에 `@company/ui/button` 경로가 없는 것입니다. 로컬 빌드는 2.0.0이 아니라 업그레이드 전 버전으로 돌고 있어서 이 문제가 드러나지 않았다고 추정합니다.

## 근거

사실로 주어진 내용은 다음과 같습니다.

- 2.0.0에서 패키지에 `exports` 필드가 추가됐습니다.
- 로컬 `node_modules`는 3일 전 업그레이드보다 먼저 설치한 것입니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- CI는 Node 18, 로컬은 Node 20입니다.

이 사실에서 다음과 같이 추론합니다.

- 패키지에 `exports`가 있으면 Node는 목록에 없는 경로의 import를 막습니다. `exports`가 없던 1.4.0에서는 `@company/ui/button`처럼 파일 경로로 직접 import할 수 있었습니다.
- 업그레이드 때 `package-lock.json`이 바뀌었으므로 CI 캐시 키도 바뀌었고, CI는 2.0.0을 새로 설치했을 가능성이 높습니다.
- 로컬은 `npm install`을 다시 하지 않았다면 1.4.0이 그대로 남아 있습니다. 그래서 로컬에서는 import가 성공했을 것입니다.
- Node 18과 20은 둘 다 `exports`를 지원합니다. 따라서 Node 버전 차이는 주원인일 가능성이 낮습니다.

## 아직 확인하지 않은 내용

- 2.0.0의 `exports`에 `./button`이 실제로 없는지 확인하지 않았습니다.
- 로컬에 설치된 `@company/ui`의 실제 버전을 확인하지 않았습니다.
- `package-lock.json`에 2.0.0이 기록돼 있는지 확인하지 않았습니다.
- 위 원인 외에 Node 버전이나 캐시가 영향을 줬는지는 확인하지 않았습니다.

## 검증 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 봅니다. 1.4.0이면 로컬 성공의 이유가 설명됩니다.
2. `node_modules/@company/ui/package.json`의 `exports`에서 `./button` 항목이 있는지 봅니다.
3. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드합니다. CI와 같은 에러가 나면 원인이 확정됩니다.
4. 3번에서 재현되지 않으면 Node 18로 같은 절차를 반복합니다.

## 해결 방향

원인이 확정되면 두 가지 중 하나를 선택할 수 있습니다.

- 앱의 import를 2.0.0 `exports`가 공개하는 경로로 바꿉니다.
- `@company/ui` 담당 팀에 `./button` 경로를 `exports`에 추가해 달라고 요청합니다.

2.0.0이 의도적으로 해당 경로를 닫았는지는 변경 로그에서 확인해야 합니다. 이 내용은 아직 모릅니다.
