**결론: 로컬 빌드가 성공하는 이유는 로컬 `node_modules`에 아직 1.4.0이 남아 있기 때문으로 보입니다. 따라서 로컬 성공은 2.0.0이 문제없다는 증거가 아닙니다.** CI 실패는 2.0.0의 `exports` 필드가 `@company/ui/button` 경로를 허용하지 않는 것이 가장 유력한 원인으로 보입니다(추론, 미확인). Node 18과 20의 차이는 보조 변수로 봅니다.

## 확인된 사실

- 3일 전 `@company/ui`가 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0에 `exports` 필드가 새로 추가됐습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 버전 변경 전에 설치됐습니다.

## 추론: 로컬 성공의 이유

로컬 `node_modules`가 버전 변경 전에 설치됐으므로, 로컬 빌드는 1.4.0을 기준으로 `@company/ui/button`을 해석했을 가능성이 높습니다. 1.4.0에서는 `exports` 제한이 없어 해당 경로가 파일로 바로 해석됐을 것입니다. Node 버전 차이로는 로컬 성공을 설명할 필요가 없습니다.

**로컬 빌드가 성공했다는 사실만으로 2.0.0이 정상이라고 판단하면 안 됩니다.** 로컬에서 2.0.0을 설치한 적이 없기 때문입니다.

## 추론: CI 실패의 원인

CI는 2.0.0을 설치했을 가능성이 높습니다. 2.0.0의 `exports` 맵에 `./button` 항목이 없거나 다른 경로로 정의됐다면, Node와 Next.js(webpack)의 모듈 해석이 `@company/ui/button`을 찾지 못합니다.

다만 Node는 `exports`에 없는 경로를 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`로 보고하므로, 보고된 `Cannot find module` 메시지가 어느 도구에서 나온 것인지 확인이 필요합니다. 확인 필요: 전체 에러 로그와 스택 트레이스.

Node 18과 20은 모두 `exports`를 지원하므로 Node 버전만으로 실패를 설명하기는 어렵습니다. 그래도 조건 변수로 배제하지 않았으므로 아래 재현 단계에서 함께 확인합니다.

캐시 키가 lock 파일의 해시이므로 lock 파일이 갱신됐다면 캐시 문제는 원인이 아닐 가능성이 높습니다. 확인 필요: 이번 변경 커밋에 `package-lock.json`이 포함됐는지.

## 확인 순서

1. 저장소의 `package-lock.json`에서 `node_modules/@company/ui` 항목의 버전이 2.0.0인지 확인합니다.
2. CI 로그에서 설치 단계가 출력한 `@company/ui` 버전과 전체 에러 스택을 확인합니다.
3. `npm view @company/ui@2.0.0 exports`로 `exports` 맵에 `./button` 항목이 있는지 확인합니다.
4. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 확인합니다.
5. Node 18 환경에서 `rm -rf node_modules && npm ci` 후 빌드해 CI 조건을 재현합니다. 재현되면 원인은 버전과 `exports`이고, 재현되지 않으면 Node 버전 차이나 CI 설정을 다시 봐야 합니다.

## 권장 조치

- 단기로는 `@company/ui`를 1.4.0으로 되돌리는 방안을 권장합니다. 빌드가 복구될 가능성이 높지만, 이것도 확인 순서 3번과 5번 결과를 본 뒤 판단해야 합니다.
- 장기로는 `@company/ui/button` import를 2.0.0의 `exports` 규칙에 맞게 바꾸거나, 패키지 관리 측에 `./button` 항목 추가를 요청하는 방안을 권장합니다.
- 로컬 개발 환경도 `npm ci`로 다시 설치해, CI와 같은 버전 조건에서 빌드를 검증합니다.
