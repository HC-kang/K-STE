가장 유력한 원인은 `@company/ui` 2.0.0에서 추가된 `exports` 필드가 `button` 하위 경로를 허용하지 않아, CI가 새로 설치한 2.0.0에서 `@company/ui/button`을 찾지 못하는 것입니다. 다만 이 설명은 제공된 증상과 변경 내용에서 추론한 것이며, 패키지 내용이나 CI 로그는 직접 확인하지 않았습니다.

로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 3일 전 이전에 설치되어 1.4.0이 그대로 남아 있기 때문으로 보입니다. 1.4.0에는 `exports` 필드가 없어서 하위 경로 import가 파일 경로 그대로 해석됩니다. 이 추정은 `npm ls @company/ui`로 확인해야 합니다.

CI 캐시는 원인이라기보다 CI가 2.0.0을 받는 경로에 가깝습니다. 캐시 키가 `package-lock.json`의 해시이므로, 업그레이드로 lock 파일이 바뀌었다면 CI는 캐시를 쓰지 못하고 2.0.0을 새로 설치합니다. 다만 lock 파일이 실제로 바뀌었는지는 확인하지 않았습니다.

Node 버전 차이는 단독 원인으로 보기 어렵습니다. Node 18도 `exports` 필드를 지원하므로, 버전 차이만으로 이 실패를 설명하기는 부족합니다. 조건부 `exports`(import, require, types 조건)나 Next.js의 모듈 해석 방식이 Node 버전에 따라 달라질 가능성은 남아 있습니다.

| 항목 | 로컬 | CI |
|---|---|---|
| `@company/ui` 버전 | 1.4.0으로 추정 | 2.0.0으로 추정 |
| Node 버전 | 20 | 18 |
| 의존성 설치 | 3일 전 이전 설치분 재사용 | lock 해시 기준 캐시 확인 후 설치 |
| `@company/ui/button` 해석 | `exports` 없음, 성공으로 추정 | `exports`에 해당 경로 없음, 실패로 추정 |

원인을 확정하려면 다음을 확인합니다.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. CI 로그에서 `npm ls @company/ui` 결과를 출력해 CI가 설치한 버전을 확인합니다.
3. `node_modules/@company/ui/package.json`의 `exports` 필드에 `./button` 항목이 있는지 확인합니다.
4. 2.0.0 변경 로그에서 하위 경로 import가 제거되었거나 경로가 바뀌었는지 확인합니다.
5. Node 18 환경에서 로컬을 재현하려면 `nvm`으로 Node 18을 설정한 뒤 `npm ci`를 실행합니다.

해결 방향은 세 가지입니다. 2.0.0이 공개한 진입점으로 import 경로를 바꾸는 방법, 패키지 관리자에게 `exports`에 해당 경로 추가를 요청하는 방법, 확인이 끝날 때까지 `@company/ui`를 1.4.0으로 고정하는 방법입니다. 어떤 방법이 맞는지는 3번과 4번의 결과에 따라 달라집니다.
