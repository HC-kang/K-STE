가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드가 `@company/ui/button` 같은 하위 경로를 모두 허용하지 않는 것입니다. CI는 캐시가 빗나가서 2.0.0을 새로 설치하므로 이 문제를 만나고, 로컬은 3일 전에 설치한 `node_modules`를 계속 써서 1.4.0으로 빌드하므로 성공합니다. 다만 저장소 코드와 패키지 내용은 아직 직접 확인하지 않았습니다. 아래 내용은 전달해 주신 사실에서 추론한 것입니다.

## 원인 설명

1.4.0에는 `exports` 필드가 없습니다. 그래서 패키지 안의 어떤 파일이든 `@company/ui/button`으로 가져올 수 있습니다. 2.0.0에는 `exports` 필드가 생겼습니다. Node와 번들러는 이 필드에 적힌 경로만 허용합니다. 2.0.0의 `exports`에 `./button` 항목이 없으면 같은 import가 실패합니다.

에러 문구 `Cannot find module`만으로는 어느 해석기가 실패를 냈는지 알 수 없습니다. 전체 스택 트레이스를 보면 Next.js의 webpack 해석기인지, Node의 require인지 구분할 수 있습니다.

## 로컬이 성공하는 이유

로컬 `node_modules`는 3일 전보다 먼저 설치한 것이므로 1.4.0일 가능성이 높습니다. 따라서 로컬 빌드 성공은 1.4.0에서 import가 동작한다는 증거일 뿐, 2.0.0에서 동작한다는 증거가 아닙니다. 두 환경은 같은 조건으로 비교되지 않았습니다.

## CI에서만 실패하는 이유

`package-lock.json` 해시가 바뀌었으므로 CI 캐시가 맞지 않고, CI는 2.0.0을 새로 설치합니다. 로컬은 캐시가 아니라 오래된 `node_modules`를 씁니다.

확인 필요: 커밋된 `package-lock.json`에 2.0.0 변경이 반영되어 있는지는 알 수 없습니다. 반영되지 않았다면 CI 설치 결과도 달라질 수 있습니다.

## 함께 볼 변수

Node 18과 Node 20의 차이도 원인이 될 수 있습니다. 2.0.0이 ESM 전용이거나 `import` 조건만 열어 두었다면 Node 18에서 `require`가 실패할 수 있습니다. 이 부분은 추론이며 패키지 구조를 보기 전에는 확정할 수 없습니다.

CI 캐시 키에 Node 버전이 없다는 점도 기록해 둘 만합니다. 다만 이번 원인으로 보기는 어렵습니다. 락 파일 해시가 바뀌었기 때문입니다.

## 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 확인합니다.
2. 2.0.0 패키지의 `package.json`에서 `exports` 맵에 `./button`이 있는지 확인합니다.
3. CI 로그에서 캐시가 맞지 않았는지와 설치된 `@company/ui` 버전을 확인합니다.
4. 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치하고 빌드합니다. 여기서도 실패하면 원인은 CI 환경이 아니라 패키지와 import 경로입니다.
5. 로컬을 Node 18로 바꿔 같은 빌드를 돌려 Node 버전 영향을 분리합니다.

## 수정 방향

1. import 경로를 2.0.0의 `exports`가 허용하는 경로로 바꿉니다. 앱 코드만 고치므로 가장 깔끔합니다. 허용 경로는 2번 확인 결과에 따라 달라집니다.
2. 배포를 빨리 막힌 상태에서 풀어야 하면 `@company/ui`를 1.4.0으로 되돌립니다. 되돌림은 가장 빠른 임시 조치입니다.
3. 패키지 쪽 `exports`에 하위 경로를 추가하는 방법도 있습니다. 패키지 관리자와 협의가 필요합니다.

확인 필요: 이 빌드 실패가 현재 배포를 막고 있는지, 그리고 2.0.0으로 올린 이유가 무엇인지는 전달해 주신 내용에 없습니다. PM은 이 두 가지를 먼저 확인해야 우선순위를 정할 수 있습니다.
