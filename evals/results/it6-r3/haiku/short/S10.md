원인은 2.0.0에 추가된 `exports` 필드(패키지 외부에 공개할 파일 경로를 정하는 설정)가 `@company/ui/button` 경로를 허용하지 않거나 가리키는 파일이 없기 때문일 가능성이 높습니다. 다만 아직 확인하지 않았으므로 수정이 되었다고 볼 수 없습니다.

## 확인된 사실

- `@company/ui`를 3일 전에 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키(캐시를 구분하는 값)는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 업그레이드 전에 설치되었습니다.

## 추론

- 로컬 빌드가 성공하는 이유는 로컬이 여전히 1.4.0을 쓰기 때문으로 보입니다. `npm install`을 다시 실행하지 않았다면 `node_modules`는 바뀌지 않습니다. 따라서 로컬 성공은 2.0.0에서 빌드가 된다는 근거가 되지 않습니다.
- CI는 2.0.0을 새로 받아 설치합니다. `package-lock.json`이 바뀌면 캐시 키도 바뀌어 CI가 새로 설치하기 때문입니다.
- 2.0.0의 `exports`가 `./button` 경로를 빠뜨렸거나 파일 위치를 바꾼 것으로 보입니다. 이 경우 import 경로가 맞지 않아 모듈을 찾지 못합니다.
- Node 18과 20의 차이가 원인일 가능성은 낮습니다. 두 버전 모두 `exports` 필드를 지원합니다. 다만 2.0.0이 ESM 전용 패키지라면 `require` 방식으로 불러올 때 두 버전 모두에서 실패할 수 있습니다.

## 확인 필요

- 에러를 낸 주체가 Next.js 빌드인지, `next.config.js`나 별도 스크립트인지 확인이 필요합니다. `exports`에서 경로를 막으면 Node는 보통 다른 메시지를 내므로, 이 메시지가 어느 도구에서 나왔는지 확인해야 합니다.
- CI 로그에서 실제로 설치된 `@company/ui` 버전이 2.0.0인지 확인이 필요합니다.
- 2.0.0의 `exports` 필드에 `./button` 항목이 있는지 확인이 필요합니다.
- 2.0.0이 ESM 전용 패키지인지 확인이 필요합니다.
- 커밋된 `package-lock.json`에 2.0.0이 기록되어 있는지 확인이 필요합니다.

## 다음 단계

1. 로컬 `node_modules`를 삭제하고 `npm ci`로 다시 설치하여 2.0.0이 설치되는지 확인합니다.
2. `node_modules/@company/ui/package.json`의 `exports` 항목에서 `./button` 경로가 있는지 확인합니다.
3. 로컬에서 Node 18로 바꾸어 빌드하여 CI 실패를 재현합니다.
4. 재현되면 import 경로를 `exports`가 허용하는 경로로 고치거나, 패키지 담당자에게 `exports` 항목 추가를 요청합니다.
5. 급하면 `@company/ui`를 1.4.0으로 고정하여 배포를 먼저 풀 수 있습니다.
