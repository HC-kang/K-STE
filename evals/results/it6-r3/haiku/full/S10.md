가장 유력한 원인은 로컬 `node_modules`가 3일 전 설치본이라서 로컬 빌드가 아직 `@company/ui` 1.4.0을 쓰고 있을 가능성입니다. 이 경우 로컬 빌드 성공은 2.0.0에서도 빌드가 된다는 근거가 되지 못합니다. 이것은 추론이며, 아래 확인 단계로 검증해야 합니다.

**제공된 사실**

- CI에서만 `Cannot find module '@company/ui/button'` 오류로 빌드가 실패합니다.
- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸고, 2.0.0에는 `exports` 필드가 추가되었습니다.
- CI는 Node 18, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json` 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

**추론**

1. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`이 패키지 안의 파일 경로로 그대로 해석됩니다. 로컬이 1.4.0을 쓰고 있다면 로컬에서는 이 import가 정상 동작합니다.
2. `exports` 필드가 있으면 하위 경로 import는 `exports`에 정의된 경로만 허용됩니다. 2.0.0의 `exports`에 `./button` 항목이 없거나 다른 경로로 매핑되어 있다면 CI와 2.0.0 기준 환경에서 import가 실패합니다.
3. CI가 오래된 캐시를 복원했거나 lock 파일이 갱신되지 않은 상태로 설치했을 수도 있습니다. 캐시 키가 lock 파일 해시이므로 lock 파일이 실제로 바뀌었는지부터 확인해야 합니다.
4. Node 18과 20 차이가 원인일 가능성은 낮습니다. 두 버전 모두 `exports`를 지원합니다. 다만 Node 18은 지원이 종료된 버전이므로 다른 호환성 문제가 섞여 있을 수 있어 함께 확인하는 것이 좋습니다.

한편 `Cannot find module`은 Node의 CommonJS 로딩 오류 문구와 비슷합니다. `exports`가 경로를 차단할 때 Node가 내는 오류는 보통 다른 문구이므로, 실패가 Next.js 빌드 중에 났는지, 설정 파일 로딩 중에 났는지, 다른 도구에서 났는지 전체 스택 트레이스로 확인해야 합니다.

**확인 단계**

1. 로컬에서 `npm ls @company/ui`를 실행해 실제 설치 버전을 확인합니다.
2. CI 로그에서 실패한 단계와 전체 스택 트레이스를 확인합니다.
3. CI 설치 로그나 `npm ls @company/ui`로 CI가 설치한 버전을 확인합니다.
4. 2.0.0 패키지의 `package.json`에서 `exports` 필드에 `./button` 또는 `./*` 매핑이 있는지 확인합니다.
5. 로컬에서 `rm -rf node_modules` 후 `npm ci`로 다시 설치하고 빌드합니다. 여기서 실패하면 패키지 설정 문제가 확정됩니다.
6. CI 캐시를 비우고 다시 실행합니다. 캐시 복원에 `restore-keys` 대체 키가 있는지도 함께 확인합니다.
7. 로컬에서 Node 18로 빌드해 Node 버전 영향을 확인합니다.

**PM에게 전할 요약**

CI 빌드가 실패하고 있으며 원인은 아직 확정되지 않았습니다. 가장 유력한 가설은 로컬과 CI가 서로 다른 버전의 `@company/ui`를 쓰고 있다는 것입니다. 확인 단계 1부터 5까지 완료한 뒤 결과를 공유하겠습니다. 2.0.0의 `exports`에 `./button` 매핑이 없는 것으로 확인되면, 패키지 관리자에게 경로를 문의하거나 import 경로를 공식 경로로 바꾸는 방안을 검토해야 합니다.
