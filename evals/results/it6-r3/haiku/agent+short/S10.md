# CI 빌드 실패 원인 분석

현재 증거로 가장 유력한 원인은 2.0.0에서 추가된 `exports` 필드가 `@company/ui/button` 경로를 공개하지 않는 것이다. 다만 이는 추론이며, 패키지 내용과 CI 로그는 아직 확인하지 않았다.

## 확인된 사실

- `@company/ui`는 3일 전 1.4.0에서 2.0.0으로 올라갔다.
- 2.0.0에 `exports` 필드(패키지가 외부에 공개할 경로를 정한 목록)가 추가됐다.
- CI는 Node 18을, 로컬은 Node 20을 사용한다.
- CI 캐시 키는 `package-lock.json`의 해시(파일 내용을 요약한 짧은 값)다.
- 로컬 `node_modules`는 업그레이드 전에 설치됐다.
- 실패 메시지는 `Cannot find module '@company/ui/button'`이다.

## 원인 후보

| 후보 | 근거 | 확인 방법 | 판단 |
|---|---|---|---|
| `exports`가 `./button` 경로를 공개하지 않음 | `exports`는 2.0.0에서 추가됐고, 실패한 경로가 하위 경로(`/button`)다. 1.4.0에는 이 제한이 없었다. | 2.0.0의 `package.json`에서 `exports` 항목을 확인한다. | 가장 유력 |
| 로컬에 여전히 1.4.0이 설치됨 | 로컬 `node_modules`가 업그레이드 전에 설치됐다. 로컬 빌드가 성공한 이유를 가장 잘 설명한다. | `npm ls @company/ui`를 실행한다. | 유력. 로컬 성공은 2.0.0 검증이 아니었을 가능성이 크다. |
| CI가 2.0.0을 설치하지 않음 | 커밋된 lock 파일에 2.0.0이 반영되지 않았다면 CI는 이전 버전으로 빌드한다. | 커밋된 `package-lock.json`에서 `@company/ui` 버전을 확인한다. | 확인 필요 |
| Node 18과 Node 20 차이 | Node 18도 `exports`를 지원하므로 버전 차이만으로 설명하기 어렵다. | 로컬에서 Node 18로 빌드한다. | 낮음. 배제되지 않았다. |
| 캐시가 오래된 모듈을 복원함 | 캐시 키가 lock 파일 해시라서 lock이 바뀌면 캐시도 새로 만들어진다. 복원 키(`restore-keys`)가 이전 캐시를 불러오도록 설정돼 있으면 문제가 생길 수 있다. | 워크플로 파일의 `actions/cache` 설정에서 `restore-keys`를 확인한다. | 낮음. 확인 필요 |

에러 메시지 형식도 단서가 된다. Node가 `exports` 제한을 위반했을 때 내는 메시지는 보통 "is not defined by exports"라는 문구를 포함한다. 지금 메시지는 "Cannot find module"이므로, 경로가 `exports`에서 막혔는지 아니면 `exports`가 가리키는 파일이 없는지 구분할 수 없다. 전체 스택 트레이스(에러가 어느 단계에서 났는지 보여 주는 기록)를 확인해야 한다.

## 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 실제로 설치된 버전을 확인한다.
2. `node_modules/@company/ui/package.json`의 `exports`에 `./button` 항목이 있는지 확인한다.
3. 커밋된 `package-lock.json`에 `@company/ui` 2.0.0이 기록돼 있는지 확인한다.
4. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드해 2.0.0 기준으로 재현한다.
5. 같은 빌드를 Node 18로 실행해 Node 버전의 영향을 확인한다.

## 현재 상태

원인은 아직 확정되지 않았다. 1번과 2번을 확인하면 대부분의 후보가 정리된다. 2번에서 `./button`이 없으면 원인은 `exports`이고, 해결은 패키지 쪽의 경로 공개 또는 import 경로 변경 중 하나다. 1번에서 1.4.0이 나오면 로컬 빌드는 2.0.0을 검증하지 않은 것이다.
