CI 빌드 실패의 가장 유력한 원인은 `@company/ui` 2.0.0에서 새로 추가된 `exports` 필드(패키지가 외부에 공개할 파일 경로를 정하는 설정)다. 로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 2.0.0 이전에 설치돼 1.4.0 파일을 그대로 쓰고 있기 때문으로 보인다. 따라서 로컬 빌드 성공은 2.0.0이 동작한다는 증거가 아니다.

## 확인된 사실

CI에서 발생한 에러는 `Cannot find module '@company/ui/button'`이다.
`@company/ui`는 3일 전에 1.4.0에서 2.0.0으로 올랐다.
2.0.0에는 `exports` 필드가 새로 추가됐다.
CI는 Node 18을, 로컬은 Node 20을 쓴다.
CI 캐시 키는 `package-lock.json`(설치 버전을 고정한 목록) 해시다.
로컬 `node_modules`는 3일 전보다 먼저 설치됐다.

## 원인 추정

`exports` 필드가 있으면 Node와 Next.js 번들러는 패키지가 명시적으로 공개한 경로만 가져올 수 있다. 1.4.0에는 이 필드가 없어서 `@company/ui/button`이 파일 경로 그대로 해석됐다. 2.0.0의 `exports`가 `./button` 경로를 공개하지 않거나 다른 이름으로 공개하면, 같은 import는 실패한다. 이 추정은 2.0.0 패키지 내용을 아직 열어 보지 않았으므로 미확인 상태다.

로컬과 CI의 차이는 설치 시점에서 생긴다. 로컬은 오래된 `node_modules`를 재사용하고, CI는 lock 파일 기준으로 새로 설치한다. 그래서 CI만 2.0.0을 받고 로컬은 1.4.0을 쓰는 상황이 생긴다.

CI 캐시 키가 lock 파일 해시이므로, lock 파일이 바뀌면 캐시 키도 바뀌어 새 설치가 일어난다. 따라서 캐시 키만으로는 CI가 1.4.0을 계속 쓰는 상황을 설명하기 어렵다. 다만 복원 키(restore-keys, 정확히 일치하는 캐시가 없을 때 쓰는 대체 키)가 오래된 캐시를 불러오도록 설정돼 있다면 1.4.0 파일이 복원될 수 있다. 확인 필요: CI 워크플로의 restore-keys 설정.

Node 18과 20의 차이가 원인일 가능성은 낮은 것으로 보인다. 두 버전 모두 `exports` 필드를 지원한다. 다만 확인 전에는 배제하지 않는다.

## 확인 방법

1. CI 로그에서 `npm ls @company/ui`의 결과를 확인한다. 이 결과로 CI가 실제로 설치한 버전이 2.0.0인지 확정한다.
2. 2.0.0 패키지의 `package.json`에서 `exports` 맵을 열어 `./button` 경로가 있는지 확인한다. 경로가 없으면 import 경로를 바꿔야 한다는 의미다.
3. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드한다. 로컬에서도 같은 에러가 나면 CI 환경 문제가 아니라 패키지 변경 문제로 확정된다.
4. 로컬에서 Node 18로 같은 빌드를 실행해 Node 버전 차이를 배제한다.
5. CI 워크플로의 캐시 단계와 `npm ci` 또는 `npm install` 사용 여부를 확인한다.

## 권장 조치

- 2.0.0의 새 기능이 이번 릴리스에 바로 필요하지 않으면 `@company/ui`를 1.4.0으로 되돌려 CI를 복구한다. 이 방법은 빠르지만 2.0.0 적용이 늦어진다.
- 2.0.0 기능이 필요하면 import 경로를 2.0.0이 공개한 경로로 바꾸거나, 패키지 팀에 `./button` 경로 공개를 요청한다.

PM이 정해야 할 사항은 2.0.0 기능이 이번 릴리스에 필요한지 여부다. 이 답에 따라 되돌리기와 경로 수정 중 하나를 고른다.
