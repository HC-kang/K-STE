## 결론

CI 빌드 실패의 가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드(패키지 외부에 공개할 경로를 정하는 설정)이다. 코드의 `@company/ui/button` 경로가 2.0.0의 `exports`에 없으면 모듈을 찾지 못하는 것으로 보인다. 다만 이 분석은 전달받은 내용만 근거로 한 추론이며, 저장소와 CI 로그는 확인하지 않았다. 원인은 아래 확인 항목으로 확정해야 한다.

## 로컬은 성공하고 CI는 실패하는 이유

로컬 `node_modules`(내 PC에 설치된 패키지 폴더)는 3일 전보다 먼저 설치되었다. 따라서 로컬에는 `@company/ui` 1.4.0이 그대로 남아 있을 가능성이 크다. 1.4.0에는 `exports` 필드가 없으므로 `@company/ui/button` 경로가 제한 없이 열려 있고, 그래서 로컬 빌드는 통과한다. 이 부분은 추론이다.

CI는 `package-lock.json`의 해시를 캐시 키(캐시를 찾는 기준값)로 쓴다. lock 파일(설치할 패키지 버전을 기록한 파일)이 2.0.0으로 바뀌었다면 캐시 키도 바뀌고, CI는 2.0.0을 새로 설치한다. 그 결과 `exports`에 막힌 경로를 import하게 되어 빌드가 실패하는 것으로 보인다.

Node 버전 차이는 가능성이 낮다. Node 18과 Node 20은 모두 `exports` 필드를 지원한다. 다만 2.0.0의 `engines` 항목(패키지가 요구하는 Node 버전)이 Node 20 이상을 요구하는지는 확인해야 한다.

| 항목 | 로컬 | CI | 구분 |
|---|---|---|---|
| Node 버전 | 20 | 18 | 전달받은 사실 |
| `node_modules` 설치 시점 | 3일 전보다 먼저 | 캐시 키가 바뀌면 새로 설치 | 캐시 동작은 추론 |
| `@company/ui` 버전 | 1.4.0으로 보임 | 2.0.0으로 보임 | 추론 |
| 빌드 결과 | 성공 | 실패 | 전달받은 사실 |

**로컬 빌드 성공은 2.0.0이 동작한다는 증거가 아니다.** 로컬은 2.0.0을 설치한 적이 없을 가능성이 크기 때문이다.

## 확인 필요 항목

1. 로컬에서 `npm ls @company/ui`를 실행해 실제 설치 버전을 확인한다.
2. `node_modules/@company/ui/package.json`의 `exports` 필드에 `./button` 또는 `./*` 항목이 있는지 확인한다.
3. CI의 설치 단계 로그에서 설치된 `@company/ui` 버전을 확인한다.
4. 커밋된 `package-lock.json`이 2.0.0으로 갱신되어 있는지 확인한다.
5. 캐시 설정에 `restore-keys`(키가 일치하지 않을 때 비슷한 이전 캐시를 복원하는 설정)가 있는지 확인한다. 있다면 이전 버전의 패키지가 섞일 수 있다.
6. 2.0.0의 `engines` 항목을 확인한다.

## 권장 조치

원인이 확인되면 세 가지 방법 중 하나를 선택하는 것을 권장한다. 첫째, import 경로를 2.0.0의 `exports`에 공개된 경로로 바꾼다. 이 방법을 가장 권장한다. 둘째, `@company/ui`를 소유한 팀에 `./button` 경로 추가를 요청한다. 셋째, 1.4.0으로 버전을 되돌린다.

수정 후에는 로컬 `node_modules`를 삭제하고 `npm ci`를 다시 실행해 2.0.0 상태에서 빌드를 검증해야 한다. 그 뒤에 CI에서도 같은 빌드가 통과하는지 확인해야 한다.
