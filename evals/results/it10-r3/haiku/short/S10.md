로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 2.0.0 이전 버전(1.4.0)을 담고 있기 때문일 가능성이 높다. CI 실패의 유력한 원인은 2.0.0에 새로 추가된 `exports` 필드가 `@company/ui/button` 같은 하위 경로 import를 막는 것이다. 이 내용은 패키지나 저장소를 직접 확인하지 않고 주어진 정보만으로 세운 추론이며, 아직 검증하지 않았다.

## 확인된 사실

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0 패키지에 `exports` 필드가 추가됐다.
- CI는 Node 18을, 로컬은 Node 20을 사용한다.
- CI 캐시 키는 `package-lock.json`의 해시다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치됐다.
- 에러 메시지는 `Error: Cannot find module '@company/ui/button'`이다.

## 추론 (미검증)

`exports` 필드가 있으면 Node와 번들러는 그 필드에 명시된 경로만 import를 허용한다. 1.4.0에는 `exports`가 없으므로 `@company/ui/button`이 파일 경로로 바로 해석됐다. 2.0.0의 `exports`에 `./button` 항목이 없거나 경로 이름이 바뀌었다면 같은 import가 실패한다. 에러가 하위 경로 import에서만 발생한다는 점이 이 가설과 맞아떨어진다.

로컬이 성공하는 이유도 같은 맥락으로 설명된다. 로컬 `node_modules`가 1.4.0이라면 로컬 빌드는 2.0.0을 검증하지 않은 셈이다.

CI에서 2.0.0이 설치됐다는 전제는 캐시 구조와 맞는다. 캐시 키가 lock 파일 해시이므로, 업그레이드로 lock이 바뀌었다면 CI는 캐시를 쓰지 못하고 새로 설치해 2.0.0을 받는다.

Node 버전 차이는 가능성이 낮다. Node 18과 20 모두 `exports`를 지원하므로 이것만으로 에러를 설명하기 어렵다. 다만 조건부 export 해석 방식의 차이는 확인하지 않았다.

## 가설 비교

| 가설 | 근거 | 확인 방법 | 가능성 |
|---|---|---|---|
| 2.0.0의 `exports`에 `./button`이 없거나 바뀜 | 2.0.0에서 `exports`가 추가됐고, 에러가 하위 경로 import에서 발생함 | 2.0.0의 `package.json`에서 `exports` 필드 확인 | 높음 |
| 로컬 `node_modules`가 1.4.0 상태임 | 로컬 설치가 3일 전보다 먼저 이뤄짐 | 로컬에서 `npm ls @company/ui` 실행 | 높음 |
| Node 18과 20의 해석 차이 | 실행 환경만 다름 | Node 18로 로컬 빌드 실행 | 낮음 |
| 캐시 문제 | 캐시 키가 lock 해시임 | CI 로그에서 캐시 적중 여부와 설치된 버전 확인 | 낮음 |

## 확인 방법

1. 사내 레지스트리에서 2.0.0의 `exports` 필드 내용을 확인한다.
2. 로컬에서 `npm ls @company/ui`를 실행해 실제 설치된 버전을 확인한다.
3. CI 로그에서 설치 단계가 2.0.0을 받았는지 확인한다.
4. 로컬에서 Node 18로 빌드해 Node 버전의 영향을 분리한다.

## 권장 조치

- 1번 확인 결과에 따라 두 가지 중 하나를 고른다. 패키지 쪽 `exports`에 `./button`을 추가해 달라고 요청하거나, 앱의 import 경로를 2.0.0이 내보내는 경로로 바꾼다.
- 로컬에서 `npm ci`로 lock 파일 기준 설치를 다시 한 뒤 빌드를 재현해야 한다. 로컬 성공을 근거로 삼지 않는 것이 좋다.
- 조치 전까지 CI의 `@company/ui` 버전을 문서에 명시한다.
