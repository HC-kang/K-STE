가장 유력한 원인은 CI만 `@company/ui` 2.0.0을 설치하고, 2.0.0의 `exports` 필드에 `./button` 경로가 없는 것입니다. 이 결론은 주어진 정황에서 추론한 것이고, 2.0.0 패키지의 실제 내용은 아직 확인하지 않았습니다.

추론의 근거는 세 가지입니다.

- 로컬 `node_modules`는 버전을 올리기 3일 전보다 먼저 설치했습니다. 그래서 로컬은 1.4.0을 그대로 쓰고 있을 가능성이 높습니다.
- `exports` 필드는 패키지가 외부에 공개하는 파일 경로의 목록입니다. 이 필드가 있으면 Node와 번들러(코드를 묶는 빌드 도구)는 목록에 적힌 경로만 허용합니다. 1.4.0에는 이 필드가 없어서 `@company/ui/button`처럼 안쪽 파일을 직접 가져올 수 있었습니다. 2.0.0에서는 목록에 `./button`이 없으면 파일이 있어도 `Cannot find module` 오류가 납니다.
- CI 캐시 키가 `package-lock.json`의 해시이므로, 버전을 올리면서 lock 파일이 바뀌었다면 캐시가 무효화됩니다. 그러면 CI는 2.0.0을 새로 설치합니다.

Node 18과 20의 차이는 주원인일 가능성이 낮다고 봅니다. `exports` 필드는 두 버전 모두 지원하기 때문입니다. 다만 이 판단도 CI에서 직접 확인하지 않았습니다.

다음 순서로 확인하면 원인을 확정할 수 있습니다.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 확인합니다.
2. 로컬에서 `rm -rf node_modules && npm ci`로 lock 파일 기준 재설치를 한 뒤 빌드합니다. 같은 오류가 나면 원인은 버전 차이로 확정됩니다.
3. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 확인합니다.
4. 2단계에서 재현되지 않으면 Node 버전을 의심합니다. 이때 로컬을 Node 18로 맞춰 다시 빌드합니다.

3단계에서 `./button`이 없다면 해결 방법은 둘 중 하나입니다. `exports`에 공개된 경로로 import 문을 고치거나, `@company/ui` 담당자에게 `./button`을 `exports`에 추가해 달라고 요청해야 합니다.

PM이 알아야 할 영향은 하나입니다. 로컬 빌드가 성공해도 CI 빌드는 실패하므로, 원인을 해결하기 전에는 CI를 거치는 배포를 할 수 없습니다.
