## 결론

가장 가능성이 높은 원인은 `@company/ui` 2.0.0에서 추가된 `exports` 필드입니다. 이 필드가 외부에 공개할 경로를 제한하므로, `@company/ui/button`처럼 하위 경로를 직접 가져오는 import가 2.0.0에서는 해석되지 않을 수 있습니다. 로컬에는 업그레이드 전에 설치된 1.4.0이 남아 있어 빌드가 통과하고, CI는 lock 파일 기준으로 새로 설치해 2.0.0을 받아 실패하는 것으로 보입니다.

## 근거

- `exports` 필드는 패키지 사용자가 가져올 수 있는 파일 경로를 패키지 작성자가 정하는 설정입니다. 이 필드가 있으면 목록에 없는 하위 경로는 가져올 수 없습니다.
- CI 캐시 키가 `package-lock.json`의 해시이므로, 업그레이드로 lock 파일이 바뀌었다면 캐시가 맞지 않아 새로 설치되었을 것입니다. 새 설치는 2.0.0을 받습니다.
- 로컬 `node_modules`가 3일 전 이전에 설치되었다면 1.4.0이 들어 있을 가능성이 높습니다. 1.4.0에는 `exports` 필드가 없으므로 하위 경로 import가 그대로 통과합니다.

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `@company/ui` 버전 | 1.4.0으로 보임 (설치 시점 기준) | 2.0.0으로 보임 (lock 기준 새 설치) |
| `exports` 필드 적용 | 없음 | 있음 |
| 하위 경로 import | 통과 | 실패 |

## 확인되지 않은 점

- 2.0.0의 `exports` 목록에 `./button`이 빠졌는지는 아직 확인하지 않았습니다.
- CI가 실제로 2.0.0을 설치했는지는 로그로 확인하지 않았습니다.
- 로컬 `node_modules`가 실제로 1.4.0인지도 확인하지 않았습니다.
- Node 버전 차이가 원인인지는 이 정보만으로 판단할 수 없습니다. `exports` 해석은 Node 18과 20 모두 지원하므로 직접 원인일 가능성은 낮습니다. 다만 빌드 도구가 Node 버전에 따라 다르게 동작할 수 있어 배제하지는 않았습니다.

## 다음 단계

1. CI 로그에서 `@company/ui`의 설치 버전을 확인하십시오. 또는 CI와 같은 환경에서 `npm ls @company/ui`를 실행하십시오.
2. 2.0.0 패키지의 `package.json`에서 `exports` 필드를 열어 `./button` 경로가 있는지 확인하십시오.
3. 로컬에서 `rm -rf node_modules && npm ci`를 실행하고 빌드하십시오. 로컬에서도 실패하면 원인이 버전 업그레이드라는 점이 확정됩니다.
4. 2.0.0의 `exports`에 `./button`이 없다면, 앱 코드를 패키지가 공개한 진입점에서 import하도록 바꾸거나 `@company/ui` 담당자에게 경로 추가를 요청하십시오. 어느 쪽이 맞는지는 2.0.0의 공개 목록을 본 뒤에 정하십시오.
