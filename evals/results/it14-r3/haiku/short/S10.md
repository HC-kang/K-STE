가장 가능성이 높은 원인은 로컬 환경이 2.0.0을 설치해 검증하지 않았다는 점입니다. 로컬 `node_modules`가 3일 전보다 먼저 설치되었으므로 `@company/ui`가 1.4.0으로 남아 있을 가능성이 큽니다. 이 경우 로컬 빌드 성공은 2.0.0에서의 성공을 뜻하지 않습니다. 이 내용은 추론이며 아직 확인하지 않았습니다.

## 확인된 사실

- 2.0.0에서 패키지에 `exports` 필드(패키지 외부에 공개할 파일 경로를 정하는 설정)가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

## 추론

로컬과 CI의 차이를 표로 정리하면 다음과 같습니다.

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `@company/ui` 설치 버전 | 1.4.0일 가능성이 높음 | 2.0.0일 가능성이 높음 (확인 필요) |
| `node_modules` 출처 | 3일 전 설치본 | 캐시 키 변경 시 새로 설치 |
| 빌드 결과 | 성공 | 실패 |

2.0.0의 `exports`에 `./button` 같은 하위 경로가 없으면 1.4.0에서 되던 `@company/ui/button` import는 2.0.0에서 해석되지 않습니다. 로컬이 1.4.0을 쓰고 있다면 같은 import가 로컬에서는 계속 성공합니다.

Node 18과 20은 모두 `exports`를 지원하므로 Node 버전 차이만으로 이 에러를 설명하기는 어렵습니다. 다만 Node 18은 2025년 4월에 지원이 종료되었으므로, 번들러나 타입 검사기가 Node 버전에 따라 다르게 동작할 가능성은 남아 있습니다.

## 확인 필요

이 분석은 저장소와 패키지 내용을 직접 확인하지 않았습니다. 원인을 특정하려면 다음 항목을 확인해야 합니다.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. CI 로그에서 CI가 설치한 `@company/ui` 버전을 확인합니다.
3. 2.0.0의 `package.json`에서 `exports` 필드에 `./button` 경로가 있는지 확인합니다.
4. CI 워크플로의 캐시 설정에 `restore-keys`가 있는지 확인합니다. 이 설정이 있으면 이전 캐시가 복원되어 CI도 구버전 `node_modules`를 쓸 수 있습니다.
5. 에러 메시지 전체 로그를 확인합니다. `Cannot find module`은 여러 도구에서 나오는 메시지이므로 로그 전체가 있어야 어느 단계에서 실패했는지 판단할 수 있습니다.

확인 결과 `exports`에 `./button`이 없다면, import 경로를 `@company/ui`의 루트 import로 바꾸거나 패키지 관리자에게 하위 경로를 `exports`에 추가해 달라고 요청할 수 있습니다.
