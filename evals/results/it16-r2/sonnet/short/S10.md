로컬은 `@company/ui` 1.4.0을 쓰고 CI는 2.0.0을 새로 설치하기 때문에, 2.0.0의 `exports` 필드가 `@company/ui/button` 경로를 공개하지 않을 가능성이 가장 높습니다. 아직 2.0.0의 `exports` 내용을 직접 보지 않았으므로 이 결론은 추론입니다.

## 확인된 사실

| 항목 | 로컬 | CI |
|---|---|---|
| Node | 20 | 18 |
| `node_modules` | 3일 전보다 먼저 설치함 | 캐시 키가 `package-lock.json`의 해시임 |
| 빌드 결과 | 성공 | `Cannot find module '@company/ui/button'` |

`@company/ui`는 3일 전에 1.4.0에서 2.0.0으로 올랐고, 2.0.0부터 패키지에 `exports` 필드가 있습니다.

## 추론한 원인

`exports` 필드는 패키지가 외부에 공개하는 import 경로를 패키지가 직접 정하는 설정입니다. 필드가 있으면 목록에 없는 경로는 파일이 실제로 있어도 import할 수 없습니다.

1.4.0에는 `exports`가 없었으므로 `@company/ui/button`이 파일 경로 그대로 열렸습니다. 2.0.0의 `exports`에 `./button`이 없거나 경로가 바뀌었다면, 같은 import가 "모듈 없음"으로 실패합니다.

로컬 `node_modules`는 업그레이드 전에 설치한 것이므로 아직 1.4.0일 가능성이 큽니다. 그래서 로컬 빌드는 2.0.0을 한 번도 거치지 않고 성공했습니다. CI는 업그레이드로 `package-lock.json`(설치할 정확한 버전을 기록한 파일)이 바뀌면서 캐시 키도 바뀌었을 것이고, 2.0.0을 새로 설치해 실패했을 것입니다.

## Node 버전의 영향

Node 18도 `exports`를 지원하므로 Node 18과 20의 차이는 주원인일 가능성이 낮습니다. 다만 실행해서 확인하지는 않았습니다.

## 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 봅니다.
2. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 봅니다.
3. `rm -rf node_modules && npm ci`로 로컬을 다시 설치한 뒤 `npm run build`를 실행해, 로컬에서도 같은 에러가 나는지 봅니다.

3번에서 에러가 재현되면 원인은 확정입니다.

## 해결 방향

- `@company/ui` 쪽 수정: 2.0.0의 `exports`에 `./button`을 추가하는 방법을 권장합니다. 앱 코드를 바꾸지 않아도 됩니다.
- 앱 쪽 수정: `exports`가 공개하는 경로로 import를 바꿉니다. 2.0.0이 `button`을 다른 경로로 옮겼다면 이 방법을 써야 합니다.

## 확인 필요

- `@company/ui` 2.0.0의 `exports`가 `./button`을 공개하는지 확인이 필요합니다.
- 2.0.0에서 `button` 파일 위치나 이름이 바뀌었는지 확인이 필요합니다.
- 로컬 `node_modules`의 `@company/ui` 버전이 실제로 1.4.0인지 확인이 필요합니다.
