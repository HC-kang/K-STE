현재 자료로 가장 유력한 원인은 로컬 `node_modules`에 `@company/ui` 1.4.0이 그대로 남아 있어서, 로컬 빌드가 2.0.0 변경을 한 번도 검사하지 않았다는 것입니다. 이는 추론이며, 로컬 설치 버전을 확인하기 전까지는 사실로 볼 수 없습니다.

## 확인된 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에서 패키지에 `exports` 필드(패키지 바깥에서 쓸 수 있는 경로를 정한 설정)가 추가되었습니다.
- 로컬 `node_modules`(의존성 패키지가 설치되는 폴더)는 3일 전보다 먼저 설치되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`(설치할 정확한 버전을 기록한 파일)의 해시(파일 내용을 요약한 값)입니다.

## 추론되는 원인

1. 로컬 `node_modules`가 1.4.0을 그대로 쓰고 있을 가능성이 큽니다. 3일 전보다 먼저 설치되었고 그 뒤 다시 설치하지 않았다면, 로컬 빌드는 2.0.0이 아니라 1.4.0으로 성공한 것입니다.
2. 2.0.0의 `exports` 필드에 `./button` 경로가 없거나 이름이 바뀌었을 가능성이 있습니다. `exports`가 있으면 공개된 경로만 import할 수 있으므로, 목록에 없는 `@company/ui/button`은 찾을 수 없습니다.
3. CI와 로컬의 운영체제 차이로 대소문자 구분이 달라졌을 가능성이 있습니다. macOS는 기본적으로 대소문자를 구분하지 않고, GitHub Actions의 기본 실행 환경인 Linux는 구분합니다. 파일명이나 import 경로의 대소문자가 다르면 CI에서만 실패합니다.
4. Node 18과 Node 20의 차이가 원인일 가능성은 낮습니다. 두 버전 모두 `exports` 필드를 지원하므로 이 차이만으로는 설명하기 어렵습니다.

에러 문구 `Cannot find module`은 Node 계열 모듈 해석에서 자주 나오는 문구입니다. 다만 실제로 에러를 낸 도구가 Node인지 Next.js 번들러인지는 확인하지 않았습니다.

## 미확인 사항과 확인 방법

| 확인 항목 | 확인 방법 | 결과에 따른 판단 |
|---|---|---|
| 로컬 설치 버전 | 프로젝트 폴더에서 `npm ls @company/ui` 실행 | 1.4.0이면 추론 1과 일치합니다. |
| CI 설치 버전 | CI 로그에서 설치된 `@company/ui` 버전 확인 | 2.0.0이면 CI만 새 버전을 쓰고 있습니다. |
| 락 파일의 버전 | `package-lock.json`의 `@company/ui` 항목 확인 | 1.4.0이면 CI 설치 방식과 락 파일의 관계를 따로 확인해야 합니다. |
| 2.0.0의 `exports` 목록 | 2.0.0 패키지의 `package.json`에서 `exports` 확인 | `./button`이 없으면 추론 2와 일치합니다. |
| 에러를 낸 도구 | CI 전체 로그에서 에러 스택 확인 | Node 실행 에러인지 번들러 에러인지 구분됩니다. |
| 대소문자 | 파일명과 import 경로의 대소문자 비교 | 다르면 추론 3과 일치합니다. |
| 로컬 재현 | 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드 | 실패하면 추론 1은 배제되고 추론 2나 3을 우선 검토합니다. |

가장 먼저 할 일은 로컬에서 `npm ls @company/ui`를 실행하는 것입니다. 이 결과로 추론 1의 여부가 가려지고, 나머지 확인 방향도 정해집니다.
