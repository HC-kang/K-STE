CI에서만 빌드가 실패하는 가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드(패키지 바깥에 공개할 경로를 정한 설정)가 `@company/ui/button` 같은 하위 경로 import를 막는 것입니다. 로컬 빌드가 성공하는 이유는 로컬 `node_modules`에 아직 1.4.0이 남아 있을 가능성이 높기 때문입니다. 이 분석은 말씀해 주신 정보만 근거로 하며, 저장소와 CI 설정은 확인하지 않았습니다.

## 확인된 사실

- CI는 Node 18, 로컬은 Node 20을 씁니다.
- `@company/ui`는 3일 전에 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0에는 `exports` 필드가 추가되었습니다.
- CI 캐시 키는 `package-lock.json`(설치할 패키지 버전을 기록한 파일)의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

## 원인 분석 (추론)

`exports` 필드가 있으면 패키지는 공개된 경로만 외부에서 불러올 수 있습니다. 1.4.0에는 이 제한이 없어서 `@company/ui/button`이 파일 경로로 바로 찾아졌습니다. 2.0.0의 공개 목록에 `button` 경로가 없으면 같은 import는 "Cannot find module" 오류로 실패합니다. 오류 메시지도 이 패턴과 맞습니다.

CI가 2.0.0을 설치하는 것으로 보입니다. 캐시 키가 lockfile 해시이므로, lockfile이 2.0.0으로 갱신되었다면 키가 바뀌어 캐시 대신 새로 설치합니다.

Node 버전 차이는 가능성이 낮습니다. Node 18과 20은 모두 `exports` 필드를 지원하는 것으로 알려져 있지만, 이 저장소에서는 검증하지 않았습니다.

## 로컬 빌드가 성공하는 이유 (추론)

로컬 `node_modules`가 3일 전보다 먼저 설치되었다면 1.4.0이 그대로 남아 있을 가능성이 높습니다. 그러면 로컬은 제한이 없는 1.4.0으로 빌드하므로 성공합니다. 따라서 로컬과 CI는 서로 다른 버전으로 빌드하고 있고, 로컬 성공은 2.0.0이 정상이라는 근거가 되지 못합니다.

## 미확인 사항

- 확인 필요: 로컬 `node_modules/@company/ui`의 실제 버전이 1.4.0인지 2.0.0인지
- 확인 필요: 2.0.0의 `exports` 목록에 `./button`이 있는지, 또는 경로가 바뀌었는지
- 확인 필요: 저장소의 `package-lock.json`이 2.0.0으로 커밋되었는지
- 확인 필요: CI 워크플로에 `restore-keys`(키가 달라도 가까운 캐시를 복원하는 설정)가 있어서 예전 캐시가 복원되는지
- 확인 필요: 코드에서 `@company/ui/button` 형태로 import하는 파일이 몇 개인지

## 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. 로컬에서 Node 18로 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드해 CI 환경과 맞춥니다.
3. `node_modules/@company/ui/package.json`의 `exports` 항목에 button 경로가 있는지 확인합니다.
4. CI 로그에서 `npm ls @company/ui` 결과와 캐시 복원 여부를 확인합니다.

## 대응 방안

- 2.0.0의 `exports` 목록에 맞춰 import 경로를 고치는 방법을 권장합니다. 원인이 경로 문제라면 가장 빠른 수정입니다.
- `@company/ui` 담당자에게 `./button` 경로를 `exports`에 추가해 달라고 요청하는 방법도 있습니다. 여러 프로젝트가 같은 import를 쓰고 있다면 이 방법이 낫습니다.
- 1.4.0으로 되돌리는 방법은 임시 조치입니다. 2.0.0 적용을 미루는 것이므로 근본 해결은 아닙니다.
