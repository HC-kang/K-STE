가장 유력한 원인은 CI와 로컬이 서로 다른 `@company/ui` 버전을 쓰고 있다는 것입니다. CI는 2.0.0을 설치해서 `exports` 제한에 걸린 것으로 보이고, 로컬은 3일 전 이전에 설치된 1.4.0을 그대로 쓰고 있어서 빌드가 통과하는 것으로 보입니다. 다만 이는 추론입니다. 이번 분석에서는 저장소, 실제 `node_modules`, CI 로그를 확인하지 않았습니다.

### 주어진 사실

- `@company/ui`는 3일 전 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0에는 `exports` 필드가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

### 원인 가설

| 가설 | 근거 | 확인 방법 |
|---|---|---|
| 로컬에는 아직 1.4.0이 설치되어 있습니다. | 로컬 `node_modules`가 업그레이드 전에 설치되었습니다. | `npm ls @company/ui`로 로컬 설치 버전을 확인합니다. |
| CI는 2.0.0을 쓰고, 2.0.0의 `exports`에는 `button` 경로가 없습니다. | 에러는 패키지 내부 경로를 직접 가져오는 import에서 발생했고, `exports`는 2.0.0에서 새로 추가되었습니다. | 2.0.0의 `package.json`에서 `exports` 항목을 확인합니다. |
| Node 18과 Node 20의 차이가 원인입니다. | 두 환경의 Node 버전이 다릅니다. | 근거가 약합니다. Node 18로 로컬 빌드를 재현해서 확인합니다. |
| CI가 이전 캐시를 사용합니다. | 캐시 키가 lock 파일 해시이므로, lock 파일이 갱신되지 않았다면 이전 캐시가 적중할 수 있습니다. | CI 로그에서 캐시 적중 여부와 설치된 버전을 확인합니다. |

에러 메시지 `Cannot find module`만으로는 `exports` 제한 때문인지 파일이 실제로 없어서인지 구분할 수 없습니다. 두 경우의 해결 방법이 다르므로 확인이 필요합니다.

### 확인 순서

1. CI 로그에서 `@company/ui`의 설치 버전과 캐시 적중 여부를 확인합니다.
2. 로컬에서 `npm ls @company/ui`를 실행해 설치 버전을 확인합니다.
3. 2.0.0의 `exports`에서 `button`에 해당하는 경로가 있는지 확인합니다.
4. 로컬에서 `npm ci`로 2.0.0을 다시 설치한 뒤 빌드하고, Node 18로도 한 번 더 빌드합니다.

### PM이 판단할 사항

원인이 확인되면 두 가지 중에서 선택해야 합니다. 2.0.0을 유지하려면 import 경로를 `exports`가 허용하는 경로로 바꿔야 합니다. 확인 필요: 2.0.0에서 `button` 모듈이 옮겨진 정확한 경로. 1.4.0으로 되돌리면 빌드는 통과할 수 있지만, 2.0.0 업그레이드의 이점은 유지되지 않습니다.
