원인은 로컬과 CI가 서로 다른 버전의 `@company/ui`를 쓰기 때문일 가능성이 가장 높습니다. 로컬은 1.4.0으로 보이고, CI는 2.0.0을 설치합니다.

## 확인된 사실

- CI 빌드만 `Cannot find module '@company/ui/button'`으로 실패합니다.
- `@company/ui` 2.0.0에는 `exports` 필드가 추가됐습니다. `exports` 필드는 패키지가 외부에 공개하는 경로의 목록이며, 목록에 없는 경로는 import할 수 없습니다.
- 로컬 `node_modules`는 업그레이드보다 먼저 설치했습니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.

## 추론

1. 로컬 `node_modules`가 업그레이드 이전에 설치됐으므로, 로컬에는 1.4.0이 남아 있을 가능성이 높습니다.
2. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`을 파일 경로로 그대로 찾을 수 있습니다. 그래서 로컬 빌드가 성공합니다.
3. CI는 `package-lock.json`에 따라 2.0.0을 설치합니다. 2.0.0의 `exports`에 `./button`이 없거나 경로가 바뀌었다면 같은 import가 실패합니다.
4. 업그레이드로 `package-lock.json` 해시가 바뀌었으므로 CI 캐시는 새로 만들어졌을 것입니다. 오래된 캐시가 원인일 가능성은 낮습니다.
5. Node 18과 20은 모두 `exports` 필드를 지원합니다. Node 버전 차이가 주원인일 가능성도 낮습니다.

## 확인되지 않은 것

- 로컬에 실제로 설치된 `@company/ui` 버전
- 2.0.0의 `exports`에 `./button`이 있는지, 있다면 어떤 경로로 연결되는지
- `button`이 2.0.0에서 삭제되거나 이름이 바뀌었는지
- 에러 메시지가 `Cannot find module`이고 `ERR_PACKAGE_PATH_NOT_EXPORTED`가 아니라는 점은 추론과 완전히 맞지 않습니다. 호출하는 도구에 따라 메시지가 달라질 수 있어서, CI 전체 로그를 확인해야 합니다.

## 검증 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. `npm view @company/ui@2.0.0 exports`를 실행해 공개 경로 목록을 확인합니다.
3. 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치한 뒤 빌드합니다. 로컬에서도 같은 에러가 나면 원인이 확정됩니다.
4. 그래도 재현되지 않으면 로컬을 Node 18로 바꿔 다시 빌드해서 Node 버전 영향을 확인합니다.

## 해결 방향

해결 방법은 3번과 2번의 결과에 따라 갈립니다. `exports`에 새 경로가 있으면 import 경로를 그 경로로 바꿉니다. `button` 경로가 공개되지 않았다면 `@company/ui` 담당자에게 공개를 요청하거나, 1.4.0으로 되돌릴지 정해야 합니다.
