# `@company/ui/button` CI 빌드 실패 원인 분석

가장 가능성이 높은 원인은 `@company/ui` 2.0.0의 `exports` 필드에 `button` 경로가 없어서 앱이 공개되지 않은 경로를 import하고 있다는 것이다. 이 분석은 전달받은 정보만으로 추론한 결과이며, 아직 코드와 패키지를 직접 확인하거나 재현하지 않았다.

## 원인 추론

`exports` 필드는 패키지가 외부에 공개하는 경로 목록이다. 이 필드가 있으면 Node와 번들러는 목록에 적힌 경로만 해석한다. 1.4.0에는 이 필드가 없어서 `@company/ui/button`처럼 하위 경로를 직접 import해도 동작했다. 2.0.0에서 필드가 추가되면서 목록에 없는 `button` 경로가 해석되지 않게 되었을 가능성이 높다.

로컬 빌드가 성공하는 이유도 설명된다. 로컬 `node_modules`는 3일 전보다 먼저 설치되었으므로 1.4.0이 그대로 들어 있다. 로컬 빌드는 2.0.0을 검증하지 않았다.

CI는 `package-lock.json` 해시를 캐시 키로 쓴다. 업그레이드로 lock 파일이 바뀌었다면 캐시가 무효화되어 CI는 2.0.0을 새로 설치한다. 그래서 실패가 업그레이드 직후부터 나타난다.

## Node 버전은 주원인일 가능성이 낮다

Node 18과 20은 모두 `exports` 필드를 지원한다. 그래도 CI와 로컬의 Node 버전이 다르므로 변수 하나로 두고 분리해서 확인해야 한다. Node 18은 2025년 4월에 공식 지원이 종료된 버전이라 장기적으로는 CI 버전도 올려야 한다.

## 확인 필요 사항

- 에러 문구 `Cannot find module`은 Node의 CommonJS 해석 실패 문구다. Next.js 빌드 중 번들러에서 발생한 에러라면 보통 `Module not found`로 표시된다. 따라서 실패 지점이 번들링 단계인지, `next.config.js`나 빌드 스크립트 같은 Node 프로세스인지 확인 필요.
- 2.0.0의 `exports` 목록에 `button`에 해당하는 경로가 있는지 확인 필요. 경로 이름이 `./components/button`처럼 다를 수 있다.
- 2.0.0 업그레이드 변경에 `package-lock.json`이 함께 포함되었는지 확인 필요.
- CI가 `npm ci`로 설치하는지 `npm install`로 설치하는지 확인 필요.

## 검증 방법

아래 순서로 실행하면 원인을 분리할 수 있다. 아직 실행하지 않았다.

1. 로컬에서 `node_modules`를 삭제하고 `npm ci`로 다시 설치한다.
2. `node_modules/@company/ui/package.json`에서 버전과 `exports` 필드를 확인한다.
3. Node 18로 빌드해 CI 실패를 재현한다.
4. 재현되면 같은 상태에서 Node 20으로 빌드한다. Node 20도 실패하면 Node 버전은 원인이 아니다.

## 해결 방안

1순위는 앱의 import 경로를 2.0.0 `exports` 목록에 있는 경로로 바꾸는 것이다. 이 방법이 패키지 설계에 맞는 수정이다.

2순위는 UI 패키지 팀과 협의해 `exports`에 `./button` 경로를 추가하는 것이다. 이 방법은 패키지 쪽 변경이 필요하다.

임시 조치로 `@company/ui`를 1.4.0으로 고정하면 CI는 통과한다. 다만 2.0.0 업그레이드가 미뤄진다.

## PM 참고 사항

CI 빌드가 실패하는 동안 배포가 막히는지 확인 필요. 원인은 앱 코드가 2.0.0에서 공개하지 않은 경로를 쓰고 있을 가능성이 높다는 것이다. 수정은 import 경로 변경 한 건으로 끝날 가능성이 높지만, 2.0.0에서 다른 변경으로 인한 문제가 더 있는지는 검증 후에 확인된다.
