원인은 아직 하나로 확정할 수 없습니다. 가장 유력한 가설은 2.0.0에서 `@company/ui/button` 경로가 사라졌거나 `exports` 필드에 막혔다는 것입니다. 로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 아직 1.4.0일 가능성으로 설명될 수 있습니다. 그렇다면 로컬 빌드는 2.0.0을 한 번도 검증하지 않은 것입니다.

## 확인된 사실

- `@company/ui`를 3일 전에 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에 `exports` 필드가 추가되었습니다.
- CI는 Node 18, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.
- 실패 메시지는 `Cannot find module '@company/ui/button'`입니다.

## 원인 후보

| 후보 | 근거 | 상태 | 확인 방법 |
|---|---|---|---|
| 2.0.0에서 `./button` 경로가 없거나 `exports`에 막혀 있습니다. | 변경 시점과 실패 시점이 같은 3일 전입니다. | 추론 | 2.0.0 설치본의 파일 목록과 `package.json`의 `exports`를 확인합니다. |
| 로컬은 1.4.0을 쓰고 있습니다. | 로컬 `node_modules`가 변경 전에 설치되었습니다. | 추론 | `npm ls @company/ui`로 설치 버전을 확인합니다. |
| CI가 오래된 캐시를 복원했습니다. | 2.0.0 업그레이드로 lock이 바뀌었다면 캐시 키도 바뀌어야 합니다. 복원 키(restore-keys) 설정은 확인하지 않았습니다. | 미확인 | 워크플로의 cache 설정과 로그의 cache hit 여부를 확인합니다. |
| Node 18과 20의 해석 차이입니다. | Node 18도 `exports`를 지원하므로 버전 차이만으로 설명되는지 불확실합니다. | 미확인 | CI만 Node 20으로 바꿔 재현합니다. |

에러 메시지 형식도 단서가 됩니다. `Cannot find module`은 Node가 `require`를 해석할 때 나는 메시지입니다. `exports`가 경로를 막으면 Node는 보통 다른 오류 코드를 냅니다. 그래서 이 메시지는 `exports` 차단보다 파일 부재에 가깝습니다. 발생한 파일도 로그에서 함께 확인하십시오. Next.js 번들러 단계가 아니라 `next.config.js`나 빌드 스크립트처럼 Node가 직접 실행하는 파일에서 났을 가능성이 있습니다.

## 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행하여 설치된 버전을 확인하십시오.
2. 1번 결과가 1.4.0이면 로컬 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드하십시오.
3. 2.0.0이 설치된 상태에서 `node_modules/@company/ui/` 아래에 `button` 파일이 있는지 확인하십시오.
4. 같은 패키지의 `package.json`에서 `exports`에 `./button` 또는 `./*` 항목이 있는지 확인하십시오.
5. CI 로그에서 에러가 난 파일 경로와 캐시 복원 여부를 확인하십시오.
6. 원인을 분리하기 위해 CI만 Node 20으로 바꿔 같은 빌드를 실행하십시오.

## 조치 방향

원인이 확정되면 조치는 다음 중 하나입니다. 2.0.0에서 `./button` 경로가 빠졌다면 `@company/ui` 쪽에 경로 복구를 요청하거나 앱의 import를 2.0.0이 노출하는 경로로 바꿉니다. 2.0.0의 변경이 앱과 맞지 않으면 1.4.0으로 되돌립니다. 캐시가 원인이면 캐시 키나 복원 설정을 고칩니다.

1-5번 결과를 받은 뒤 원인을 확정하고 조치를 고르십시오.
