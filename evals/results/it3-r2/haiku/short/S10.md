## 결론

가장 유력한 원인은 로컬에 1.4.0이 그대로 남아 있고, CI는 2.0.0을 설치하는데, 2.0.0의 `exports` 필드가 `@company/ui/button` 경로를 허용하지 않는 것이다. 아직 검증하지 않은 추론이므로 아래 확인 항목으로 먼저 확인해야 한다.

## 확인된 사실

`@company/ui`를 3일 전에 1.4.0에서 2.0.0으로 올렸다.
2.0.0에는 `exports` 필드가 추가되었다.
로컬 `node_modules`는 3일 전보다 먼저 설치되었다.
CI는 Node 18을, 로컬은 Node 20을 사용한다.
CI 캐시 키는 `package-lock.json`의 해시이다.

## 추론

로컬 `node_modules`는 업그레이드 이전에 설치되었으므로 1.4.0이 남아 있을 가능성이 높다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`이 파일 경로로 그대로 해석된다. 이 때문에 로컬 빌드는 성공한다.

CI는 `package-lock.json`을 기준으로 설치하므로 lockfile이 2.0.0을 가리키면 2.0.0을 받는다. 캐시 키가 lockfile 해시이므로 lockfile이 바뀌면 새 캐시가 만들어지고 2.0.0이 설치된다. 이는 CI에서만 실패하는 현상과 맞아떨어진다.

2.0.0의 `exports`에 `./button` 항목이 없다면 이 경로의 import는 차단된다.

Node 버전 차이는 원인일 가능성이 낮다. Node 18과 20은 `exports` 해석 방식이 같다. 다만 2.0.0이 ESM 전용 패키지라면 Node 18에서 `require`가 실패할 수 있다.

## 확인 필요

에러 메시지가 `Cannot find module`이다. `exports`가 경로를 차단하면 Node는 보통 `Package subpath './button' is not defined by "exports"`를 낸다. 따라서 이 메시지가 어느 단계(번들러 또는 Node 런타임)에서 나왔는지 확인 필요하다.
CI 로그에서 빌드 단계와 전체 에러 메시지를 확인 필요하다.
CI 빌드에 실제로 설치된 `@company/ui` 버전을 확인 필요하다.
2.0.0의 `exports`에 `./button`이 있는지 확인 필요하다.
2.0.0이 ESM 전용인지 CJS를 포함하는지 확인 필요하다.
CI 워크플로에 `restore-keys`가 설정되어 있는지 확인 필요하다. 설정되어 있으면 이전 캐시가 복원되어 다른 버전이 설치될 수 있다.

## 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행하여 설치 버전을 확인한다.
2. CI 로그에 같은 명령을 추가하여 설치 버전을 비교한다.
3. `node_modules/@company/ui/package.json`의 `exports`를 열어 `./button` 항목이 있는지 본다.
4. `.github/workflows`의 캐시 단계에서 `key`와 `restore-keys`를 본다.
5. CI의 Node 버전을 20으로 바꿔 빌드하여 Node 버전의 영향을 분리한다.

## 조치 방향

`exports`에 `./button`이 없으면 import 경로를 2.0.0이 공개한 경로로 바꾼다. 패키지 제공 측에 경로 추가를 요청하는 방법도 있다.
로컬도 `npm ci`로 재설치하여 로컬과 CI가 같은 버전을 쓰도록 맞춘다. 이후 로컬에서도 같은 에러가 재현되는지 확인한다.

## PM 참고

현재 CI 빌드가 실패하는 상태이다. 로컬 빌드 성공을 근거로 CI 실패를 무시하면 안 된다.
