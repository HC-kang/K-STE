CI 빌드가 실패하는 가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드가 `./button` 서브패스를 열어 두지 않은 것입니다. 로컬은 아직 1.4.0을 쓰고 있어서 이 문제가 드러나지 않았을 가능성이 높습니다.

## 사실

- 에러는 `Cannot find module '@company/ui/button'`이고 CI에서만 발생합니다.
- `@company/ui`는 3일 전에 1.4.0에서 2.0.0으로 올랐고, 2.0.0부터 `exports` 필드가 있습니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치한 것입니다.
- CI 캐시 키는 `package-lock.json`의 해시이고, 버전을 올리면 lock 파일이 바뀝니다.

## 추론

- 로컬 `node_modules`에는 1.4.0이 남아 있을 가능성이 높습니다. 1.4.0에는 `exports`가 없어서 `@company/ui/button`이 파일 경로로 그대로 해석됩니다.
- CI는 lock 파일 변경으로 캐시가 갱신되어 2.0.0을 새로 설치합니다. `exports`가 있으면 Node와 번들러는 `exports`에 선언된 경로만 허용하므로, `./button`이 선언되지 않았다면 모듈을 찾지 못합니다.
- Node 18과 20은 둘 다 `exports`를 지원합니다. 따라서 Node 버전 차이는 주된 원인일 가능성이 낮습니다.
- 캐시 키는 lock 파일 해시를 쓰므로 오래된 캐시를 재사용했을 가능성도 낮습니다.

## 확인 필요

- 로컬 `node_modules/@company/ui/package.json`의 `version`이 1.4.0인지 확인해야 합니다.
- 2.0.0의 `exports`에 `./button` 또는 이에 해당하는 패턴이 있는지 확인해야 합니다.
- 2.0.0의 changelog나 마이그레이션 문서에 import 경로 변경이 적혀 있는지 확인해야 합니다.

## 검증 방법

1. 로컬에서 `node_modules`와 `.next`를 지우고 `npm ci`를 실행한 뒤 빌드합니다. CI와 같은 오류가 나면 원인이 확정됩니다.
2. `npm ls @company/ui`로 로컬과 CI의 설치 버전을 비교합니다.
3. `node -p "require('@company/ui/package.json').exports"`로 `exports` 내용을 확인합니다. `exports`가 `./package.json`을 열어 두지 않았다면 이 명령은 실패하므로, 그 경우 `node_modules/@company/ui/package.json` 파일을 직접 읽습니다.

## 해결 방향

원인이 확정되면 아래 중 하나를 선택합니다.

- 2.0.0이 공개한 import 경로로 코드를 수정합니다.
- `@company/ui`를 관리하는 쪽에 `./button`을 `exports`에 추가해 달라고 요청합니다.
- 급하면 `@company/ui`를 1.4.0으로 고정합니다. 이 경우 2.0.0 업그레이드는 미뤄집니다.

로컬 환경이 CI와 다른 상태로 3일간 유지된 점도 문제입니다. 로컬 검증은 `npm ci` 직후 기준으로 하는 것을 권장합니다.
