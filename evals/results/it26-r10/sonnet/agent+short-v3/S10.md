가장 유력한 원인은 로컬과 CI가 서로 다른 버전의 `@company/ui`를 쓰고 있다는 점입니다. 아직 확인하지 않은 추론입니다.

## 사실

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `@company/ui` 설치 시점 | 3일 전보다 먼저 | 알 수 없음 |
| 빌드 결과 | 성공 | `Cannot find module '@company/ui/button'`으로 실패 |

- `@company/ui`를 3일 전에 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0부터 패키지에 `exports` 필드가 있습니다.
- `exports` 필드는 패키지가 외부에 공개할 경로를 직접 정하는 설정입니다. 목록에 없는 경로는 `import`로 불러올 수 없습니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.

## 추론

로컬 `node_modules`는 업그레이드보다 먼저 설치했으므로 1.4.0이 그대로 남아 있을 가능성이 높습니다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`이 파일 경로로 바로 열립니다. 그래서 로컬 빌드는 2.0.0을 한 번도 쓰지 않고 성공했을 수 있습니다.

CI는 `package-lock.json`이 바뀌어 캐시 키도 바뀌었으므로, 2.0.0을 새로 설치했을 가능성이 높습니다. 2.0.0의 `exports` 목록에 `./button`이 없거나 이름이 바뀌었다면 이 오류가 납니다.

## 아직 모르는 것

- 로컬에 설치된 `@company/ui`의 실제 버전을 모릅니다.
- 2.0.0의 `exports` 목록에 `./button`이 있는지 모릅니다.
- Node 18과 20의 차이가 이 오류에 영향을 주는지 모릅니다. `exports` 필드 자체는 두 버전 모두 지원하므로, 영향이 있더라도 주원인은 아닐 것으로 보입니다.
- 캐시는 원인일 가능성이 낮습니다. 락파일이 바뀌면 캐시 키도 바뀌어서 오래된 캐시를 재사용하지 않기 때문입니다.

## 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 보십시오. 1.4.0이면 위 추론이 맞습니다.
2. 로컬에서 `rm -rf node_modules && npm ci`로 락파일 기준으로 다시 설치하고 빌드하십시오. 로컬에서도 같은 오류가 나면 CI 환경은 원인이 아닙니다.
3. 2.0.0의 `package.json`에서 `exports` 목록을 읽고 `./button`이 있는지 보십시오.
4. 2.0.0이 설치된 상태에서 Node 20으로 CI 빌드를 돌려 보십시오. 이 빌드에서도 실패하면 Node 버전은 원인이 아닙니다.

## 수정 방향

수정 방향은 3번의 결과에 따라 달라집니다.

- `./button`이 목록에 없고 다른 경로로 바뀌었다면, 앱의 `import` 경로를 2.0.0의 경로로 고쳐야 합니다.
- 경로가 빠진 것이 실수라면, `@company/ui` 담당자에게 `exports`에 `./button`을 추가해 달라고 요청해야 합니다.
- 당장 CI를 살려야 하면 `@company/ui`를 1.4.0으로 되돌릴 수 있습니다. 이 경우 2.0.0으로 올린 목적은 달성하지 못합니다.

PM에게 필요한 판단은 마지막 항목 하나입니다. 2.0.0 전환을 이번 일정에 포함할지, 1.4.0으로 되돌릴지를 정해야 합니다.
