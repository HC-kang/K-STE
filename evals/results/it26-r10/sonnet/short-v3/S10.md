원인은 로컬이 아직 `@company/ui` 1.4.0을 쓰고 있고, CI만 2.0.0을 설치해서 `exports` 필드의 제한을 받는 것으로 보입니다. 아래 내용 중 사실은 주신 정보이고, 추론은 그 정보에서 이끌어낸 판단입니다.

| 항목 | 로컬 | CI |
|---|---|---|
| `@company/ui` 버전 | 1.4.0으로 추정 | 2.0.0으로 추정 |
| `exports` 필드 | 없음 | 있음 |
| Node | 20 | 18 |
| `node_modules` | 3일 전보다 먼저 설치 | 캐시 미스 후 새로 설치로 추정 |

**추론 과정**
1. 로컬 `node_modules`는 업그레이드보다 먼저 설치했으므로, 로컬 빌드는 1.4.0 기준으로 실행됩니다. 로컬 성공은 2.0.0에서도 빌드가 된다는 근거가 되지 않습니다.
2. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`을 파일 경로로 바로 찾을 수 있습니다.
3. 2.0.0에는 `exports` 필드가 있어서, 그 필드에 선언한 경로만 import할 수 있습니다. `./button`이 선언되어 있지 않거나 가리키는 파일이 없으면 `Cannot find module` 에러가 납니다.
4. 업그레이드 때 `package-lock.json`이 바뀌었으므로 캐시 키도 바뀌었고, CI는 2.0.0을 새로 설치했을 가능성이 큽니다. 캐시가 원인이라면 CI가 오래된 1.4.0을 쓰므로 성공해야 하는데, 실제로는 실패하므로 캐시는 원인이 아닌 것으로 보입니다.
5. Node 18과 20은 둘 다 `exports` 필드를 지원합니다. Node 버전 차이는 주원인이 아닐 가능성이 높습니다.

**확인 필요**
- 2.0.0의 `exports`에 `./button`이 선언되어 있는지, 선언되어 있다면 어떤 파일을 가리키는지는 아직 확인하지 않았습니다.
- 로컬 `node_modules`에 실제로 1.4.0이 설치되어 있는지도 확인하지 않았습니다.

**검증 순서**
1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인한다.
2. 로컬에서 `node_modules/@company/ui/package.json`의 `exports` 필드를 확인한다.
3. 로컬에서 `rm -rf node_modules && npm ci`로 CI와 같은 상태를 만든 뒤 빌드한다. 이때 같은 에러가 나면 원인이 확정됩니다.
4. 3번이 실패하면 Node 18로 바꿔서도 빌드해 Node 버전 영향을 배제한다.

**수정 방향**
- 2.0.0의 `exports`에 선언된 경로로 import 경로를 바꾸는 방법이 있습니다.
- `@company/ui` 쪽에서 `./button`을 `exports`에 추가하는 방법도 있습니다. 2.0.0이 의도적으로 공개 경로를 줄인 것이라면 이 방법은 권장하지 않습니다.
