CI에서만 실패하는 가장 유력한 원인은 2.0.0의 `exports` 필드(패키지가 외부에 공개하는 경로 목록)가 `@company/ui/button` 같은 경로를 허용하지 않는 것입니다. 로컬 `node_modules`는 3일 전에 설치된 것이라 1.4.0이 남아 있는 것으로 보이며, 그래서 로컬 빌드는 이 문제를 재현하지 못합니다.

**확인된 사실**

- 2.0.0에서 패키지에 `exports` 필드가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다. 잠금 파일이 바뀌면 캐시가 새로 만들어지고 패키지를 새로 설치합니다.

**추론**

- 로컬 빌드는 1.4.0으로 통과했을 가능성이 큽니다. 1.4.0에는 `exports` 제한이 없어서 깊은 경로 import(패키지 안의 파일을 직접 가리키는 import)가 그대로 동작합니다.
- CI는 2.0.0을 설치합니다. 2.0.0의 `exports`에 `./button` 항목이 없으면 `@company/ui/button` import가 실패합니다. 이것이 에러의 직접 원인으로 보입니다.
- Node 버전 차이는 원인일 가능성이 낮습니다. Node 18과 20은 모두 `exports`를 지원하므로 버전 차이만으로 이 에러가 나지는 않습니다.
- 에러 문구 `Cannot find module`은 Node가 파일을 직접 실행할 때 나는 형식입니다. 웹팩 번들링 실패는 보통 `Module not found`로 나타납니다. 따라서 실패 지점이 Next.js 빌드 자체가 아니라 Node로 직접 실행되는 파일(예: 설정 파일, 스크립트)일 수 있습니다.

**확인 필요**

- 확인 필요: 2.0.0의 `exports`에 `./button` 또는 `./*` 항목이 있는지 봐야 합니다. `npm view @company/ui@2.0.0 exports`로 읽기만 하면 확인할 수 있습니다.
- 확인 필요: CI와 로컬에서 실제로 설치된 버전이 각각 무엇인지 `npm ls @company/ui`로 봐야 합니다. 로컬은 1.4.0, CI는 2.0.0으로 예상합니다.
- 확인 필요: CI 로그에서 에러가 난 명령과 import 위치 전체를 봐야 합니다.
- 확인 필요: `package-lock.json`에 2.0.0이 커밋되어 있는지 봐야 합니다. 잠금 파일이 맞지 않으면 `npm ci`가 이 에러 대신 다른 에러로 실패하므로, 잠금 파일은 갱신되었을 가능성이 큽니다.

**권장 조치**

1. 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치한 뒤 빌드해서 같은 에러가 나는지 재현하는 것을 권장합니다. 재현되면 원인이 확정됩니다.
2. 재현되면 import 경로를 2.0.0의 `exports`가 허용하는 경로로 바꾸거나, 패키지 관리자에게 `./button` 항목 추가를 요청합니다.
3. 2.0.0 업그레이드를 되돌리는 것은 가능하지만, 2.0.0이 필요한 이유가 있다면 import 수정이 근본 해결입니다.
4. 원인이 확정되기 전에 CI의 Node 버전을 20으로 맞출 필요는 없습니다.
