현재 정보만으로는 원인을 확정할 수 없습니다. 가장 유력한 추론은 CI가 `@company/ui` 2.0.0을 설치하지 않았거나, 2.0.0의 `exports` 필드가 `button` 경로를 노출하지 않는다는 것입니다. 로컬 빌드가 성공하는 이유도 로컬에 1.4.0이 남아 있을 가능성이 높아서이므로, 로컬 결과는 2.0.0 경로를 검증하지 못합니다.

### 확인된 사실

- CI는 Node 18, 로컬은 Node 20을 사용합니다.
- `@company/ui` 2.0.0에 `exports` 필드가 추가되었습니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.

### 추론

- 로컬 `node_modules`가 오래된 설치본이면 로컬은 1.4.0 구조로 `@company/ui/button`을 해석합니다. 따라서 로컬 빌드 성공은 2.0.0에서 문제가 없다는 근거가 되지 않습니다.
- `exports` 필드가 있으면 패키지에서 명시한 경로만 외부에서 import할 수 있습니다. 2.0.0의 `exports`에 `./button`이 없거나 파일 위치가 바뀌었다면 import가 실패합니다.
- 캐시 키가 lockfile 해시이므로 lockfile이 2.0.0으로 갱신되었다면 키는 바뀝니다. 다만 restore-keys 같은 접두사 복원 설정이 있으면 이전 캐시(1.4.0)가 복원될 수 있습니다.
- Node 18은 Node 20과 모듈 해석 방식이 다를 수 있습니다. 다만 에러가 `Cannot find module`이므로 ESM 전용 패키지 문제일 가능성은 낮습니다. 확인 필요: 2.0.0이 ESM 전용인지 여부.

### 미확인 항목

- 확인 필요: CI에서 실패가 처음 발생한 날짜가 2.0.0 업그레이드 날짜와 같은지.
- 확인 필요: CI 로그에 실제로 설치된 `@company/ui` 버전.
- 확인 필요: 2.0.0 `package.json`의 `exports` 맵에 `./button` 항목이 있는지.
- 확인 필요: 캐시 설정에 restore-keys가 있는지.

### 다음 확인 순서

1. 로컬에서 `npm ls @company/ui`로 설치된 버전을 확인합니다.
2. 2.0.0 패키지의 `package.json`에서 `exports` 맵과 `button` 파일 위치를 확인합니다.
3. CI 로그에서 `npm ci` 직후 `@company/ui`의 설치 버전과 경로를 확인합니다.
4. 캐시 설정 파일에서 restore-keys 유무를 확인합니다.
5. 로컬 `node_modules`를 삭제하고 `npm ci`로 다시 설치한 뒤 빌드하여 2.0.0 경로를 재현합니다.

**로컬 빌드 성공을 근거로 2.0.0 문제가 없다고 판단하면 안 됩니다.** 5번 단계에서 재현하기 전까지는 로컬 결과를 신뢰하지 않는 것이 맞습니다.

Node 버전은 CI와 로컬을 맞추는 것을 권장합니다. 이렇게 하면 Node 차이로 생기는 변수를 줄일 수 있습니다.
