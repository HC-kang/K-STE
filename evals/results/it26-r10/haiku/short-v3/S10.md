현재 가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다. CI는 lock 파일 기준으로 새로 설치하면서 2.0.0을 받아 `@company/ui/button`을 해석하지 못하고 있으며, 로컬은 3일 전에 설치된 1.4.0을 그대로 쓰고 있어 빌드가 성공합니다. 아직 검증하지 않은 추론이므로 아래 미확인 항목부터 확인해야 합니다.

## 확인된 사실

- CI 빌드는 `Cannot find module '@company/ui/button'` 에러로 실패합니다.
- `@company/ui`는 3일 전에 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0에는 `exports` 필드가 새로 추가됐습니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치됐습니다.

## 추론

- `exports` 필드가 있으면 Node와 번들러는 패키지가 공개한 경로만 해석합니다. 2.0.0의 `exports` 맵에 `./button`이 없다면 `@company/ui/button` import는 실패합니다.
- 로컬 `node_modules`에는 `exports`가 없는 1.4.0이 남아 있어서 같은 import가 성공합니다.
- lock 파일이 2.0.0으로 바뀌면 캐시 키도 바뀌므로 CI는 캐시를 새로 만들며 2.0.0을 설치합니다.
- Node 18과 Node 20 모두 `exports` 필드를 지원하므로 Node 버전 차이는 주요 원인일 가능성이 낮습니다.

## 미확인 사항

확인 필요: CI 로그에서 실제로 2.0.0이 설치됐는지 봐야 합니다.

확인 필요: 2.0.0 패키지의 `exports` 맵에 `./button` 항목이 있는지 봐야 합니다.

확인 필요: CI의 캐시 적중 여부(cache hit)와 복원 설정을 봐야 합니다.

검증 방법은 다음과 같습니다.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 확인합니다. 1.4.0이면 추론과 일치합니다.
2. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 봅니다.
3. 로컬에서 `rm -rf node_modules && npm ci`로 lock 기준 재설치 후 빌드합니다. 여기서 실패하면 원인이 재현된 것입니다.

## 해결 방향

원인이 확인되면 아래 세 가지 방향 중에서 선택해야 합니다.

| 방향 | 장점 | 단점 |
|---|---|---|
| import 경로를 2.0.0 `exports`가 허용하는 공개 경로로 변경 | 패키지 코드를 바꾸지 않아도 됩니다. | 2.0.0에 공개 경로가 없으면 쓸 수 없습니다. 확인 필요: 변경해야 할 import 범위를 봐야 합니다. |
| `@company/ui` 2.0.0의 `exports`에 `./button` 추가를 패키지 관리 측에 요청 | import 코드를 그대로 쓸 수 있습니다. | 패키지 재배포가 필요하고 시간이 걸립니다. |
| `@company/ui`를 1.4.0으로 고정 | 즉시 빌드가 성공합니다. | 2.0.0의 변경 사항을 쓸 수 없고, 나중에 업그레이드할 부담이 남습니다. |
