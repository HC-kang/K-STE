원인은 아직 확정되지 않았습니다. 가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다. 로컬에서 성공한 이유는 로컬 `node_modules`가 업그레이드 전 버전(1.4.0)을 그대로 담고 있기 때문으로 추정합니다.

## 입력받은 사실

- CI 빌드는 실패하고 로컬 빌드는 성공합니다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에 `exports` 필드(패키지가 외부에 공개할 경로를 정하는 설정)가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 업그레이드 전에 설치되었습니다.

## 추론

1. 로컬은 1.4.0을 계속 쓰고 있을 가능성이 큽니다. 그래서 로컬 빌드 성공은 2.0.0이 동작한다는 증거가 되지 않습니다.
2. `package-lock.json`이 바뀌면 캐시 키도 바뀌어 CI는 캐시를 쓰지 못합니다. 이때 CI는 새로 설치하면서 2.0.0을 받습니다.
3. `exports` 필드가 있으면 목록에 없는 하위 경로(`@company/ui/button`)는 외부에서 import할 수 없습니다. 그래서 2.0.0에서 이 import가 실패할 가능성이 높습니다.
4. Node 18도 `exports`를 지원하므로 Node 버전 차이가 직접 원인일 가능성은 낮다고 봅니다.
5. 에러 문구 `Cannot find module`은 Node의 모듈 해석기에서 나오는 형식입니다. Next.js 번들링 중 실패라면 보통 `Module not found` 문구가 나옵니다. 그래서 실패 지점이 `next.config` 같은 Node 직접 실행 파일일 수 있습니다. 확인 필요: 실패한 CI 로그에서 어느 단계가 실패했는지 확인해야 합니다.

## 미확인

- 2.0.0의 `exports` 목록에 `./button` 항목이 있는지 확인하지 않았습니다.
- CI 로그에 설치된 `@company/ui` 버전이 2.0.0으로 찍혔는지 확인하지 않았습니다.
- Node 18과 Node 20에서 실제로 결과가 다른지 재현하지 않았습니다.

## 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. `node_modules/@company/ui/package.json`의 `exports` 필드에 `./button`이 있는지 확인합니다.
3. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 Node 20으로 빌드합니다. 이 빌드가 실패하면 원인은 2.0.0이며 CI 환경 차이가 아닙니다.
4. 같은 과정을 Node 18로 반복합니다.
5. CI 로그에서 설치된 버전과 캐시 복원 여부를 확인합니다.

## 조치 방안 (권장)

- 빠른 복구: `@company/ui`를 1.4.0으로 고정해 CI를 먼저 통과시킵니다.
- 근본 수정: `@company/ui`는 사내 패키지이므로, 2.0.0의 `exports` 목록에 `./button` 경로를 추가하는 방법을 권장합니다. 앱의 import 경로를 바꾸는 방법도 있습니다.
- 재발 방지: 로컬에서도 `npm ci`로 새로 설치한 뒤 빌드하고, CI와 로컬의 Node 버전을 맞춥니다(예: `.nvmrc` 파일 사용).
