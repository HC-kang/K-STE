## 요약

CI 빌드 실패의 가장 유력한 원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드가 `button` 경로를 공개하지 않은 것이다. 로컬 빌드가 성공하는 이유는 로컬 `node_modules`에 아직 1.4.0이 남아 있어서 `exports` 필드의 영향을 받지 않기 때문으로 추정한다. 이 원인은 아직 확인되지 않았으므로 아래 확인 절차로 검증해야 한다.

## 확인된 사실

- CI(GitHub Actions) 빌드가 `Error: Cannot find module '@company/ui/button'` 오류로 실패한다.
- 로컬 빌드는 성공한다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에는 `exports` 필드가 추가되었다.
- CI는 Node 18을, 로컬은 Node 20을 사용한다.
- CI 캐시 키는 `package-lock.json`의 해시다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었다.

## 용어 설명

- `exports` 필드(패키지가 외부에 공개하는 경로를 정하는 설정): 이 필드가 있으면 목록에 없는 경로로 가져오는 것이 막힌다.
- 캐시 키(CI가 저장된 의존성을 재사용할지 판단하는 식별값): 키가 바뀌면 CI가 의존성을 새로 설치한다.

## 추론

로컬 `node_modules`가 3일 전보다 먼저 설치되었으므로, 로컬은 여전히 1.4.0을 사용하고 있을 가능성이 높다. 반면 CI는 `package-lock.json`이 바뀌어 캐시 키가 달라졌다면 새로 설치하므로 2.0.0을 받는다. 따라서 두 환경의 차이는 패키지 버전 차이로 가장 잘 설명된다.

로컬 빌드 성공은 2.0.0이 정상이라는 증거가 아니다. 로컬이 2.0.0을 검증하지 않은 상태이기 때문이다.

### 원인 후보

| 후보 | 근거 | 가능성 | 검증 방법 |
|---|---|---|---|
| 2.0.0의 `exports`가 `button` 경로를 공개하지 않는다 | 2.0.0에 `exports`가 추가되었다 | 높음 | 2.0.0 패키지의 `package.json`에서 `exports` 항목을 확인한다 |
| 로컬이 1.4.0을 그대로 사용한다 | 로컬 `node_modules`가 3일 전보다 먼저 설치되었다 | 높음(로컬 성공을 설명한다) | 로컬 `node_modules/@company/ui/package.json`의 `version` 값을 확인한다 |
| CI가 오래된 캐시를 복원한다 | 캐시 키가 lock 파일 해시만 사용한다 | 낮음 | CI 로그에서 캐시 적중 여부와 설치된 버전을 확인한다 |
| Node 18과 20의 차이 | 두 버전 모두 `exports`를 지원한다 | 낮음 | Node 18 환경에서 로컬 빌드를 재현한다 |

캐시는 `package-lock.json`이 3일 전 커밋에서 함께 바뀌었다면 실패 원인이 아니다. 키가 바뀌어 최신 패키지를 받았기 때문이다. 다만 lock 파일이 커밋되지 않았다면 오래된 캐시가 복원되어 현상이 달라질 수 있다.

## 미확인 사항

- 2.0.0의 `exports` 필드에 `button` 경로가 실제로 있는지 여부
- 로컬 `node_modules`에 설치된 실제 버전
- CI 로그에 찍힌 실제 설치 버전
- Node 18에서 `button` 외에 다른 오류가 있는지 여부
- 이번 실패가 배포를 막는 범위

## 확인 절차

1. 로컬에서 `node_modules/@company/ui/package.json`의 `version` 값을 확인한다.
2. 2.0.0 패키지의 `package.json`에서 `exports` 항목을 열어 `./button` 또는 `./*` 경로가 있는지 확인한다.
3. CI 로그에 `npm ls @company/ui` 결과를 출력하도록 추가하고, 설치된 버전을 확인한다.
4. Node 18로 맞춘 환경에서 `rm -rf node_modules` 후 `npm ci`를 실행하여 빌드를 재현한다.

## 해결 방안

1. 패키지 쪽: `@company/ui` 담당자에게 `exports`에 `button` 경로를 추가해 달라고 요청한다.
2. 앱 쪽: `import` 경로를 2.0.0이 공개한 경로로 바꾼다.
3. 임시 방편: 1.4.0으로 되돌리고 2.0.0 전환을 다시 계획한다.
4. 캐시: CI 캐시 키에 Node 버전을 포함하는 것을 권장한다. 또한 lock 파일 변경이 커밋에 포함되었는지 확인해야 한다.

1번과 2번 중 어느 쪽으로 갈지는 확인 절차 2번의 결과에 따라 정한다.
