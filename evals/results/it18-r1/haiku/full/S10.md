가장 유력한 원인은 2.0.0에서 추가된 `exports` 필드(패키지가 외부에 공개할 import 경로를 정하는 설정)가 `@company/ui/button` 경로를 공개하지 않는 것입니다. 로컬 빌드가 성공하는 이유는 3일 전 이전에 설치된 `node_modules`가 남아 있어 옛 버전(1.4.0으로 추정)으로 빌드되기 때문으로 보입니다. 아직 검증하지 않은 가설이므로 아래 확인 항목을 먼저 실행하십시오.

## 확인된 사실

- CI에서 `Cannot find module '@company/ui/button'` 에러로 빌드가 실패합니다.
- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드가 새로 추가되었습니다.
- CI는 Node 18, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`(설치 버전을 고정하는 파일)의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

## 추론

1. `exports` 필드가 있으면 import는 그 필드에 적힌 경로만 허용됩니다. 2.0.0의 `exports`에 `./button`이 없거나 다른 경로로 바뀌었다면 `@company/ui/button`은 해석되지 않습니다. 1.4.0에는 `exports`가 없어서 같은 경로가 파일 구조대로 찾아지므로 통과했을 것입니다.
2. 로컬은 3일 전 이전에 설치된 `node_modules`를 그대로 쓰고 있을 가능성이 큽니다. 이 경우 로컬 빌드 성공은 2.0.0을 검증한 결과가 아닙니다.
3. CI는 `package-lock.json`대로 새로 설치하므로 2.0.0을 받고, 그래서 CI에서만 실패합니다.
4. Node 18과 20은 모두 `exports`를 지원하므로 Node 버전 차이 자체가 직접 원인일 가능성은 낮습니다. 설치된 패키지 버전의 차이가 원인일 가능성이 더 높습니다.
5. 캐시 키가 lockfile 해시이므로 lockfile이 바뀌었다면 키도 바뀌어 새로 설치되는 것이 정상입니다. 다만 캐시 복원 시 이전 캐시가 fallback으로 들어왔는지는 CI 로그로 확인해야 합니다. 이것은 원인이라기보다 가능한 2차 요인입니다.

## 확인 필요

- 2.0.0의 `exports`에 `./button` 경로가 있는지 확인되지 않았습니다.
- 로컬에 설치된 `@company/ui`의 실제 버전을 확인하지 않았습니다.
- CI가 실제로 설치한 버전과 캐시 복원 여부를 로그에서 확인하지 않았습니다.
- lockfile이 2.0.0을 가리키는지 확인하지 않았습니다.

## 다음 단계

1. `npm ls @company/ui`로 로컬 설치 버전을 확인하십시오. 1.4.0이면 로컬은 2.0.0을 검증하지 않은 상태입니다.
2. `npm view @company/ui@2.0.0 exports`로 2.0.0이 `button` 경로를 공개하는지 확인하십시오. 공개하지 않는다면 import 경로를 2.0.0이 공개한 경로로 바꾸거나, 패키지 관리자에게 해당 경로 추가를 요청하십시오.
3. 로컬에서 `rm -rf node_modules && npm ci`로 새로 설치한 뒤 빌드하여 CI와 같은 조건에서 재현하십시오. 재현되면 원인이 확정됩니다.
