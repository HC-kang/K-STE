가장 유력한 원인은 2.0.0의 `exports` 필드(패키지 외부에 공개할 경로를 정하는 설정)가 `@company/ui/button` 경로를 공개하지 않는 것이다. 다만 이는 추론이며, 2.0.0의 `package.json`을 확인하기 전에는 확정할 수 없다. 로컬 빌드 성공은 2.0.0에서도 빌드가 된다는 증거가 아니다.

## 확인된 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에서 패키지에 `exports` 필드가 추가되었다.
- 에러 메시지는 `Cannot find module '@company/ui/button'`이다.
- CI는 Node 18을, 로컬은 Node 20을 쓴다.
- CI 캐시 키(캐시를 찾는 기준값)는 `package-lock.json`(설치 버전을 기록한 파일)의 해시이다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었다.

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| 설치 방식 | 기존 `node_modules` 재사용으로 보인다(추론) | 캐시 키가 바뀌면 새로 설치한다(추론) |
| `@company/ui` 버전 | 1.4.0으로 보인다(추론) | 2.0.0으로 보인다(추론) |

## 추론: 원인 경로

1. 로컬은 3일 전에 설치된 `node_modules`를 그대로 쓰므로 1.4.0이 남아 있을 가능성이 크다.
2. 1.4.0에서는 `@company/ui/button`이 파일 경로로 바로 해석되어 로컬 빌드가 성공한다.
3. `package-lock.json`이 2.0.0으로 갱신되면 해시가 바뀌므로 CI는 캐시를 쓰지 못하고 2.0.0을 새로 설치한다.
4. 2.0.0은 `exports`를 가지므로 Node와 번들러는 `exports`에 정의된 경로만 허용한다.
5. `exports`에 `./button`이 정의되지 않았다면 `@company/ui/button` 해석이 실패한다.

Node 18과 Node 20은 모두 `exports`를 지원하므로, Node 버전 차이만으로 이 에러가 생겼다고 보기는 어렵다. 다만 Node 버전이 번들러 동작에 영향을 주는지는 확인하지 않았다.

## 확인 필요

- 2.0.0의 `package.json`에 `./button` 또는 이를 포함하는 패턴이 `exports`에 있는지 확인 필요.
- 로컬 `node_modules/@company/ui/package.json`의 `version` 값이 1.4.0인지 확인 필요.
- CI 로그에서 설치된 `@company/ui` 버전이 2.0.0으로 나오는지 확인 필요.
- 로컬에서 Node 18로 재현했을 때 같은 에러가 나는지 확인 필요.

## 확인 방법

1. `npm ls @company/ui`로 로컬에 설치된 버전을 확인한다.
2. `node_modules/@company/ui/package.json`과 2.0.0의 `package.json`에서 `exports` 값을 비교한다.
3. `rm -rf node_modules && npm ci`로 설치를 다시 한 뒤 Node 18로 빌드해 재현한다.

## 권장 조치

- `exports`에 `./button`이 빠져 있다면 `@company/ui` 담당자가 2.0.0 `exports`에 해당 경로를 추가하도록 협의하는 것을 권장한다.
- 앱의 import 경로를 `exports`에 정의된 경로로 바꾸는 방법도 있다. 정의된 경로가 무엇인지는 확인 필요.
- 원인이 확정되기 전까지는 `@company/ui`를 1.4.0으로 되돌릴 수 있다.
