로컬 빌드는 1.4.0으로, CI 빌드는 2.0.0으로 실행되고 있을 가능성이 가장 큽니다. 이 버전 차이가 CI에서만 실패하는 이유로 보입니다. 아래 내용 중 "추론"과 "미확인"은 아직 직접 확인하지 않은 부분입니다.

## 원인 추론

`exports` 필드는 패키지가 외부에 공개하는 import 경로의 목록입니다. 패키지에 `exports`가 있으면 목록에 없는 하위 경로는 import할 수 없습니다. 1.4.0에는 `exports`가 없어서 `@company/ui/button` 같은 하위 경로를 자유롭게 import할 수 있었습니다. 2.0.0에서 `exports`가 추가됐으므로, 목록에 `./button`이 없거나 경로가 달라졌다면 이 import가 실패합니다.

로컬 `node_modules`는 업그레이드 3일 전보다 먼저 설치한 것이므로 1.4.0이 남아 있을 가능성이 큽니다. 이 경우 로컬 빌드는 2.0.0을 한 번도 사용하지 않았습니다. CI는 `package-lock.json`에 적힌 2.0.0을 새로 설치하므로 같은 import에서 실패합니다.

## 다른 가능성

Node 버전 차이는 주된 원인일 가능성이 낮습니다. Node 18과 Node 20 모두 `exports`를 지원하기 때문입니다.

CI 캐시도 원인일 가능성이 낮습니다. 캐시 키가 `package-lock.json`의 해시이고, 업그레이드로 이 파일이 바뀌었으므로 CI는 옛 캐시를 쓰지 않고 2.0.0을 새로 설치했을 것입니다.

## 미확인 사항

- 로컬에 설치된 `@company/ui`의 실제 버전.
- 2.0.0의 `exports`에 `./button`이 있는지 여부.
- 2.0.0에서 button 파일의 위치나 이름이 바뀌었는지 여부. `exports`가 막는 경우에는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`가 나오므로, 현재 에러 문구는 파일 자체가 없는 경우와도 맞습니다.
- CI가 처음 실패한 시점이 업그레이드 커밋과 일치하는지 여부.

## 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행하고, `node_modules/@company/ui/package.json`의 `version`을 읽습니다.
2. CI 로그의 설치 단계에서 `@company/ui`의 설치 버전을 읽습니다.
3. 2.0.0의 `package.json`에서 `exports`에 `./button`이 있는지 읽고, 패키지 안에 button 파일이 있는지 봅니다.
4. 로컬에서 `rm -rf node_modules && npm ci`를 실행하고 빌드해서 CI와 같은 에러가 나는지 봅니다.
5. 4번에서 재현되지 않으면 CI의 Node를 20으로 바꿔 실행해서 Node 버전의 영향을 따로 가립니다.

## 해결 방향

4번에서 재현되면 원인은 확정입니다. 이후에는 아래 중 하나를 선택합니다.

- 앱의 import 경로를 2.0.0의 `exports`에 공개된 경로로 바꿉니다.
- `@company/ui` 담당자에게 `./button`을 `exports`에 추가하도록 요청합니다.
- 급한 경우 `@company/ui`를 1.4.0으로 고정해서 CI를 복구하고, 위 둘 중 하나를 끝낸 뒤 다시 2.0.0으로 올립니다.

개발자는 로컬 `node_modules`를 지우고 `npm ci`로 다시 설치하는 습관을 들이는 것을 권장합니다. 의존성을 올린 뒤에 로컬 빌드만으로는 CI 결과를 보장할 수 없습니다.
