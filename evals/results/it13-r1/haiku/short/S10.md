현재 자료만으로는 원인을 단정할 수 없습니다. 가장 유력한 가설은 로컬 `node_modules`가 아직 1.4.0이어서 로컬 빌드가 2.0.0 변경을 검증하지 못했다는 것입니다. 이 가설은 아직 확인되지 않았습니다.

### 확인된 사실

- CI 빌드가 `Cannot find module '@company/ui/button'` 오류로 실패합니다.
- 3일 전 `@company/ui` 버전을 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드(패키지 외부에 공개할 파일 경로를 정한 설정)가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키(캐시를 구분하는 값)는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 이전에 설치되었습니다.

### 추론

- 로컬 `node_modules`에는 1.4.0이 남아 있을 가능성이 높습니다. 그러면 로컬 빌드 성공은 2.0.0에서 `button` 경로가 동작한다는 증거가 되지 못합니다.
- `Cannot find module`은 보통 파일 자체를 찾지 못했을 때 나오는 문구입니다. 따라서 `exports`에 `./button` 항목이 빠졌거나 파일 위치가 바뀌었을 가능성을 함께 봐야 합니다.
- Node 버전 차이가 단독 원인일 가능성은 낮아 보입니다. `exports` 해석은 Node 18과 20 모두 지원합니다.
- `package-lock.json`이 2.0.0으로 갱신되어 커밋되었다면 캐시 키가 바뀌어 CI가 새로 설치했을 것입니다. 이 경우 CI에는 2.0.0이 설치되었으므로, 원인은 2.0.0의 구조 변경일 가능성이 큽니다.

### 미확인

- 2.0.0의 `exports` 필드 내용과 `button` 파일의 실제 위치
- CI 로그에 찍힌 실제 설치 버전
- `package-lock.json`이 2.0.0으로 갱신되어 커밋되었는지 여부
- 로컬에 설치된 실제 버전
- 위 가설을 재현한 실행 결과는 아직 없습니다.

### 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. CI 로그에서 설치 단계의 `@company/ui` 버전을 확인합니다.
3. 2.0.0 패키지의 `package.json`에서 `exports` 항목에 `./button`이 있는지 확인합니다.
4. 로컬에서 `node_modules`를 지우고 2.0.0을 새로 설치한 뒤 빌드해 로컬에서도 같은 오류가 나는지 확인합니다.
5. 로컬에서 Node 18로 같은 빌드를 실행해 Node 버전의 영향을 분리합니다.
