CI 실패의 가장 유력한 원인은 `@company/ui` 2.0.0에서 추가된 `exports` 필드입니다. `exports`는 패키지 밖에서 가져올 수 있는 경로를 정해 두는데, 앱이 쓰는 `@company/ui/button`이 이 목록에 없으면 Node는 모듈을 찾지 못합니다. 다만 아직 패키지 내용을 직접 열어 보지 않았으므로 이 원인은 추정입니다.

확인된 사실은 다음과 같습니다. CI에서만 실패하고 로컬에서는 성공합니다. 실패 시점은 2.0.0으로 올린 시점과 맞고, 2.0.0에는 `exports` 필드가 새로 들어갔습니다.

로컬이 성공하는 이유는 로컬 `node_modules`가 3일 전보다 먼저 설치되었다는 점으로 설명될 수 있습니다. 로컬에는 1.4.0 파일이 그대로 남아 있을 가능성이 높습니다. 1.4.0에는 `exports`가 없어서 `button` 파일을 경로로 바로 찾을 수 있습니다. 그러면 로컬 빌드는 2.0.0을 전혀 검증하지 않은 상태로 성공한 것입니다.

CI 캐시 키가 `package-lock.json`의 해시이므로, lock 파일이 2.0.0으로 갱신되어 커밋되었다면 CI는 새 캐시를 만들고 2.0.0을 설치합니다. 이 점은 CI가 새 버전으로 실패했다는 설명과 맞습니다. 다만 lock 파일이 실제로 2.0.0을 가리키는지는 아직 확인되지 않았습니다.

Node 18과 20의 차이는 현재 원인으로 볼 근거가 없습니다. `exports`는 Node 18에서도 지원되므로, 버전 차이만으로 이 오류가 생긴다고 보기는 어렵습니다. 원인을 가리는 데 필요한 점검은 아래 표와 같습니다.

| 가설 | 점검 방법 | 결과에 따른 판단 |
|---|---|---|
| 2.0.0의 `exports`에 `./button` 경로가 없다 | `node_modules/@company/ui/package.json`의 `exports` 항목 조회 | 경로가 없으면 원인이 확정에 가깝습니다. |
| 로컬이 1.4.0을 쓰고 있다 | `npm ls @company/ui` 실행 | 1.4.0이면 로컬 성공이 설명됩니다. |
| CI가 2.0.0을 설치했다 | CI 로그에서 설치된 버전 조회 | 2.0.0이면 CI와 로컬의 설치 버전이 다른 것입니다. |
| Node 버전이 영향을 준다 | 로컬에서 `nvm use 18` 후 `rm -rf node_modules && npm ci && npm run build` 실행 | Node 18에서만 실패하면 버전 영향을 의심할 수 있습니다. 두 버전 모두 실패하면 Node는 원인이 아닙니다. |

원인이 확정되면 수정 방법은 두 가지입니다. 2.0.0 문서나 소스에서 `button`의 새 import 경로를 찾아 코드를 맞추거나, `@company/ui`를 1.4.0으로 되돌리는 방법입니다.

개발자는 표의 첫 번째와 두 번째 점검을 먼저 실행하고 결과를 공유하십시오.
