**가장 가능성이 높은 원인은 로컬 `node_modules`에 아직 1.4.0이 남아 있어서, 로컬 빌드가 2.0.0을 한 번도 검증하지 않았다는 점입니다.** 이는 추론이며 아직 확인하지 않았습니다. 그러므로 **로컬 빌드 성공을 2.0.0 검증으로 보면 안 됩니다.**

## 추론한 원인

`exports` 필드(패키지가 외부에 공개하는 경로 목록)가 있으면 공개된 경로만 가져올 수 있습니다. 1.4.0에는 이 필드가 없어서 `@company/ui/button`처럼 내부 파일 경로를 직접 가져오는 방식(딥 임포트)이 동작했습니다. 2.0.0에서 `./button`이 공개 목록에 없다면 이 import는 실패합니다.

차이는 다음과 같이 설명됩니다. 로컬 `node_modules`는 3일 전보다 먼저 설치되어 1.4.0이 들어 있을 가능성이 큽니다. 그래서 로컬은 1.4.0으로 빌드되어 성공합니다. CI는 `package-lock.json`을 기준으로 새로 설치하므로 2.0.0을 받아 실패합니다.

## 다른 요인에 대한 판단

Node 18과 20의 `exports` 해석 규칙은 같으므로 Node 버전 차이가 주원인일 가능성은 낮습니다. 다만 Node 버전에 따라 기본 npm 메이저 버전이 다를 수 있으므로, 설치 결과가 달라지는지는 재현으로 확인해야 합니다.

캐시 키가 lockfile 해시라면, 버전이 바뀌면서 lockfile도 바뀌었을 때 CI 캐시는 항상 새로 만들어집니다. 따라서 CI가 2.0.0을 받는 설명과 맞습니다. 워크플로에 `restore-keys`(부분 일치 캐시 복원) 설정이 있다면 오래된 캐시가 복원될 수 있으니 확인이 필요합니다.

## 확인 필요 항목

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. CI 로그에서 같은 명령의 출력을 확인합니다.
3. 2.0.0 패키지의 `package.json`에 `./button` 경로가 `exports`에 있는지 확인합니다.
4. 에러 문구를 전체 로그에서 확인합니다. `Cannot find module`은 Node가 내는 문구이고, Next.js 빌드 단계에서는 보통 `Module not found`가 나옵니다. 어느 단계에서 실패하는지 확인이 필요합니다.
5. 로컬에서 Node 18로 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드해 CI 조건을 재현합니다.

## 조치 선택지

단기 조치는 세 가지입니다. 첫째, import를 2.0.0이 공개한 경로로 바꿉니다. 이때 올바른 경로는 패키지 문서에서 확인해야 합니다. 둘째, 라이브러리 담당자에게 `./button`을 공개해 달라고 요청합니다. 셋째, 빠른 복구가 필요하면 1.4.0으로 임시 고정합니다.

재발 방지는 다음과 같습니다. 로컬도 `npm ci`로 lockfile 기준 재설치를 해야 합니다. Node 버전은 `.nvmrc`와 CI 설정에 같이 고정하는 것을 권장합니다.
