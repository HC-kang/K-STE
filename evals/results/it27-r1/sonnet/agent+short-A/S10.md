가장 가능성이 높은 원인은 로컬이 아직 `@company/ui` 1.4.0을 쓰고 있어서, 2.0.0에서 생긴 `exports` 제한이 로컬 빌드에는 적용되지 않는 것입니다. 이 내용은 추론이며, 아래 확인 방법으로 검증하기 전까지는 확정이 아닙니다.

## 확인된 사실

- CI(GitHub Actions) 빌드만 `Error: Cannot find module '@company/ui/button'`로 실패합니다. 로컬 빌드는 성공합니다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0 패키지에는 `exports` 필드가 추가됐습니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치한 것입니다.

## 추론

1. `exports` 필드(패키지가 외부에 공개하는 import 경로를 `package.json`에 적어 제한하는 설정)가 있으면, 거기에 적지 않은 경로로는 import할 수 없습니다. 2.0.0의 `exports`에 `./button`이 없거나 형식이 다르면, `@company/ui/button` import는 `Cannot find module`로 실패합니다.
2. 로컬 `node_modules`는 업그레이드보다 먼저 설치했으므로 1.4.0이 남아 있을 가능성이 큽니다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button` import가 파일 경로로 그대로 동작합니다.
3. `package-lock.json`이 2.0.0으로 바뀌었다면, CI는 캐시 키가 달라져 2.0.0을 새로 설치합니다. 그래서 CI에서만 실패합니다.
4. Node 18과 20은 둘 다 `exports` 필드를 지원합니다. 그래서 Node 버전 차이는 원인일 가능성이 낮다고 봅니다.
5. 캐시도 원인일 가능성이 낮습니다. 캐시 키가 `package-lock.json` 해시이므로, 업그레이드 때 키가 바뀌어 1.4.0 캐시를 복원하지 않았을 것입니다.

## 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 봅니다.
2. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드합니다. 로컬에서도 같은 에러가 나면 추론 1-3이 맞습니다.
3. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 봅니다.
4. CI 로그의 `npm ci` 단계에서 `@company/ui`가 2.0.0으로 설치됐는지 봅니다.

## 해결 방향

2번에서 같은 에러가 재현되면, 3번 결과에 따라 둘 중 하나를 선택해야 합니다.

- `exports`에 `./button`이 없으면 `@company/ui` 쪽에 경로를 추가하거나, 앱의 import 경로를 2.0.0이 공개하는 경로로 바꿔야 합니다.
- `exports`에 `./button`이 있는데도 실패하면, 조건 키(`import`, `require`, `types` 등)가 앱의 빌드 방식과 맞는지 따로 봐야 합니다.

확인 필요: 2.0.0이 공개하는 `button` 경로가 무엇인지는 주어진 정보에 없습니다. 이 경로가 정해져야 import 수정 범위를 알 수 있습니다.
