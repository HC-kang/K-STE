가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다. 이 필드에 `./button` 경로가 없으면 `@company/ui/button` import가 해석되지 않습니다. 다만 아래 내용은 아직 사실로 확인되지 않았으므로 원인으로 확정하기 전에 검증해야 합니다.

로컬 빌드 성공은 2.0.0에서 빌드가 통과한다는 근거가 아닐 수 있습니다. 로컬 `node_modules`가 3일 전보다 먼저 설치되었다면 로컬에는 1.4.0이 남아 있을 가능성이 큽니다. 1.4.0에는 `exports`가 없어서 하위 경로를 파일 경로대로 찾기 때문에 로컬에서는 빌드가 통과했을 수 있습니다.

| 구분 | 내용 |
|---|---|
| 사실 | CI에서만 빌드가 실패하고 로컬은 성공합니다. 에러는 `Cannot find module '@company/ui/button'`입니다. 3일 전 1.4.0에서 2.0.0으로 올렸고, 2.0.0에 `exports` 필드가 추가되었습니다. CI는 Node 18, 로컬은 Node 20을 씁니다. CI 캐시 키는 `package-lock.json` 해시입니다. 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다. |
| 추론 | 2.0.0의 `exports`에 `./button`이 없어서 import가 차단되었을 가능성이 가장 큽니다. 로컬은 1.4.0을 쓰고 있어서 성공했을 가능성이 큽니다. CI는 lock 파일 기준으로 2.0.0을 설치했을 가능성이 큽니다. |
| 미확인 | 2.0.0의 `exports` 실제 내용, 로컬에 설치된 실제 버전, CI 로그의 설치 버전, Node 18과 20의 차이가 이 에러에 영향을 주는지 여부입니다. |

에러 문구만으로는 `exports`가 경로를 차단한 경우와 2.0.0에서 파일 경로가 바뀐 경우를 구분하기 어렵습니다. 두 경우 모두 같은 에러가 날 수 있습니다. Node 18과 20은 둘 다 `exports`를 지원하므로, 버전 차이만으로 이 에러가 생겼다고 보기는 어렵습니다.

개발자는 다음 순서로 원인을 좁히십시오.
1. CI 로그에서 설치된 `@company/ui` 버전을 찾으십시오.
2. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 찾으십시오.
3. 로컬 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드해서 2.0.0에서도 같은 에러가 나는지 재현하십시오.
4. 2.0.0 패키지의 `package.json`에서 `exports` 항목에 `./button`이 있는지 살펴보십시오.
5. 재현되면 Node 18로 로컬 빌드를 돌려 CI 환경과 같은 조건에서 결과를 비교하십시오.

PM은 이 빌드 실패가 현재 배포를 막고 있는지와, 2.0.0 대응과 1.4.0 유지 중 어느 쪽으로 갈지 결정이 필요한지를 개발팀에 물어보십시오.
