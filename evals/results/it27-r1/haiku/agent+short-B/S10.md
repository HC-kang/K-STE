현재 원인은 아직 확정되지 않았습니다. 가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드(패키지 외부에서 쓸 수 있는 경로를 정하는 설정)가 `@company/ui/button` 경로를 허용하지 않는 것입니다.

## 주어진 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0부터 `exports` 필드가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`(설치할 패키지 버전을 고정한 파일)의 해시입니다.
- 로컬 `node_modules`(설치된 패키지가 들어 있는 폴더)는 3일 전 업그레이드보다 먼저 설치되었습니다.

## 추론

업그레이드로 `package-lock.json`이 바뀌었으므로 CI의 캐시 키도 바뀝니다. 그래서 CI는 저장된 캐시를 쓰지 못하고 2.0.0을 새로 설치합니다. 따라서 CI 빌드는 2.0.0을 실제로 쓰는 첫 빌드일 가능성이 큽니다.

로컬은 상황이 다를 수 있습니다. 로컬 `node_modules`가 업그레이드 전에 설치되었으므로 1.4.0이 그대로 남아 있을 수 있습니다. 이 경우 로컬 빌드 성공은 2.0.0에 문제가 없다는 증거가 되지 않습니다.

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `@company/ui` 버전 | 1.4.0일 가능성 (설치 시점 기준) | 2.0.0일 가능성 (새 설치 기준) |
| 의존성 준비 방식 | 3일 전 이전 설치분 재사용 | 저장된 캐시가 없어 새로 설치 |

오류 문구 `Cannot find module`은 Node가 `require`로 파일을 찾지 못할 때 내는 문구입니다. Next.js 빌드 중 웹팩이 내는 오류라면 문구가 다를 가능성이 큽니다. 따라서 이 오류가 빌드의 어느 단계에서 나왔는지는 전체 로그를 봐야 알 수 있습니다.

Node 18은 2025년 4월에 지원이 끝났습니다. 다만 2.0.0이 Node 20 이상을 요구하는지는 현재 근거가 없습니다. 2.0.0의 `engines` 필드를 봐야 합니다.

배포 영향 범위는 제공된 정보만으로는 판단할 수 없습니다.

## 점검 항목

1. 로컬 `node_modules/@company/ui/package.json`의 `version` 값을 봅니다. 1.4.0이면 로컬 성공은 이전 버전 기준입니다.
2. 2.0.0의 `package.json`에서 `exports`에 `./button` 또는 `./*` 패턴이 있는지 봅니다.
3. 2.0.0의 `engines` 필드에서 요구하는 Node 버전을 봅니다.
4. CI 로그에서 오류가 난 단계와 전체 메시지를 봅니다.
5. CI 캐시 설정에 `restore-keys`(이전 키의 캐시를 대신 불러오는 설정)가 있는지 봅니다. 있으면 오래된 `node_modules`가 쓰였을 수 있습니다.

## 권장 작업

1. 로컬에서 `node_modules`를 지우고 `npm ci`로 lockfile 기준 재설치한 뒤 빌드합니다. Node 18로 같은 조건을 재현하는 것을 권장합니다.
2. 2.0.0의 `exports`에 `button` 경로가 없으면 `@company/ui` 담당자에게 경로 추가를 요청합니다. 루트 경로에서 Button을 내보내는지 먼저 본 뒤, 루트에서 가져오도록 import 방식을 바꿀 수도 있습니다.
3. CI 빌드를 빨리 복구해야 하면 `@company/ui`를 1.4.0으로 되돌릴 수 있습니다. 이 경우 2.0.0에서 추가된 기능은 쓸 수 없으므로, 되돌릴지는 PM과 함께 정합니다.
4. CI의 Node 버전을 20 이상으로 올리는 것을 권장합니다.
