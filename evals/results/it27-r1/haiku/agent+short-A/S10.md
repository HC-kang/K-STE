가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다. 로컬 `node_modules`에는 1.4.0이 남아 있을 가능성이 높고, CI는 2.0.0을 새로 설치하므로 `@company/ui/button` 경로가 막히는 것으로 보입니다. 이 내용은 전달받은 사실에서 추론한 것이며, 코드와 로그는 아직 확인하지 않았습니다.

## 원인 가설

`exports` 필드가 있으면 패키지 바깥에서 가져올 수 있는 경로는 `exports`에 적힌 경로로 제한됩니다. 적히지 않은 경로는 Node와 번들러가 해석하지 못합니다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`이 파일 경로대로 풀립니다.

로컬 `node_modules`는 3일 전보다 먼저 설치됐으므로 1.4.0일 가능성이 높습니다. 그래서 로컬 빌드는 성공합니다. CI는 `package-lock.json` 해시로 캐시 키를 잡습니다. lock 파일이 2.0.0으로 갱신됐다면 캐시 키가 바뀌어 CI가 2.0.0을 새로 설치합니다.

Node 버전 차이가 원인일 가능성은 낮습니다. `exports`를 해석하는 방식은 Node 18과 Node 20에서 같습니다.

에러 메시지도 단서입니다. `Cannot find module`은 Node가 `require`로 모듈을 찾지 못할 때 나오는 메시지입니다. 웹팩의 빌드 에러는 보통 `Module not found`로 표시됩니다. 따라서 에러가 난 위치가 Next.js 설정 파일처럼 Node가 직접 실행하는 파일일 수 있습니다.

## 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인하십시오. 1.4.0이면 가설이 맞을 가능성이 높습니다.
2. 2.0.0 패키지의 `package.json`에서 `exports` 항목에 `./button`이 있는지 확인하십시오.
3. CI 로그에서 빌드 실패 직전의 `npm ls @company/ui` 결과와 에러가 난 파일 경로를 확인하십시오.
4. 같은 커밋에서 `package-lock.json`의 `@company/ui` 버전이 2.0.0으로 바뀌었는지 확인하십시오.

## 해결 선택지

| 방법 | 내용 | 특징 |
|---|---|---|
| import 경로 수정 | 2.0.0 `exports`에 있는 경로로 바꿉니다 | 2.0.0을 유지합니다 |
| 1.4.0 고정 | `package.json`과 lock 파일에서 버전을 1.4.0으로 되돌립니다 | 2.0.0 적용이 늦어집니다 |
| 담당자에게 요청 | `./button` 경로를 `exports`에 추가해 달라고 요청합니다 | 요청 결과를 기다려야 합니다 |

확인 필요: 이 빌드 실패가 배포를 막고 있는지. 1번과 2번의 결과로 원인을 확정할 수 있습니다.
