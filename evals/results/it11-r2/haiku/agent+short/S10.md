## 결론

CI에서만 실패하는 가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드가 `button` 하위 경로를 노출하지 않는 것이다. 로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 3일 전 이전에 설치된 1.4.0일 가능성이 높기 때문으로 보인다. 따라서 로컬 성공은 2.0.0이 정상이라는 근거가 되지 않는다. 이 분석은 제공된 정보만으로 작성했으며, 저장소, CI 로그, 패키지 소스는 직접 확인하지 않았다.

## 확인된 사실 (제공된 정보)

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에 `exports` 필드가 추가되었다.
- CI는 Node 18, 로컬은 Node 20을 사용한다.
- CI 캐시 키는 `package-lock.json`의 해시다.
- 로컬 `node_modules`는 3일 전 이전에 설치되었다.
- CI 에러는 `Error: Cannot find module '@company/ui/button'`이다.

## 원인 분석 (추론)

`exports` 필드가 있는 패키지는 그 필드에 적힌 경로만 외부에서 가져올 수 있다. 1.4.0에는 `exports`가 없으므로 `@company/ui/button`은 파일 경로로 그대로 해석되었다. 2.0.0에서 `exports`가 생기면서 `./button`이 목록에 없거나 다른 이름으로 바뀌었다면, 같은 import는 CI에서 실패한다. 로컬에는 1.4.0이 있으므로 같은 import가 성공한다.

다만 Node의 `exports` 위반 에러는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`로 표시되고, 보고된 메시지는 `Cannot find module`이다. 이 차이는 에러가 Node의 `require` 단계에서 나왔는지, Next.js 번들러나 TypeScript 단계에서 나왔는지에 따라 달라진다. 확인 필요: 전체 CI 로그에서 에러가 발생한 단계를 확인해야 한다.

## 가능성이 낮은 원인

- **Node 18과 20의 차이**: `exports` 해석은 Node 12.7 이후 양쪽 모두 지원하므로, 버전 차이만으로 이 에러가 날 가능성은 낮다. 다만 2.0.0이 ESM 전용 패키지라면 Node 18에서 `require`로 가져올 때 문제가 생길 수 있다. 확인 필요: 2.0.0의 모듈 형식.
- **CI 캐시**: 캐시 키가 lock 파일 해시이므로, lock 파일이 2.0.0으로 갱신되어 커밋되었다면 CI는 새로 설치하여 2.0.0을 받는다. 확인 필요: `package-lock.json`이 실제로 2.0.0을 가리키는지, CI 설정에 `restore-keys`로 이전 캐시를 복원하는 설정이 있는지 확인해야 한다.

## 확인 방법

1. 로컬에서 `npm ls @company/ui`를 실행하여 설치된 버전을 확인한다.
2. 로컬에서 `rm -rf node_modules && npm ci`로 lock 파일 기준으로 다시 설치한 뒤 빌드한다. 실패하면 로컬에서도 재현된 것이다.
3. `cat node_modules/@company/ui/package.json`으로 2.0.0의 `exports` 목록에 `./button` 또는 그 대체 경로가 있는지 확인한다.
4. CI 로그에서 에러가 난 단계를 확인한다.

## 조치 방안

1. 2.0.0의 `exports`에서 실제로 노출된 경로로 import를 수정한다. 이 방법이 가장 빠르게 빌드를 복구하는 방법이다.
2. `@company/ui` 소유 팀이 같은 조직이라면 `./button` 경로를 `exports`에 추가해 달라고 요청한다.
3. 2.0.0 대응이 당장 어렵다면 1.4.0으로 되돌린다. 이 방법은 빌드를 복구하지만 2.0.0 마이그레이션은 미룬다.
4. 로컬과 CI의 Node 버전을 맞춘다. Node 18은 2025년 4월에 지원이 종료되었으므로, CI를 Node 20 이상으로 올리는 것을 권장한다.
5. 로컬 검증 절차에 `npm ci` 후 빌드를 추가하여, 오래된 `node_modules`로 검증하는 일이 반복되지 않도록 한다.
