**결론: 가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드가 `button` 하위 경로를 공개하지 않는 것입니다.** 이 추론은 2.0.0의 `exports` 값을 직접 확인해야 확정할 수 있습니다.

**확인된 사실**
- 2.0.0에서 `exports` 필드가 추가되었습니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다. 로컬 빌드는 업그레이드 전 버전인 1.4.0으로 실행되었을 가능성이 높습니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.

**추론**
- `exports` 필드에 `./button` 항목이 없으면 `@company/ui/button` 임포트는 CI에서든 로컬에서든 해석되지 않습니다. 로컬이 성공한 이유는 로컬이 2.0.0을 쓰지 않기 때문으로 보입니다. 로컬 성공은 2.0.0에서 이 임포트가 동작한다는 증거가 아닙니다.

**가설별 상태**

| 가설 | 근거 | 상태 |
|---|---|---|
| 2.0.0의 `exports`가 `./button`을 공개하지 않음 | 2.0.0에 `exports`가 추가됨, 로컬은 구버전 설치 | 가장 유력, 패키지 확인 필요 |
| Node 18과 20의 해석 차이 | 두 버전 모두 `exports`를 지원함 | 배제되지 않음, 같은 Node 버전으로 재현 필요 |
| 캐시가 오래된 설치 결과를 씀 | 캐시 키가 lock 해시임 | 가능성 낮음, 워크플로의 복원 설정 확인 필요 |
| 커밋된 lock 파일이 2.0.0을 반영하지 않음 | 미확인 | 확인 필요 |

**에러 메시지에 대해**
Node는 `exports`에 없는 경로를 막을 때 보통 "Package subpath ... is not defined by exports"라는 메시지를 냅니다. "Cannot find module"은 파일 부재나 경로 오류에서도 나옵니다.
확인 필요: "Cannot find module". 가능한 해석은 Node의 `exports` 해석 실패와 번들러 단계의 파일 부재 두 가지입니다. 전체 스택 트레이스로 어느 단계에서 실패하는지 확인하십시오.

**다음 확인 순서**
1. `@company/ui` 2.0.0의 `package.json`에서 `exports` 필드에 `./button` 항목이 있는지 확인하십시오.
2. CI 로그에서 설치된 `@company/ui` 버전과 Node 버전을 출력하여 확인하십시오.
3. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤, Node 18과 20 각각으로 빌드하여 같은 에러가 나는지 확인하십시오.
4. 2.0.0 패키지에 `./button` 경로가 없으면 임포트를 2.0.0이 공개한 경로로 바꾸거나 패키지 측에 경로 추가를 요청하십시오. 당장 빌드를 복구해야 하면 1.4.0 고정도 선택지입니다.

PM께서는 특히 2번의 CI 로그 결과를 기다려 주시면 원인 확정 시점을 정할 수 있습니다.
