현재 자료로 가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다. 다만 아직 확인되지 않은 추론이므로, 아래 확인 항목을 먼저 확인하십시오.

업그레이드 후 CI 캐시 키(`package-lock.json` 해시)가 바뀌었을 가능성이 높으므로, CI는 새로 설치하면서 2.0.0을 받았을 것으로 보입니다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`이 파일 위치대로 해석됩니다. 2.0.0에서는 `exports`에 등록된 경로만 import할 수 있으므로, 등록되지 않은 `./button` 경로가 실패로 이어질 수 있습니다.

로컬 빌드가 성공한 이유는 로컬 `node_modules`가 업그레이드 전에 설치되어 1.4.0이 남아 있을 가능성이 높기 때문입니다. 따라서 로컬 성공은 2.0.0이 정상이라는 증거가 아닙니다. 로컬에서는 2.0.0이 아직 검증되지 않은 상태입니다.

| 요인 | 현재 근거 | 판단 |
|---|---|---|
| 2.0.0의 `exports` 추가 | 업그레이드 시점과 실패 시점이 맞고, 1.4.0과 2.0.0의 차이가 이 경로 해석에 해당합니다. | 가장 유력하지만 미확인입니다. |
| Node 18과 20의 차이 | 두 버전 모두 `exports`를 지원하며, 이 에러를 만든다는 근거는 현재 없습니다. | 원인일 가능성은 낮습니다. 재현 실험에서 확인합니다. |
| CI 캐시 키 | 키가 lockfile 해시이므로 lockfile이 바뀌면 새 설치가 일어납니다. | 업그레이드 커밋에 lockfile 변경이 포함되었는지 확인 필요합니다. |
| 로컬 `node_modules` | 업그레이드 전에 설치되어 1.4.0일 가능성이 높습니다. | 로컬 성공은 설명하지만 2.0.0 검증은 되지 않았습니다. |

확인 필요: 에러 문구. `Cannot find module`은 파일을 찾지 못했을 때 나오는 문구입니다. `exports`에서 경로를 막았을 때 Node는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`를 냅니다. 따라서 `exports`가 가리키는 파일이 실제로 없거나, 다른 원인일 수 있습니다. 전체 스택 트레이스가 필요합니다.

다음 순서로 확인하십시오.

1. CI 로그에서 `npm ls @company/ui`의 출력을 확인하여 실제 설치 버전이 2.0.0인지 보십시오.
2. 실패 로그의 전체 스택 트레이스에서 에러를 낸 파일과 import 줄을 찾으십시오.
3. 2.0.0의 `package.json`에서 `exports` 항목을 열고, 코드가 import하는 `./button` 경로가 등록되어 있는지 확인하십시오.
4. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드하십시오. 실패가 재현되면 2.0.0과 빌드 실패의 연관이 확인됩니다.
5. 같은 빌드를 Node 18로 로컬에서 실행하여 Node 버전의 영향을 확인하십시오.
6. CI 캐시 설정에 `restore-keys`가 있는지 확인하십시오. 있다면 이전 캐시가 복원되었을 수 있습니다.

3번에서 `./button`이 등록되어 있지 않다고 확인되면, 대응 방향은 세 가지입니다. 코드의 import 경로를 `exports`가 허용하는 경로로 바꾸거나, `@company/ui` 제작자에게 경로 추가를 요청하거나, 2.0.0 업그레이드를 보류하는 것입니다. 어느 쪽을 택할지는 PM과 함께 정하십시오.
