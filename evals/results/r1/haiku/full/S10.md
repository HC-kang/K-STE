# @company/ui 2.0.0 업그레이드 후 CI 빌드 실패 원인 분석

현재 원인은 확정되지 않았다. 가장 유력한 원인은 @company/ui 2.0.0에 새로 추가된 `exports` 필드다. 로컬 빌드가 성공하는 이유는 Node 버전 차이보다 로컬 `node_modules`에 1.4.0이 남아 있기 때문으로 보인다. 아래 내용은 제공된 사실에서 추론한 것이며, 확인하지 않은 항목은 따로 적었다.

## 확인된 사실

- 3일 전 @company/ui를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에 `exports` 필드가 추가됐다.
- CI는 Node 18, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 package-lock.json의 해시다.
- 로컬 `node_modules`는 업그레이드 3일 전에 설치됐다.

## 원인 분석

`exports` 필드가 있으면 Node와 번들러는 패키지가 명시한 경로만 가져올 수 있다. `@company/ui/button`이 `exports` 목록에 없으면 이 경로의 import는 해석에 실패한다. 에러 메시지 `Cannot find module`은 이 해석 실패에서 나온 것으로 보인다.

로컬 빌드가 성공한 이유는 다음과 같이 추론한다. 로컬 `node_modules`가 업그레이드 전에 설치됐으므로 1.4.0이 그대로 남아 있을 가능성이 높다. 1.4.0에는 `exports` 필드가 없어 `@company/ui/button`이 파일 경로로 해석된다. 따라서 로컬 빌드는 2.0.0 동작을 검증하지 않았다.

Node 18과 20의 차이가 원인일 가능성은 낮다고 본다. 두 버전 모두 `exports` 필드를 지원한다. 다만 npm 버전이 달라 lock 파일 해석이 달라질 수 있으므로 이 가능성은 확인이 필요하다.

## 확인 필요 항목

- CI가 실제로 설치한 @company/ui 버전이다. 캐시 설정에 `restore-keys` 같은 대체 키가 있으면 이전 캐시가 복원됐을 수 있다.
- package-lock.json에 @company/ui 2.0.0이 기록됐는지 여부다.
- 2.0.0 패키지의 `exports` 필드에 `button` 경로가 포함됐는지 여부다.
- 프로젝트 코드에서 `@company/ui/` 하위 경로를 import하는 곳이 몇 군데인지 여부다.

## 검증 절차

1. CI 빌드 단계에 `npm ls @company/ui`를 추가하여 실제 설치 버전을 확인한다.
2. 2.0.0의 package.json을 열어 `exports` 필드에 `./button` 경로가 있는지 확인한다.
3. 프로젝트에서 `@company/ui/`로 시작하는 import를 검색하여 목록을 만든다.
4. Node 18로 전환한 뒤 로컬에서 `node_modules`를 삭제하고 `npm ci`로 다시 설치한다.
5. 같은 환경에서 빌드를 실행하여 에러가 재현되는지 확인한다.

## 수정 방향

검증 결과에 따라 다음 중 하나를 고른다.

- 호출하는 쪽을 고친다. `exports`가 허용하는 경로로 import를 바꾼다.
- 패키지 관리 팀에 요청한다. 필요한 경로를 `exports`에 추가해 달라고 요청한다.
- 임시 조치로 1.4.0에 고정한다. 원인이 해결될 때까지 업그레이드를 되돌린다.

PM에게는 현재 상태를 "원인 가설 확인 중, 로컬 재현 후 수정 방향 결정 예정"으로 공유하는 것을 권장한다.
