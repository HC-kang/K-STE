# `@company/ui` 2.0.0 업그레이드 후 CI 빌드 실패 원인 분석

## 요약

- **CI에서만 실패하는 게 아니라 2.0.0 설치 상태라면 로컬에서도 실패할 가능성이 높습니다.** 로컬 `node_modules`가 3일 전 이전 설치본(1.4.0)이라서, 로컬 빌드는 2.0.0을 검증하지 않았습니다.
- Node 18/20 차이는 주요 원인일 가능성이 낮습니다. 두 버전 모두 `exports` 필드를 지원합니다.
- 가장 유력한 원인은 **2.0.0의 `exports` 필드가 `@company/ui/button` 경로를 제대로 노출하지 않는 것**입니다. 정확한 원인은 아래 확인 단계로 1~2분이면 특정할 수 있습니다.

## 배경

| 항목 | 내용 |
|---|---|
| 변경 | `@company/ui` 1.4.0 → 2.0.0 (3일 전) |
| 2.0.0 변경점 | `package.json`에 `exports` 필드 추가 |
| CI | Node 18, 캐시 키 = `package-lock.json` 해시 |
| 로컬 | Node 20, `node_modules`는 3일 전보다 이전에 설치됨 |
| 증상 | CI 빌드 실패: `Cannot find module '@company/ui/button'` |

## 원인 분석

### 1. 로컬이 성공하는 이유: 로컬은 1.4.0으로 빌드하고 있을 가능성이 큼 (가장 유력)

- 로컬 `node_modules`가 설치된 이후 `npm install`/`npm ci`를 다시 하지 않았다면, 여전히 1.4.0이 들어 있습니다.
- 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`이 `node_modules/@company/ui/button.js` 같은 파일 경로로 그냥 해석됩니다. 그래서 성공합니다.
- 즉 **"로컬 성공"은 2.0.0이 정상이라는 근거가 아닙니다.** 같은 조건에서 검증되지 않았기 때문입니다.

### 2. 2.0.0에서 `exports`가 `./button` 경로를 노출하지 않을 가능성 (유력)

`exports`가 있으면 Node와 번들러는 `exports`에 명시된 경로만 허용합니다. 다음 중 하나가 원인일 수 있습니다.

- `exports`에 `./button` 항목이 없음 (예: `./components/button`으로 경로가 바뀜)
- 패턴 매핑(`./*`)이 있어도 실제 파일 경로와 맞지 않음
- 배포 패키지에 해당 파일이 포함되지 않음 (`files` 필드 누락 등)

참고로 Node가 `exports` 제한 때문에 막으면 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`가 나옵니다. `Cannot find module`은 **파일 자체가 없거나, `exports`를 무시하는 도구(예: TypeScript의 구형 `moduleResolution: node`)가 해석한 경우**에 주로 나타납니다.

### 3. TypeScript 타입 해석 문제 (가능성 있음)

- Next.js 빌드는 타입 체크를 수행합니다. TypeScript가 `moduleResolution: "node"`(node10)로 설정돼 있으면 `exports`를 읽지 않습니다.
- 1.4.0 로컬 환경에서는 타입 파일이 그대로 보여서 통과하고, 2.0.0을 설치한 환경에서만 실패할 수 있습니다.
- 이 경우 에러 메시지도 `Cannot find module ... or its corresponding type declarations`처럼 보일 수 있습니다.

### 4. Node 18 vs 20 (가능성 낮음, 배제 필요)

- Node 18과 20 모두 `exports`를 지원하므로 단순 경로 해석 차이로는 설명되지 않습니다.
- 다만 2.0.0이 ESM 전용이거나 `require(esm)`에 의존하면 Node 18에서만 실패할 수 있습니다.
- 두 Node 버전에서 npm 버전도 다릅니다(Node 18은 npm 9 계열, Node 20은 npm 10 계열). 이 차이도 lockfile 해석에 영향을 줄 수 있으니 함께 확인합니다.

### 5. 캐시 문제 (낮음)

- 캐시 키가 `package-lock.json` 해시이므로, lockfile이 바뀌었다면 캐시가 새로 만들어져 보통 문제가 없습니다.
- 다만 `restore-keys`로 이전 캐시를 fallback 복원하고 있다면, 1.4.0이 담긴 `node_modules`가 복원됐을 수 있습니다.
- 또 `package.json`만 바꾸고 lockfile을 커밋하지 않았다면 CI 설치 결과가 달라질 수 있습니다.

## 확인 방법

아래 순서로 확인하면 원인을 좁힐 수 있습니다.

1. **로컬 설치 버전 확인**
   ```bash
   npm ls @company/ui
   ```
   1.4.0이면 가설 1이 확인됩니다.

2. **로컬에서 2.0.0을 깨끗하게 재현**
   ```bash
   rm -rf node_modules && npm ci
   npm run build
   ```
   여기서도 실패하면 CI만의 문제가 아니라 2.0.0 자체의 문제입니다.

3. **패키지의 `exports` 확인**
   ```bash
   cat node_modules/@company/ui/package.json | grep -A 30 '"exports"'
   ls node_modules/@company/ui
   ```
   `./button` 경로가 있는지, 실제 파일이 존재하는지 봅니다.

4. **TypeScript 설정 확인**
   `tsconfig.json`의 `moduleResolution` 값을 확인합니다. `node` 또는 `node10`이면 가설 3을 의심합니다.

5. **CI에서 Node 20으로 한 번 돌려보기**
   Node 버전 차이를 배제하는 용도입니다. 여기서도 같은 에러가 나면 Node 버전은 원인이 아닙니다.

## 해결 방안

원인 확인 결과에 따라 달라집니다.

- **`exports`에 경로가 없거나 바뀐 경우**: `@company/ui`의 메인테이너에게 경로 확인을 요청하거나, 앱 코드의 import 경로를 2.0.0 기준으로 수정합니다 (예: `@company/ui/components/button` 등).
- **패키지 파일이 누락된 경우**: 패키지 배포 문제이므로 `@company/ui` 쪽에서 2.0.1 같은 패치 릴리스가 필요합니다.
- **TypeScript 해석 문제인 경우**: `tsconfig.json`의 `moduleResolution`을 `bundler` 또는 `node16`/`nodenext`로 올리는 것을 검토합니다. 또는 패키지가 `typesVersions`를 제공하는지 확인합니다.
- **Node 18 호환 문제인 경우**: CI의 Node 버전을 로컬과 맞추거나(예: Node 20), 패키지 쪽 호환성 문제를 해결합니다.
- **임시 조치**: 빠르게 복구가 필요하면 `@company/ui`를 1.4.0으로 되돌려 CI를 통과시킨 뒤, 2.0.0 마이그레이션을 별도 작업으로 진행합니다.

## PM 관점 요약

- 현재 빌드가 깨져 있고, 원인은 `@company/ui` 2.0.0 업그레이드와 연결되어 있습니다.
- 로컬에서 성공했던 것은 로컬 설치본이 오래되어서이므로, 업그레이드 검증이 아직 끝나지 않은 상태로 보는 것이 맞습니다.
- 빠른 복구(1.4.0 롤백)와 정식 수정(2.0.0 경로 대응) 중 어느 쪽으로 갈지 결정이 필요합니다. 원인 확인은 위 1~3번 단계로 짧게 끝낼 수 있습니다.

## 아직 모르는 것

- 2.0.0의 `exports` 필드 실제 내용
- `tsconfig.json`의 `moduleResolution` 값
- 에러가 발생하는 정확한 빌드 단계 (webpack 번들링인지, `next.config.js` 같은 설정 파일 로드인지). 에러 형식이 `Error: Cannot find module`이면 Next.js 번들러보다는 Node 런타임이 설정 파일을 `require`하면서 나는 에러일 수도 있습니다. 전체 로그 한 줄을 확인하면 좋습니다.

위 확인 결과를 알려주시면 원인을 더 좁혀서 정리해 드리겠습니다.
