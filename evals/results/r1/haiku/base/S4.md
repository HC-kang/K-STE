# 운영 배포 롤백 런북: payment-api

**대상 서비스:** payment-api
**배포 도구:** ArgoCD
**롤백 명령:** `argocd app rollback payment-api <REVISION>`

> **중요 규칙**
> - DB 마이그레이션이 포함된 배포는 **절대 롤백하지 않는다.** 마이그레이션이 포함됐다면 롤백을 중단하고 DBA **박지은**에게 연락한다.
> - 롤백 전 마이그레이션 여부 확인은 필수 단계다. 건너뛰지 않는다.

---

## 1. 사전 준비

- [ ] ArgoCD CLI로 로그인되어 있는지 확인한다.
  ```bash
  argocd login <ARGOCD_SERVER>
  argocd app get payment-api
  ```
- [ ] 현재 배포된 리비전(현재 버전)과 롤백 대상 리비전을 확인한다.
  ```bash
  argocd app history payment-api
  ```
  출력된 `ID` 열의 값이 `<REVISION>`이다. 롤백 대상은 직전 정상 배포의 ID다.
- [ ] 장애 상황과 롤백 사유를 기록한다.

## 2. 마이그레이션 포함 여부 확인 (필수 게이트)

현재 리비전과 롤백 대상 리비전 사이에 DB 마이그레이션이 포함되어 있는지 확인한다.

1. 두 리비전에 해당하는 커밋 범위를 확인한다. (`<CURRENT_SHA>`와 `<TARGET_SHA>`는 `argocd app history` 또는 `argocd app get`의 revision 값이다.)
   ```bash
   git log --oneline <TARGET_SHA>..<CURRENT_SHA>
   git diff --stat <TARGET_SHA>..<CURRENT_SHA> -- <MIGRATION_PATH>
   ```
   `<MIGRATION_PATH>`는 팀의 마이그레이션 디렉터리다. (예: `db/migrations/`) 실제 경로를 확인해서 넣는다.
2. 해당 범위에 마이그레이션 파일 변경이 **하나라도** 있으면 아래 분기를 따른다.

| 결과 | 조치 |
|---|---|
| **마이그레이션 포함** | **롤백 중단.** DBA 박지은에게 즉시 연락한다. 롤백 명령을 실행하지 않는다. |
| **마이그레이션 없음** | 3단계로 진행한다. |
| **확인 불가** (경로가 불명확하거나 커밋 범위를 알 수 없음) | 포함된 것으로 간주하고 중단한다. DBA에게 확인을 요청한다. |

> 마이그레이션 포함 시 DBA 연락처: **박지은** (DBA) / `<연락 수단 및 번호>`

## 3. 롤백 실행

ArgoCD에서 auto-sync가 켜져 있으면 롤백이 다시 최신 상태로 덮일 수 있다. 롤백 전에 auto-sync 상태를 확인하고, 켜져 있으면 끈다.

```bash
# auto-sync 상태 확인
argocd app get payment-api -o json | jq '.spec.syncPolicy'

# auto-sync가 켜져 있으면 일시 중지 (롤백 후 반드시 복구)
argocd app set payment-api --sync-policy none

# 롤백 실행
argocd app rollback payment-api <REVISION>

# 상태 확인 (Synced / Healthy 여부)
argocd app wait payment-api --health --timeout 300
argocd app get payment-api
```

- [ ] 롤백 명령이 성공했고 앱 상태가 Healthy인지 확인한다.
- [ ] 롤백 대상 리비전과 현재 이미지 태그가 일치하는지 확인한다.

## 4. 롤백 후 검증

### 4-1. 헬스 체크

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://<PAYMENT_API_HOST>/healthz
```

- [ ] 응답 코드가 **200**인지 확인한다. 200이 아니면 아래 "문제 발생 시"를 따른다.

### 4-2. 결제 테스트 주문

- [ ] 결제 테스트 주문을 **1건** 진행하고 **성공**하는지 확인한다.
  - 테스트 계정과 테스트 결제 수단(샌드박스)을 사용한다. 실제 결제가 발생하지 않도록 주의한다.
  - 주문 상태가 성공으로 기록되고 결제 완료 응답을 받는지 확인한다.
- [ ] 테스트 주문 ID를 기록한다: `<TEST_ORDER_ID>`

### 4-3. auto-sync 복구

검증이 끝나면 3단계에서 끈 auto-sync를 원래 설정으로 되돌린다.

```bash
argocd app set payment-api --sync-policy automated
```

> 복구 시 ArgoCD가 Git의 최신 상태로 다시 sync하면서 롤백한 버전이 되돌아갈 수 있다. 롤백 상태를 유지해야 하면 Git 측 조치(예: 원인 수정 커밋 또는 revert)가 끝날 때까지 auto-sync를 끈 상태로 둔다. 이 판단은 담당자와 확인한다.

## 5. 문제 발생 시

| 상황 | 조치 |
|---|---|
| `/healthz`가 200이 아님 | 롤백을 되돌리는 것을 검토하고 담당자에게 즉시 보고한다. 로그(`argocd app logs payment-api`)를 확인한다. |
| 테스트 주문 실패 | 즉시 보고하고 원인을 확인한다. 결제 장애가 계속되면 상위 담당자와 함께 판단한다. |
| 롤백 중 마이그레이션 관련 오류 발생 | 즉시 중단하고 DBA 박지은에게 연락한다. |

## 6. #deploy 채널 이력 기록

롤백이 끝나면 #deploy 채널에 아래 양식으로 남긴다.

```
[롤백 완료] payment-api
- 시각: <YYYY-MM-DD HH:MM KST>
- 작업자: <이름>
- 롤백 전 리비전: <CURRENT_REVISION> (<CURRENT_SHA>)
- 롤백 후 리비전: <REVISION> (<TARGET_SHA>)
- 사유: <장애 내용 또는 롤백 사유>
- 마이그레이션 포함 여부: 없음 (확인 방법: <커밋 범위 / 확인 결과>)
- 헬스 체크: /healthz 200 OK
- 결제 테스트 주문: 성공 (주문 ID: <TEST_ORDER_ID>)
- auto-sync: 복구 완료 / 유지(사유: ...)
- 후속 조치: <원인 분석, 수정 배포 계획 등>
```

마이그레이션이 포함되어 롤백을 중단한 경우에도 #deploy에 중단 사실과 DBA 연락 여부를 같은 방식으로 남긴다.
