CI 빌드 실패의 원인으로 가장 유력한 것은 `@company/ui` 2.0.0에 추가된 `exports` 필드(패키지가 외부에 공개하는 import 경로를 정한 설정)이다. 2.0.0의 `exports`에 `./button` 경로가 없다면 `@company/ui/button` import가 거부되어 이 오류가 난다. 다만 아직 실행으로 검증하지 않았으므로 아래 확인 절차로 확정해야 한다.

확인된 사실은 다음과 같다.

- 3일 전 `@company/ui`가 1.4.0에서 2.0.0으로 올라갔다.
- 2.0.0에 `exports` 필드가 추가되었다.
- CI는 Node 18을, 로컬은 Node 20을 사용한다.
- CI 캐시 키는 `package-lock.json`(의존성 버전을 고정한 파일)의 해시이다.
- 로컬 `node_modules`(설치된 패키지가 담긴 폴더)는 3일 전보다 먼저 설치되었다.

추론은 다음과 같다. 로컬 `node_modules`는 3일 전에 설치되었으므로 1.4.0을 그대로 쓰고 있을 가능성이 높다. 1.4.0에는 `exports`가 없어 하위 경로 import가 성공한다. CI는 lock 파일이 바뀌어 캐시 키가 달라졌으므로 패키지를 새로 설치하면서 2.0.0을 받았을 것으로 보인다. 확인 필요: CI가 실제로 2.0.0을 설치했는지는 로그로 확인해야 한다.

Node 버전 차이는 원인일 가능성이 낮다. Node 18과 20은 모두 `exports` 필드를 지원하기 때문이다. 다만 이 역시 추론이며, Node 18에서 재현해 보기 전까지는 배제할 수 없다.

| 구분 | 로컬 | CI |
|---|---|---|
| 패키지 설치 방식 | 3일 전에 설치한 node_modules 재사용 | lock 파일 변경으로 새로 설치(추론) |
| `@company/ui` 버전 | 1.4.0(추론) | 2.0.0(추론) |
| Node 버전 | 20 | 18 |
| 빌드 결과 | 성공 | 실패 |

확인 절차는 다음과 같다.

1. 로컬에서 `npm ls @company/ui`를 실행하여 설치된 버전을 확인한다.
2. CI 로그의 설치 단계에서 `@company/ui` 버전이 2.0.0인지 확인한다.
3. `node_modules/@company/ui/package.json`의 `exports` 항목에 `./button` 경로가 있는지 확인한다.
4. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드하여 실패가 재현되는지 확인한다.
5. Node 18 환경에서 같은 빌드를 실행하여 Node 버전의 영향을 확인한다.

해결 방법은 세 가지로 나눌 수 있다.

| 방법 | 내용 | 장단점 |
|---|---|---|
| import 경로 수정 | `@company/ui` 루트에서 필요한 항목을 가져오도록 호출부를 바꾼다. | 패키지 변경 없이 즉시 해결된다. 호출부가 많으면 수정 범위가 넓다. |
| 패키지 측 `exports` 보완 | `@company/ui` 담당자가 2.0.0에 `./button` 경로를 추가하고 새 버전을 배포한다. | 근본 해결이다. 배포 절차가 필요하다. |
| 1.4.0 고정 | `@company/ui` 버전을 1.4.0으로 되돌린다. | 임시 조치로 빠르다. 2.0.0의 변경 사항을 쓸 수 없다. |

이 분석은 저장소의 코드를 열어 보거나 명령을 실행하지 않고 제공된 정보만으로 작성되었다. 따라서 위 추론과 확인 절차의 결과로 원인을 확정해야 한다.
