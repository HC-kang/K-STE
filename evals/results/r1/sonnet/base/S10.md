# CI 빌드 실패 원인 분석: `Cannot find module '@company/ui/button'`

## 한 줄 요약
`@company/ui` 2.0.0에서 추가된 `exports` 필드 때문에 `@company/ui/button` 같은 **deep import 경로가 더 이상 허용되지 않는데**, 로컬은 예전(1.4.0) `node_modules`가 남아 있어 문제가 가려졌고, CI는 2.0.0을 새로 설치해서 실패가 드러난 것으로 보인다.

## 가장 유력한 원인

**1. `exports` 필드가 deep import를 막는다**
- `exports`가 없으면 `@company/ui/button`처럼 패키지 내부 파일 경로를 직접 import할 수 있다.
- `exports`가 생기면 **명시적으로 노출된 경로만** import 가능하다. 목록에 `./button`이 없거나 경로 매핑이 다르면 `Cannot find module`이 발생한다.
- 2.0.0은 메이저 버전 업이므로, 이 변경은 의도된 breaking change일 가능성이 높다.

**2. 로컬은 사실상 1.4.0으로 빌드되고 있을 가능성이 높다**
- 로컬 `node_modules`는 업그레이드 3일 전에 설치된 것이다. `package.json`/lock은 2.0.0이지만 **실제 설치된 패키지는 1.4.0일 수 있다.**
- 그래서 로컬 빌드는 "성공"하지만, 실제로는 업그레이드를 검증하지 못한 상태다.

**3. CI는 lock 기준으로 깨끗하게 2.0.0을 설치한다**
- `package-lock.json`이 바뀌었으므로 캐시 키도 바뀌고, CI는 2.0.0을 새로 받는다. 그래서 CI에서만 실패한다.

## 부차적 요인 (확인 필요)

| 요인 | 영향 | 비고 |
|---|---|---|
| Node 18 vs 20 | 낮음~중간 | 두 버전 모두 `exports`를 지원하므로 주원인은 아니다. 다만 `exports` 조건(conditions) 해석이나 번들러/TS의 `moduleResolution` 설정에 따라 차이가 날 수 있다. |
| `moduleResolution` 설정 | 중간 | TS가 `node`(구형)이면 `exports`를 무시하고, `bundler`/`node16`이면 적용한다. 빌드 단계마다 해석이 다를 수 있다. |
| 캐시 | 낮음 | 캐시 키가 lock 해시라 stale cache 가능성은 낮다. 단, 키에 Node 버전이 없으므로 Node 버전을 바꿀 때는 주의해야 한다. |

## 확인 방법 (순서대로)

```bash
# 1. 로컬에 실제로 설치된 버전 확인 (가장 먼저)
npm ls @company/ui
cat node_modules/@company/ui/package.json | grep '"version"'

# 2. 2.0.0의 exports 목록 확인
cat node_modules/@company/ui/package.json | jq .exports

# 3. 로컬을 CI와 동일하게 재현
rm -rf node_modules .next
npm ci
npm run build
```

3번에서 로컬도 같은 에러가 나면 원인이 확정된다. Node 18로도 확인하려면 `nvm use 18`을 사용한다.

## 해결 방안

| 선택지 | 내용 | 적합한 경우 |
|---|---|---|
| **A. import 경로 수정** | `exports`에 노출된 공식 경로로 바꾼다 (예: `@company/ui`의 named export, 또는 문서화된 서브패스). | 권장. 2.0.0 마이그레이션 가이드를 따르는 정석 방법 |
| **B. 패키지에 서브패스 추가 요청** | `@company/ui` 담당 팀에 `./button` export 추가를 요청한다. | 해당 경로가 의도치 않게 누락됐다면 |
| **C. 1.4.0으로 롤백** | 임시 조치로 버전을 되돌린다. | 급히 CI를 복구해야 할 때 |

## 재발 방지
- 의존성 변경 후에는 **`npm ci`로 클린 설치한 뒤 빌드**하는 습관을 들인다.
- 로컬 Node 버전을 CI와 맞춘다 (`.nvmrc` 또는 `engines` 필드).
- 메이저 버전 업그레이드 시 changelog의 breaking changes를 PR 설명에 확인한다.

## PM 참고 사항
- **영향:** 배포 파이프라인 차단. 앱 코드 버그가 아니라 의존성 업그레이드에 따른 호환성 문제다.
- **예상 작업량:** import 경로 수정이면 보통 소규모 (해당 import 위치 수에 비례).
- **위험도:** 낮음. 원인이 명확하고 롤백 경로도 있다.
