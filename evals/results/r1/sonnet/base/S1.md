**한 줄 요약**
지금은 서버 4대가 각자 "메모장"을 따로 갖고 있어서 서로 내용이 다를 수 있는데, Redis를 도입하면 4대가 "공용 메모장" 하나를 같이 보게 됩니다.

**로컬 캐시 vs Redis 캐시**

| | 로컬 캐시 (현재) | Redis 캐시 (도입 예정) |
|---|---|---|
| 비유 | 직원마다 각자 책상 위 메모장 | 사무실 중앙 공용 화이트보드 |
| 위치 | 각 서버 내부 | 별도의 캐시 서버 1대 |
| 내용 | 서버마다 따로 저장 (서로 다를 수 있음) | 서버 4대가 같은 내용을 봄 |
| 속도 | 매우 빠름 | 아주 빠름 (로컬보다 약간 느림) |

**지금 겪는 문제**
- 서버 4대가 각자 상품 목록을 5분간 따로 기억합니다.
- 가격을 바꿔도 서버마다 갱신 시점이 달라서, 고객에게 최대 5분까지 이전 가격이 보일 수 있습니다.
- 같은 고객이 새로고침할 때 서버가 바뀌면 가격이 달라 보이는 일도 생길 수 있습니다.

**Redis 도입 후 좋아지는 점**
1. **가격 변경이 바로 반영됩니다.** 공용 캐시를 한 번만 갱신하면 4대 모두 즉시 새 가격을 보여줍니다. (최대 5분 지연 → 거의 즉시)
2. **서버마다 값이 다른 문제가 사라집니다.** 어느 서버를 거쳐도 고객은 같은 가격을 봅니다.
3. **데이터베이스 부담이 줄어듭니다.** 지금은 서버 4대가 각자 데이터를 따로 불러오지만, 공용 캐시는 한 번만 불러오면 모두가 같이 씁니다.

**알아두실 점**
- 캐시 서버를 새로 운영해야 하므로 비용과 관리 포인트가 하나 늘어납니다.
- 캐시 서버가 1대라서, 이 서버에 문제가 생기면 일시적으로 응답이 느려지거나 데이터베이스 부하가 커질 수 있습니다. 장애 대비(예: 이중화)는 별도로 검토가 필요합니다.
- 서버 내부 메모리보다는 아주 조금 느리지만, 고객이 체감할 수준은 아닙니다.

**정리**
이번 도입의 가장 큰 효과는 "가격을 바꿨는데 고객에게는 이전 가격이 보이는 문제"를 해결하는 것입니다.
