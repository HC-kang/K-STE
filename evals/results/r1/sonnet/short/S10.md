로컬 빌드가 성공하는 이유는 로컬이 아직 `@company/ui` 1.4.0을 쓰기 때문이고, CI 실패의 원인은 2.0.0의 `exports` 필드가 `@company/ui/button` 경로를 열어 두지 않은 것으로 추정합니다.

## 확인된 사실

- CI는 `package-lock.json`의 해시로 캐시를 만듭니다. 3일 전 업그레이드로 lock 파일이 바뀌었으므로 CI는 캐시를 쓰지 않고 2.0.0을 새로 설치합니다.
- 로컬 `node_modules`는 업그레이드 전에 설치한 것입니다. 로컬은 1.4.0으로 빌드하므로 2.0.0의 변경을 겪지 않습니다.
- 2.0.0은 `exports` 필드를 추가했습니다. `exports`는 패키지가 외부에 공개할 import 경로를 직접 지정하는 필드입니다. 이 필드가 있으면 목록에 없는 경로는 파일이 실제로 있어도 import할 수 없습니다.

## 추론

2.0.0의 `exports`에 `./button`이 없거나 이름이 바뀌었다면, `@company/ui/button`을 import하는 코드는 `Cannot find module` 오류로 실패합니다. 오류가 CI에서만 보이는 현상과 시점(3일 전 업그레이드)이 모두 이 설명과 맞습니다.

Node 18과 Node 20은 둘 다 `exports`를 지원합니다. 따라서 Node 버전 차이는 주된 원인일 가능성이 낮습니다.

## 확인 필요

- 2.0.0 패키지의 `exports`에 `./button`이 실제로 있는지 확인하지 않았습니다.
- 경로가 바뀌었다면 새 경로가 무엇인지 확인하지 않았습니다.

## 확인 방법

1. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드한다. CI와 같은 오류가 나면 원인이 확정된다.
2. `node_modules/@company/ui/package.json`의 `exports` 항목에서 `./button`을 찾는다.
3. 2.0.0 릴리스 노트에서 import 경로 변경이나 breaking change(하위 호환이 깨지는 변경) 항목을 확인한다.

## 조치 방향

`exports`에서 확인한 새 경로로 import를 수정합니다. 새 경로가 없으면 `@company/ui` 담당 팀에 `./button` 공개를 요청합니다. 임시로는 `@company/ui`를 1.4.0으로 고정할 수 있습니다.

Node 버전을 맞추는 것은 별개의 정리 작업으로, 이번 오류의 해결책은 아닙니다.
