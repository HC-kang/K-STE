로컬 빌드가 성공하는 이유는 로컬에 `@company/ui` 2.0.0이 설치돼 있지 않기 때문으로 보입니다. 로컬 `node_modules`가 3일 전 설치본이라 1.4.0이 들어 있을 가능성이 높습니다. CI 실패의 유력한 원인은 2.0.0의 `exports` 필드가 `@company/ui/button` 경로를 허용하지 않는 것입니다. 다만 이 두 가지는 아직 확인하지 않은 추론입니다.

확인된 사실은 다음과 같습니다.

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드가 새로 추가됐습니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치했습니다.

`exports` 필드가 있으면 Node와 번들러는 그 필드에 적힌 경로만 허용합니다. 1.4.0에는 `exports`가 없어서 `@company/ui/button`이 파일 경로로 그대로 열렸습니다. 2.0.0의 `exports`에 `./button` 항목이 없거나 다른 경로로 연결돼 있으면 CI에서 이 import가 실패합니다. 이 설명은 추론입니다. 2.0.0 패키지의 `package.json`을 열어 보기 전까지는 확인되지 않습니다.

**오류 문구가 `exports` 원인과 맞지 않을 수 있습니다.** `Cannot find module`은 Node의 CommonJS 해석 실패 문구입니다. `exports`에 경로가 없을 때 Node는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`를, webpack은 "is not exported" 계열 문구를 냅니다. 확인 필요: CI 로그 전체 스택 트레이스와 CI에서 실제 설치된 `@company/ui` 버전.

가설별로 정리하면 다음과 같습니다.

| 가설 | 근거 | 상태 | 확인 방법 |
|---|---|---|---|
| 로컬은 1.4.0을 쓰고 CI는 2.0.0을 쓴다 | 로컬 `node_modules`가 3일 전 설치본이다 | 추론 | 로컬에서 `npm ls @company/ui` 실행 |
| 2.0.0 `exports`에 `./button` 경로가 없다 | 1.4.0은 깊은 경로를 허용했고 2.0.0은 `exports`로 제한한다 | 추론 | 2.0.0 `package.json`의 `exports` 확인 |
| CI가 오래된 `node_modules`를 복원한다 | 캐시 키는 lock 해시지만 복원 키(restore-keys) 설정은 모른다 | 확인 필요 | CI 캐시 설정과 설치 로그 확인 |
| Node 18과 20 차이 때문이다 | 두 버전 모두 `exports`를 지원한다 | 낮은 가능성 | Node 18로 로컬 빌드를 재현 |

권장하는 확인 순서는 다음과 같습니다.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다.
2. 로컬 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드합니다. 여기서 실패하면 로컬에서도 재현된 것이므로 원인이 CI 환경이 아니라 패키지 변경입니다.
3. 2.0.0 패키지의 `package.json`에서 `exports`에 `./button` 또는 그에 해당하는 항목이 있는지 확인합니다.
4. CI 로그에서 설치 단계의 버전과 전체 스택 트레이스를 확인합니다.
5. 로컬을 Node 18로 바꿔 빌드하면 Node 버전 차이를 배제할 수 있습니다.

수정 방향은 세 가지입니다. 2.0.0 문서에 적힌 경로로 import를 바꾸는 방법을 권장합니다. `@company/ui` 담당자에게 `exports`에 `./button`을 추가해 달라고 요청하는 방법도 있습니다. 1.4.0으로 임시 고정하는 방법은 빠르지만 나중에 다시 올려야 하므로 권장하지 않습니다.

**로컬 빌드가 성공했다는 사실만으로 CI 실패 원인을 배제하면 안 됩니다.** 로컬이 실제로 2.0.0을 쓰는지 먼저 확인해야 합니다.
