CI에서만 빌드가 실패하는 가장 유력한 원인은 CI가 `@company/ui` 2.0.0을 설치하는데, 2.0.0의 `exports` 필드가 `@company/ui/button` 경로를 공개하지 않거나 다른 경로로 바꿨기 때문으로 보입니다. 로컬은 3일 전에 설치한 1.4.0을 그대로 쓰고 있을 가능성이 높아서 빌드가 성공하는 것으로 보입니다. 이는 주어진 사실에 근거한 추론이며, 아직 로그나 패키지 파일로 검증하지 않았습니다.

## 확인된 사실

- `@company/ui`를 1.4.0에서 2.0.0으로 3일 전에 올렸습니다.
- 2.0.0에는 `exports` 필드(패키지 바깥에서 가져올 수 있는 파일 경로를 정한 목록)가 추가됐습니다.
- CI는 Node.js 18을, 로컬은 Node.js 20을 씁니다.
- CI 캐시 키는 `package-lock.json`(설치할 패키지 버전을 기록한 파일)의 해시입니다. 해시는 파일 내용으로 계산한 고유 값입니다.
- 로컬 `node_modules`(설치된 패키지가 담긴 폴더)는 3일 전보다 먼저 설치됐습니다.
- 오류 메시지는 `Error: Cannot find module '@company/ui/button'`입니다.

## 추론

로컬 `node_modules`가 업데이트 이전에 설치됐다면 로컬에는 1.4.0이 남아 있을 가능성이 높습니다. 1.4.0에는 `exports` 필드가 없으므로 `@company/ui/button` 같은 경로가 파일 위치대로 찾아집니다. 그래서 로컬 빌드는 2.0.0을 한 번도 쓰지 않은 상태로 성공합니다.

2.0.0 설치 후 `package-lock.json`이 바뀌었다면 캐시 키도 바뀌어 CI는 새로 설치합니다. 그러면 CI는 2.0.0을 받고, 새 `exports` 필드의 제한이 적용됩니다.

Node.js 18과 20의 차이는 이 오류의 직접 원인으로 보기는 어렵습니다. 다만 배제하지는 못했습니다. 일반적으로 `Cannot find module`은 Node.js가 내는 메시지 형식이고, Next.js 빌드 과정에서는 다른 도구의 메시지 형식이 나올 수 있습니다. 어느 도구가 이 오류를 냈는지는 CI 로그의 전체 스택 트레이스(오류가 발생한 호출 경로 기록)로 확인해야 합니다.

## 미검증 항목

- CI 로그의 전체 스택 트레이스와 오류를 낸 도구
- 로컬에서 실제 설치된 `@company/ui` 버전
- 2.0.0 `exports` 필드에 `./button`이 있는지 여부
- 커밋된 `package-lock.json`에 2.0.0이 반영됐는지 여부
- CI 캐시 설정에 `restore-keys`(키가 맞지 않을 때 이전 캐시를 복원하는 설정)가 있는지 여부

## 검증 순서

1. 로컬에서 `rm -rf node_modules && npm ci`로 새로 설치하고, `npm ls @company/ui`로 버전을 봅니다. 로컬도 2.0.0으로 실패하면 추론이 맞는 것입니다.
2. 같은 설치 상태에서 Node.js 18로 빌드해 봅니다. 이 결과로 Node.js 버전의 영향을 나눠서 볼 수 있습니다.
3. 2.0.0 패키지의 `package.json`에서 `exports` 항목을 찾아 `./button` 경로가 있는지 비교합니다.

## 해결 방향 (검증 후 결정)

검증으로 원인이 확인되면 두 가지 방법을 고려할 수 있습니다. 첫째, 2.0.0 문서에 맞게 import 경로를 고치는 방법입니다. 둘째, 당장 빌드를 살리려면 `@company/ui`를 1.4.0으로 고정하는 방법입니다. 검증 전에는 코드를 고치지 않는 것을 권장합니다.

## PM 요약

3일 전 라이브러리의 주요 버전(major version) 업데이트 이후 CI에서만 import 경로 오류가 났습니다. 로컬은 업데이트 전에 설치된 버전을 써서 재현되지 않았습니다. 원인은 위 검증 순서를 마친 뒤에 확정할 수 있습니다.
