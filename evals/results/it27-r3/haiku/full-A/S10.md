가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드가 `@company/ui/button` 경로를 공개하지 않는 것으로 보입니다. 로컬에서는 3일 전 이전에 설치된 1.4.0이 그대로 쓰여 빌드가 성공했을 가능성이 큽니다. 다만 아래 가설들을 아직 검증하지 않았으므로 원인을 확정할 수는 없습니다.

`exports` 필드는 패키지 외부에 공개할 파일 경로를 정하는 설정입니다. 1.4.0에는 이 설정이 없어서 파일 경로로 직접 찾을 수 있었지만, 2.0.0부터는 `exports`에 적힌 경로만 import할 수 있습니다.

| 가설 | 근거 | 확인 방법 |
|---|---|---|
| 2.0.0의 `exports`에 `./button` 경로가 없다 | 2.0.0에서 `exports`가 추가되었고, 에러가 `@company/ui/button` 경로에서 발생했다 | 2.0.0 패키지의 package.json에서 `exports` 항목을 확인한다 |
| 로컬 `node_modules`에 1.4.0이 남아 있다 | 로컬 설치가 3일 전보다 먼저라 버전 변경이 반영되지 않았을 수 있다 | 로컬에서 `npm ls @company/ui`를 실행한다 |
| CI가 2.0.0을 설치한다 | CI 캐시 키가 `package-lock.json` 해시라 lock 파일이 바뀌면 새로 설치된다 | CI 로그에서 `npm ls @company/ui` 결과를 확인한다 |
| Node 18과 Node 20의 차이 | 두 버전 모두 `exports`를 지원하므로 가능성이 낮다 | 로컬을 Node 18로 바꿔 빌드한다 |

확인 필요: 에러가 발생한 단계. `Cannot find module`은 Node가 모듈을 찾지 못할 때 내는 메시지 형식입니다. Next.js 빌드 과정의 번들러 단계에서 나는 에러는 보통 `Module not found`로 표시됩니다. 에러가 Next.js 빌드 중에 나는지, 설정 파일이나 스크립트를 Node가 직접 실행하면서 나는지에 따라 원인 해석이 달라지므로 CI 전체 로그에서 발생 위치를 확인해야 합니다.

PM에게 공유할 요약은 다음과 같습니다. 3일 전 UI 라이브러리 버전을 올리면서 새 버전이 파일 경로 규칙을 바꾼 것으로 추정됩니다. CI는 새 버전을 설치하고 로컬은 옛 버전을 쓰고 있어서 빌드 결과가 갈린 것으로 보입니다.

개발자는 다음 순서로 확인하십시오.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인하십시오.
2. 2.0.0 패키지의 `exports` 항목에 `./button`이 있는지 확인하십시오.
3. `./button`이 있으면 import 경로를 `exports`에 맞게 고치십시오. 없으면 `@company/ui` 담당 팀에 `exports` 추가를 요청하거나 1.4.0 고정을 검토하십시오.
4. 로컬 `node_modules`를 삭제한 뒤 `npm ci`로 다시 설치하고 빌드해서 CI와 같은 조건으로 재현되는지 확인하십시오.
