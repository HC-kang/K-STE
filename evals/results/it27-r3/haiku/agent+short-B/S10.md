현재 가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드가 `button` 하위 경로를 다르게 정의했기 때문이다. 다만 로컬 `node_modules`에 설치된 실제 버전을 확인하지 않았으므로 이 원인은 아직 확정되지 않았다.

## 확인된 사실

- CI 빌드는 `@company/ui/button` import에서 실패한다.
- 로컬 빌드는 성공한다.
- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에 `exports` 필드가 추가되었다.
- CI는 Node 18을, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`의 해시다.
- 로컬 `node_modules`는 업그레이드 3일 전보다 먼저 설치되었다.

## 원인 추론

`exports` 필드가 있으면 Node와 번들러는 `exports`에 정의된 경로만 허용한다. 2.0.0의 `exports`에 `./button`이 없거나 다른 경로(예: `./components/button`)로 정의되어 있으면 `@company/ui/button` import가 실패한다. 1.4.0에는 `exports`가 없었으므로 파일 경로로 직접 해석되어 같은 import가 통과했다.

로컬 빌드가 성공하는 이유는 로컬 `node_modules`에 1.4.0이 남아 있기 때문일 가능성이 높다. 이 경우 로컬 빌드는 2.0.0을 검증하지 않은 것이다. 로컬에서 `npm install`로 lockfile을 갱신하지 않았다면 이 가능성은 더 높아진다.

에러 메시지 형식도 원인 범위를 좁히는 단서다. `Cannot find module`은 Node가 해석한 파일이 실제로 없을 때 주로 나오는 형식이다. `exports`에 경로가 없을 때 Node는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`를 낸다. Next.js의 웹팩은 `Module not found: Can't resolve`를 낸다. 따라서 어느 도구가 에러를 냈는지 전체 로그로 확인해야 한다.

Node 18과 20의 차이가 원인일 가능성은 상대적으로 낮다. 두 버전 모두 `exports`를 지원하기 때문이다. 다만 2.0.0이 ESM 전용 패키지라면 CJS 경로로 `require`할 때 Node 18에서 실패할 수 있다. npm 버전도 두 환경에서 다를 수 있으므로 함께 확인한다.

CI 캐시는 lockfile 해시를 키로 쓰므로 lockfile이 2.0.0으로 갱신되었다면 캐시 미스가 나고 새로 설치된다. 캐시가 `restore-keys`로 이전 캐시를 복원했다면 1.4.0 파일이 쓰일 수 있다.

## 가설별 확인 방법

| 가설 | 근거 | 확인 방법 | 가능성 |
|---|---|---|---|
| 2.0.0 `exports`에 `./button` 경로가 없거나 다름 | 2.0.0에서 `exports`가 추가되었다 | 2.0.0의 `package.json`에서 `exports` 원문 확인 | 높음 |
| 로컬은 1.4.0을 사용 중 | 로컬 `node_modules`가 업그레이드 전에 설치되었다 | 로컬에서 `npm ls @company/ui` 실행 | 높음 |
| `exports`가 가리키는 파일이 패키지에 없음 | 메시지가 `Cannot find module` 형식이다 | 설치된 패키지에서 `exports` 대상 파일 존재 여부 확인 | 중간 |
| 대소문자 불일치 | macOS는 대소문자를 구분하지 않고 CI의 Linux는 구분한다 | import 경로와 실제 파일명 비교 | 중간 |
| 2.0.0이 ESM 전용이라 Node 18에서 `require` 실패 | Node 18과 20의 차이, 2.0.0의 모듈 형식 | 2.0.0의 `type` 필드와 `exports`의 `import`/`require` 조건 확인 | 낮음에서 중간 |
| 캐시에서 이전 `node_modules` 복원 | 캐시 키가 lockfile 해시이고 복원 키가 있을 수 있다 | CI 로그에서 cache hit 여부와 매칭된 키 확인 | 낮음 |

## 권장 조치

1. 로컬에서 `npm ls @company/ui`를 실행하여 실제 설치 버전을 확인한다.
2. CI 로그 전체에서 에러를 낸 도구와 해석 경로를 확인한다.
3. 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치한 뒤 Node 18로 빌드하여 실패를 재현한다.
4. 재현되면 2.0.0의 `exports`와 import 경로를 비교한다. 패키지 쪽 수정이 필요하면 `@company/ui` 담당자와 협의한다.
5. import 경로를 맞춘 뒤 CI에서 빌드가 통과하는지 확인한다.

## 확인 필요

- CI 로그 전체에서 에러를 낸 도구가 무엇인지
- 2.0.0의 `package.json`에 있는 `exports` 원문
- 로컬 `node_modules`에 설치된 `@company/ui`의 실제 버전
- 2.0.0이 ESM 전용인지 여부
- CI 캐시 복원 로그에서 cache hit 여부와 매칭된 키

이 분석은 제공된 사실에 근거한 추론이다. 저장소와 CI 로그를 직접 확인하지 않았으므로 위 항목을 확인한 뒤 원인을 확정한다.
