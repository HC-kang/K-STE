원인은 CI와 로컬이 서로 다른 버전의 `@company/ui`를 쓰고 있기 때문으로 보입니다. 아래 내용 중 사실과 추론은 구분해서 적었고, 추론은 아직 검증하지 않았습니다.

**사실**
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0부터 패키지에 `exports` 필드(패키지가 바깥에 공개하는 import 경로를 제한하는 package.json 설정)가 있습니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치했습니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- CI는 Node 18, 로컬은 Node 20입니다.

**추론**
- 로컬 `node_modules`는 업그레이드 전에 설치했으므로 1.4.0이 들어 있을 가능성이 높습니다. 1.4.0에는 `exports` 필드가 없어서 `@company/ui/button`을 파일 경로로 그대로 읽을 수 있습니다.
- 업그레이드로 `package-lock.json`이 바뀌었으면 캐시 키도 바뀝니다. 그러면 CI는 캐시 없이 2.0.0을 새로 설치합니다.
- `exports` 필드가 있으면 Node는 그 목록에 없는 경로를 불러오지 못하게 막습니다. 2.0.0의 `exports`에 `./button`이 없거나 이름이 다르면 `Cannot find module '@company/ui/button'`이 납니다.
- 따라서 로컬은 2.0.0으로 빌드한 적이 없고, CI가 2.0.0으로 처음 빌드하다 실패했다고 보는 것이 가장 자연스럽습니다.

Node 버전 차이는 원인일 가능성이 낮아 보입니다. 이 추론의 근거는 `exports` 해석 규칙이 Node 18과 20에서 같다는 일반 지식이고, 이 프로젝트에서 직접 실험한 결과는 아닙니다.

**검증 순서**
1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 확인하십시오.
2. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 다시 빌드하십시오. 로컬에서도 같은 에러가 나면 원인은 2.0.0의 `exports`입니다.
3. 2.0.0 패키지의 `package.json`에서 `exports` 목록에 `./button`이 있는지 보십시오.
4. 2.0.0에서 `button`의 공개 경로가 바뀌었는지 `@company/ui`의 변경 기록(changelog)을 확인하십시오.

**수정 방향**
검증 결과에 따라 둘 중 하나를 택합니다. 2.0.0이 `button`의 새 import 경로를 공개했다면 앱의 import 경로를 바꿉니다. 경로를 공개하지 않았다면 `@company/ui`의 `exports`에 `./button`을 추가해야 합니다. 어느 쪽인지는 3번과 4번을 확인해야 알 수 있습니다.

확인 필요: `package-lock.json`에 2.0.0이 실제로 기록돼 있는지 확인되지 않았습니다. 1.4.0으로 남아 있다면 위 추론이 맞지 않으므로 CI 설치 로그에서 `@company/ui` 버전을 먼저 보십시오.
