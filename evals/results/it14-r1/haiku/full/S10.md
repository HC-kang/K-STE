**가장 가능성이 높은 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다.** CI는 `package-lock.json`에 따라 2.0.0을 새로 설치하고, 로컬은 3일 전 설치본(1.4.0일 가능성이 큼)을 그대로 쓰고 있을 가능성이 높습니다. 다만 오류 문구와 Node 버전 차이는 아직 설명이 부족하므로 아래 확인이 필요합니다.

**확인된 사실**

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드가 추가되었습니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.

**추론**

- `exports` 필드는 패키지가 외부에 공개하는 경로의 목록입니다. 이 필드가 있으면 목록에 없는 하위 경로(예: `@company/ui/button`)를 가져올 수 없습니다. 1.4.0에는 이 필드가 없어서 같은 경로가 파일 경로로 그대로 해석되었을 것으로 보입니다.
- 로컬에 1.4.0이 남아 있다면 로컬 빌드가 성공하는 것은 설명됩니다. 로컬은 2.0.0 해석을 한 번도 거치지 않았기 때문입니다.
- CI 캐시 키가 lock 파일 해시이므로, lock 파일이 바뀐 뒤 CI는 새로 설치했을 가능성이 높습니다. 캐시가 원인이라는 근거는 없습니다.
- Node 18과 20은 모두 `exports` 필드를 지원합니다. 따라서 Node 버전 차이만으로는 설명되지 않습니다.

**미확인**

- 로컬에 실제로 설치된 `@company/ui` 버전은 확인하지 않았습니다.
- 2.0.0의 `exports` 목록에 `./button`이 있는지는 확인하지 않았습니다.
- 오류 문구 `Cannot find module`은 Node의 `require` 해석 실패 문구에 가깝습니다. `exports`가 경로를 막을 때 Node가 내는 문구와는 다릅니다. 따라서 오류가 Next.js 빌드, 설정 파일, 테스트 중 어디서 나는지 전체 로그로 확인해야 합니다.
- CI가 실제로 설치한 버전과 lock 파일에 기록된 버전도 확인하지 않았습니다.

다음 순서로 확인하십시오.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인하십시오.
2. 2.0.0의 `node_modules/@company/ui/package.json`에서 `exports` 필드에 `./button`이 있는지 확인하십시오.
3. CI 로그에서 오류가 발생한 단계와 설치된 버전을 확인하십시오.
4. 로컬에서 `rm -rf node_modules && npm ci`로 새로 설치한 뒤 Node 18과 Node 20으로 각각 빌드해 재현되는지 확인하십시오.
