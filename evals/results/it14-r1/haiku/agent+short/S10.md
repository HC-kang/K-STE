가장 가능성이 높은 원인은 2.0.0에 새로 추가된 `exports` 필드가 `@company/ui/button` 같은 하위 경로 import를 막는 것으로 보입니다. 로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 3일 전 설치본이라 1.4.0이 그대로 남아 있기 때문으로 보입니다. 이 내용은 전달해 주신 정보에 따른 추론이며, 패키지 코드나 빌드를 직접 확인하지는 않았습니다.

## 확인된 사실

- 3일 전 `@company/ui`가 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0에는 `exports` 필드가 추가되었습니다.
- CI에서 `Cannot find module '@company/ui/button'` 에러가 발생하고, 로컬에서는 빌드가 성공합니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

## 원인 추론

`exports` 필드가 있으면 Node와 번들러는 그 필드에 적힌 경로만 외부에 공개합니다. 1.4.0에 `exports`가 없었다면 `@company/ui/button`은 패키지 안의 파일 경로로 바로 찾아졌을 것입니다. 2.0.0의 `exports`에 `./button`이나 이를 포함하는 패턴(`./*`)이 없다면 같은 import가 실패하고, 이는 에러 메시지와 맞아떨어집니다.

## 로컬에서 성공하는 이유

로컬 `node_modules`가 1.4.0 상태로 남아 있으면 로컬 빌드는 2.0.0이 아닌 1.4.0으로 빌드됩니다. CI는 lock 파일 기준으로 2.0.0을 새로 설치하므로 두 환경의 결과가 달라집니다.

**로컬 빌드 성공을 근거로 2.0.0과의 호환성이 정상이라고 판단하면 안 됩니다.**

## Node 버전과 캐시 키

Node 18과 Node 20은 모두 `exports` 필드를 지원하므로, 두 버전의 차이가 이 에러의 직접 원인이라고 보기는 어렵습니다. 다만 CI와 로컬의 npm 버전이나 빌드 도구 버전은 다를 수 있으므로 변수로 남겨 둡니다.

캐시 키가 lock 파일 해시이므로 lock이 2.0.0으로 갱신되어 커밋되었다면 CI는 캐시 없이 새로 설치합니다. CI가 실패한다는 사실은 CI가 2.0.0을 설치했다는 뜻으로 보이며, 이는 위 추론과 일치합니다.

## 확인 필요 사항

- 확인 필요: 2.0.0의 `exports`에 `./button` 경로가 있는지 여부입니다. 깨끗이 설치한 뒤 `node_modules/@company/ui/package.json`에서 확인해야 합니다.
- 확인 필요: 에러가 어느 단계에서 발생하는지입니다. `Cannot find module`은 Node의 `require` 에러 형식이며, webpack 기반 Next.js 빌드는 보통 `Module not found`를 출력합니다. 전체 CI 로그에서 어떤 명령이 실패했는지 확인해야 합니다.
- 확인 필요: 2.0.0 업그레이드 변경이 CI가 빌드하는 브랜치에 들어갔는지 여부입니다.

## 다음 단계

1. 로컬에서 `rm -rf node_modules && npm ci`로 lock 기준 재설치하고, `npm ls @company/ui`로 설치된 버전을 확인합니다.
2. Node 18로 `node -e "require.resolve('@company/ui/button')"`을 실행해 같은 에러가 재현되는지 확인합니다.
3. 재현되면 조치 방법을 고릅니다. 앱 쪽에서는 `import { Button } from '@company/ui'`처럼 루트 경로로 바꾸는 방법을 권장합니다.
4. 패키지 쪽에서 `exports`에 `./button`을 추가하는 방법은 라이브러리 담당 팀의 작업이 필요합니다.
5. 당장 배포를 막아야 하면 `@company/ui`를 1.4.0으로 임시로 되돌릴 수 있습니다.
