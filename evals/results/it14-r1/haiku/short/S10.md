가장 가능성이 높은 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드(패키지가 외부에 공개하는 경로 목록)가 `button` 하위 경로 import를 막은 것입니다. 다만 아직 검증하지 않은 추론이므로 아래 순서로 확인해야 합니다.

## 사실과 추론

사실은 다음과 같습니다.

- 3일 전 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에 `exports` 필드가 추가되었습니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키(캐시를 찾는 기준값)는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `node_modules` 설치 시점 | 3일 전 이전 | 실행할 때마다 lock 파일 기준 설치 |
| 빌드 결과 | 성공 | 실패 |

**로컬 빌드 성공은 2.0.0이 정상이라는 증거가 아닙니다.** 로컬 `node_modules`가 3일 전 이전에 설치되었으므로, 로컬은 1.4.0을 쓰고 있을 가능성이 높습니다(추론).

원인에 대한 추론은 다음과 같습니다.

1. 1.4.0에는 `exports`가 없어서 `@company/ui/button`이 패키지 안의 파일 경로로 바로 풀립니다.
2. 2.0.0에는 `exports`가 있어서, 목록에 `./button`이 없으면 이 경로의 import가 차단됩니다.
3. 로컬은 옛 설치본을 쓰므로 이 차단 규칙을 거치지 않고 빌드가 성공합니다.
4. CI는 lock 파일 기준으로 새로 설치하므로 2.0.0을 받고, 차단 규칙에 걸려 실패합니다.

Node 버전 차이는 이 에러의 직접 원인으로 보기 어렵습니다. Node 18도 `exports`를 지원하기 때문입니다. 에러 문구도 확인이 필요합니다. `Cannot find module`은 Node의 CommonJS 해석 오류 문구에 가깝고, Node에서 `exports` 차단은 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`로 표시됩니다. 따라서 실패를 낸 쪽이 Next.js(webpack) 해석기인지 CI 로그에서 확인해야 합니다.

## 검증 순서

1. 로컬에서 `node_modules/@company/ui/package.json`의 `version`을 확인합니다. 1.4.0이면 위 추론과 맞습니다.
2. 2.0.0 패키지의 `package.json`에서 `exports` 항목에 `./button`이 있는지 확인합니다.
3. CI 로그에서 `@company/ui`가 실제로 설치된 버전과 에러를 낸 도구를 확인합니다.
4. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드하여 재현합니다. Node 18로도 같은 과정을 한 번 실행합니다.

## 해결 방향

- `exports`에 공개된 경로로 import 경로를 바꿉니다. 2.0.0 문서나 `exports` 목록을 기준으로 합니다.
- `./button` 경로가 필요하면 `@company/ui` 제공 측에 추가를 요청합니다.
- 당장 CI를 통과시켜야 하면 1.4.0으로 되돌릴 수 있습니다. 이 경우 2.0.0 적용은 미뤄집니다.
