원인은 로컬 빌드가 `@company/ui` 1.4.0으로 돌고 CI 빌드가 2.0.0으로 돌기 때문으로 추정합니다. 2.0.0에 추가된 `exports` 필드(패키지가 외부에 공개하는 파일 경로를 제한하는 설정)에 `./button`이 없거나 경로가 달라서 `@company/ui/button`을 찾지 못하는 것으로 보입니다. 아래 내용은 모두 주어진 정보에서 추론한 것이고, 직접 확인한 항목은 없습니다.

| 항목 | 로컬 | CI |
|---|---|---|
| `@company/ui` 버전 | 1.4.0일 가능성이 높습니다(추정). | 2.0.0일 가능성이 높습니다(추정). |
| Node | 20입니다. | 18입니다. |
| 설치 시점 | 업그레이드 3일 전보다 이전입니다. | 락 파일(`package-lock.json`)이 바뀌어 캐시가 새로 만들어졌을 것으로 봅니다(추정). |

1.4.0에는 `exports`가 없었으므로 패키지 안의 어떤 파일 경로든 불러올 수 있었습니다. 2.0.0부터는 `exports`에 적힌 경로만 불러올 수 있습니다. 로컬 `node_modules`가 업그레이드 전에 설치된 상태라면 로컬 빌드는 1.4.0으로 성공하고, 2.0.0을 설치하는 CI만 실패합니다.

다른 후보 두 가지는 가능성이 낮다고 봅니다.

- **Node 버전 차이:** `exports`는 Node 18과 20이 모두 지원합니다. 그래서 버전 차이가 주원인일 가능성은 낮습니다. 다만 2.0.0의 `exports` 형식이 Node 18에서만 문제되는지는 확인하지 않았습니다.
- **오래된 CI 캐시:** 캐시 키가 락 파일 해시이므로 버전을 올리면 키가 바뀝니다. 그래서 옛 캐시가 재사용됐을 가능성은 낮습니다.

원인을 확정하려면 다음 순서로 확인합니다.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 봅니다.
2. `node_modules/@company/ui/package.json`의 `exports`에 `./button`이 있는지 봅니다.
3. 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치한 뒤 빌드합니다. 같은 에러가 나면 원인이 확정됩니다.
4. 같은 에러가 나지 않으면 로컬에서 Node 18로 빌드해 Node 차이를 확인합니다.

확인 결과 `./button`이 `exports`에 없다면, 2.0.0이 공개하는 새 경로로 import를 바꾸거나 패키지 담당자에게 `./button` 공개 여부를 물어야 합니다. 확인 필요: 2.0.0의 `exports`에 `./button`에 해당하는 경로가 있는지, 그리고 CI 로그에서 실제로 설치된 `@company/ui` 버전이 2.0.0인지 알아야 합니다.
