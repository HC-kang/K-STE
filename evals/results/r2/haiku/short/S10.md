가장 유력한 원인은 CI가 `@company/ui` 2.0.0을 새로 설치하는 반면, 로컬에는 3일 전보다 먼저 설치된 1.4.0이 남아 있다는 점이다. 다만 이는 추론이며, CI 로그와 2.0.0 패키지 내용을 확인하기 전까지 확정하지 않는다.

로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 오래된 1.4.0을 그대로 쓰기 때문으로 추론한다. 1.4.0에는 `exports` 필드(패키지 외부에 공개할 파일 경로를 정하는 설정)가 없어서 `@company/ui/button` 같은 하위 경로 import가 그대로 해석된다. 따라서 `package.json`을 2.0.0으로 올렸더라도 로컬에서는 1.4.0이 계속 쓰여 빌드가 성공한다.

2.0.0에서 `exports` 필드가 추가되었으므로, 이 필드에 `./button`이나 `./*` 같은 경로가 없으면 하위 경로 접근이 제한된다. 다만 에러 메시지가 `Cannot find module`이라는 점은 확인이 필요하다. Node는 `exports`로 막힌 경로에 대해 보통 `Package subpath './button' is not defined by "exports"` 같은 별도 메시지를 낸다. 따라서 `exports` 제한이 아니라 2.0.0에서 `button` 파일이 예상한 위치에 없는 경우일 수도 있다. 빌드에 쓰는 번들러(파일을 묶어 웹 앱을 만드는 도구)와 CI 로그 전문을 함께 확인해야 한다.

CI 캐시 키는 `package-lock.json`(설치할 패키지 버전을 고정하는 파일)의 해시이므로, lockfile이 2.0.0으로 바뀌었다면 키도 바뀌어 캐시가 새로 만들어지는 것이 정상이다. 따라서 오래된 캐시가 1.4.0을 복원했을 가능성은 낮다고 추론한다.

Node 버전 차이는 원인일 가능성이 낮다고 추론한다. Node 18과 20 모두 `exports` 필드를 지원하기 때문이다. 다만 CI에서만 재현되는 이유가 Node 차이 때문인지는 확인되지 않았다.

| 항목 | 로컬 | CI |
|---|---|---|
| `@company/ui` 버전 | 1.4.0으로 추정 (확인 필요) | 2.0.0으로 추정 (확인 필요) |
| Node 버전 | 20 | 18 |
| `node_modules` 출처 | 3일 전보다 먼저 한 설치 | 캐시 복원 또는 새 설치 |
| 빌드 결과 | 성공 | 실패 |

이번 분석은 전달받은 내용만 근거로 하였다. 저장소 코드, CI 로그, 2.0.0 패키지 파일은 확인하지 않았다. 원인을 확정하려면 다음 순서로 확인한다.

1. 로컬에서 `npm ls @company/ui`를 실행하여 실제 설치 버전을 확인한다.
2. CI 로그에서 `@company/ui`가 설치된 버전과 실패 지점의 전체 에러 문구를 확인한다.
3. 2.0.0 패키지의 `package.json`에서 `exports` 필드에 `./button` 또는 `./*`가 있는지 확인한다.
4. 2.0.0 패키지 안에 `button` 파일이 실제로 존재하는 경로를 확인한다.
5. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 빌드하여 로컬에서도 같은 에러가 재현되는지 확인한다.

재현이 확인되면 조치 방향은 세 가지로 검토할 수 있다. 첫째, 2.0.0 패키지 측에 `button` 경로를 `exports`에 추가하도록 요청하거나 공개된 import 경로로 바꾼다. 둘째, 당장은 `@company/ui`를 1.4.0으로 고정하여 빌드를 복구한다. 셋째, 버전 변경 후 `package-lock.json`을 다시 생성하여 로컬과 CI의 설치 결과를 맞춘다.
