# 빌드 실패 원인 분석: CI에서만 `Cannot find module '@company/ui/button'` 발생

## 한 줄 요약

**가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드 추가로 인해 `@company/ui/button` 같은 하위 경로 import가 막힌 것입니다.** 로컬은 3일 전에 설치된 오래된 `node_modules`(1.4.0)를 쓰고 있어서 문제가 드러나지 않습니다. CI는 lockfile 기준으로 새로 설치하므로 2.0.0을 받아 실패합니다.

> 아직 확정은 아닙니다. 아래 "확인 方法"의 명령 2~3개로 검증할 수 있습니다.

---

## 1. 상황 정리

| 구분 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `node_modules` | 3일 전 설치 (1.4.0 추정) | lockfile 기준 새로 설치 (2.0.0 추정) |
| `@company/ui/button` 해석 | 성공 | 실패 |

---

## 2. 원인 가설 (가능성 순)

### 가설 A: 로컬 `node_modules`가 오래되어 업그레이드를 반영하지 못함 (가장 유력)

- 2.0.0 이전 버전(1.4.0)은 `exports` 필드가 없었습니다. 그래서 `@company/ui/button`처럼 파일 경로를 직접 가리키는 import가 제한 없이 동작했습니다.
- 2.0.0에서 `exports` 필드가 추가되면 **명시된 경로만 import할 수 있습니다.** `./button`이 `exports`에 없다면 하위 경로 import는 막힙니다.
- 로컬은 3일 전 `node_modules`를 쓰므로 2.0.0 변경이 적용되지 않았습니다. 그래서 로컬 빌드는 성공합니다.
- CI는 lockfile 해시가 바뀌었으니 캐시가 미스되고, 새로 설치하면서 2.0.0을 받습니다. 그래서 실패합니다.

**즉, 로컬 환경이 실제 의존성 상태를 반영하지 못하고 있습니다.**

### 가설 B: Node 18과 20의 차이 (보조 요인일 가능성)

- `exports` 해석 자체는 Node 18과 20 모두 지원하므로 단독 원인일 가능성은 낮습니다.
- 다만 2.0.0이 **ESM 전용**(또는 `require` 조건 없이 `import` 조건만 제공)이라면, Node 18에서는 `require`로 로드할 때 실패할 수 있습니다. 로컬 Node 20.19 이상은 `require(esm)`를 지원하므로 로컬에서만 통과할 수 있습니다.
- 2.0.0의 `engines` 필드가 Node 20 이상을 요구하는지도 확인해야 합니다.

### 가설 C: 에러 메시지 자체의 해석 차이

- `exports`에 없는 경로를 Node가 직접 해석하면 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`가 나옵니다.
- 지금 메시지는 `Cannot find module`입니다. 이는 Node의 CJS 로더나 Next/webpack 해석 과정에서 나올 수 있는 문구이므로, **전체 스택 트레이스를 확인해서 어느 단계에서 나는지 봐야 합니다.**
- 혹시 CI에서 `node_modules` 자체가 불완전하게 설치되었을 가능성도 함께 확인합니다.

### 가설 D: CI 캐시 복원 방식 (확인 필요)

- 캐시 키가 lockfile 해시라면 정확히 일치할 때만 복원됩니다.
- 하지만 `restore-keys`에 접두사 기반 fallback이 설정되어 있다면, **이전 캐시(1.4.0)가 복원되어 CI도 오히려 통과**할 수도 있습니다. 반대로 특정 상황에서는 캐시와 실제 설치 버전이 어긋날 수 있습니다.
- 이 경우 CI 설정(`actions/cache` 설정, `restore-keys`)을 확인해야 합니다.

## 3. 확인 방법

**로컬에서 (문제 재현):**
```bash
# 현재 로컬에 설치된 버전 확인
npm ls @company/ui

# 2.0.0의 exports 필드 확인 (./button 항목이 있는지)
node -p "JSON.stringify(require('@company/ui/package.json').exports, null, 2)"

# 깨끗한 환경에서 lockfile 기준 재설치 후 빌드 재현
rm -rf node_modules && npm ci && npm run build
```

**CI에서:**
- 설치 직후 `npm ls @company/ui` 출력을 로그에 남겨 실제 설치 버전을 확인합니다.
- `node -v`로 실제 Node 버전을 확인합니다.
- 전체 에러 스택 트레이스를 확인합니다.
- `actions/cache`의 `key`와 `restore-keys` 설정을 확인합니다.

**판정 기준:**
- 깨끗한 설치 후 로컬에서도 같은 에러가 나면 → **가설 A 확정**
- 로컬(Node 18)에서도 재현되면 → 가설 B 추가 확인
- CI 로그에 `@company/ui@1.4.0`이 찍히면 → 캐시 문제(가설 D)

## 4. 해결 옵션

| 옵션 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. import 경로 수정 (권장)** | `@company/ui/button` → `@company/ui` 루트 import로 변경 | 2.0.0 정책과 맞음 | 코드 여러 곳 수정 필요 |
| **B. 패키지 쪽 `exports` 보완** | `"./button"` 항목 추가 (패키지 관리자에게 요청) | 소비자 코드 수정 불필요 | 패키지 릴리스 필요 |
| **C. 임시 롤백** | `@company/ui`를 1.4.0으로 되돌림 | 즉시 복구 | 업그레이드 지연, 임시 조치 |
| **D. 로컬 정상화** | `rm -rf node_modules && npm ci` | 로컬/CI 불일치 해소 | 근본 원인 해결 아님 |

**단기:** C로 빌드를 즉시 복구하고, D로 로컬 환경을 맞춥니다.
**중기:** A 또는 B로 import 방식을 정리합니다.

---

## 5. 재발 방지

- 메이저 버전 업그레이드 PR은 **로컬에서 `rm -rf node_modules && npm ci` 후 빌드 검증**을 필수 절차로 둡니다.
- 로컬과 CI의 Node 버전을 `.nvmrc` 또는 `engines` 필드로 맞춥니다.
- CI에서 설치된 주요 패키지 버전을 로그에 남깁니다.
- 공통 UI 패키지는 메이저 업그레이드 시 **changelog의 breaking change 항목(exports 추가 등)**을 함께 검토합니다.

---

## 6. PM 참고 요약

- **영향:** CI 빌드 실패로 배포 파이프라인이 막혀 있습니다. 로컬 개발은 가능합니다.
- **원인:** 공통 UI 라이브러리 메이저 업그레이드(2.0.0)에서 import 경로 정책이 바뀌었는데, 로컬 환경이 이를 반영하지 못한 상태로 검증이 이루어졌습니다.
- **조치:** 즉시 복구(롤백 또는 설정 수정)와 근본 수정(import 경로 정리)을 나눠 진행합니다.
- **예상 소요:** 원인 확인은 짧게 끝날 수 있고, 근본 수정 범위는 import 사용처 개수에 따라 달라집니다. 사용처 수를 파악하면 일정 추정이 가능합니다.
