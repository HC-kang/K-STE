# CI 빌드 실패 원인 분석

현재 원인은 확정되지 않았다. 가장 먼저 확인할 가설은 로컬 `node_modules`가 3일 전 이전 설치분이라 `@company/ui` 1.4.0을 그대로 쓰고 있을 가능성이다. 이 경우 로컬 빌드 성공은 2.0.0 변경이 문제없다는 증거가 되지 못한다.

## 확인된 사실

- `@company/ui`를 1.4.0에서 2.0.0으로 3일 전에 올렸다.
- 2.0.0 패키지에 `exports` 필드가 추가됐다.
- CI는 Node 18, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`의 해시다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치됐다.
- CI 에러는 `Error: Cannot find module '@company/ui/button'`이다.

## 원인 후보

| 후보 | 근거 | 확인 방법 |
|---|---|---|
| 로컬이 옛 버전(1.4.0)을 사용한다 | 로컬 `node_modules`가 3일 전 이전에 설치됐다. | 로컬에서 `npm ls @company/ui`를 실행한다. 1.4.0이 나오면 로컬 성공은 2.0.0 검증이 아니다. |
| `exports`에 `button` 경로가 없거나 이름이 다르다 | `exports`가 추가되면 정의되지 않은 서브경로는 가져올 수 없다. | 2.0.0 `package.json`의 `exports` 항목을 확인한다. |
| 대소문자 차이 | 로컬 macOS 기본 파일시스템은 대소문자를 구분하지 않고, CI 리눅스는 구분한다. | 소스의 import 문자열과 패키지 실제 파일명(`Button` 또는 `button`)을 대조한다. |
| 조건(condition) 불일치 | `exports`에 `import`만 있는데 빌드 경로가 `require`를 쓰면 해석이 실패할 수 있다. 추론이며 미확인이다. | CI 로그에서 어떤 도구가 에러를 냈는지 확인한다. |
| CI 캐시 또는 설치 방식 문제 | 캐시 키가 lockfile 해시라 lockfile이 바뀌면 키도 바뀐다. 다만 복원 키 폴백이나 `npm install` 사용 시 이전 설치분이 남을 수 있다. | CI 로그에서 캐시 적중 여부, `npm ci`와 `npm install` 중 무엇을 썼는지, 설치된 버전을 확인한다. |
| Node 18과 20 차이 | Node 18도 `exports`를 지원하므로 단독 원인일 가능성은 낮다. | 같은 Node 버전에서 두 환경을 비교한다. |

## 에러 메시지에 대한 참고

`Cannot find module`은 Node의 CommonJS 해석 실패 문구로 알려져 있다. Node가 `exports` 규칙에 어긋난 경로를 처리할 때는 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`를 낸다. 따라서 이 에러가 Next.js 빌드에서 났는지, 테스트 러너나 별도 스크립트에서 났는지 확인이 필요하다. 에러를 낸 도구에 따라 확인할 대상이 달라진다.

## 확인 순서

1. 로컬에서 `npm ls @company/ui`를 실행하여 설치 버전을 확인한다.
2. 로컬 `node_modules`를 삭제하고 `npm ci`로 다시 설치한 뒤 빌드한다.
3. 2.0.0 `package.json`의 `exports`에서 `button` 경로 정의를 확인한다.
4. CI 로그에서 에러가 난 단계와 전체 스택 트레이스를 확인한다.
5. CI 빌드 단계 앞에 `npm ls @company/ui` 출력 단계를 추가한다.
6. 로컬을 Node 18로 빌드하여 Node 버전 영향을 분리한다.

## PM을 위한 요약

현재 원인은 미확정이다. 로컬 빌드가 성공한 결과는 로컬 설치 버전이 달라 신뢰하기 어렵다. 1번과 2번 확인은 각각 수 분 안에 끝날 것으로 보인다. 그 결과에 따라 원인이 가려지며, 2.0.0 업그레이드를 유지할지 여부는 원인 확인 후에 결정하는 것이 맞다.
