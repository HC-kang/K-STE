# 원인 분석: CI에서만 `Cannot find module '@company/ui/button'` 발생

## 한 줄 요약
`@company/ui` 2.0.0이 `exports` 필드를 추가하면서 **deep import(`@company/ui/button`)가 더 이상 허용되지 않게 된 것**이 가장 유력한 원인이다. 로컬은 3일 전 이전에 설치한 1.4.0이 그대로 남아 있어 문제가 가려졌다.

## 원인 (가능성 높은 순)

### 1. `exports` 필드로 인한 deep import 차단 (주원인)
- `exports`가 있으면 Node는 **명시적으로 노출된 경로만** import를 허용한다. 선언되지 않은 `@company/ui/button`은 파일이 실제로 있어도 `Cannot find module`(또는 `ERR_PACKAGE_PATH_NOT_EXPORTED`)이 된다.
- 1.4.0에는 `exports`가 없어서 `@company/ui/button`이 파일 경로 그대로 해석됐다.
- 이는 2.0.0의 **breaking change**에 해당한다.

### 2. 로컬이 "낡은" `node_modules`를 쓰고 있음 (왜 로컬은 성공하는가)
- 로컬 `node_modules`는 업그레이드 이전에 설치되어 **실제로는 1.4.0**일 가능성이 높다.
- CI는 `package-lock.json` 기준으로 2.0.0을 새로 설치하므로 문제가 처음 드러났다.
- 즉 "로컬 성공"은 2.0.0에서 검증된 결과가 아니다.

### 3. Node 18 vs 20 차이 (보조 요인, 확인 필요)
- 두 버전 모두 `exports`를 지원하지만, 서브패스 패턴(`"./*"`), 조건부 export(`import`/`require`/`types`) 해석 및 번들러 동작에 미묘한 차이가 있을 수 있다.
- 주원인은 아니지만, 2.0.0의 `exports` 설정이 Node 20 기준으로만 검증됐을 가능성은 배제하지 못한다. 패키지의 `engines` 필드도 확인이 필요하다.

### 4. 캐시 (원인 아님, 배제 가능)
- 캐시 키가 `package-lock.json` 해시이므로 lock이 바뀌면 캐시도 갱신된다. 오래된 캐시가 원인일 가능성은 낮다.

## 근거가 되는 정황
| 사실 | 해석 |
|---|---|
| 3일 전 1.4.0 → 2.0.0 | 시점이 문제 발생과 일치 |
| 2.0.0에 `exports` 추가 | deep import 경로 차단 가능 |
| 로컬 `node_modules`가 그 이전 설치 | 로컬은 아직 1.4.0 |
| CI는 lock 기준 클린 설치 | 2.0.0으로 빌드 → 실패 |

## 확인 방법 (5분 내)
```bash
# 1. 로컬에 실제 설치된 버전 확인 (1.4.0이면 가설 확정)
npm ls @company/ui

# 2. 2.0.0이 노출하는 경로 확인
node -p "require('./node_modules/@company/ui/package.json').exports"

# 3. 로컬에서 CI와 동일하게 재현
rm -rf node_modules .next && npm ci && npm run build
# (가능하면 Node 18로: nvm use 18)
```

## 해결 방안
| 방안 | 내용 | 비고 |
|---|---|---|
| **A. import 경로 수정** | `exports`에 노출된 공식 경로로 변경 (예: `@company/ui` 루트 또는 문서화된 서브패스) | 권장. 릴리스 노트/마이그레이션 가이드 확인 |
| B. 패키지 쪽 수정 | `@company/ui`의 `exports`에 `"./button"` 추가 후 2.0.1 배포 | 사용처가 많다면 이쪽이 효율적 |
| C. 임시 롤백 | 1.4.0으로 고정 | 급한 경우의 우회책. 근본 해결 아님 |

## 재발 방지
- 로컬 개발도 업그레이드 후 `npm ci`로 클린 설치하는 습관 또는 문서화
- **로컬과 CI의 Node 버전 통일** (`.nvmrc`, `engines`, `actions/setup-node`에서 `node-version-file` 사용)
- 메이저 버전 업그레이드 PR은 CI 통과 확인 후 머지
- 의존성 업그레이드는 변경 로그의 breaking change 확인을 체크리스트화

## PM 참고용 요약
- **영향**: 배포 파이프라인 차단. 서비스 자체 장애는 아님.
- **원인**: 라이브러리 메이저 업그레이드의 breaking change + 로컬 환경이 오래된 상태.
- **예상 조치 시간**: 경로 수정(A) 기준 수 시간 내. 임시 롤백(C)은 즉시 가능.
- **리스크**: 같은 패키지의 다른 deep import도 동일하게 깨질 수 있으므로 전체 검색(`grep -r "@company/ui/"`) 필요.

> 참고: 위 내용은 제공된 정황에 기반한 분석이며, 실제 확정을 위해 "확인 방법" 1~2번 결과를 먼저 확인하길 권한다.
