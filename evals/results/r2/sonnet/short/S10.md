가장 유력한 원인은 로컬이 `@company/ui` 1.4.0을 그대로 쓰고 CI만 2.0.0을 설치해서, 2.0.0의 `exports` 필드가 `@company/ui/button` 경로를 막은 것입니다. 아래 내용 중 이 연결은 추론이고, 확인한 사실이 아닙니다.

`exports` 필드가 없는 패키지는 `@company/ui/button`처럼 내부 파일 경로를 직접 불러올 수 있습니다. `exports` 필드가 있는 패키지는 그 필드에 선언한 경로만 불러올 수 있습니다. 2.0.0의 `exports`에 `./button`이 없거나 다른 이름으로 선언돼 있으면, 같은 import 구문이 2.0.0에서만 실패합니다. 로컬 `node_modules`는 3일 전 업그레이드보다 먼저 설치한 것이어서 1.4.0이 남아 있을 가능성이 높고, 그래서 로컬 빌드만 성공했을 수 있습니다.

원인 후보별 판단은 다음과 같습니다.

| 후보 | 판단 | 근거 |
|---|---|---|
| 로컬 1.4.0, CI 2.0.0 차이와 `exports` 제한 | 가장 유력 | 설치 시점, 업그레이드 시점, `exports` 추가가 모두 일치합니다. |
| Node 18과 20의 차이 | 가능성 낮음 | 두 버전 모두 `exports`를 지원합니다. 다만 `exports` 안의 조건 설정에 따라 차이가 날 수는 있습니다. |
| CI 캐시가 오래된 의존성을 복원 | 가능성 낮음 | 캐시 키가 `package-lock.json` 해시여서 업그레이드 커밋에서 키가 바뀌었을 것입니다. 확인 필요: 업그레이드 때 lock 파일을 커밋했는지 봐야 합니다. |

에러 메시지에 대한 참고 사항이 있습니다. Node가 `exports` 때문에 경로를 막으면 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`를 냅니다. 이번처럼 "Cannot find module"로 보이는 것은 빌드 도구가 메시지를 바꿨기 때문일 수 있지만, 이 부분도 확인하지 않았습니다.

확인 순서는 다음과 같습니다.

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전이 1.4.0인지 확인합니다.
2. 2.0.0의 `package.json`에서 `exports`에 `./button`이 선언돼 있는지 확인합니다.
3. 로컬에서 `rm -rf node_modules && npm ci && npm run build`를 실행해 CI와 같은 조건으로 실패가 재현되는지 확인합니다.
4. 3번에서 재현되지 않으면 Node 18로 같은 빌드를 실행해 Node 버전 차이를 확인합니다.

3번에서 실패가 재현되고 2번에서 `./button`이 없다면, 수정 방향은 두 가지입니다. import 경로를 2.0.0이 선언한 경로로 바꾸거나, `@company/ui` 담당자에게 `./button` 서브패스 export를 추가해 달라고 요청합니다. 이 경우 CI 설정은 바꿀 필요가 없습니다.
