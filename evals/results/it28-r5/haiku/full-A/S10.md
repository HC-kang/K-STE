가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드가 `button` 하위 경로를 허용하지 않거나 다른 경로로 바꿨기 때문입니다. 로컬 빌드가 성공한 이유는 3일 전에 설치한 node_modules가 여전히 1.4.0을 쓰고 있을 가능성이 높기 때문으로 보입니다(추론). 아래 확인 사항으로 이 판단을 검증하십시오.

### 근거

`exports` 필드가 있으면 Node는 그 맵에 적힌 하위 경로만 import를 허용합니다. 맵에 `./button`이 없으면 파일이 실제로 있어도 `@company/ui/button`은 해석되지 않고, Node는 `Cannot find module` 오류를 냅니다.

로컬 node_modules는 2.0.0 출시 전에 설치되었으므로 1.4.0이 그대로 남아 있을 가능성이 높습니다. 1.4.0에는 `exports` 제한이 없어 같은 import가 통과합니다. 따라서 로컬 성공은 로컬에서도 2.0.0이 빌드된다는 증거가 아닙니다.

CI는 `package-lock.json`이 2.0.0으로 갱신되어 커밋되었다면 캐시 키가 바뀌어 새로 설치하므로 2.0.0을 받습니다. 오래된 캐시가 원인일 가능성은 낮습니다(추론).

오류 형식도 단서가 됩니다. `Cannot find module`은 Node의 모듈 해석 오류 형식입니다. webpack 단계에서 실패했다면 보통 `Module not found`로 표시되므로, 실패 지점은 `next.config.js`나 Node로 직접 실행되는 스크립트일 수 있습니다(추론).

### 원인 후보 비교

| 후보 | 근거 | 판단 |
|---|---|---|
| 2.0.0의 `exports`에 `button` 경로가 없거나 변경됨 | 2.0.0에서 `exports`가 추가됨, 로컬만 성공함 | 가능성 높음 |
| Node 18과 20의 차이 | CI와 로컬의 Node 버전이 다름 | 가능성 낮음. 두 버전 모두 `exports`를 지원함(추론) |
| 오래된 CI 캐시 | 캐시 키가 lock 파일 해시임 | 가능성 낮음. lock이 갱신되었다면 캐시가 바뀜(추론) |
| 로컬이 실제로는 1.4.0을 씀 | 3일 전에 설치한 node_modules를 사용함 | 가능성 높음(추론). 확인 필요 |

### 확인 필요

1. 로컬과 CI에서 `npm ls @company/ui`를 실행해 실제 설치 버전을 비교합니다.
2. 2.0.0 패키지의 `package.json`에서 `exports` 맵에 `./button`이 있는지, 있다면 어떤 경로인지 확인합니다.
3. CI 로그의 스택 트레이스로 오류가 난 파일과 실행 단계를 확인합니다.
4. 3일 전 변경에 갱신된 `package-lock.json`이 포함되어 커밋되었는지 확인합니다.

개발자는 1번과 2번의 결과를 먼저 확인한 뒤, `exports` 맵에 맞게 import 경로를 고칠지 `@company/ui`를 1.4.0으로 되돌릴지 고르십시오. PM에게는 CI 빌드가 실패하고 있으며 원인이 아직 확정되지 않았다는 점을 함께 전달하십시오.
