가장 가능성이 높은 원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드입니다. `exports`는 패키지 밖에서 가져올 수 있는 경로를 목록으로 정하는 설정입니다. 2.0.0의 목록에 `./button` 경로가 없다면 `@company/ui/button` import는 해석되지 않아 실패합니다. 이는 추론이며, 아직 2.0.0의 `exports` 내용을 직접 확인하지 않았습니다.

로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 3일 전 업그레이드보다 먼저 설치되었기 때문일 가능성이 큽니다. 그렇다면 로컬에는 `exports`가 없는 1.4.0이 들어 있고, 그래서 `button` 경로가 그대로 열려 있었을 것입니다. 따라서 로컬 성공은 2.0.0에서도 빌드된다는 증거가 아닙니다. 로컬은 2.0.0을 실제로 검증하지 않은 상태일 수 있습니다.

CI가 실패한다는 사실은 CI가 2.0.0을 받았음을 시사합니다. 캐시 키가 `package-lock.json` 해시이므로 lock 파일이 2.0.0으로 갱신되었다면 캐시가 무효화되어 새로 설치되었을 것입니다. 다만 CI가 실제로 어떤 버전을 설치했는지는 로그로 확인되지 않았습니다.

| 가설 | 근거 | 가능성 | 확인 방법 |
|---|---|---|---|
| 2.0.0의 `exports`에 `./button` 경로가 없음 | 2.0.0에 `exports`가 추가됨, 서브경로 import에서 실패 | 높음 (추론) | `npm view @company/ui@2.0.0 exports` |
| 로컬은 1.4.0 상태임 | 로컬 `node_modules`가 업그레이드 전에 설치됨 | 높음 (추론) | `npm ls @company/ui` |
| CI의 Node 18이 원인임 | 실패가 CI에서만 발생함 | 낮음 (추론) | CI에서 Node 20으로 같은 빌드를 실행함 |
| 캐시가 원인임 | 캐시 키가 lock 해시임 | 낮음 (추론) | CI 로그에서 캐시 적중 여부와 설치된 버전을 확인함 |

Node 18과 20은 모두 `exports`를 지원하므로 버전 차이만으로 이 에러가 난다고 보기는 어렵습니다. 다만 Node 18은 2025년 4월에 지원이 끝났으므로 CI의 Node 버전은 별도로 점검할 필요가 있습니다.

확인되지 않은 사항은 다음과 같습니다.
- 2.0.0의 `exports` 목록에 `./button`이나 `./*` 패턴이 있는지
- 로컬에 실제로 설치된 `@company/ui` 버전
- 실패한 파일의 import 문과 Next.js 버전
- CI 캐시 설정에 이전 캐시로 대체하는 `restore-keys`가 있는지

가장 빠른 확인은 다음 순서입니다. 먼저 2.0.0의 `exports`를 확인하고, 로컬에서 `node_modules`를 새로 설치한 뒤 빌드합니다. 로컬 clean 설치에서도 같은 에러가 나면 원인이 확정됩니다.

```
npm view @company/ui@2.0.0 exports
npm ls @company/ui
rm -rf node_modules && npm ci && npm run build
```

확인 후 조치 방향은 두 가지입니다. 2.0.0이 제공하는 경로로 import를 바꾸거나, 당장 전환이 어려우면 1.4.0에 고정한 뒤 2.0.0 대응을 나중에 진행하는 방법입니다.
