## 결론

CI 실패의 가장 유력한 원인은 2.0.0에 새로 추가된 `exports` 필드가 `@company/ui/button` 경로를 허용하지 않는 것이다. 다만 이 원인은 아직 확인되지 않았다. 로컬 빌드가 성공하는 것은 2.0.0으로 검증한 결과가 아닐 가능성이 크다. 로컬 `node_modules`가 3일 전 이전에 설치되어 1.4.0을 그대로 쓰고 있을 수 있기 때문이다.

## 확인된 사실

- 3일 전(약 2026-10-14) `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에 `exports` 필드가 추가됐다.
- CI는 Node 18, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`의 해시다.
- 로컬 `node_modules`는 업그레이드 이전에 설치됐다.
- 실패 에러는 `Cannot find module '@company/ui/button'`이다.

## 추론: 로컬과 CI가 다른 버전을 쓰고 있다

업그레이드로 `package-lock.json`이 바뀌었으므로 CI 캐시 키도 바뀐다. 그래서 CI는 새로 설치하여 2.0.0을 쓴다. 반면 로컬은 1.4.0이 설치된 상태이므로 `@company/ui/button` 경로가 그대로 동작한다.

따라서 로컬과 CI의 차이는 Node 버전보다 설치된 패키지 버전일 가능성이 크다. 이 내용은 추론이며 아래 확인 방법으로 검증해야 한다.

## 원인 가설

| 가설 | 근거 | 가능성 | 확인 방법 |
|---|---|---|---|
| 2.0.0의 `exports`에 `./button` 경로가 없거나 다른 경로로 바뀌었다 | 실패 시점과 `exports` 추가 시점이 맞는다 | 높음 (미확인) | 2.0.0의 `package.json`에서 `exports` 항목 확인 |
| 로컬이 1.4.0을 쓰고 있어 2.0.0을 검증하지 않았다 | 로컬 `node_modules`가 업그레이드 이전에 설치됐다 | 높음 (로컬 성공의 이유로 유력) | `npm ls @company/ui` 실행 |
| `exports`의 `types` 조건이 없어 TypeScript 타입 해석이 실패했다 | `Cannot find module` 메시지는 Node 런타임보다 TypeScript(TS2307)에서 자주 나온다 | 중간 (미확인) | CI 로그에서 실패 단계 확인 |
| Node 18과 20의 차이 | `exports` 해석은 두 버전에서 같게 동작한다. 다만 번들된 npm 버전이 달라 설치 결과가 다를 수 있다 | 낮음 | Node 18로 로컬 재현 |
| 캐시 복원 문제 | 캐시 키가 lock 해시라 정상이라면 새 캐시가 생긴다 | 낮음 (복원 키 설정 시 재검토) | CI 캐시 설정 확인 |

확인 필요: 에러 메시지가 Node 런타임 형식과 정확히 같은지 확인해야 한다. `exports` 불일치는 Node에서 보통 `ERR_PACKAGE_PATH_NOT_EXPORTED`로 나타난다. 전체 로그와 스택 트레이스가 있어야 어느 도구에서 실패하는지 확정할 수 있다.

## 확인 방법 (권장 순서)

1. 로컬에서 `npm ls @company/ui`를 실행하여 설치된 버전을 확인한다.
2. 2.0.0의 `package.json`에서 `exports` 필드에 `./button` 항목과 `types` 조건이 있는지 확인한다.
3. 로컬에서 `rm -rf node_modules && npm ci`로 다시 설치한 뒤 Node 18로 빌드하여 실패를 재현한다.
4. CI 로그에서 실패한 단계, 설치된 `@company/ui` 버전, 캐시 복원 여부를 확인한다.

## 확인 필요 항목

- 전체 에러 로그와 실패한 단계 (`next build`, 타입 검사, 린트 중 무엇인지)
- CI 캐시 설정에 `restore-keys`가 있는지 여부
- 사용 중인 Next.js 버전과 Node 18 지원 범위
- 2.0.0 변경 로그에 `./button` 경로 변경이 기록되어 있는지 여부

## 수정 방향 (권장, 아직 적용하지 않음)

- `exports`에 `./button`이 없으면 패키지 관리자에게 `exports` 항목 추가를 요청하거나, 2.0.0이 허용하는 import 경로로 바꾼다.
- 로컬과 CI의 Node 버전을 하나로 맞춘다. `.nvmrc`나 `engines` 필드에 기준 버전을 적는 것을 권장한다. 기준 버전은 Next.js 지원 범위를 보고 정한다.
- 의존성을 올린 뒤에는 로컬에서도 `npm ci`로 다시 설치하고 빌드하는 절차를 추가해야 한다. 그래야 로컬 결과가 CI와 같은 버전을 검증한다.

## PM 관점 요약

현재 CI 빌드가 실패하는 상태이며 배포가 막혀 있을 가능성이 있다. 로컬 빌드 성공은 2.0.0 검증 결과로 볼 수 없다. 원인 확정은 위 확인 방법 1과 2를 먼저 하면 된다.
