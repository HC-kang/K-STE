현재 정보로는 2.0.0에 새로 추가된 `exports` 필드가 가장 유력한 원인입니다. 다만 아직 재현하지 않았으므로 아래 확인이 끝나야 원인을 확정할 수 있습니다.

## 확인된 사실

- `@company/ui`를 1.4.0에서 2.0.0으로 올렸고, 이 변경은 3일 전에 이루어졌습니다.
- 2.0.0에서 `exports` 필드(패키지가 외부에 공개할 경로를 정하는 설정)가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

## 추론

- `exports` 필드가 있으면 패키지 내부 파일을 경로로 직접 가져오는 방식(깊은 임포트, deep import)은 공개 목록에 있는 경로만 허용됩니다. 2.0.0의 `exports` 목록에 `./button`이 빠졌을 가능성이 있습니다.
- 로컬 `node_modules`가 3일 전 이전에 설치되었다면 로컬에는 1.4.0이 남아 있을 가능성이 큽니다. 이 경우 로컬 빌드 성공은 2.0.0이 동작한다는 증거가 되지 않습니다.
- `package-lock.json`이 바뀌면 캐시 키도 바뀌므로 CI는 새로 설치하고, 그 결과 2.0.0을 받았을 가능성이 큽니다. 이는 CI에서만 실패하는 현상과 맞습니다.
- Node 18과 20의 차이가 원인일 가능성은 낮아 보입니다. 다만 두 환경에 포함된 npm 버전이 다를 수 있으므로 설치 결과 차이는 확인이 필요합니다.
- 에러 문구 `Cannot find module`은 Node와 번들러 중 어느 쪽이 던졌는지에 따라 달라집니다. 전체 스택 트레이스를 봐야 어느 단계에서 실패했는지 알 수 있습니다.

## 확인 방법

| 가설 | 확인 방법 | 결과에 따른 판단 |
|---|---|---|
| CI가 2.0.0을 설치하지 않았다 | CI 로그에서 `npm ls @company/ui`의 결과를 확인합니다. | 1.4.0이 나오면 캐시나 설치 과정을 조사해야 합니다. |
| 2.0.0의 `exports`에 `./button`이 없다 | 2.0.0의 `package.json`에서 `exports` 항목을 확인합니다. | `./button`이 없으면 원인이 확정됩니다. |
| 로컬에 1.4.0이 남아 있다 | 로컬에서 `npm ls @company/ui`를 실행합니다. | 1.4.0이 나오면 로컬 성공은 2.0.0 검증이 아닙니다. |
| Node 버전 차이가 원인이다 | 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 Node 18과 Node 20에서 각각 빌드합니다. | Node 18에서만 실패하면 Node 버전이 원인일 가능성이 높아집니다. |

## 권장 순서

1. CI 로그에서 설치된 `@company/ui` 버전과 전체 스택 트레이스를 확인합니다.
2. 2.0.0의 `exports`에 `./button`이 있는지 확인합니다.
3. 로컬에서 `node_modules`를 지우고 새로 설치한 뒤 Node 18과 Node 20에서 각각 빌드합니다.

수정 방향은 위 결과에 따라 달라집니다. 호출하는 쪽의 import 경로를 공개 경로로 바꾸는 방법과 패키지 쪽에서 `exports`에 경로를 추가하는 방법이 있습니다. 원인이 확정되기 전까지 임시 조치로 1.4.0에 고정하는 방법도 선택지가 될 수 있습니다.
