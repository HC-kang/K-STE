## 결론

가장 가능성이 높은 원인은 `@company/ui` 2.0.0의 `exports` 필드가 `button` 하위 경로를 노출하지 않은 것입니다. 로컬 빌드가 성공하는 이유는 로컬 `node_modules`에 설치된 1.4.0이 그대로 남아 있기 때문일 가능성이 높습니다. 두 가설은 아직 확인하지 않았습니다.

## 실패가 CI에서만 나는 경로

1. 2.0.0부터 패키지에 `exports` 필드가 생겼습니다. `exports`가 있으면 Node와 번들러는 맵에 명시된 경로로만 모듈을 가져올 수 있습니다. 맵에 `./button`이 없으면 `@company/ui/button`은 해석되지 않습니다. 에러 메시지와 시점이 이 가설과 맞습니다.
2. CI 캐시 키는 `package-lock.json`의 해시입니다. lock 파일이 바뀐 커밋부터 캐시가 새로 만들어지고, 그 과정에서 2.0.0이 설치됩니다. 그 결과 CI에서 실패합니다.
3. 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다. 그래서 1.4.0이 남아 있을 가능성이 높습니다. 1.4.0에는 이 import를 막는 `exports` 제한이 없어서 로컬 빌드가 통과합니다.

## 원인 후보 비교

| 후보 | 근거 | 확인 방법 |
|---|---|---|
| 2.0.0 `exports` 맵에 `./button` 경로가 없다 | 에러 메시지, `exports` 추가 시점과 실패 시작 시점이 맞음 | `npm view @company/ui@2.0.0 exports` 실행 |
| 로컬이 1.4.0을 쓰고 있다 | 로컬 설치가 3일 전보다 먼저 이루어짐 | 로컬에서 `npm ls @company/ui` 실행 |
| Node 18과 20의 차이 | CI와 로컬의 Node 버전이 다름 | 로컬에서 Node 18로 빌드해 재현 |

Node 18도 `exports`를 지원하므로 버전 차이만으로 이 에러가 나는 경우는 드뭅니다. 그래도 Node 18로 재현해서 배제하십시오.

## 다음 단계

1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인하십시오. 1.4.0이면 로컬 빌드는 2.0.0 상태를 검증하지 않은 것입니다.
2. `npm view @company/ui@2.0.0 exports`로 `exports` 맵에 `./button`이 있는지 확인하십시오.
3. 맵에 `./button`이 없으면 `@company/ui` 담당자에게 맵 추가를 요청하십시오. 맵에 있는 경로로 import를 바꾸는 방법도 있습니다.
4. 당장 빌드를 살리려면 `@company/ui`를 1.4.0으로 고정하는 방법이 있습니다.

배포가 막힌 기간과 영향 범위는 주어진 정보로 판단할 수 없습니다.
