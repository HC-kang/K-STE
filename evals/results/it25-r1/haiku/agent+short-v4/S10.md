## 결론

가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드가 `button` 하위 경로를 공개하지 않는 것이다. 이는 추론이며, 2.0.0 패키지의 `exports` 내용을 아직 확인하지 않았다. 로컬은 3일 전에 설치한 1.4.0이 남아 있어서 성공하고, CI는 2.0.0을 새로 설치해서 실패한다.

## 확인된 사실

- `@company/ui`를 1.4.0에서 2.0.0으로 올렸다. 올린 시점은 3일 전이다.
- 2.0.0에는 `exports` 필드가 추가됐다.
- CI는 Node 18, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`의 해시다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치됐다.
- 실패 에러는 `Error: Cannot find module '@company/ui/button'`이다.

## 원인 분석

`exports` 필드는 패키지가 외부에 공개할 파일 경로를 정하는 설정이다. 이 필드가 있으면 Node와 번들러(웹 코드를 묶어 내보내는 도구)는 목록에 없는 하위 경로(`@company/ui/button`처럼 패키지 이름 뒤에 파일 경로를 붙인 import)를 찾지 않는다. 1.4.0에는 이 필드가 없었으므로 `@company/ui/button`이 실제 파일 경로로 직접 찾아졌다. 2.0.0에서 `button` 경로가 목록에 빠졌다면 같은 import가 실패한다. 이 내용은 아직 확인하지 않은 추론이다.

로컬 빌드가 성공하는 이유는 로컬 `node_modules`가 3일 전에 설치된 것이라 1.4.0이 그대로 들어 있을 가능성이 높기 때문이다. 이 경우 로컬은 2.0.0의 `exports` 변경을 한 번도 받지 않았다.

CI는 `package-lock.json`이 바뀌면 캐시 키도 바뀌므로 새로 설치한다. 그 결과 2.0.0이 설치되고 import가 실패한다. 캐시 키가 lockfile 해시이므로 캐시가 오래된 1.4.0을 재사용했을 가능성은 낮다. 다만 캐시 복원에 이전 키 대체(restore-keys) 설정이 있으면 이 판단은 달라질 수 있다.

Node 버전 차이는 원인일 가능성이 낮다. Node 18도 `exports` 필드를 지원하기 때문이다. 다만 Next.js나 번들러 버전에 따라 해석이 다를 수 있으므로 Node 버전은 가설로만 남겨 둔다.

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `@company/ui` 버전 | 1.4.0으로 추정 (3일 전 설치분) | 2.0.0으로 추정 (lockfile 변경 후 설치) |
| `node_modules` | 3일 전 설치분 그대로 | 캐시 키 기준으로 새로 설치 |
| 빌드 결과 | 성공 | 실패 |

## 확인 필요 항목

다음 항목을 확인하면 원인을 확정할 수 있다.

1. 로컬에서 `npm ls @company/ui`를 실행해 실제 설치 버전을 확인한다. 1.4.0이면 위 추론이 맞을 가능성이 높다.
2. `npm view @company/ui@2.0.0 exports`로 2.0.0의 `exports` 목록에 `./button`이 있는지 확인한다.
3. CI 로그에서 실패한 파일과 import 줄을 확인한다.
4. CI가 `npm ci`를 쓰는지 `npm install`을 쓰는지 확인한다. `npm install`이면 lockfile과 다른 버전이 설치될 수 있다.
5. 캐시 설정에 이전 키 대체(restore-keys)가 있는지 확인한다.

## 권장 조치

1. 패키지 쪽에 2.0.0의 `exports`에 `button` 경로를 추가하도록 요청한다. 이것이 공개 경로를 바꾼 원인을 고치는 방법이다.
2. 앱 쪽에서는 2.0.0이 공개한 경로로 import를 바꾼다. 패키지 수정을 기다리는 동안 이 방법을 쓸 수 있다.
3. 급하게 빌드를 살려야 하면 `@company/ui`를 1.4.0으로 고정하고 lockfile을 갱신한다.
4. Node 버전을 맞추는 작업은 원인을 확인한 뒤에 진행한다. 지금은 우선순위가 낮다.
