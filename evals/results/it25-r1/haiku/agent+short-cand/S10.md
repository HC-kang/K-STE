가장 가능성이 높은 원인은 `@company/ui` 2.0.0의 `exports` 필드가 `./button` 경로를 노출하지 않아서, CI가 `@company/ui/button`을 찾지 못하는 것입니다. 다만 패키지 내용과 lock 파일은 아직 확인하지 않았으므로 이 원인은 가설입니다.

## 확인된 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드가 새로 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

## 로컬과 CI의 차이

| 항목 | 로컬 | CI |
|---|---|---|
| Node 버전 | 20 | 18 |
| `node_modules` 출처 | 3일 전 이전에 설치됨 | 캐시가 복원되지 않으면 lock 파일 기준으로 새로 설치됨 |
| `@company/ui` 버전 | 1.4.0일 가능성이 높음 (미확인) | 2.0.0 |

## 추론

`exports` 필드가 있으면 패키지 바깥에서 가져올 수 있는 경로가 `exports`에 적힌 경로로 제한됩니다. 1.4.0에는 이 필드가 없어서 `@company/ui/button` 같은 하위 경로가 제한 없이 해석되었습니다. 2.0.0에서 `./button` 항목이 빠졌다면 CI에서 이 에러가 납니다.

로컬 빌드가 성공하는 이유는 3일 전에 설치한 `node_modules`에 1.4.0이 남아 있기 때문일 가능성이 높습니다. **따라서 로컬 빌드 성공은 코드가 정상이라는 근거가 되지 않습니다.**

Node 18과 20은 모두 `exports` 필드를 지원합니다. 그러므로 Node 버전 차이만으로 이 에러가 나는 경우는 드물다고 봅니다.

캐시는 원인이 아닐 가능성이 높습니다. 캐시 키가 lock 파일 해시이므로, lock 파일이 3일 전에 바뀌었다면 CI는 새로 설치해서 2.0.0을 받습니다.

## 미확인 사항

- 2.0.0의 `exports` 맵에 `./button` 항목이 있는지 보지 않았습니다.
- 로컬 `node_modules`에 실제로 설치된 버전을 확인하지 않았습니다.
- 2.0.0이 ESM 전용인지는 알 수 없습니다.
- 저장소의 `package.json`, lock 파일, CI 로그는 확인하지 않았습니다.

## 확인 순서

1. 로컬에서 `node_modules/@company/ui/package.json`의 `version` 값을 봅니다. 1.4.0이면 로컬 성공의 이유가 설명됩니다.
2. 2.0.0 패키지의 `exports` 맵에 `./button` 또는 `./*` 항목이 있는지 봅니다.
3. Node 18로 `rm -rf node_modules && npm ci`를 실행해 CI와 같은 조건에서 에러가 재현되는지 봅니다.
4. 재현되면 import 경로를 2.0.0의 `exports`에 맞게 바꾸거나, 패키지 쪽 `exports`에 `./button`을 추가해 달라고 요청하는 것을 권장합니다.
