CI 실패의 가장 유력한 원인은 `@company/ui` 2.0.0에 새로 추가된 `exports` 필드로 보입니다. 다만 로컬 빌드는 1.4.0 기준으로 성공했을 가능성이 커서, 로컬 성공이 2.0.0의 정상 동작을 증명하지는 않습니다.

## 확인된 사실

- CI 빌드는 실패하고, 로컬 빌드는 성공합니다.
- 실패 메시지는 `Error: Cannot find module '@company/ui/button'`입니다.
- `@company/ui`는 3일 전에 1.4.0에서 2.0.0으로 올라갔습니다.
- 2.0.0에는 `exports` 필드(패키지 밖에서 가져올 수 있는 파일 경로를 정한 설정)가 추가됐습니다.
- CI는 Node 18을 쓰고, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시(파일 내용을 요약한 값)입니다.
- 로컬 `node_modules`는 업그레이드 전인 3일 전보다 먼저 설치됐습니다.

## 추론

1. `exports` 필드에 `button` 경로가 빠졌거나 이름이 바뀌었다면, `@company/ui/button` 경로는 해석되지 않습니다. 3일 전 메이저 버전 업그레이드 시점과 실패 시점이 맞습니다.
2. 로컬 `node_modules`는 업그레이드 전에 설치됐으므로 1.4.0일 가능성이 큽니다. 그러면 로컬은 2.0.0을 한 번도 빌드하지 않은 상태입니다.
3. `package-lock.json`이 바뀌면 캐시 키도 바뀌므로, CI는 캐시 없이 새로 설치하면서 2.0.0을 받습니다. 그래서 CI와 로컬이 서로 다른 버전으로 빌드하게 됩니다.
4. `exports` 해석 규칙은 Node 18과 20에서 대체로 같습니다. 다만 2.0.0이 ESM 전용(`import`만 지원)이면 CommonJS(`require`)로 읽는 파일에서 Node 18은 실패하고 Node 20 일부 버전은 성공할 수 있습니다. 이 경우에는 Node 버전이 원인입니다.
5. 오류 문구 "Cannot find module"은 Node가 `require`를 해석할 때 나오는 형식입니다. Next.js 번들러의 오류는 보통 "Module not found"로 표시되므로, 실패 지점은 `next.config.js` 같이 Node가 직접 실행하는 파일일 수 있습니다.

## 확인 필요

- CI 로그의 전체 스택 트레이스에서 실패한 파일 경로가 어디인지 확인해야 합니다.
- 로컬 `node_modules/@company/ui/package.json`의 `version` 값이 1.4.0인지 확인해야 합니다. 1.4.0이면 로컬 성공은 검증이 아닙니다.
- 2.0.0 패키지의 `exports`에 `./button` 또는 `./*` 항목이 있는지 확인해야 합니다.
- 2.0.0이 ESM 전용인지, `exports`에 `require` 조건이 있는지 확인해야 합니다.
- 업그레이드 커밋에 `package-lock.json`이 함께 들어갔는지 확인해야 합니다.
- 로컬에서 `node_modules`를 지우고 `npm ci` 후 Node 18로 빌드했을 때 같은 오류가 나는지 확인해야 합니다. 재현되면 원인이 확정됩니다.
