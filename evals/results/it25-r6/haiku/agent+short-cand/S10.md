CI 빌드 실패의 가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 필드(패키지가 외부에 공개할 경로를 적는 설정)에 `button` 경로가 없는 것이다. 이는 아직 확인하지 않은 추론이다.

## 확인된 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에는 `exports` 필드가 추가되었다.
- CI는 Node 18을, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`(설치할 패키지 버전을 고정하는 파일)의 해시(내용을 요약한 고정 길이 값)다.
- 로컬 `node_modules`(설치된 패키지가 담긴 폴더)는 3일 전보다 먼저 설치한 것이다.

## 원인 추정 (추론)

첫째, 1.4.0에는 `exports` 필드가 없었다. 그래서 `@company/ui/button`은 패키지 안의 파일 경로로 바로 풀렸다.

둘째, 2.0.0에서는 `exports` 목록이 외부에서 쓸 수 있는 경로를 정한다. `button` 경로가 이 목록에 없으면 같은 import가 실패한다.

셋째, 로컬 `node_modules`에는 1.4.0이 그대로 남아 있다. 그래서 로컬 빌드는 새 `exports` 제한을 받지 않고 성공한다. 설치 명령을 다시 실행하지 않았다면 이 설명이 맞다.

넷째, `package-lock.json`이 바뀌면 캐시 키도 바뀐다. CI 캐시가 복원되지 않았다면 CI는 새로 설치하면서 2.0.0을 받는다. 그래서 CI에서만 실패한다.

**로컬 빌드 성공은 2.0.0이 정상이라는 증거가 아니다.** 로컬이 실제로 2.0.0을 쓰는지부터 확인해야 한다.

Node 버전 차이는 주원인일 가능성이 낮다. Node 18과 20은 모두 `exports`를 지원한다. 다만 Node 18에서 직접 재현하지 않았으므로 이 가능성을 배제하지 않는다.

확인 필요: 오류 문구 `Cannot find module`은 Node의 `exports` 차단 오류와 형태가 다르다. 따라서 오류를 낸 주체가 Next.js의 번들러(코드를 묶어 빌드하는 도구)일 수 있다. 이 부분은 미확인이다.

## 확인 순서

1. CI 로그에서 `npm ls @company/ui` 결과를 보고 실제로 설치된 버전을 본다.
2. 2.0.0 패키지의 `package.json`에서 `exports` 목록을 보고 `./button` 항목이 있는지 본다.
3. 로컬에서 `rm -rf node_modules && npm ci`를 실행한 뒤 빌드한다. 이때도 실패하면 패키지 버전이 원인이라는 추론이 맞다.
4. 3번을 Node 18로 반복한다. nvm(Node 버전 전환 도구)을 쓰면 된다.

## 조치 방향

- 권장한다. `@company/ui/button` import를 2.0.0 문서나 `exports` 목록에 있는 경로로 바꾼다.
- 해도 된다. 임시로 `@company/ui`를 1.4.0으로 되돌린다. 이때 `package.json`과 `package-lock.json`을 함께 되돌려야 한다.
- 2.0.0 패키지 관리자에게 `./button` 경로 추가를 요청할 수 있다.

`@company/ui/`로 시작하는 import가 프로젝트에 몇 곳이나 있는지 전체 검색으로 세어야 영향 범위를 알 수 있다.

## 미확인 사항

- 배포 파이프라인이 이 실패 때문에 멈췄는지는 아직 모른다.
- 2.0.0 변경 기록에 `button` 경로 변경이 적혀 있었는지는 모른다.
- CI가 실제로 어떤 버전을 설치했는지는 CI 로그를 보기 전까지 모른다.
