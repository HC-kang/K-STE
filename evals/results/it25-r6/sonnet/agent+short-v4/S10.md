CI 빌드가 실패하는 가장 유력한 원인은 `@company/ui` 2.0.0의 `exports` 설정이 `@company/ui/button` 경로를 공개하지 않는 것으로 보입니다. 로컬 빌드는 아직 1.4.0을 쓰고 있어서 이 문제가 드러나지 않았을 가능성이 높습니다. 아래 내용 중 "추론"은 확인하지 않은 판단입니다.

`exports`는 패키지가 외부에 공개할 파일 경로를 제한하는 `package.json` 설정입니다. 이 필드가 있으면 Node는 목록에 없는 경로의 import를 막고 `Cannot find module` 오류를 냅니다. 1.4.0에는 이 필드가 없었으므로 `@company/ui/button`이 실제 파일 경로로 열렸습니다.

사실은 다음과 같습니다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에서 `exports` 필드가 추가됐습니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치한 것입니다.
- CI는 Node 18, 로컬은 Node 20을 씁니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.

추론은 다음과 같습니다.
- 로컬 `node_modules`에는 아직 1.4.0이 설치돼 있습니다. 그래서 로컬은 `exports` 제한을 받지 않고 빌드에 성공합니다.
- CI는 2.0.0을 설치합니다. 그래서 `exports`에 `./button`이 없거나 경로가 바뀌었다면 빌드가 실패합니다.
- Node 버전 차이는 원인일 가능성이 낮습니다. Node 18과 20은 둘 다 `exports`를 지원합니다.
- CI 캐시는 원인일 가능성이 낮습니다. 버전을 올릴 때 `package-lock.json`이 바뀌었다면 캐시 키도 바뀌어 캐시를 새로 만듭니다.

아직 확인하지 않은 사항은 다음과 같습니다.
- 2.0.0의 `exports`에 `./button`이 실제로 있는지 확인하지 않았습니다.
- 2.0.0으로 올린 `package-lock.json`을 커밋했는지 확인하지 않았습니다.
- 로컬 `node_modules`의 `@company/ui` 버전을 확인하지 않았습니다.

원인은 다음 순서로 검증하십시오.
1. 로컬에서 `npm ls @company/ui`를 실행해 설치된 버전을 확인합니다. 1.4.0이면 추론이 맞습니다.
2. 로컬에서 `rm -rf node_modules && npm ci`로 `package-lock.json` 기준으로 다시 설치합니다.
3. 로컬에서 빌드합니다. CI와 같은 오류가 나면 원인이 확정됩니다.
4. 오류가 나면 `node_modules/@company/ui/package.json`의 `exports`에서 공개된 경로를 확인합니다.

`./button`이 공개되지 않았다면 두 가지 중 하나로 고쳐야 합니다. 하나는 앱의 import 경로를 2.0.0이 공개한 경로로 바꾸는 것입니다. 다른 하나는 `@company/ui` 담당자에게 `./button`을 `exports`에 추가해 달라고 요청하는 것입니다. 2.0.0이 의도적으로 경로를 바꿨다면 앞의 방법을 권장합니다.

PM에게 공유할 일정 영향은 다음과 같습니다. 원인이 확정되기 전에는 수정 범위를 알 수 없습니다. 위 1-3단계는 로컬에서 실행할 수 있습니다.
