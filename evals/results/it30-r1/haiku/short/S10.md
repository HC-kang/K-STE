현재 정보만으로는 원인을 하나로 특정할 수 없습니다. 가장 유력한 가설은 CI가 2.0.0을 설치했지만 2.0.0의 `exports` 필드가 `button` 하위 경로를 허용하지 않는다는 것입니다. 이 내용은 추론이며 아직 검증하지 않았습니다.

## 확인된 사실

- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸습니다.
- 2.0.0에는 `exports` 필드가 추가되었습니다.
- CI는 Node 18을, 로컬은 Node 20을 사용합니다.
- CI 캐시 키는 `package-lock.json`의 해시입니다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었습니다.

## 추론

- `exports` 필드가 있으면 패키지 외부에 공개되는 경로가 정해집니다. 2.0.0의 `exports`에 `./button`이 없으면 `@company/ui/button` import는 실패합니다.
- 로컬의 `node_modules`에는 1.4.0이 남아 있을 가능성이 큽니다. 그래서 로컬 빌드가 성공하더라도 2.0.0에서 import가 되는지는 증명되지 않습니다.
- 오류 문구 "Cannot find module"은 Node가 `exports` 제한을 알릴 때 쓰는 문구와 다릅니다. 따라서 패키지 자체가 CI에 설치되지 않았을 가능성도 함께 봐야 합니다.
- 캐시 키가 lock 파일 해시이므로, 3일 전 이후 lock 파일이 바뀌지 않았다면 예전 캐시가 복원되어 1.4.0이 쓰일 수 있습니다.
- Node 18과 Node 20의 차이는 번들러나 npm 버전 차이에서 올 수 있습니다. 이 가능성은 낮다고 봅니다.

## 로컬과 CI 비교

| 항목 | 로컬 | CI |
| --- | --- | --- |
| Node 버전 | 20 | 18 |
| `node_modules` 출처 | 3일 전 이전 설치 (1.4.0일 가능성) | 캐시 복원 또는 새 설치 |
| 캐시 기준 | 없음 | `package-lock.json` 해시 |

## 확인 방법

1. CI 빌드 단계에 `npm ls @company/ui`를 추가해 실제 설치된 버전을 출력합니다.
2. 2.0.0 패키지의 `package.json`에서 `exports` 필드에 `./button` 항목이 있는지 봅니다.
3. 로컬에서 `rm -rf node_modules && npm ci`로 새로 설치한 뒤 빌드합니다.
4. Node 18로 로컬 빌드를 실행해 Node 버전의 영향을 분리합니다.
5. CI 캐시를 비우고 같은 커밋으로 다시 실행합니다.

## 미확인 사항

- 2.0.0의 `exports` 필드 전체 내용
- 3일 전 커밋에서 `package-lock.json`이 바뀌었는지 여부
- CI 워크플로에서 쓰는 설치 명령이 `npm ci`인지 `npm install`인지 여부
- 프로젝트의 Next.js 버전
