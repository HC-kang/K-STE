# 원인 분석: CI에서만 발생하는 `Cannot find module '@company/ui/button'` 빌드 실패

## 요약

**가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다.** 이 필드가 있으면 Node와 번들러는 패키지가 명시적으로 노출한 경로만 import할 수 있습니다. `@company/ui/button` 같은 깊은 경로(deep import)가 2.0.0의 `exports`에 없으면 이 에러가 납니다.

로컬에서 성공하는 이유는 **로컬 `node_modules`가 여전히 1.4.0이기 때문**일 가능성이 높습니다. 3일 전에 설치된 `node_modules`는 `package.json`을 바꿔도 자동으로 갱신되지 않으므로, 로컬은 `exports` 제한이 없는 옛 버전으로 빌드하고 있을 수 있습니다. CI는 `package-lock.json` 해시가 바뀌면서 캐시가 무효화되고 2.0.0을 새로 설치하기 때문에 문제가 드러납니다.

> 아래 내용은 제공된 사실에서 추론한 결과이며, 실제 코드와 패키지 내용으로 아직 검증하지 않았습니다.

## 원인 체인

| 단계 | 내용 | 결과 |
|---|---|---|
| 1 | 3일 전 `@company/ui` 1.4.0 → 2.0.0 업그레이드 | `package.json`과 lockfile 변경 |
| 2 | 2.0.0에 `exports` 필드 추가 | 노출되지 않은 깊은 경로 import 차단 |
| 3 | 로컬 `node_modules`는 업그레이드 전에 설치됨 | 로컬은 여전히 1.4.0으로 빌드, 성공 |
| 4 | lockfile 해시 변경으로 CI 캐시 무효화 | CI는 2.0.0을 새로 설치 |
| 5 | CI에서 `@company/ui/button` 해석 실패 | 빌드 실패 |

## 배제하거나 부차적으로 볼 요인

- **Node 18 vs 20:** `exports` 필드 자체는 Node 14 이후 모두 지원하므로, 이 에러의 직접 원인일 가능성은 낮습니다. 다만 2.0.0이 Node 20 이상 기능에 의존하거나 ESM 전용이라면 Node 18에서 별도 문제가 생길 수 있으므로 확인이 필요합니다. Next.js 버전의 `engines` 요구사항도 함께 확인하세요.
- **캐시 키:** lockfile 해시 기반 키는 업그레이드 후 올바르게 갱신된 것으로 보입니다. 다만 Node 버전이 키에 포함되지 않으면 Node 18/20 간 캐시가 섞일 수 있습니다.
- **대소문자 차이:** macOS는 대소문자를 구분하지 않고 Linux CI는 구분합니다. `@company/ui/Button`과 `button`처럼 경로 대소문자가 다르면 로컬에서만 성공하고 CI에서만 실패합니다. 확인 비용이 적으니 함께 점검하세요.

## 확인 방법 (개발자용)

1. **로컬이 실제로 어떤 버전을 쓰는지 확인**
   ```bash
   npm ls @company/ui
   grep '"version"' node_modules/@company/ui/package.json
   ```
   1.4.0이 나오면 가설이 맞을 가능성이 높습니다.
2. **로컬 재현**
   ```bash
   rm -rf node_modules && npm ci && npm run build
   ```
   여기서도 실패하면 CI와 같은 조건에서 재현된 것입니다.
3. **2.0.0의 `exports` 확인**: `node_modules/@company/ui/package.json`에서 `exports` 맵에 `./button` 또는 `./*` 패턴이 있는지 봅니다.
4. **Node 18로 재현**: `nvm use 18` 후 같은 빌드를 실행합니다.

## 해결 옵션

1. **import 경로 수정(권장, 2.0.0을 유지하는 경우):** `exports`가 노출하는 경로(예: 루트 `@company/ui`의 named export)로 import를 바꿉니다.
2. **라이브러리 쪽 수정:** `@company/ui`가 팀 내부 패키지라면 `exports`에 `"./button"` 또는 `"./*"`를 추가해 기존 경로를 유지할 수 있습니다. 이 경우 다른 소비자에게도 영향을 줄 수 있으니 확인하세요.
3. **임시 롤백:** 빠르게 파이프라인을 복구해야 하면 1.4.0으로 되돌리고 수정 작업을 나중에 진행합니다.
4. **Node 버전 통일:** 로컬과 CI 중 하나로 맞추세요. `.nvmrc`와 `package.json`의 `engines`에 명시하면 같은 문제가 재발하지 않습니다.

**재발 방지:** 로컬 검증 전에 `node_modules`를 재설치하는 습관을 들이고, CI에서 `npm ci`를 사용하는 현재 방식을 유지하세요.

## PM 공유용 요약

- **무슨 일인가:** 3일 전 공용 UI 라이브러리를 메이저 버전(2.0.0)으로 올렸는데, 새 버전이 import 경로 규칙을 바꿨습니다. 로컬 개발 환경은 이전 버전이 남아 있어 문제가 보이지 않았고, 배포 파이프라인(CI)은 새 버전을 설치하기 때문에 빌드가 실패합니다.
- **영향:** 배포 파이프라인이 차단된 상태입니다. 기능 코드에 직접 영향을 줬는지는 아직 확인 전입니다.
- **수정 예상:** 대부분 import 경로 수정으로 해결될 가능성이 높지만, 영향받는 파일 수는 아직 파악하지 못했습니다. 개발자가 `@company/ui/` 경로 사용처를 검색해 범위를 확인한 뒤 일정을 잡는 것이 좋습니다.
- **즉시 조치 옵션:** 빠른 복구가 필요하면 1.4.0으로 임시 롤백할 수 있습니다.
