현재 사실만으로는 원인을 확정할 수 없습니다. 가장 유력한 설명은 로컬과 CI가 서로 다른 버전의 `@company/ui`를 쓰고 있다는 것입니다.

로컬 `node_modules`가 3일 전보다 먼저 설치되었으므로, 그 뒤에 다시 설치하지 않았다면 로컬은 아직 1.4.0을 쓰고 있을 수 있습니다. 그러면 로컬 빌드 성공은 2.0.0을 검증한 결과가 아닙니다. CI는 lock 파일을 따라 2.0.0을 설치하므로 같은 코드가 다른 패키지 버전에서 빌드되는 셈입니다. 2.0.0에 추가된 `exports` 필드에 `./button` 경로가 없거나 제한되어 있다면 이 import는 해석되지 않습니다. 다만 2.0.0의 `exports` 내용은 아직 확인하지 않았습니다.

| 원인 후보 | 현재 사실 | 가능성 | 검증 방법 |
|---|---|---|---|
| 로컬이 1.4.0을 사용 | 로컬 `node_modules`가 3일 전보다 먼저 설치됨 | 높음(추론) | 로컬에서 `npm ls @company/ui` 실행 |
| 2.0.0의 `exports`에 `./button` 경로 없음 또는 제한됨 | `exports` 필드가 추가됨, 내용은 미확인 | 높음(추론) | 2.0.0의 `package.json`에서 `exports` 항목 확인 |
| Node 18과 20의 차이 | 버전이 다름, 차이를 보여 주는 사실은 없음 | 낮음(추론) | Node 18로 `npm ci` 후 빌드 |
| CI 캐시 | 캐시 키는 lock 파일 해시 | 낮음(추론) | 캐시 hit 또는 miss 로그 확인, lock 파일이 업그레이드 커밋에서 바뀌었는지 확인 |

Node 18도 `exports`를 지원하므로 `exports` 필드 자체가 CI 실패의 원인이라고 보기는 어렵습니다. 문제는 `exports`에 정의된 경로와 import 경로가 맞는지에 있을 가능성이 큽니다.

다음 순서로 확인하십시오.

1. 로컬에서 `npm ls @company/ui`를 실행해 실제로 설치된 버전을 확인하십시오.
2. CI 로그에서 설치된 `@company/ui` 버전을 확인하십시오.
3. 2.0.0 패키지의 `exports` 필드에 `./button` 또는 이를 포함하는 패턴이 있는지 확인하십시오.
4. 로컬에서 `node_modules`를 지우고 Node 18로 `npm ci` 후 빌드하여 재현되는지 확인하십시오.

PM에게는 "로컬 빌드가 옛 버전을 쓰고 있을 가능성이 있어 원인 후보 두 가지를 확인 중이며, 수정 방향은 확인 결과 후에 정하겠습니다"라고 전달하시면 됩니다.
