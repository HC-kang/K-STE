# 원인 분석: CI에서만 `Cannot find module '@company/ui/button'` 발생

## 요약 (PM용)
- **원인(가능성 높음)**: `@company/ui` 2.0.0은 `exports` 필드로 외부에서 import할 수 있는 경로를 제한한다. `@company/ui/button`이 허용 경로에 없어서 빌드가 실패한다.
- **로컬이 성공하는 이유**: 로컬 `node_modules`가 업그레이드 전에 설치되어 있어 실제로는 1.4.0을 쓰고 있다. 즉 로컬 빌드는 2.0.0을 검증하지 못했다.
- **CI가 정상 동작하는 것이다**: CI가 문제를 만든 게 아니라 업그레이드의 호환성 문제를 처음 드러냈다.
- **영향**: 2.0.0으로 올린 브랜치는 CI를 통과할 수 없다. 수정은 import 경로 변경이나 패키지 `exports` 보완 수준으로, 규모가 크지 않을 가능성이 높다.

## 상세 분석 (개발자용)

**1. `exports` 필드가 경로 접근을 막는다**
- 1.4.0은 `exports`가 없어서 `@company/ui/button`이 `node_modules/@company/ui/button.js` 같은 실제 파일 경로로 resolve됐다.
- 2.0.0부터 `exports`가 있으면 Node와 번들러는 거기에 선언된 subpath만 허용한다. `"./button"`이 없거나 이름·경로가 바뀌었다면 파일이 존재해도 `Cannot find module`이 발생한다.

**2. 로컬이 성공하는 이유**
- 로컬 `node_modules`는 3일 전 업그레이드보다 먼저 설치됐다. `package.json`과 lock 파일은 2.0.0인데 실제 설치본은 1.4.0일 가능성이 높다.

**3. CI에서 실패하는 이유**
- 캐시 키가 `package-lock.json` 해시이므로, 업그레이드로 lock 파일이 바뀌면서 캐시가 미스되고 2.0.0이 새로 설치됐다. 캐시는 의도대로 동작했고 원인이 아니다.

**4. Node 18 vs 20은 원인일 가능성이 낮다**
- 두 버전 모두 `exports`를 지원한다. 다만 `exports`에 쓰인 조건(condition)이나 패턴에 따라 차이가 날 수 있으므로 아래 검증에서 배제하는 게 좋다.
- 환경 불일치는 별도의 위험 요소이므로 이번에 같이 정리할 만하다.

## 확인 방법 (추정 검증)
1. 로컬에서 `npm ls @company/ui`와 `node_modules/@company/ui/package.json`의 `version`을 확인한다. 1.4.0이면 3번 가설이 맞다.
2. 로컬에서 `rm -rf node_modules && npm ci`로 재설치한 뒤 빌드한다. CI와 같은 에러가 나면 원인이 확정된다.
3. 2.0.0의 `package.json`에서 `exports`에 `./button`이 있는지 확인한다. 없다면 변경 로그나 마이그레이션 문서에서 대체 경로를 찾는다.
4. 같은 재설치 상태에서 Node 18과 20으로 각각 빌드해 Node 버전 영향을 배제한다.

## 해결 방안
| 방안 | 내용 | 비고 |
|---|---|---|
| A. import 경로 수정 | 2.0.0이 노출하는 경로(예: 루트 import나 `@company/ui/components/button`)로 변경 | 권장 |
| B. 패키지 수정 | `@company/ui`에 `"./button"` subpath를 `exports`에 추가해 재배포 | 다른 사용처도 영향받는 경우 |
| C. 1.4.0으로 롤백 | 임시 조치 | 근본 해결 아님 |

## 재발 방지
- 로컬에서도 `npm ci`로 설치해 lock 파일과 실제 설치본을 일치시킨다.
- `.nvmrc`나 `engines`로 Node 버전을 CI와 로컬에서 통일한다.
- 메이저 버전 업그레이드 PR은 클린 설치 후 빌드한 결과를 확인하고 머지한다.
