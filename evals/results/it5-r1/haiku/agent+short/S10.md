## 결론

CI에서만 실패하는 원인은 2.0.0에 새로 추가된 `exports` 필드일 가능성이 가장 크다. 2.0.0에서 `./button` 하위 경로가 `exports`에 없으면 import가 막힌다. 로컬은 3일 전에 설치한 `node_modules`에 남은 1.4.0을 쓰고 있어서 이 문제가 드러나지 않는다. 이 결론은 추론이며 아직 확인하지 않았다.

## 확인된 사실

- 2.0.0에 `exports` 필드가 추가되었다.
- 로컬 `node_modules`는 3일 전보다 먼저 설치되었다.
- CI는 Node 18을, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`의 해시다.

## 추론

1. lock 파일이 2.0.0을 가리키면 CI는 2.0.0을 설치한다.
2. 2.0.0의 `exports`가 `./button`을 노출하지 않으면 Node의 모듈 해석이 하위 경로 import를 차단한다.
3. 로컬은 설치 시점상 1.4.0을 쓰므로 같은 import가 통과한다.

에러 문구 `Cannot find module`만으로는 원인을 단정할 수 없다. `exports` 차단과 파일 경로 불일치가 비슷한 문구를 낼 수 있다. 전체 CI 로그에서 실제 오류 코드를 확인해야 한다.

## 가능성이 낮은 원인

- Node 18과 20의 차이: `exports` 자체는 Node 18에서도 지원된다. 다만 Next.js 빌드 단계의 해석 방식 차이는 확인하지 않았다.
- 캐시 오염: 캐시 키가 lock 해시이므로 lock이 바뀌면 캐시가 새로 만들어진다. 단, lock 파일이 커밋되지 않았다면 이 판단은 달라진다. 확인 필요: lock 파일 변경 커밋 여부.

## 검증 순서

1. CI 로그에서 실제 설치된 `@company/ui` 버전을 확인한다.
2. 2.0.0 패키지의 `package.json`에서 `exports` 필드에 `./button` 경로가 있는지 확인한다.
3. 로컬에서 `node_modules`를 지우고 `npm ci`로 다시 설치한 뒤 Node 20으로 빌드한다. 재현되면 2.0.0의 `exports`가 원인일 가능성이 커진다.
4. 같은 방식으로 Node 18에서도 빌드해 Node 버전의 영향을 분리한다.

## 조치 제안 (검증 후 진행)

- import 경로를 `exports`에 노출된 경로로 바꾼다.
- 패키지 담당자에게 `./button` 경로를 `exports`에 추가해 달라고 요청한다.
- 급하면 `@company/ui`를 1.4.0으로 되돌린다.

이번 분석은 저장소와 CI 설정을 보지 않고 제공된 정보만으로 작성했다. 실행한 검사는 없다.
