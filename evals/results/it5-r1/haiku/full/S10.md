CI 실패의 가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드입니다. 이 설명은 아직 확인하지 않은 추론입니다.

`exports` 필드는 패키지가 외부에 공개한 경로만 import할 수 있게 제한합니다. 1.4.0에는 이 필드가 없어서 `@company/ui/button` 같은 내부 파일 경로를 자유롭게 import할 수 있었습니다. 2.0.0의 `exports`에 `./button`이 빠져 있다면 같은 import가 "Cannot find module"로 실패합니다. 에러 메시지와 이 설명이 일치합니다.

로컬과 CI의 차이는 다음과 같습니다.

| 항목 | 로컬 | CI |
|---|---|---|
| `@company/ui` 버전 | 3일 전 설치본, 1.4.0으로 추정 | lock 파일 기준 새로 설치, 2.0.0 |
| Node 버전 | 20 | 18 |
| 빌드 결과 | 성공 | 실패 |

로컬이 성공한 이유는 Node 버전이 아니라 3일 전에 설치된 `node_modules`가 그대로 남아 있기 때문으로 보입니다. 3일 전 이후 `npm install`을 다시 실행하지 않았다면 로컬은 여전히 1.4.0을 쓰고 있을 것입니다.

Node 18과 20은 모두 `exports`를 지원하므로, Node 버전 차이만으로 이 에러가 나는 가능성은 낮다고 봅니다. 캐시도 `package-lock.json` 해시가 키이므로 lock 변경 후 2.0.0 설치를 막지 않습니다. 다만 워크플로에 `restore-keys` 같은 대체 키가 있는지는 확인하지 않았습니다.

원인을 확정하려면 다음을 확인하십시오.

1. 로컬에서 `npm ls @company/ui`를 실행해 실제 설치 버전을 확인하십시오.
2. 2.0.0 패키지의 `package.json`을 열어 `exports` 필드에 `./button` 경로가 있는지 확인하십시오.
3. `rm -rf node_modules && npm ci`로 클린 설치한 뒤 Node 20과 Node 18에서 각각 빌드하십시오.

클린 설치 빌드가 Node 18에서만 실패하면 `exports` 원인이 확정됩니다. 두 Node 버전 모두 실패하면 `exports` 경로 문제를 우선 확인하고, 두 버전 모두 성공하면 CI 환경 차이를 다시 조사하십시오.
