## 결론

가장 유력한 원인은 `@company/ui` 2.0.0에 추가된 `exports` 필드가 `./button` 경로를 공개하지 않아서, 새로 설치한 환경에서 `@company/ui/button` import가 해석되지 않는 것이다. 로컬 빌드가 성공하는 이유는 3일 전에 설치한 `node_modules`에 1.4.0이 남아 있어 `exports` 제한이 없기 때문으로 추정한다. 이 원인은 아직 패키지 내용으로 확인하지 않았다.

## 확인된 사실

- CI에서만 `Error: Cannot find module '@company/ui/button'` 에러로 빌드가 실패한다.
- 로컬 빌드는 성공한다.
- 3일 전에 `@company/ui`를 1.4.0에서 2.0.0으로 올렸다.
- 2.0.0에 `exports` 필드가 추가되었다.
- CI는 Node 18, 로컬은 Node 20을 쓴다.
- CI 캐시 키는 `package-lock.json`의 해시다.
- 로컬 `node_modules`는 업그레이드 3일 전에 설치되었다.

## 추론

1. `exports` 필드가 있으면 패키지가 공개한 경로만 import할 수 있다. `exports`에 `./button`이 없으면 `@company/ui/button`은 해석되지 않으며, 이때 위와 같은 에러가 발생한다.
2. 로컬 `node_modules`에는 1.4.0이 남아 있을 가능성이 높다. 1.4.0에는 `exports` 제한이 없으므로 같은 import가 성공한다.
3. `package-lock.json`이 업그레이드 커밋에 포함되었다면 해시가 바뀌어 CI 캐시가 무효화되고, CI는 2.0.0을 새로 설치한다. 그래서 CI에서만 실패가 드러난다.
4. Node 18과 Node 20의 차이는 `exports` 해석의 차이로 보기 어렵다. 두 버전 모두 `exports`를 지원한다. 다만 CI와 로컬의 npm 버전 차이로 lock 파일 해석이 달라질 가능성은 남아 있다.

## 미확인 항목

- 2.0.0 `package.json`의 `exports`에 `./button`이 있는지 확인하지 않았다.
- 로컬 `node_modules`에 설치된 실제 버전을 확인하지 않았다.
- `package-lock.json`이 업그레이드 커밋에 포함되었는지 확인하지 않았다.
- CI 캐시 설정에 이전 키를 복원하는 `restore-keys`가 있는지 확인하지 않았다.

## 검증 방법

1. 로컬에서 `node_modules`를 삭제하고 `npm ci`를 실행한 뒤 빌드한다. 실패하면 로컬 성공은 오래된 설치 상태 때문이다.
2. `node_modules/@company/ui/package.json`의 `version` 값을 확인한다.
3. 같은 파일의 `exports` 항목에 `./button`이 있는지 확인한다.
4. CI 로그에서 실제로 설치된 `@company/ui` 버전을 확인한다.
5. Node 18 환경에서 1번을 다시 실행해 Node 버전의 영향을 분리한다.

## 조치 방향

- import 경로를 2.0.0이 공개한 경로로 바꾼다. 2.0.0 문서나 `exports` 항목을 기준으로 한다.
- 또는 `@company/ui` 쪽 `exports`에 `./button`을 추가하는 수정을 요청한다. 이는 해당 패키지 담당 팀과 협의가 필요하다.
- 캐시 키에 설치된 패키지 버전이 반영되지 않는다면 같은 문제가 다시 발생할 수 있으므로 캐시 설정도 함께 점검한다.

## PM 관점 확인 사항

- 현재 CI가 막혀서 배포 파이프라인이 중단되었는지 확인 필요: 배포 일정에 영향이 있는지 파악해야 한다.
- 2.0.0 변경 내용에 공개 경로 변경이 명시되어 있었는지 확인 필요: 같은 종류의 문제가 다른 프로젝트에서도 발생할 수 있다.
