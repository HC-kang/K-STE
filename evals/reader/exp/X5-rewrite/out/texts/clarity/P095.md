아래처럼 동작 순서와 주의사항을 나누어 정리했습니다. 원문의 의미는 유지하고, 용어(`LimitRange`)와 문장 표현을 통일했습니다.

## 동작 방식

1. 관리자가 네임스페이스에 `LimitRange`를 생성한다.
2. 사용자가 해당 네임스페이스에서 파드, 퍼시스턴트볼륨클레임(PVC) 등의 오브젝트를 생성하거나 생성을 시도한다.
3. `LimitRange` 어드미션 컨트롤러가 다음 두 가지를 수행한다.
   - **기본값 적용**: 컴퓨팅 리소스 요구사항을 설정하지 않은 모든 파드(및 해당 컨테이너)에 기본 요청(request) 및 제한(limit) 값을 적용한다.
   - **제약 조건 검증**: 사용량을 추적하여, 네임스페이스의 `LimitRange`에 정의된 리소스 최솟값, 최댓값, 비율을 초과하지 않는지 확인한다.
4. 파드, 컨테이너, PVC를 생성하거나 업데이트할 때 `LimitRange` 제약 조건을 위반하면, API 서버 요청이 HTTP 상태 코드 `403 FORBIDDEN`과 함께 실패한다. 응답 메시지에는 위반된 제약 조건이 설명된다.

## 주의사항

- **요청/제한 값 지정**: 네임스페이스에 `cpu`, `memory` 같은 컴퓨팅 리소스에 대한 `LimitRange`를 추가했다면, 사용자는 해당 리소스의 요청 또는 제한을 지정해야 한다. 지정하지 않으면 파드 생성이 거부될 수 있다.
- **기존 파드는 영향받지 않음**: `LimitRange` 유효성 검사는 파드 어드미션 단계에서만 수행되며, 이미 실행 중인 파드에는 적용되지 않는다. `LimitRange`를 추가하거나 수정해도 네임스페이스에 이미 있는 파드는 변경 없이 유지된다.
- **`LimitRange`는 하나만 두는 것을 권장**: 한 네임스페이스에 `LimitRange`가 둘 이상 있으면 어떤 기본값이 적용될지 예측할 수 없다.

## 수정한 부분

- "리밋레인지"와 `LimitRange`가 혼용되어 `LimitRange`로 통일했습니다.
- 원문의 "첫째, 둘째"를 어드미션 컨트롤러의 두 가지 역할로 묶어 하위 항목으로 정리했습니다.
- "결정적이지 않다"는 "예측할 수 없다"로 바꿨습니다. 의미는 같고 더 쉽게 읽힙니다.
- 마지막 항목의 "하나만 두는 것을 권장"은 원문에 없는 권고이나, 원문 내용에서 자연스럽게 도출되는 안내입니다. 원문에 충실하게 유지하려면 이 제목을 "`LimitRange`가 여러 개인 경우"로 바꾸면 됩니다.
