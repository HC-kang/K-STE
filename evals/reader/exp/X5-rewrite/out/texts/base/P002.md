쿠버네티스의 서비스(Service) API는 파드 그룹을 네트워크를 통해 노출하는 추상화입니다. 각 서비스 오브젝트는 엔드포인트의 논리적 집합(일반적으로 파드)과 해당 파드에 접근하는 정책을 함께 정의합니다.

예를 들어, 3개의 레플리카로 실행되는 스테이트리스 이미지 처리 백엔드를 생각해 봅시다. 이 레플리카들은 서로 대체할 수 있어서, 프론트엔드는 어떤 백엔드를 사용하는지 신경 쓰지 않습니다. 백엔드 세트를 구성하는 실제 파드가 바뀌더라도 프론트엔드 클라이언트는 이를 알 필요가 없고, 백엔드 세트 자체를 추적할 필요도 없습니다. 서비스 추상화가 이러한 디커플링(decoupling)을 가능하게 합니다.

서비스가 대상으로 하는 파드 집합은 보통 사용자가 정의한 셀렉터(selector)로 결정됩니다. 서비스 엔드포인트를 정의하는 다른 방법은 _셀렉터가 없는_ 서비스를 참고하세요.

워크로드가 HTTP를 사용한다면 인그레스(Ingress)로 웹 트래픽이 워크로드에 도달하는 방식을 제어할 수 있습니다. 인그레스는 서비스 타입은 아니지만 클러스터의 진입점 역할을 합니다. 라우팅 규칙을 하나의 리소스로 통합할 수 있어서, 클러스터 안에서 개별적으로 실행되는 워크로드의 여러 컴포넌트를 단일 리스너 뒤에서 노출할 수 있습니다.

쿠버네티스용 게이트웨이(Gateway) API는 인그레스와 서비스를 넘어서는 추가 기능을 제공합니다. 게이트웨이는 커스텀 리소스 데피니션(CustomResourceDefinition)으로 구현된 확장 API 집합입니다. 클러스터에 추가한 뒤, 클러스터에서 실행 중인 네트워크 서비스에 대한 접근을 구성하는 데 사용할 수 있습니다.

**주요 변경 사항**
- 어색한 줄바꿈과 끊긴 문장을 정리하고, "~이다" 체를 "~합니다" 체로 통일했습니다.
- 긴 문장을 나누고, 흩어져 있던 "서비스 추상화는 이러한 디커플링을 가능하게 한다"를 앞 문단에 합쳤습니다.
- "커스텀리소스데피니션" 같은 붙여 쓴 표현은 띄어 쓰고, 주요 용어에는 영문을 병기했습니다.

원문의 "~이다" 체를 유지하길 원하시면 말씀해 주세요.
