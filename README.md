# K-STE

K-STE는 AI가 쓰는 한국어 업무 글을 개발자와 비개발자가 한 번에 이해하게 만드는 Agent Skill이다. ASD-STE100(항공 정비 문서용 통제 언어)의 원칙을 한국어 업무 글에 맞게 옮겼다. 목표는 독자가 잘못 읽을 수 없는 글이다. 글을 짧게 만드는 것은 목표가 아니다. 그래서 전문용어를 일상어로 바꾸지 않는다. 대신 단어마다 뜻을 하나로 정하고, 의무 강도와 작업 상태를 정해진 말로 쓴다.

같은 모델(Claude Sonnet)에 같은 사실을 주고 Slack 장애 공유 메시지를 쓰게 한 결과다. 두 출력은 평가 기록의 원본을 그대로 옮겼다.

## 설치와 적용

규칙은 두 방법으로 적용한다. 상시 적용은 모든 답변에 기본 문체로 적용하는 방법이다. 스킬은 재작성과 검수 요청에 자세한 절차를 적용하는 방법이다. 스킬은 모델이 필요하다고 판단할 때만 실행된다. 그래서 상시 적용은 지침 파일에 짧은판을 넣어서 처리한다.

| 환경 | 상시 적용 | 재작성·검수 |
|---|---|---|
| Claude Code, Codex, Cursor | `CLAUDE.md`나 `AGENTS.md`에 짧은판을 붙인다 | `npx skills add HC-kang/K-STE`로 스킬을 설치한다 |
| Claude.ai | 설정의 개인 선호(personal preferences)에 짧은판을 붙인다 | `skills/k-ste` 폴더를 zip으로 묶어 스킬로 올린다. 또는 프로젝트 지침에 전체판을 붙인다 |
| ChatGPT | 맞춤 지침에 짧은판을 붙인다 | 프로젝트 지침이나 GPT 지침에 전체판을 붙인다 |
| Gemini | 저장된 정보에 짧은판을 붙인다 | Gem 지침에 전체판을 붙인다 |
| Slack 봇, API 호출 | 시스템 프롬프트에 전체판을 넣는다 | 같은 전체판이 처리한다 |

짧은판(1,500자 이하)과 전체판(약 5,700자)은 [`prompts/system-prompt.md`](prompts/system-prompt.md)에 있다. 짧은판에는 검수 표 형식이 없다. 1,500자 한도 때문에 K15와 K13의 완료 동사 규칙도 짧은판에는 없다. 짧은판에 날짜 규칙을 넣은 후보는 독자 패널에서 날짜 오독을 줄였지만, 지금의 짧은판과 같은 실행에서 번갈아 잰 시나리오 평가에서 사전 기준을 통과하지 못해서 넣지 않았다([`evals/results/NOTES.md`](evals/results/NOTES.md) 22-26차). 짧은판만 쓰면 재작성의 뜻 보존도 약하다(아래 평가 참고). 그래서 재작성과 검수는 스킬이나 전체판으로 한다.

코딩 에이전트에서는 스킬과 짧은판을 함께 쓰는 구성을 권장한다. 짧은판의 12번 규칙이 재작성과 검수 요청을 스킬로 넘긴다.

팀 용어집은 지침 파일(`CLAUDE.md`, `AGENTS.md`)이나 시스템 프롬프트에 본문으로 넣는다. 29차(S23)에서 메모가 용어집이 금지한 말("테넌트", "릴리스")을 쓸 때, 용어집 본문을 `CLAUDE.md`에 넣은 구성은 그 말을 0/20회 썼다. 시스템 프롬프트에 넣은 구성은 base 0/20, full 1/20이었다. `CLAUDE.md`에 용어집 파일의 경로만 적으면 7/20, 저장소에 파일로만 두면 20/20이었다. 파일로만 둔 구성은 20회 모두 파일을 읽지 않았다. 그래서 K-STE 규칙에는 용어집 문장을 넣지 않았다.

## 사용법

- 쓰기: 따로 요청하지 않아도 규칙대로 쓴다.
- 재작성: "이 글 쉽게 바꿔줘", "다듬어줘", "줄여줘"라고 요청한다. 고친 글만 나온다. 원문이 두 가지로 읽히는 곳은 고치지 않고 `확인 필요:`로 묻는다.
- 검수: "이 글 검사해줘"라고 요청한다. `| 규칙 | 원문 | 고친 글 |` 표가 나온다.

## 규칙

K0이 다른 모든 규칙보다 우선한다. 전체 규칙과 예문은 [`skills/k-ste/SKILL.md`](skills/k-ste/SKILL.md)에 있다.

| ID | 규칙 |
|---|---|
| K0 | 의미를 보존한다. 사실을 더하지 않고, 조건, 범위, 한정어, 인과 관계, 확신 정도, 의무 강도를 바꾸지 않는다. 두 가지로 읽히는 곳은 고르지 않는다. |
| K1 | 답변은 결론을 첫 문장에 쓴다. |
| K2 | 한 문장에 정보 하나를 쓴다. 문장을 나눌 때 조건과 접속 관계를 이어 쓴다. |
| K3 | 주어, 조사, 어미를 생략하지 않는다. 명사로 끝내지 않는다. |
| K4 | 같은 대상과 같은 동작에는 같은 단어를 쓴다. 새 글에서 앞의 대상은 "해당" 대신 이름으로 다시 가리킨다. |
| K5 | 능동형으로 쓰고 이중 피동을 쓰지 않는다. |
| K6 | 사실, 추론, 미확인을 구분한다. |
| K7 | 조건을 동작 앞에 쓴다. |
| K8 | 비개발자 독자에게는 어려운 용어를 처음 나올 때 풀이한다. |
| K9 | 서두, 맺음 제안, 근거 없는 평가어를 쓰지 않는다. |
| K10 | 줄글이 기본이다. 볼드는 경고에만 쓰고, 이모지와 엠대시를 쓰지 않는다. |
| K11 | 답변은 합니다체, 문서는 한다체로 쓴다. 한 글에서 섞지 않는다. |
| K12 | 새 글의 규정과 요구사항은 정해진 형태로 쓴다. 요구는 "해야 한다", 금지는 "하면 안 된다", 권고는 "권장한다", 허락은 "해도 된다", 의무 없음은 "하지 않아도 된다", 가능은 "할 수 있다"다. |
| K13 | 새 글에서 "처리", "확인", "반영", "완료", "적용", "조치", "대응", "정상"은 무엇을 어디에 했는지 붙여 쓴다. "마쳤다", "끝냈다"를 쓸 때 결과가 사실에 있으면 바로 결과를 쓴다. 재작성에서는 바꾸지 않고, 가리키는 대상에 따라 독자의 행동이 달라질 때만 묻는다. |
| K14 | 새 글에서 수치나 기준이 있으면 "안정적", "원활" 같은 판정어 대신 수치와 기준을 쓴다. |
| K15 | 날짜는 그때 하는 일(실행일)과 그때까지 끝낼 일(기한)을 구분해서 쓴다. 둘을 "~부터 ~까지" 하나의 기간으로 묶어 요약하지 않는다. 사실이 둘 중 무엇인지 밝히지 않은 날짜는 한쪽으로 정하지 않고 묻는다. 밝힌 날짜는 묻지 않는다. |

## 평가

[`evals/`](evals/)에 시나리오 23개, 결함 계수기, 블라인드 판정기, 실행 기록이 있다. 생성 모델은 Claude Sonnet과 Claude Haiku이고, 판정 모델은 Claude Opus다. 각 실행은 사용자 설정을 읽지 않는 격리 세션에서 했다.

| 조건 | 설명 |
|---|---|
| base | 규칙 없음 |
| short | 시스템 프롬프트에 짧은판 (웹 채팅과 같은 구성) |
| full | 시스템 프롬프트에 전체판 (사내 자동화와 같은 구성) |
| agent+short | Claude Code에 스킬 설치, `CLAUDE.md`에 짧은판 (권장 로컬 구성) |

아래 표는 지금 배포하는 규칙(`bbb5228`)을 한 실행(30차)에서 잰 값이다. base가 적용 전이고, 나머지 세 조건이 적용 후다. 조건마다 시나리오 S1-S19를 모델별 3회 실행했다. S12, S13, S15-S18의 예정일과 기한은 실행일(2026-10-28)보다 앞선 날짜가 됐다. 그래서 이 여섯 시나리오는 날짜만 10-14일 뒤로 미룬 사본으로 쟀다(아래 "이 결과를 읽을 때" 참고).

| 지표 | base (적용 전) | short | full | agent+short |
|---|---:|---:|---:|---:|
| 어휘 통제 시나리오 통과 (S11-S15) | 6/30 | 25/30 | 29/30 | 29/30 |
| 목록 밖 모호어 시나리오 통과 (S16) | 0/6 | 5/6 | 6/6 | 4/6 |
| 완료 동사 시나리오 통과 (S17) | 0/6 | 6/6 | 6/6 | 6/6 |
| 실행일과 기한 시나리오 통과 (S18, S19) | 5/12 | 10/12 | 11/12 | 12/12 |
| 재작성에서 뜻이 바뀌지 않음 (S5-S7) | 1/18 | 14/18 | 18/18 | 17/18 |
| 답변의 첫 문장이 결론 (S1, S2, S10) | 2/18 | 18/18 | 17/18 | 18/18 |
| 독자가 보는 결함, 실행 1회당 (Haiku, S1-S10) | 88.7 | 5.0 | 2.3 | 2.3 |
| 독자가 보는 결함, 실행 1회당 (Sonnet, S1-S10) | 62.7 | 4.0 | 1.0 | 2.7 |
| 홍보 문구 요청에 범위 밖이라고 알림 (S8) | 0/6 | 0/6 | 6/6 | 0/6 |
| 검수 요청에 표와 실제 규칙 ID로 답함 (S9) | 0/6 | 0/6 | 6/6 | 6/6 |
| 재작성·검수 요청에 스킬 실행 | - | - | - | 30/30 |

어휘 통제 시나리오는 다음과 같다.

| ID | 확인하는 것 |
|---|---|
| S11 | 사내 지침 문서에서 요구, 금지, 권고, 허락, 의무 없음, 가능을 서로 다른 형태로 쓰는가 |
| S12 | 압축된 작업 메모를 보고할 때 병합, 스테이징 배포, 운영 배포의 차이를 "반영", "완료"로 흐리지 않는가 |
| S13 | 부하 테스트 결과를 "안정적" 같은 판정어 대신 수치와 기준으로 쓰는가 |
| S14 | "조치", "정상화", "해당 문서"를 재작성할 때 지어내지 않고 묻는가 |
| S15 | 서버와 설정이 둘 이상인 회의록에서 "해당", "이"로 대상을 흐리지 않고, 실행일을 기한으로 쓰지 않는가 |
| S16 | 규칙 목록에 없는 "검토", "마무리", "개선" 같은 말로 결과를 흐리지 않는가 |
| S17 | "이관 끝남" 같은 메모를 결과 없이 "마쳤습니다"로 보고하지 않는가 |
| S18 | 교육일, 업데이트일(실행일)과 설문, 비밀번호 변경(기한)을 구분하고, 기한을 기간의 끝으로 묶지 않는가 |
| S19 | S18과 같은 유형을 다른 분야(프로젝트 일정 메일)로 재는가 |

독자가 보는 결함은 `evals/score.py`가 센다. 볼드 남용, 엠대시, 짧은 섹션 헤더, 이모지, 서두와 맺음 제안, 명사로 끝나는 목록 항목, 이중 피동, 문체 혼용이 포함된다. 뜻 보존, 결론 위치, S11-S19 통과는 `evals/judge.py`가 블라인드로 판정한다.

이 결과를 읽을 때 다음을 함께 본다.

- 칸마다 6-30회로 잰 값이다. 같은 규칙에서도 차수마다 결과가 흔들린다. 바꾸지 않은 짧은판도 16차와 18차 사이에 S11이 6/6에서 4/6으로, Sonnet 결함이 4.0에서 7.0으로 바뀌었다. 그래서 한 차수의 1-3점 차이로 결론을 내리지 않는다.
- S11-S15는 규칙의 단어 목록과 같은 단어로 만들었다. 목록 밖 단어로 만든 S16은 어휘 통제 규칙을 넣기 전의 규칙도 5/6-6/6을 통과했다(9차). 그래서 S16의 base와의 차이를 단어 목록이 일반화된 근거로 보지 않는다.
- S17(완료 동사)은 K13의 완료 동사 규칙을 넣기 전의 규칙도 모두 통과했다(17차). 그래서 S17의 base와의 차이를 그 규칙의 효과로 보지 않는다.
- 규칙의 대상 단어("정상", "완료", "확인")가 S7 원문에 들어 있다. 그래서 S5-S7은 회귀 확인으로만 쓰고, 개선의 근거로 쓰지 않는다.
- 표의 S5-S7은 18회로 잰 값이다. 지금 규칙을 40회씩 잰 29차의 S5-S7 판정 통과는 full 102/120, agent+short 110/120이었다.
- 남은 가장 큰 실패는 S7("최대한 짧게 줄여줘")의 두 번째 절 주어 탈락이다. 조건절에서 "백업이"를 뺀 출력(글자 기준)은 29차에서 full 10/40, agent+short 5/40이었다. 30차에서는 short 5/6, full 0/6, agent+short 0/6이었다. 판정기는 short의 5개 중 2개만 실패로 봤다. 그다음은 메모에 없는 행위자를 더하는 실패다. 30차 S16에서 "개발팀은"처럼 행위자를 더한 출력은 short 1회, agent+short 2회였다.
- 판정 기준을 여러 번 고쳤다. S11은 같은 문장을 다르게 판정해서, S18은 기간 요약 기준이 S19에만 있어서 고쳤다. 고칠 때마다 비교하던 두 규칙의 출력을 모두 다시 판정했다.
- Claude Code는 `--system-prompt`로 시스템 프롬프트를 바꿔도 실행일을 모델에 알린다. 원래 날짜로 잰 30차의 S12, S13, S15-S18에서는 적용 후 조건이 "10/21(수)은 오늘(10/28)보다 앞선 날짜입니다" 같은 "확인 필요" 줄을 썼다. 판정기는 이 줄을 메모에 없는 사실로 보고 실패로 셌다. 그래서 여섯 시나리오의 통과는 원래 날짜에서 base 13/36, short 12/36, full 17/36, agent+short 16/36이었고, 날짜를 미룬 사본에서 6/36, 29/36, 34/36, 33/36이었다. 저장소의 시나리오는 바꾸지 않았다. 이 여섯 시나리오는 [`evals/results/it30-prompt/run-dates.sh`](evals/results/it30-prompt/run-dates.sh)처럼 날짜를 실행일 뒤로 미룬 사본으로 재야 한다.
- 경계 표현에는 규칙을 더하지 않았다. 29차에서 사실의 경계("25MB를 넘으면", "만 19세가 안 된")를 기준값에서 다르게 읽히게 쓴 출력은 full과 agent+short 각 0/20, base 2/20(S21)이었다. 밝히지 않은 경계("7일 안에", "10월 31일 이후")를 한쪽으로 정한 출력은 세 조건 모두 0/20이었다(S22). full 1/20은 밝힌 경계("20명이 되면")를 열린 것으로 물었다.

규칙을 고칠 때는 같은 실행에서 고치기 전 규칙과 번갈아 재서, 실행 전에 정한 기준으로 판정해야 한다. 기준값을 다른 날의 차수에서 가져오면 안 된다. 같은 규칙도 18차와 21차 사이에 short S15가 6/6에서 4/6으로, full S18이 6/6에서 3/6으로 움직였다. SKILL.md 본문은 6,478자를 넘으면 안 된다. 규칙을 더하면 같은 경로에서 같은 글자 수를 빼야 한다.

자세한 기록과 각 차수의 실패, 수정 이유는 [`evals/results/NOTES.md`](evals/results/NOTES.md)에 있다.

### 독자 패널 평가

[`evals/reader/`](evals/reader/)는 다른 회사의 모델(Grok, Codex)을 독자로 써서 이해도를 객관식으로 잰다. 문항은 Codex가 글을 쓰기 전에 사실 목록이나 원문으로 만들었고, 채점은 기계로 한다. 사전 등록, 측정 도구 검증, 결과는 [`evals/reader/README.md`](evals/reader/README.md)에 있다.

| 지표 | base | clarity | short | full |
|---|---:|---:|---:|---:|
| 새 글, 전체 읽기 정답률 (Grok, 280문항 × 2) | 99.5% | 99.3% | 99.3% | 99.5% |
| 새 글, 앞 250자만 읽은 정답률 (Haiku) | 10.7% | 10.5% | 17.1% | 18.6% |
| 새 글, 평균 길이 | 1,298자 | 1,333자 | 971자 | 911자 |
| 다듬기, 전체 읽기 정답률 (Grok, 원문 120/120) | 118/120 | 118/120 | 116/120 | 118/120 |
| 다듬기, 뜻을 말없이 바꿔 틀린 문항 | 2 | 2 | 0 | 0 |
| 다듬기, "확인 필요" 때문에 E를 고른 문항 | 0 | 0 | 4 | 2 |

clarity는 "명확하고 오해 없게 쓴다" 한 줄 지시다. 전체 읽기에서는 모든 조건이 천장이어서 K-STE의 이해도 이득이 측정되지 않았다. K-STE의 이득은 밀도(같은 사실을 더 적은 글자로 쓴다)에서, 비용은 "확인 필요"에서 나왔다. 앞부분 읽기의 차이도 대부분 밀도로 설명된다. 천장을 깨려는 후속 실험 11개의 결과는 [`evals/reader/exp/README.md`](evals/reader/exp/README.md)에 있다. 오독으로 천장이 깨진 실험은 입력 메모가 흐린 세 실험(X1 빈칸, X7 흐린 날짜, X8 흐린 대상)이다. 세 실험 모두 오독은 글쓴이가 메모에 없는 내용을 정한 곳에서 나왔다. X1에서 빈칸을 묻는 문항의 오독률은 base 28.8%, full 15.9%였다(차이 -13.2%p, 95% 신뢰구간 -22.6%p에서 -4.9%p). X8에서 대상 함정 문항의 오독률은 base 15.8%, full 6.7%였다(-8.5%p, -17.7%p에서 0.0%p). 이 차이는 사전 기준으로는 유의하지 않다. "명확하게 써라" 한 줄 지시는 두 실험 모두에서 차이를 만들지 못했다. X1의 글을 보기 없이 읽혀도 결과는 같은 방향이었다(빈칸 문항 오독률 base 45.5%, full 23.5%, 차이 -22.6%p, -33.7%p에서 -12.5%p). X7에서는 메모가 실행일인지 기한인지 밝히지 않은 날짜를 짧은판과 전체판이 base보다 더 많이 한쪽으로 정했다(오독률 base 38.9%, short 84.9%, full 63.5%). 그래서 전체판과 스킬의 K15에 "밝히지 않은 날짜는 한쪽으로 정하지 않고 묻는다"와 "밝힌 날짜는 묻지 않는다"를 더했다. 같은 날 잰 전체판의 날짜 빈칸 문항 오독률은 이 두 문장을 넣기 전 63.2%, 넣은 뒤 14.7%였다(X10 새 메모와 X12, Grok 136개). 분명한 날짜 문항의 정답률 차이는 0.0%p(-2.0%p에서 2.0%p)였다. 대상 함정 문항의 오독은 메모 72개로 잰 X14에서 2.49%p 줄었다(-4.63%p에서 -0.29%p). 짧은판에는 이 문장을 넣지 않았다. 짧은판 후보는 독자 패널을 통과했지만 시나리오 평가의 사전 기준을 통과하지 못했다.

## 한계

- K-STE는 공인 표준이 아니다. ASD-STE100을 번역한 것도 아니다.
- 전체판의 지시문 20어절, 설명문 25어절 기준에는 한국어 근거가 없다. 그래서 검토 신호로만 쓴다. 스킬에서는 27차에 지웠다.
- 판정자도 Claude다. 사람이 만든 정답과 대조하지 않았다.
- 시나리오는 23개이고 한 사람이 만들었다.
- `agent+short`는 Claude Code 기본 시스템 프롬프트를 쓰므로 다른 조건과 직접 비교할 수 없다.
- 홍보 문구, 창작 글, 영어 글에는 적용하지 않는다.
