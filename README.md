# K-STE

K-STE는 AI가 쓰는 한국어 업무 글을 개발자와 비개발자가 한 번에 이해하게 만드는 Agent Skill이다. ASD-STE100(항공 정비 문서용 통제 언어)의 원칙을 한국어 업무 글에 맞게 옮겼다. 목표는 독자가 잘못 읽을 수 없는 글이다. 글을 짧게 만드는 것은 목표가 아니다. 그래서 전문용어를 일상어로 바꾸지 않는다. 대신 단어마다 뜻을 하나로 정하고, 의무 강도와 작업 상태를 정해진 말로 쓴다.

같은 모델(Claude Sonnet)에 같은 사실을 주고 Slack 장애 공유 메시지를 쓰게 한 결과다. 두 출력은 평가 기록의 원본을 그대로 옮겼다.

## 설치와 적용

규칙은 두 방법으로 적용한다. 상시 적용은 모든 답변에 기본 문체로 적용하는 방법이다. 스킬은 재작성과 검수 요청에 자세한 절차를 적용하는 방법이다. 스킬은 모델이 필요하다고 판단할 때만 실행된다. 그래서 상시 적용은 지침 파일에 짧은판을 넣어서 처리한다.

| 환경 | 상시 적용 | 재작성·검수 |
|---|---|---|
| Claude Code, Codex, Cursor | `CLAUDE.md`나 `AGENTS.md`에 짧은판을 붙인다 | `npx skills add HC-kang/K-STE`로 스킬을 설치한다 |
| Claude.ai | 설정의 개인 선호(personal preferences)에 짧은판을 붙인다 | `skills/k-ste` 폴더를 zip으로 묶어 스킬로 올린다. 또는 프로젝트 지침에 전체판을 붙인다 |
| ChatGPT | 맞춤 지침에 짧은판을 붙인다 | 프로젝트 지침이나 GPT 지침에 전체판을 붙인다 |
| Gemini | 저장된 정보에 짧은판을 붙인다 | Gem 지침에 전체판을 붙인다 |
| Slack 봇, API 호출 | 시스템 프롬프트에 전체판을 넣는다 | 같은 전체판이 처리한다 |

짧은판(1,500자 이하)과 전체판(약 5,100자)은 [`prompts/system-prompt.md`](prompts/system-prompt.md)에 있다. 짧은판에는 검수 표 형식이 없다. 짧은판만 쓰면 재작성의 뜻 보존도 약하다(아래 평가 참고). 그래서 재작성과 검수는 스킬이나 전체판으로 한다.

코딩 에이전트에서는 스킬과 짧은판을 함께 쓰는 구성을 권장한다. 짧은판의 12번 규칙이 재작성과 검수 요청을 스킬로 넘긴다.

## 사용법

- 쓰기: 따로 요청하지 않아도 규칙대로 쓴다.
- 재작성: "이 글 쉽게 바꿔줘", "다듬어줘", "줄여줘"라고 요청한다. 고친 글만 나온다. 원문이 두 가지로 읽히는 곳은 고치지 않고 `확인 필요:`로 묻는다.
- 검수: "이 글 검사해줘"라고 요청한다. `| 규칙 | 원문 | 고친 글 |` 표가 나온다.

## 규칙

K0이 다른 모든 규칙보다 우선한다. 전체 규칙과 예문은 [`skills/k-ste/SKILL.md`](skills/k-ste/SKILL.md)에 있다.

| ID | 규칙 |
|---|---|
| K0 | 의미를 보존한다. 사실을 더하지 않고, 조건, 범위, 한정어, 인과 관계, 확신 정도, 의무 강도를 바꾸지 않는다. 두 가지로 읽히는 곳은 고르지 않는다. |
| K1 | 답변은 결론을 첫 문장에 쓴다. |
| K2 | 한 문장에 정보 하나를 쓴다. 문장을 나눌 때 조건과 접속 관계를 이어 쓴다. |
| K3 | 주어, 조사, 어미를 생략하지 않는다. 명사로 끝내지 않는다. |
| K4 | 같은 대상과 같은 동작에는 같은 단어를 쓴다. 새 글에서 앞의 대상은 "해당" 대신 이름으로 다시 가리킨다. |
| K5 | 능동형으로 쓰고 이중 피동을 쓰지 않는다. |
| K6 | 사실, 추론, 미확인을 구분한다. |
| K7 | 조건을 동작 앞에 쓴다. |
| K8 | 비개발자 독자에게는 어려운 용어를 처음 나올 때 풀이한다. |
| K9 | 서두, 맺음 제안, 근거 없는 평가어를 쓰지 않는다. |
| K10 | 줄글이 기본이다. 볼드는 경고에만 쓰고, 이모지와 엠대시를 쓰지 않는다. |
| K11 | 답변은 합니다체, 문서는 한다체로 쓴다. 한 글에서 섞지 않는다. |
| K12 | 새 글의 규정과 요구사항은 정해진 형태로 쓴다. 요구는 "해야 한다", 금지는 "하면 안 된다", 권고는 "권장한다", 허락은 "해도 된다", 의무 없음은 "하지 않아도 된다", 가능은 "할 수 있다"다. |
| K13 | 새 글에서 "처리", "확인", "반영", "완료", "적용", "조치", "대응", "정상"은 무엇을 어디에 했는지 붙여 쓴다. 재작성에서는 바꾸지 않고, 가리키는 대상에 따라 독자의 행동이 달라질 때만 묻는다. |
| K14 | 새 글에서 수치나 기준이 있으면 "안정적", "원활" 같은 판정어 대신 수치와 기준을 쓴다. |

## 평가

[`evals/`](evals/)에 시나리오 15개, 결함 계수기, 블라인드 판정기, 실행 기록이 있다. 생성 모델은 Claude Sonnet과 Claude Haiku이고, 판정 모델은 Claude Opus다. 각 실행은 사용자 설정을 읽지 않는 격리 세션에서 했다.

| 조건 | 설명 |
|---|---|
| base | 규칙 없음 |
| short | 시스템 프롬프트에 짧은판 (웹 채팅과 같은 구성) |
| full | 시스템 프롬프트에 전체판 (사내 자동화와 같은 구성) |
| agent+short | Claude Code에 스킬 설치, `CLAUDE.md`에 짧은판 (권장 로컬 구성) |

v1은 어휘 통제 규칙(K12-K14)을 넣기 전의 규칙이고, v2는 지금 규칙이다. v2 수치는 모두 15차 측정이다. v1 수치의 출처는 지표마다 다르다. 결함과 결론 위치는 6차, 재작성 뜻 보존은 8차, S11-S16은 9차(v1 커밋으로 다시 실행) 결과다. 각 조건은 모델별 3회 실행했고, 기준선(base)은 모델별 2회 실행했다.

| 지표 | base | short (v1 → v2) | full (v1 → v2) | agent+short (v1 → v2) |
|---|---:|---:|---:|---:|
| 어휘 통제 시나리오 통과 (S11-S15) | 3/20 | 24/30 → 25/30 | 22/30 → 28/30 | 20/30 → 26/30 |
| 목록 밖 모호어 시나리오 통과 (S16) | 0/4 | 6/6 → 5/6 | 6/6 → 6/6 | 5/6 → 5/6 |
| 재작성에서 뜻이 바뀌지 않음 (S5-S7) | 0/12 | 11/18 → 11/18 | 15/18 → 15/18 | 16/18 → 17/18 |
| 답변의 첫 문장이 결론 (S1, S2, S10) | 0/12 | 18/18 → 18/18 | 17/18 → 18/18 | 16/18 → 17/18 |
| 독자가 보는 결함, 실행 1회당 (Haiku, S1-S10) | 94.5 | 3.3 → 10.7 | 3.3 → 2.3 | 4.0 → 8.0 |
| 독자가 보는 결함, 실행 1회당 (Sonnet, S1-S10) | 101.0 | 5.0 → 5.3 | 2.0 → 2.3 | 2.7 → 1.0 |
| 홍보 문구 요청에 범위 밖이라고 알림 (S8) | - | 0/6 → 0/6 | 6/6 → 6/6 | 0/6 → 0/6 |
| 검수 요청에 표와 실제 규칙 ID로 답함 (S9) | - | 0/6 → 0/6 | 6/6 → 6/6 | 6/6 → 6/6 |
| 재작성·검수 요청에 스킬 실행 | - | - | - | 18/18 → 29/30 |

어휘 통제 시나리오는 다음과 같다.

| ID | 확인하는 것 |
|---|---|
| S11 | 사내 지침 문서에서 요구, 금지, 권고, 허락, 의무 없음, 가능을 서로 다른 형태로 쓰는가 |
| S12 | 압축된 작업 메모를 보고할 때 병합, 스테이징 배포, 운영 배포의 차이를 "반영", "완료"로 흐리지 않는가 |
| S13 | 부하 테스트 결과를 "안정적" 같은 판정어 대신 수치와 기준으로 쓰는가 |
| S14 | "조치", "정상화", "해당 문서"를 재작성할 때 지어내지 않고 묻는가 |
| S15 | 서버와 설정이 둘 이상인 회의록에서 "해당", "이"로 대상을 흐리지 않는가 |
| S16 | 규칙 목록에 없는 "검토", "마무리", "개선" 같은 말로 결과를 흐리지 않는가 |

독자가 보는 결함은 `evals/score.py`가 센다. 볼드 남용, 엠대시, 짧은 섹션 헤더, 이모지, 서두와 맺음 제안, 명사로 끝나는 목록 항목, 이중 피동, 문체 혼용이 포함된다. 뜻 보존, 결론 위치, S11-S16 통과는 `evals/judge.py`가 블라인드로 판정한다.

이 결과를 읽을 때 다음을 함께 본다.

- 어휘 통제 규칙은 전체판과 스킬 구성에서 효과가 있었다. 짧은판만 쓰는 구성에서는 S11-S15 통과가 거의 늘지 않았다.
- S11-S15는 규칙의 단어 목록과 같은 단어로 만들었다. 그래서 목록 밖 단어로 만든 S16을 따로 쟀다. S16에서는 v1과 v2의 차이가 없었다. v2의 S16 실패 2건 중 1건은 메모에 없는 행위자("개발팀은")를 주어로 더한 경우다. 다른 1건은 메모에 없는 인과("기준에 못 미쳐서 아직 고치지 않았다")를 더한 경우다.
- 규칙의 대상 단어("정상", "완료", "확인")가 S7 원문에 들어 있다. 그래서 S5-S7은 회귀 확인으로만 쓰고, 개선의 근거로 쓰지 않는다.
- S11 판정 기준은 v2 출력을 본 뒤에 고쳤다. 같은 문장을 다르게 판정하는 오류였다. 고친 기준으로 v1과 v2를 모두 다시 판정했다.
- Haiku 짧은판의 결함은 차수마다 9-32건(실행 3회 합계)으로 크게 흔들린다. 15차의 32건 중 26건은 출력 3개에 몰려 있다. 한 검수 출력의 볼드 11개와 두 런북의 결함 15개(명사형 항목 13개 포함)다.
- S12에서는 "QA를 마쳤습니다"처럼 "완료" 대신 "마치다", "끝내다"를 써서 결과를 흐리는 실패가 남았다.
- S15에서는 실행일("10월 23일에 점검한다")을 "기한" 열에 넣는 실패가 남았다. 기한과 실행일을 구분하는 규칙은 아직 없다.
- S7("최대한 짧게 줄여줘")에서는 두 번째 문장의 주어를 빼고 "실패하면"만 쓰는 실패가 남았다. 짧은판만 쓰면 0/6이다.

자세한 기록과 각 차수의 실패, 수정 이유는 [`evals/results/NOTES.md`](evals/results/NOTES.md)에 있다.

## 한계

- K-STE는 공인 표준이 아니다. ASD-STE100을 번역한 것도 아니다.
- 지시문 20어절, 설명문 25어절 기준에는 한국어 근거가 없다. 그래서 검토 신호로만 쓴다.
- 판정자도 Claude다. 사람이 만든 정답과 대조하지 않았다.
- 시나리오는 15개이고 한 사람이 만들었다.
- `agent+short`는 Claude Code 기본 시스템 프롬프트를 쓰므로 다른 조건과 직접 비교할 수 없다.
- 홍보 문구, 창작 글, 영어 글에는 적용하지 않는다.
