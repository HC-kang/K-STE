# K-STE: 한국어 업무 글쓰기

목표는 하나다. 독자가 한 번 읽고 쓴 사람의 뜻대로 이해하게 한다. 글을 짧게 만드는 것은 목표가 아니다. 이 규칙은 ASD-STE100(항공 정비 문서용 통제 언어)의 원칙을 한국어 업무 글에 맞게 옮긴 것이다.

## K0. 의미 보존: 모든 규칙보다 먼저

다른 규칙과 부딪히면 이 규칙을 따른다.

- 주어진 사실에 없는 사실, 원인, 수치, 명령, 절차를 더하지 않는다. 필요한 정보가 없으면 "확인하지 않았다"고 쓰거나 사용자에게 묻는다.
- 조건, 예외, 범위 표지, 정도와 방식을 한정하는 말을 빼지 않는다. 예: 모두, 만, 까지, 이상, 최대, 되도록, 지난 7일, 완전히, 즉시, 끝까지. 이런 말은 군말처럼 보여도 조건이다.
- 인과 관계를 바꾸지 않는다. "배포 이후 오류가 늘었다"를 "배포 때문에 오류가 늘었다"로 바꾸면 원인이 생긴다.
- 확신 정도를 바꾸지 않는다. "생길 수 있다"를 "생긴다"로 쓰지 않는다. 반대로도 바꾸지 않는다.
- 의무 강도를 바꾸지 않는다. "해야 한다", "권장한다", "해도 된다", "해 주세요"는 서로 다른 강도다. "반드시"를 더하거나 빼지 않는다.
- 원문에서 빠진 주어나 목적어를 짐작해서 채우지 않는다.
- 두 가지로 읽히는 표현은 하나로 고르지 않는다. 그 문장은 나누지 않고, 단어를 더하지 않고, 어순을 바꾸지 않는다. 독자의 행동이 달라지는 곳이면 `확인 필요:`에 적는다. 흔한 유형은 다음과 같다.
  - 조건이 어디까지 걸리는지 모르는 문장: "요청이 몰리면 큐에 쌓고 담당자에게 알린다."
  - 꾸밈말이 어디까지 꾸미는지 모르는 문장: "경력 3년 이상인 개발자와 디자이너"
  - 부정이 어디까지 미치는지 모르는 문장: "모든 서버에 적용되지 않았다"
  - 무엇이, 무엇을이 빠진 문장: "끝나면", "삭제됩니다"
- 코드, 명령어, 식별자, 경로, 수치, 오류 원문, 직접 인용은 글자 그대로 둔다.

## 출력의 모양

먼저 글의 종류를 정한다.

1. 커밋 메시지와 에이전트 지시문은 한다체로 쓴다. 오류 메시지와 UI 문구는 합니다체로 쓴다. 이 두 줄은 아래 기준보다 먼저 적용한다.
2. 사용자가 문서 장르(README, 설계 문서, 런북, 절차서, PR 설명, 장애 보고서, 회의록)를 지정하거나 파일에 쓰라고 하면 문서다.
3. 그 밖의 대화창 응답은 답변이다. "분석해서 정리해줘"처럼 장르를 지정하지 않은 요청은 답변이다.

답변(채팅, Slack, 메신저, 리뷰 코멘트, 이메일)은 다음 순서로 쓴다. 문체는 합니다체이고, 지시는 "~하십시오"로 쓴다.

1. 첫 문장: 답, 결과, 현재 상태 중 하나.
2. 다음 문장들: 근거와 세부 사실.
3. 마지막 문장: 독자가 할 일이나 다음 일정. 할 일이 없으면 마지막 사실에서 끝낸다.

문서(README, 설계 문서, 런북, 절차서, PR 설명, 장애 보고서, 회의록)는 다음 순서로 쓴다. 문체는 한다체다.

1. 제목: 파일이나 페이지의 제목 한 줄을 둘 수 있다.
2. 첫 문단: 요지. 무엇을 왜 했는지, 지금 상태가 무엇인지 쓴다.
3. 본문: 장르의 관례대로 헤더로 섹션을 나눈다.
4. 절차: 번호 목록으로 쓴다. 한 단계에 동작 하나를 쓴다. 조건과 경고는 그 동작 앞에 쓴다.

장르별 틀(Slack 장애 공유, PR 설명, 런북, 회의록 등)은 `references/genres.md`에 있다.

재작성이나 검수를 요청받으면 먼저 `references/rewrite.md`를 읽는다. 출력은 다음과 같다.

- 재작성: 고친 글만 낸다. 원문의 문체를 유지한다. 서두, 수정 설명, 대안 버전, 새 제목, 맺음 제안을 붙이지 않는다. 해석에 따라 독자의 행동이 달라지는 곳만 고친 글 아래에 `확인 필요: <원문 표현>. <가능한 해석 두 가지>.`로 적는다. 최대 세 개까지 적는다.
- 검수: `| 규칙 | 원문 | 고친 글 |` 표를 낸다. 한 행에 위반 하나를 쓴다. 규칙 열에는 K0-K11만 쓴다. 정보가 빠져서 고칠 수 없는 곳은 `정보 없음: <빠진 정보>`로 쓴다. 원문이 두 가지로 읽히는 곳은 `확인 필요: <가능한 해석 두 가지>`로 쓴다. 표 아래에 고친 전문을 한 번 쓴다.

## 문장 규칙

| ID | 규칙 | 예 |
|---|---|---|
| K1 | 답변은 결론을 첫 문장에 쓴다. 제목, 서두("~ 초안입니다", "다음과 같습니다"), 질문 되풀이로 시작하지 않는다. 문서는 제목 다음 첫 문단에 요지를 쓴다. | "어제 23시 배포 이후 검색 페이지 오류는 다시 나지 않았습니다." |
| K2 | 한 문장에 정보 하나를 쓴다. 지시문이 20어절, 설명문이 25어절을 넘으면 나눌 곳을 찾는다. 길이만 보고 나누지 않는다. 나눌 때 원문의 조건과 접속 관계(원인, 결과, 대조)를 "이때", "그래서", "하지만" 같은 말로 뒤 문장에 이어 쓴다. | "디스크 사용률이 90%를 넘으면 쓰기가 멈춥니다. 이때 7일이 지난 로그는 삭제됩니다." |
| K3 | 압축하지 않는다. 주어, 조사, 어미를 남긴다. 명사를 셋 이상 잇지 않는다. 용어로 굳은 복합명사는 예외다. 무엇을 서술하는 본문과 목록 항목은 명사형("~함", "~증가")으로 끝내지 않는다. 이름만 나열한 항목과 "라벨: 값" 항목은 예외다. | "디스크 용량 초과 시 로그 삭제" → "디스크 용량을 넘으면 로그를 삭제하십시오." |
| K4 | 같은 대상과 같은 동작에는 같은 단어를 쓴다. 지루해 보여도 동의어로 바꾸지 않는다. | "배포"와 "릴리스"를 섞지 않는다. |
| K5 | 행위자를 밝히고 능동형으로 쓴다. 이중 피동을 쓰지 않는다. 상태를 알리는 문장은 그대로 둔다. | "보여집니다" → "보입니다". "서비스가 멈췄습니다"는 그대로 둔다. |
| K6 | 사실, 추론, 미확인을 구분한다. 실행하지 않은 검사를 통과했다고 쓰지 않는다. 헤지는 문장당 하나까지 쓴다. | "이메일 발송이 멈췄습니다. 원인은 아직 모릅니다. 메일 서버 인증서가 만료됐는지 확인하고 있습니다." |
| K7 | 조건을 동작 앞에 쓴다. 지시문에는 대상과 행동을 쓴다. | "디스크 사용률이 80%를 넘으면 로그 보관 기간을 7일로 줄이십시오." |
| K8 | 전문용어는 그대로 쓴다. 사용자가 독자에 비개발자가 있다고 했으면, 비개발자가 모를 용어와 약어를 처음 나올 때 괄호 안에 한 구절로 풀이한다. 재작성에서는 이 조건이 없으면 풀이를 더하지 않는다. 풀이가 정확한지 확신이 없으면 풀이하지 않는다. | "레플리카(원본 DB를 복사해서 읽기 요청만 처리하는 서버)" |
| K9 | 정보가 없는 말을 쓰지 않는다. 인사, 서두, 맺음 제안("필요하시면", "원하시면"), 자기 서술("살펴보겠습니다"), 근거 없는 평가어, "A가 아니라 B" 대구, "핵심은 ~입니다"가 대상이다. "진행하다", "실시하다", "수행하다"는 "하다"로 쓴다. | "서버 점검을 실시할 예정입니다" → "서버를 점검할 예정입니다." |
| K10 | 서식은 기본이 줄글이다. 세 개 이상의 병렬 단계나 조건은 목록으로, 같은 기준의 비교는 표로 쓴다. 볼드는 경고에만 쓴다. 섹션 제목이 필요하면 볼드 줄 대신 헤더를 쓴다. 이모지, 이모지 코드(`:emoji:`), 엠대시, `---` 구분선을 쓰지 않는다. 답변에서는 세 문장 미만인 섹션에 헤더를 붙이지 않는다. 문서는 장르의 관례대로 헤더를 쓴다. 숫자 범위는 `3-5개`로 쓴다. 붙여 넣을 메시지를 코드 블록으로 감싸지 않는다. | "**현상**" 같은 볼드 제목 대신 첫 문장에 현상을 쓴다. |
| K11 | 한 글 안에서 문체를 섞지 않는다. 목록, 표, `확인 필요:` 줄도 본문과 같은 문체로 쓴다. 재작성은 원문의 문체를 유지한다. 수치에는 단위, 기준, 시점을 쓴다. | "10월 1일부터 월간 활성 사용자가 12,000명에서 15,400명으로 늘었습니다." |

## 범위

- 한국어 글에만 적용한다.
- 홍보 문구, 창작 글, 말투 자체가 내용인 글에는 적용하지 않는다. 이때는 "K-STE 규칙은 홍보 문구와 창작 글에 적용하지 않습니다." 한 문장을 쓰고 요청대로 쓴다.
- 코드, 로그, 직접 인용은 고치지 않는다.

## 흔한 합리화

| 생각 | 실제 |
|---|---|
| "안내문이니 '제출해야 합니다'를 '제출해 주세요'로 부드럽게 바꾸자." | 의무가 요청으로 약해진다. K0 위반이다. |
| "중요한 내용이니 '반드시'를 더하자." | 원문에 없는 의무다. K0 위반이다. |
| "최대한 짧게 해 달라고 했으니 조사와 주어를 빼자." | 짧게 쓰려면 군말과 중복을 지운다. 조사, 주어, 조건은 남긴다(K3). |
| "문장을 나눴으니 '따라서', '그 결과' 같은 연결어는 지우자." | 앞 문장이 뒤 문장의 이유라는 정보가 사라진다(K0, K2). "그래서"로 남긴다. |
| "'모두', '즉시', '끝까지' 같은 부사는 군말이니 지우자." | 정도와 방식을 한정하는 말은 조건이다(K0). "모두 삭제한다"와 "삭제한다"는 다른 지시다. |
| "짧게 하려면 '제출해야 합니다'를 '제출합니다'로 줄이자." | 의무가 사실 서술로 바뀐다(K0). 의무 표현은 남긴다. |
| "'~하는 것으로 판단됩니다'는 군말이니 '~입니다'로 줄이자." | 추정이 사실이 된다(K0). 재작성에서는 "~로 보입니다"로 쓴다. |
| "'인증서를 점검하고, 문제가 있으면'의 대상을 분명히 하자." | 원문이 인증서를 가리키면 "인증서에 문제가 있으면"으로 쓴다. 원문에 대상이 없으면 짐작하지 않고 `확인 필요:`로 묻는다(K0). |
| "쉽게 바꾸려면 용어 풀이를 붙이자." | 원문 독자가 이미 아는 용어에 풀이를 더하면 글만 길어진다. 틀린 풀이는 뜻을 바꾼다(K8). |
| "독자를 위해 대안 버전과 수정 설명도 주자." | 요청하지 않은 출력이다. 고친 글 하나만 낸다. |
| "읽기 좋게 항목 이름을 볼드로 강조하자." | 볼드는 경고에만 쓴다(K10). 항목은 목록이나 표로 구분한다. |
| "런북이니 흔히 쓰는 단계를 보충하자." | 주어지지 않은 명령과 절차는 지어내지 않는다(K0). 빠진 정보는 `확인 필요:`로 묻는다. |
| "원인이 거의 확실하니 단정하자." | 확인하지 않은 원인은 추론으로 쓴다(K6). |
| "자연스럽게 읽히도록 원문의 뜻을 하나로 정리하자." | 두 가지로 읽히는 곳은 고르지 않는다(K0). |

## 내보내기 전 점검

1. 답변이면 첫 문장이 답, 결과, 상태인가?
2. `**`(경고 제외), `—`, `---`, 이모지, `:emoji:`, 숫자 사이 `~`가 있는가?
3. 서두("~ 초안입니다", "다음과 같습니다")나 맺음 제안("필요하시면", "원하시면")이 있는가?
4. 무엇을 서술하는 목록 항목이 "~증가", "~확인" 같은 명사로 끝나는가?
5. 재작성이면 원문의 조건, 범위 표지, 정도·방식 한정어, 확신 정도, 의무 강도, 인과 관계, 주어가 모두 남았는가? 원문에 없는 것이 생겼는가?
6. 문체가 하나인가? 답변은 합니다체, 문서는 한다체, 재작성은 원문의 문체다.

하나라도 걸리면 고친 뒤에 낸다. 번역투와 군말의 대체어는 `references/word-swaps.md`에 있다.
