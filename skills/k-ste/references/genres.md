# 장르별 틀

모든 장르에 `SKILL.md`의 K0-K11을 적용한다. 아래는 장르마다 다른 순서와 문체다. 예문의 이름, 수치, 명령은 설명용이다. 실제 글에는 사용자가 준 사실만 쓴다.

## 답변 (채팅, 메신저)

문체: 합니다체. 순서: 답 → 근거 → 할 일.

- 단순 사실이나 상태: 1-3문장.
- 설명이나 추천: 답 한 문장, 근거 2-4문장.
- 원인 진단이나 결정: 결론, 근거, 영향, 다음 행동.

두 문장짜리 답에 헤더나 목록을 쓰지 않는다.

## 비개발자에게 하는 설명

문체: 합니다체. 순서: 독자에게 달라지는 것 → 동작 원리 → 비용이나 위험.

- 첫 문장에 독자의 업무나 고객에게 달라지는 점을 쓴다.
- 기술 용어는 처음 나올 때 괄호 안에 한 구절로 풀이한다.
- 비유는 한 번만 쓴다. 비유를 쓴 뒤에는 실제 동작을 한 문장으로 쓴다.

예: "검색 인덱스(검색을 빠르게 하려고 미리 정리해 둔 목록)를 매시간 갱신하면, 새 상품이 등록 후 1시간 안에 검색됩니다. 지금은 인덱스를 하루에 한 번 새벽 3시에 갱신해서, 오늘 등록한 상품은 내일 아침부터 검색됩니다."

## Slack 상태 공유와 장애 공유

문체: 합니다체. 순서: 현재 상태 → 영향 → 확인한 사실 → 모르는 것 → 다음 업데이트.

- 첫 문장에 무엇이 언제부터 어떤 상태인지 쓴다. 제목 줄을 따로 두지 않는다.
- 수치는 "이전 값에서 현재 값으로"와 시각을 함께 쓴다.
- 원인을 모르면 "원인은 아직 모릅니다."라고 쓴다. 확인 중인 가설은 "~인지 확인하고 있습니다."로 쓴다.
- 담당자와 다음 업데이트 시각으로 끝낸다.

예: "09:40 KST부터 사내 위키 검색이 동작하지 않습니다. 문서 열람과 편집은 정상입니다. 원인은 아직 모릅니다. 09:30에 끝난 검색 엔진 업그레이드가 원인인지 확인하고 있습니다. 담당자는 이서연이고, 다음 업데이트는 10:30에 합니다."

## 장애 보고서 (사후 분석)

문체: 한다체. 순서: 요약 → 영향 → 타임라인 → 원인 → 조치 → 재발 방지.

- 요약은 세 문장 이내로 쓴다. 무엇이, 언제, 얼마나 영향을 줬는지 쓴다.
- 타임라인은 시각과 사건을 단순 과거형으로 쓴다.
- 확인한 원인과 추정한 원인을 구분한다.
- 재발 방지 항목에는 담당자와 기한을 쓴다. 정보가 없으면 "담당자 정보 없음"이라고 쓴다.

## PR 설명

문체: 한다체. 순서: 무엇을 바꿨는지 → 왜 → 검증 → 남은 일.

- 첫 문장에 변경 내용을 한 문장으로 쓴다.
- 검증 절에는 실행한 검사와 실행하지 않은 검사를 나눠 쓴다. 실행하지 않은 검사를 체크박스로 체크하지 않는다.
- 요청하지 않은 조언("이슈를 자동으로 닫지 않으려면...")을 덧붙이지 않는다.

예: "CSV 내보내기에서 쉼표가 들어간 상품명을 큰따옴표로 감싸도록 고쳤다. 쉼표 때문에 열이 밀려서 가격이 상품명 열에 들어갔다. 단위 테스트는 로컬에서 통과했다. 운영 환경의 내보내기는 아직 확인하지 않았다."

## 커밋 메시지

- 제목: 무엇을 했는지 한 줄로 쓴다. 저장소의 기존 관례(영어, Conventional Commits 등)가 있으면 따른다.
- 본문: 한다체. 왜 바꿨는지 쓴다.

## 런북과 절차서

문체: 한다체. 순서: 목적 한 문장 → 사전 확인 → 절차 → 결과 확인 → 기록.

- 한 단계에 동작 하나를 쓴다.
- 조건과 경고는 그 동작 앞에 쓴다. 되돌릴 수 없는 동작 앞에는 **경고:**를 붙인다. 볼드는 이 경고에만 쓴다.
- 명령은 코드 블록으로 쓴다. 사용자가 주지 않은 명령, 호스트, 연락처는 지어내지 않는다. 필요하면 "확인 필요:"로 적는다.

예:
1. 교체할 인증서의 만료일이 기존 인증서보다 늦은지 확인한다.
2. **경고:** 새 인증서의 도메인 목록에 `api.example.com`이 없으면 교체하지 않고 보안 담당자에게 연락한다.
3. 도메인 목록이 맞으면 다음 명령으로 인증서를 교체한다.

## 회의록

문체: 한다체. 순서: 결정 사항 → 할 일(담당자, 기한) → 논의 요약 → 미결 사항.

- 결정 사항을 맨 위에 쓴다.
- 할 일은 "담당자가 무엇을 언제까지 한다." 형태의 문장으로 쓴다.

## 오류 메시지와 UI 문구

문체: 합니다체. 순서: 무슨 일이 생겼는지 → 독자가 할 일.

- "오류가 발생했습니다"만 쓰지 않는다. 무엇이 실패했는지 쓴다.
- 버튼 이름은 동작을 쓴다. "확인" 대신 "삭제", "저장"처럼 쓴다.

예: "파일이 20MB를 넘어서 올리지 못했습니다. 20MB 이하로 줄여서 다시 올리십시오."

## 에이전트 지시문 (프롬프트, AGENTS.md)

문체: 한다체. 순서: 목적 → 규칙 → 출력 형식.

- 한 문장에 지시 하나를 쓴다.
- 조건을 지시 앞에 쓴다. 문장 끝에 붙은 조건은 모델이 놓친다.
- "~하는 것이 좋다"는 모델이 선택 사항으로 읽는다. 필수이면 "~한다", 선택이면 지운다.
- 같은 동작에는 같은 동사를 쓴다. "확인", "검증", "체크"를 섞으면 모델이 세 가지 다른 작업으로 읽는다.
